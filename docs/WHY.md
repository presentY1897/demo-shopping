# 기술적 의사결정

> **초안입니다.** TASK-0100 F5 의 여섯 주제를 「문제 → 선택지 → 판단 근거 → 결과」로
> 다시 쓴 것입니다. `docs/decisions/DECISIONS.md` 는 결정의 **목록**이고, 이 문서는
> 그중 설명할 값이 있는 것들의 **이유**입니다.

이 프로젝트에서 실제로 갈림길이었던 여섯 가지를 적었습니다. 각 항목은 「무엇이
문제였나 → 어떤 길이 있었나 → 왜 그 길을 골랐나 → 그래서 무엇이 달라졌나」 순서입니다.

---

## 1. 왜 주문을 두 단으로 나눴나

### 문제

한 번의 결제로 **여러 판매자의 물건**을 살 수 있습니다. 그런데 그 뒤에 일어나는 일은
판매자마다 따로입니다 — A는 오늘 보내고 B는 품절이라 취소하고, 배송비도 각자 매기고,
정산도 각자 받습니다.

주문을 한 덩어리로 두면 「이 주문은 배송중인가」라는 질문에 답할 수 없습니다. 절반은
배송중이고 절반은 취소됐기 때문입니다.

### 선택지

| 길 | 어떻게 되나 |
| --- | --- |
| 주문 하나에 상태 하나 | 「부분 배송중」 같은 상태가 계속 늘어난다. 두 판매자면 상태가 곱해진다 |
| 판매자별로 **주문을 따로 만든다** | 결제가 쪼개진다. 카드 승인이 판매자 수만큼 일어나고, 하나만 실패하면 수습이 어렵다 |
| **결제는 하나, 상태는 판매자별로** | 표가 하나 늘어난다 |

### 판단 근거

**돈은 한 번 움직이고, 물건은 여러 번 움직입니다.** 그 둘의 수명이 다르므로 표도
달라야 합니다.

`Order` 는 결제·수령인·주문번호를 갖고 한 번만 만들어집니다. `SellerOrder` 는 판매자
몫이고 자기 상태(`결제완료 → 주문확인 → 배송중 → 배송완료 → 구매확정`)와 자기
운송장을 갖습니다. 취소·반품도 `SellerOrder` 단위입니다.

### 결과

- 「이 주문은 어디까지 왔나」에 **판매자별로** 답합니다.
- 부분 취소가 특수 사례가 아니라 **기본 구조**가 됐습니다.
- 정산이 자연스럽게 붙습니다 — `SellerOrder` 가 곧 정산의 한 줄입니다.
- 대가: 화면이 「주문」과 「배송」을 구분해서 보여 줘야 합니다. 구매자에게는 주문
  하나로 보이지만 그 안에 배송이 여럿입니다.

## 2. 왜 속성을 EAV 대신 하이브리드로 했나

### 문제

카테고리마다 필요한 정보가 다릅니다. 코트는 색상·소재·핏이 필요하고, 신발은 사이즈
체계가, 가방은 수납이 필요합니다. **그리고 그 목록은 운영자가 늘립니다** — 코드를
고치지 않고요.

### 선택지

| 길 | 어떻게 되나 |
| --- | --- |
| 카테고리마다 컬럼 | 새 카테고리마다 마이그레이션. 운영자가 못 늘린다 |
| 순수 EAV (정의도 값도 표) | 상품 20개를 읽는 데 조인이 폭증한다. 속성 10개면 200줄을 모아 20줄로 접어야 한다 |
| **정의는 표, 값은 JSONB** | DB 가 값의 형식을 못 지킨다 |

### 판단 근거

**정의와 값에 필요한 것이 서로 다릅니다.**

정의(`AttributeDefinition`)는 **읽어서 화면을 만들어야** 합니다 — 상품 등록 폼과 검색
필터가 이 정의에서 자동으로 생성됩니다. 그러려면 표여야 합니다.

값은 **통째로 읽고 통째로 씁니다.** 「색상이 블랙인 상품」을 DB 에서 찾을 일이 없습니다 —
그것은 검색 엔진이 하는 일입니다. DB 는 상품 한 줄을 꺼낼 때 값을 함께 꺼내면 됩니다.

### 결과

- 운영자가 관리자 화면에서 속성을 추가하면 **등록 폼과 검색 필터가 함께 바뀝니다.**
  코드 변경이 없습니다.
- 상품 목록 조회에 조인이 늘지 않습니다.
- 대가: **DB 가 값을 검사하지 못합니다.** JSONB 안은 데이터베이스에게 그냥 문서입니다.
  그래서 값의 타입·필수·선택지는 애플리케이션이 정의에서 zod 스키마를 **동적으로 만들어**
  검사합니다. 이 프로젝트에서 「마지막 방어선은 DB」라는 원칙이 깨지는 유일한 자리이고,
  그 사실을 `erd.md` 에 적어 두었습니다.

## 3. 왜 재고를 예약 방식으로 했나

### 문제

주문서를 열어 놓고 결제까지 몇 분이 걸립니다. 그 사이에 다른 사람이 마지막 하나를
사 가면, 결제를 마친 사람에게 「없다」고 말해야 합니다. **돈은 이미 받은 뒤에요.**

### 선택지

| 길 | 어떻게 되나 |
| --- | --- |
| 결제 성공에 재고 차감 | 위의 문제가 그대로 남는다 |
| 주문서를 열 때 차감 | 안 사고 떠난 사람의 재고가 영영 잠긴다 |
| **주문서를 열 때 예약, 결제에 확정, 안 하면 만료** | 만료를 돌보는 배치가 필요하다 |

### 판단 근거

**재고에는 「있다」와 「내 것이다」가 따로 있어야 합니다.** 상품에 `stock`(총량)과
`reserved`(잡혀 있는 양)를 두고, 살 수 있는 수량은 그 차입니다.

예약을 만드는 것은 조건부 갱신 한 문장입니다 — `UPDATE ... WHERE stock - reserved >= 수량`.
경합이 나면 갱신이 0줄이고, 그것이 곧 품절입니다. 잠금을 따로 걸지 않습니다.

### 결과

- 결제를 마친 사람에게 「없다」고 말하는 일이 없습니다.
- 만료된 예약은 배치가 풀고, 그 배치가 멈춰 있으면 대시보드가 **「몇 분째 안 돌았다」**를
  보여 줍니다 — 「0건 처리」와 「안 돌았다」는 다른 말입니다.
- 재고 변화는 전부 원장(`StockLedger`)에 남습니다. 현재값은 원장의 결과이고, 정합성
  배치가 둘을 대조합니다.

## 4. 왜 결제 프로바이더를 추상화했나 (가상 카드의 역할)

### 문제

포트폴리오 사이트에서 **실제 돈이 움직이면 안 됩니다.** 그런데 결제를 흉내만 내면
「결제가 붙어 있다」고 말할 수 없습니다 — 승인·취소·부분 환불·잔액 부족 같은 것이
실제로 일어나야 합니다.

### 선택지

| 길 | 어떻게 되나 |
| --- | --- |
| 결제를 아예 빼고 「주문 완료」로 끝낸다 | 환불·정산이 전부 가짜가 된다 |
| 실제 PG 만 붙인다 | 방문자가 카드번호를 넣어야 한다. 아무도 안 한다 |
| **결제를 인터페이스로 두고 구현을 둘** | 인터페이스를 설계해야 한다 |

### 판단 근거

**결제에서 도메인이 필요로 하는 것은 네 가지뿐입니다** — 승인, 취소, 부분 취소, 그리고
그 결과의 기록. 그 넷이면 주문·환불·정산이 전부 돌아갑니다.

그래서 가상 카드가 **진짜 결제 수단**입니다. 한도가 있고, 잔액이 줄고, 부족하면 거절하고,
환불하면 돌아옵니다. 거래는 원장에 남습니다. 실제 PG(토스페이먼츠)는 같은 인터페이스의
다른 구현이고, 결제창까지 실제로 뜹니다.

### 결과

- 방문자가 **아무것도 입력하지 않고** 결제·환불·부분 취소를 전부 겪습니다.
- 환불 계산이 진짜입니다 — 카드 잔액이 실제로 그만큼 돌아옵니다. E2E 검사가 그
  숫자를 잽니다.
- 대가: 가상 카드가 「실제 카드가 아니다」라는 것을 **화면이 계속 말해야** 합니다.
  카드번호를 9999 로 시작하게 한 것도 그래서입니다.

## 5. 왜 검색을 Meilisearch 로 했나

### 문제

상품 검색에 필요한 것은 **오타 보정, 자동완성, 패싯 필터**입니다. 「코투」로 검색해도
코트가 나와야 하고, 색상별 개수가 필터 옆에 붙어야 합니다.

### 선택지

| 길 | 어떻게 되나 |
| --- | --- |
| PostgreSQL 전문 검색 | 한국어 형태소 분석이 없다. 오타 보정도 직접 만들어야 한다 |
| Elasticsearch | 할 수 있는 일이 가장 많다. 메모리를 가장 많이 먹고 설정이 가장 길다 |
| **Meilisearch** | 오타 보정과 패싯이 기본값. 대신 세밀한 튜닝 여지가 적다 |

### 판단 근거

**이 프로젝트의 검색은 상품 몇만 건입니다.** Elasticsearch 가 잘하는 것 — 수억 건, 복잡한
집계, 클러스터 — 은 여기 없는 문제입니다. 그리고 무료 인스턴스에서 돌려야 합니다.

Meilisearch 는 오타 보정과 패싯이 설정 없이 동작하고, 색인 정의가 JSON 한 덩어리입니다.
속성 정의가 바뀌면 필터 가능한 필드 목록도 함께 바뀌어야 하는데, 그 갱신이 한 줄입니다.

### 결과

- 오타 보정·자동완성·패싯이 **처음부터** 동작합니다.
- 색인은 **비동기**입니다. 상품을 저장한 그 순간 검색에 나오지는 않고, 대시보드가
  「색인 대기 몇 건, 가장 오래된 것이 언제」를 보여 줍니다.
- 대가: 검색이 죽어도 화면은 살아야 합니다. 카테고리 화면은 검색 엔진을 거치므로,
  그쪽이 답하지 않을 때 **빈 목록이 아니라 「지금 검색을 쓸 수 없다」**고 말합니다.

## 6. 부분 환불의 안분 계산을 어떻게 풀었나

### 문제

3만원짜리와 2만원짜리를 함께 사면서 5천원 쿠폰을 썼습니다. 2만원짜리만 취소하면
얼마를 돌려줘야 할까요?

**2만원이 아닙니다.** 그 상품에 붙어 있던 할인 2천원을 빼서 **1만 8천원**입니다.

### 선택지

| 길 | 어떻게 되나 |
| --- | --- |
| 환불할 때 다시 계산한다 | 그 사이 쿠폰 정책이 바뀌면 값이 달라진다 |
| 할인을 주문 단위로만 갖는다 | 위 질문에 답할 수 없다 |
| **주문 시점에 항목별로 나눠 저장한다** | 나눗셈의 나머지를 어떻게 할지 정해야 한다 |

### 판단 근거

**환불은 과거를 되돌리는 일이므로 과거의 숫자로 해야 합니다.** 그래서 주문을 만드는
순간 각 항목이 짊어진 할인액을 계산해 함께 저장합니다.

나눗셈에서 원 단위가 남습니다. 5천원을 3:2 로 나누면 3000 + 2000 으로 딱 떨어지지만,
7원을 3:2 로 나누면 4 + 2 = 6 이고 1원이 뜹니다. **그 1원을 버리면 합계가 안 맞습니다** —
환불을 다 해도 결제금액에 못 미칩니다. 그래서 잔여는 금액이 가장 큰 항목에 몰아
넣습니다. 규칙이 하나여야 어느 쪽에서 계산해도 같은 답이 나옵니다.

### 결과

- 부분 취소가 **덧셈과 뺄셈**이 됐습니다. 항목의 안분액을 빼면 끝입니다.
- 합계가 언제나 보존됩니다 — 모든 항목을 환불하면 결제금액과 정확히 같습니다.
- 계산은 `packages/shared` 의 순수 함수 한 벌이고, 서버와 화면이 **같은 코드**를
  씁니다. 두 벌이면 어느 날 갈립니다.
- 이 규칙은 `docs/design/pricing.md` 에 있고, 배송비 부담(누구 잘못인가)까지 같은
  문서가 다룹니다.

## 이 여섯 가지에 공통으로 흐르는 것

**1. 잔액이 있는 것에는 원장을 둔다.** 재고·적립금·가상 카드가 그렇습니다. 현재값은
원장의 결과이고, 둘이 어긋났는지 대조하는 배치가 따로 있습니다. **검출만 하고 고치지
않습니다** — 원인을 모르는 채 값을 고치면 다음에 같은 자리가 또 어긋나도 조용히
덮어써 버립니다.

**2. 마지막 방어선은 DB 다.** 애플리케이션이 막는 것은 전부 CHECK 제약이 한 번 더
막습니다. 유일한 예외가 JSONB 안의 속성 값이고, 그 사실을 문서에 적어 두었습니다.

**3. 「없음」과 「0」은 다르다.** 재지 못한 것을 0으로 두면 아무것도 안 한 대상이 가장
좋아 보입니다. 배치가 한 번도 안 돈 것과 0건 처리한 것도 다릅니다.
