# TASK-0118: 콜드 스타트 502 · 재시도 예산을 경과 시간으로

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M02 배포 파이프라인 |
| 상태 | 완료 |
| 작성일 | 2026-09-09 |
| 브랜치 | `feature/cold-start-502` |
| 선행 작업 | TASK-0101 |

## 1. 목적

배포된 shop 이 API 를 부르지 못한다. 브라우저 콘솔은 **CORS 위반**이라고 말하지만 CORS 설정은
멀쩡하다. 실제로 일어난 일은 **콜드 스타트**이고, 그것은 TASK-0101 이 이미 대비한 상황이다.

그런데도 화면이 실패로 떨어진다. 이유는 TASK-0101 이 세운 **Render 동작 모델이 실제와 다르기
때문**이다. 그 모델은 대역(`sleepingInstance`)에도 그대로 들어가 있어서, 프로덕션이 망가진 동안
`cold-start-replay` 는 세 번 다 초록색이었다.

이 TASK 는 모델을 실측으로 교체하고, 그 위에서 재시도 예산을 다시 잡는다. 끝나면 **잠든 API 로
들어온 첫 방문자가 버튼을 누르지 않고 정상 화면에 도달한다** — TASK-0101 이 F3 으로 약속했지만
프로덕션에서는 지켜지지 않고 있는 것.

## 2. 범위

### 포함
- 잠든 인스턴스로 간 요청이 **실제로** 어떻게 실패하는지 실측 (4.1)
- `packages/api-mocks` 의 `sleepingInstance` 를 실측 동작으로 교체 (4.6)
- 재시도 예산의 단위를 **시도 횟수 → 경과 시간**으로 (4.4 · 4.5)
- 세 앱(`shop` · `seller` · `admin`)에 동일 적용 — 정책 코드가 셋에 복사돼 있다 (TASK-0101 R9)
- `cold-start-replay` 를 새 모델로 재실행하고 측정값을 기록
- README 의 콜드 스타트 서술과 TASK-0101 4.4 · 6.3 을 실측으로 개정

### 제외 (이번에 하지 않는 것)
- **유료 플랜 전환** — 비용 결정은 이 TASK 의 것이 아니다
- **cron 핑** — TASK-0101 4.8 이 750h 산술로 이미 닫았다. 오늘의 실측은 그 산술을 건드리지 않으므로
  결정을 다시 열지 않는다
- **검색 엔진 병렬 웨이크업** — TASK-0101 R5, TASK-0009 소유
- **`useApiWake` 공통화** — TASK-0101 R9. 이 TASK 는 세 벌을 **같은 값으로 고칠 뿐** 한 벌로 합치지
  않는다. 합치는 일은 그 자체로 세 앱의 렌더 경로를 건드리고, 지금은 프로덕션이 깨져 있다
- **API · 인프라 변경** — 서버는 정상이다. 고칠 것은 전적으로 클라이언트 재시도 정책이다

## 3. 요구사항

### 기능 요구사항
- [ ] 잠든 API 로 진입한 방문자가 **사람 개입 없이** 정상 화면에 도달한다
- [ ] 502 가 즉시 돌아와도 재시도 예산이 조기 소진되지 않는다
- [ ] 15초 2단계 안내가 **실제로 노출된다** — 지금은 그 전에 실패로 떨어져 볼 수 없다
- [ ] 콜드 스타트 1회당 API 요청 수에 **상한이 있다** (TASK-0009 R8)
- [ ] 대역이 실측 동작을 재현한다 — 정책이 다시 어긋나면 `cold-start-replay` 가 빨개진다

### 비기능 요구사항
- 콜드 스타트 1회당 요청 수 상한을 문서에 숫자로 적는다
- 부팅이 끝난 뒤 방문자가 그것을 모른 채 더 기다리는 시간의 상한을 정한다 (4.5)

## 4. 설계

### 4.1 실측 — 잠든 인스턴스는 요청을 붙잡지 않는다

2026-09-09, 배포된 서비스에 직접 측정했다. 관측 창은 `api.demo-shopping.com` 이 실패하고 있다는
신고를 받은 직후다.

| 시각 (UTC) | 요청 | 결과 | 소요 |
| --- | --- | --- | --- |
| 10:28:19 | `OPTIONS /api/v1/health` (Origin: shop) | **502** · `x-render-routing: dynamic-paid-error` | 0.54초 |
| 10:28:20 | `GET /api/v1/health` | **502** · 같음 | 0.24초 |
| 10:28:2x ~ | 같은 요청 3회 | **502** 3회 | 0.24 · 0.67 · 0.24초 |
| 10:31:00 | `GET /api/v1/health` (onrender 호스트 직접) | **200** · `uptime: 170` | 1.38초 |
| 10:31:28 | `GET /api/v1/health` (커스텀 도메인) | **200** · CORS 헤더 정상 | — |
| 10:31:29 | `OPTIONS /api/v1/search` | **204** · preflight 정상 | — |

**두 가지가 확정된다.**

1. **Render 는 자는 인스턴스로 온 요청을 붙잡지 않는다.** 0.24초에 502 를 돌려준다. 응답 본문은
   Render 엣지가 만든 HTML 이고 `server: cloudflare` · `x-render-routing: dynamic-paid-error` 가
   붙어 있다 — 우리 앱을 지나지 않았다.
2. **CORS 설정은 정상이다.** 인스턴스가 깨어난 뒤 같은 커스텀 도메인이
   `access-control-allow-origin: https://shop.demo-shopping.com` 을 정확히 돌려준다.
   `render.yaml` 의 `CORS_ORIGINS` 도 `configure-app.ts` 의 `corsOptionsFor` 도 손댈 것이 없다.

`uptime: 170` 은 10:31:00 시점에 프로세스가 170초째였다는 뜻이고, 역산하면 10:28:10 경 기동이
시작됐다 — **첫 502 를 받은 시각과 같다.** 즉 첫 요청이 기동을 유발했고, 그 뒤 약 3분 동안 엣지는
502 를 돌려주고 있었다. `startCommand` 가 `db:deploy` 를 먼저 돌리고 Render 자체 헬스 프로브가
통과해야 라우팅이 열리므로, 이 구간이 502 창이다.

> **정확한 502 창 길이는 6.3 에서 잰다.** 위 관측은 창의 존재와 즉시 실패를 확정하지만, 시작과 끝을
> 모두 담지는 못했다 — 창 도중에 관측을 시작했다.

**이것은 TASK-0101 R8 을 부분적으로 닫는다.** 그 TASK 는 49분 관찰 동안 spin down 을 한 번도 보지
못했고, "무언가가 서비스를 계속 깨워 두고 있다"를 열린 위험으로 남겼다. 오늘 서비스는 **분명히
잠들어 있었다.** 상시 가동 가설은 최소한 항상 참은 아니다. 인스턴스 시간 사용량 확인은 여전히
소유자 작업이므로 R8 자체는 TASK-0009 에 남는다.

### 4.2 왜 "CORS 정책 위반"으로 보이는가

이 절은 다음에 같은 콘솔을 보는 사람을 위한 것이다. **에러 메시지가 원인을 가리키지 않는다.**

```
Access to fetch at 'https://api.demo-shopping.com/api/v1/health'
from origin 'https://shop.demo-shopping.com' has been blocked by CORS policy:
Response to preflight request doesn't pass access control check:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

브라우저는 사실만 말하고 있다. 502 HTML 에는 정말로 `Access-Control-Allow-Origin` 이 없다. 다만
**그것이 없는 이유가 CORS 설정이 아니라 서버가 응답하지 않았다는 것**이다. 애플리케이션이
응답을 만들지 못하면 CORS 헤더를 붙일 주체 자체가 없다.

| 콘솔이 말하는 것 | 실제 |
| --- | --- |
| CORS 정책에 막혔다 | 사실. 502 에 CORS 헤더가 없다 |
| `Access-Control-Allow-Origin` 이 없다 | 사실. Render 엣지의 에러 페이지다 |
| **CORS 설정이 틀렸다** | **거짓.** 깨어 있으면 정확한 헤더가 온다 |

판별법은 하나다 — **오리진 없이 부른다.** CORS 는 브라우저의 규칙이므로 `curl` 은 그 층을 지나지
않고 진짜 상태 코드를 보여 준다.

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://api.demo-shopping.com/api/v1/health
# 502 → 서버 문제. CORS 설정을 보지 말 것
# 200 → 그때 비로소 CORS 설정을 의심한다
```

이 두 줄을 README 의 문제 해결 절에 넣는다 (6.4).

### 4.3 예산이 4초 만에 사라진다

TASK-0101 4.4 는 재시도 예산을 143초로 설계했다. 그 계산은 **각 시도가 자기 타임아웃을 끝까지
쓴다**는 전제 위에 있고, 그 전제는 `wake-policy.ts` 주석에 그대로 적혀 있다.

> Render holds a request aimed at a sleeping instance open until the instance answers

4.1 이 그것을 뒤집는다. 시도는 타임아웃이 아니라 **0.3초**에 끝난다.

| | 설계가 가정한 것 | 실제 |
| --- | --- | --- |
| 시도 1 | 10초 소모 | **0.3초** (502) |
| 백오프 | 1초 | 1초 |
| 시도 2 | 40초 소모 | **0.3초** (502) |
| 백오프 | 2초 | 2초 |
| 시도 3 | 90초 소모 | **0.3초** (502) |
| **누적** | **143초** | **약 3.9초** |

**타임아웃은 상한이지 소모량이 아니다.** 상한 세 개를 더해 예산을 만들면, 응답이 빠를수록 예산이
빨리 사라지는 거꾸로 된 구조가 된다. 그리고 실패는 성공보다 빠르다.

방문자가 보는 것은 이렇다.

| 경과 | 화면 | 서버 |
| --- | --- | --- |
| 0 ~ 3초 | 스켈레톤 | 부팅 중 |
| 3.0초 | "서버를 준비하는 중입니다" (1단계 안내) | 부팅 중 |
| **3.9초** | **실패 안내 + 재시도 버튼** | **부팅 중 — 앞으로 86초 더** |
| 15초 | — | 부팅 중 |

**15초 2단계 안내는 도달 불가능하다.** "무료 플랜 데모라 최대 2분 걸릴 수 있습니다"라는, 정확히
이 상황을 설명하는 문장이 이 상황에서만 뜨지 않는다. 재시도 버튼을 눌러도 4초 뒤 같은 화면이고,
방문자는 부팅이 끝날 때까지 그것을 20번 남짓 반복해야 한다. 신고된 콘솔에 `/health` 가 열 번 넘게
찍힌 것이 그 흔적이다 — 재시도 루프 3회에 `visibilitychange` · `online` 재요청이 얹힌 결과다.

### 4.4 고칠 것은 숫자가 아니라 예산의 단위

타임아웃을 키우는 것은 답이 아니다. 502 는 타임아웃과 무관하게 0.3초에 돌아오므로, 10·40·90 을
30·120·270 으로 바꿔도 예산은 여전히 4초다.

**예산을 경과 시간으로 센다.**

```
지금:  for (타임아웃 of [10s, 40s, 90s])   ← 예산 = 시도 횟수
바꾼 뒤: while (경과 < 예산)                 ← 예산 = 벽시계
```

이러면 시도가 얼마나 빨리 실패하든 예산이 줄지 않는다. 빨리 실패하면 **더 많이** 시도할 뿐이고,
그것이 부팅 중인 인스턴스를 기다리는 올바른 동작이다.

**부수 효과 하나: 등급별 타임아웃이 필요 없어진다.** 10 · 40 · 90 의 등급은 **합이 143초가 되게
하려고** 있었다. 예산이 총량을 직접 강제하면 그 역할이 사라진다. 시도별 마감은 한 값이면 되고,
그 값은 **90초** — 만약 Render 가 언젠가 요청을 붙잡는다면 한 번의 시도로 기동을 그대로 받아 내는
값이다. 두 동작 중 무엇이 와도 정책이 성립한다.

### 4.5 새 정책

| 상수 | 지금 | 바꾼 뒤 | 근거 |
| --- | --- | --- | --- |
| `attemptTimeoutsMs` | `[10_000, 40_000, 90_000]` | **삭제** | 4.4 |
| `attemptTimeoutMs` | — | **90_000** | 붙잡힌 요청 하나를 끝까지 받아 내는 값 |
| `budgetMs` | — | **150_000** | 실측 부팅 90초 + 여유 |
| `backoffMs` | `[1_000, 2_000]` | **`[1_000, 2_000, 4_000, 8_000]` · 마지막 값 반복** | 아래 |

**마지막 값이 반복되는 것을 상수 하나로 표현한다.** 별도의 `maxBackoffMs` 를 두면 「목록과 상한
중 어느 쪽이 이기는가」를 읽는 사람이 매번 확인해야 한다. `backoffFor(policy, attempt)` 가 목록을
넘어가면 마지막 값을 돌려주고, 그 규칙이 정책 스펙에 단언돼 있다.
| `noticeAfterMs` | 3_000 | 유지 | TASK-0101 4.2 |
| `longWaitNoticeAfterMs` | 15_000 | 유지 | TASK-0101 4.2 — 이번에야 실제로 뜬다 |
| `expectedColdStartMs` | 90_000 | 6.3 실측으로 확정 | 진행 표시에만 쓴다 |

**백오프 상한을 8초로 두는 이유.** 이 값은 **부팅이 이미 끝났는데 방문자가 그것을 모른 채 더
기다리는 시간의 상한**이다. 마지막 시도가 t=88초에 실패하고 인스턴스가 t=90초에 준비를 마치면,
다음 시도는 t=96초다 — 6초를 헛되이 기다린다. 90초를 기다린 사람에게 8초는 9%다. 상한을 15초로
두면 17%이고, 그 시간은 진행 표시가 95%에 붙어 멈춰 있는 구간이라 체감이 실제보다 길다.

**요청 수 상한은 22회다.** 백오프 1+2+4+8 = 15초를 쓴 뒤 남은 135초를 8초 간격으로 나눈다
(`1 + 4 + ⌊135/8⌋ = 22`). 이 값을 코드가 아니라 **테스트가 단언한다** (F6) — 예산이나 백오프를
누가 고치면 상한이 조용히 늘지 않게.

**요청 22회가 R8 을 위협하지 않는 이유.** 인스턴스 시간은 요청 수가 아니라 **깨어 있는 시간**으로
청구된다. 부팅 중인 인스턴스에 요청을 더 보내도 부팅이 길어지지 않고, 깨어난 뒤의 15분 유휴
타이머는 어차피 첫 요청이 시작한 것이다. 즉 22회는 3회와 **같은 인스턴스 시간**을 쓴다. 실제로
줄어드는 쪽이다 — 지금은 사람이 재시도 버튼을 그만큼 누르고 있고, 포기하고 새로고침하면 진행 중인
대기를 버리고 처음부터 다시 센다.

### 4.6 대역을 고치지 않으면 이 TASK 는 초록색인 채로 끝난다

**이 절이 이 TASK 의 핵심이다.**

`cold-start-replay` 는 프로덕션이 깨져 있는 내내 통과했다. 회차마다 92초를 재현하며 "정상 렌더 —
버튼을 누른 곳이 없다"를 단언했다. 테스트가 게을러서가 아니다. **대역이 틀린 모델을 정확하게
재현했기 때문이다.** `packages/api-mocks/src/waking.ts` 의 주석이 그 모델을 명시하고,
`cold-start-replay.spec.tsx` 의 머리 주석이 같은 문장을 되풀이한다.

> Render does not reject a request aimed at a sleeping service: it holds it, starts
> the instance, and answers every request that arrived in the meantime as soon as
> the instance is up. So the deadline is **shared** — a caller that gives up after
> 10 seconds and asks again does not restart the 90 second wait, it joins one
> already 10 seconds along.

구현도 그 문장 그대로다 — `readyAt ??= Date.now() + wakesAfterMs` 가 인스턴스마다 하나인 마감을
만들고, 그 전에 온 요청은 `await delay(remaining)` 으로 붙잡힌다.

TASK-0101 6.3 은 이 선택을 이렇게 적었다. "요청마다 지연을 거는 모델이었다면 어떤 재시도 정책도
통과할 수 없었을 것이다." **그 문장은 경고였는데 설계 근거로 읽혔다.** 어떤 정책도 통과하지 못하는
모델이라면 둘 중 하나다 — 모델이 틀렸거나, 정책이 통과해서는 안 되거나. 확인 없이 첫 번째로
정했고, 오늘 두 번째였음이 드러났다.

그래서 **정책보다 대역을 먼저 고친다.**

| | 지금 (`sleepingInstance`) | 바꾼 뒤 (`sleepingInstance`) |
| --- | --- | --- |
| 자는 동안 온 요청 | 붙잡는다 | **즉시 502** (본문 HTML, CORS 헤더 없음) |
| 마감 | 인스턴스마다 하나 (공유) | 인스턴스마다 하나 — **502 창의 길이** |
| 기동 완료 후 | 대기 중이던 요청을 한꺼번에 응답 | 그 다음 요청부터 200 |

**기존 모델은 지우지 않고 `heldRequestInstance` 로 남긴다.** Render 의 동작은 플랜·리전·엣지 구성에
따라 달라질 수 있고, 4.4 가 정한 정책은 두 동작 모두에서 성립해야 한다. 리플레이는 **두 모델 각각**을
돈다 (F4). 통과 기준은 같다 — 사람이 버튼을 누르지 않고 정상 렌더에 도달한다.

순서를 뒤집으면(정책 먼저, 대역 나중) 새 정책이 옛 모델에서도 통과하므로, 대역이 여전히 틀렸다는
사실을 아무것도 알려 주지 않는다.

### 4.7 화면 · 컴포넌트

새 화면이 없다. 15초 안내는 이미 `wake-waiting.tsx` 에 있고, 이번 수정이 하는 일은 **그 안내에
도달하게 하는 것**이다.

**시도 번호는 두 자리에서 화면에 찍히고 있었다.**

| 자리 | 표시 |
| --- | --- |
| `wake-waiting.tsx` | `초 · 시도 1/3` — 기다리는 동안 |
| `wake-failure.tsx` | `시도 3/3` — 예산을 다 쓴 뒤 |

둘 다 `policy.attemptTimeoutsMs.length` 를 분모로 썼다. 4.5 가 그 배열을 지우므로 **고치지 않으면
컴파일되지 않는다.** 값을 갈아 끼우는 선택지도 없다 — 예산이 벽시계인 이상 전체 시도 수는 미리
정해지지 않고, "22번 중 7번째"는 아무에게도 쓸모가 없다.

**두 자리 모두에서 뺀다.** 기다리는 화면에는 경과 시간과 진행 표시가 이미 있고, 실패 화면에는
사유와 재시도 버튼이 있다. `messages.attemptLabel` 은 쓰이는 곳이 사라지므로 세 앱의 `ko.ts` 와
`types.ts` 에서 함께 지운다.

**`useApiWake` 의 `attempt` 는 남긴다.** 화면에 쓰지 않지만 루프가 돌고 있다는 것을 스펙이
단언하는 데 쓰이고, 로그에도 의미가 있다. 사라지는 것은 `attempts`(전체 수)다.

### 6.3 측정 결과

구현 전 채운다. 표의 빈칸이 이 TASK 의 근거다.

#### 502 창 재측정 — **실패했고, 그것도 결과다**

`budgetMs` 를 확정하려고 19분을 비운 뒤 3초 간격 폴링을 걸었다. 결과:

```
probe 시작 17:03:48Z
17:03:50  200  1.43초   ← uptime 2894 (48분)
```

**서비스가 잠들지 않았다.** 19분 무요청에도 프로세스가 48분째 살아 있었다. `uptime` 을 역산하면
16:15 경 기동인데, 그 직전 16:14 에 TASK-0122 머지로 API 가 재배포됐다 — `buildFilter` 의
`apps/api/**` 에 테스트 파일도 걸린다.

**그래서 502 창의 정확한 길이는 재지 못했다.** 이 TASK 가 가진 실측은 아침의 관측 하나뿐이다.

| 시각 (UTC) | 관측 |
| --- | --- |
| 10:28:19 | 첫 502 (`x-render-routing: dynamic-paid-error`), **0.24~0.67초** |
| 10:28:2x | 502 3회 더, 모두 1초 미만 |
| 10:31:00 | 200 · `uptime: 170` → 프로세스 기동 10:28:10 |

즉 **502 창은 2.7분 이하**이고 하한은 최소 1분이다. 시작과 끝을 모두 담은 관측은 없다.

**`budgetMs = 150_000` 의 근거는 그래서 창이 아니라 부팅 시간이다.** TASK-0101 4.1 이 실측한
부팅 90초에 60% 여유를 얹은 값이고, TASK-0101 이 143초를 계산한 것과 같은 근거다. 창을 재서
확정하겠다고 초안에 적었지만 **재지 못했으므로 그렇게 적지 않는다.**

> **이것은 TASK-0101 R8 을 다시 세운다.** 그 TASK 도 49분 관찰 동안 spin down 을 보지 못했고,
> "무언가가 계속 깨워 두고 있다"를 열린 위험으로 남겼다. 오늘 아침에는 분명히 잠들어 있었고
> (10:28 의 502), 오후에는 19분을 비워도 깨어 있었다. 두 관측이 모두 사실이라면 잠드는 조건이
> 단순한 15분 무활동이 아니라는 뜻이다. 후보는 `render.yaml` 의 `healthCheckPath` 에 대한 Render
> 자체 프로브다 — 확인은 대시보드의 인스턴스 시간 사용량으로만 가능하고 소유자 작업이다.

#### 리플레이 — 두 모델 각각 (2026-09-10)

```
COLD_START_REPLAY=1 pnpm --filter @shopping/shop test cold-start-replay
```

| 모델 | 결과 |
| --- | --- |
| `sleepingInstance` (즉시 거절 · Render 실측) | **통과** · ready 103.2초 |
| `heldRequestInstance` (요청 보류 · 옛 모델) | **통과** |

**한 정책이 두 동작을 모두 버틴다.** 즉시 거절 쪽의 103.2초는 구조적으로 98초(부팅 90 + 백오프
상한 8)이고 나머지는 리플레이가 약 15회의 실제 요청·렌더를 도는 비용이다 — 스펙이 그 둘을
`REPLAY_OVERHEAD_MS` 로 나눠 적는다.

#### F5 — 옛 정책이 새 대역에서 빨개진다

정책을 고치기 **전에** 대역만 바꾸고 돌렸다.

```
× keeps the page up, explains the wait in two stages, and recovers by itself
TestingLibraryElementError: Unable to find an element with the text:
  무료 플랜 데모 환경이라 … 처음 접속은 최대 2분까지 걸릴 수 있습니다.
```

**15초 2단계 안내에 도달하지 못한다** — 4.3 이 예상한 증상 그대로다. 예산이 4초 만에 소진되므로
그 문장은 뜰 기회가 없다.

| R8 | **502 본문이 클라이언트에 닿으면 `malformed_response` 가 되고, 그것은 재시도하지 않는 최종 사유다** | 구현 중 발견. 브라우저에서는 CORS 가 먼저 막아 `network` 가 되므로 재시도된다 — 즉 **CORS 때문에 살아 있는 셈**이다. 같은 오리진이거나 서버에서 부르면 한 번 시도하고 끝난다. 대역은 브라우저가 보는 것(전송 실패)을 재현하고, 이 사실을 `waking.ts` 주석에 남겼다. `wake.ts` 의 분류를 바꾸는 것은 별건이다 |

| R6 | 502 가 아닌 다른 실패(503 · 504 · TLS)로 나타날 수 있다 | 낮음. `wake.ts` 는 이미 `network` · `timeout` · `http` 를 전부 재시도한다 — 상태 코드가 아니라 **예산**이 문제였다. 새 정책은 실패의 종류와 무관하게 성립한다 |
| R7 | 방문자가 실패 화면을 본 뒤 새로고침하면 예산이 처음부터 다시 센다 | 감수. 새로고침은 진행 중인 부팅을 버리지 않는다 — 인스턴스는 계속 뜨는 중이고 다음 요청이 그것을 받는다. 4.3 의 "20번 반복"이 1회로 줄어드는 것이 이 TASK 의 효과다 |
