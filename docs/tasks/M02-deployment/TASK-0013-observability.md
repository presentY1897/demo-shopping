## 1. 목적

배포된 서비스에서 무슨 일이 일어나는지 볼 수 있게 한다. 이후 마일스톤에서 장애를 만났을 때 로그를 뒤질 수 있는 상태를 만든다.

## 2. 범위

### 포함
- 구조화 로깅 (JSON), 요청 ID 전파
- 민감정보 마스킹 (토큰, 카드번호, 이메일)
- 에러 추적 도구 연동 (Sentry 무료 플랜)
- 프론트 3개 앱에도 에러 추적 적용
- 헬스체크 외부 모니터링 (5분 주기, 실패 시 알림)
- 스케줄러 동작 여부를 헬스체크에 포함할 자리 마련

### 제외
- APM·분산 추적
- 대시보드 구축
- 로그 장기 보관

## 3. 요구사항

- [ ] 모든 요청 로그에 요청 ID 가 붙고 응답 헤더로도 전달된다
- [ ] 로그에 토큰·카드번호·이메일 전문이 남지 않는다
- [ ] 처리되지 않은 예외가 에러 추적 도구에 수집된다
- [ ] 프론트에서 발생한 에러도 수집된다
- [ ] 헬스체크 실패 시 알림이 온다

## 4. 설계

```
요청 → requestId 생성(또는 헤더 승계) → 로거 컨텍스트에 주입 → 응답 헤더 X-Request-Id
예외 → 전역 필터 → 구조화 로그 + Sentry 전송 (requestId 태그)
```

마스킹 대상: `authorization`, `cookie`, `cardNumber`, `cvc`, `email`(도메인만 남김), `phone`(뒷자리 마스킹)

**헬스체크 확장 지점**: 이후 재고 예약 만료 스케줄러, 데모 계정 정리 스케줄러, 검색 인덱싱 큐의 상태를 여기에 추가한다. 이번엔 스키마와 자리만 만든다.

## 5. 구현 계획

1. 구조화 로거 설정, 요청 ID 미들웨어
2. 마스킹 유틸 및 로거 연결
3. Sentry 프로젝트 생성, API 연동
4. 프론트 3개 앱 연동 (소스맵 업로드 포함)
5. 헬스체크 확장 스키마 (`checks: { name, status, lastRunAt }[]`)
6. 외부 모니터링 등록 및 알림 채널 연결
