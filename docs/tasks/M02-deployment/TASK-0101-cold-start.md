# TASK-0101: 콜드 스타트 대응 · 서버 웨이크업 UX

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M02 배포 파이프라인 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/cold-start` |
| 선행 작업 | TASK-0010 |

## 1. 목적

무료·저가 플랜의 백엔드는 무활동 시 잠든다. **첫 방문자가 빈 화면을 보는 상황**을 막는다. 데모 URL 을 채용 담당자에게 보내는 프로젝트라 첫인상이 여기서 결정된다.

## 2. 범위

### 포함
- 프론트 진입 시 백그라운드 **프리워밍** — 페이지 렌더와 동시에 `/health` 호출로 API 를 깨움
- API 응답이 지연될 때의 UX — 스켈레톤 + 안내. **노출 시점은 실측 콜드 스타트(4.1)를 근거로 정한다**
- 타임아웃·재시도 정책 (지수 백오프, 최대 3회)
- 깨어남 감지 후 자동 재요청
- 외부 cron 핑 — 쓸지 말지 판단하고 근거를 남긴다 (4.8)
- 콜드 스타트 소요 시간 측정·기록
- 검색 인덱스 준비 상태를 헬스체크에 노출 (준비되지 않았으면 검색 대신 안내)
- 플랫폼별 sleep 정책 문서화

### 제외
- 유료 플랜 전환 (비용 결정은 별도)
- **검색 색인 파이프라인 자체** — TASK-0038. 이 TASK 는 "색인이 준비됐는가"를 **보고**할 뿐 색인하지 않는다
- **헬스 응답 스키마에 필드 추가** — `packages/shared` 는 TASK-0011 소유. 기존 `search` 필드의 의미를 넓혀서 푼다 (4.7)

## 3. 요구사항

- [x] 서버가 자고 있어도 화면이 깨지지 않는다
- [x] 3초 이상 걸리면 이유를 알려주는 안내가 뜬다
- [x] 안내가 **경과 시간과 함께 계속 움직인다** — 90초 동안 정지한 화면으로 보이지 않는다 (4.2)
- [x] 서버가 깨어나면 자동으로 다시 요청한다
- [x] 프리워밍이 페이지 렌더를 막지 않는다
- [x] 프리워밍이 **서비스를 상시 깨워 두지 않는다** (TASK-0009 R8)
- [x] 콜드 스타트 소요 시간을 측정할 수 있다

## 4. 설계

### 4.1 실측 — 무엇을 얼마나 기다리는가

2026-09-03, 배포된 서비스에 직접 측정했다.

| 대상 | 상태 | 첫 응답 |
| --- | --- | --- |
| `https://shopping-api-96sy.onrender.com/api/v1/health` | 15분 이상 무활동 후 | **약 90초** |
| 같은 엔드포인트 | 깨어 있을 때 | **0.35초** (한국에서 싱가포르 리전, TLS 포함 0.7초) |
| `https://shopping-search-frrb.onrender.com/health` | 무활동 후 | API 와 같은 무료 web 서비스 등급 |

**초안이 가정한 "재기동 약 1분"은 틀렸다.** 90초는 그 1.5배이고, 이 차이가 UX 설계를 바꾼다. 측정 방법은 6.3 에 있다.

### 4.2 3초 임계는 유지한다. 다만 3초짜리 안내 하나로는 90초를 버틸 수 없다

안내를 3초에 한 번 띄우고 끝내면, 남은 87초 동안 화면은 **정지한 것과 구분되지 않는다.** 사람은 그 화면을 고장으로 읽고 새로고침하며, 새로고침은 진행 중인 기동을 기다리는 대신 처음부터 다시 기다리게 만든다.

그래서 임계는 3초로 두되 **단계와 경과 시간**을 붙인다.

| 경과 | 화면 |
| --- | --- |
| 0 ~ 3초 | 스켈레톤만. 0.35초에 끝나는 평소 방문과 구분되지 않아야 한다 |
| 3초 ~ | "서버를 준비하는 중입니다" + **경과 초** + 진행 표시 |
| 15초 ~ | 위에 더해 "무료 플랜 데모 환경이라 처음 접속은 최대 2분까지 걸릴 수 있습니다" |
| 재시도 소진 | 실패 안내 + 재시도 버튼 |

**왜 두 번째 임계가 15초인가.** 깨어 있는 서버(0.35초)와 자는 서버(90초) 사이에는 중간값이 거의 없다 — 3초를 넘겼다면 십중팔구 콜드 스타트다. 그렇다고 3초 시점에 "2분 걸립니다"라고 말하면, 네트워크가 잠깐 느렸을 뿐인 방문자에게 없는 문제를 심는다. 15초는 콜드 스타트가 사실상 확정되는 지점이다.

**왜 "최대 2분"인가.** 실측 90초에 여유를 얹은 값이다. "90초"라고 적으면 91초에 거짓말이 되고, R1 이 경계한 "변명처럼 읽히는 안내"가 된다.

### 4.3 프리워밍은 별도 핑이 아니라 첫 데이터 요청이다

프리워밍 핑과 데이터 요청을 따로 두면 요청이 두 배가 되고, **무료 인스턴스 시간(R8)만 두 배로 쓴다.** 깨우는 일과 데이터를 얻는 일은 같은 `/health` 한 번으로 끝난다.

"렌더를 막지 않는 것"은 요청을 **옮겨서** 해결한다.

```
지금:  서버 컴포넌트가 await loadHealth() → 페이지 전체가 5초 타임아웃까지 멈춤
       (콜드 스타트에서는 반드시 실패 화면이 나온다. 5초 < 90초)

바꾼 뒤: 서버 컴포넌트는 await 없이 HTML 을 즉시 내보낸다
        → 클라이언트 컴포넌트가 마운트 시점에 요청을 시작한다
        → 대기·재시도·경과 시간이 전부 브라우저에서 돈다
```

서버 렌더 경로에 await 가 하나도 남지 않으므로 **F4 는 구조적으로 보장된다.** "재 봤더니 안 느리더라"가 아니라, 기다릴 것이 없다.

### 4.4 타임아웃·재시도

`packages/shared` 의 기본 타임아웃 5초는 콜드 스타트를 절대 통과하지 못한다. 스키마도 클라이언트도 건드리지 않고 **호출별 `timeoutMs`** 로 덮는다.

| 시도 | 타임아웃 | 직전 백오프 | 누적 상한 |
| --- | --- | --- | --- |
| 1 | 10초 | — | 10초 |
| 2 | 40초 | 1초 | 51초 |
| 3 | 90초 | 2초 | **143초** |

- **타임아웃이 커진다.** Render 는 자는 인스턴스로 온 요청을 끊지 않고 붙잡았다가 기동이 끝나면 응답한다. 그래서 1번 시도는 "깨어 있는데 느린가"를 10초 안에 가려내고, 마지막 시도는 90초 기동을 그대로 기다린다.
- 백오프는 **지수(1초 → 2초), 최대 3회** — 명세 그대로.
- 누적 상한 143초는 실측 90초에 60% 여유를 둔 값이다.
- `configuration`(API 주소 미설정)과 `aborted`(사용자 이탈)는 **재시도하지 않는다.** 다시 해도 결과가 같거나, 이미 떠난 사람을 위해 무료 시간을 쓰는 일이다.

### 4.5 깨어남 감지 후 자동 재요청 — 폴링하지 않는다

폴링은 곧 "항상 깨우기"이고 R8 위반이다. 대신 **상한이 있는 신호**만 쓴다.

| 신호 | 동작 |
| --- | --- |
| 재시도 루프의 다음 시도 | 이것이 곧 깨어남 감지다 — Render 가 기동을 마치면 붙잡고 있던 요청이 응답된다 |
| `online` 이벤트 | 실패 상태였다면 즉시 1회 재요청 |
| 탭이 다시 보임 (`visibilitychange`) | 〃 |
| 검색이 아직 준비되지 않음 | **최대 3회**, 5초 → 15초 → 30초 뒤 재확인. 소진되면 수동 버튼으로 넘긴다 |

전부 상한이 있고, 사람이 탭을 열어 둔 동안에만 돈다. 배경 타이머도, 서비스 워커도, 주기 작업도 없다.

### 4.6 검색 엔진은 **따로** 잔다

검색 엔진은 별도 free web 서비스다(TASK-0009 4장). API 만 깨우면 첫 검색에서 90초를 다시 기다린다.

**이미 있는 것:** API 의 `/health` 는 `SearchHealthIndicator` 를 통해 검색 엔진의 `/health` 를 **서버에서** 부른다. 그 요청이 Render 에 닿는 순간 검색 서비스의 기동이 시작된다 — 즉 API 를 깨우면 검색도 깨워진다. 다만 **순차**다.

```
t=0      브라우저 → API                     API 기동 시작
t≈75s    API 프로세스 부팅 → 검색 웨이크업 킥   검색 기동 시작
t≈90s    API 가 /health 응답                search: "down" (설계상 정상, TASK-0009 R10)
t≈165s   검색 준비 완료
```

**이 TASK 가 더하는 것:** `SearchWarmupService` — API 부팅(`OnApplicationBootstrap`) 시점에 검색 엔진으로 **비차단 요청 1회**를 쏜다. Render 자체 헬스 프로브의 타이밍에 기대지 않고, 검색 기동이 API 가 응답을 시작하기 **전에** 출발한다. 프로세스당 1회이므로 R8 에 안전하다.

**병렬로 만들려면** 브라우저가 검색 서비스의 공개 URL 을 직접 두드려야 하고(위 165초 → 90초), 그러려면 `NEXT_PUBLIC_SEARCH_URL` 이 필요하다. 그 값은 빌드 시점에 JS 번들에 박히므로 TASK-0009 가 정한 "주소를 굳이 알리지 않는다"를 뒤집는다. 보호는 마스터 키가 전담하니 유출이 곧 사고는 아니지만, **그 결정은 TASK-0009 의 것이다.** R5 로 남긴다.

### 4.7 검색 인덱스 준비 상태를 헬스체크에 노출

응답 스키마(`packages/shared/src/health.ts`)는 TASK-0011 소유라 이번에 필드를 추가할 수 없다. 새 필드를 만드는 대신 **기존 `search` 필드의 의미를 넓힌다.**

| 값 | 뜻 |
| --- | --- |
| `down` | 엔진에 닿지 못한다 (자는 중 · 죽음) |
| `degraded` | 엔진은 살아 있으나 **기대하는 색인이 조회 가능하지 않다** (없음 · 비었음 · 색인 진행 중) |
| `ok` | 엔진이 살아 있고 기대하는 색인이 전부 조회 가능 |

`healthStatusSchema` 가 `degraded` 에 붙여 둔 정의("reachable but answering something unexpected")와 어긋나지 않는다. 프론트는 **`search !== 'ok'` 이면 검색 대신 안내**를 띄운다 — 방문자에게 "깨는 중"과 "색인 중"은 똑같이 "아직 검색할 수 없다"이기 때문이다.

**기대 색인 목록은 지금 비어 있다.** 카탈로그 색인은 TASK-0038 이 만든다. 목록이 비면 검사는 요청을 보내지 않고 `ok` 를 유지한다. 없는 색인을 "준비 안 됨"으로 보고하면 **TASK-0009 의 F3(`search: "ok"`)이 TASK-0038 전까지 영구히 불가능해지기** 때문이다. 기계는 전부 갖췄고, TASK-0038 이 목록에 `products` 한 줄을 넣으면 켜진다.

색인 조회는 마스터 키가 필요한 `GET /indexes/{uid}/stats` 를 쓴다. `/health` 는 플랫폼 프로브가 부르는 경로이므로 **재색인을 트리거하지 않는다** — TASK-0009 가 "헬스체크가 그 판정을 겸하지 않는다"로 정한 그대로다. 보고만 한다.

### 4.8 외부 cron 핑 — **쓰지 않는다**

약관을 따지기 전에 산술이 끝낸다.

- 무료 인스턴스 시간 **750h/월을 워크스페이스 전체가 공유**한다 (TASK-0009 R8).
- 서비스는 API·검색 **2개**. cron 으로 상시 가동하면 2 × 730h = **1460h**, 한도의 **1.9배**다.
- 그러면 한 달의 절반쯤에 750h 를 소진하고 **그 뒤로는 두 서비스가 모두 정지**한다. cron 은 콜드 스타트 90초를 없애는 대신 **월 후반 전체를 다운타임으로 바꾼다.**
- 서비스당 예산은 750 ÷ 2 = **375h/월 = 하루 12.5시간**이다. 24시간 가동은 어떤 간격으로도 들어가지 않는다.

**방문 기반 웨이크업의 소모량**은 이렇다. 한 번 깨우면 마지막 요청 후 15분까지 살아 있으므로 방문 1회 ≈ 서비스당 0.25h, 두 서비스가 함께 깨므로 **방문 1회 ≈ 0.5h**. 즉 **월 1500회 방문**까지 한도 안이다. 포트폴리오 데모에 충분하다.

대신 **수동 워밍업을 문서화한다.** 링크를 보내기 직전에 `curl` 한 줄을 실행하면 받는 사람은 0.35초 화면을 본다(README "무료 플랜에서 알고 있어야 하는 것"). **자동화하지 않는 것이 핵심이다** — 자동화하는 순간 위의 산술로 돌아간다.

### 4.9 플랫폼별 sleep 정책

| 구성 요소 | sleep | 재개 | 근거 |
| --- | --- | --- | --- |
| Render 무료 web (api) | 15분 무활동 | **실측 약 90초** | 4.1 |
| Render 무료 web (검색) | 15분 무활동, API 와 **독립** | 같은 등급 | 4.6 |
| Neon 무료 (postgres) | 5분 무활동 시 scale-to-zero | 수백 ms — 체감되지 않음 | TASK-0009 |
| Meilisearch 인덱스 | 재기동 시 **소실** (영구 디스크 없음) | 자동 재색인 수 초 (TASK-0038) | TASK-0009 |
| Vercel (웹 3개) | 잠들지 않음 | — | 정적/서버리스 |

**웹 앱은 잠들지 않는다.** 그래서 방문자는 항상 화면을 먼저 보고, 기다리는 것은 데이터 영역뿐이다 — 4.3 이 성립하는 전제다.
