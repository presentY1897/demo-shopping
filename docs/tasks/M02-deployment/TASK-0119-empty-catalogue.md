# TASK-0119: 배포 카탈로그 부트스트랩 · 빈 카탈로그를 신호로 만든다

| 항목 | 내용 |

| 마일스톤 | M02 배포 파이프라인 |
| 상태 | 초안 |
| 작성일 | 2026-09-09 |
| 브랜치 | `fix/empty-catalogue` |

## 1. 목적

배포된 shop 이 "보여줄 상품이 없습니다"를 띄우고 검색은 500 을 낸다. 원인은 하나다 —
**프로덕션 DB 에 시드가 한 번도 돌지 않았다.**

그런데 고쳐야 할 것은 그것만이 아니다. **데이터가 없다는 사실을 어떤 신호도 말하지 않았다.**
헬스체크는 `search: "ok"` 였고, Render 대시보드는 Live 였고, 로그에도 아무것도 남지 않았다.
카탈로그가 빈 배포와 정상 배포가 **겉으로 구별되지 않는다.**

끝나면 세 가지가 성립한다.

1. 배포 절차에 카탈로그를 넣는 자리가 있다
2. 빈 카탈로그가 500 이 아니라 빈 결과로 나타난다
3. 헬스체크가 그 상태를 **말한다**

## 2. 범위

### 포함

- `EXPECTED_SEARCH_INDEXES` 에 `products` 를 넣어 헬스체크가 색인 준비를 실제로 검사 (4.4)
- 배포 환경에서 위 셋을 확인하는 절차 (6.3)

### 제외 (이번에 하지 않는 것)
- **시드 내용 변경** — TASK-0037 소유. 이 TASK 는 **언제·어떻게 실행하는가**만 다룬다
- **색인 파이프라인 변경** — TASK-0038 소유. **예외 하나**: `size()` 가 없는 인덱스와 닿지 않는
  엔진을 구별하지 못해 자동 복구가 막히는 것 (4.7). 오늘 장애의 직접 원인 중 하나이고 수정이
  4.3 과 같은 줄기라 이 TASK 가 가져온다. 그 밖의 파이프라인 변경은 그대로 제외한다
- **R2 이미지** — TASK-0011 진행중. 시드가 이미지를 건너뛰어도 이 TASK 의 완료 기준은 충족된다 (R1)
- **콜드 스타트 재시도 예산** — TASK-0118. 증상이 같은 화면에 나타날 뿐 원인이 다르다

## 3. 요구사항

### 기능 요구사항
- [ ] 배포된 shop 홈에 상품이 보인다
- [ ] 검색이 결과를 돌려준다
- [ ] **인덱스가 없을 때 검색이 500 을 내지 않는다** — 데이터가 있든 없든

- 시드가 **부팅 경로에 아무것도 더하지 않는다** — 콜드 스타트는 TASK-0118 이 줄이는 중이다

## 4. 설계

### 4.1 무엇이 휘발성이고 무엇이 영속인가

이 구분이 이 TASK 의 전부다.

| 저장소 | 재기동하면 | 이미 있는 복구 | 오늘 상태 |
| --- | --- | --- | --- |
| Neon PostgreSQL (카탈로그) | **남는다** | 필요 없다 — 1회 주입이면 끝 | **비어 있다** |
| Meilisearch 인덱스 | **사라진다** (영구 디스크 없음, TASK-0009) | `ensurePopulated()` 자동 재색인 | 비어 있다 |

**자동 재색인은 이미 있다.** 없는 것은 그것이 읽을 **원본**이다 — 다만 구현 중에 그 복구 자체에
구멍이 있다는 것이 드러났다. 4.7 에 적었고, 이 절의 "정상 동작한다"는 그만큼 약해진다.

```ts
async ensurePopulated(): Promise<boolean> {
  const size = await this.index.size()
  if (size === null || size > 0) return false
  const written = await this.reindexAll()   // 카탈로그가 비면 0
  if (written > 0) this.logger.log(`인덱스가 비어 있어 ${written}건을 다시 채웠습니다.`)
  return written > 0
}
```

`written = 0` 은 실패가 아니라 **조용한 성공**이다. 로그도 남지 않고 `searchIndex.lastRunAt` 도
`null` 로 남는다 — 실측이 정확히 그랬다 (6.3). 복구 장치가 "복구할 것이 없다"를 정상으로 보고하는
동안 사이트는 비어 있었다.

### 4.2 시드는 부팅 경로에 넣지 않는다

세 가지를 검토했다.

| 안 | 방식 | 판정 |
| --- | --- | --- |
| A | `startCommand` 에 `db:seed` 추가 | **기각.** `pnpm db:seed` 는 `prisma/seed.mts` 런처를 거치고 그 파일은 **매 실행마다 `nest build` 를 돌린다.** 512MB 무료 인스턴스에서 매 기동마다 빌드다. `node dist/seed/run.js` 를 직접 불러 빌드를 피해도, 800개 상품의 존재 확인이 부팅에 붙는다 |
| B | 부팅 시 "비어 있으면 시드" (`ensurePopulated` 패턴) | **기각.** 같은 이유. 시드는 상품을 `ProductService`·`StockService` 를 **통해** 쓴다 (TASK-0037 F3·F4). 인덱스 재색인과 무게가 다르다 |
| C | **소유자 1회 수동 + 체크리스트** | **채택** |

**C 를 고른 이유는 Neon 이 영속이기 때문이다.** 재기동마다 사라지는 것은 Meilisearch 인덱스뿐이고
그쪽에는 이미 자동 복구가 있다 (4.1). 카탈로그는 한 번 넣으면 남는다. 한 번 하면 되는 일을 위해
매 부팅에 비용을 얹는 것은, TASK-0118 이 콜드 스타트에서 줄이려는 것과 정확히 반대 방향이다.

C 의 단점은 "DB 를 새로 만들면 사람이 다시 해야 한다"인데, **그것이 체크리스트가 존재하는 이유다.**
오늘의 문제도 자동화가 없어서가 아니라 **절차에 자리가 없어서** 생겼다 — `render.yaml` 의
`startCommand` 는 `db:deploy` 만 돌고, `docs/OWNER-CHECKLIST.md` B절 9단계 어디에도 시드가 없다.

#### 실행 명령

시드는 **가산적**이다. `seed-runner.ts` 는 `existing` 을 세어 없는 것만 만들고 `deleteMany` 나
`TRUNCATE` 가 없으며, `run.ts` 는 끝에 `AppMeta` 의 `seed.version` 을 남긴다. 두 번 돌려도 안전하다.

```bash
# 1) 확인 — 정말 비어 있는가
DATABASE_URL='<Neon 연결 문자열>' pnpm db:seed:verify

# 2) 시드
DATABASE_URL='<Neon 연결 문자열>' pnpm db:seed
```

`--scale` 은 `full`(판매자 15 · 상품 800)이 기본이고 `small`(5 · 50)이 있다. **배포에는 `full` 을
쓴다** — 데모의 목적이 카탈로그가 있는 화면을 보여 주는 것이다. `small` 은 R2 가 걸릴 때의 대안이다.

**시드 뒤 API 재기동은 필요 없다.** 인덱서가 1초마다 돌고 60틱마다 `ensurePopulated()` 를 부른다
(`INDEXER_POLL_MS = 1_000` · `POPULATION_CHECK_TICKS = 60`). **약 1분 안에** 인덱스가 채워진다.
서비스가 잠들어 있으면 다음 방문이 깨우고 그때 채워진다.

### 4.3 없는 인덱스는 500 이 아니다

**데이터와 무관한 버그다.** 시드를 넣어도 남는다 — 인덱스는 재기동마다 사라지고, 사라진 직후부터
`ensurePopulated()` 가 채우기까지의 최대 60초 동안 모든 검색이 지금 코드에서 500 이다.

`apps/api/src/search/search-index.ts:176`:

```ts
if (!response.ok) throw new Error(messageOf(response.status, await response.text()))
```

Meilisearch 는 없는 인덱스에 404 와 `{"code":"index_not_found", ...}` 를 준다. 위 한 줄이 그것을
다른 모든 실패와 **똑같이** 예외로 만들고, 질의 경로에 잡는 곳이 없어 500 이 된다.

**고치는 방식**: 본문의 `index_not_found` **코드만** 골라 "아직 준비되지 않음"으로 바꾸고 빈 결과를
돌려준다. **상태 코드가 아니라 본문의 코드로 판별한다** — 404 를 통째로 빈 결과로 바꾸면 오타 난
경로나 잘못된 마스터 키 같은 진짜 오류까지 조용히 삼킨다. 그것이 이 TASK 가 고치려는 실패의
모양 그 자체다.

빈 결과를 받은 방문자가 "상품이 없다"와 "아직 준비 중"을 구별하는 일은 4.4 가 맡는다.

### 4.4 헬스체크가 진실을 말하게 한다

`apps/api/src/health/search-indexes.ts:20` 은 지금 이렇다.

```ts
export const EXPECTED_SEARCH_INDEXES: readonly string[] = []
```

**목록이 비면 검사는 요청을 보내지 않고 `ok` 를 유지한다.** 그래서 검색이 500 을 내는 내내
헬스체크는 `search: "ok"` 였다. 대시보드도 헬스체크도 정상이라고 말하는 배포에서 사이트만
비어 있었다.

TASK-0101 4.7 이 비워 둔 것은 **당시에는 옳았다.** 카탈로그 색인이 아직 없었고, 넣으면
TASK-0009 F3(`search: "ok"`)이 영구히 불가능해진다. 그래서 이렇게 인계했다 (R6).

> 목록에 `products` 를 넣는 순간 켜진다. 지금 넣으면 TASK-0009 F3 가 영구히 불가능해진다.

**TASK-0038 은 완료됐고, 그 한 줄은 들어가지 않았다.** 인계가 떨어졌다. 이 TASK 가 그것을 줍는다.

```ts
export const EXPECTED_SEARCH_INDEXES: readonly string[] = ['products']
```

**넣는 순간 현재 배포가 `search: "degraded"` 로 바뀐다. 그것이 맞다** — 검색은 실제로 되지 않는다.
시드가 끝나면 `ok` 로 돌아온다. 지표가 나빠지는 것이 아니라, 지금까지 거짓말하던 지표가 사실을
말하기 시작하는 것이다.

**프론트 변경은 없다.** `search !== 'ok'` 이면 검색 대신 준비 중 안내를 띄우는 동작이 이미 있다
(TASK-0101 4.7). 그 화면은 만들어져 있었고, 그것을 켜는 신호만 없었다.

### 4.5 순서가 중요하다

```
1. 4.4 (헬스 한 줄)  → 지금 배포가 즉시 degraded 로 바뀐다.  ← 이것이 증거다
2. 4.3 (500 → 빈 결과) → 인덱스 없이도 검색이 200 을 준다
3. 시드 실행           → 데이터가 들어온다
4. 세 지표가 함께 ok 로 돌아오는 것을 확인
```

**시드를 먼저 돌리면 1·2 를 검증할 수 없다.** 데이터가 들어온 뒤에는 두 버그 모두 증상이 사라지고,
다음 재기동 때 다시 나타난다. 고쳤는지 알 수 없는 수정은 고치지 않은 것과 같다.

### 4.7 자동 복구가 막혀 있다 — 구현 중 발견

**4.1 은 "자동 재색인은 이미 있고 정상 동작한다"로 적었다. 절반만 맞았다.**

복구 경로는 이렇게 생겼다.

```
onApplicationBootstrap()
  → configure()          인덱스를 만들고 설정을 넣는다 (ensureIndex: true)
  → ensureCurrentShape()
  → ensurePopulated()    비어 있으면 다시 채운다
tick()  (1초마다)
  → drain()
  → 60틱마다 ensurePopulated()
```

`configure()` 는 **부팅에서 한 번만** 불린다 (`search-indexer.service.ts:103`). 주기 경로에는
없다. 그런데 그 한 번이 실패할 수 있고, 실패는 조용하다.

```ts
} catch (error) {
  // A cold engine is the normal state of a fresh deployment. The next tick
  // and the next boot both try again.
  this.logger.warn(`검색 인덱스 설정을 적용하지 못했습니다: ${String(error)}`)
}
```

**주석이 틀렸다. 다음 tick 은 `configure()` 를 부르지 않는다.** 그리고 `configure()` 없이는
인덱스가 만들어지지 않는다.

남은 복구 후보는 `ensurePopulated()` 하나인데, 그쪽도 막혀 있다.

```ts
const size = await this.index.size()
if (size === null || size > 0) return false   // ← 없는 인덱스는 여기서 걸린다
```

`size()` 는 `/indexes/products/stats` 를 부르고, **없는 인덱스에 대한 404 를 다른 모든 실패와
함께 삼켜 `null` 을 돌려준다.** `null` 은 "닿지 못했다"는 뜻으로 설계된 값이라 (R5 — 네트워크가
한 번 튀었다고 전체 재색인을 돌리지 않기 위한 것) `ensurePopulated()` 는 재구축하지 않는다.

**그래서 엔진이 API 부팅 시점에 자고 있으면 인덱스는 영원히 만들어지지 않는다.** 그리고 그것은
드문 일이 아니라 **정상 경로**다 — 검색 엔진은 별도의 무료 서비스이고 API 보다 약 75초 늦게
깨어난다 (TASK-0101 4.6). API 부팅 시점의 엔진은 대개 자고 있다.

로컬 엔진으로 확인했다.

```
GET /indexes/products/stats  (없는 인덱스)
→ HTTP 404
  {"message":"Index `products` not found.","code":"index_not_found", ...}
```

#### 고치는 방법

4.3 이 이미 `SearchEngineError` 에 엔진의 `code` 를 실어 두었다. `size()` 가 그것을 읽으면 된다.

| 엔진 응답 | 지금 `size()` | 바꾼 뒤 |
| --- | --- | --- |
| `index_not_found` | `null` (닿지 못함) | **`0`** — 인덱스가 없다는 것은 문서가 0건이라는 확정이다 |
| 그 밖의 실패 · 타임아웃 | `null` | `null` (그대로) |

`0` 이 되면 `ensurePopulated()` → `reindexAll()` → `rebuild()` → `configure()` 로 이어져
**인덱스가 만들어지고 채워진다.** R5 가 지키려던 것("네트워크 하나 튀었다고 전체 재색인 금지")은
그대로 남는다 — 그쪽은 여전히 `null` 이다.

**이 수정 없이는 4.3 만으로 증상이 가려진다.** 500 이 빈 화면으로 바뀌긴 하지만 검색은 영영
돌아오지 않는다. 시드가 그것을 덮는 이유는 상품 쓰기가 `upsert` 를 태우고 Meilisearch 가 문서
쓰기 시점에 인덱스를 자동 생성하기 때문인데, **그것은 복구가 아니라 우연이다.** 엔진이 재기동한
뒤 아무도 상품을 수정하지 않으면 검색은 계속 비어 있다.

### 4.6 데이터 모델 · API · 화면

- 데이터 모델 변경: **없음.** 마이그레이션이 없다
- API: 새 엔드포인트 없음. `GET /api/v1/search` 의 **실패 모드만** 바뀐다 (500 → 200 + 빈 결과)
- 화면: **없음.** 4.4 가 켜는 안내 화면은 이미 있다
- 역할별 권한: 해당 없음. 전부 비인증 공개 경로다
