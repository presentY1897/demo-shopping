# TASK-0054: 가상 카드 결제 · 실패 재현

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M08 결제 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/virtual-card-payment` |
| 선행 작업 | TASK-0053 |

## 1. 목적

가상 카드 프로바이더를 구현한다. **실패 시나리오를 의도적으로 만들 수 있는 것**이 이 TASK 의 핵심 가치다.

## 2. 범위

### 포함
- `VirtualCardProvider` 구현 (authorize/capture/cancel/refund/getStatus)
- 결제 승인 시 카드 원장 차감, 재고 예약 확정 연동
- **실패 시나리오 재현 장치**
  - 한도 초과 / 잔액 부족
  - 승인 거절 (카드 상태·랜덤)
  - 승인 지연 (N초 지연 후 응답)
  - 타임아웃
- 실패 유도 방법: 특정 한도 카드, 또는 개발용 헤더/플래그
- 취소·부분 환불 시 원장 복구
- 결제 화면 (카드 선택 → 즉시 승인)

### 제외
- 토스 연동 (TASK-0055)
- 실패 후 복구 처리 전반 (TASK-0057)

## 3. 요구사항

- [ ] 가상 카드로 결제하면 즉시 승인된다
- [ ] 한도를 넘으면 거절된다
- [ ] 승인 지연·타임아웃을 재현할 수 있다
- [ ] 취소·환불하면 카드 잔액이 복구된다
- [ ] 승인 시 재고 예약이 확정된다

## 4. 설계

| 실패 시나리오 | 유도 방법 |
| --- | --- |
| 한도 초과 | 한도가 낮은 카드를 발급해 사용 |
| 승인 거절 | 카드 상태를 `SUSPENDED` 로 변경 (4.1). **랜덤 거절은 만들지 않는다** (4.6) |
| 승인 지연 | 데모 화면의 "지연 재현" 옵션 (개발·데모 환경만) |
| 타임아웃 | 지연 시간을 타임아웃 초과로 설정 |

**이 장치를 두는 이유**: 토스 테스트만으로는 실패 경로를 보여주기 어렵다. 결제가 실패했을 때 재고 예약이 풀리는지, 주문이 올바른 상태로 가는지를 시연할 수 있어야 한다. 포트폴리오에서 설명거리가 가장 많은 부분이다.

**운영 환경에서는 지연·랜덤 거절을 비활성화**한다. 한도 초과·카드 정지는 정상 기능이므로 유지한다.

### 4.1 카드 상태는 `BLOCKED` 가 아니라 `SUSPENDED` 다 (2026-09-05 정정)

위 표가 「카드 상태를 BLOCKED 로 변경」이라고 적었는데, TASK-0053 이 만든 상태는
`ACTIVE` · `SUSPENDED` · `DELETED` 셋이다. **되살릴 수 있는가**로 가른 이름이라
`SUSPENDED` 가 이 표가 뜻하는 것이다 — 실패를 재현하고 다시 정상으로 돌려놓을 수
있어야 시연이 된다.

### 4.2 승인이 예약을 확정하는 자리는 **주문 쪽**이다

「승인 시 재고 예약 확정」을 결제 서비스가 직접 하면 결제가 주문과 재고를 알게 된다.
그러면 토스 프로바이더가 붙는 날 같은 지식이 한 벌 더 생기거나, 결제 서비스가 두
프로바이더의 사정을 다 아는 자리가 된다.

그래서 **결제는 결제만 하고**, 「주문이 결제됐다」를 받는 자리를 주문 쪽에 둔다.
그 자리가 예약을 확정하고(TASK-0048 `confirm`) `SellerOrder` 를 `PAID` 로 옮긴다.
프로바이더가 무엇이든 그 뒤는 같다 — 그것이 D-031 이 말하는 추상화의 값이다.

### 4.3 실패했을 때 예약은 **유지된다** (F2)

풀지 않는다. 한도가 모자라 거절당한 사람이 다음에 할 일은 **다른 카드로 다시 하는
것**이고, 그때 재고가 이미 남에게 갔으면 그 시도는 무의미하다.

풀어 주는 것은 TTL 이다 — 15분이 지나면 만료 스케줄러가 가져간다(TASK-0051). 실패가
곧 포기는 아니라는 것이 이 설계의 전제이고, 「실패 후 복구 처리 전반」이 TASK-0057 의
몫인 이유도 같다.

### 4.4 실패 재현은 **환경변수로 완전히 차단한다** (F8 · R1)

지연과 랜덤 거절은 `PAYMENT_SIMULATION` 이 켜져 있을 때만 존재한다. 운영에서는 그
플래그가 없으므로 코드 경로 자체가 닫힌다.

**한도 초과와 카드 정지는 그 플래그와 무관하다.** 그것은 재현 장치가 아니라 정상
기능이고, 운영에서도 일어나야 한다 — 오히려 그 둘만으로 실패 시연의 대부분이 된다.

### 4.5 타임아웃은 **모드**이지 진짜 마감이 아니다 (F5, 2026-09-05 정정)

처음에 「프로바이더가 자기 마감을 갖고 넘기면 스스로 끊는다」로 적었는데, 만든 것은
그것이 아니다. `PAYMENT_SIMULATION=timeout` 일 때 프로바이더가 **끊긴 것처럼 답한다** —
지연과 타임아웃이 다른 값인 것은 맞지만(그래야 재는 것이 검사의 인내심이 아니다),
**임의의 느림을 실제로 끊지는 않는다.**

느린 승인은 여전히 Prisma 의 트랜잭션 마감(기본 5초)에 걸려 끝나고, 그때의 `FAILED` 는
프로바이더가 아니라 데이터베이스가 만든 것이다.

그렇게 둔 이유는 이 TASK 가 재는 것이 **끊긴 뒤의 상태**이기 때문이다 — 결제가
`FAILED` 이고 결제키가 없으며 예약이 그대로 `HELD` 이고 재고와 카드 원장이 움직이지
않았다는 것. 그것은 모드로 충분히 재현되고, 실제 마감을 두는 일은 「저쪽이 승인했는지
모르는 상태」를 다루는 TASK-0057 의 몫이다. **거기까지 한 척하지 않는다.**

### 4.6 랜덤 거절은 만들지 않는다 (2026-09-05 정정)

4장 표가 「승인 거절 (카드 상태·랜덤)」이라고 적었는데 **카드 상태만 만든다.**

랜덤 거절은 시연에서 재현되지 않는 실패다 — 보여 주려고 눌렀는데 통과해 버리면 그
자리에서 할 수 있는 일이 없고, 반대로 검사에서는 통과해야 할 것이 가끔 빨개진다.
카드를 `SUSPENDED` 로 바꾸는 것은 **누르면 반드시 일어나는** 거절이고, 시연에는 그쪽이
낫다.

한도가 낮은 카드로 결제하는 것까지 합치면 「승인 거절」의 두 얼굴이 모두 재현된다 —
카드가 막힌 경우와 돈이 모자란 경우다.

## 5. 구현 계획

## 6. 완료 기준

### 6.1 기능

| # | 기준 | 측정 방법 | 목표 | 실측 | 충족 |
| --- | --- | --- | --- | --- | --- |
| F1 | 정상 승인 | 카드로 결제 | 승인, 주문 PAID, 예약 확정 | **한 검사가 사슬 전체를 본다** — 결제 `PAID` · 판매자 몫 `PAID` · 상태 이력 두 줄 · 예약 `CONFIRMED` · 재고 10→8 · `reserved` 0 · 원장에 `RESERVE_CONFIRM` 한 줄 · 카드 사용액이 실결제액과 같고 대사가 깨끗하다. **금액을 어디에도 적어 넣지 않았다** — 전부 `order.paidAmount` 에서 온다 | [x] |
| F2 | 한도 초과 | 한도 낮은 카드 | 거절, 주문 미완료, **예약 유지** | 거절되고 예약은 그대로 `HELD`. 이어서 **다른 카드로 같은 주문을 끝낼 수 있다** — 그것이 예약을 안 푸는 이유다 (4.3) | [x] |
| F3 | 카드 정지 | `SUSPENDED` 카드 | 거절 + 사유 | 거절되고 사유가 화면에 나온다 | [x] |
| F4 | 승인 지연 | `PAYMENT_SIMULATION=delay` | 로딩 후 정상 승인 | 지연 상수 이상 걸리고 **끝난다** | [x] |
| F5 | 타임아웃 | `PAYMENT_SIMULATION=timeout` | 실패, 상태 일관 | 결제 `FAILED`, 결제키 없음, 예약 `HELD`, 재고·카드 원장 그대로, 대사 깨끗. **다만 이것은 모드이지 진짜 마감이 아니다** (4.5) | [x] |
| F6 | 취소 복구 | 전체 환불 | 카드 잔액 원복 | 원복 | [x] |
| F7 | 부분 환불 | 일부 환불 | 그만큼만 복구 | 그만큼만 | [x] |
| F8 | 운영 비활성 | 플래그 없이 | 동작하지 않음 | 지연 상수보다 **빨리** 끝나고 정상 승인된다(실측 21ms vs 300ms 상한). 상한은 프로바이더가 내보내는 상수를 그대로 쓰고, F4 가 대조군이다 — 화면에서만 옵션을 숨기고 서버가 여전히 자는 구현은 여기서 죽는다 | [x] |

**F8 이 증명하지 못하는 것도 적어 둔다.** 이것은 **관찰된 동작**이지 코드 경로의 부재가
아니다 — 살아 있는 `if (flag)` 와 분기 자체가 없는 것을 밖에서 구분할 수는 없다. 그리고
랜덤 거절은 애초에 만들지 않았으므로(4.6) 그 항목은 지금 비어 있는 보초다.
