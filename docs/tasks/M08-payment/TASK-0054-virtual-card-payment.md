# TASK-0054: 가상 카드 결제 · 실패 재현

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M08 결제 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/virtual-card-payment` |
| 선행 작업 | TASK-0053 |

## 1. 목적

가상 카드 프로바이더를 구현한다. **실패 시나리오를 의도적으로 만들 수 있는 것**이 이 TASK 의 핵심 가치다.

## 2. 범위

### 포함
- `VirtualCardProvider` 구현 (authorize/capture/cancel/refund/getStatus)
- 결제 승인 시 카드 원장 차감, 재고 예약 확정 연동
- **실패 시나리오 재현 장치**
  - 한도 초과 / 잔액 부족
  - 승인 거절 (카드 상태·랜덤)
  - 승인 지연 (N초 지연 후 응답)
  - 타임아웃
- 실패 유도 방법: 특정 한도 카드, 또는 개발용 헤더/플래그
- 취소·부분 환불 시 원장 복구
- 결제 화면 (카드 선택 → 즉시 승인)

### 제외
- 토스 연동 (TASK-0055)
- 실패 후 복구 처리 전반 (TASK-0057)

## 3. 요구사항

- [ ] 가상 카드로 결제하면 즉시 승인된다
- [ ] 한도를 넘으면 거절된다
- [ ] 승인 지연·타임아웃을 재현할 수 있다
- [ ] 취소·환불하면 카드 잔액이 복구된다
- [ ] 승인 시 재고 예약이 확정된다

## 4. 설계

| 실패 시나리오 | 유도 방법 |
| --- | --- |
| 한도 초과 | 한도가 낮은 카드를 발급해 사용 |
| 승인 거절 | 카드 상태를 `SUSPENDED` 로 변경 (4.1) |
| 승인 지연 | 데모 화면의 "지연 재현" 옵션 (개발·데모 환경만) |
| 타임아웃 | 지연 시간을 타임아웃 초과로 설정 |

**이 장치를 두는 이유**: 토스 테스트만으로는 실패 경로를 보여주기 어렵다. 결제가 실패했을 때 재고 예약이 풀리는지, 주문이 올바른 상태로 가는지를 시연할 수 있어야 한다. 포트폴리오에서 설명거리가 가장 많은 부분이다.

**운영 환경에서는 지연·랜덤 거절을 비활성화**한다. 한도 초과·카드 정지는 정상 기능이므로 유지한다.

### 4.1 카드 상태는 `BLOCKED` 가 아니라 `SUSPENDED` 다 (2026-09-05 정정)

위 표가 「카드 상태를 BLOCKED 로 변경」이라고 적었는데, TASK-0053 이 만든 상태는
`ACTIVE` · `SUSPENDED` · `DELETED` 셋이다. **되살릴 수 있는가**로 가른 이름이라
`SUSPENDED` 가 이 표가 뜻하는 것이다 — 실패를 재현하고 다시 정상으로 돌려놓을 수
있어야 시연이 된다.

### 4.2 승인이 예약을 확정하는 자리는 **주문 쪽**이다

「승인 시 재고 예약 확정」을 결제 서비스가 직접 하면 결제가 주문과 재고를 알게 된다.
그러면 토스 프로바이더가 붙는 날 같은 지식이 한 벌 더 생기거나, 결제 서비스가 두
프로바이더의 사정을 다 아는 자리가 된다.

그래서 **결제는 결제만 하고**, 「주문이 결제됐다」를 받는 자리를 주문 쪽에 둔다.
그 자리가 예약을 확정하고(TASK-0048 `confirm`) `SellerOrder` 를 `PAID` 로 옮긴다.
프로바이더가 무엇이든 그 뒤는 같다 — 그것이 D-031 이 말하는 추상화의 값이다.

### 4.3 실패했을 때 예약은 **유지된다** (F2)

풀지 않는다. 한도가 모자라 거절당한 사람이 다음에 할 일은 **다른 카드로 다시 하는
것**이고, 그때 재고가 이미 남에게 갔으면 그 시도는 무의미하다.

풀어 주는 것은 TTL 이다 — 15분이 지나면 만료 스케줄러가 가져간다(TASK-0051). 실패가
곧 포기는 아니라는 것이 이 설계의 전제이고, 「실패 후 복구 처리 전반」이 TASK-0057 의
몫인 이유도 같다.

### 4.4 실패 재현은 **환경변수로 완전히 차단한다** (F8 · R1)

지연과 랜덤 거절은 `PAYMENT_SIMULATION` 이 켜져 있을 때만 존재한다. 운영에서는 그
플래그가 없으므로 코드 경로 자체가 닫힌다.

**한도 초과와 카드 정지는 그 플래그와 무관하다.** 그것은 재현 장치가 아니라 정상
기능이고, 운영에서도 일어나야 한다 — 오히려 그 둘만으로 실패 시연의 대부분이 된다.

### 4.5 타임아웃은 「오래 걸린다」가 아니라 **「끊는다」**다 (F5)

지연을 아주 길게 잡는 것으로 타임아웃을 흉내 내면, 재는 것이 프로바이더가 아니라
검사의 인내심이 된다. 프로바이더가 자기 마감을 갖고 그것을 넘기면 **스스로 끊는다** —
그래야 「끊긴 뒤 상태가 일관적인가」를 초 단위로 재지 않고 물어볼 수 있다.

끊긴 결제는 `FAILED` 다. 저쪽이 실제로 승인했는지 우리가 모르는 상태이므로, 그 불일치를
찾아 고치는 것은 대사(TASK-0056 · 0057)의 몫이다.

## 5. 구현 계획

1. 프로바이더 구현체 골격
2. 승인 로직 (원장 차감 + 예약 확정)
3. 실패 시나리오 장치
4. 취소·환불 (원장 복구)
5. 결제 화면 (카드 선택·승인)
6. 실패 케이스 테스트
