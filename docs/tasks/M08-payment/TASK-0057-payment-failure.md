# TASK-0057: 결제 실패 · 복구 처리

| 항목 | 내용 |
| --- | --- |

| 상태 | 완료 |
| 작성일 | 2026-09-02 |

## 1. 목적

결제가 실패하거나 중간에 끊겼을 때 **재고·주문·결제 상태를 일관되게** 되돌린다. 가상 카드의 실패 재현 장치로 이 동작을 시연할 수 있게 한다.

## 2. 범위

### 포함
- 실패 유형별 처리: 승인 거절 / 타임아웃 / 사용자 이탈 / 서버 오류
- **승인은 됐는데 주문 확정이 실패한 경우 보상 처리** (자동 취소)
- 재고 예약 해제·유지 판단
- 재결제 흐름 (예약이 살아있으면 그대로, 만료됐으면 재예약)
- 실패 사유별 사용자 안내 메시지
- 실패 이력 조회 (관리자용)
- 미확정 결제 감지 배치 — 승인됐으나 주문이 완료되지 않은 건

### 제외
- 취소·반품 (M10)

## 3. 요구사항

- [x] 승인 거절 시 재고 예약이 유지되어 바로 재결제할 수 있다
- [x] ~~승인 후 주문 확정 실패 시 결제가 자동 취소된다~~ → **되감지 않고 마저 끝낸다** (4.2 · D-221). 되감는 것은 매입 없이 남은 승인이다
- [x] 예약 만료 후 재결제하면 재고를 다시 확인한다
- [x] 실패 사유가 사용자에게 이해되는 말로 표시된다 — 「확인 중」이 어휘에 늘었다
- [x] 결제됐는데 주문이 없는 상태가 남지 않는다 — 우리 흐름에서는 「주문이 없다」 대신 「주문이 안 끝났다」이고, 배치가 그것을 끝낸다

## 4. 설계

| 상황 | 재고 예약 | 결제 | 주문 |
| --- | --- | --- | --- |
| 승인 거절 | **유지** (재시도 대비) | FAILED | PAYMENT_PENDING 유지 |
| 사용자 이탈 | 해제 | 미생성 | PAYMENT_PENDING → 만료 시 FAILED |
| 승인 후 주문 확정 실패 | 해제 | **자동 취소** | 미생성 |
| 예약 만료 후 결제 시도 | 재예약 필요 | 진행 불가 | 재고 재확인 |

**"승인은 됐는데 주문이 없는 상태"가 가장 위험하다.** 사용자는 돈을 냈는데 주문이 없다. 이걸 감지하는 배치를 반드시 둔다.

### 4.1 재결제가 **주문을 하나 더 만든다** (TASK-0055 에서 넘어옴)

「재결제 흐름 — 예약이 살아있으면 그대로」는 화면이 자기가 만든 주문을 **기억하고
있을 때만** 성립한다. 지금 그 기억은 `usePayment` 의 ref 하나이고, 화면이 새로
마운트되면 사라진다.

새로 마운트되는 경로가 이미 둘이다.

| 언제 | 결과 |
| --- | --- |
| 카드가 거절돼 새로고침한 뒤 다시 결제 | 같은 `checkoutId` 로 **두 번째 `Order`** |
| 토스 결제창을 닫고 실패 화면 → 주문서로 돌아와 다시 결제 | 같음 (TASK-0055) |

**재고가 두 몫 잠기지는 않는다** — `OrderService.write` 는 이미 잡힌 예약을 보면
재예약을 건너뛴다. 남는 것은 **결제되지 않은 주문 한 건**이고, 그것이 주문 목록에
보이면 산 사람은 자기가 두 번 주문했다고 읽는다.

고치는 길이 둘이고 **둘 다 이 TASK 의 것**이다.

- `POST /orders` 를 `checkoutId` 기준 **멱등**으로 만든다 — 같은 주문서로 두 번째가
  오면 첫 번째를 돌려준다. 서버만 고치면 되고, 화면이 무엇을 기억하든 안전해진다.
- 리다이렉트 URL 에 주문 id 를 실어 주문서가 그것을 이어받게 한다 — 화면만 고치면
  되지만, 새로고침이라는 다른 경로는 여전히 남는다.

**앞쪽이 낫다.** 뒤쪽은 우리가 아는 경로만 막고, 이 문제의 성질은 「화면의 기억을
믿었다」이기 때문이다.

### 4.2 우리 흐름은 **주문이 먼저**다 — 4장의 표를 다시 적는다

4장의 표는 「승인 후 주문 저장」 순서를 전제로 쓰였다. 실제로 만들어진 흐름은 반대다
(TASK-0050 · 0054): **주문서 → 주문 → 결제 시작 → 승인 → 매입 → 주문 완료.**
결제를 걸 대상이 주문이라 주문이 먼저 있어야 하기 때문이다.

그래서 「승인은 됐는데 주문이 없다」는 상태가 **생기지 않는다.** 대신 그 자리에
다른 것이 있다: **매입은 끝났는데 주문이 완료되지 않았다**(`Payment.PAID` 인데
`SellerOrder.PAYMENT_PENDING`). `OrderService.markPaid` 가 매입 직후에 도는데,
그 사이에 프로세스가 죽으면 남는 모양이다.

**그때 보상은 되감기가 아니라 「마저 끝내기」다.** 돈은 이미 우리 쪽으로 왔고
사람은 물건을 기다린다 — 그것을 취소하는 것은 사고를 두 번째로 만드는 일이다.
`markPaid` 는 멱등하므로 배치가 그냥 다시 부르면 된다.

| 상황 | 재고 예약 | 결제 | 주문 | 보상 |
| --- | --- | --- | --- | --- |
| 승인 거절 | **유지** (재시도 대비) | `FAILED` | `PAYMENT_PENDING` 유지 | 없음 — 다른 카드로 다시 하면 된다 |
| 결제사에 닿지 못함 | **유지** | `UNRESOLVED` | 유지 | 대사가 푼다 (TASK-0056) |
| 사용자 이탈 (승인 전) | TTL 로 해제 | `READY` 로 남음 | 유지 → 결제 없이 남는다 | 없음 |
| **매입 후 주문 확정 실패** | 그대로 | `PAID` | `PAYMENT_PENDING` | **앞으로** — `markPaid` 재실행 |
| **승인만 하고 사라짐** | TTL 로 해제 | `AUTHORIZED` | 유지 | **뒤로** — 승인 취소 (4.3) |
| 예약 만료 후 결제 시도 | 재예약 필요 | 진행 불가 | 재고 재확인 | 없음 |

### 4.3 되감아야 하는 경우가 **하나** 있다 — 매입 없이 남은 `AUTHORIZED`

승인만 받고 사라진 결제다. 예약은 TTL 15분이 지나 풀리고 재고는 남에게 가는데,
**카드 쪽에는 돈이 잡혀 있다.** 가상 카드에서는 그 사람의 한도가 물려 있고(`charge`
가 승인 시점에 원장을 깎는다), 토스에서는 실제 카드의 승인이 살아 있다.

이것을 푸는 화살표가 **지금 없다.** `paymentTransitions` 에서 `AUTHORIZED` 가 갈 수
있는 곳은 `PAID` 뿐이고, `payment-rules.ts` 는 그 이유까지 적어 뒀다 — 「승인만 된
건을 무르는 것은 환불이 아니라 승인 취소이고, 설계 문서가 그 화살표를 그리지
않았으므로 여기에도 없다」.

**그래서 `AUTHORIZED → CANCELED` 를 더한다.** 환불(`PAID → …`)과 다른 길인 것이
중요하다 — 매입 전 취소는 프로바이더 API 도 다르고(`cancel` 대 `refund`) 수수료도
다르며, 우리 장부에서도 「돌려준 돈」이 아니라 「받은 적 없는 돈」이다. 포트에
`cancel` 이 이미 있고 지금까지 아무도 부르지 않았던 이유가 이것이다.

**감지 조건은 보수적이다** (R1). 매입까지 가는 정상 결제가 몇 초 만에 끝나는데,
그것을 취소해 버리면 사고를 우리가 만든다. 그래서 「승인된 지 오래됐고 + 그 주문에
살아 있는 예약이 없다」 둘을 함께 본다 — 뒤쪽이 곧 「이 결제로 살 수 있는 것이 이미
없다」는 뜻이다.

### 4.5 두 프로바이더에서 「승인 취소」가 **같은 말이 아니다**

포트의 `cancel` 은 하나지만 저쪽에서 일어나는 일이 다르다.

| | 가상 카드 | 토스 |
| --- | --- | --- |
| `AUTHORIZED` 라는 것은 | 승인 시점에 원장을 깎았다 | **이미 매입까지 끝났다** (토스의 승인 한 번이 둘 다다) |
| 취소가 하는 일 | 한도를 돌려준다 | 실제로 **돈을 돌려보낸다** |
| 우리 장부 | 받은 적 없는 돈 | 받은 적 없는 돈 |

**그래도 우리 쪽 이름은 하나다.** 우리가 아는 사실은 「매입 단계를 우리가 완료하지
못했다」이고, 그 결제로 살 수 있는 물건은 이미 없다 — 저쪽에서 돈이 어디까지 왔는지는
프로바이더의 사정이고, 그것을 우리 상태 이름에 반영하면 화면과 정산이 프로바이더를
알아야 한다.

토스에서 이 상태가 생기는 경로가 좁은 것도 적어 둔다: `confirm` 은 성공했는데 우리
`settle` 이 끝나지 못한 경우다. 그때 사람은 **돈을 낸 채 주문을 못 받은** 상태이므로,
배치가 되감아 주지 않으면 그 돈은 아무 데도 가지 않는다.

### 4.4 `POST /orders` 를 `checkoutId` 로 멱등하게 만든다 (이월)

TASK-0055 에서 넘어온 것이다. 화면이 새로 마운트되면 자기가 만든 주문을 잊고, 같은
주문서로 두 번째 주문이 만들어진다. **재고가 두 몫 잠기지는 않지만**(이미 잡힌
예약을 보면 재예약을 건너뛴다) 결제되지 않은 주문 한 건이 남고, 그것이 주문 목록에
보이면 산 사람은 자기가 두 번 주문했다고 읽는다.

같은 주문서로 두 번째가 오면 **첫 번째를 그대로 돌려준다.** `Order.checkoutId` 가
이미 유니크라 데이터베이스는 처음부터 그렇게 믿고 있었다 — 지금은 그 제약이 500 으로
드러날 뿐이고, 그것을 200 으로 바꾸는 일이다.

**실측**: 주문 멱등 7건 · 낙오 배치 통합 18건 · 낙오 규칙 단위(분기 100%) · 화면 「확인 중」 9건 +
axe 4건. 전체 게이트 4개 초록(**5,252건 통과** / 1건 skip).

**변이 시험으로 확인한 것** — 세 조건을 각각 빼고 돌려 **정확히 한 검사씩** 빨개지는 것을
보였다: `NOT EXISTS (… HELD)`(살아 있는 예약), `approvedAt <` (임계치), `updatedAt <`(앞쪽 유예).
즉 **두 조건이 AND 라는 사실이 검사로 증명된다** — 이것이 R1 이 요구한 「보수적인 감지」의 증거다.
