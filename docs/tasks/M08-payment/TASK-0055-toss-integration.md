# TASK-0055: 토스페이먼츠 연동

| 항목 | 내용 |

## 1. 목적

토스페이먼츠 테스트 환경을 연동한다. 실제 PG 결제창 흐름을 구현한 경험이 이 프로젝트의 어필 포인트다. (D-010)

## 2. 범위

### 포함
- 토스 결제위젯/결제창 연동 (프론트)
- 결제 요청 → 결제창 → 성공/실패 리다이렉트
- **서버 승인 API 호출** (결제창 성공 ≠ 승인 완료)
- 금액 검증 — 클라이언트가 보낸 금액과 서버 주문 금액 대조
- 취소·부분취소 API
- `TossProvider` 구현체
- 테스트 카드 안내 (데모 사용자용)

### 제외
- 웹훅 (TASK-0056)
- 실제 운영 키 사용

## 3. 요구사항

- [x] 토스 결제창으로 결제가 완료된다 — 우리 쪽 절반은 잰다(4.2). 진짜 결제창은 키를 넣고 눌러야 한다(6.4)
- [x] 결제창 성공 후 서버 승인까지 마쳐야 주문이 완료된다
- [x] 금액이 조작되면 승인이 거부된다 — **토스를 부르기 전에**
- [x] 취소·부분취소가 동작한다
- [x] 데모 사용자에게 테스트 카드 정보가 안내된다 — 번호가 아니라 링크로(4.7)

## 4. 설계

```
주문서 → 토스 결제창 (clientKey)
       → 성공 리다이렉트 (paymentKey, orderId, amount)
       → 서버: 주문 금액과 amount 대조 → 승인 API 호출 (secretKey)
       → 승인 성공 시 주문 PAID + 예약 확정
```

**금액 대조가 필수다.** 결제창에서 돌아온 금액을 그대로 믿고 승인하면 조작된 금액으로 결제될 수 있다. 서버에 저장된 주문 금액과 반드시 대조한다.

**결제창 성공만으로 완료 처리하지 않는다.** 서버 승인 API 가 최종 확정이다. 이 두 단계를 구분하지 않는 것이 PG 연동에서 가장 흔한 실수다.

### 4.1 키가 없어도 만든다 — 없으면 **프로바이더가 안 붙는다** (2026-09-05)

5장 1번이 「토스 테스트 키 발급」인데, 그것을 기다릴 이유가 없다. 이 저장소는 이미
같은 모양을 두 번 했다 — Google OAuth 와 R2 는 **자격증명이 없으면 그 기능만 없고
나머지는 그대로 돈다**(`AppConfig.googleOAuth`·`storage` 가 `null` 을 갖는다).

토스도 같다. 키가 둘 다 없으면 `TossProvider` 가 레지스트리에 **등록되지 않고**,
결제수단 목록에 나오지 않으며, 가상 카드만으로 전체 흐름이 완결된다(D-031).

**일부만 채우면 부팅이 거부된다.** 반쪽짜리 설정으로 뜨면 결제창은 열리는데 승인이
안 되고, 그 증상은 사용자에게 「결제 실패」로만 보인다 — 설정 실수를 사용자가 대신
겪는 모양이라 그러느니 안 뜨는 편이 낫다.

그래서 **CI 에도 키가 없다.** 검사는 토스 HTTP 를 가짜로 두고 우리 쪽 판단만 잰다 —
금액 대조, 상태 전이, 취소 누계. 진짜 결제창은 사람이 키를 넣고 눌러 보는 것이고,
그것은 검사가 대신할 수 없는 종류다.

### 4.2 재는 것은 **우리 쪽 절반**이다

이 TASK 의 값은 「토스가 잘 동작하는가」가 아니라 **「우리가 토스를 잘못 믿지 않는가」**다.
그중 하나가 F2 이고, 나머지도 전부 우리 코드에 있다.

| 재는 것 | 어디에 |
| --- | --- |
| 금액 대조 | 결제창이 돌려준 `amount` 를 **DB 의 주문 금액**과 맞춘다 |
| 승인 2단계 | 결제창 성공은 승인이 아니다. 서버 승인 API 가 최종 확정이다 |
| 취소 누계 | 부분 취소가 승인액을 넘지 못한다 |

토스 HTTP 자체는 가짜로 둔다. 진짜를 부르는 검사는 **네트워크와 남의 가동률에 따라
빨개지고**, 그때 고칠 것이 우리에게 없다.

### 4.3 `orderId` 는 우리 주문 id 가 아니라 **결제 id** 다

토스는 자기가 부르는 `orderId` 를 요구하고 그것으로 멱등을 판단한다. 거기에 우리
`Order.id` 를 주면 **한 주문에 결제를 두 번 시도할 수 없다** — 첫 시도가 실패해
다른 카드로 다시 하는 것이 정확히 그 경우다(TASK-0054 4.3).

그래서 `Payment.id` 를 준다. 결제 시도마다 새로 생기는 값이고, 그것이 토스가 뜻하는
「주문」에 더 가깝다.

### 4.4 secretKey 가 번들에 없다는 것을 **검사가 지킨다** (6.2 · R1)

「확인한다」로 두면 아무도 확인하지 않는다. `apps/shop/test/secret-key-containment.spec.ts`
가 그 확인을 대신한다 — 공개 접두어가 붙은 시크릿 이름, shop 소스에 등장한
`TOSS_SECRET_KEY`, 키 모양의 리터럴 셋을 찾는다. 사람이 이름을 잘못 짓는
순간(`NEXT_PUBLIC_` 을 붙이는 순간) 빨개진다.

**산출물이 아니라 이름을 본다.** 앱의 `test` 스크립트는 `vitest run` 하나뿐이라 CI 는
빌드 없이 테스트를 돌고, `.next` 가 있을 때만 도는 검사는 정작 PR 에서 한 번도 돌지
않는 장식이 된다. 그래서 초록의 뜻은 「번들이 깨끗함이 증명됐다」가 아니라 **「번들에
그 값이 들어갈 이름을 아무도 쓰지 않았다」**다.

### 4.5 테스트 카드 안내는 **가상 카드 아래**에 둔다 (R3)

가상 카드가 기본이고 토스가 선택지다. 데모 방문자가 토스 테스트 카드번호를 알 리
없으므로, 토스를 고른 사람에게만 그 번호를 보여 준다 — 처음부터 보여 주면 무엇을
골라야 하는지가 더 헷갈린다.

### 4.6 포트의 한 자리 이름을 고친다 — `cardId` → `methodRef`

TASK-0052 는 승인 요청의 한 자리를 「프로바이더마다 뜻이 달라도 되는 자리」라고
적어 두고 **첫 구현의 이름**을 붙였다(`AuthorizeRequest.cardId`). 두 번째 구현이
붙는 순간 그 이름이 거짓이 된다 — 토스가 그 자리에 넣는 것은 카드가 아니라
**결제창이 돌려준 `paymentKey`** 다.

이것이 「두 구현을 동시에 염두에 두고 만든다」가 실제로 검증되는 방식이다. 하나만
보고 만든 이름은 그 하나의 모양을 인터페이스로 굳히고, 두 번째가 올 때 드러난다.
`Payment.methodRef` 컬럼이 처음부터 이 뜻이었으므로 그 이름으로 맞춘다. 라우트의
요청 본문은 `cardId` 그대로다 — 가상 카드로 결제하는 화면이 보내는 것은 실제로
카드 id 이고, 바깥의 계약까지 바꿀 이유는 없다.

### 4.7 안내는 카드번호가 아니라 **링크**다 (F7)

테스트 카드번호를 화면에 박지 않는다. **확인할 수 없는 번호를 적는 것이 링크보다
나쁘기 때문**이다 — 번호는 저쪽 사정으로 바뀌고, 틀린 번호를 보고 세 번 실패한
사람은 우리 결제가 고장 났다고 결론 내린다. 「테스트 환경이라 실제로 청구되지
않는다」와 토스 문서로 가는 링크가 F7 이 요구하는 안내다.

### 4.8 SDK 는 스크립트로 붙인다 — 의존성을 늘리지 않는다 (8장)

`js.tosspayments.com/v2/standard` 를 동적으로 붙이고 `window.TossPayments` 를 쓴다.
npm 패키지를 넣으면 lockfile 이 바뀌어 **모든 워크트리가 재설치**해야 하고, 대역의
경계가 라이브러리 안으로 들어가 검사가 「우리가 무엇을 불렀는가」 대신 「라이브러리가
무엇을 불렀는가」를 흉내 내게 된다 — `google-oauth.client.ts` 가 같은 이유로 라이브러리
없이 `fetch` 세 번이다.

### 6.4 검사가 닿지 못하는 절반 — 사람이 눌러야 아는 것

**키가 없으므로 진짜 결제창은 한 번도 열린 적이 없다.** 그것이 4.1 이 선택한 대가이고,
숨기지 않고 적어 둔다. 키를 넣은 뒤 사람이 확인할 것:

| # | 무엇 | 왜 검사가 못 하나 |
| --- | --- | --- |
| 1 | 결제창이 실제로 뜨는가 | CDN 스크립트 로딩·`TossPayments(clientKey)` 호출이 모듈 경계에서 갈아 끼워진다. 검사가 증명하는 것은 **우리가 저쪽에 무엇을 어떤 모양으로 넘기는가**까지다 |
| 2 | v2 표준 결제창의 인자가 맞는가 | 저쪽 API 의 모양은 저쪽 사정이다. 틀리면 창이 안 뜬다 |
| 3 | 리다이렉트가 우리 쿼리를 보존하는가 | 「주문서로 돌아가기」가 우리가 실어 보낸 `?checkout=` 위에 서 있다. 토스가 덮어쓰면 `/cart` 로 떨어지고, **그 폴백은 검사로 덮어 뒀다** |
| 4 | 승인이 실제로 나는가 | 토스 HTTP 는 대역이다(4.2). 진짜를 부르는 검사는 남의 가동률에 따라 빨개지고 그때 우리에게 고칠 것이 없다 |
