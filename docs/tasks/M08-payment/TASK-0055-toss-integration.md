# TASK-0055: 토스페이먼츠 연동

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M08 결제 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/toss-integration` |
| 선행 작업 | TASK-0052 |

## 1. 목적

토스페이먼츠 테스트 환경을 연동한다. 실제 PG 결제창 흐름을 구현한 경험이 이 프로젝트의 어필 포인트다. (D-010)

## 2. 범위

### 포함
- 토스 결제위젯/결제창 연동 (프론트)
- 결제 요청 → 결제창 → 성공/실패 리다이렉트
- **서버 승인 API 호출** (결제창 성공 ≠ 승인 완료)
- 금액 검증 — 클라이언트가 보낸 금액과 서버 주문 금액 대조
- 취소·부분취소 API
- `TossProvider` 구현체
- 테스트 카드 안내 (데모 사용자용)

### 제외
- 웹훅 (TASK-0056)
- 실제 운영 키 사용

## 3. 요구사항

- [ ] 토스 결제창으로 결제가 완료된다
- [ ] 결제창 성공 후 서버 승인까지 마쳐야 주문이 완료된다
- [ ] 금액이 조작되면 승인이 거부된다
- [ ] 취소·부분취소가 동작한다
- [ ] 데모 사용자에게 테스트 카드 정보가 안내된다

## 4. 설계

```
주문서 → 토스 결제창 (clientKey)
       → 성공 리다이렉트 (paymentKey, orderId, amount)
       → 서버: 주문 금액과 amount 대조 → 승인 API 호출 (secretKey)
       → 승인 성공 시 주문 PAID + 예약 확정
```

**금액 대조가 필수다.** 결제창에서 돌아온 금액을 그대로 믿고 승인하면 조작된 금액으로 결제될 수 있다. 서버에 저장된 주문 금액과 반드시 대조한다.

**결제창 성공만으로 완료 처리하지 않는다.** 서버 승인 API 가 최종 확정이다. 이 두 단계를 구분하지 않는 것이 PG 연동에서 가장 흔한 실수다.

### 4.1 키가 없어도 만든다 — 없으면 **프로바이더가 안 붙는다** (2026-09-05)

5장 1번이 「토스 테스트 키 발급」인데, 그것을 기다릴 이유가 없다. 이 저장소는 이미
같은 모양을 두 번 했다 — Google OAuth 와 R2 는 **자격증명이 없으면 그 기능만 없고
나머지는 그대로 돈다**(`AppConfig.googleOAuth`·`storage` 가 `null` 을 갖는다).

토스도 같다. 키가 둘 다 없으면 `TossProvider` 가 레지스트리에 **등록되지 않고**,
결제수단 목록에 나오지 않으며, 가상 카드만으로 전체 흐름이 완결된다(D-031).

**일부만 채우면 부팅이 거부된다.** 반쪽짜리 설정으로 뜨면 결제창은 열리는데 승인이
안 되고, 그 증상은 사용자에게 「결제 실패」로만 보인다 — 설정 실수를 사용자가 대신
겪는 모양이라 그러느니 안 뜨는 편이 낫다.

그래서 **CI 에도 키가 없다.** 검사는 토스 HTTP 를 가짜로 두고 우리 쪽 판단만 잰다 —
금액 대조, 상태 전이, 취소 누계. 진짜 결제창은 사람이 키를 넣고 눌러 보는 것이고,
그것은 검사가 대신할 수 없는 종류다.

### 4.2 재는 것은 **우리 쪽 절반**이다

이 TASK 의 값은 「토스가 잘 동작하는가」가 아니라 **「우리가 토스를 잘못 믿지 않는가」**다.
그중 하나가 F2 이고, 나머지도 전부 우리 코드에 있다.

| 재는 것 | 어디에 |
| --- | --- |
| 금액 대조 | 결제창이 돌려준 `amount` 를 **DB 의 주문 금액**과 맞춘다 |
| 승인 2단계 | 결제창 성공은 승인이 아니다. 서버 승인 API 가 최종 확정이다 |
| 취소 누계 | 부분 취소가 승인액을 넘지 못한다 |

토스 HTTP 자체는 가짜로 둔다. 진짜를 부르는 검사는 **네트워크와 남의 가동률에 따라
빨개지고**, 그때 고칠 것이 우리에게 없다.

### 4.3 `orderId` 는 우리 주문 id 가 아니라 **결제 id** 다

토스는 자기가 부르는 `orderId` 를 요구하고 그것으로 멱등을 판단한다. 거기에 우리
`Order.id` 를 주면 **한 주문에 결제를 두 번 시도할 수 없다** — 첫 시도가 실패해
다른 카드로 다시 하는 것이 정확히 그 경우다(TASK-0054 4.3).

그래서 `Payment.id` 를 준다. 결제 시도마다 새로 생기는 값이고, 그것이 토스가 뜻하는
「주문」에 더 가깝다.

### 4.4 secretKey 가 번들에 없다는 것을 **검사가 지킨다** (6.2 · R1)

「확인한다」로 두면 아무도 확인하지 않는다. 빌드 산출물에서 `TOSS_SECRET_KEY` 와
`test_sk_` 접두어를 찾는 검사를 둔다 — 사람이 이름을 잘못 짓는 순간(`NEXT_PUBLIC_`
을 붙이는 순간) 빨개진다.

### 4.5 테스트 카드 안내는 **가상 카드 아래**에 둔다 (R3)

가상 카드가 기본이고 토스가 선택지다. 데모 방문자가 토스 테스트 카드번호를 알 리
없으므로, 토스를 고른 사람에게만 그 번호를 보여 준다 — 처음부터 보여 주면 무엇을
골라야 하는지가 더 헷갈린다.

## 5. 구현 계획

1. 토스 테스트 키 발급, 환경변수 등록
2. 프론트 결제위젯 연동
3. 성공·실패 리다이렉트 처리
4. 서버 승인 API + 금액 대조
5. `TossProvider` 구현 (취소·환불 포함)
6. 테스트 카드 안내 UI
7. 실패 경로 테스트
