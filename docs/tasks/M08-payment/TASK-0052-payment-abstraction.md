## 1. 목적

결제 도메인 스키마와 프로바이더 인터페이스를 만든다. 두 구현이 같은 계약을 따르게 한다.

## 2. 범위

### 포함
- `Payment` — 주문, 프로바이더, 상태, 승인액, 누적취소액, 외부 결제키, 승인시각
- `PaymentEvent` — 상태 변화·웹훅 원문 로그
- `Refund` — 부분 환불 N건
- `PaymentProvider` 인터페이스: `authorize` / `capture` / `cancel` / `refund` / `getStatus`
- 프로바이더 레지스트리 (주문의 결제수단에 따라 구현 선택)
- 결제 상태 머신 구현
- 금액 검증 — 취소·환불 누계가 승인액을 넘지 않음

### 제외
- 각 프로바이더 구현 (TASK-0054, 0055)
- 웹훅 (TASK-0056)

## 3. 요구사항

- [ ] 두 프로바이더가 같은 인터페이스로 호출된다
- [ ] 결제 상태 전이가 정의된 경로만 허용된다
- [ ] 부분 환불을 여러 번 기록할 수 있다
- [ ] 환불 누계가 승인액을 초과할 수 없다
- [ ] 모든 상태 변화가 이벤트로 남는다

## 4. 설계

```ts
interface PaymentProvider {
  authorize(req): Promise<AuthorizeResult>   // 승인
  capture(paymentKey, amount): Promise<...>  // 매입 확정
  cancel(paymentKey, amount, reason)         // 취소(부분 가능)
  refund(paymentKey, amount, reason)         // 환불(부분 가능)
  getStatus(paymentKey)                      // 조회 (대사용)
}
```

상태 전이는 `docs/design/state-machines.md` 3장을 따른다.

**`PaymentEvent` 를 두는 이유**: 결제는 외부 시스템과의 대화라 "무슨 일이 있었는지"가 로그로 남아야 한다. 분쟁이나 불일치 조사의 유일한 근거다.

## 5. 구현 계획

1. 스키마·인덱스·마이그레이션
2. 인터페이스·타입 정의 (`packages/shared`)
3. 프로바이더 레지스트리
4. 상태 머신 + 전이 검증
5. 금액 검증 로직
6. 이벤트 기록 공통 처리
