## 1. 목적

결제 도메인 스키마와 프로바이더 인터페이스를 만든다. 두 구현이 같은 계약을 따르게 한다.

## 2. 범위

### 포함
- `Payment` — 주문, 프로바이더, 상태, 승인액, 누적취소액, 외부 결제키, 승인시각
- `PaymentEvent` — 상태 변화·웹훅 원문 로그
- `Refund` — 부분 환불 N건
- `PaymentProvider` 인터페이스: `authorize` / `capture` / `cancel` / `refund` / `getStatus`
- 프로바이더 레지스트리 (주문의 결제수단에 따라 구현 선택)
- 결제 상태 머신 구현
- 금액 검증 — 취소·환불 누계가 승인액을 넘지 않음

### 제외
- 각 프로바이더 구현 (TASK-0054, 0055)
- 웹훅 (TASK-0056)

## 3. 요구사항

- [ ] 두 프로바이더가 같은 인터페이스로 호출된다
- [ ] 결제 상태 전이가 정의된 경로만 허용된다
- [ ] 부분 환불을 여러 번 기록할 수 있다
- [ ] 환불 누계가 승인액을 초과할 수 없다
- [ ] 모든 상태 변화가 이벤트로 남는다

## 4. 설계

```ts
interface PaymentProvider {
  authorize(req): Promise<AuthorizeResult>   // 승인
  capture(paymentKey, amount): Promise<...>  // 매입 확정
  cancel(paymentKey, amount, reason)         // 취소(부분 가능)
  refund(paymentKey, amount, reason)         // 환불(부분 가능)
  getStatus(paymentKey)                      // 조회 (대사용)
}
```

상태 전이는 `docs/design/state-machines.md` 3장을 따른다.

**`PaymentEvent` 를 두는 이유**: 결제는 외부 시스템과의 대화라 "무슨 일이 있었는지"가 로그로 남아야 한다. 분쟁이나 불일치 조사의 유일한 근거다.

### 4.1 프로바이더 포트는 `packages/shared` 가 아니라 `apps/api` 에 둔다 (2026-09-05)

5장이 「인터페이스·타입 정의 (`packages/shared`)」라고 적었는데, 그 인터페이스는
**선을 넘어가지 않는다.** 브라우저는 결제사와 직접 말하지 않고, 화면이 아는 것은
`Payment` 의 상태와 금액뿐이다.

그래서 갈라 둔다.

| 어디에 | 무엇이 |
| --- | --- |
| `packages/shared/src/api/payments.ts` | 선을 넘어가는 모양 — 상태·프로바이더 이름·`Payment`·`Refund` |
| `apps/api/src/payment/payment-provider.ts` | 포트 — `authorize`·`capture`·`cancel`·`refund`·`getStatus` |

공유 패키지에 포트를 두면 브라우저 번들이 서버의 개념을 들고 다니게 되고, 그것은
「공유」가 아니라 **「어디에 둘지 안 정했다」**는 뜻이다.

### 4.2 레지스트리는 **비어 있는 채로** 시작한다

구현은 TASK-0054(가상 카드)와 TASK-0055(토스)가 넣는다 — 이 TASK 의 「제외」에
그렇게 적혀 있다. 그래서 여기서 만드는 것은 **고르는 자리**뿐이고, 검사는 가짜
프로바이더를 등록해 F1 을 잰다.

없는 프로바이더를 물으면 **던진다.** 조용히 아무것도 안 하는 것이 최악인데, 결제에서
그 모양은 「돈이 안 빠졌는데 주문은 됐다」이기 때문이다.

### 4.3 거절은 예외가 아니라 값이다

한도 초과와 승인 거절은 **프로그램의 오류가 아니라 정상적인 대답**이다. 던지면
부르는 쪽이 「진짜 오류」와 구분하려고 예외 타입을 뒤지게 된다 — `authorize` 는
`{ approved, paymentKey, reason }` 을 돌려주고, 던지는 것은 **결제사에 닿지 못했을
때**다.

### 4.4 환불 상한은 애플리케이션과 DB 가 **둘 다** 지킨다

F4 는 애플리케이션의 판단이고, `Payment_canceledAmount_check`
(`0 <= canceledAmount <= authorizedAmount`)는 같은 규칙을 데이터베이스에 적어 둔
것이다. 두 벌인 이유는 F6 이다 — 동시에 들어온 두 환불이 각자 「아직 여유가 있다」를
읽는 것이 그 경합이고, 지는 쪽을 최종적으로 거절하는 것은 제약이다.

**돈이 걸린 자리에서 방어선이 하나뿐이면 안 된다.** 재고에서 이미 같은 판단을 했다
(`ProductVariant_reserved_check`, TASK-0048).

### 4.5 `PaymentEvent` 는 상태를 **안 바꾼 사건**도 남긴다

그래서 `kind` 가 상태 이름과 따로 있다. 같은 웹훅이 두 번 오면 두 번째는 아무 상태도
바꾸지 않지만(TASK-0056 의 멱등), **그것이 왔다는 사실은 남아야 한다** — 분쟁이나
불일치 조사에서 유일한 근거가 이 로그다.

`PaymentEvent_transition_check` 가 「전후가 둘 다 있거나 둘 다 없다」를 지킨다. 한쪽만
있는 행은 읽는 사람이 「어디서 왔는지 모르겠다」로 끝나는 기록이다.

## 5. 구현 계획

1. 스키마·인덱스·마이그레이션
2. 인터페이스·타입 정의 (`packages/shared`)
3. 프로바이더 레지스트리
4. 상태 머신 + 전이 검증
5. 금액 검증 로직
6. 이벤트 기록 공통 처리
