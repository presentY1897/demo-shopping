# TASK-0056: 결제 웹훅 (멱등 처리)

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M08 결제 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/payment-webhook` |
| 선행 작업 | TASK-0055 |

## 1. 목적

토스 웹훅을 수신해 결제 상태를 동기화한다. **웹훅은 중복 도착과 순서 뒤바뀜을 전제로 설계**한다.

## 2. 범위

### 포함
- 웹훅 엔드포인트 (인증·서명 검증)
- **멱등 처리** — 같은 이벤트가 여러 번 와도 한 번만 반영
- 순서 역전 처리 (오래된 이벤트가 나중에 도착)
- 원문을 `PaymentEvent` 에 보존
- 처리 실패 시 재시도 큐
- 웹훅 미수신 대비 **대사(reconciliation) 배치** — 주기적으로 토스 상태 조회 후 대조
- **`UNRESOLVED` 상태 추가** (D-220) — 닿지 못한 승인이 갇히지 않게 한다
- 헬스체크에 마지막 웹훅 수신 시각

### 제외
- 가상 카드 (웹훅 없음, 동기 처리)

## 3. 요구사항

- [ ] 같은 웹훅이 3번 와도 상태가 한 번만 변경된다
- [ ] 오래된 이벤트가 나중에 와도 최신 상태를 덮어쓰지 않는다
- [ ] 서명이 유효하지 않으면 거부된다
- [ ] 웹훅을 놓쳐도 대사 배치가 상태를 맞춘다
- [ ] **닿지 못한 승인이 `UNRESOLVED` 로 남고, 대사가 그것을 승인 또는 실패로 보낸다**
- [ ] 모든 웹훅 원문이 보존된다

## 4. 설계

```
웹훅 수신 → ① 서명 검증
           ② eventId 로 중복 확인 (이미 처리했으면 200 반환하고 종료)
           ③ 이벤트 시각과 현재 상태 비교 → 오래된 이벤트면 기록만 하고 무시
           ④ 상태 반영
           ⑤ PaymentEvent 기록
```

**중복에도 200 을 반환한다.** 에러를 반환하면 PG 가 계속 재전송한다.

**대사 배치**를 두는 이유: 웹훅은 유실될 수 있다. 결제는 돈이 걸린 영역이라 "못 받았으면 그만"이 허용되지 않는다. 주기적으로 PENDING·불일치 결제를 조회해 실제 상태와 맞춘다.

### 4.1 닿지 못한 승인은 **`UNRESOLVED`** 다 — 상태를 하나 더한다 (D-220)

TASK-0055 의 승인은 토스에 닿지 못하면(`TOSS_UNREACHABLE`) 결제를 `FAILED` 로 적었다.
낙관적으로 `AUTHORIZED` 로 두면 그 불일치가 **매입할 때가 되어서야 돈으로** 나타나기
때문이고, 그 판단 자체는 옳다.

문제는 그다음이었다. `paymentTransitions` 에서 **`FAILED` 는 나가는 화살표가 없는
종착지**인데, 닿지 못했다는 것은 「거절당했다」가 아니라 **「승인됐는지 우리가
모른다」**이고 실제로 저쪽에서는 승인이 나 있을 수 있다. 그때 이 TASK 의 대사
배치(F6)가 그 결제를 찾아내도 **옮길 곳이 없었다.**

**상태를 하나 더한다.** 사용자가 2026-09-05 에 승인했고 근거는 D-220 이다.

```
READY ──→ AUTHORIZED ──→ PAID
  │           ↑
  ├──→ FAILED │
  │           │
  └──→ UNRESOLVED ──┴──→ FAILED
```

| 규칙 | 왜 |
| --- | --- |
| **닿지 못했을 때만** 들어간다 | 거절은 답이다. 답이 있으면 `FAILED` 다 |
| 나가는 길은 **대사만** 연다 | 사용자의 조작으로 옮길 근거가 우리에게 없다 |
| 매입이 아니라 `AUTHORIZED` 로 나간다 | 「승인된 결제를 매입한다」가 한 곳에만 있게 된다 |
| 그동안 **주문 미완료 · 예약 유지** | 놓아 버리면 대사가 「승인됐다」를 확인해도 팔 물건이 없다 |
| 화면은 **「확인 중, 다시 결제하지 마세요」** | 거절과 문장이 달라야 한다. 그것이 상태를 나눈 이유다 |

### 4.2 그래서 프로바이더가 **셋을 구분해 답해야** 한다

`AuthorizeResult` 는 `{ approved, paymentKey, reason }` 이었다. 불리언 하나로는 「거절」과
「모름」을 말할 수 없어, **판별 유니온**으로 바꾼다.

```ts
type AuthorizeResult =
  | { outcome: 'approved'; paymentKey: string }
  | { outcome: 'declined'; reason: string }
  | { outcome: 'unknown'; reason: string }
```

덤으로 타입이 정확해진다 — 예전 모양은 `paymentKey` 가 승인됐을 때만 있는데도 늘
`string | null` 이라, 부르는 쪽이 있을 리 없는 널을 매번 확인했다.

**가상 카드는 `unknown` 을 내지 않는다.** 우리 프로세스 안에서 트랜잭션으로 끝나 「모르는」
결과가 생길 수 없기 때문이고, 재현 장치의 `timeout` 모드도 한도를 쓰기 **전에** 돌아오므로
불일치가 없다. 이 상태는 **남의 서버가 있는 프로바이더의 것**이다.

## 5. 구현 계획

1. 웹훅 엔드포인트 + 서명 검증
2. 멱등 키 저장·확인
3. 순서 역전 처리
4. 상태 반영 + 이벤트 기록
5. 실패 재시도
6. 대사 배치
7. 헬스체크 연동
