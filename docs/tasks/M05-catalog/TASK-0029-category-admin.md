# TASK-0029: 관리자 카테고리 관리 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M05 카탈로그 |
| 상태 | 완료 |

| 브랜치 | `feature/category-admin` |
| 선행 작업 | TASK-0028 |

## 1. 목적

관리자가 코드 수정 없이 카테고리를 추가·이동·정렬할 수 있게 한다.

## 2. 범위

### 포함
- 트리 뷰 (펼침·접힘)
- 추가·수정·비활성화
- 드래그로 이동·정렬 (또는 버튼 방식)
- 삭제 제한 — 하위나 상품이 있으면 비활성화만 허용
- 변경 즉시 반영 확인

### 제외
- 속성 관리 (TASK-0031)
- 카테고리별 수수료율 (M12)

## 3. 요구사항

- [ ] 트리 구조가 시각적으로 보인다
- [ ] 카테고리를 추가하면 즉시 상품 등록 폼의 선택지에 나타난다
- [ ] 상품이 있는 카테고리는 삭제되지 않는다
- [ ] 이동은 즉시 반영되고 이름 수정은 저장 버튼을 눌러야 반영된다
- [ ] 동시 수정 시 나중 저장이 앞선 변경을 덮어쓰지 않는다
- [ ] 동시 이동 시 트리가 깨지지 않는다

## 4. 설계

삭제 대신 **비활성화**를 기본으로 한다. 카테고리를 지우면 그 카테고리에 속한 상품과 과거 주문의 분류가 깨진다.

드래그 이동은 접근성 문제가 있으므로 **키보드로도 이동 가능한 대체 수단**(위/아래/상위/하위 버튼)을 함께 제공한다.

### 반영 시점 — 조작에 따라 다르다

| 조작 | 방식 | 이유 |
| --- | --- | --- |
| 이동·정렬 | **즉시 반영** (드래그 놓는 순간 저장) | 트리 조작은 결과를 눈으로 확인하며 하는 작업이다. 저장 버튼을 두면 "지금 화면이 저장된 상태인가"가 모호해진다 |
| 이름·설명·활성 여부 | **폼 + 저장 버튼** | 입력 중간 상태가 저장되면 안 된다 |

즉시 반영 조작은 실패 시 **원래 위치로 되돌리고** 토스트로 알린다.

### 동시 수정 처리

두 관리자가 같은 카테고리를 동시에 다루는 상황을 두 가지로 나눈다.

**① 필드 수정 충돌 — 낙관적 잠금**

`Category` 에 `version` 컬럼을 둔다. 저장 시 읽어온 버전을 함께 보내고, DB 의 버전과 다르면 거부한다.

```
UPDATE category SET name=?, version=version+1
WHERE id=? AND version=?        ← 0건 갱신이면 충돌
```

충돌 시 화면: "다른 관리자가 이 카테고리를 수정했습니다. 최신 내용을 불러올까요?" — 상대 변경을 덮어쓰지 않는다. 마지막 저장이 이기는 방식(last-write-wins)은 조용히 남의 작업을 지운다.

**② 트리 이동 충돌 — 직렬화**

이동은 자신과 하위 전체의 `path` 를 재계산하므로, 두 이동이 겹치면 트리가 깨진다. 낙관적 잠금으로는 부족하다.

트리 이동 전체를 **DB 어드바이저리 락으로 직렬화**한다. 한 번에 하나의 이동만 실행되고 나머지는 대기한다. 카테고리 이동은 드문 작업이라 대기 비용이 문제되지 않는다.

**트랜잭션 수행 시간 동안**: 이동 트랜잭션은 자신과 하위 노드만 잠근다. 40개 규모에서 수십 ms 다. 조회는 잠기지 않으므로 다른 관리자의 화면이 멈추지 않는다.

### 화면 구성

`apps/admin` 의 `/categories` 한 페이지다. 콘솔 레이아웃(사이드바·헤더)은 TASK-0019 가 만들므로
여기서는 `<main>` 한 겹만 두고, 0019 가 페이지 본문을 그대로 옮겨 담을 수 있게 한다.

```
/categories
├─ 트리                 role="tree" · 펼침·접힘 · 로빙 탭인덱스
├─ 작업 막대            선택한 노드에 대한 위/아래/상위로/하위로 · 수정 · 비활성화 · 삭제
└─ 대화상자 3종         추가·수정 폼 / 삭제·비활성화 확인 / 수정 충돌(409)
```

**서버 렌더는 아무것도 기다리지 않는다.** 무료 플랜 API 는 절전에서 깨는 데 최대 90초가 걸리고,
서버 컴포넌트에서 트리를 `await` 하면 그 시간 동안 마크업이 한 글자도 나가지 않는다(TASK-0101 4.3).
트리 조회는 클라이언트 컴포넌트의 이펙트에서 일어나고, 그 대가로 화면은 로딩·빈·에러·정상 네 상태를
모두 갖는다(U1).

### 드래그를 넣지 않는다 — 버튼과 키보드만

2장은 "드래그로 이동·정렬 (또는 버튼 방식)"을 열어 두었고, 4장은 드래그를 넣더라도 키보드 대체
수단이 **필수**라고 적었다. 그러면 대체 수단 쪽이 이미 완전한 조작 경로이므로, 드래그는 같은
뮤테이션에 얹히는 **두 번째 입력 경로**가 된다. 그것을 넣지 않기로 한다.

| 근거 | 내용 |
| --- | --- |
| 접근성 | 키보드 경로가 1급 시민이어야 한다(U5). 드래그를 먼저 만들면 키보드는 언제나 나중이 되고, 실제로 그렇게 빠진다 |
| 검증 가능성 | 프론트 테스트는 jsdom 이다. HTML5 드래그 이벤트는 jsdom 에서 의미 있게 재현되지 않아, **드래그 경로만 게이트를 통과하지 않은 채 머지**된다 |
| 의존성 | 드래그 라이브러리(dnd-kit 등)를 하나 더 고정하지 않는다. 8장의 "드래그 라이브러리"는 **없음**으로 확정한다 |
| 밀도 | 콘솔은 밀도 2단계 고정(D-033)이라 행 높이가 일정하다. 버튼 4개 막대가 흔들릴 여지가 없다 |

대신 키보드 조작을 **아웃라인 편집기 수준**으로 만든다.

| 키 | 동작 |
| --- | --- |
| `↑` `↓` | 보이는 노드 사이 이동 (접힌 하위는 건너뛴다) |
| `→` | 접혀 있으면 펼치고, 펼쳐져 있으면 첫 하위로 |
| `←` | 펼쳐져 있으면 접고, 접혀 있으면 상위로 |
| `Home` `End` | 첫 노드 · 마지막 노드 |
| `Alt+↑` `Alt+↓` | 형제 사이에서 **순서 이동** |
| `Alt+←` `Alt+→` | **상위로 꺼내기 · 이전 형제의 하위로 넣기** |

**작업 버튼은 트리 안이 아니라 트리 밖 작업 막대에 둔다.** `role="treeitem"` 안에 포커스 가능한
버튼을 넣으면 **트리가 탭 정지 하나라는 성질이 깨진다.** WAI-ARIA 트리는 위젯 전체가 탭 정지
하나이고 안쪽은 화살표로 걷는다 — 행마다 버튼 4개를 넣으면 Tab 이 40행 × 4번 멈추고, 행 안의
컨트롤로 들어가는 별도 키 규약(treegrid 패턴)이 필요해진다.

> **axe 는 이것을 잡지 못한다.** 확인해 봤다 — `treeitem` 안에 `<button>` 을 넣고 접근성 스펙을
> 돌렸더니 9/9 통과했다. `nested-interactive` 규칙은 **자식이 presentational 인 역할**(button ·
> checkbox · tab 등)만 대상으로 하고 `treeitem` 은 거기 들지 않는다. 게이트가 잡아 주지 않는
> 판단이라서 문서에 적고, `Tab` 이 트리를 벗어나는지 확인하는 스펙을 따로 둔다.

### 이동을 어떤 요청으로 표현하는가

| 조작 | 요청 | 이유 |
| --- | --- | --- |
| 위로 · 아래로 | `POST /categories/reorder` — 해당 상위의 하위 **전체 순서** | 계약이 그렇게 정의돼 있다. "나를 3번째로" 두 개가 겹치면 아무도 요청하지 않은 순서가 남는다 |
| 상위로 · 하위로 | `POST /categories/:id/move` — `sortOrder` 생략 | 생략하면 새 상위의 **마지막**에 붙는다. 위치까지 한 번에 지정하려면 move + reorder 두 번이 되고, 둘 사이는 원자적이지 않다. 붙인 뒤 위/아래로 옮기는 편이 결과가 예측 가능하다 |

### 낙관적 반영과 원위치

이동·정렬은 응답을 기다리지 않고 화면을 먼저 바꾼다. 이때 **로컬 상태가 고쳐 쓰는 필드는
`parentId` 와 `sortOrder` 둘뿐**이다. `path` 와 `depth` 는 서버가 하위 전체를 재계산해야 알 수 있는
값이라, 화면이 흉내 내면 응답이 오기 전까지 **거짓말하는 필드**가 된다. 그래서 화면의 행 타입은
`Omit<CategoryNode, 'path' | 'depth'>` 이고, 들여쓰기 단계는 `parentId` 사슬에서 매번 계산한다.

성공하면 응답에 담겨 온 노드로 해당 행을 덮어쓴다(재조회 없음 — `move` 도 `reorder` 도 `version` 을
올리지 않으므로 나머지 행은 그대로 유효하다). 실패하면 요청 직전의 스냅샷으로 되돌리고 토스트로
알린다.

### 409 를 화면이 구분하는 방법

API 의 오류 봉투는 상태 코드에서 코드를 만든다 — **409 는 전부 `CONFLICT`** 이고, 무엇이 충돌했는지는
`details[0]` 의 한국어 문장에만 있다. 화면이 그 문장을 문자열 비교하면 API 의 문구를 고치는 순간
조용히 깨진다. 그래서 **어느 요청이 409 를 받았는지**로 나눈다.

| 요청 | 409 의 의미 | 화면 |
| --- | --- | --- |
| `POST /categories` | 슬러그 중복뿐 | 슬러그 필드에 오류 표시 (U2) |
| `PATCH /categories/:id` | 낙관적 잠금 **또는** 슬러그 중복 | 트리를 다시 읽어 **버전을 비교**한다. 보낸 버전과 다르면 잠금 충돌, 같으면 슬러그 중복 |
| `DELETE /categories/:id` | 하위가 남아 있음 | 삭제 거부 안내 + 비활성화로 유도 |

잠금 충돌일 때는 **덮어쓰지 않는다.** 대화상자에 서버의 현재 값과 내가 입력한 값을 나란히 놓고 두 갈래를 준다.

- **최신 내용 불러오기** — 폼을 서버 값으로 갈아끼우고 버전을 새로 잡는다. 저장은 하지 않는다
- **내 입력으로 덮어쓰기** — 새 버전으로 다시 저장한다. 사람이 화면에서 상대 변경을 보고 고른 결과다

> 이것이 계약의 빈틈이다. 화면이 `error.code` 하나로 갈래를 나눌 수 없어 **요청 종류 + 버전 비교**라는
> 우회를 쓴다. 코드를 세분(`CATEGORY_VERSION_CONFLICT` · `CATEGORY_SLUG_TAKEN` ·
> `CATEGORY_HAS_CHILDREN`)하는 것이 옳지만, `packages/shared` 와 `apps/api` 는 TASK-0030 이
> 작업 중이라 이번 범위에서 건드리지 않는다. 후속 TASK 로 넘긴다.

### 삭제 제한 — 두 겹

| 겹 | 무엇을 막나 | 어떻게 |
| --- | --- | --- |
| 화면 | **하위가 있는 카테고리** | 트리가 이미 알고 있으므로 삭제 버튼을 비활성화하고 사유를 적는다. 비활성화 버튼만 남는다 |
| 서버 | 그 외 전부 | `DELETE` 의 409 를 그대로 보여주고 비활성화로 유도한다 |

**상품이 있는 카테고리는 이번에 화면이 미리 막을 수 없다.** `Product` 모델이 아직 없고(M05 후속),
`CategoryNode` 에 상품 수가 없어서 트리만으로는 알 수 없다. 서버가 상품을 세기 시작하면 그때도
화면은 같은 자리(409 안내)에서 받는다. 미리 막으려면 `CategoryNode` 에 `productCount` 가 필요하다 —
계약 변경이므로 후속 TASK 로 남긴다.

### 폼 규약은 여기서 확정하지 않는다

TASK-0017 이 폼 시스템의 표준(필드 오류 표시·서버 오류 매핑·제출 중 잠금)을 세우는 중이다. 이 TASK 는
그것을 발명하지 않고, **`apps/admin/src/form/` 한 곳에** 최소 구현을 모아 둔다. 0017 이 머지되면 이
디렉터리를 지우고 import 를 바꾸는 것으로 끝나야 한다.

## 5. 구현 계획

1. **모킹 먼저** — `packages/api-mocks` 에 카테고리 경로·픽스처(40개 3단계 트리)와 **상태를 가진
   핸들러**. 슬러그 중복·버전 충돌·하위 존재 거부를 실제 API 와 같은 상태 코드로 낸다
2. 순수 로직 — 평탄화·보이는 순서·이동 가능 판정 (`lib/categories/tree.ts`)
3. 오류 매핑 — `ApiClientError` → 닫힌 사유 집합 (`lib/categories/errors.ts`)
4. 데이터 훅 — 조회 4상태, 낙관적 이동과 원위치 (`lib/categories/use-category-tree.ts`)
5. 트리 뷰 — ARIA 트리 · 로빙 탭인덱스 · 키보드 이동
6. 작업 막대와 대화상자 3종 (추가·수정 폼 / 삭제·비활성화 / 충돌)
7. 폼 최소 구현을 `src/form/` 에 격리
8. 스펙 — 4상태 · 키보드만으로 이동 · 409 · 삭제 제한 · 원위치 · axe
