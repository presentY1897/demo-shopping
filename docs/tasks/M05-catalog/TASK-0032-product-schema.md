## 1. 목적

상품 3단 구조(Product / Option / Variant)를 만든다. 재고와 가격의 단위는 Variant(SKU)다. (D-024)

## 2. 범위

### 포함
- `Product` — 판매자, 카테고리, 이름, 설명, 상태, `attributes`(JSONB), 캐시 컬럼(`minPrice`, `ratingAvg`, `ratingCount`, `salesCount`)
- `ProductImage` — 순서
- `ProductOption` / `ProductOptionValue` — 이름, 값, 순서, `meta`(색상칩 등)
- `ProductVariant` — SKU, 가격, 정가, 재고, 상태, **1회 주문 최대 수량**
- `VariantOptionValue` — 조합 매핑
- **옵션 조합으로 Variant 일괄 생성** 로직
- 옵션 없는 상품도 Variant 1개 강제 생성
- 상품 CRUD API (판매자 소유권 검사 포함)
- 캐시 컬럼 갱신 로직

### 제외
- 상품 등록 화면 (TASK-0114) · 편집기 저장 계약 API (TASK-0113)
- 재고 원장 (TASK-0036)
- 검색 인덱싱 (M06)

## 3. 요구사항

- [ ] 색상 3 × 사이즈 4 를 지정하면 Variant 12개가 생성된다
- [ ] 옵션 없는 상품도 Variant 1개를 갖는다
- [ ] 판매자는 자신의 상품만 수정할 수 있다
- [ ] 상품 저장 시 속성 검증(TASK-0030)을 반드시 통과한다
- [ ] `minPrice` 가 Variant 가격 변경에 따라 갱신된다
- [ ] 판매자가 1회 주문당 최대 구매 수량을 지정할 수 있다

## 4. 설계

```
Product ─ ProductOption(색상) ─ Value(블랙, 화이트, 그레이)
        ─ ProductOption(사이즈) ─ Value(S, M, L, XL)
        ─ ProductVariant × 12 ─ VariantOptionValue (조합 매핑)
```

가격은 **Variant 절대값**이다. "기본가 + 추가금" 방식은 할인 계산 시 적용 대상이 모호해진다.

일부 조합만 판매하는 경우(블랙은 있는데 블랙/XL 은 없음)를 허용한다. 생성 후 개별 Variant 를 비활성화하는 방식으로 처리한다.

### 4.1 1회 주문 최대 수량 (`maxPurchaseQuantity`)

한 사람이 전 재고를 쓸어가는 것을 막는다. 인기 상품·한정 수량 상품에서 실제로 필요한 기능이고, 데모에서도 재고 1개짜리 상품을 한 명이 독점하면 다른 방문자가 체험할 수 없다.

| 위치 | 값 |
| --- | --- |
| `Product.maxPurchaseQuantity` | 상품 전체 기본값 (null = 무제한) |
| `ProductVariant.maxPurchaseQuantity` | 개별 SKU 재정의 (null = 상품 값 상속) |

검증 지점은 **네 곳 전부**다. 하나라도 빠지면 우회 경로가 된다.

1. 장바구니 담기·수량 변경 (TASK-0045)
2. 주문서 진입 시 (TASK-0050)
3. 재고 예약 시 (TASK-0048)
4. 주문 생성 시 (TASK-0049) ← 최종 방어선

1인당 **누적** 구매 제한(예: 계정당 평생 1개)은 범위 밖이다. 재구매·반품 후 재주문까지 고려하면 규칙이 복잡해지고, 얻는 것에 비해 비용이 크다.

**해석 규칙은 순수 함수로 이 TASK 가 만든다.** 네 곳이 각자 `variant.max ?? product.max` 를 쓰면 네 번째 곳에서 우선순위가 뒤집혀도 아무도 모른다. `resolvePurchaseLimit` 하나를 두고 나머지 세 TASK 가 그것을 부른다 — 그래서 이 함수는 분기 100% 대상이다.

### 4.2 식별자 — Product·Variant 는 UUIDv7, Option 계열도 마찬가지

`Category` 는 짧은 연번이다(`path` 에 문자열로 이어붙이므로). **여기서는 반대 선택을 한다.**

- `Product.id` 는 공개 URL(`/products/[id]`)에 실린다. 연번이면 총 상품 수와 신규 등록 속도가 그대로 드러나고 순회가 가능하다.
- `ProductVariant.id` 는 **주문·재고 원장·예약이 영원히 가리킬 앵커**다(3장, TASK-0036·0048). 연번은 재사용 사고의 여지가 있고, 원장 행이 엉뚱한 SKU 를 가리키면 대사가 조용히 틀어진다.
- `ProductOption`·`ProductOptionValue`·`ProductImage` 는 상품과 함께 다니는 종속 행이지만, 같은 요청 안에서 Variant 조합 매핑의 대상이 되므로 같은 규칙을 따른다. 형식이 섞이면 조합 매핑 코드가 두 가지 id 를 다뤄야 한다.

v4 가 아니라 **v7** 인 것은 계정 테이블과 같은 이유다 — 시간 접두사가 남아 삽입이 B-tree 오른쪽 끝에 몰린다.

### 4.3 조합을 DB 가 쥐게 만든다

옵션·Variant 모델의 진짜 위험은 "12개가 만들어지는가"가 아니라 **잘못된 조합이 표현 가능한가**이다. 셋을 DB 가 막는다.

| 규칙 | 어떻게 |
| --- | --- |
| Variant 는 한 옵션당 값을 **정확히 하나** 갖는다 | `VariantOptionValue` 에 `optionId` 를 두고 `UNIQUE (variantId, optionId)`. `optionId` 가 값과 어긋나지 못하도록 `(optionValueId, optionId) → ProductOptionValue(id, optionId)` **복합 외래키** |
| 매핑은 **한 상품 안에서만** 일어난다 | 같은 행에 `productId` 를 두고 `(variantId, productId) → ProductVariant(id, productId)`, `(optionId, productId) → ProductOption(id, productId)` 복합 외래키 2개. 다른 상품의 옵션값을 가진 Variant 가 **표현 불가능**해진다 |
| 같은 조합의 살아있는 Variant 는 **하나뿐** | `ProductVariant.optionSignature` (옵션값 id 를 정렬해 이어붙인 정규형) + `UNIQUE (productId, optionSignature) WHERE "deletedAt" IS NULL` |

`Category` 가 `(parentId, parentPath) → (id, path)` 로 경로 캐시의 드리프트를 표현 불가능하게 만든 것과 같은 수법이다. 비정규화 컬럼을 두되, **그 컬럼이 거짓말을 할 수 없게** 복합 외래키로 묶는다.

**`optionSignature` 가 F2 를 공짜로 준다.** 옵션이 없는 상품의 서명은 빈 문자열이고, 부분 유니크 인덱스는 빈 문자열도 값으로 취급한다 — 즉 "옵션 없는 상품의 살아있는 Variant 는 최대 1개"가 애플리케이션 규칙이 아니라 **인덱스**가 된다.

**서명과 매핑 행의 일치는 DB 가 못 쥔다.** 집계가 필요하고 CHECK 에는 집계를 쓸 수 없다. 그래서 서명은 서비스가 매핑을 쓰는 그 트랜잭션에서 같이 쓰고, 5장 경계표에 명시한다.

### 4.4 주문 스냅샷이 가능한 모양인가

CLAUDE.md 6장의 "주문·결제·정산 값은 스냅샷"은 주문 테이블이 생기는 M07 의 요구사항이지만, **그때 가서 스키마를 바꾸면 늦는다.** 이 스키마가 스냅샷을 가능하게 하는 성질은 넷이다.

1. **가격이 절대값이다.** `price` 하나를 복사하면 그 시점의 판매가가 완전히 보존된다. "기본가 + 추가금"이면 스냅샷이 두 값이 되고, 둘 중 하나만 복사한 코드가 반드시 생긴다.
2. **금액은 전부 정수(원)다.** `price`·`listPrice`·`minPrice` 가 `Int` 이고 부동소수 컬럼은 스키마 어디에도 없다(`schema-guards.spec.ts` 가 `Float`·`Decimal` 부재를 검사한다).
3. **참조가 끊기지 않는다.** `Product`·`ProductVariant` 는 소프트 삭제(`deletedAt`)이고 id 는 재사용되지 않는다. 판매자가 상품을 내려도 `OrderItem.variantId` 는 계속 실재하는 행을 가리킨다. `ProductOption`·`ProductOptionValue` 로 가는 외래키는 `Restrict` 라 조합 이름의 출처도 남는다.
4. **한 행에서 스냅샷이 완결된다.** 주문서가 그려야 하는 것 — 상품명, 옵션 조합, SKU, 단가 — 이 `Product`·`ProductVariant`·`VariantOptionValue` 세 테이블의 **현재 행**으로 전부 만들어진다. 다른 시점의 값을 되짚어야 하는 컬럼이 없다.

검증은 "스냅샷을 만든 뒤 원본을 바꿔도 스냅샷이 그대로인가"가 아니라 — 그건 M07 의 코드가 할 일이다 — **원본을 바꾼 뒤에도 스냅샷이 가리키던 행이 그 자리에 있는가**로 한다(6.1 F10).

### 4.5 재고는 컬럼 하나, 원장은 TASK-0036

`ProductVariant.stock` 은 **현재값**이다. 원장(`StockLedger`)과 예약(`StockReservation`)은 TASK-0036·0048 소유이고 여기서 만들지 않는다.

이 TASK 가 책임지는 것은 **그 원장이 붙을 수 있는 모양**이다.

- 원장은 `variantId` 를 외래키로 잡는다 → Variant id 가 안정적이고(4.2) 하드 삭제되지 않아야 한다.
- 가용재고 계산은 `stock − SUM(HELD 예약)` 이다(`erd.md` 3장) → `stock` 은 Variant 행에 있어야 하고 정수여야 한다.
- 조건부 갱신 `UPDATE ... WHERE stock - reserved >= qty` 가 동작하려면 `stock` 에 음수 하한 CHECK 이 있어야 한다. `stock >= 0` 을 지금 넣는다.

**이 TASK 의 API 는 `stock` 을 절대값으로 쓴다.** D-024 의 "재고 수정 입력은 조정량"은 재고 관리 화면(TASK-0036)의 규칙이고, 상품 등록 시점의 초기 재고에는 조정량이라는 개념이 없다. 상품이 만들어진 뒤의 증감은 TASK-0036 이 원장으로 처리한다.

### 4.6 캐시 컬럼은 파생이지 누산이 아니다

`minPrice` 는 **한 문장으로 다시 계산**한다.

```sql
UPDATE "Product" p
   SET "minPrice" = (SELECT min(v."price") FROM "ProductVariant" v
                      WHERE v."productId" = p."id" AND v."deletedAt" IS NULL AND v."isActive")
 WHERE p."id" = $1
```

증분(`if (newPrice < minPrice) minPrice = newPrice`)으로 갱신하지 않는다. 증분은 **가격을 올렸을 때 틀린다** — 최저가 Variant 가 비싸지면 최저가는 올라가야 하는데 증분식은 내려가기만 한다. R2 의 "캐시와 실제 값 불일치"는 대부분 이 형태로 발생한다.

값이 파생이므로 "갱신은 서비스 한 곳에서만"(R2)이 지킬 수 있는 규칙이 된다 — `refreshProductCache` 하나를 모든 쓰기 경로 끝에서 부른다.

**`minPrice` 는 판매 가능한 Variant 의 최저가다.** 비활성 Variant 를 세면 목록에 뜬 가격으로 살 수 없는 상품이 생긴다. 살아있고 활성인 Variant 가 하나도 없으면 `NULL` 이고, 그 상태의 상품은 `ACTIVE` 가 될 수 없다.

**`ratingAvg` 는 정수다** — 별점 평균 × 100 (0~500). 금액이 아니지만 `Float` 를 스키마에 들이는 순간 S4 가드가 깨지고, 무엇보다 소수 컬럼 하나가 생기면 다음 소수 컬럼의 근거가 된다. `ratingCount = 0` 이면 `ratingAvg = 0` 이라는 짝도 CHECK 으로 못박는다. 실제 채우는 것은 M13(리뷰)이다.

### 4.7 쓰기 경합 — 상품 행을 먼저 잠근다

상품 쓰기는 `SELECT ... FOR UPDATE` 로 `Product` 행을 잠근 **뒤에** `version` 을 비교한다. 순서가 반대면 안 된다.

**왜 낙관적 잠금만으로 부족한가.** `version` 은 "두 사람이 같은 화면을 열었다"를 잡는 장치이고(D-004), 잡아 주는 것은 *충돌 통보*다. 그런데 한 요청 안에서 Variant 를 쓰고 그 결과로 `minPrice` 를 다시 계산하는 흐름은, 두 트랜잭션이 겹치면 **각자 자기 변경만 보이는 스냅샷에서 최저가를 계산**한다(READ COMMITTED). 나중에 커밋한 쪽이 남의 인하를 못 본 값을 덮어쓴다 — 어떤 제약도 반대하지 않는 조용한 손상이다.

행 잠금을 먼저 잡으면 두 번째 트랜잭션은 첫 번째가 커밋할 때까지 기다렸다가 **갱신된 `version` 을 읽고** 409 를 받는다. 즉 잠금이 직렬화를 만들고, `version` 이 그 직렬화의 결과를 사용자에게 설명한다. 둘 다 필요하다.

음성 대조군은 이 잠금만 뺀 같은 흐름이다(6.1 A7, 7.3).

### 4.8 옵션 **축**은 바꾸지 않는다. 값만 바꾼다

R1 이 정의한 것은 값 단위의 변경이다 — "옵션 값 추가는 Variant 추가, 삭제는 해당 Variant 비활성화".

**옵션 자체(색상·사이즈라는 축)의 추가·삭제는 이 TASK 의 범위 밖**으로 둔다. 축이 바뀌면 기존 Variant 의 조합 **원소 수**가 달라져 `optionSignature` 가 전부 무효가 되고, 살아있는 Variant 를 전부 버리고 다시 만드는 것 외에 방법이 없다. 주문 이력이 걸린 뒤에는 그것이 불가능하다.

이 TASK 의 `PATCH` 는 축의 개수·순서가 저장된 것과 다르면 400 으로 거부한다. 전체 교체가 필요한 시나리오(초안 상태의 편집기 저장)는 **TASK-0113** 이 한 요청·한 트랜잭션 계약으로 다룬다.

값 변경의 규칙은 R1 그대로다.

| 변경 | 결과 |
| --- | --- |
| 값 추가 | 그 값이 참여하는 조합의 Variant 를 **새로 만든다** (`variantDefaults` 로) |
| 값 삭제 | 그 값을 쓰는 Variant 를 **비활성화**한다. 행은 남는다 |
| 값 이름 변경 | 라벨만 바뀐다. Variant 는 그대로 |

### 4.9 상태와 "강제 숨김"

```
DRAFT      작성 중. 노출되지 않는다
ACTIVE     판매 중
INACTIVE   판매자가 내렸다
SUSPENDED  관리자가 강제 숨김 처리했다
```

`SUSPENDED` 는 **판매자가 설정하거나 해제할 수 없다.** 그렇지 않으면 강제 숨김이 아니다.

권한 체계로 표현한다 — 상태를 `SUSPENDED` 로 바꾸거나 `SUSPENDED` 에서 빼내는 요청은 `product.write` 를 **`own` 이 아닌 스코프로** 들고 있어야 통과한다. 판매자의 그랜트는 `product.write:own` 하나뿐이므로 403 이고, `ADMIN_OPERATOR`(`any`)와 데모 관리자가 데모 상품에 대해 갖는 `demo` 는 통과한다. `isDemo` 를 읽는 코드는 여전히 없다(TASK-0105 F8).

전용 퍼미션(`product.suspend`)을 새로 만들지 않은 이유는 그것이 `packages/shared` 의 권한표와 생성 문서(`permission-matrix.md`)를 바꾸는 일이고, 같은 시점에 다른 작업이 그 파일들을 보고 있기 때문이다. 스코프로 표현 가능한 것에 퍼미션을 늘리는 것은 D-212 가 말하는 "새로 만드는 것"에 해당한다.

### 4.10 새 도메인 오류 코드를 만들지 않는다

`error-contract.md` 6장은 새 코드를 더할 때 **각 앱 카탈로그의 문장도 함께 더하라**고 한다. 카탈로그는 `apps/admin/src/messages/ko.ts` 에 있고 `Record<UserFacingErrorCode, string>` 으로 전수 검사된다 — 코드만 더하면 `pnpm typecheck` 가 깨진다.

이 TASK 는 `apps/admin` 을 건드리지 않는다(TASK-0031 이 같은 시점에 그 앱을 쓴다). 그래서 **상품 도메인 코드는 이 TASK 에서 만들지 않고**, 실패를 전송 계층 코드(`BAD_REQUEST`·`CONFLICT`·`FORBIDDEN`·`NOT_FOUND`)와 필드 단위 `INVALID` 로 답한다. 이것은 계약 위반이 아니라 계약이 명시적으로 허용하는 상태다 — `error-contract.md` 2.1 과 "아직 코드를 붙이지 않은 엔드포인트"의 `details` 문자열 형태.

봉투와 `details[].field` 는 처음부터 지킨다. 코드만 나중에 붙으면 되고, 붙이는 시점은 **그 실패를 화면에 그리는 TASK**(TASK-0113·0114)다. 그 TASK 가 앱 카탈로그도 함께 소유한다.

### 4.11 TASK-0030 이 여기로 넘긴 두 가지

TASK-0030 은 `Product` 가 없어서 닫지 못한 위험 둘을 이 TASK 로 넘겼다.

| | TASK-0030 | 여기서 |
| --- | --- | --- |
| R2 | 정의 삭제 시 **사용 중이면 차단** | 정의가 붙은 카테고리 계통에 그 `key` 를 실제로 담고 있는 살아있는 상품이 있으면 삭제를 409 로 거부 |
| R5 | 선택지 축소 시 **사용 중 검사** | 제거되는 선택지를 실제로 쓰고 있는 상품이 있으면 400. 아무도 쓰지 않는 선택지는 그대로 지워진다(운영자가 오타를 지울 수 있어야 한다) |

둘 다 한 문장짜리 조회다. `Category.path` 로 하위 계통을 잡고 `Product.attributes` JSONB 를 본다.

### 4.12 DB 가 쥐는 것과 애플리케이션이 쥐는 것

| 규칙 | 어디서 | 왜 |
| --- | --- | --- |
| 판매자당 live SKU 유일 | 부분 유니크 인덱스 `(sellerId, sku) WHERE "deletedAt" IS NULL` | 두 요청이 동시에 "없다"를 확인할 수 있는 검사다. `sellerId` 는 `(productId, sellerId) → Product(id, sellerId)` 복합 외래키로 상품과 묶여 있어 드리프트할 수 없다 |
| 상품당 live 조합 유일 (옵션 없는 상품의 Variant 1개 포함) | 부분 유니크 인덱스 `(productId, optionSignature)` | 〃. 두 Variant 가 같은 조합이면 어느 쪽 가격을 보여줄지가 새로고침마다 달라진다 |
| Variant 는 한 옵션당 값 하나 | `UNIQUE (variantId, optionId)` + 복합 외래키 | 4.3 |
| 매핑이 한 상품 안에 머문다 | 복합 외래키 2개 | 4.3 |
| 금액·수량의 하한 (`price >= 0`, `stock >= 0`, `maxPurchaseQuantity >= 1`, `sortOrder >= 0`) | CHECK | 애플리케이션 검증은 임포트 스크립트가 우회한다 |
| 정가는 판매가 이상 | CHECK | 할인율이 음수가 되면 목록이 "-30% 할인"을 거꾸로 그린다 |
| 별점 짝 (`ratingCount = 0 → ratingAvg = 0`, `0 <= ratingAvg <= 500`) | CHECK | 4.6 |
| 상품·Variant 가 실재하는 대상을 가리킨다 | 외래키 `Restrict` | 카탈로그가 조용히 지워지는 경로를 막는다 |
| **`optionSignature` 가 매핑 행과 일치** | **애플리케이션** (같은 트랜잭션) | 집계가 필요하고 CHECK 에 집계를 쓸 수 없다 |
| **속성 값의 타입·필수·선택지** | **애플리케이션** (TASK-0030 동적 zod) | 값이 JSONB 다. 저장 경로는 `AttributeService.validateAttributes` 하나뿐이다 |
| **`minPrice` 가 실제 최저가와 같다** | **애플리케이션 + 상품 행 잠금** | 다른 행을 집계해야 답할 수 있다. 경합이 있고, 그래서 음성 대조군을 갖는다 (4.7) |
| **판매자 소유권** | **애플리케이션** (`assertResourceAccess`) | 행을 읽어야 알 수 있고, DB 에는 요청자가 누구인지가 없다 |

경계에 있는 규칙에 대해서는 **DB 가 그 INSERT 를 실제로 받아들이는 것**도 테스트로 고정한다. "DB 가 막아 주겠지"가 나중에 애플리케이션 검사를 지우는 근거가 되지 않게 하기 위해서다(TASK-0030 7.4 와 같은 이유).

## 5. 구현 계획

1. 스키마·인덱스·마이그레이션 — DB 가 쥘 수 있는 것만 제약으로(4.12), 나머지는 근거와 함께 애플리케이션에
2. `packages/shared` 계약 스키마 + 클라이언트 메서드 (C1)
3. 순수 로직 — 조합 생성기·서명 정규형(4.3), 구매 수량 해석기(4.1). 둘 다 분기 100%
4. 상품 CRUD 서비스 — 속성 검증 연결(TASK-0030), 소유권 검사, 상품 행 잠금(4.7)
5. 캐시 컬럼 갱신 — 파생 재계산 한 문장(4.6)
6. 옵션 값 추가·삭제(4.8)와 속성 정의 사용 중 검사(4.11)
7. 테스트 — 실 DB 제약(S5), 경합과 음성 대조군(A7), 쿼리 수(A5), 스냅샷 앵커(F10)

| R4 | 상품 도메인 오류 코드가 없어 화면이 실패를 구분하지 못한다 | 봉투와 `details[].field` 는 지금 지킨다. 코드는 화면을 만드는 TASK-0113·0114 가 앱 카탈로그와 함께 붙인다 (4.10) |

### 7.3 A7 — 동시 요청 검증과 음성 대조군

`apps/api/test/db/product-contention.spec.ts`, 각 10회 반복.

**이 TASK 가 A7 대상인 이유.** 잔액도 재고도 아니다. 경합하는 것은 `Product.minPrice` 이고, 경합하는 이유는 상품 쓰기가 한 문장이 아니라 **Variant 를 쓰고 그 결과를 파생하는** 흐름이기 때문이다(4.6). 두 트랜잭션이 동시에 그 일을 하면 각자 자기 변경만 담긴 스냅샷에서 최저가를 구한다.

PostgreSQL 의 READ COMMITTED 가 이것을 이론적 순서 문제 이상으로 만든다. 같은 행을 갱신하는 두 문장 중 나중 것은 기다렸다가 `WHERE` 를 새 행 버전으로 다시 평가하지만, **`SET` 절의 서브쿼리는 문장이 시작할 때의 스냅샷을 유지한다.** 진 쪽은 낡은 값을 덮어쓰는 것이 아니라 **더 이상 존재하지 않는 카탈로그로 계산한 최저가**를 쓴다. 어떤 제약도 반대하지 않는다 — "이게 진짜 최저가인가"는 집계이고 CHECK 에 집계를 쓸 수 없다(7.4).

| 시나리오 | 결과 |
| --- | --- |
| 서로 다른 Variant 를 동시에 인하 (2건) | 정확히 1건 성공, 1건 **409**. `minPrice` 가 커밋된 카탈로그의 실제 최저가와 일치, `version` 은 정확히 +1 |
| 409 를 받은 쪽이 다시 읽고 재시도 | 성공하고 캐시가 다시 참이 된다 — 409 가 막다른 길이 아니라는 것 |
| 같은 SKU 로 동시 등록 (2건) | 1건 성공, 1건 **409**. live SKU 는 정확히 1개. 이건 **인덱스가 혼자 이긴다** — check-then-insert 가 아니다 |
| 쓰기 3건 중 조회 6건 동시 실행 | 어떤 조회도 한 구매자 선택을 두 행으로 해석하지 않는다 |

**음성 대조군 — 상품 행을 전혀 잠그지 않는 구현, 실 테이블.** TASK-0028 은 제약을 뺀 픽스처 테이블이 필요했다(실 테이블은 손상을 표현 불가능하게 만들어 두어서). 여기엔 뺄 제약이 없다 — 이 규칙을 DB 가 쥔 적이 없다는 것이 대조군의 존재 이유이고, 그래서 배포되는 테이블 위에서 그대로 재현된다. 인터리빙은 우연에 맡기지 않고 두 커넥션의 단계를 직접 순서지어 고정했다.

- 두 트랜잭션 모두 같은 `version` 을 읽고 둘 다 커밋한다. **10회 전부** `minPrice` 가 실제 최저가와 다르다.
- 손상은 "행이 이상하다"가 아니다. 5,000원짜리 Variant 가 테이블에 있는데 **매장은 10,000원을 광고한다.** 그리고 두 편집 중 하나는 `version` 을 남에게 넘겨준 채 조용히 사라진다 — 10회 전부 `version` 이 2가 아니라 1이다.
- 같은 픽스처를 서비스로 돌리면 캐시가 매번 카탈로그와 일치한다.

**잠금이 실제로 일을 하는지 확인했다.** 서비스에서 `SELECT … FOR UPDATE` 를 지우고 같은 스펙을 돌리면 소프트 단언 **40개 중 30개가 실패**한다. 어느 30개인지가 중요하다.

| 단언 | 잠금 없이 | 왜 |
| --- | --- | --- |
| 정확히 1건 성공 · 나머지 409 · `version` +1 | **전부 실패** (30개) | `version` 을 잠기지 않은 스냅샷에서 읽으므로 두 요청이 모두 통과한다. 아무도 충돌을 통보받지 않는다 |
| `minPrice` = 실제 최저가 | 통과 (10개) | 몇 줄 뒤의 `UPDATE "Product"` 가 **우연히** 같은 행 잠금을 늦게 잡는다 |

그래서 잠금을 명시적으로, 그리고 **먼저** 잡는다. 나중에 우연히 잡히는 잠금은 쓰기는 지켜도 **판정은 못 지킨다** — 그때는 이미 낡은 `version` 으로 비교를 끝낸 뒤다. 확인 후 원복했다.

### 7.4 S5 — DB 와 애플리케이션의 경계

| 규칙 | 어디서 | 왜 거기인가 |
| --- | --- | --- |
| 판매자당 live SKU 유일 | 부분 유니크 인덱스 | 두 요청이 동시에 통과할 수 있는 검사다. 소프트 삭제된 Variant 가 SKU 를 영원히 붙잡지 않도록 부분 인덱스 |
| 상품당 live 조합 유일 (옵션 없는 상품의 Variant 1개 포함) | 부분 유니크 인덱스 | 〃. 조합이 둘이면 매장이 한 선택에 두 행으로 답한다 |
| Variant 는 한 옵션당 값 하나 | 유니크 + 복합 외래키 | 4.3 |
| 매핑이 한 상품 안에 머문다 | 복합 외래키 2개 | 4.3. 다른 상품의 옵션값을 가진 Variant 가 **표현 불가능**해진다 |
| Variant 의 판매자 사본이 상품과 일치 | 복합 외래키 | 이게 없으면 "판매자당 SKU 유일"이 아무도 참으로 유지하지 않는 컬럼 위의 인덱스가 된다 |
| 금액·수량의 하한, 정가 ≥ 판매가, 별점 짝, SKU 형식, 속성 값이 객체 | CHECK | 애플리케이션 검증은 임포트 스크립트와 psql 세션이 우회한다 |
| 판매 중인 상품에는 가격이 있다 | CHECK | `minPrice` 가 NULL 인 것은 주문 가능한 Variant 가 없다는 뜻이다. 그래서 상품은 항상 초안으로 삽입되고, 제약을 완화해야 하는 중간 상태가 없다 |
| 상품·Variant 가 실재하는 대상을 가리킨다 | 외래키 `RESTRICT` · 매핑은 `NO ACTION` | 카탈로그가 조용히 지워지는 경로를 막는다. 매핑 쪽이 `NO ACTION` 인 이유는 검증 시점이 **문장 끝**이라, Variant 와 매핑을 한 문장으로 다시 쓰는 것이 합법이기 때문이다 |
| **조합 정규형이 매핑 행과 일치** | **애플리케이션** (같은 트랜잭션) | 판별에 집계가 필요하고 CHECK 에 집계를 쓸 수 없다 |
| **`minPrice` 가 실제 최저가와 같다** | **애플리케이션 + 상품 행 잠금** | 〃. 여기만 경합이 있고, 그래서 음성 대조군을 갖는다 (7.3) |
| **속성 값의 타입·필수·선택지** | **애플리케이션** (TASK-0030 동적 zod) | 값이 JSONB 다 |
| **판매자 소유권** | **애플리케이션** (`assertResourceAccess`) | 행을 읽어야 알 수 있고, DB 에는 요청자가 누구인지가 없다 |

경계로 넘어온 두 규칙(정규형 일치, `minPrice`)에 대해 **DB 가 해당 UPDATE 를 실제로 받아들이는 것**을 테스트로 고정했다. "DB 가 막아 주겠지"라는 착각이 나중에 애플리케이션 검사를 지우는 근거가 되지 않게 하기 위해서다(TASK-0030 7.4 와 같은 이유).
