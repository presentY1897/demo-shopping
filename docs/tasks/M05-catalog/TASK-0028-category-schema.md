## 4. 설계

```
path 예시: "/1/5/12/"     → 하위 전체 조회는 path LIKE '/1/5/%'
```

인접 리스트만 쓰면 하위 전체 조회에 재귀가 필요하다. `path` 를 캐시하면 인덱스 하나로 끝난다. 대신 이동 시 하위를 함께 갱신해야 하는데, 카테고리 이동은 드문 작업이라 이쪽이 유리하다.

### 4.1 불변식은 DB 가 쥔다

`path` 는 캐시이므로 **어긋날 수 있다**는 것이 이 설계의 유일한 위험이다. 그래서 규칙을 애플리케이션이 아니라 스키마에 넣었다.

| 제약 | 내용 |
| --- | --- |
| `Category_path_shape_check` | `path = COALESCE(parentPath,'/') ‖ id ‖ '/'` |
| `Category_parentId_parentPath_fkey` | `(parentId, parentPath) → (id, path)` **복합 외래키** |
| `Category_parent_pairing_check` | `parentId` 와 `parentPath` 는 함께 있거나 함께 없다 |
| `Category_depth_path_check` | `depth` = `path` 안의 id 개수 |
| `Category_depth_range_check` | `1 ≤ depth ≤ 3` |
| `Category_slug_active_key` | 살아 있는 행에 대해서만 `slug` 유니크 (부분 유니크 인덱스) |
| `Category_sortOrder_check` | `sortOrder ≥ 0` |

`parentPath` 열은 **복합 외래키가 가리킬 대상을 만들기 위해** 존재한다. 이 세 가지가 함께 걸리면 **순환 참조는 "검사 대상"이 아니라 "표현 불가능"** 이 된다 — 모든 노드의 `path` 는 부모보다 반드시 길고, 순환은 자기보다 긴 자기 경로를 요구하기 때문이다. 깊이 상한도 파생된다: `depth` 가 `path` 를 따라가므로 4단계가 되는 순간 그 행이 거부된다.

**애플리케이션 검증은 없애지 않는다.** 서비스가 같은 규칙을 먼저 확인해 400 과 한국어 메시지를 돌려주고, DB 는 어떤 코드 경로로도 깨진 트리가 커밋되지 않도록 막는다. 동시 요청 두 건이 각자 "지금 트리도 정상이고 내 변경도 정상"이라고 판단하는 상황이 애플리케이션 검증이 지는 지점이다.

### 4.2 이동은 한 문장

옮기는 노드와 하위 전체를 하나의 `UPDATE ... WHERE path LIKE '/1/5/%'` 로 다시 쓴다. 이유는 두 가지다.

- 복합 외래키가 `ON UPDATE NO ACTION` 이라 검증 시점이 **문장 끝**이다. 부모와 하위를 따로 갱신하면 중간 상태에서 외래키가 거부한다.
- 비용이 하위 노드 수와 무관하다 — 인덱스 범위 스캔 1회 + 갱신 N행이고, **문장 수는 항상 같다**(게이트 A5).

### 4.3 동시성 — 어드바이저리 락 + 낙관적 잠금

DECISIONS 4장의 구분을 그대로 따른다.

| 대상 | 방식 |
| --- | --- |
| 트리 구조 변경 (생성·이동·정렬·삭제) | `pg_advisory_xact_lock` — 트랜잭션의 **첫 문장**으로 잡는다 |
| 이름·슬러그·활성 여부 편집 | 낙관적 잠금 `version` (조건부 `UPDATE` 1문장) |

**락을 읽기 전에 잡는 것이 핵심**이다. 읽고 나서 잡으면 앞 홀더가 다시 쓰고 있던 트리를 기준으로 판단하게 된다. 격리 수준은 기본값 `READ COMMITTED` 여야 한다 — `REPEATABLE READ` 면 스냅샷이 락 획득 **전에** 고정되어 대기가 무의미해진다.

트리 전체를 하나의 락으로 덮는다. 이동은 임의의 두 서브트리를 관계시키므로 노드별 락은 데드락 회피 순서가 필요하고, 그러고도 도중에 생기는 노드를 놓친다. 이동은 드문 작업이므로(4장) 경합 비용은 이론적이다.

**구조 변경은 `version` 을 올리지 않는다.** 남이 형제 순서를 바꿨다는 이유로 이름 편집이 충돌로 튕기면 알림이 소음이 된다.

### 4.4 번호 재사용 정책

**`id` 는 재사용하지 않는다.** 5번 카테고리를 지워도 다음 카테고리는 6번이고, 5번은 영구 결번이다.

재사용하면 과거 로그·주문 스냅샷·검색 인덱스에 남은 `categoryId: 5` 가 **엉뚱한 카테고리를 가리키게 된다.** 데이터가 조용히 잘못되는 종류의 문제라 추적도 어렵다.

- 애초에 카테고리는 **소프트 삭제**(`deletedAt`)이므로 행이 사라지지도 않는다. 상품이 있으면 비활성화만 허용한다(TASK-0029).
- `path` 는 id 기반이라 결번이 있어도 무관하다. `/1/5/12/` 에서 5번이 비활성이어도 경로는 유효하다.
- `sortOrder` 는 **표시 순서용 별개 값**이다. 중간이 비어도 정렬 결과에 영향이 없으므로 자동으로 채우지 않는다. 사용자가 순서를 바꿀 때만 재계산한다.
- 시퀀스는 롤백되지 않으므로 **실패한 INSERT 도 번호를 태운다.** 이것이 결번 보장의 실제 메커니즘이다.

### 4.5 엔드포인트

| 메서드 · 경로 | 퍼미션 | 응답 |
| --- | --- | --- |
| `GET /api/v1/categories?rootId=&includeInactive=` | `catalog.read` | `{ nodes }` (중첩 트리) |
| `POST /api/v1/categories` | `catalog.write` | `{ category }` |
| `PATCH /api/v1/categories/:id` | `catalog.write` | `{ category }` (낙관적 잠금) |
| `POST /api/v1/categories/:id/move` | `catalog.write` | `{ category }` |
| `POST /api/v1/categories/reorder` | `catalog.write` | `{ categories }` |
| `DELETE /api/v1/categories/:id` | `catalog.delete` | `{ category }` (소프트 삭제) |

기존 퍼미션 3개로 충분해 **권한 매트릭스는 바뀌지 않는다.** 카테고리는 플랫폼 소유(`platformOwnership`)이므로 스코프 `demo` 로 좁혀진 `DEMO_ADMIN` 은 읽기만 된다.

정렬은 "옮긴 하나"가 아니라 **형제 전체 배열**을 받는다. "3번째로" 는 각자 다른 배치에서 계산한 값이라 둘을 적용하면 아무도 요청하지 않은 순서가 남는다.

| 같은 노드를 서로 다른 부모로 동시 이동 (2건) | 둘 다 성공하고 **각 응답이 실제로 수행된 이동을 기술**한다. 하위 노드의 `path` 도 따라옴 |
| 이동 × 생성이 3단계 상한에서 충돌 | 정확히 1건 성공, 1건 **400**(500 아님). `max(depth) ≤ 3` |
| 서로를 부모로 삼는 이동 2건 (순환) | 정확히 1건 성공, 1건 400. 최종 트리는 두 가지 정상 형태 중 하나 |
| 같은 형제 집합 동시 정렬 (3건) | 전부 성공. `sortOrder` 는 0·1·2·3 의 순열이고, 결과는 **제출된 배치 중 하나**와 정확히 일치 |
| 같은 `version` 으로 동시 편집 (2건) | 1건 200, 1건 **409**. `version` 은 정확히 +1 |

**음성 대조군 A — 락 없는 구현, 실 테이블.** 두 트랜잭션이 모두 읽은 뒤에 쓰도록 `barrier` 로 고정한다. 결과는 갱신 행 수 `[2, 0]` — **한쪽은 성공했다고 답하면서 단 한 행도 옮기지 않았다.** 트리는 멀쩡한데(제약이 지킨다) 호출자가 받은 답이 거짓이다. 같은 상황을 서비스로 돌리면 두 요청 모두 실제로 이동한다.

**음성 대조군 B — 락도 제약도 없음** (`TestCategoryNaive` 픽스처 테이블, `test/setup/test-schema.sql`). 같은 인터리빙에서 실제로 트리가 깨진다.

- **순환 참조**: 두 이동이 모두 커밋되어 A 의 부모가 B, B 의 부모가 A 가 된다. 부모를 따라 올라가면 끝나지 않는다.
- **끊어진 경로 캐시**: 서브트리 이동과 하위 생성이 겹치면, `parentId` 로는 자손인 노드가 `path LIKE` 조회에서 빠진다. "이 카테고리 아래 무엇이 있나"에 답이 두 개가 된다 — `path` 캐시가 없애려던 바로 그 상황.

대조군 B 가 필요한 이유: 실 테이블은 제약이 손상을 **표현 불가능**하게 만들어 두었기 때문에, 락을 빼도 "트리가 깨지는 모습"을 볼 수 없다. 제약이 무엇을 막고 있는지 확인하지 않은 채로 두면 A7 통과가 무엇을 증명하는지 알 수 없다.
