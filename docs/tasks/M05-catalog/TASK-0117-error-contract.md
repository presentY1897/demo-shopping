## 1. 목적

**서버가 실패를 알릴 때 한국어 문장 하나만 보내고 있다.** 화면은 그 문장을 파싱해서
"어느 입력칸의 문제인지" 를 되짚고 있고, 문구를 다듬는 순간 조용히 깨진다.

이 TASK 는 오류 응답에 **기계가 읽을 정보(`field`·`code`)** 를 붙이고, 그 위에서
**사용자가 읽을 문장을 다시 쓴다.** 끝나면:

- 오류가 폼 맨 위가 아니라 **문제가 된 입력칸 아래**에 뜨고 그 칸으로 포커스가 간다
- 화면이 상황에 맞는 **복구 수단**을 고를 수 있다 (덮어쓰기 다이얼로그 / 슬러그 수정 / 하위 정리)
- 사용자가 손쓸 수 없는 실패에는 **문의 번호**가 함께 나와 QA 가 로그를 찾아갈 수 있다
- 내부 식별자(`slug`, `orderedIds`, 엔드포인트 사정)가 **사용자 화면에 나오지 않는다**

### 지금 실제로 나가는 것

```json
{ "error": { "code": "CONFLICT", "details": ["하위 카테고리가 남아 있어 삭제할 수 없습니다."] } }
```

`code` 는 HTTP 상태(409)에서 기계적으로 파생되므로 **서로 다른 세 상황이 모두 `CONFLICT`** 다.
`details` 는 문자열 배열이라 어느 필드인지 알 수 없다.

### 지금 화면이 하고 있는 우회

| 화면 | 우회 방법 | 깨지는 조건 |
| --- | --- | --- |
| 폼 (`packages/ui/src/form/server-errors.ts`) | `"slug 값이 올바르지 않습니다."` 의 **첫 토큰**을 필드명으로 사용 | 문구를 `"슬러그 형식이…"` 로 바꾸면 매핑 실패 → 오류가 폼 상단으로 떠오름 |
| 카테고리 관리 (`category-workspace.tsx`) | **자기가 보낸 HTTP 메서드**로 역추론. PATCH 면 트리를 다시 읽어 `version` 비교 | 한 엔드포인트가 두 종류 409 를 내면 구분 불가 |

두 경우 모두 **오류 문구는 계속 표시되므로 테스트가 잡지 못한다.** 잘못된 자리에 뜰 뿐이다.

## 2. 범위

### 포함

**계약**

- `packages/shared` 에 `apiFieldErrorSchema` 추가: `{ field: string, message: string, code?: string }`
- `apiErrorSchema.error` 에 `requestId: string` 추가
- `all-exceptions.filter.ts` 의 `detailsOf` 가 **객체 detail 을 버리지 않게** 수정
- 도메인 오류 코드 부여 (아래 4.2 표)

**백엔드 문구**

- 내부 식별자가 새는 문구를 **코드 + 사용자 문장**으로 교체
- 개발자 실수를 알리는 `ForbiddenException` 2건을 **500 으로 내리고 화면에서 감춤**
- `parse-input.ts` 의 `describeIssue` 가 필드 경로를 `field` 로 내보내도록 변경

**프론트**

- `ApiClientError` 가 응답 헤더 `x-request-id` 를 담도록 수정
- 오류 문구를 **각 앱의 메시지 카탈로그**(`messages/ko.ts`)로 이관, `code` 로 조회
- 사용자가 대응할 수 없는 실패에 **문의 번호 표시 + 복사** UI

**카탈로그**

- `CategoryNode.productCount` 추가 (화면이 "상품 있는 카테고리 삭제" 를 미리 안내)

### 제외 (이번에 하지 않는 것)

- **문의 접수 화면·백오피스.** 이번에는 사용자가 **번호를 전달할 수 있게** 하는 데까지다.
  접수 채널은 M13 커뮤니티/문의가 맡는다
- 영어 등 다른 언어 문구. 카탈로그 구조만 맞추고 `ko` 만 채운다 (CLAUDE.md 6장)
- 로그 수집·검색 인프라. `requestId` 로 로그를 **찾을 수 있는 상태**까지이고, 검색 UI 는 TASK-0013(관측)
- 카탈로그 밖 도메인(주문·결제 등)의 코드 부여. 아직 존재하지 않는다.
  **규약과 도구를 여기서 만들고**, 이후 TASK 들이 자기 도메인에서 따른다

## 4. 설계

### 4.1 봉투

```ts
// packages/shared/src/api-error.ts
export const apiFieldErrorSchema = z.object({
  field: z.string().min(1),      // 폼 필드 경로. "slug", "attributes.0.options"
  message: z.string().min(1),    // 카탈로그에 code 가 없을 때 쓸 대비책
  code: z.string().min(1).optional(),
  params: z.record(z.string(), z.union([z.string(), z.number()])).optional(),
})

export const apiErrorSchema = z.object({
  error: z.object({
    code: z.string().min(1),
    message: z.string().min(1),
    details: z.array(z.unknown()),   // 문자열 · apiFieldError 혼재 허용
    requestId: z.string().min(1),    // ← 추가
  }),
})
```

**`params` 를 더한 이유 (승인 문서에 없던 필드).** 4.2 표의 문장 두 개가 값을 끼워 넣는다 —
`카테고리는 {max}단계까지만` 과 `'{name}' 에 같은 이름의 속성이`. 그 값(최대 깊이, 충돌한
카테고리 이름)은 **서버만 아는 사실**이므로, 프론트 카탈로그가 문장을 소유하려면 값이 함께
와야 한다. `params` 없이 하면 두 문장만 서버 문장을 그대로 쓰게 되고, 그것이 정확히 F7 이
막으려는 상태다. `optional` 이라 기존 응답과 호환된다.

**`details` 를 `z.array(z.unknown())` 로 두는 이유.** 유니온으로 좁히면 아직 코드를 안 붙인
엔드포인트의 문자열 detail 이 스키마에서 걸린다. 읽는 쪽이 형태를 판별하는 편이
**한 번에 전부 고치지 않아도 되게** 한다. 판별은 `isApiFieldError(x)` 하나로 모은다.

**문장을 서버가 계속 보내는 이유.** `message` 를 없애면 카탈로그에 없는 새 코드가 왔을 때
사용자가 **빈 화면**을 본다. 서버 문장은 최후의 대비책으로 남기고, **화면은 `code` 를 먼저 본다.**

### 4.2 코드 부여

**새 `code` 는 봉투의 `error.code` 에 실린다.** detail 이 아니라 봉투인 이유는 완료 기준 F1 이
`세 응답의 code 가 모두 다름` 을 재는 자리이기 때문이고, `하위 존재` 처럼 **어떤 입력칸의
문제도 아닌 실패**가 있기 때문이다. 필드가 있는 실패는 `details[]` 에 같은 `code` 를 단 필드
오류를 함께 싣는다.

| 현재 | 새 `code` | 사용자에게 보일 문장 (프론트 카탈로그) |
| --- | --- | --- |
| 409 `CONFLICT` (슬러그 중복) | `CATEGORY_SLUG_TAKEN` | 이미 쓰고 있는 주소예요. 다른 주소를 입력해 주세요. |
| 409 `CONFLICT` (버전 충돌) | `CATEGORY_VERSION_CONFLICT` | 다른 관리자가 먼저 저장했어요. 최신 내용을 불러올까요? |
| 409 `CONFLICT` (하위 존재) | `CATEGORY_HAS_CHILDREN` | 하위 카테고리를 먼저 옮기거나 삭제해 주세요. |
| 409 `CONFLICT` (속성 계통 중복) | `ATTRIBUTE_KEY_TAKEN` | '{name}' 에 같은 이름의 속성이 이미 있어요. |
| 400 (깊이 초과) | `CATEGORY_MAX_DEPTH` | 카테고리는 {max}단계까지만 만들 수 있어요. |
| 400 (자기 하위로 이동) | `CATEGORY_MOVE_INTO_SELF` | 카테고리를 자기 자신이나 그 아래로 옮길 수 없어요. |
| 400 `orderedIds` | `CATEGORY_REORDER_MISMATCH` | 순서가 화면과 어긋났어요. 새로고침한 뒤 다시 시도해 주세요. |
| 400 (상위 없음) | `CATEGORY_PARENT_MISSING` | 선택한 상위 카테고리가 없어졌어요. 목록을 새로고침해 주세요. |

**문장 규칙**

1. **사용자가 한 행동의 언어로 쓴다.** `orderedIds` 가 아니라 "순서".
2. **다음에 무엇을 할지 말한다.** "…할 수 없습니다" 로 끝내지 않는다.
3. **원인을 짚을 수 있으면 이름으로 짚는다.** `'색상' 속성은 '의류' 에 이미…` 는 이미 좋다.
4. 내부 식별자를 쓰지 않는다. `slug` → "주소".

### 4.3 사용자가 볼 이유가 없는 오류

```ts
// permission.guard.ts — 지금
throw new ForbiddenException('엔드포인트 권한 선언이 잘못되었습니다.')
throw new ForbiddenException('엔드포인트에 퍼미션이 선언되지 않았습니다.')
```

둘 다 **개발자가 코드를 잘못 짠 상황**이다. 403 으로 보이면 사용자는 "내 권한이 부족한가" 로
잘못 판단하고, 할 수 있는 일이 없다. `InternalServerErrorException` 으로 바꾸고 화면은
아래 4.4 의 문의 안내를 보여 준다. **서버 로그에는 원래 문장을 그대로 남긴다.**

같은 이유로 `"인증 정보가 없어 요청을 처리할 수 없습니다."` 는 `AUTH_REQUIRED` +
"로그인이 필요해요." 로 바꾼다. 사용자에게 필요한 것은 인증 정보의 유무가 아니라 다음 행동이다.

### 4.4 QA 로 이어지는 길

`requestId` 는 **이미 만들어지고 있다** — `request-context.middleware.ts` 가 `randomUUID()` 로
만들어 응답 헤더 `x-request-id` 에 싣고, CORS `exposedHeaders` 에도 이미 올라가 있다.
**빠진 곳은 두 군데뿐이다.**

1. `ApiClientError` 가 그 헤더를 읽지 않는다 → 읽어서 `requestId` 로 보관
2. 오류 봉투에 없다 → `buildErrorBody` 가 넣는다 (헤더를 못 읽는 상황 대비)

화면 규약:

| 실패 성격 | 보여 주는 것 |
| --- | --- |
| 사용자가 고칠 수 있음 (검증·충돌) | 문장 + 복구 수단. **번호를 보여 주지 않는다** — 잡음이다 |
| 사용자가 고칠 수 없음 (500·503·네트워크) | 문장 + **문의 번호 + 복사 버튼** |

```
일시적인 문제가 생겼어요. 잠시 후 다시 시도해 주세요.
문의하실 때 이 번호를 알려주시면 더 빨리 확인할 수 있어요.

  4f3c1a90-…-a7b2   [복사]
```

**번호는 QA 가 로그에서 같은 값을 찾을 수 있어야 의미가 있다.** 그래서 완료 기준 F6 은
"화면에 번호가 뜬다" 가 아니라 **"그 번호로 서버 로그의 해당 요청을 찾을 수 있다"** 이다.

### 4.6 권한

역할별 차이 없음. 오류 표현은 세 앱 공통이고, **권한 부족(403)의 문구는 바꾸지 않는다** —
`access-denied.ts` 의 일반 문구는 의도적으로 무엇이 부족한지 밝히지 않는다(정보 노출 방지).

### 4.7 구현에서 확정한 판단

승인된 4.1~4.6 을 바꾸지 않되, 문서가 정하지 않고 남긴 자리를 구현 착수 전에 아래로 고정한다.

| # | 판단 | 근거 |
| --- | --- | --- |
| J1 | 도메인 코드 목록은 `packages/shared/src/api/error-codes.ts` 한 곳에 둔다 | 서버가 던지는 문자열과 프론트 카탈로그의 열쇠가 같아야 한다. 두 곳에 적으면 오타가 "문장 없는 오류"로 조용히 나타난다 (C1 과 같은 이유) |
| J2 | 앱 카탈로그의 `errors` 는 `Record<UserFacingErrorCode, string>` 로 **전수 타입**을 건다 | 코드를 추가하고 문장을 빠뜨리면 `pnpm typecheck` 가 잡는다. 런타임에 빈 문장이 뜨는 길을 없앤다 |

### 4.8 F3 을 어떻게 잴 것인가

**음성 대조군은 스크립트다.** 서버(와 서버 대역인 msw)가 내는 한국어 실패 문장 31종을 기계적으로
다른 말로 바꾸고 — 필드 경로·코드·상태·모양은 그대로 두고 — 스펙을 다시 돌린다. 문장에 기대고
있던 것만 빨개진다.

특히 `parse-input.ts` 의 `` `${path} 값이 올바르지 않습니다.` `` 는
`` `입력하신 내용을 다시 확인해 주세요. (${path})` `` 로 바꾼다. **필드 이름이 문장 앞에서
사라지므로**, 선두 토큰 추론에 기대는 코드는 여기서 반드시 깨진다.

측정은 두 번 한다.

| 측정 | 무엇을 비교하나 |
| --- | --- |
| A | **같은 스크립트, 같은 명령**을 착수 시점(`17fd9ce`)과 완료 시점에 돌린다 |
| B | 이 TASK 가 새로 쓴 계약 스펙만, **구현 파일을 착수 시점으로 되돌린 채** 돌린다 |

A 는 "기존 스펙이 문장에 묶여 있었다"를, B 는 "새 스펙이 실제로 깨진 것을 잡는다"를 보인다.
둘 다 없으면 0 이라는 숫자가 아무것도 증명하지 않는다.

### 6.6 F6 실증 기록

실 HTTP 로 500 을 3회 유발하고(퍼미션 미선언 핸들러 — 4.3 이 말하는 상황 그대로),
응답 헤더 `x-request-id` 와 본문 `error.requestId` 가 같은 값임을 확인한 뒤 그 번호로
서버가 실제로 쓴 로그 파일을 `grep` 했다.

```
=== 화면에 뜰 문의 번호 ===
e30b3f8b-0236-4d2f-8d13-70ffb7c7e02d

=== grep 결과 ===
[error] GET /api/v1/boom 500 e30b3f8b-…-70ffb7c7e02d InternalServerErrorException
[error] GET /api/v1/boom 500 5.7ms e30b3f8b-…-70ffb7c7e02d
--- 건수: 2 ---

세 번호 각각 2건 · 존재하지 않는 번호 0건 · 같은 시간대의 404 요청은 매칭되지 않음
```

**2줄인 이유**는 한 요청이 두 곳에 기록되기 때문이다 — 예외 필터가 남긴 실패 기록과
미들웨어가 남긴 종료 기록. 완료 기준의 "1건"은 **한 요청만 특정된다**는 뜻이고, 그 성질은
지켜졌다(다른 요청 0줄, 없는 번호 0줄).

같은 로그에 `BoomController.boom 에 퍼미션 선언이 없어 요청을 차단했습니다.` 가 남아 있고
**응답 본문에는 없다** — F8 이 함께 실증됐다.

## 7. 리스크 / 열린 질문

| # | 내용 | 대응 |
| --- | --- | --- |
| R1 | 문구를 바꾸면 기존 스펙이 문장을 단언하고 있어 무더기로 깨질 수 있다 | 스펙이 **문장이 아니라 `code`** 를 단언하도록 먼저 바꾼다. 그 자체가 F3 의 증거다 |
| R2 | `requestId` 를 화면에 띄우면 내부 정보 노출 아닌가 | UUID 는 **그 자체로 아무것도 알려주지 않는다.** 서버 로그와 대조해야만 의미가 생긴다. 단, 사용자가 고칠 수 있는 실패에는 띄우지 않는다 |
| R3 | `productCount` 가 항상 0 이면 화면이 잘못 안내한다 | 화면은 `productCount > 0` 일 때만 사전 안내하고, **서버 409 는 그대로 처리**한다. 0 이어도 동작이 지금과 같다 |
| R4 | 카탈로그 밖 도메인은 아직 코드가 없다 | `details` 혼재 허용(4.1)으로 **점진 적용**. F9 가 이것을 고정한다 |
| R5 | "문의" 채널이 아직 없다 | 이번엔 **번호를 전달 가능하게** 하는 데까지. 안내 문구는 채널이 생기면 카탈로그 한 줄로 바뀐다 |
