## 1. 목적

카테고리별 속성 정의를 테이블로 만들고, 정의로부터 **검증 스키마를 동적 생성**하는 로직을 만든다. 값은 `Product.attributes` JSONB 에 저장한다. (D-025)

## 2. 범위

### 포함
- `AttributeDefinition` — 카테고리, key, label, type, options, `isFilterable`, `isRequired`, `sortOrder`
- 타입: TEXT / NUMBER / SELECT / MULTI_SELECT / BOOLEAN
- **상위 카테고리로부터 상속** — 해당 카테고리의 유효 속성 목록 조회 API
- 정의로부터 zod 스키마 동적 생성기
- 값 검증 함수 (저장 전 필수 호출)
- 정의 CRUD API
- key 중복 방지 (같은 카테고리 계통 내)

### 제외
- 관리자 화면 (TASK-0031)
- 검색 필터 UI (M06)

## 4. 설계

```
카테고리 "코트"의 유효 속성 = 자신 + 조상들의 정의 (path 를 이용해 한 번에 조회)

validateAttributes(categoryId, values)
  ① 유효 속성 목록 조회
  ② 정의로부터 zod 스키마 생성 (타입·필수·선택지 반영)
  ③ parse → 실패 시 필드별 오류 반환
```

**DB 가 값을 강제하지 못하므로 이 검증 함수가 무결성의 유일한 방어선이다.** 상품 저장 경로가 이 함수를 우회할 수 없게 서비스 계층 한 곳으로 모은다.

### 4.1 상속 — "가장 가까운 정의가 이긴다"

유효 속성은 **자신과 조상들의 정의를 합친 것**이고, 같은 `key` 가 계통에 두 번 나타나면 **더 깊은(가까운) 정의가 이긴다.**

새 정의를 만들 때는 계통 안의 중복을 **거부**한다(F7). 그런데 해석 함수는 그것과 별개로 **전 함수(total function)** 여야 한다 — 중복이 존재할 수 없다고 가정하면 안 된다.

이유는 **카테고리 이동**이다. 루트 A 가 `brand` 를 정의하고, 다른 루트 B 아래의 X 도 `brand` 를 정의한 상태에서 X 를 A 아래로 옮기면, 두 정의가 한 계통에 들어온다. 이동은 TASK-0028 의 기능이고 속성을 보지 않는다. 이때 해석 함수가 "있을 수 없다"고 던지면 **관리자 화면 전체가 카테고리 이동 한 번으로 죽는다.**

그래서 중복은 오류가 아니라 **가림(override)** 으로 정의한다. 가까운 정의가 이기는 것은 상속을 가진 어떤 체계에서도 자연스러운 규칙이고, 결과가 결정적이다. 대신 그 상태가 **조용히** 생기지 않도록 생성 시점에서 막는다 — 생성은 사람이 지금 하는 실수이고, 이동은 의도한 재배치다.

### 4.2 계통 중복 검사는 왜 애플리케이션인가 (S5 경계)

`(categoryId, key)` 중복은 부분 유니크 인덱스가 막는다. 그러나 **계통 전체**의 중복은 "조상이나 자손 중에 같은 key 를 가진 행이 있는가"이고, 이는 다른 행을 **조회**해야 답할 수 있다. PostgreSQL 의 CHECK 제약에는 **서브쿼리를 쓸 수 없다.** 배제 제약(EXCLUDE)도 "한 path 가 다른 path 의 접두사"를 표현하는 연산자가 기본 제공되지 않는다.

즉 이 규칙은 **DB 가 강제할 수 없다.** 그러면 두 요청이 각자 "계통에 없다"를 확인하고 둘 다 커밋하는 경합이 남는다(A7). 그래서 정의 쓰기는 **카테고리 트리 어드바이저리 락**을 잡는다.

**왜 전용 락이 아니라 트리 락인가.** 계통이라는 개념 자체가 트리의 모양이고, 그 모양을 다시 쓰는 것이 카테고리 이동이다. 전용 락을 쓰면 "조상 목록을 읽고 → 중복을 확인하는" 사이에 이동이 끼어들어, 확인한 계통과 삽입되는 계통이 달라진다. 트리 락을 공유하면 확인과 삽입이 같은 트리에 대해 일어난다. 비용은 없다시피 하다 — 카테고리 이동도 속성 정의 변경도 관리자만 하는 드문 작업이고, **조회는 어느 쪽 락도 잡지 않는다.**

락이 막지 **못하는** 것도 분명히 해 둔다. 정의를 만든 **뒤에** 카테고리를 옮기면 계통에 중복이 생긴다. 그것이 4.1 의 해석 규칙이 전 함수여야 하는 이유다.

### 4.3 조회는 한 문장

유효 속성 조회는 `Category` 에서 대상의 `path` 를 읽고 그 자리에서 조상 id 배열로 바꿔 조인한다.

```sql
LEFT JOIN "AttributeDefinition" d
  ON d."categoryId" = ANY (string_to_array(btrim(t."path", '/'), '/')::int[])
```

문장 하나이므로 스냅샷이 일관되고(읽는 중에 이동이 끼어들어 계통이 반쯤 바뀌는 일이 없다), `= ANY` 가 `AttributeDefinition_categoryId_key_active_key`(부분 유니크, `categoryId` 선두, `deletedAt IS NULL` 조건 내장)를 타므로 깊이가 늘어도 문장 수가 늘지 않는다(A5). `LEFT JOIN` 인 이유는 **정의가 하나도 없는 카테고리와 존재하지 않는 카테고리를 구분**하기 위해서다 — 전자는 행 1개(정의 열이 NULL), 후자는 0개다.

### 4.4 수정할 수 있는 것과 없는 것

`key` 와 `type` 은 **바꿀 수 없다.** 둘 다 이미 저장된 상품의 `attributes` JSONB 가 의미하는 바를 바꿔 버린다 — `key` 를 고치면 기존 값이 전부 고아가 되고, `type` 을 고치면 기존 값이 전부 타입 위반이 된다. 바꾸고 싶으면 새 정의를 만들고 옛 정의를 지운다. 지우는 것은 소프트 삭제이므로 옛 값의 출처는 남는다.

`label`·`options`·`isRequired`·`isFilterable`·`sortOrder` 는 수정 가능하고, **낙관적 잠금(`version`)** 을 건다(DECISIONS 4 — 사람이 편집하는 데이터).

### 4.5 값 검증을 엔드포인트로 만들지 않는다

`validateAttributes` 는 **서비스 메서드**이고 HTTP 표면이 없다. 상품 저장(TASK-0032)이 이 메서드를 부르는 것이 요구사항이고, 검증만 하는 엔드포인트를 두면 "검증은 통과했으니 저장해도 된다"는 두 번째 진실이 생긴다 — 그 사이에 정의가 바뀌면 거짓이 된다. 화면은 같은 정의를 받아 스스로 그리고, 최종 판단은 저장하는 그 호출이 한다.

| R2 | 정의 삭제 후 상품에 고아 key 잔존 | 정의 삭제 시 사용 중이면 차단, 강제 삭제 시 정리 배치 제공. **`Product` 가 아직 없으므로 "사용 중" 검사는 TASK-0032 가 붙인다** — 이 TASK 에서는 소프트 삭제만 하고, 값이 생기기 전이므로 고아가 발생할 수 없다 |
| R3 | 카테고리 이동으로 계통에 같은 key 가 겹친다 | 오류가 아니라 **가림**으로 정의하고 해석 함수를 전 함수로 만든다 (4.1). 생성 시점의 중복만 거부한다 |
| R4 | 속성 정의 변경이 트리 락을 잡아 카테고리 이동과 경합한다 | 둘 다 관리자만 하는 드문 쓰기이고 조회는 락을 잡지 않는다 (4.2). 실측 생성 p95 8.0ms |
| R5 | `options` 를 좁히면 이미 저장된 값이 검증을 통과하지 못한다 | 선택지 축소는 허용하되(운영자가 오타를 지울 수 있어야 한다) 사용 중 검사는 R2 와 같은 시점, 즉 TASK-0032 에서 붙인다 |

### 7.3 A7 — 동시 요청 검증과 음성 대조군

`apps/api/test/db/attribute-lineage-contention.spec.ts`, 각 10회 반복.

**이 TASK 가 A7 대상인 이유가 다른 TASK 와 다르다.** 잔액도 재고도 순서도 멱등도 아니다. 걸리는 이유는 **"계통에 같은 key 하나"가 DB 가 강제할 수 없는 규칙**이라는 것이다(7.4). 그래서 애플리케이션의 check-then-insert 가 되고, 그것은 동시 요청 두 건이 정확히 깨뜨리는 모양이다. 다른 제약들이 PostgreSQL 에서 공짜로 얻는 보장을 이 규칙만 여기서 벌어야 한다.

| 시나리오 | 결과 |
| --- | --- |
| 계통의 양 끝(루트·잎)에서 같은 key 동시 생성 (2건) | 정확히 1건 성공, 1건 **409** + 충돌 카테고리 이름. live 정의는 정확히 1개 |
| 정의 생성 × 카테고리 이동 (2건) | 거부는 0건 또는 1건(409). 어느 인터리빙이든 유효 속성 조회는 **key 당 정확히 하나**를 답한다 |
| 정의 3건 생성 중 조회 6건 동시 실행 | 어떤 조회도 같은 key 를 두 번 보지 않고, 만들어지는 중인 집합의 부분집합만 본다 (조회가 한 문장이라 스냅샷이 일관된다) |
| 같은 `version` 으로 동시 편집 (2건) | 1건 200, 1건 **409**. `version` 은 정확히 +1 |

**음성 대조군 — 락 없는 구현, 실 테이블.** 서비스와 똑같은 검사·삽입을 raw SQL 로 다시 쓰되 `pg_advisory_xact_lock` 만 뺐다. `barrier` 로 "둘 다 검사한 뒤에 쓴다"를 고정한다.

- 두 트랜잭션 모두 충돌 **0건**을 보고 둘 다 커밋한다. live 정의가 **2개**가 된다. 어떤 제약도 반대하지 않는다 — 반대할 수 있는 제약이 없다.
- 손상은 "행이 2개"가 아니다. 가까운 정의가 이기므로, 운영자가 `의류` 에 **필수로 걸어 둔 브랜드가 `티셔츠` 에서 조용히 선택 항목이 된다.** `validateAttributes(티셔츠, {})` 가 통과한다. 같은 순간 `validateAttributes(의류, {})` 는 여전히 거부하므로, 한 트리 안에서 같은 질문에 답이 둘이다.
- 같은 픽스처를 서비스로 돌리면 1건이 409 를 받고 계통에 답이 하나 남는다.

**락이 실제로 일을 하는지 확인했다.** `pg_advisory_xact_lock` 호출을 지우고 같은 스펙을 돌리면 계통 경합 단언 **20개 중 19개가 실패**한다(나머지 1개는 우연히 겹치지 않은 실행). 확인 후 원복했다.

**대조군을 하나 더 두지 않은 이유.** TASK-0028 은 제약을 뺀 픽스처 테이블(`TestCategoryNaive`)이 필요했다 — 실 테이블은 제약이 손상을 표현 불가능하게 만들어 두어 락을 빼도 깨진 트리를 볼 수 없기 때문이다. 여기엔 뺄 제약이 없다. 처음부터 DB 가 이 규칙을 쥔 적이 없다는 것이 이 파일의 존재 이유이고, 그래서 실 테이블 위의 대조군 하나로 손상이 그대로 재현된다.

**락이 막지 못하는 것.** 정의를 만든 **뒤에** 카테고리를 옮기면 계통에 중복이 생긴다. 락은 "검사한 계통 = 삽입되는 계통"을 보장할 뿐 미래의 이동을 막지 않는다. 그래서 해석 함수가 전 함수이고(4.1), 위 표의 두 번째 시나리오가 그것을 확인한다 — 그 시나리오는 락을 빼도 통과한다. 락이 아니라 해석 규칙이 지키는 성질이기 때문이다.

### 7.4 S5 — DB 와 애플리케이션의 경계

| 규칙 | 어디서 | 왜 거기인가 |
| --- | --- | --- |
| 카테고리당 live key 유일 | 부분 유니크 인덱스 | 두 요청이 동시에 통과할 수 있는 검사다. 소프트 삭제된 정의가 key 를 영원히 붙잡지 않도록 부분 인덱스 |
| key 형식 | CHECK | JSONB 키이자 Meilisearch 필터 필드명. 잘못되면 **오류 없이** 아무것도 매치하지 않는다 |
| 선택지 ↔ 타입 일치 (양방향, 최소 1개) | CHECK | 선택지 0개 SELECT 는 어떤 값도 통과시키지 못해 그 카테고리를 영구 저장 불가로 만든다 |
| 선택지에 빈 문자열 없음 · 라벨 비어 있지 않음 · `sortOrder` ≥ 0 | CHECK | |
| 정의는 실재하는 카테고리에 붙는다 | 외래키 `RESTRICT` | 카테고리 하드 삭제는 아무도 쓰지 않는 경로이므로 막혀 있어야 한다 |
| 타입은 5종 뿐 | enum | 알 수 없는 타입이 **표현 불가능**해지므로 생성기가 기본 분기 없는 `Record<AttributeType, …>` 를 쓸 수 있다 |
| **계통 전체의 key 유일** | **애플리케이션 + 트리 락** | 다른 행을 **조회**해야 답할 수 있다. CHECK 에 서브쿼리를 쓸 수 없고, "한 path 가 다른 path 의 접두사"를 표현하는 배제 연산자도 기본 제공되지 않는다 |
| **선택지 중복 없음** | **애플리케이션** | 중복 판정에 집계(`DISTINCT`)가 필요하고 CHECK 에 집계를 쓸 수 없다 |
| **값의 타입·필수·선택지** | **애플리케이션 (동적 zod)** | 값이 JSONB 다. `{"weight": "무거움"}` 을 `{"weight": 1200}` 과 똑같이 받는다 |

경계에 있는 두 규칙(선택지 중복, 계통 key)에 대해 **DB 가 해당 INSERT 를 실제로 받아들이는 것**을 테스트로 고정했다. "DB 가 막아 주겠지"라는 착각이 나중에 애플리케이션 검사를 지우는 근거가 되지 않게 하기 위해서다.

### 8.1 zod 4 에서 확인한 것

| 사실 | 영향 |
| --- | --- |
| `z.number()` 가 `NaN`·`Infinity` 를 이미 거부한다 | `.finite()` 를 얹지 않았다 — 어떤 입력도 닿을 수 없는 분기가 되어 분기 100% 를 불가능하게 만든다 |
| 필드 파싱 실패가 객체의 `.check()` 를 건너뛴다 | 필수 검사를 `.check()` 가 아니라 **필드 스키마를 `optional()` 로 만들지 않는 것**으로 표현했다. 그래야 값 오류와 필수 누락이 **함께** 보고된다 |
| `z.enum([])` 는 예외를 던지지 않고 모든 값을 거부한다 | 선택지 0개인 정의가 생성기에 도달해도 "아무 값도 통과하지 않는다"로 안전하게 끝난다 |
