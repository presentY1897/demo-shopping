# TASK-0031: 관리자 속성 관리 화면

## 1. 목적

관리자가 카테고리를 골라 속성을 정의하는 화면을 만든다. **D-005 "코드 수정 없이 설정 가능"이 눈으로 확인되는 지점**이다.

## 2. 범위

### 포함
- 카테고리 선택 → 해당 카테고리의 속성 목록 (상속분은 출처 표시)
- 속성 추가·수정 폼 (타입별로 입력 항목이 달라짐)
- SELECT/MULTI_SELECT 의 선택지 편집
- `isFilterable` 토글 — 검색 필터 노출 여부
- 표시 순서 조정
- 사용 중인 속성 삭제 차단
- 미리보기 — 정의로부터 생성될 상품 등록 폼 모습

### 제외
- 검색 필터 UI 실제 동작 (M06)

## 3. 요구사항

- [x] 상속된 속성과 직접 정의한 속성이 구분되어 보인다 — 같은 목록 안에서 `… 에서 물려받음` 배지로
- [x] 타입을 고르면 그에 맞는 설정 항목만 나타난다
- [x] 미리보기로 상품 등록 폼 모습을 확인할 수 있다 — 편집 폼을 모달이 아닌 인라인 패널로 둔 이유(4.11)
- [x] 사용 중인 속성은 삭제되지 않는다 — 차단은 동작한다. **사용 상품 수 안내만** 계약 부재로 이월 (F5)

## 4. 설계

미리보기는 TASK-0017 의 **동적 폼 생성기**를 그대로 쓴다. 관리자가 정의를 만들면서 결과를 즉시 보는 구조라, 판매자가 실제로 볼 화면과 어긋날 수 없다.

아래는 구현 전에 확정한 판단이다. **API 는 TASK-0030 이 이미 만들었고 이 TASK 는 붙이기만 한다** — 엔드포인트 4개(`GET/POST /attributes`, `PATCH/DELETE /attributes/:id`)와 `packages/shared` 계약을 그대로 쓴다.

### 4.1 카테고리 선택은 트리가 아니라 경로 셀렉트다

TASK-0029 가 만든 카테고리 트리는 roving `tabindex`·`aria-level`·낙관적 이동을 갖춘 편집기다. 이 화면에서 카테고리는 **편집 대상이 아니라 필터**이므로 그 트리를 다시 그리면 같은 데이터의 세 번째 렌더링이 되고, 이 화면에서는 쓸 수 없는 조작(하위 추가·이동·정렬)이 전부 따라온다.

그래서 카테고리 선택은 `Select` 하나이고, 각 항목의 라벨이 **전체 경로**(`여성 › 아우터 › 코트`)다. 트리 구조는 라벨이 나르고, 탭 정지점은 40개가 아니라 1개가 된다. 데이터는 TASK-0029 의 `toRows`·`childrenOf` 를 그대로 재사용해 깊이 우선 순서로 편다 — 트리 해석을 두 벌 두지 않는다.

비활성 카테고리도 후보에 남긴다. 정의는 비활성 카테고리에도 붙어 있고, 보이지 않으면 되살릴 수도 고칠 수도 없다(TASK-0029 가 `includeInactive=true` 로 트리를 받는 것과 같은 이유).

### 4.2 상속은 목록 한 벌로 보여 준다 — 구역을 나누지 않는다

유효 속성 조회(`GET /attributes?categoryId=`)는 **일반 → 구체** 순으로 정렬된 한 벌을 답하고, 각 항목이 `inherited` 와 **정의를 소유한 `categoryId`** 를 함께 나른다. 화면은 그 순서를 그대로 그린다.

상속분을 별도 구역으로 접어 두는 안을 버렸다. 이 목록의 순서가 곧 **상품 등록 폼의 필드 순서**이고(미리보기가 같은 배열로 만들어진다), 구역을 나누면 화면이 보여 주는 순서와 실제 폼의 순서가 달라진다. F4 가 "실제 상품 등록 폼과 동일한 모습"을 요구하는 이상 목록도 폼과 같은 순서여야 한다.

대신 각 행이 **출처를 이름으로 밝힌다.** 상속된 행은 소유 카테고리 이름을 배지로 달고, 그 행의 편집·삭제 버튼 자리에는 **"정의된 곳으로 이동"** 이 들어간다 — 누르면 셀렉트가 그 카테고리로 바뀐다. "여기서는 못 고친다"를 비활성 버튼으로 말하면 막다른 길이지만(TASK-0029 `removeBlocked` 와 같은 문제), 고칠 수 있는 곳으로 데려다주면 안내가 된다.

**가림(override)은 화면이 다루지 않는다.** 계통에 같은 `key` 가 둘 있으면 가까운 정의가 이기고, 그 판정은 서버의 `resolveEffectiveAttributes` 가 이미 끝낸 뒤 **key 당 한 행**만 내려보낸다(TASK-0030 4.1). 화면이 다시 판정하면 두 번째 진실이 된다.

### 4.3 `key` 와 `type` 은 만들 때만 있는 입력이다

수정 요청 스키마(`updateAttributeRequestSchema`)에는 `key` 도 `type` 도 없다. 둘 다 이미 저장된 `Product.attributes` JSONB 의 **의미**를 바꾸기 때문이다(TASK-0030 4.4). 그래서 폼은 한 컴포넌트이되 두 모드다.

| | 만들기 | 수정 |
| --- | --- | --- |
| `key` · `type` | 입력 | **읽기 전용 표시** + 바꾸려면 새로 만들고 지우라는 안내 |
| `label` · `options` · `isRequired` · `isFilterable` · `sortOrder` | 입력 | 입력 |
| `version` | — | 숨은 값, 낙관적 잠금 |

읽기 전용을 `disabled` 입력으로 그리지 않는다. 비활성 입력은 탭 순회에서 빠져 키보드 사용자가 값을 읽을 수 없다(P4). 값과 함께 "왜 못 바꾸는가"를 문장으로 적는다.

### 4.4 타입별 항목은 계약 함수가 가른다

"타입을 고르면 그에 맞는 설정 항목만 나타난다"(F2)의 분기는 화면이 아는 목록이 아니라 `packages/shared` 의 `attributeTypeHasOptions(type)` 이 정한다. 선택지 편집기는 그 함수가 `true` 인 타입에만 나타난다. 타입이 6번째로 늘어나면 계약 한 곳만 바뀐다.

### 4.5 폼의 규칙은 계약 스키마가, 문구는 카탈로그가

폼은 TASK-0017 의 `useForm` 을 쓴다(`Form` · `FormField` · `DynamicForm` 과 같은 진입점). `useForm` 은 zod 스키마 하나를 받으므로, 앱은 **계약 스키마를 술어로 감싼 폼 스키마**를 만든다.

```
key   → z.string().min(1, 카탈로그.keyRequired)
              .refine(v => attributeKeySchema.safeParse(v).success, 카탈로그.keyFormat)
label → 같은 방식으로 attributeLabelSchema
```

규칙은 여전히 `packages/shared` 한 곳에 있고(C1), 문구만 앱이 정한다. 서버 문장을 그대로 쓰지 않는 이유는 그 문장이 내부 식별자를 담기 때문이다 — `optionIssues` 는 `"SELECT 속성은 선택지가 최소 1개 필요합니다."` 라고 답하는데 `SELECT` 는 사용자의 낱말이 아니다(오류 계약 3장 규칙 4).

그래서 선택지 규칙만은 앱이 **술어를 다시 적는다.** 다시 적은 것이 어긋나지 않는다는 보장은 주석이 아니라 스펙이다 — `optionProblems()` 와 `optionIssues()` 가 같은 입력표에서 **같은 판정**을 내리는지 검사한다. 드리프트를 말로 막지 않고 테스트로 막는다.

### 4.6 순서 변경은 PATCH 두 번이고, 실패하면 되돌리지 않고 다시 읽는다

카테고리에는 `POST /categories/reorder` 가 있어 한 번에 원자적으로 순서를 바꾼다. **속성에는 그런 엔드포인트가 없다.** `sortOrder` 는 `PATCH /attributes/:id` 의 필드 하나이고, 각 행은 자기 `version` 을 들고 있다.

이웃한 두 행의 `sortOrder` 를 맞바꾸려면 요청이 둘 필요하다. 그 사이에 하나가 실패할 수 있고, 그때 남는 상태는 **손상이 아니라 절반만 반영된 유효한 상태**다. TASK-0029 처럼 스냅샷으로 원위치시키는 선택지도 있지만, 그러려면 실패를 되돌리는 요청을 또 보내야 하고 그것도 실패할 수 있다.

그래서 이 화면은 **되돌리지 않고 다시 읽는다.** 낙관적으로 즉시 그리고(DECISIONS 4장), 실패하면 목록을 서버에서 새로 받아 사실을 보여 준 뒤 실패를 알린다. 화면이 지킬 수 없는 약속(원자성)을 지키는 척하지 않는 편이 낫다.

`sortOrder` 를 같은 값으로 몰아 동점을 만드는 한 번짜리 요청도 검토했다가 버렸다. 서버의 정렬은 `(깊이, sortOrder, id)` 이므로 동점이 생기면 순서가 id 로 결정되어 관리자가 지정한 순서와 달라진다.

**상속된 행은 순서 조작 대상이 아니다.** 정렬의 1순위가 소유 카테고리의 깊이라, 상속분은 항상 자기 정의보다 앞에 온다. 위·아래 버튼은 이 카테고리가 소유한 행들 사이에서만 동작한다.

### 4.7 삭제 — F5 의 절반은 이 화면이 만들 수 없다

F5 는 "사용 중인 속성은 삭제되지 않는다 + 사용 상품 수 안내"를 요구한다. **이 브랜치를 딴 시점의 API 는 그 질문에 답하지 못했다.** TASK-0030 R2 와 `AttributeService.remove` 주석이 명시한 대로, "사용 중" 검사는 `Product` 가 생기는 TASK-0032 의 몫이었다.

이 TASK 는 `apps/api` 와 `packages/shared` 를 건드리지 않으므로 코드를 만들어 낼 수 없다. 없는 응답을 모킹으로 지어내 화면 테스트를 초록으로 만드는 것은 계약 게이트가 막으려는 바로 그 상태다.

그래서 화면 쪽 거부 경로만 만든다 — 삭제가 **충돌로 거부되면 확인 다이얼로그가 닫히지 않고 설명으로 바뀐다**(TASK-0029 의 `remove-blocked` 모양). 분기는 봉투 `code` 이고, 아직 도메인이 이름 붙이지 않은 409 의 코드는 `CONFLICT` 다 — 오류 계약 2.1 이 그렇게 정해 둔 값이므로 이것도 문장이 아니라 코드로 가르는 것이다.

> **작업 중에 절반이 채워졌다.** TASK-0032 가 `main`(`c9e139a`)에 `refuseRemovalInUse` 를 넣어, 정의의 카테고리와 그 아래에서 값을 들고 있는 상품이 있으면 409 를 던진다. 도메인 코드는 붙이지 않았으므로 봉투는 예상대로 `CONFLICT` 이고, **화면은 고칠 것이 없다.** 남은 것은 "사용 상품 수"뿐이고 그 수는 응답에 실려 오지 않는다.

삭제 자체는 소프트 삭제다. 확인 다이얼로그는 그것을 말한다 — 정의는 사라지지만 이미 저장된 값의 출처는 남는다.

### 4.8 오류는 `code` 로 갈리고 `field` 로 놓인다 (TASK-0117)

한국어 문장을 읽는 분기는 하나도 만들지 않는다.

| 서버가 보내는 것 | 화면이 하는 일 |
| --- | --- |
| `ATTRIBUTE_KEY_TAKEN` (409, `field: 'key'`, `params.name`) | `key` 입력칸 아래에 카탈로그 문장. `{name}` 은 충돌한 카테고리 이름으로 채워진다 |
| `ATTRIBUTE_VERSION_CONFLICT` (409, `field: 'version'`) | **충돌 다이얼로그** — 지금 저장된 값과 내가 입력한 값을 나란히 놓고 사람이 고른다 |
| `INVALID` (400, `field: 'options'`) | 선택지 편집기 아래 |
| 코드 없는 400 + 문자열 `details` | 폼 상단 (`FormError`). 놓을 곳을 지어내지 않는다 |
| 5xx | `ErrorNotice` + **문의 번호**. 토스트가 아니다 — 번호는 옮겨 적으라고 보여 주는 값인데 토스트는 읽는 중에 사라진다 |
| 응답 없음(네트워크·타임아웃) | 토스트. **번호를 만들어 내지 않는다** |

`version` 은 폼의 입력이 아니므로 `serverFieldErrors` 의 필드 목록에 없다. 그래서 버전 충돌은 필드에 붙지 못하고, **코드로 먼저 가로채** 다이얼로그를 연다 — 순서가 뒤바뀌면 사용자가 건드린 적 없는 값에 오류가 달린다.

`ATTRIBUTE_KEY_TAKEN` 은 `details[].field` 로도 오고 봉투 `code` 로도 오므로 양쪽을 다 받는다(`codeFields` 매핑). 서버가 항목을 빠뜨려도 메시지는 제자리에 놓인다.

### 4.9 실패 해석 모듈을 카테고리에서 꺼낸다

`src/lib/categories/errors.ts` 의 `categoryFailure`·`hasCode`·`failureMessage`·`quotableRequestId` 는 이름만 카테고리일 뿐 **카테고리에 대해 아무것도 모른다.** 봉투를 읽고, 코드로 문장을 찾고, 번호를 보여 줄지 정한다.

속성 화면이 그것을 그대로 필요로 한다. 복사하면 두 벌이 되고 한 벌만 고쳐지는 날이 온다. 그래서 `src/lib/api-failure.ts` 로 **옮긴다**(`ApiFailure`·`apiFailure`·…). 카테고리 화면은 새 경로를 가리키기만 하고 동작은 그대로다. 분기 100% 임계값도 새 경로로 옮긴다.

`failures` 문구 레코드는 화면마다 다를 수 있으므로 `failureMessage` 가 **인자로** 받는다 — 카탈로그를 어느 슬라이스에서 읽을지는 부르는 쪽이 안다.

### 4.10 미리보기는 편집 중인 정의까지 포함한다

미리보기 패널은 `EffectiveAttribute[]` 를 `FieldDef[]` 로 옮겨 `DynamicForm` 에 넘긴다. 옮기는 함수는 순수하고, 타입 매핑은 기본 분기 없는 `Record<AttributeType, FieldType>` 다 — enum 이 닫혀 있으므로 알 수 없는 타입이 표현 불가능하다(TASK-0030 7.4).

**폼 다이얼로그가 열려 있으면 미리보기는 저장 전 값을 반영한다.** R1("미리보기와 실제 폼이 어긋남")의 대응은 같은 생성기를 쓰는 것이고, 그 위에 "지금 입력 중인 정의가 폼에서 어떻게 보일지"까지 보여야 관리자가 저장 전에 판단할 수 있다. 목록에 없는 정의는 초안으로 끼워 넣고, 이미 있는 정의를 수정 중이면 그 자리에서 갈아 끼운다.

미리보기 폼은 필드 구성이 바뀔 때 **다시 마운트**된다. `useForm` 은 `initialValues` 를 첫 렌더에만 읽으므로, 정의가 늘거나 줄어도 값 객체는 옛 키를 그대로 들고 있다. 필드 서명(`key:type` 나열)을 `key` 로 주어 구성이 바뀌면 새 폼이 되게 한다.

미리보기에는 제출 버튼이 없다. 누를 수 있는데 아무 일도 일어나지 않는 버튼은 미리보기가 아니라 거짓말이다.

### 4.11 그래서 편집 폼은 다이얼로그가 아니다

TASK-0029 의 카테고리 편집은 모달이다. 여기서 같은 선택을 하면 **4.10 이 성립하지 않는다** — 모달이 열려 있는 동안 미리보기는 그 뒤에 가려지고, "입력하면서 결과를 본다"는 구조 자체가 없어진다.

그래서 이 화면의 추가·수정 폼은 **오른쪽 열의 인라인 패널**이고, 그 바로 아래에 미리보기가 있다. 왼쪽 열의 목록은 그대로 있으므로 어떤 속성을 고쳤는지도 보인다. 화면의 존재 이유가 "정의를 만들면 이렇게 된다"를 눈으로 보여 주는 것(D-005)이므로, 그 둘이 동시에 보이는 것이 이 화면의 요구사항이다.

모달로 남는 것은 **결정**뿐이다 — 삭제 확인과 버전 충돌. 둘 다 편집이 아니라 답을 요구하는 질문이고, 그동안 뒤를 볼 이유가 없다.

### 6.4 P1 — 왜 못 넘겼고, 무엇이 원인인가

실측(Lighthouse 12, 모바일 프리셋, 프로덕션 빌드 `next start`, 5회 중앙값).

| 라우트 | LCP | JS 전송량 | `unused-javascript` |
| --- | --- | --- | --- |
| `/orders` (셸 + 페이지 헤더) | **1,805ms** (1806·1805·1805·2363) | 204KB | 94KiB |
| **`/attributes` (이 TASK)** | **2,709ms** | 398KB | 230KiB |
| `/categories` (TASK-0029, 이미 머지됨) | **2,710ms** | 397KB | 230KiB |

**같은 세션에서 `/orders` 가 1,805ms 로 재현된다.** 즉 기준선 1,804ms 는 이 머신에서 그대로 맞고, +905ms 는 측정 노이즈가 아니다.

**그런데 `/categories` 가 1ms 차이로 같은 값이다.** 두 화면이 불러오는 청크도 같다 — `/orders` 대비 늘어난 3개(약 194KB) 중 큰 둘(97KB·90KB)은 두 화면이 **공유**한다. 내용이 아니라 **콘솔의 상호작용 화면이 공통으로 지는 짐**(Radix · zod · 폼 시스템 · 클라이언트 경계)이다. LCP 요소도 두 화면 모두 `PageHeader` 의 설명 문단으로 같고, 서버가 이미 보낸 마크업이다. 늦는 것은 그리는 시점이지 만드는 시점이 아니다(Render Delay 83%, TTFB 452ms).

**이 관측이 [D-217](../../decisions/2026-09-04-session-03.md) 의 근거가 됐다.** 게이트가 이 TASK 와
무관한 부채로 이 TASK 를 막고 있었고, 그것을 오케스트레이터가 세 라우트를 직접 재서 확인했다
(`/orders` 1,806ms · `/categories` 2,858ms · `/attributes` 2,859ms). **LCP 는 화면 게이트에서
빠졌고**, 측정은 고칠 곳을 찾을 때 쓰는 방법으로 TASK-0097 이 소유한다.

**이 TASK 가 줄일 수 있는 것이 남아 있는지도 확인했다.** 늘어난 194KB 중 이 화면만의 코드는 1KB 미만(`/categories` 와의 차이)이다. 편집 폼을 `next/dynamic` 으로 미루는 안은 청크를 나누기만 할 뿐 공유 벤더 청크를 건드리지 못한다. 남는 것은 셸·벤더 번들을 줄이는 일이고 그것은 TASK-0097 의 1장이 이미 받아 둔 항목이다.

### 6.5 F5 — 무엇이 되고 무엇이 안 되는가

| | 상태 |
| --- | --- |
| 사용 중인 속성 삭제가 **차단되는가** | **된다.** `main` 의 `AttributeService.refuseRemovalInUse` 가 409 를 던지고(정의의 카테고리와 그 아래에서 `Product.attributes` 가 그 key 를 들고 있으면), 화면이 봉투 `CONFLICT` 를 받아 다이얼로그를 설명으로 바꾼다 |
| **사용 상품 수**가 안내되는가 | **안 된다.** 그 수를 나를 `params` 가 응답에 없다. 만들려면 `packages/shared` 에 코드를 더하고 서비스가 개수를 세어 보내야 하는데, 둘 다 이 TASK 의 소유 밖이다 |
| 선택지를 좁힐 때 | `main` 이 같은 시점에 `refuseNarrowingInUse` 도 넣었다 — 400 + `{ field: 'options', code: 'INVALID' }`. **화면은 이미 그 모양을 선택지 목록 아래에 놓는다**(오류 계약 스펙이 정확히 그 응답을 쏜다) |

이 브랜치의 모킹 API 는 `Product` 를 모르므로 "상품이 쓰고 있는 속성"을 만들어 낼 수 없다. 그래서 스펙은 **응답 모양**을 쏜다 — 실 API 가 지금 보내는 것과 같은 409 `CONFLICT` 를. 사용 상품 수까지 확인하려면 상품을 만들 수 있는 대역이 필요하고, 그것은 상품 화면 TASK 의 몫이다.
