## 1. 목적

재고 변동을 전부 원장에 기록한다. "재고가 왜 줄었나"에 답할 수 있고, 이후 주문·취소·반품이 이 원장을 통해 재고를 움직이게 한다.

## 2. 범위

### 포함
- `StockLedger` — variant, 유형, 수량(±), 참조(주문 등), 사유, 처리자, `balanceAfter`
- 유형: INBOUND / SALE / CANCEL / RETURN_IN / ADJUST / RESERVE_CONFIRM
- 재고 변경 서비스 — **모든 재고 변경은 이 서비스만 통과**
- `ProductVariant.stock` 갱신과 원장 기록을 한 트랜잭션으로
- 원장 조회 API + 판매자 화면(Variant 별 이력)
- 재고 정합성 점검 (원장 합계 = 현재 재고)

### 제외
- 예약(Reservation) — M07
- 주문 연동 — M07 이후

## 3. 요구사항

- [ ] 모든 재고 변경이 원장에 남는다
- [ ] 원장 합계와 현재 재고가 항상 일치한다
- [ ] 재고를 음수로 만들 수 없다
- [ ] 동시 변경에도 정합성이 깨지지 않는다
- [ ] 판매자가 Variant 별 재고 이력을 볼 수 있다

## 4. 설계

```
adjustStock({ variantId, type, quantity, refType, refId, reason, actorId })
  트랜잭션:
    ① SELECT stock, max(seq) FROM ProductVariant ... FOR UPDATE
    ② 결과 재고 < 0 이면 실패
    ③ variant.stock 갱신
    ④ StockLedger 기록 (seq = 직전 + 1, balanceAfter 포함)
```

`balanceAfter` 를 저장하는 이유: 원장을 처음부터 합산하지 않고도 특정 시점 재고를 알 수 있고, 정합성 점검이 쉬워진다.

### 4.1 원장이 현재값을 설명한다 — 지켜야 할 네 성질

CLAUDE.md 6장은 "현재값은 원장의 결과이며 대사가 가능해야 한다"고 말한다. 그것을 검사 가능한 문장 넷으로 푼다.

| # | 성질 | 뜻 |
| --- | --- | --- |
| L1 | **합계 일치** | `ProductVariant.stock = SUM(StockLedger.quantity)` — 예외 없이, 모든 Variant 에 대해 |
| L2 | **사슬 연결** | `balanceAfter(n) = balanceAfter(n-1) + quantity(n)`, 첫 행은 `balanceAfter(1) = quantity(1)` |
| L3 | **끝점 일치** | 마지막 행의 `balanceAfter` = 현재 `stock` |
| L4 | **자리 연속** | `seq` 가 1부터 빈틈 없이 이어진다 (`max(seq) = count(*)`) |

L1 만으로는 부족하다. 합계가 맞아도 `balanceAfter` 가 엉뚱하면 "이 시점의 재고는 얼마였나"에 답하지 못하고, 그것이 `balanceAfter` 를 저장하는 유일한 이유다. L4 는 행이 지워졌거나 잠금 밖에서 삽입됐다는 신호다.

**L1~L4 가 곧 대사 절차다.** `StockService.reconcile()` 이 네 가지를 한 문장으로 검사하고, 어긋난 Variant 와 **어느 성질이 깨졌는지**를 돌려준다. "합계가 다르다"만 알려주는 점검은 원인을 못 짚는다.

**초기 재고도 원장에 남는다.** TASK-0032 의 상품 등록은 `variantDefaults.stock` 을 Variant 행에 직접 썼다. 그대로 두면 L1 이 **모든 상품에 대해 처음부터 거짓**이다 — 원장이 설명하지 못하는 재고가 태어나는 순간 생긴다. 그래서 Variant 가 만들어질 때 `stock > 0` 이면 `INBOUND` 행을 함께 남긴다 (4.8).

### 4.2 원장 행의 자리는 `(variantId, seq)` 다

기본키를 전역 id 하나로 두지 않고 **Variant 별 일련번호**로 잡는다.

| 후보 | 문제 |
| --- | --- |
| UUIDv7 | 같은 밀리초 안의 두 행은 꼬리가 난수라 **순서가 정해지지 않는다.** `balanceAfter` 를 시간순으로 그리면 사슬이 거꾸로 보일 수 있다 |
| 전역 `BIGSERIAL` | 순서는 맞지만 커서에 전역 발급량이 실려 나가고, "빈틈 없음"(L4)을 Variant 단위로 물을 수 없다 |
| **`(variantId, seq)`** | 순서가 정확하고, 자리 중복을 **PK 가 거부**하며, 커서가 작고, L4 를 셀 수 있다 |

`seq` 는 **행 잠금을 쥔 채** `직전 최대 + 1` 로 계산한다. 그래서 잠금 밖에서 삽입된 행은 PK 충돌로 거부되거나 빈틈을 남긴다 — 즉 **PK 가 "잠금을 지나지 않은 기록"을 잡는 그물**이 된다. 잠금 없는 구현에서 이것이 실제로 어떻게 드러나는지는 7.3.

순서가 정확한 것이 왜 중요한가: `ProductVariant.id` 는 UUIDv7 이어도 상관없다(그 행은 하나뿐이다). 원장은 **행들 사이의 순서 자체가 데이터**다.

### 4.3 유형과 부호 — 방향은 유형이 정한다

| 유형 | 부호 | 언제 |
| --- | --- | --- |
| `INBOUND` | + | 입고. Variant 생성 시의 초기 재고도 여기 |
| `SALE` | − | 판매 확정 차감 |
| `CANCEL` | + | 주문 취소로 되돌아옴 |
| `RETURN_IN` | + | 반품 입고 |
| `RESERVE_CONFIRM` | − | 예약 확정에 따른 실차감 (M07) |
| `ADJUST` | ± | 관리자·판매자 조정. **사유 필수** |

**부호를 DB 가 쥔다.** `SALE` 인데 `quantity > 0` 인 행은 CHECK 이 거부한다. 유형과 부호가 어긋난 행은 원장을 읽는 모든 화면과 배치를 거짓말하게 만들고, 애플리케이션 검증은 임포트 스크립트가 우회한다.

`ADJUST` 만 양방향이고, 그래서 **`ADJUST` 에는 사유가 필수**다(CHECK). 나머지 유형은 무엇이 일어났는지를 유형 자체가 말하지만 조정은 사람의 판단이라 이유가 없으면 감사할 수 없다.

`quantity = 0` 은 변동이 아니다. CHECK 이 거부한다 — 0 짜리 행이 섞이면 L4 의 "빈틈 없음"이 의미를 잃는다.

### 4.4 같은 변동을 두 번 기록할 수 없다

주문·취소·반품은 재시도되는 경로다. 같은 주문 항목의 `SALE` 이 두 번 기록되면 재고가 두 번 빠지고, 그것을 **원장만 보고는 알 수 없다** — 두 행 다 형식이 완벽하다.

```
UNIQUE (variantId, type, refType, refId) WHERE "refId" IS NOT NULL
```

부분 유니크 인덱스인 이유: 참조 없는 변동(판매자의 입고·조정)은 같은 값이 여러 번 있는 것이 정상이다. "+5 입고"를 두 번 하는 것은 중복이 아니라 두 번의 입고다.

**검사가 아니라 인덱스인 이유**는 TASK-0032 의 SKU 와 같다. `SELECT ... 없으면 INSERT` 는 두 요청이 동시에 통과할 수 있는 검사다. 여기서는 행 잠금이 그것을 직렬화해 주지만, 잠금이 지켜 주는 것에 기대는 규칙과 **표현 자체가 불가능한** 규칙은 다르다. 후자만 psql 세션과 임포트 스크립트에도 적용된다.

`refType`·`refId` 는 **함께 있거나 함께 없다**(CHECK). 한쪽만 있는 행은 멱등 키가 될 수도, 안 될 수도 없는 상태다.

`refType` 은 열거형이고 값은 지금 `docs/design/erd.md` 가 이름 붙인 테이블에서만 온다 — `ORDER_ITEM`(4장), `STOCK_RESERVATION`(3장), `CLAIM_ITEM`(5장). 아직 존재하지 않는 테이블이지만 **원장이 가리킬 대상은 이미 설계에 있고**, 자유 문자열로 두면 M07 이 오타 하나로 멱등 키를 비껴간다.

### 4.5 원장은 고쳐 쓰지 않는다

```sql
CREATE TRIGGER "StockLedger_append_only"
  BEFORE UPDATE OR DELETE ON "StockLedger" ...  -- RAISE EXCEPTION
```

원장의 값어치는 "무엇이 일어났는가"를 **되돌릴 수 없게** 적어 두는 데 있다. 행을 고칠 수 있으면 그것은 원장이 아니라 그냥 로그이고, 재고가 왜 줄었는지에 대한 답이 나중에 달라질 수 있다.

잘못 적은 변동은 **반대 방향 `ADJUST` 로 상쇄**한다. 지우지 않는다. 그래야 "누가 언제 무엇을 되돌렸나"까지 원장에 남는다.

이것은 CHECK 이나 인덱스로 표현할 수 없어 **트리거**가 된다. 이 저장소의 첫 트리거이고, 트리거를 늘리는 것이 좋다는 뜻은 아니다 — 여기서만 필요한 이유는 금지 대상이 *값*이 아니라 *동작*이기 때문이다. 그래서 `updatedAt` 컬럼도 두지 않는다. 갱신되지 않는 테이블에 갱신 시각이 있으면 그 자체가 거짓말이다.

`TRUNCATE` 는 행 트리거를 발동시키지 않으므로 테스트 격리(워커 DB + `TRUNCATE`)는 그대로 동작한다.

### 4.6 여러 계정이 동시에 재고를 바꾸면

판매자가 입고 +5 를 처리하는 동시에 구매자 셋이 각각 1개씩 사는 상황이다. 카테고리(TASK-0029)와 달리 **낙관적 잠금을 쓰지 않는다.**

| | 카테고리 수정 | 재고 변경 |
| --- | --- | --- |
| 충돌 시 | 사용자에게 알리고 선택하게 함 | 알릴 대상이 없다 (구매자는 재고 숫자를 모른다) |
| 방식 | 낙관적 잠금(`version`) | **행 잠금으로 직렬화** |

```sql
BEGIN;
  SELECT stock FROM product_variant WHERE id = ? FOR UPDATE;  ← 여기서 순번이 정해진다
  -- 결과 재고 < 0 이면 ROLLBACK
  UPDATE product_variant SET stock = stock + ?;
  INSERT INTO stock_ledger (...);
COMMIT;
```

- 동시에 10건이 들어와도 **한 줄로 세워져 순서대로 처리**된다. 각자 자기 차례에 현재 재고를 다시 읽으므로 덮어쓰기가 없다.
- 재고가 부족한 요청만 실패하고 나머지는 성공한다. "누가 먼저 눌렀나"가 정직하게 결정된다.
- 원장은 append-only 라 충돌 자체가 없다. 잠그는 것은 `ProductVariant` 한 행뿐이다.
- 잠금 구간은 수 ms 다. 상품이 다르면 서로 다른 행이라 아예 경합하지 않는다.

**절대값이 아니라 조정량으로 받는 이유**도 같다(TASK-0115). "재고를 17로 설정"은 그 사이 팔린 수량을 덮어쓴다. "+5 입고"는 언제 처리되든 결과가 맞는다.

**`stock >= 0` CHECK 은 이 경합을 잡지 못한다.** 재고 1개에 −1 차감 두 건이 잠금 없이 겹치면 둘 다 `0` 을 쓴다. `0 >= 0` 이므로 제약은 침묵하고, 손상은 **재고가 음수가 되는 것이 아니라 원장 합계와 어긋나는 것**으로 나타난다 — 1개짜리 재고에서 2개가 팔렸는데 어떤 행도 이상해 보이지 않는다. 이것이 이 TASK 에 음성 대조군이 필요한 이유이고, 7.3 이 그것을 수치로 고정한다.

> **측정 후 덧붙임.** 그 손상은 4.2 의 기본키가 있는 설계에서는 **재현되지 않는다.** 두 요청이 같은 자리를 계산하므로 진 쪽이 키에 부딪힌다. 그래서 대조군을 둘로 나눴다 — 자리가 없는 원장에서 손상을 보이고(①), 실제 테이블에서는 잠금이 지키는 것이 정합성이 아니라 **판정과 처리량**임을 보인다(②). 7.3 참조.

**조건부 갱신(`UPDATE ... WHERE stock >= ?`)이 아니라 명시적 행 잠금인 이유.** 조건부 갱신도 같은 행 잠금을 잡으므로 `stock` 자체는 지킨다. 그러나 이 트랜잭션은 재고 한 컬럼만 쓰는 것이 아니라 **잠금 안에서 세 가지를 결정**한다 — 부족 여부, 다음 `seq`, `balanceAfter`. 잠금이 UPDATE 에 딸려 **나중에** 잡히면 그 셋은 잠기지 않은 스냅샷에서 계산된 뒤다. TASK-0032 7.3 이 "우연히 늦게 잡히는 잠금은 쓰기는 지켜도 판정은 못 지킨다"로 측정한 것과 같은 구조라, 여기서도 잠금을 **명시적으로, 그리고 먼저** 잡는다. 예약(TASK-0048)은 결정할 것이 "충분한가" 하나뿐이라 조건부 갱신이 맞고, 그래서 방식이 다르다.

### 4.7 모든 재고 변경이 이 서비스를 지난다

R1 이 지적한 위험은 "서비스를 우회한 직접 UPDATE"다. 코드 리뷰 항목으로 두면 다음 사람이 모른다. 오늘 `ProductVariant.stock` 을 쓰는 경로는 셋이고 **전부 원장을 지나게 바꾼다.**

| 경로 | 지금 | 바뀐 뒤 |
| --- | --- | --- |
| 상품 등록 시 Variant 생성 | `stock` 을 행에 직접 씀 | 같은 트랜잭션에서 `INBOUND`(seq 1) 를 함께 기록 |
| 옵션 값 추가로 Variant 신설 | 〃 | 〃 |
| `PATCH /products/:id` 의 `variants[].stock` | 절대값을 직접 씀 | **Variant 행을 잠그고** 현재값과의 차이를 `ADJUST` 로 기록 |

세 번째가 미묘하다. TASK-0032 4.5 는 "상품이 만들어진 뒤의 증감은 TASK-0036 이 원장으로 처리한다"고 적었지만 `updateProductRequestSchema` 는 여전히 절대값 `stock` 을 받는다. **필드를 없애지 않는다** — 쓰기 계약의 주인은 TASK-0113 이고, 계약을 바꾸는 것과 원장을 참으로 만드는 것은 다른 일이다. 대신 절대값을 **잠금 안에서 조정량으로 환산**해 기록한다. 그러면 그 사이에 팔린 수량이 원장에서 사라지지 않는다(재고 숫자는 여전히 요청한 절대값이 되지만, 그것은 호출자가 요청한 바다). 조정량 입력이 왜 나은지는 4.6 그대로이고, 그것을 강제하는 것은 TASK-0115·0116 의 몫이다.

**갓 만들어진 Variant 에는 잠금을 걸지 않는다.** 그 행은 같은 트랜잭션이 방금 INSERT 했고 커밋 전이므로 다른 트랜잭션이 볼 수도, 잠글 수도 없다. 직렬화할 상대가 없다. 100개 조합이면 잠금 100회를 아끼는 차이라 성능이 아니라 **의미**의 문제로도 그렇게 한다.

**규칙을 테스트로 고정한다.** `src/**` 에서 `ProductVariant` 의 `stock` 에 값을 대입하는 코드가 `stock.service.ts` 밖에 없다는 것을 스펙이 검사한다 (TASK-0032 F8 의 `isDemo` grep 과 같은 수법). 리뷰 체크리스트는 잊히지만 빨간 테스트는 잊히지 않는다.

### 4.8 원장 조회 API

| 메서드 · 경로 | 용도 | 퍼미션 |
| --- | --- | --- |
| `GET /api/v1/variants/:id/ledger?cursor=&limit=` | 한 Variant 의 재고 변동 이력 | `product.read` |

- 소유권은 Variant → Product → Seller 로 풀어 `assertResourceAccess` 에 넘긴다. 판매자는 `own`, 운영자는 `any`.
- 응답에 **현재 재고와 원장 합계를 함께** 싣는다. 화면이 대사를 눈으로 할 수 있어야 "대사가 가능하다"가 실현된 것이다.
- 커서는 `seq` 다. 내림차순으로 읽고 `seq < cursor` 로 다음 장을 받는다. 전역 발급량이 새지 않고, 페이지 사이에 새 행이 끼어들어도 중복·누락이 없다 (새 행은 항상 더 큰 `seq` 다).

**`/seller/...` 아래 두지 않은 이유.** TASK-0115 의 경로표는 `GET /api/v1/seller/variants/:id/ledger` 로 적고 있다. 원장은 판매자 콘솔의 데이터가 아니라 **Variant 의 데이터**이고, "재고가 왜 줄었나"를 묻는 사람에는 운영자도 포함된다. 콘솔 전용 목록·집계(TASK-0115)와 달리 이 응답은 호출자에 따라 달라지지 않는다. TASK-0115 는 이 엔드포인트를 그대로 쓰면 되고, 두 번 만들지 않는다.

### 4.9 판매자 화면은 여기서 만들지 않는다

2장의 "판매자 화면(Variant 별 이력)"과 F5 는 **TASK-0116**(판매자 상품 목록 · 재고 관리 화면)이 소유한다. D-208 이 화면과 API 를 레이어로 가른 시점(2026-09-03)에 TASK-0035 가 0115·0116 으로 쪼개졌고, `docs/design/pages.md` 2장의 `/products/[id]/stock`(Variant 별 재고, 변동 이력)이 그 문서 범위에 그대로 들어가 있다. 이 TASK 의 변경 이력은 그때 재고 조정 API 의 이관만 반영했고 화면 쪽은 손대지 않아 중복이 남았다.

같은 시점에 다른 작업이 `apps/seller` 를 쓰고 있기도 하다. **F5 는 이 TASK 에서 충족하지 않으며 `[x]` 로 적지 않는다.** 화면이 필요로 하는 것(응답 계약, `packages/shared` 스키마, 실제 응답의 `parse`)은 여기서 끝내 둔다.

### 4.10 새 도메인 오류 코드를 만들지 않는다

TASK-0032 4.10 과 같은 판단이고 이유는 하나 더 있다. 재고 서비스의 거부는 둘이다 — 재고 부족, 같은 변동의 재기록. 그런데 **오늘 HTTP 로 그 둘에 닿는 경로가 없다**: 조정 엔드포인트는 TASK-0115 소유이고, `PATCH /products/:id` 가 받는 절대값은 스키마가 이미 `0` 이상으로 막아 부족을 만들 수 없다. 화면에 뜰 수 없는 코드를 카탈로그에 넣으면 어느 앱도 그 문장을 검증할 수 없다.

그래서 거부는 전송 계층 코드(`409`·`400`·`404`·`403`)와 `details[].field` 로 답한다 — `error-contract.md` 2.1 이 명시적으로 허용하는 상태다. 코드는 그 실패를 **화면에 그리는** TASK-0115·0116 이 앱 카탈로그와 함께 붙인다.

### 4.11 정합성 점검은 스크립트가 아니라 서비스 메서드다

5장 계획은 "정합성 점검 스크립트"였다. `StockService.reconcile()` 로 만든다.

`apps/api/scripts/*.mjs` 는 커버리지 대상 밖이고 TypeScript 소스를 읽을 수 없어, 스크립트로 두면 **같은 SQL 이 두 벌**이 되고 그중 아무 테스트도 돌지 않는 쪽이 운영에서 쓰이게 된다. 점검 로직이 서비스에 있으면 실 PostgreSQL 스펙이 그것을 직접 돌리고(F2·F10), M15 의 정합성 배치(TASK-0032 R2)와 M07 이후의 예약 정리도 같은 메서드를 부른다.

### 4.12 DB 가 쥐는 것과 애플리케이션이 쥐는 것

| 규칙 | 어디서 | 왜 |
| --- | --- | --- |
| 원장 행의 자리가 겹치지 않는다 | PK `(variantId, seq)` | 잠금 밖에서 삽입된 행을 잡는 그물 (4.2) |
| 같은 참조의 같은 변동은 한 번뿐 | 부분 유니크 인덱스 `WHERE "refId" IS NOT NULL` | 두 요청이 동시에 "없다"를 확인할 수 있는 검사다 (4.4) |
| 유형과 부호가 맞는다 | CHECK | 애플리케이션 검증은 임포트 스크립트가 우회한다 |
| `quantity <> 0`, `balanceAfter >= 0`, `seq >= 1` | CHECK | 〃 |
| `refType` · `refId` 는 짝이다 | CHECK | 한쪽만 있는 행은 멱등 키가 될 수 없다 |
| `ADJUST` 에는 사유가 있다 | CHECK | 조정은 사람의 판단이고 이유 없이는 감사할 수 없다 |
| 재고가 음수가 되지 않는다 | CHECK (`ProductVariant_stock_check`, TASK-0032) | 마지막 방어선. **경합은 못 잡는다** (4.6) |
| 원장 행이 실재하는 Variant 를 가리킨다 | 외래키 `RESTRICT` | Variant 는 소프트 삭제라 사라지지 않는다 |
| 원장은 수정·삭제되지 않는다 | **트리거** | 금지 대상이 값이 아니라 동작이다 (4.5) |
| **`stock` = 원장 합계 (L1)** | **애플리케이션 + Variant 행 잠금** | 다른 테이블을 집계해야 답할 수 있고 CHECK 에 집계를 쓸 수 없다. **경합이 있고, 그래서 음성 대조군을 갖는다** |
| **`balanceAfter` 사슬 (L2·L3)** | **애플리케이션 + Variant 행 잠금** | 〃. 직전 행을 읽어야 알 수 있다 |
| **`seq` 의 연속성 (L4)** | **애플리케이션** (PK 가 중복만 막는다) | 빈틈은 집계로만 보인다 |
| **판매자 소유권** | **애플리케이션** (`assertResourceAccess`) | 행을 읽어야 알 수 있고 DB 에는 요청자가 없다 |

경계로 넘어온 규칙에 대해서는 **DB 가 그 INSERT·UPDATE 를 실제로 받아들이는 것**까지 테스트로 고정한다. "DB 가 막아 주겠지"가 나중에 애플리케이션 검사를 지우는 근거가 되지 않게 하기 위해서다 (TASK-0032 7.4 와 같은 이유).

### 4.13 L1 을 지연 제약 트리거로 강제하지 않는 이유

경계표가 "집계라서 CHECK 에 쓸 수 없다"로 끝나는 것은 절반만 맞다. **`DEFERRABLE
INITIALLY DEFERRED` 제약 트리거는 집계를 쓸 수 있고**, 커밋 시점에 돈다. 게다가
비싸지도 않다 — L2 를 INSERT 마다 직전 행 하나로 검사하고 L3 을 커밋 때 마지막 행
하나로 검사하면 둘 다 기본키 인덱스로 O(1) 이고, 그 둘이면 L1 이 귀납으로 따라온다.
즉 "재고 = 원장 합계"를 **DB 가 쥐게 만들 수 있었다.** 그렇게 하지 않았다.

| | |
| --- | --- |
| **실패 지점이 COMMIT 으로 간다** | 커밋에서 터지는 제약은 어느 입력의 문제인지 말할 수 없다. `details[].field` 가 없는 500 이 되고, 서비스가 이미 잠금 안에서 같은 것을 판정한 뒤라 사용자에게 남는 것은 잡음뿐이다 |
| **산술이 두 벌이 된다** | `nextBalance` 와 같은 계산을 PL/pgSQL 로 한 번 더 쓴다. 둘이 어긋나면 그것을 알려 주는 것은 아무것도 없다 |
| **CLAUDE.md 가 요구한 것은 "대사가 가능해야 한다"** | 깨질 수 없는 것은 대사할 필요가 없다. 대사를 무의미하게 만드는 방향은 그 문장이 말하는 바가 아니다 |
| **가장 뜨거운 쓰기 경로다** | 판매 한 건마다 도는 트리거를 하나 늘리는 것은, 그것이 O(1) 이더라도 잠금 구간 안의 왕복을 늘린다 |

대신 **기본키가 그 일의 상당 부분을 한다.** `(variantId, seq)` 는 잠금을 지나지
않은 두 번째 기록을 거부하므로, 고전적인 lost update 는 조용한 손상이 아니라
충돌이 된다. 7.3 이 그것을 실제로 측정한다.

### 7.3 A7 — 동시 요청 검증과 음성 대조군

`apps/api/test/db/stock-ledger-contention.spec.ts`. 시나리오마다 10회 반복하고
관측 **230개**를 soft 단언으로 남긴다 — 깨진 구현이 "몇 개가 무너지는가"를
보고하게 하기 위해서다.

| 시나리오 | 결과 |
| --- | --- |
| 재고 1개에 동시 판매 10건 | 1건 성공 · 9건 409. 원장 2건(개시 + 판매), L1~L4 전부 참 |
| 입고 +5 와 판매 3건 동시 | 최종 12, 원장 5건이 자리 1~5 에 **빈틈 없이**. 빈틈이 없다는 것이 곧 전부가 잠금을 지났다는 뜻이다 |
| 재고 4개에 판매 9건 동시 | 정확히 4건 성공 · 5건 409 |
| 한 Variant 를 잡아 둔 채 **다른** Variant 변경 | 기다리지 않고 끝난다 |
| 한 Variant 를 잡아 둔 채 **같은** Variant 변경 | `pg_stat_activity` 에서 실제로 잠금 대기 상태가 됐다가 COMMIT 뒤 완료 |

#### 대조군 ① — 자리 없는 원장, 잠금 없음 (픽스처 테이블)

대부분의 구현이 쓰는 모양이다: 전역 id, 덧붙이는 행, 그 옆의 `stock` 컬럼.
`TestLedgerNaive` 는 그것을 그대로 두고 **자리(`seq`)와 사슬 검사만 뺐다.**
장벽으로 "모두 읽은 뒤에 아무나 쓴다"를 고정했다.

- 잠금 없이 돌리면 **10회 전부 손상.** 재고 1개에서 2개가 팔리고 `stock` 은 0 이다.
  `stock >= 0` CHECK 은 침묵한다 — 손상은 음수가 아니라 **"재고가 왜 줄었나"에
  답이 두 개가 되는 것**이다.
- 같은 픽스처, 같은 흐름에 `FOR UPDATE` **한 줄만** 넣으면 10회 전부 사라진다.
  1건 성공, 원장 1건, `stock` = 1 + 합계.

#### 대조군 ② — 실제 테이블, 잠금만 제거

같은 흐름을 배포되는 테이블 위에서 돌렸다. **여기서는 손상이 나지 않는다.**
`(variantId, seq)` 가 기본키이고 두 요청이 같은 자리를 계산하므로, 진 쪽은
조용히 덮어쓰는 대신 키에 부딪힌다. 10회 전부 1건 기록 · 1건 충돌 · L1~L4 참.

**이것이 이 TASK 의 가장 중요한 발견이다.** 기본키가 lost update 를 **표현
불가능하게** 만들고 있었다 — 설계가 잠금 하나를 잃어도 원장이 거짓말을 하지
않는다. 그렇다고 잠금이 없어도 되는 것은 아니다. 아래가 그 이유다.

#### 서비스에서 `FOR UPDATE` 를 지우면

확인 후 원복했다. **230개 관측 중 90개가 실패한다.** 어느 90개인지가 중요하다.

| 단언 | 잠금 없이 | 왜 |
| --- | --- | --- |
| **L1~L4** (합계·사슬·끝점·자리) — 관측 80개 | **전부 통과** | 기본키가 두 번째 기록을 쳐낸다. 원장은 끝까지 재고를 설명한다 |
| 진 요청의 상태가 409 | **실패** (10개) | "재고가 부족합니다"가 아니라 **기본키 위반**이 올라온다. 호출자가 받는 것은 자기가 고칠 수 있는 답이 아니다 |
| 입고 +5 와 판매 3건이 **전부** 성공 | **실패** (40개) | 충돌한 요청이 통째로 버려진다. 최종 재고가 12 가 아니라 9 나 15 이고 원장이 5건이 아니라 2~3건이다. **일어났어야 할 변동이 사라진다** |
| 재고 4개에 판매 9건 중 4건 성공 | **실패** (40개) | 같은 이유로 2~3건만 팔린다. 팔 수 있는 재고가 팔리지 않는다 |

즉 잠금이 지키는 것은 **정합성이 아니라 판정과 처리량**이다. 기본키는 조용한
유실을 거부로 바꿔 주지만, 그 거부는 사용자가 읽을 수 있는 답이 아니고 성공했어야
할 요청까지 함께 버린다. TASK-0032 가 "우연히 늦게 잡히는 잠금은 쓰기는 지켜도
판정은 못 지킨다"로 정리한 것과 같은 결론에 반대쪽에서 도착했다.

### 7.4 S5 — DB 와 애플리케이션의 경계

| 규칙 | 어디서 | 왜 거기인가 |
| --- | --- | --- |
| 한 자리에 한 행 | 기본키 `(variantId, seq)` | 자리는 잠금 안에서만 발급된다. 밖에서 들어온 행은 충돌하거나 빈틈을 남긴다 |
| 같은 참조의 같은 변동은 한 번뿐 | 부분 유니크 인덱스 | 두 요청이 동시에 "없다"를 확인할 수 있는 검사다. 참조 없는 입고·조정은 반복이 정상이라 부분 인덱스 |
| 유형과 부호, 0 아님, 잔액·자리 하한, 참조 짝, `ADJUST` 의 사유 | CHECK | 애플리케이션 검증은 임포트 스크립트와 psql 세션이 우회한다 |
| 원장은 수정·삭제되지 않는다 | **트리거** | 금지 대상이 값이 아니라 **동작**이라 CHECK 으로 표현할 수 없다 |
| 현재 재고가 음수가 아니다 | CHECK (`ProductVariant`, TASK-0032) | 마지막 방어선. **경합은 못 잡는다** — 7.3 대조군 ① |
| **L1 합계 일치** | **애플리케이션 + Variant 행 잠금** | 다른 테이블을 집계해야 답할 수 있다. 지연 제약 트리거로 옮길 수 있었고 옮기지 않았다 (4.13) |
| **L2 사슬 · L3 끝점 · L4 자리 연속** | **애플리케이션 + 대사** | 〃 |
| **판매자 소유권** | **애플리케이션** (`assertResourceAccess`) | 행을 읽어야 알 수 있고 DB 에는 요청자가 없다 |

경계로 넘어온 규칙에 대해 **DB 가 그 INSERT·UPDATE 를 실제로 받아들이는 것**까지
테스트로 고정했다 — 합계가 어긋난 재고, 사슬이 끊긴 잔액, 건너뛴 자리 셋 다
DB 는 받아들인다. "DB 가 막아 주겠지"가 나중에 행 잠금이나 대사를 지우는 근거가
되지 않게 하기 위해서다 (TASK-0032 7.4 와 같은 이유).

### 7.5 곁에서 발견한 것 — 이 TASK 에서 고치지 않았다

`ProductService` 의 기본 SKU 접두사는 상품 id(UUIDv7)의 앞 8자리에서 나온다.
그 8자리는 밀리초 타임스탬프의 상위 32비트라 **약 65초마다 한 번 바뀐다.** 즉 한
판매자가 1분 안에 상품 두 개를 `skuPrefix` 없이 등록하면 두 번째가
`ProductVariant_seller_sku_key` 에 걸려 409 를 받는다. 이 TASK 의 스펙들이 한
판매자로 상품을 반복 생성하다가 밟았고, 스펙 쪽에서 접두사를 명시하는 것으로
피했다.

고치지 않은 이유는 쓰기 계약의 주인이 **TASK-0113** 이고, 접두사에 엔트로피를
더하면 TASK-0032 F1 이 고정한 "생성 SKU 번호가 판매자가 표에서 읽는 순서와 같다"가
함께 바뀌기 때문이다. 재고 원장과 무관한 변경이라 여기서 섞지 않는다.
