# TASK-0033: 이미지 업로드 위젯

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M05 카탈로그 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/image-upload` |
| 선행 작업 | TASK-0032 |

## 1. 목적

TASK-0011 의 presigned URL 경로를 실제 UI 로 감싼다. 판매자가 여러 이미지를 올리고 순서를 정할 수 있게 한다.

## 2. 범위

### 포함
- 업로드 위젯 (드래그&드롭 + 파일 선택)
- 다중 업로드, 진행률 표시
- 클라이언트 리사이즈 (업로드 전 축소로 용량·시간 절감)
- 순서 변경, 대표 이미지 지정
- 갤러리에서 빼기 · 업로드 실패 재시도 · 진행 중 취소
- 위젯을 실제로 조작해 보는 **개발 전용 확인 화면**

### 제외 (이번에 하지 않는 것)
- **presign 엔드포인트와 그 인증·역할 가드** → TASK-0011 이 끝냈다. 계획 1번이 사라진 이유는 4.1
- **상품 저장 API** → TASK-0113. 위젯이 만드는 것은 `images: [{ url, alt }]` 배열까지다
- **상품 편집기 화면** → TASK-0114. 위젯을 폼 필드로 붙이는 것은 그쪽이다
- **R2 객체 삭제와 고아 정리** → 엔드포인트가 없다. 4.8
- 서버 사이드 이미지 변환·썸네일 생성
- 이미지 CDN 최적화

## 3. 요구사항

- [ ] 이미지 5장을 한 번에 올릴 수 있다
- [ ] 업로드 중 진행률이 보인다
- [ ] 순서를 바꾸면 상품 상세의 표시 순서가 바뀐다
- [ ] 로그인하지 않으면 presign 이 거부된다
- [ ] 업로드 실패 시 재시도할 수 있다

## 4. 설계

```
파일 선택 → 클라이언트 리사이즈(최대 2000px) → presign 요청 → R2 직접 PUT → 상품 저장 시 URL 기록
```

**클라이언트 리사이즈를 넣는 이유**: 원본 사진은 5~10MB 가 흔하다. 서버 변환 없이 용량 문제를 해결하는
가장 싼 방법이다.

아래 11개 절은 **구현 전에** 쓴 판단이다. 계획서(5장)와 달라진 곳은 그 사실을 함께 적는다.

### 4.1 계획 1번은 이미 끝나 있었다

5장 구현 계획의 1번은 "presign 엔드포인트에 인증·역할 가드 추가 (TASK-0011 보완)" 였다. **그 보완은
TASK-0011 이 그 안에서 해 버렸다** — `UploadsController.presign` 에 `@RequirePermission('media.upload')`
가 붙어 있고, 퍼미션은 `SELLER_OWNER:own` · `ADMIN_OPERATOR:any` · `DEMO_ADMIN:demo` 로 배분되어 있으며,
스토어 소유권은 `assertResourceAccess` 가 판정한다. TASK-0011 6.2 가 A3(권한 403 3종)·A4(인증 401)를
실 DB 통합 스펙으로 측정해 두었다.

그래서 이 TASK 는 **`apps/api` 를 한 줄도 고치지 않는다.** 같은 시점에 TASK-0036(재고 원장)이 그 트리를
쓰고 있기도 하다. 계약이 부족하면 고치지 않고 보고한다.

### 4.2 위젯의 자리 — `packages/ui` 와 `apps/seller` 로 나눈다

한 덩어리로 두면 둘 중 하나를 포기하게 된다. `packages/ui` 에 다 넣으면 API 클라이언트와 한국어 문구가
컴포넌트 패키지로 들어오고, `apps/seller` 에 다 넣으면 드롭존과 갤러리가 **axe 게이트 밖**에 남는다
(`test/story-a11y.spec.tsx` 는 스토리만 훑는다). 그래서 경계를 **"브라우저 API 와 문구를 아는가"** 로 긋는다.

| 자리 | 무엇이 | 이유 |
| --- | --- | --- |
| `packages/ui/src/media/` | `ImageDropZone` · `ImageUploadList` — 보이는 것 전부 | 스토리가 붙고 axe 가 돈다. 문구는 전부 prop |
| `apps/seller/src/lib/uploads/` | 리사이즈 계산 · 전송 · 큐 · 실패 해석 | 순수 로직 + 주입되는 포트. Q5 분기 100% 대상 |
| `apps/seller/src/components/product-images/` | 위 둘을 잇는 위젯 | 카탈로그에서 문구를 받아 컴포넌트에 넘긴다 |

`media/` 는 새 엔트리포인트를 만들지 않고 `src/components/index.ts` 로 재수출한다 — `feedback/` 이 같은
선택을 한 이유 그대로다. `test/story-coverage.spec.ts` 는 배럴을 읽으므로, 손으로 등록해야 하는 네 번째
엔트리포인트는 **한 줄 잊는 것만으로 컴포넌트가 접근성 검사 밖으로 나가는** 길이 된다.

### 4.3 항목 하나의 상태 머신

위젯의 단위는 "파일"이 아니라 **갤러리 항목**이다. 올라가는 중인 것과 이미 올라간 것이 한 목록에 섞여
있고, 순서 조작은 둘 다에 걸린다.

```
queued ─→ preparing ─→ requesting ─→ uploading ─→ uploaded
   │          │             │            │
   └──────────┴─────────────┴────────────┴──→ failed ──(재시도)──→ queued
                                         └──→ canceled
```

| 상태 | 무엇을 하는 중 |
| --- | --- |
| `queued` | 차례를 기다린다. 동시 3개까지만 올린다 |
| `preparing` | 클라이언트 리사이즈. 여기서 크기·형식이 확정된다 |
| `requesting` | `POST /uploads/presign` |
| `uploading` | R2 로 PUT. 진행률이 여기서만 움직인다 |
| `uploaded` | `publicUrl` 확보. 저장 요청에 실릴 수 있다 |
| `failed` | 실패 이유를 가진다. 재시도 가능 |
| `canceled` | 사용자가 멈췄다. 목록에서 사라진다 |

**동시 3개**로 잡은 이유: 브라우저의 오리진당 커넥션 한도(6)를 다 쓰면 presign 요청이 업로드 뒤에 줄을
서고, 진행률 막대 5개가 동시에 기어가는 화면은 5개 중 무엇이 끝나가는지 말해 주지 않는다. 큐 선택은
부수효과 없는 함수다.

### 4.4 클라이언트 리사이즈 — 순수 계산과 브라우저 어댑터를 나눈다

축소 자체는 `createImageBitmap` + 캔버스이고 jsdom 에 없다. 그래서 두 조각으로 자른다.

| 조각 | 무엇 | 검증 |
| --- | --- | --- |
| `fitWithin({ width, height }, max)` | 목표 치수 계산 | 순수. **분기 100%** |
| `plannedUpload(file, bitmapSize, encoded)` | 원본과 축소본 중 무엇을 보낼지 | 순수. **분기 100%** |
| `ImageEncoder` 포트 | 실제 디코드·리샘플·인코드 | 브라우저에서만. 스펙은 가짜를 주입 |

규칙 세 가지를 못 박는다.

1. **긴 변이 2000px 이하면 손대지 않는다.** 재인코딩은 손실이고, 이미 작은 사진을 다시 굽는 것은 얻는
   것 없이 잃기만 한다.
2. **출력 형식은 원본 형식을 유지한다.** presign 계약은 확장자와 MIME 이 일치할 것을 요구한다
   (`uploadImageFormats`). 형식을 바꾸면 파일 이름도 바꿔 보내야 하고, 실패했을 때 "내가 고른 파일"과
   "올라간 파일"이 달라 설명이 어려워진다.
3. **축소본이 원본보다 크면 원본을 보낸다.** PNG 스크린샷을 축소해 다시 PNG 로 구우면 커지는 일이 있다.
   판단은 바이트 수 비교 한 줄이고, 그것이 정직하다.

축소 후에도 5MB(`UPLOAD_MAX_BYTES`)를 넘으면 **발급을 요청하지 않고** 그 항목만 실패시킨다. 품질을
낮춰 가며 다시 굽는 루프는 넣지 않는다 — 2000px JPEG 은 보통 1MB 미만이라 실제로 거의 걸리지 않는데,
루프는 항상 돌고 항상 유지 대상이 된다.

### 4.5 진행률은 `XMLHttpRequest` 로만 얻을 수 있다

`fetch` 는 **업로드** 진행률을 보고하지 않는다. 요청 본문을 스트림으로 넘기는 방법은 `duplex: 'half'` 와
HTTP/2 를 요구하고 브라우저 지원이 갈린다. `XMLHttpRequest.upload.onprogress` 가 지금 유일한 표준 경로다.

그래서 전송을 **포트**로 둔다.

```ts
interface UploadTransport {
  put(request: StoragePutRequest, hooks: { onProgress, signal }): Promise<StoragePutResult>
}
```

기본 구현이 XHR 이다. 스펙은 진행률 표시를 검증할 때 가짜 전송을 주입하고, 요청이 실제로 나가는 경로는
msw 핸들러가 받는다. **어느 쪽도 실 네트워크를 열지 않는다** — `setupTestServer` 가 소켓까지 센다.

### 4.6 순서와 대표 이미지 — 배열 순서가 곧 `sortOrder` 다

`ProductImage` 에 `isPrimary` 를 두지 않는다. 이유는 두 가지다.

- **서버가 이미 그렇게 저장한다.** `ProductService.writeImages` 가 요청 배열의 인덱스를 `sortOrder` 로
  쓰고, 읽을 때 `orderBy: [{ sortOrder }, { id }]` 로 되돌린다. 목록 썸네일이 첫 장인 것은 이 순서의 결과다.
- **컬럼을 더하는 것은 `schema.prisma` 변경**이고 그 파일은 TASK-0032 가 소유하며, 지금 TASK-0036 이
  같은 트리에서 작업 중이다 (DECISIONS 11장: 스키마를 건드리는 TASK 는 동시에 하나).

그래서 **"대표로 지정" = 그 항목을 맨 앞으로 옮기기**다. 화면에는 첫 항목에 대표 배지가 붙는다.

**순서 변경은 버튼이 1차, 드래그는 넣지 않는다.** HTML5 드래그 앤 드롭은 키보드로 조작할 수 없어 P4·U5 를
통과할 수 없고, 접근 가능한 드래그를 직접 만드는 것은 이 TASK 의 크기를 두 배로 만든다. 항목마다
`앞으로`·`뒤로`·`대표로` 버튼을 두면 포인터와 키보드가 같은 핸들러를 쓴다 — `/categories` 트리가
"행 안에 포커스 가능한 요소를 두지 않고 작업 막대가 맡는다"로 푼 것과 같은 종류의 판단이다.
드래그 앤 드롭은 **파일을 떨어뜨리는 쪽**에만 있다.

### 4.7 실패·재시도·취소

| 무엇 | 어떻게 |
| --- | --- |
| 실패 범위 | **항목 단위.** 5장 중 2장이 실패하면 3장은 `uploaded` 로 남고 저장에 실릴 수 있다 |
| 재시도 | **presign 부터 다시 한다.** URL 은 5분 만료이고 서명이 크기·형식에 묶여 있어, 옛 URL 재사용은 만료나 불일치로 다시 실패한다 |
| 재시도 단위 | 항목별 버튼 + "실패한 것만 다시 시도" 버튼 |
| 취소 | `AbortSignal` → `xhr.abort()`. PUT 은 원자적이라 부분 객체가 남지 않는다 |
| 자동 재시도 | **하지 않는다.** 실패의 절반은 5MB 초과·형식 거부처럼 다시 해도 같은 답이 오는 것들이고, 나머지 절반(네트워크)은 사람이 상황을 안다 |

### 4.8 삭제가 이 TASK 에서 끝나지 않는 이유

원래 범위는 "삭제 (R2 객체 + DB 행)" 였다. **둘 다 이 브랜치가 할 수 없다.**

| 무엇 | 왜 못 하는가 | 누가 하는가 |
| --- | --- | --- |
| DB 행 | 아직 행이 없다. `ProductImage` 는 상품을 저장할 때 생기고, 저장은 TASK-0113 이다. 갤러리에서 뺀 항목은 저장 요청에 실리지 않으므로 행이 애초에 만들어지지 않고, 수정 시에는 `images` 가 갤러리를 통째로 교체한다 | TASK-0113 |
| R2 객체 | 삭제 엔드포인트가 없다. `DELETE /uploads/:key` 는 `apps/api` 이고 이 브랜치는 그 트리를 소유하지 않는다 | 별도 TASK |

**7장 R1 의 `tmp/` 전략도 클라이언트가 실행할 수 없다.** 키는 서버가 만든다
(`products/{sellerId}/{uuid}.{ext}`, TASK-0011 4.4) — 그것이 남의 스토어 경로를 얻는 게임을 없앤 설계이고,
클라이언트가 접두사를 고르게 하면 그 게임이 돌아온다. 임시 키와 이동은 **발급 쪽에서** 풀어야 한다.

그래서 이 TASK 에서 삭제는 **갤러리에서 빼는 것까지**이고, 올라갔지만 저장되지 않은 객체는 고아로 남는다.
완료 기준 F6 은 미충족으로 남긴다. 유출 위험은 없다 — 키가 UUID 이고 공개 도메인은 운영 버킷을 본다.

### 4.9 오류를 TASK-0117 규약에 붙이는 방법

이 위젯의 실패는 **두 종류이고 출처가 다르다.**

| 출처 | 봉투 | 요청 번호 | 화면 |
| --- | --- | --- | --- |
| 우리 API (`/uploads/presign`) | `{ error: { code, message, details, requestId } }` | 있다 | 코드로 문장을 고른다. `details[].field` 를 항목 메시지로 옮긴다 |
| R2 (presigned PUT) | **없다.** 남의 XML 이고 `x-request-id` 도 없다 | 없다 | 좁힌 이유값으로 문장을 고른다. **번호를 보여 주지 않는다** |

**새 도메인 코드를 만들지 않는다.** `userFacingErrorCodes` 는 각 앱 카탈로그가 `Record` 로 전부 답해야
하는 목록이고, 코드를 하나 더하면 `apps/admin` 의 카탈로그도 고쳐야 한다 — 이 브랜치가 소유하지 않는
트리다. 실제로 필요하지도 않다. presign 이 내는 실패는 전부 전송 계층 코드로 말할 수 있다.

| 상황 | `code` | 화면 |
| --- | --- | --- |
| 로그인하지 않음 | `AUTH_REQUIRED` (401) | 로그인이 필요하다고 말한다 |
| 남의 스토어 · 권한 없음 | `FORBIDDEN` (403) | 이 스토어에 올릴 수 없다고 말한다 |
| 형식·용량 거부 | `BAD_REQUEST` (400) | `details[].field` 가 있으면 그 항목에, 없으면 위젯 상단에 |
| R2 미설정 | `SERVICE_UNAVAILABLE` (503) | 저장소가 준비되지 않았다고 말한다 |
| 그 밖의 5xx | `INTERNAL_ERROR` | 문장 + **요청 번호**(`ErrorNotice`) |
| 응답 자체가 없음 | — (`kind` 가 `network` · `timeout`) | 문장 + 다시 시도. 번호 없음 |

R2 쪽 실패는 응답을 그대로 보여 줄 수 없으므로(남의 XML) 다음 다섯 가지로 좁힌다.

| 이유 | 언제 | 어떻게 아는가 |
| --- | --- | --- |
| `blocked` | CORS 프리플라이트 거부, 오프라인 | XHR `error` 이벤트, status 0 |
| `rejected` | 서명 불일치 · 만료 (403) | status 403 |
| `aborted` | 사용자가 취소 | `abort` 이벤트 |
| `timeout` | 제한 시간 초과 | `timeout` 이벤트 |
| `http` | 그 밖의 non-2xx | status |

`blocked` 는 **코드가 아니라 버킷 설정**일 수 있는 유일한 실패다. 그래서 문구가 "네트워크 또는 저장소
설정"을 함께 말한다 — 판매자에게는 "잠시 후 다시" 이지만, 개발 확인 화면에서는 status 0 이 곧
프리플라이트 실패라는 사실이 로그에 남는다.

### 4.10 인증이 없어서 지금 일어나는 일 — presign 은 **항상** 401 이다

`AnonymousPrincipalResolver` 가 아직 자리에 있다. 모든 요청이 익명이고, 퍼미션을 선언한 엔드포인트는
전부 401 이다 (TASK-0021/0022 가 이 provider 를 교체한다).

**F5(비로그인 presign 거부)는 그래서 실 서버로 그냥 확인된다.** 동시에, 브라우저에서
`presign → PUT` 을 한 세션으로 이어 볼 수는 없다. 그래서 실측을 둘로 나눈다.

| 무엇 | 어떻게 | 무엇을 증명하는가 |
| --- | --- | --- |
| 브라우저 → 우리 API | 확인 화면에서 업로드 시도 | presign 이 401 `AUTH_REQUIRED` 이고 화면이 그것을 말한다 |
| 브라우저 → R2 | `apps/api/src/storage` 의 **서명 코드를 그대로 호출**해 URL 을 만들고, 오리진 `http://localhost:3031` 에서 실제 전송 모듈로 PUT | CORS 프리플라이트 · 서명 헤더 · 만료가 **브라우저 경로에서도** 그대로 동작한다 |

두 번째가 이 TASK 에서 아무도 본 적 없는 구간이다. TASK-0011 은 서명·용량·형식·만료·변조를 6/6 으로
검증했지만 전부 **서버에서** 했다 — 프리플라이트는 브라우저만 보낸다.

### 4.11 확인 화면은 개발 전용이다

`/products/new` 는 TASK-0114 가 소유하고, 그 화면이 오기 전에는 위젯을 놓을 곳이 없다. 그래서
**`/components/image-upload`** 를 만든다 — 이미 개발 전용인 컴포넌트 갤러리(`/components`) 아래다.
`NODE_ENV !== 'production'` 이면 렌더하고 아니면 `notFound()`, `/components` 와 `/tokens` 가 쓰는 선례
그대로다. 라우트는 프로덕션에서도 **컴파일·타입체크·빌드된다** — 빌드에서 제외된 화면은 아무도 모르게 썩는다.

TASK-0114 가 위젯을 폼에 붙이면 이 라우트는 지운다. 2장의 "개발 전용 확인 화면"이 그것이다.

## 5. 구현 계획

1. 이 문서 4장 — 계획 대비 달라진 것을 **구현 전에** 적는다
2. `packages/ui` 표시 컴포넌트 2개 + 스토리 + `components` 배럴 재수출
3. 순수 로직 — 리사이즈 계산 · 큐 · 실패 해석 (분기 100%)
4. 전송 포트와 XHR 구현
5. `packages/api-mocks` — presign 핸들러와 **저장소 PUT 대역**(서명 헤더 불일치를 R2 처럼 403 으로 거부)
6. 위젯 조립 + 판매자 문구 카탈로그
7. 개발 전용 확인 화면
8. 프론트 스펙 — U1·U2·U3·U5·U6 · C2
9. **실 R2 브라우저 왕복** (4.10)
10. 6장 완료표를 실측값으로 채우고 `docs/design/pages.md` 갱신
