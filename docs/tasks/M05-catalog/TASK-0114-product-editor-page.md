# TASK-0114: 판매자 상품 편집기 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M05 카탈로그 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-03 |
| 브랜치 | `feature/product-editor-page` |
| 선행 작업 | TASK-0113, TASK-0033, TASK-0017, TASK-0019, TASK-0023, TASK-0107 |

> **분할 유래** — TASK-0034(판매자 상품 등록 · 수정)의 화면 절반이다. D-208 에 따라 화면과 API 를 나눴고,
> API 는 TASK-0113 이 맡는다. 원본은 범위가 전부 UI 였는데 그 UI 가 부를 API 가 어디에도 없었다.

## 1. 목적

`apps/seller` 의 상품 등록 · 수정 화면을 만든다. **카테고리를 고르면 속성 입력 폼이 자동 생성**되고,
**옵션 조합에서 Variant 표가 자동 생성**되는 것이 이 화면의 핵심이다.

## 2. 범위

### 포함
- `/products/new` · `/products/[id]/edit` — 등록 · 수정
- 기본 정보 (이름 · 설명 · 카테고리)
- **카테고리 선택 시 속성 폼 자동 생성** — TASK-0030 의 정의 조회 + TASK-0017 의 동적 폼 생성기
- **카테고리 변경 시 같은 key 의 입력값 유지**, 나머지는 버림
- 이미지 업로드 위젯 연결 (TASK-0033) — 순서 변경 · 대표 지정
- **옵션 정의 UI** — 옵션명 추가, 값 추가·삭제·정렬
- **옵션 조합 → Variant 표 자동 생성** — 가격 · 재고 · SKU · **1회 최대 구매 수량**의 일괄 입력과 개별 입력
- 조합 수 상한(`PRODUCT_MAX_VARIANTS`) 초과 시 안내
- 임시저장(`DRAFT`) / 발행(`ACTIVE`) 전환. **발행은 별도 엔드포인트**(`POST /products/:id/publish`)다
- 수정 모드 — 기존 값 로드, 옵션 변경 시 어떤 조합이 추가·비활성화되는지 **저장 전 미리 표시**
- **초안이 미완성일 수 있다는 안내** ([TASK-0113](./TASK-0113-product-write-api.md) 7.3 이 넘긴 것) —
  임시저장은 필수 속성이 비어도 성공하고 발행만 전량을 요구하므로, 「판매 시작」이 왜 막혔는지를
  화면이 말해야 한다
- **옵션 축 자체는 수정에서 바꿀 수 없다는 안내** (TASK-0113 7.3 · 그 문서 R8) — 축을 더하거나 빼면
  API 가 400 이다. 값만 추가·삭제할 수 있다는 것을 수정 모드에서 미리 말한다
- **미리보기** — 구매자 상세 화면 레이아웃으로 렌더
- `productWriteRequestSchema` · `productDetailResponseSchema` 로 **모킹 데이터를 만들고 `parse` 로 검증**
- **카탈로그 도메인 오류 코드를 화면에 그린다** ([TASK-0032](./TASK-0032-product-schema.md) 4.10 ·
  [TASK-0036](./TASK-0036-stock-ledger.md) 4.10 이 TASK-0113 과 함께 넘긴 것) — 코드 정의와
  `apps/seller` 카탈로그 문장은 [TASK-0113](./TASK-0113-product-write-api.md) 이 만든다. 이 TASK 는
  그 코드별로 **어디에 무엇을 띄울지**를 정한다(필드 옆 · 표 위 · 토스트)

### 제외 (이번에 하지 않는 것)
- **상품 저장 · 조회 API** → TASK-0113
- **속성 정의 관리 화면** → TASK-0031
- **이미지 업로드 위젯 자체** → TASK-0033. 여기서는 배치하고 결과 URL 을 폼에 연결한다
- **상품 목록 · 재고 조정 화면** → TASK-0116
- 검색 노출 → M06
- 실제 API 호출 테스트 — 백엔드는 모킹한다

## 3. 요구사항

### 기능 요구사항
- [ ] 카테고리를 바꾸면 속성 폼이 즉시 바뀐다
- [ ] 카테고리를 되돌리면 같은 key 의 입력값이 남아 있다
- [ ] 옵션 3 × 4 를 넣으면 Variant 12행 표가 생성된다
- [ ] Variant 가격 · 재고 · 최대 구매 수량을 일괄 입력할 수 있다
- [ ] 임시저장 후 다시 들어오면 입력값이 복원된다
- [ ] 필수 속성이 비면 발행이 막히고 **해당 필드에** 오류가 표시된다
- [ ] 수정 시 옵션을 늘리면 어떤 조합이 추가되는지 저장 전에 보인다
- [ ] 미리보기가 구매자 상세와 같은 레이아웃으로 보인다

### 비기능 요구사항
- Variant 표가 100행일 때도 입력이 버벅이지 않는다 (행 단위 렌더 분리)
- 콘솔 화면 — 밀도 토글 없음(2단계 고정), 데스크톱 우선

## 4. 설계

### 흐름

```
① 기본 정보 → ② 카테고리 선택 → ③ 속성 폼 (자동 생성) → ④ 이미지
                                   ↓
④ 옵션 정의 → ⑤ Variant 표 (조합 자동 생성) → ⑥ 가격·재고 입력 → 저장
```

카테고리 변경 시 이미 입력한 속성값은 **키가 같으면 유지**하고 나머지는 버린다. 전부 날리면 카테고리를
잘못 골랐다가 되돌릴 때 다시 입력해야 한다.

Variant 표는 행이 많아질 수 있으므로 **일괄 입력(전체 가격 동일 적용)을 먼저** 제공한다.

### 화면 / 컴포넌트

```
apps/seller/src/app/products/new/page.tsx
apps/seller/src/app/products/[id]/edit/page.tsx
        └ ProductEditor           네 상태(로딩 · 없음 · 에러 · 정상)와 저장 결과를 소유
            ├ ProductBasicFields      이름 · 설명 · 카테고리
            ├ ProductAttributeFields   카테고리 정의로부터 생성 (TASK-0017 `DynamicForm`)
            ├ ProductImageField        TASK-0033 위젯 래핑
            ├ ProductOptionEditor      옵션명 · 값
            ├ VariantTable             조합 표 + 일괄 입력 (행은 `memo`)
            └ ProductPreview           구매자 상세 레이아웃
```

`src/` 가 계획에는 없었다. 세 앱 전부 `src/app/` 이므로 경로 쪽을 고친다.

**판정은 순수 함수로 뗀다**(R2, Q5 강화 대상). `apps/seller/src/lib/products/` 에 조합 전개 ·
차분 · 카테고리 변경 시 값 유지 · 저장 본문 만들기 · 실패의 배치가 들어가고, 컴포넌트는 그것을
그리기만 한다. `apps/api` 의 `variant-rules.ts` 를 **가져다 쓸 수 없다** — 앱을 가로질러 import
할 수 없으므로 조합 전개는 화면 쪽에 한 벌이 더 있고, 그래서 그쪽이 분기 100% 대상이다.

### 미리보기의 밀도

미리보기는 구매자 화면을 흉내내지만 **밀도 `STANDARD` 고정**으로 렌더한다. 콘솔에는 밀도 토글이 없고
(TASK-0019), 판매자가 미리보기 안에서 밀도를 바꾸는 것은 이 화면의 목적이 아니다. 밀도 3단계 검증은
구매자 상품 상세(TASK-0043)가 받는다. 그래서 **P6 · U4 는 해당 없음**이다.

### 절단면 — `packages/shared` 의 zod 스키마

TASK-0113 이 정의한 스키마를 그대로 쓰고, **모킹 응답도 같은 스키마로 만든다.**

**계획이 적은 이름 셋은 존재하지 않는다.** TASK-0113 이 착수 시 같은 것을 발견하고 그 문서 4장에
대조표를 남겼다 — 새 이름을 만들면 C1(단일 출처)이 그 자리에서 거짓이 되므로 기존 이름에 맞춘다.
아래가 실제 이름이고, 계획했던 이름은 오른쪽에 남겨 둔다.

| 실제 스키마 | 계획 시 이름 | 이 화면에서의 용도 |
| --- | --- | --- |
| `createProductRequestSchema` · `updateProductRequestSchema` | `productWriteRequestSchema` | 저장 본문의 클라이언트 검증 |
| `productPublishRequestSchema` | (없었음) | 발행 · 발행 취소 본문 (`version` 하나) |
| `productOptionInputSchema` · `productVariantInputSchema` | 〃 | 옵션 에디터 · Variant 표의 행 타입 |
| `variantDefaultsSchema` | (없었음) | 일괄 입력의 값. 새로 생기는 조합이 여기서 출발한다 |
| `productImageInputSchema` | (없었음) | 이미지 위젯이 돌려준 URL 을 저장 본문에 싣는 형태 |
| `productSchema` · `productResponseSchema` | `productDetailResponseSchema` | 수정 모드 로드 · 미리보기. **모킹 응답 `parse`** |
| `productStatusSchema` · `sellerSettableStatuses` | `productStatusSchema` | `DRAFT` / `ACTIVE` 배지와 버튼 문구의 값 출처 |
| `attributeValuesSchema` | `productAttributeValuesSchema` | 속성값 컨테이너. 키별 타입은 TASK-0030 의 **동적 zod 스키마**가 판정 |

**조합 수 상한은 `PRODUCT_MAX_VARIANTS` = 200 이다.** 계획이 적은 100 은 TASK-0032 가 그 상수를
세우기 전의 숫자이고, TASK-0113 이 착수 시 같은 자리를 고쳤다(그 문서 4장 「조합 수 상한」).
화면은 숫자를 다시 적지 않고 상수를 import 한다 — 두 곳에 적힌 순간 화면과 서버가 다른 값을 막는다.

속성 폼은 정의(`AttributeDefinition`)에서 zod 스키마를 만들어 검증한다 — 서버가 저장 직전에 쓰는 것과
**같은 생성기**(TASK-0030)를 쓴다. 검증 규칙을 화면에 따로 적으면 서버와 어긋난다.

### 도메인 오류 코드를 어디에 그리는가

**코드와 문장은 TASK-0113 이 만들었다. 이 TASK 의 몫은 배치다** — 같은 400 이라도 고칠 곳이 필드
안이냐 표냐 화면 전체냐가 다르고, 그 차이를 화면이 표현하지 않으면 코드를 나눈 값이 사라진다.

자리는 셋이다.

| 자리 | 언제 | 무엇이 붙나 |
| --- | --- | --- |
| **필드 옆** | 고칠 것이 하나의 입력 안에 있다 | `FormField` 의 `aria-describedby` 로 묶인 오류 문장. `useForm` 이 첫 무효 컨트롤로 포커스를 옮긴다 |
| **표 위** | 고칠 것이 옵션 · Variant 표 안에 흩어져 있다 | 표 바로 위의 `role="alert"` 안내. 표를 스크롤해도 문장이 따라다니지 않으므로 무엇을 고칠지 먼저 읽고 내려간다 |
| **토스트** | 결과를 알릴 뿐 고칠 것이 없다 | 저장 성공 · 발행 · 발행 취소, 그리고 응답이 아예 오지 않은 실패(`transport`) |

그 위에 하나 더 있다 — **배너**. 화면 전체가 막힌 상태(스토어 미승인, 낙관적 잠금 충돌)는 어느
입력의 문제도 아니고 토스트처럼 사라져서도 안 되므로, 폼 위에 남는다.

| `code` | 자리 | 왜 |
| --- | --- | --- |
| `PRODUCT_ATTRIBUTES_REQUIRED` | **필드 옆** | 응답이 `details[].field = attributes.<key>` 를 준다. 비어 있는 속성 **전부**를 한 번에 이름 짓는다(TASK-0113 F3) — 하나씩 고치게 하면 발행 버튼을 다섯 번 눌러야 한다 |
| `PRODUCT_TOO_MANY_VARIANTS` | **표 위** | `field = options` 다. 고칠 곳은 옵션 값 목록이고, 표에는 이미 상한을 넘긴 조합이 그려져 있다. **화면은 서버에 물어보기 전에 같은 상수로 먼저 막는다**(F9) — 이 코드는 그 예방이 새는 경우의 그물이다 |
| `PRODUCT_NOT_SELLABLE` | **표 위** | `field = status` 지만 status 는 입력이 아니다. 고칠 곳은 표의 「판매」 스위치이므로 표 위에 붙인다 |
| `PRODUCT_SELLER_INACTIVE` | **배너** | 403 이고 필드가 없다. 소유권 403(`FORBIDDEN`)과 **정반대의 다음 수**다 — 이쪽은 내 스토어가 맞고 심사가 안 끝났다. 폼을 계속 그리되 저장 버튼 위에 남긴다 |
| `PRODUCT_SKU_TAKEN` | **표 위** | 409 인데 필드가 없다(서버가 어느 행인지 모른다 — 부분 유니크 인덱스가 답한 것이다). 고칠 곳은 표의 SKU 열이므로 표 위에서 "SKU 를 바꿔 주세요"를 말한다. **다시 불러오기를 권하지 않는다** — 재조회로 풀리지 않는 409 다 |
| `PRODUCT_VERSION_CONFLICT` | **배너** | 나머지 409. 다시 불러오면 풀리므로 「최신 내용 불러오기」와 「그대로 저장」을 함께 준다 — 입점 화면의 충돌 배너(TASK-0109)와 같은 모양이고, 입력값은 하나도 덮어쓰지 않는다(DECISIONS 4) |
| `INVALID` (`images.<n>.url`) | **필드 옆** | 이미지 절 아래. 다른 스토어의 키를 가리키는 URL 은 이미지를 다시 올려야 한다(TASK-0113 F14) |
| `INVALID` (`options.…` · `variants.…`) | **표 위** | 중복 옵션명 · 중복 값 · 없는 조합. 전부 옵션·Variant 표 안의 문제다 |
| 그 밖의 코드 · `transport` | **토스트** | 이 화면이 이름을 갖지 못한 실패. 카탈로그가 답하고, 없으면 서버 문장이 그대로 나간다 |

`ATTRIBUTE_IN_USE` 는 **이 화면에서 나오지 않는다.** 속성 정의를 지우는 것은 `DELETE /attributes/:id`
이고 그 화면은 `apps/admin` 이다(HANDOFF 3.1). 판매자 카탈로그가 문장을 갖는 것은
`Record<UserFacingErrorCode, string>` 이 전수 검사라서이지 여기서 닿기 때문이 아니다.

배치는 `packages/ui` 의 `serverFieldErrors` 가 이미 가진 두 손잡이로 표현한다 — `fields` 는 폼이 아는
경로 목록이고, `codeFields` 는 필드를 말하지 않는 코드를 어디에 놓을지다. 화면에 `if (code === …)`
사슬을 쓰지 않는 이유이고, 표 위·배너·토스트의 갈림은 그 앞에서 한 번만 판정한다.

### 브라우저로 열 수 없다 — P2 를 무엇으로 재는가

**이 화면은 지금 브라우저로 열리지 않는다.** 로그인 경로가 Google OAuth 뿐이고 데모 계정은
TASK-0024 다(HANDOFF 1장). TASK-0109 · 0110 · 0112 가 전부 같은 벽에 부딪혔고, 셋 다 Lighthouse
대신 **조립된 화면에 axe 를 직접 돌렸다.** 이 TASK 도 같은 방식을 쓴다.

- **P2 는 그대로 게이트다.** `packages/ui` 가 스토리마다 axe 를 돌리지만 접근성 있는 컴포넌트의
  집합이 접근성 있는 화면은 아니다 — 필드 배선, 표의 행 헤더, 옵션 세트의 `fieldset`, 차분 안내의
  live region 은 조립된 뒤에만 존재한다. 그것이 여기서 재는 것이다.
- **P3 · P4 는 jsdom 에서 잰다.** `matchMedia` 를 세 폭으로 스텁하고(테스트 지원의 `VIEWPORTS`)
  Tab 순회를 실제로 돌린다. 픽셀 넘침은 jsdom 이 잴 수 없으므로, 넘칠 수 있는 것(Variant 표)을
  **가로 스크롤 컨테이너 안에 가두었는지**로 대신 잰다.
- **P1(LCP)은 게이트가 아니다** — D-217 이후 QUALITY-GATES 2장이 성능을 게이트에서 뺐다. 계획이
  적은 「P1 LCP 2.5s」는 그 결정 이전의 표다. 대신 무거운 것을 새로 들였는지를 **신고**한다.

### 역할별 권한

`apps/seller` 진입은 TASK-0023 의 미들웨어가 판정한다. 스토어가 `ACTIVE` 가 아니면 이 화면 대신 안내
화면이 뜬다(TASK-0109). 저장 버튼은 `can('product.write')` 로 비활성 처리하되, 실제 차단은 서버의

#### `api-failure.ts` — 합치지 않은 근거

HANDOFF 3.3 은 합치는 일을 **파일 이동이 아니라 설계 결정**으로 규정했다. 두 질문이 있었고 둘 다
이 TASK 에서 답이 나왔다.

| 질문 | 답 | 근거 |
| --- | --- | --- |
| `hasCode` 를 공통 API 로 둘 것인가 | **그렇다.** 이 화면이 필요로 한다 — 낙관적 잠금 409 는 배너, SKU 409 는 표 위, 판매자 상태 403 은 배너로 갈린다. seller 판에 admin · shop 과 **같은 시그니처**로 더했다 | 4장 오류 코드 배치표 |
| 메시지 `params` 를 보간할 것인가 | **판매자 화면은 필요 없다.** 유일하게 `params` 를 갖는 `PRODUCT_TOO_MANY_VARIANTS` 는 판매자 카탈로그가 `PRODUCT_MAX_VARIANTS` 를 import 해 문장에 넣는다(TASK-0113). 보간기는 admin 에 남고, 공통 판은 `paramsOf` 를 **넘겨주기만** 하면 된다 — 카탈로그가 템플릿을 쓸지 말지는 앱이 정한다 | `apps/seller/src/lib/errors.ts` 머리말 |

**그런데도 합치지 못한다. 갈 곳이 없다.**

| 후보 | 왜 아닌가 |
| --- | --- |
| `packages/shared/src/api/` | **옳은 자리이고, 이 TASK 의 소유 밖이다.** 계약은 TASK-0113 이 정의했고 이 TASK 의 「절대 건드리지 마라」에 그 경로가 있다 |
| `packages/ui` | 이 모듈은 `@shopping/shared` 의 오류 봉투를 읽는다. `packages/ui/src/form/server-errors.ts` 머리말이 정확히 그것을 거부한다 — "컴포넌트 라이브러리에 REST 클라이언트를 끌고 들어오는 것" |
| 새 패키지 | 세 앱의 `package.json` 을 함께 고쳐야 하고 `apps/shop` 은 TASK-0024 가 열려 있다 |

그리고 **셋 중 둘만 합치면 세 번째가 갈라진다.** `apps/shop` 판은 전수 카탈로그가 없는 것이
의도이고(그 파일의 표), seller 파일 머리말이 이미 "반쪽 이동은 공통 판과 남은 판이 어긋날 자유를
준다"고 경고한다. 같은 함정을 다른 조합으로 밟는 것이다.

**남긴 것**: 세 판의 함수 집합이 이제 같다(`apiFailure` · `hasCode` · `failureMessage` ·
`quotableRequestId`). 남은 차이는 각 앱의 `ApiConfigurationError` 임포트와 `failureMessage` 의
카탈로그 타입뿐이고, 둘 다 **인자로 바꿀 수 있는 것**이다 — 즉 자리만 생기면 이동은 기계적이다.
