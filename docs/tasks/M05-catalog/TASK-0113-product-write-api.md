# TASK-0113: 상품 등록 · 수정 API

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M05 카탈로그 |
| 상태 | 승인 대기 |
| 작성일 | 2026-09-03 |
| 브랜치 | `feature/product-write-api` |
| 선행 작업 | TASK-0032, TASK-0030, TASK-0108, TASK-0106 |

> **분할 유래** — TASK-0034(판매자 상품 등록 · 수정)를 D-208 에 따라 나누면서 **원래 없던 백엔드 절반을
> 채운다.** 원본 TASK-0034 의 범위는 전부 UI 였고, 편집기가 부를 상품 저장 API 가 어느 TASK 에도 없었다.
> TASK-0032 는 스키마와 엔티티 CRUD 골격까지이며, **편집기가 한 번에 저장하는 계약**은 비어 있었다.
> 화면은 TASK-0114 가 맡는다.

## 1. 목적

판매자 상품 편집기가 부를 **쓰기 API** 를 만든다. 상품 하나를 저장하는 요청이 기본 정보 · 속성값 ·
이미지 · 옵션 · Variant 를 **한 트랜잭션으로** 처리하게 하는 것이 핵심이다.

**왜 이 TASK 가 필요한가.** 편집기 화면은 "저장" 한 번에 다섯 종류의 데이터를 함께 보낸다. 엔티티마다
따로 호출하면 중간에 실패했을 때 옵션만 있고 Variant 는 없는 상품이 남는다. TASK-0032 가 만든 것은
테이블과 엔티티 단위 CRUD 이고, **그것을 편집기의 단위로 묶는 계약이 이 TASK** 다.

## 2. 범위

### 포함
- **상품 생성 API** — 기본 정보(이름 · 설명 · 카테고리) + `attributes` + 이미지 + 옵션 + Variant 를 한 요청·한 트랜잭션으로
- **상품 수정 API** — 기존 값 로드용 상세 조회 + 부분 갱신. **옵션 변경 차분 처리**(추가된 조합은 생성,
  사라진 조합은 비활성화)
- **속성값 동적 검증 연동** — 저장 전 `validateAttributes(categoryId, values)`(TASK-0030) 필수 통과
- **상태 전환** — `DRAFT` ↔ `ACTIVE`. 임시저장은 필수 속성 미충족을 허용하고, `ACTIVE` 전환은 전부 요구
- **Variant 일괄 생성 지원** — 옵션 조합 → Variant 생성은 TASK-0032 의 로직을 호출한다. 이 TASK 는
  **조합 수 상한(100) 검증**과 가격 · 재고 · SKU · `maxPurchaseQuantity` 일괄 값 반영을 담당
- **주문에 사용된 Variant 보호** — 삭제 대신 비활성화만 허용
- **소유권 · 판매자 상태 검사** — `product.write:own` + `assertSellerActive`(TASK-0108)
- **미리보기용 상세 조회** — 편집기가 구매자 화면 레이아웃으로 그릴 수 있는 응답
- 절단면이 되는 zod 스키마를 `packages/shared` 에 정의

### 제외 (이번에 하지 않는 것)
- **상품 편집기 화면** → TASK-0114
- **스키마 · 테이블 · 옵션 조합 생성 로직 자체** → TASK-0032. 이 TASK 는 그것을 호출한다
- **속성 정의 · 동적 zod 생성기** → TASK-0030
- **이미지 업로드(presign · R2 전송)** → TASK-0011 · TASK-0033. 이 API 는 업로드가 끝난 **URL 과 순서**만 받는다
- **상품 목록 조회 · 재고 조정** → TASK-0115
- 검색 인덱싱 → M06(TASK-0038)
- `schema.prisma` 변경 → TASK-0032 가 소유한다

## 3. 요구사항

### 기능 요구사항
- [ ] 편집기의 저장 한 번이 상품 · 속성값 · 이미지 · 옵션 · Variant 를 모두 반영한다
- [ ] 저장 중 하나라도 실패하면 아무것도 남지 않는다 (트랜잭션)
- [ ] 필수 속성이 비면 `ACTIVE` 저장이 거부되고 **어느 필드인지** 응답에 담긴다
- [ ] 임시저장(`DRAFT`)은 필수 속성이 비어도 성공한다
- [ ] 옵션에 값을 추가하면 새 조합만 생기고 기존 Variant 의 재고가 유지된다
- [ ] 옵션 조합이 100개를 넘으면 400 이다
- [ ] 판매자는 자기 상품만 수정할 수 있다 (403)
- [ ] `ACTIVE` 가 아닌 판매자는 상품을 등록할 수 없다 (403)
- [ ] `maxPurchaseQuantity` 를 저장하고 상세 응답에 그대로 실어 준다

### 비기능 요구사항
- 옵션 조합 생성 · 차분 계산은 **부수효과 없는 순수 함수**로 분리한다 (Q5 강화 대상)
- 상세 조회는 Variant · 이미지 · 옵션을 함께 반환하되 N+1 이 없어야 한다

## 4. 설계

### API / 라우트

| 메서드 · 경로 | 용도 | 퍼미션 |
| --- | --- | --- |
| `POST /api/v1/seller/products` | 상품 생성 (DRAFT 또는 ACTIVE) | `product.write:own` |
| `GET /api/v1/seller/products/:id` | 편집기 로드 · 미리보기용 상세 | `product.read:own` |
| `PATCH /api/v1/seller/products/:id` | 상품 수정 (옵션 차분 포함) | `product.write:own` |
| `POST /api/v1/seller/products/:id/publish` | `DRAFT → ACTIVE` | `product.write:own` |
| `POST /api/v1/seller/products/:id/unpublish` | `ACTIVE → DRAFT` | `product.write:own` |

**새 퍼미션은 없다.** `product.write` · `product.read` 는 TASK-0105 가 이미 `SELLER_OWNER:own` 으로
부여했다. 이 TASK 가 확인할 것은 그 스코프가 실제로 남의 상품을 막는가다(F7).

### 판매자 상태 검사

```
@RequirePermission('product.write')      ← 무엇을 할 수 있나  (TASK-0105)
assertSellerActive(seller, 'product.write')  ← 지금 할 수 있나 (TASK-0108)
```

두 검사는 다른 질문에 답한다. 퍼미션은 역할의 능력이고, 상태 검사는 스토어의 현재 상태다. `PENDING` ·
`REJECTED` · `SUSPENDED` 판매자는 퍼미션이 있어도 403 이다 — 원본 TASK-0026 의 F3 가 여기서 지켜진다.

### 저장 단위 — 한 요청, 한 트랜잭션

```
POST /seller/products
  ① 판매자 상태 검사
  ② attributes 를 validateAttributes(categoryId, values) 로 검증   ← TASK-0030
  ③ 옵션 조합 전개 → 조합 수 ≤ 100 확인
  ④ 트랜잭션:
       Product → ProductImage → ProductOption/Value → ProductVariant → VariantOptionValue
  ⑤ minPrice 등 캐시 컬럼 갱신 (TASK-0032 의 로직)
```

### 수정 시 옵션 차분

| 상황 | 처리 |
| --- | --- |
| 옵션 값 추가 | 새로 생기는 조합만 Variant 생성. **기존 Variant 는 손대지 않는다**(재고 유지) |
| 옵션 값 삭제 | 해당 조합 Variant 를 **비활성화**. 주문 이력이 참조하므로 삭제하지 않는다 |
| 옵션 자체 삭제 | 남은 조합으로 재전개. 사라지는 조합은 비활성화 |
| 가격 · 재고 일괄 | 요청에 실린 Variant 행 값을 그대로 반영 |

**재고를 이 API 로 바꾸지 않는다.** 편집기에서 신규 Variant 의 초기 재고를 넣는 것까지가 이 TASK 이고,
이후의 재고 증감은 전부 원장을 통한다(TASK-0036 · TASK-0115). 두 경로를 열어 두면 원장 합계와 현재
재고가 어긋난다.

### 절단면 — `packages/shared` 의 zod 스키마

이 TASK 가 **정의**하고 그대로 응답한다. TASK-0114 가 **같은 스키마로 모킹 데이터를 만든다.**

| 스키마 | 내용 | 쓰는 곳 |
| --- | --- | --- |
| `productStatusSchema` | `DRAFT` / `ACTIVE` / `INACTIVE` | 0113 · 0114 · 0115 · 0116 |
| `productWriteRequestSchema` | 저장 본문 전체 (기본 정보 + attributes + images + options + variants) | 0113 · 0114 |
| `productOptionInputSchema` | 옵션명 + 값 목록 + 순서 | 0113 · 0114 |
| `productVariantInputSchema` | SKU · 가격 · 재고 · `maxPurchaseQuantity` · 조합 매핑 | 0113 · 0114 |
| `productDetailResponseSchema` | 편집기 로드 · 미리보기 응답 (옵션 · Variant · 이미지 포함) | 0113 · 0114 |
| `productAttributeValuesSchema` | `attributes` JSONB 값의 공통 형태 (키별 타입 검증은 TASK-0030 의 동적 스키마) | 0113 · 0114 |

**조합 수 상한 100 은 `productWriteRequestSchema` 에 담는다.** 화면이 먼저 막고 서버가 다시 막되, 숫자는
한 곳에만 있어야 한다.

### 역할별 권한

| 역할 | 할 수 있는 것 |
| --- | --- |
| 판매자(SELLER_OWNER, `ACTIVE`) | 자기 상품 생성 · 수정 · 발행 · 발행 취소 |
| 판매자(그 외 상태) | 없음 — 403 |
| 관리자(ADMIN_OPERATOR) | `product.write:any` 를 가지지만 이 엔드포인트는 `/seller/` 경로다. 관리자 강제 숨김은 M14(TASK-0095) |
| 구매자(BUYER) | 없음 — `product.write` 미보유, 403 |

## 5. 구현 계획

1. `packages/shared` 에 절단면 스키마 6종 정의 + `index.ts` export
2. 옵션 조합 전개 · 차분 계산 순수 함수 (분기 100% 대상)
3. 생성 API (트랜잭션 · 속성 검증 · 조합 상한)
4. 상세 조회 API (편집기 로드 · 미리보기, N+1 제거)
5. 수정 API (옵션 차분 · 기존 재고 보존)
6. 발행 · 발행 취소 API (`ACTIVE` 전환 시 필수 속성 전량 검증)
7. 소유권 · 판매자 상태 검사 연결
8. 실제 PostgreSQL 통합 테스트 — 트랜잭션 롤백, 차분, 권한, 조합 상한
