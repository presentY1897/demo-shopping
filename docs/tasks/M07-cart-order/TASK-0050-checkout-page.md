# TASK-0050: 주문서 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M07 장바구니·주문 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/checkout-page` |
| 선행 작업 | TASK-0049 |

## 1. 목적

주문서 화면을 만든다. **진입 시 재고가 예약되고, 결제 직전까지의 흐름이 완성**된다.

## 2. 범위

### 포함
- 주문 항목 확인 (판매자별 그룹)
- 배송지 선택·신규 입력 (TASK-0111 의 배송지 API · `addressSchema` 재사용)
- 배송 요청사항
- 금액 요약 (상품금액·할인·배송비·총액)
- 쿠폰·적립금 영역 **자리** (M11 연결)
- 결제수단 선택 **자리** (M08 연결)
- **진입 시 재고 예약 + 남은 시간 표시**
- 예약 만료 시 안내·재시도
- 약관 동의
- 주문하기 → 주문 생성 → 결제 페이지 이동
- 이탈 시 예약 해제

### 제외
- 실제 결제 (M08)
- 쿠폰·적립금 적용 (M11)

## 3. 요구사항

- [ ] 주문서에 진입하면 재고가 예약된다
- [ ] 남은 시간이 표시되고 만료되면 안내가 나온다
- [ ] 페이지를 벗어나면 예약이 해제된다
- [ ] 금액이 장바구니와 일치한다
- [ ] 배송지를 선택하거나 새로 입력할 수 있다

## 4. 설계

```
장바구니 → [주문하기] → 주문서 진입
                         ├ 재고 예약 (15분)
                         ├ 타이머 표시
                         └ 이탈(beforeunload/라우트 변경) → 예약 해제 요청
```

**예약 해제를 이탈 시 시도하되 의존하지 않는다.** 브라우저를 강제 종료하면 신호가 안 온다. 만료 스케줄러(TASK-0051)가 최종 안전망이다.

타이머는 남은 시간이 3분 이하일 때 강조한다. 결제 중 만료되면 사용자가 당황하므로 미리 알린다.

### 4.1 주문서는 **표가 아니라 예약 묶음**이다 (2026-09-05)

4장의 흐름은 「주문서 진입 → 재고 예약」인데, TASK-0049 는 예약을 **주문 생성
안에서** 잡았다. 그 TASK 에 주문서가 없었기 때문이고, 승인된 4장 ③ 이 그렇게 적혀
있었다. 이제 주문서가 생기므로 예약이 제자리로 온다.

**새 표를 만들지 않는다.** 주문서 하나는 곧 **같은 `checkoutId` 를 가진 `HELD`
예약들**이다(TASK-0048 4.1 이 그 컬럼을 만들 때 이미 그 모양이었다). 그 행들이
`variantId` 와 `quantity` 를 들고 있고, 주문서가 그려야 하는 나머지 — 상품명 · 옵션 ·
사진 · 브랜드 · 가격 — 는 전부 `ProductVariant` 에서 따라간다. 표를 하나 더 만들면
같은 사실이 두 곳에 살고, 둘이 갈리는 날 어느 쪽이 맞는지 아무도 모른다.

그래서 **4장은 여전히 해당 없다** — 스키마가 바뀌지 않는다.

| 라우트 | 하는 일 |
| --- | --- |
| `POST /checkouts` | 고른 장바구니 줄로 예약을 잡고 주문서 id 를 낸다 |
| `GET /checkouts/:id` | 그 예약들로 주문서를 다시 그린다. 만료됐으면 410 |
| `DELETE /checkouts/:id` | 이탈. 그 시도의 예약 전부를 푼다 |

**주문서를 만드는 것은 장바구니의 「주문하기」다.** 화면이 `/checkout` 으로 먼저
가서 그 자리에서 예약하는 방법도 있지만, 그러면 새로고침 한 번에 예약이 한 벌 더
잡힌다. 장바구니가 만들고 `/checkout/{id}` 로 보내면, 새로고침은 **같은 주문서를
다시 읽는** 일이 된다.

### 4.2 3장이 적용된다 (2026-09-05 정정)

6.2 가 「3~4장 해당 없음」인데 4.1 이 엔드포인트 셋을 더한다. 4장은 그대로 해당
없고(스키마 변경이 없다), **3장은 전 항목 적용된다** — 남의 주문서를 읽거나 푸는
것이 표현 가능해졌으므로 A3·A4 가 특히 그렇다.

### 4.3 주문 생성은 이미 잡힌 예약을 **쓴다**

`POST /orders` 가 `checkoutId` 를 받는다. 오면 그 예약을 그대로 쓰고 새로 잡지
않는다 — 두 번 잡으면 한 사람이 같은 물건을 두 몫 잠근다.

`itemIds` 로 부르는 길도 남는다. 주문서를 거치지 않는 주문(API 직접 호출)이 여전히
성립해야 하고, 그 길에서 예약을 안 잡으면 오버셀이 뚫린다. **지켜야 하는 성질은
「주문에는 그것을 덮는 `HELD` 예약이 있다」이지 「예약이 어디서 잡혔나」가 아니다.**

### 4.4 이탈 해제는 **시도하되 의존하지 않는다**

4장이 이미 적어 둔 것이고, 여기서 지키는 방식은 `sendBeacon` 이다 — 페이지가 사라지는
중에 보내는 `fetch` 는 브라우저가 취소한다. 그래도 강제 종료에는 신호가 없고, 그때의
안전망은 만료 스케줄러(TASK-0051)다.

### 4.5 쿠폰·적립금·결제수단은 **자리만** 둔다

범위가 그렇게 적혀 있다. 자리를 「준비 중」으로 비워 두는 대신 **무엇이 들어올지**를
적는다 — 빈 상자는 만들다 만 화면으로 보이고, 이름이 붙은 빈 상자는 아직 안 온
기능으로 보인다.

## 5. 구현 계획

1. 주문서 데이터 로딩 + 재고 예약
2. 항목·금액 요약 표시
3. 배송지 선택·입력
4. 타이머 + 만료 처리
5. 쿠폰·결제수단 자리 배치
6. 약관 동의 + 주문 생성 연결
7. 이탈 시 해제
