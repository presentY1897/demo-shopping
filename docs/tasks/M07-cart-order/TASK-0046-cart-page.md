# TASK-0046: 장바구니 화면 (판매자별 그룹)

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M07 장바구니·주문 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/cart-page` |
| 선행 작업 | TASK-0045 |

## 1. 목적

장바구니 화면을 만든다. **판매자별 묶음과 그룹별 배송비**가 눈에 보이게 한다 — 마켓플레이스 구조를 사용자가 이해하는 첫 지점이다.

## 2. 범위

### 포함
- 판매자별 그룹 표시, 그룹 헤더에 브랜드명·배송비
- 수량 변경·삭제·선택 삭제
- 전체·그룹·개별 선택 체크박스
- 선택 항목 기준 합계 (상품금액·배송비·총액)
- 품절·가격변동 항목 표시와 처리
- 무료배송 조건까지 남은 금액 안내
- 빈 장바구니 상태
- 헤더 장바구니 개수 배지 연결
- 주문하기 → 주문서 이동

### 제외
- 주문서 (TASK-0050)
- 쿠폰·적립금 (M11)

## 3. 요구사항

- [ ] 판매자별로 묶여 보이고 그룹마다 배송비가 표시된다
- [ ] 선택한 항목만 합계에 반영된다
- [ ] 품절 항목은 선택할 수 없고 이유가 표시된다
- [ ] 수량 변경이 합계에 즉시 반영된다

## 4. 설계

```
[✓] 브랜드A                      배송비 3,000원
    [✓] 울 코트 / 블랙 / M   1개   189,000원
    [✓] 니트 / 그레이 / L     2개    59,000원
    ─ 무료배송까지 11,000원 남음

[✓] 브랜드B                      무료배송
    [ ] (품절) 스니커즈 / 270      — 재고 없음
```

품절 항목은 **삭제하지 않고 남긴다.** 사용자가 뭘 담았는지 기억하고 재입고를 기다릴 수 있어야 한다.

### 4.1 배송비를 응답에 싣는다 — TASK-0045 4.1 의 회수 (2026-09-05)

TASK-0045 는 배송비를 장바구니 응답에서 **뺐다.** 「없는 규칙으로 지어낸 숫자를
실으면 화면이 그대로 그린다」가 그 이유였고, 그때는 무료 기준도 판매자별 기본
배송비도 스키마에 없었다. 지금은 둘 다 있다 — TASK-0049 4.1 이 `Seller` 에 컬럼을
만들었고 계산은 TASK-0047 의 엔진이 한다.

그래서 그룹이 **정책**을 든다.

| 필드 | 뜻 |
| --- | --- |
| `shippingFee` | 이 판매자의 기본 배송비 |
| `freeShippingThreshold` | 이 금액 이상이면 무료. `null` 이면 무료 조건이 없다 |

계산된 배송비가 아니라 정책인 이유는 **선택이 브라우저에 있기 때문**이다. 합계는
고른 항목에 대해서만 내는데(F2), 서버가 계산해 보낸 숫자는 누군가 체크 하나를 푸는
순간 틀린 값이 된다. 「그때 다시 부른다」는 방법도 있지만, 체크박스 하나에 왕복이
붙는 화면은 쓸 수 없다.

### 4.2 합계는 화면이 `calculateOrder` 로 낸다

`packages/shared` 의 계산 엔진을 화면이 직접 부른다. 곱하고 더하는 것이 전부처럼
보이지만 무료배송 판정이 **쿠폰까지 반영한 상품금액** 기준이고(`pricing.md` 1장),
적립금은 물건 값을 먼저 덮는다 — 그 규칙들이 화면에 두 번째 구현으로 생기면
「장바구니가 보여 준 금액과 결제 금액이 다르다」가 된다. 그것은 신고되지 않는
종류의 버그다: 사는 사람은 결제 금액이 맞는 줄 안다.

쿠폰도 적립금도 M11 이라 오늘 넘기는 할인 목록은 비어 있다. 그래도 엔진을 거치는
이유가 위와 같다.

### 4.3 3장은 A1 · A5 만 다시 잰다

6.2 가 「3~4장 해당 없음」인데 4.1 이 응답을 바꾼다. 다만 **새 라우트도 스키마
변경도 없다** — 두 필드는 이미 조인되어 있던 `Seller` 행에서 온다. 그래서 권한·인증
(A3·A4)과 입력 검증(A2)은 TASK-0045 가 잰 그대로이고, 여기서 다시 재는 것은
응답 시간(A1)과 **질의 수가 늘지 않았다는 것**(A5)뿐이다. 4장은 여전히 해당 없다.

### 4.4 「주문하기」가 갈 곳을 먼저 만든다

주문서 화면은 TASK-0050 이다. 죽은 링크나 비활성 버튼 대신 `/cart` 가 그랬던 것처럼
**실제 라우트에 껍데기**를 두고, TASK-0050 이 그 파일을 그대로 대체한다
(`pages.md` 3장이 이미 그 방식을 적어 두었다).

### 4.5 담기를 여기서 잇는다

`purchase-controls.tsx` 가 「M07 owns the basket」이라고 적어 둔 버튼이다. 장바구니
화면만 만들고 담을 방법을 두지 않으면 그 화면에 무언가를 넣는 길이 시드밖에 없고,
F1·F2·F7 을 사람이 눌러 확인할 수 없다.

「바로 구매」는 그대로 둔다 — 주문서로 곧장 들어가는 길은 TASK-0050 의 것이다.
`aria-disabled` 라 탭 순서에 남고, 그래서 왜 안 되는지를 읽을 수 있다(TASK-0023 4장).

### 4.6 장바구니의 `stock` 은 **실물 재고**로 남는다

TASK-0048 이 「구매자 화면은 전부 가용재고를 읽는다」를 정했는데 장바구니는 예외다.
예약은 15분짜리이고 장바구니는 며칠씩 머무는 곳이라, 남이 잠깐 주문서에 들고 있다고
「품절」이라고 쓰면 **기다리면 오는 것을 안 온다고 말하는 것**이 된다.

대신 그 간극은 원래부터 `notices` 의 몫이다(TASK-0045) — 담을 때 통과한 수량이
조회할 때도 살 수 있다는 보장은 없고, 실제로 막는 것은 주문 시점의 예약이다(D-026).

## 6. 완료 기준

### 6.1 기능

| # | 기준 | 측정 방법 | 목표 | 실측 | 충족 |
| --- | --- | --- | --- | --- | --- |
| F1 | 그룹 표시 | 판매자 2곳 담기 | 그룹마다 배송비 표시 | 판매자마다 `region` 하나, 머리에 브랜드명과 배송비. 배송 정책이 **그룹마다 다르다** — 한쪽은 무료 기준 5만원, 한쪽은 조건 없음 | [x] |
| F2 | 선택 합계 | 일부만 선택 | 선택분만 합계 반영 | 코트 하나만 고르면 189,000원. 합계는 `calculateOrder` 가 낸다(4.2) | [x] |
| F3 | 선택 연동 | 그룹 체크 해제 | 하위 전부 해제, 전체 상태 갱신 | 그룹을 끄면 그 그룹만 꺼지고 맨 위는 `indeterminate` 가 된다. **일부만 골라 둔 그룹을 누르면 전부 켜진다** — 그 상태에서 사람이 원하는 것은 「나머지도」다 | [x] |
| F4 | 수량 변경 | 수량 증가 | 합계 즉시 반영 | 니트 2→3 에서 상품금액 592,000 · 결제예정 594,500. 상한(2)에 닿으면 「+」가 잠긴다 — 서버가 거절할 요청을 보내는 대신 | [x] |
| F5 | 품절 | 품절 항목 확인 | 선택 불가 + 사유, 삭제되지 않음 | 체크박스가 `disabled` 이고 사유가 그 줄에 있다. **그룹의 체크 상태에서도 세지 않는다** — 세면 그 체크박스는 영원히 절반만 켜진 채로 남는다 | [x] |
| F6 | 무료배송 안내 | 조건 미달 그룹 | 남은 금액 표시, 충족 시 사라짐 | 3만원어치면 「20,000원 더 담으면 무료배송」, 넘기면 그 줄이 사라지고 배송비가 0원이 된다. 무료 조건이 **없는** 판매자에게는 처음부터 나오지 않는다 | [x] |
| F7 | 빈 상태 | 전부 삭제 | 빈 상태 + 쇼핑 계속하기 | 빈 상태와 홈 링크. 막다른 길이 아니다 | [x] |
| F8 | 9조합 | 밀도 3 × 뷰포트 3 | 깨짐 0건 | 9조합 전부에서 제목·두 그룹·합계가 있고 **주문 버튼이 정확히 하나** (D-055) | [x] |

**axe 는 한 곳을 잡았다.** 썸네일이 상품 이름과 **같은 곳으로 가는 두 번째 링크**인데,
사진이 없는 줄에서는 이름조차 없는 링크가 되어 `link-name` 위반이었다. 마우스로는
사진을 누르는 것이 편하므로 링크는 두고 접근성 트리와 탭 순서에서 뺐다 — 보조 기술에
같은 목적지가 두 번 읽히는 것도 함께 없어진다.
