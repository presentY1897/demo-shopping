## 1. 목적

장바구니 데이터와 API 를 만든다. 담는 단위는 **Variant(SKU)** 다.

## 2. 범위

### 포함
- `Cart` / `CartItem` — 사용자당 1개, Variant + 수량
- 담기·수량 변경·삭제·선택 삭제 API
- 담을 때 재고 확인 (예약은 하지 않음)
- **1회 주문 최대 수량 검증** (`maxPurchaseQuantity`, TASK-0032)
- 판매자별 그룹핑된 조회 응답
- 가격·재고 변동 감지 (담은 시점 대비)
- 비로그인 장바구니 (localStorage) → 로그인 시 서버 병합
- 최대 담기 수량 제한

### 제외
- 화면 (TASK-0046)
- 금액 계산 (TASK-0047)
- 재고 예약 (TASK-0048)

## 3. 요구사항

- [x] 같은 Variant 를 다시 담으면 수량이 합산된다
- [x] 재고보다 많은 수량은 담을 수 없다
- [x] 판매자가 정한 1회 최대 구매 수량을 넘길 수 없다
- [x] 조회 시 판매자별로 묶여서 나온다
- [x] 담은 뒤 가격이 바뀌면 알 수 있다
- [x] 비로그인 장바구니가 로그인 시 병합된다

## 4. 설계

```
GET /api/v1/cart
{
  groups: [
    { seller: {...}, items: [...], productAmount, shippingFee },
    ...
  ],
  totalProductAmount, totalShippingFee
}
```

**판매자별 그룹핑을 API 에서 하는 이유**: 배송비가 판매자 단위로 붙고(D-023), 주문도 판매자별로 분할된다. 클라이언트가 매번 그룹핑하면 규칙이 여러 곳에 흩어진다.

**장바구니에서 재고를 예약하지 않는 이유**: 담고 안 사는 사람 때문에 재고가 계속 잠긴다. 예약은 주문서 진입 시점이다. (D-026)

### 4.1 `shippingFee` 는 아직 계산하지 않는다 (2026-09-05 정정)

위 응답 스케치에 `shippingFee` 와 `totalShippingFee` 가 있는데, **2장이 금액 계산을 TASK-0047 로
빼 두었다.** 그리고 `pricing.md` 의 배송비는 「SellerOrder 단위로 부과, **조건부 무료**」다 —
그 조건(무료 기준액, 판매자별 기본 배송비)은 스키마에 아직 없다.

없는 규칙으로 지어낸 숫자를 응답에 실으면 화면이 그것을 그대로 그리고, TASK-0047 이 진짜 규칙을
넣는 날 **금액이 바뀐다.** 그래서 이 TASK 의 응답은 이렇게 낸다:

| 필드 | 지금 | 왜 |
| --- | --- | --- |
| `productAmount` · `totalProductAmount` | **낸다** | Σ(`price` × 수량)이다. 계산 규칙이 아니라 장바구니에 든 것 자체다 |
| `shippingFee` · `totalShippingFee` | **내지 않는다** | 조건부 무료 규칙이 없다. TASK-0047 이 넣는다 |

응답에 **없는 것**과 `0` 은 다르다. `0` 은 「무료다」라는 약속이고, 없는 것은 「아직 모른다」다.

### 4.2 장바구니는 자기 퍼미션을 갖는다 (2026-09-05)

`cart.read` · `cart.write` 를 더한다. `order.*` 를 재사용하지 않는 이유가 있다 — **운영자가
`order.read` 를 `any` 로 갖는다.** 재사용하면 운영자가 아무의 장바구니나 읽을 수 있다는 뜻이
되고, 그것은 아무도 요구한 적 없는 사생활 확대다.

`BUYER` 와 `SELLER_OWNER` 가 `own` 으로 갖는다. `ADMIN_SUPER` 는 모든 퍼미션을 `any` 로 갖는
규칙이라 자동으로 따라오지만, **라우트에 id 가 없으므로 행사할 대상이 없다**(4.3).

### 4.3 F7 은 403 이 될 수 없다 (2026-09-05 정정)

F7 이 「타인 장바구니 조회 시도 → 403」인데, 4장의 설계가 `GET /api/v1/cart` 다 — **경로에 id 가
없다.** `/me` 와 같은 모양이고, 남을 가리킬 방법이 애초에 없다.

그래서 기준을 「거절된다」가 아니라 **「가리킬 수 없다」**로 바꾼다. 재는 것 둘:

- 토큰 없이 부르면 **401**
- 장바구니 라우트 어디에도 사용자 id 를 받는 자리가 없다 (구조로 확인)

퍼미션 가드는 그대로 두 번째 방어선이다 — 화면이 아니라 서비스가 소유자를 정한다.

| F2c | 합산 우회 | 2개 담고 다시 1개 | 합산 3이므로 거부 | 거부. 검사하는 것은 요청의 1이 아니라 합산된 3이다 | [x] |
| F3 | 그룹핑 | 판매자 3곳 | 그룹 3개 | 그룹 3개, 각자 소계. 한 판매자의 두 상품은 한 그룹 | [x] |
| F4 | 가격 변동 | 담은 뒤 가격 변경 | 변동 플래그 | `price_increased` 와 함께 지금 가격·담을 때 가격 **둘 다** 내려간다 | [x] |
| F5 | 품절 감지 | 담은 뒤 재고 0 | 품절 표시 | `sold_out`. 재고가 **줄기만** 한 경우는 `stock_reduced` 로 따로 — 뺄 일과 수량을 낮출 일은 다르다 | [x] |
| F6 | 병합 | 비로그인으로 담고 로그인 | 병합, 중복은 합산 | 합산되고, **상한을 넘으면 상한까지만 남긴다**. 거절하지 않는다 — 로그인 직후의 「합칠 수 없습니다」는 사람이 할 수 있는 일이 없는 화면이다 | [x] |
| F7 | 소유권 | 라우트에 id 가 있는가 · 토큰 없이 | 가리킬 수 없다 + 401 | 401 확인. 두 계정이 각자의 장바구니를 갖고, **남을 가리킬 자리가 없다**(4.3) | [x] |
| F8 | 데모 정리 | 데모 계정 만료 | 장바구니가 함께 지워진다 | `Cart` 와 `CartItem` 모두. 실계정 것은 그대로 | [x] |
| F9 | 동시 담기 (A7) | 같은 Variant 를 동시에 | 상한을 넘지 않는다 | 상한 2에 2개씩 둘을 동시에 → 하나만 통과, 수량 2. 셋을 1개씩 → 줄 하나, 수량 3 | [x] |

**A7 을 채우다 조용한 버그를 하나 찾았다.** 같은 상품을 동시에 세 번 담으면 수량이 3이 아니라
**1** 이 됐다. 원인은 트랜잭션 안에서 장바구니 행을 만들려 한 것이다 — Postgres 는 트랜잭션 안의
한 문장이 실패하면 **그 트랜잭션 전체를 중단시키므로**, 유니크 위반을 잡아 다시 읽어도 이미
늦었고 이후의 모든 문장이 거절된다. 증상은 「담기가 가끔 안 먹는다」였다.

고친 모양: 장바구니 행을 만드는 일은 **트랜잭션 밖에서** 각자의 문장으로, 그 다음 트랜잭션 안에서
그 행을 `FOR UPDATE` 로 잠근다. 잠그는 것은 장바구니이지 Variant 가 아니다 — 재고를 예약하지
않으므로(D-026) Variant 를 잠글 이유가 없고, 잠그면 같은 인기 상품을 담는 사람들이 서로를
기다린다. 음성 대조군으로 확인했다: 잠금을 빼면 그 검사가 빨개진다.
