# TASK-0049: 주문 생성 API (2단 분할)

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M07 장바구니·주문 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/order-create` |
| 선행 작업 | TASK-0047, TASK-0048 |

## 1. 목적

주문을 **Order → SellerOrder → OrderItem** 2단 구조로 생성한다. 이 프로젝트 도메인 설계의 중심이다. (D-023)

## 2. 범위

### 포함
- `Order` / `SellerOrder` / `OrderItem` / `OrderStatusHistory` 스키마
- 주문 생성 트랜잭션: 검증(재고·판매상태·**최대 구매 수량**) → 금액 계산 → 재고 예약 → 저장
- **상품·판매자·수령인 스냅샷 저장**
- 주문번호 생성 규칙
- 판매자별 분할 로직
- 항목별 안분액 저장 (TASK-0047 결과)
- 주문 조회 API (구매자·판매자 권한별)
- 실패 시 예약 롤백

### 제외
- 결제 (M08)
- 주문서 화면 (TASK-0050)
- 상태 전이 (M09)

## 3. 요구사항

- [ ] 3개 판매자 상품을 주문하면 SellerOrder 3개가 생긴다
- [ ] 결제는 Order 단위 1건으로 준비된다
- [ ] 상품명·가격이 나중에 바뀌어도 주문서는 그대로다
- [ ] 재고 예약 실패 시 주문이 생성되지 않는다
- [ ] 판매자는 자기 SellerOrder 만 조회할 수 있다

## 4. 설계

```
POST /api/v1/orders
① 장바구니 항목 검증 (판매 상태·가격 변동)
② 금액 계산 (TASK-0047)
③ 재고 예약 (TASK-0048) — 하나라도 실패하면 전체 롤백
④ Order + SellerOrder(판매자별) + OrderItem 저장
⑤ 상태 PAYMENT_PENDING
```

**스냅샷 컬럼**: `OrderItem.productSnapshot` 에 상품명·옵션·이미지·판매자명을 JSONB 로 저장한다. 상품이 삭제되거나 데모 판매자가 만료돼도(TASK-0025) 주문 이력이 온전해야 한다.

주문번호: `YYYYMMDD-{짧은 난수}` — 사람이 읽고 전달할 수 있어야 한다.

### 4.1 배송 정책이 스키마에 없다 — 여기서 만든다 (2026-09-05 정정)

F2 는 「계산 엔진 결과와 **1원도** 차이 없음」을 요구하는데, 그 엔진은
`shippingPolicies` 를 입력으로 받는다(TASK-0047). **그것을 만들어 주는 것이 아직
없다.** TASK-0108 이 「배송 정책은 M09」라고 적어 두었지만 그것은 **판매자 설정
화면**의 이야기이고, 화면보다 먼저 필요한 것은 값이 놓일 자리다 — 없는 규칙으로
지어낸 배송비를 주문에 저장하는 것은 TASK-0045 4.1 이 거절한 바로 그 일이다.

그래서 `Seller` 에 두 컬럼을 더한다.

| 컬럼 | 뜻 |
| --- | --- |
| `shippingFee` | 이 판매자의 기본 배송비 |
| `freeShippingThreshold` | 이 금액 이상이면 무료. `null` 이면 무료 조건이 없다 |

`null` 과 `0` 은 다르다 — `0` 은 「0원 이상이면 무료」, 즉 **언제나 무료**다
(`ShippingPolicy` 의 주석이 이미 그렇게 정해 두었다).

기본값은 플랫폼 기본이고 판매자가 바꾼다. 지금은 바꿀 화면이 없으므로 **M09 가 그
화면을 붙일 때까지 전부 기본값**이고, 그 사실이 컬럼의 기본값으로 적혀 있는 편이
「어딘가에서 3,000원이 나온다」보다 낫다.

### 4.2 쿠폰·적립금은 아직 없다 (M11) — 그런데 안분은 지금 저장한다

F8 은 「할인 적용 주문 → `OrderItem` 에 안분액 저장됨」인데 쿠폰도 적립금도 M11 이다.
할인 목록이 언제나 비면 안분액은 전부 0이고, F8 은 **아무것도 재지 않는 검사**가 된다.

그래서 주문 생성 서비스는 `discounts` 를 **인자로 받는다.** 컨트롤러는 오늘 빈
배열을 넘기고, M11 이 쿠폰·적립금을 계산해 채운다. F8 은 서비스를 직접 불러 할인이
실제로 항목까지 안분되어 저장되는지를 잰다 — 엔드포인트가 아직 그 입력을 받지 않는
것과, 저장 경로가 없는 것은 다른 이야기다.

### 4.3 예약과 주문은 `checkoutId` 로 이어진다 (TASK-0048 4.1 의 회수)

TASK-0048 이 「`Order` 를 만들 때 그 행에 같은 `checkoutId` 를 적거나 `orderId`
컬럼을 더한다」로 남겨 둔 결정이다. **`checkoutId` 를 고른다.**

`orderId` 를 예약에 달면 순서가 막힌다 — 4장의 흐름이 ③ 예약 → ④ 저장이라 예약을
잡는 시점에 주문 행이 아직 없다. `checkoutId` 는 주문 서비스가 **둘 중 어느 행보다
먼저** 만드는 값이라 그 문제가 없고, 「이 주문이 잡은 예약 전부」를 푸는 일이
`releaseCheckout(order.checkoutId)` 한 줄이 된다 — TASK-0048 이 이미 만들어 둔 것이다.

`Order.checkoutId` 는 유니크다. 한 주문서 시도가 두 주문이 되는 것은 재시도의
버그이고, 그때 예약은 둘 중 하나만 가리키게 된다.

### 4.4 결제가 없으므로 예약은 잡힌 채로 남는다 (M08)

주문은 `PAYMENT_PENDING` 으로 생기고 예약은 `HELD` 로 남는다. 확정하는 것은 결제
승인(M08)의 일이다. 그때까지 그 재고를 지키는 것이 예약의 존재 이유이고, 결제가 오지
않으면 TASK-0051 이 TTL 만료로 풀면서 `SellerOrder` 를 `PAYMENT_FAILED` 로 옮긴다.

**따라서 이 TASK 는 재고를 한 개도 차감하지 않는다.** 원장에 남는 것도 없다. 이상해
보이지만 그것이 D-026 의 구조다 — 판 것이 아니라 잡아 둔 것이다.

### 4.5 장바구니는 비우지 않는다

범위에 없고, 비우면 안 되는 이유가 따로 있다. 주문 생성은 결제의 **앞**이고, 결제가
실패하면 사람은 방금 담았던 것을 다시 담아야 한다. 비우는 것은 결제 승인(M08)의 일이다.

### 4.6 수령인은 저장된 배송지에서 **복사**한다

요청은 `addressId` 를 보내고 주문은 그 값을 자기 컬럼에 적는다. 가리키지 않는 이유는
`profile.ts` 의 `addressSchema` 주석이 이미 적어 두었다 — 배송지는 지워지고 고쳐지지만
「어디로 보냈나」는 바뀌면 안 된다.
