## 1. 목적

주문 금액 계산과 **항목별 할인 안분**을 구현한다. `docs/design/pricing.md` 가 이 코드의 명세다.

## 2. 범위

### 포함
- 계산 순서 구현: 상품금액 → 상품할인 → (할인 목록) → 배송비 → 실결제금액
- **할인을 목록으로 받는 인터페이스** — 쿠폰·적립금이 아직 없어도 구조는 완성
- 항목별 안분 (원 단위 잔여를 최대 항목에 몰아 합계 보존)
- 판매자별 소계 계산
- 배송비 규칙 (판매자별, 무료배송 조건)
- 계산 결과 스냅샷 구조 (주문 저장용)
- 역산 함수 — 항목 일부 취소 시 환불액 계산 (M10 에서 사용)

### 제외
- 쿠폰·적립금 실제 규칙 (M11)
- 주문 저장 (TASK-0049)

## 3. 요구사항

- [x] 안분액의 합이 전체 할인액과 1원도 어긋나지 않는다
- [x] 판매자별 소계의 합이 전체와 일치한다
- [x] 금액이 전부 정수로 계산된다
- [x] 할인 목록이 비어도 정상 동작한다
- [x] 항목 일부에 대한 환불액을 계산할 수 있다

## 4. 설계

```ts
calculateOrder({
  items: [{ variantId, unitPrice, quantity, sellerId }],
  discounts: [{ type, amount, scope: 'ORDER'|'SELLER'|'ITEM', targetId?, bearer }],
  shippingPolicies: [...]
}) => {
  totalProductAmount, totalDiscountAmount, totalShippingFee, paidAmount,
  sellerOrders: [{ sellerId, productAmount, discountAmount, shippingFee }],
  items: [{ ..., itemDiscountAmount, couponDiscountAmount, pointDiscountAmount }]
}
```

**`discounts` 를 목록으로 받는 이유**(D-036): 지금은 빈 배열이지만 M11 에서 쿠폰·적립금이 이 목록에 들어온다. 계산기를 다시 만들지 않는다.

안분 규칙과 잔여 처리는 `docs/design/pricing.md` 2장을 그대로 따른다.

## 5. 구현 계획

1. 계산 입출력 타입 정의 (`packages/shared`)
2. 상품금액·소계 계산
3. 안분 알고리즘 + 잔여 처리
4. 배송비 규칙
5. 환불액 역산 함수
6. **속성 기반 테스트** — 무작위 입력에서 합계 보존 검증

## 6. 완료 기준

### 6.1 기능

| # | 기준 | 측정 방법 | 목표 | 실측 | 충족 |
| --- | --- | --- | --- | --- | --- |
| F1 | 기본 계산 | 항목 3개, 할인 없음 | 합계 정확 | 28,000원. 빈 주문도 0으로 답한다 | [x] |
| F2 | 안분 합계 보존 | 10,000원을 3항목에 | 합 = 10,000 (오차 0) | 정확 | [x] |
| F3 | 나누어떨어지지 않는 경우 | 같은 금액 3항목 | 3334+3333+3333 | 그대로. 동점이면 **먼저 나온 것**에 잔여를 준다 — 순서를 정해 두지 않으면 같은 입력이 실행마다 다른 답을 낸다 | [x] |
| F4 | 판매자 소계 | 판매자 2곳 | 소계 합 = 전체 | 상품금액도 실결제금액도 일치. 판매자 쿠폰은 그 판매자 항목에만 | [x] |
| F5 | 배송비 | 조건 충족·미달 | 각각 정확 | 임계값 **정확히 같으면 무료**. 정책이 없으면 0원 — 「모르니까 3,000원」은 아무도 동의한 적 없는 금액이다 | [x] |
| F6 | 빈 할인 목록 | `discounts=[]` | 정상 동작 | 정상 | [x] |
| F7 | 환불 역산 | 항목 1개 취소 | 안분액 반영 | 20,000원이 아니라 18,000원. **배송비 재부과**까지 — 부분 취소로 무료 조건이 깨지면 환불액에서 차감된다 | [x] |
| F8 | 무작위 검증 | 1000회 | 위반 0건 | 위반 0. **실제로 버그를 잡았다** (아래) | [x] |

**F8 이 잡은 것.** 적립금이 배송비를 낼 수 있는데(명세가 「① − ③ + ④ 범위 내에서」라 적었다) 그
몫까지 항목에 안분하고 있었다. 그러면 **항목의 할인이 상품금액을 넘고**, 부분 취소에서 환불액이
음수가 된다 — 취소했는데 돈을 더 내라는 화면이다. 손으로 쓴 검사 열댓 개는 전부 통과했고,
무작위 1000회가 39번째 주문에서 잡았다.

고친 모양: 적립금은 **물건 값을 먼저 덮고 남은 것이 배송비를 낸다.** 배송비를 낸 몫은 항목이
아니라 `SellerOrder.shippingPointAmount` 에 따로 센다 — 그쪽이 그 돈이 실제로 간 곳이다.

같은 이유로 **깎을 수 있는 것보다 큰 쿠폰은 거기까지만 적용된다.** 10,000원짜리 주문에 20,000원
쿠폰을 쓰면 10,000원이 깎이고 끝이다. 그래서 응답의 `totalCouponDiscountAmount` 는 요청된
금액이 아니라 **실제로 적용된 금액**이다.

### 6.2 품질 게이트

[공통 품질 게이트](../QUALITY-GATES.md) 적용. 예외:
- **Q5 강화** — 계산 엔진은 **분기 커버리지 100%**. 금액이 틀리면 실제 돈이 틀어진다
- **2장 해당 없음**
- **3~4장 해당 없음** — 순수 함수

**문서를 먼저 고친 것 하나.** `pricing.md` 가 「조건부 무료」라고만 적어 두고 어느 금액으로
판정하는지는 말하지 않았는데, 세 후보가 실제로 다른 값을 낸다. **상품금액 − 쿠폰 할인**으로
정하고 그 이유를 문서에 적었다 — 적립금까지 빼면 「적립금 3,000원을 썼더니 배송비 3,000원이
붙었다」가 생기고, 그 화면은 설명할 수 없다. 가르는 기준은 **쿠폰은 값을 깎는 것이고 적립금은
내는 방법이다.**
