# TASK-0051: 예약 만료 스케줄러

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M07 장바구니·주문 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/reservation-expiry` |
| 선행 작업 | TASK-0048 |

## 1. 목적

만료된 재고 예약을 자동 해제한다. **이 스케줄러가 멈추면 재고가 잠긴다** — 그래서 헬스체크 대상이다. (D-026)

## 2. 범위

### 포함
- 만료 예약 정리 스케줄러 (주기 1분)
- 결제 대기 상태로 방치된 주문 처리 (PAYMENT_PENDING → PAYMENT_FAILED)
- 헬스체크에 마지막 실행 시각·처리 건수 노출
- 처리 지연 임계치 초과 시 degraded 표시
- 수동 실행 API (관리자)
- 정합성 점검 — `reserved` 캐시 vs HELD 합계

### 제외
- 관리자 화면 (M14)

## 3. 요구사항

- [ ] 만료된 예약이 1분 내 해제된다
- [ ] 해제된 만큼 가용재고가 복원된다
- [ ] 확정된 예약은 건드리지 않는다
- [ ] 스케줄러 상태를 헬스체크로 알 수 있다
- [ ] 다중 인스턴스에서도 중복 처리되지 않는다

## 4. 설계

```
매 1분:
  ① HELD && expiresAt < now 인 예약 조회 (배치 상한 적용)
  ② 각각 release() → reserved 감소, 상태 RELEASED
  ③ 연결된 주문이 PAYMENT_PENDING 이면 PAYMENT_FAILED 로 전이
  ④ 실행 결과 기록
```

**중복 실행 방지**: 배포 인스턴스가 늘어나면 스케줄러가 동시에 돈다. DB 어드바이저리 락으로 한 번에 하나만 실행되게 한다.

**정합성 점검**은 별도 주기(예: 1시간)로 돌려 `reserved` 캐시와 실제 HELD 합계를 대조하고, 어긋나면 로그와 알림을 남긴다. 자동 보정은 하지 않는다 — 원인을 모르는 채 값을 고치면 문제가 숨는다.

### 4.1 배치 상한이 있는 이유는 성능이 아니라 **장애를 안 만드는 것**이다 (2026-09-05)

4장이 「배치 상한 적용」이라고만 적어 두었다. 한 번에 200건이고, 이유는 잠금이다 —
만료가 천 건 쌓인 날 한 트랜잭션으로 전부 풀면 그동안 그 variant 들의 행이 잠겨
**담기와 주문이 함께 멈춘다.** 청소가 장애를 만드는 모양이다.

남은 것은 다음 주기가 가져간다. 주기가 1분이므로 천 건은 다섯 주기 안에 사라지고,
그동안 누구도 기다리지 않는다.

### 4.2 어드바이저리 락은 **트랜잭션 단위**다

`pg_try_advisory_xact_lock` 이다. 세션 락은 풀어 주는 것을 잊으면 영원히 남고, 잊는
경우는 예외가 아니라 **프로세스가 죽는 경우**다 — 그때 세션 락은 연결이 끊길 때까지
남는다. 트랜잭션 락은 데이터베이스가 알아서 놓는다.

락을 못 잡으면 `skipped` 로 답하고 아무것도 하지 않는다. 기다리지 않는 이유는 이미
다른 인스턴스가 같은 일을 하고 있기 때문이다.

**락이 없으면 어떤 모양으로 실패하나.** 두 인스턴스가 같은 예약을 동시에 풀면
`reserved` 가 두 번 줄어 음수 쪽으로 어긋나고, 그것은
`ProductVariant_reserved_check` 가 거절한다 — 증상은 「가끔 청소가 실패한다」이고,
그 로그만 보고 원인을 찾기는 어렵다.

### 4.3 수동 실행은 자기 퍼미션을 갖는다 — `reservation.sweep`

`order.write` 를 재사용하지 않은 이유는 스코프다. 구매자와 판매자가 그것을 `own`
으로 갖고 있는데 이 잡은 **소유자가 없는 전역 작업**이라 `own` 으로 좁힐 대상이
없다 — 재사용하면 「내 것만」이 아무 뜻이 없는 자리에서 통과한다.

운영자와 최고 관리자가 갖는다. 손으로 돌릴 수 있어야 하는 이유는 R1 이다: 헬스체크가
degraded 를 보여 주는데 고칠 방법이 배포뿐이면 그 신호는 절반만 쓸모 있다.

### 4.4 한 번도 안 돈 것은 **멈춘 것으로 친다**

「아직 안 돌았을 뿐」과 「멈췄다」를 밖에서 구분할 방법이 없고, 둘 중 안전한 해석은
멈췄다는 쪽이다. 부팅 직후 한 주기 동안 degraded 로 보이는 것이, 잠긴 재고를 못 보는
것보다 낫다.

임계치는 주기의 **다섯 배**(5분)다. 한 번 걸러 뛰는 것은 재시작이나 배포로도
일어나므로 그것까지 알람으로 만들면 아무도 알람을 안 보게 된다.

### 4.5 정합성 점검은 **고치지 않는다**

R2 가 정한 대로다. 원인을 모르는 채 값을 고치면 문제가 숨는다 — 검출하고 기록하는
것까지가 이 잡의 일이고, 보정은 사람의 판단이다. 그래서 점검은 `GET` 이고 아무것도
쓰지 않는다.

### 6.1 기능

| # | 기준 | 측정 방법 | 목표 | 실측 | 충족 |
| --- | --- | --- | --- | --- | --- |
| F1 | 만료 해제 | 만료 시각을 과거로 | RELEASED, 가용재고 복원 | 풀리고 **그 몫을 다음 사람이 실제로 잡는다**. 음성 대조군으로 아직 안 지난 예약은 건드리지 않는 것까지 확인했다 — 전부 푸는 구현도 앞의 검사만으로는 통과한다 | [x] |
| F2 | 확정 보호 | CONFIRMED 예약 존재 | 건드리지 않음 | 만료 시각이 지나도 그대로. 같은 variant 에 붙은 만료 예약은 그 옆에서 정상적으로 풀린다 — 거르는 기준이 variant 가 아니라 상태라는 뜻이다 | [x] |
| F3 | 주문 전이 | 만료된 결제 대기 주문 | PAYMENT_FAILED | 전이되고 `OrderStatusHistory` 에 `actorId: null` 로 남는다 — 옮긴 것이 사람이 아니다. 살아 있는 주문서는 건드리지 않고, `PAID` 인 몫도 건드리지 않는다 | [x] |
| F4 | 중복 방지 | 인스턴스 2개 동시 실행 | 처리 중복 0건 | 두 가지로 잰다. **짜 맞춘 쪽** — 바깥 연결이 락을 쥔 채로 열어 두면 `skipped: true` 로 답하고 `lastRunAt` 도 남기지 않는다(건너뛴 것을 실행으로 적으면 헬스체크가 멈춘 스케줄러를 건강하다고 말한다). **안 짜 맞춘 쪽** — 만료 150건에 동시 실행 2회, 푼 수의 합이 정확히 150이고 `reserved` 가 음수로 가지 않는다 | [x] |
| F5 | 헬스체크 | `/health` | 상태·마지막 실행·건수 | `reservationExpiry: { status, lastRunAt, releasedCount }`. **필수 필드다** — 「없다」와 「멈췄다」를 구분하면 분기만 늘고, 없는 것을 정상으로 지나치게 된다 | [x] |
| F6 | 지연 감지 | 스케줄러 중지 후 | degraded | 5분(주기의 다섯 배)이 지나면 degraded 이고 맨 위 `status` 까지 함께 내려간다. **한 번도 안 돌았으면 degraded** 다 (4.4) | [x] |
| F7 | 정합성 점검 | 캐시를 틀리게 함 | 검출·기록 | 검출하고 **고치지 않는다** (R2). 깨끗한 상태에서는 빈 배열인데, 그때도 잡혀 있는 예약을 남겨 둬 등식이 `0 = 0` 으로만 참이 되지 않게 했다 | [x] |
| F8 | 대량 처리 | 만료 1000건 | 배치 내 분할, 누락 0 | `[200, 200, 200, 200, 200]` 다섯 주기. 푼 것의 만료 시각이 남은 것보다 **전부 이르다** — 오래된 것부터 가져가므로 굶는 예약이 없다. 끝나면 `HELD` 0건 · `RELEASED` 1000건 · `reserved` 0 | [x] |

**F8 의 1000건은 원시 SQL 로 만든다.** 두 방법을 실제로 쟀다 — 서비스로 한 건씩 잡으면
**7,768ms**(한 건이 대화형 트랜잭션 하나라 왕복이 1000번), `INSERT … generate_series`
한 문장이면 **59ms** 다. 시험 대상은 잡는 길이 아니라 **치우는 길**이므로 만드는 쪽을
빠르게 하고 청소는 서비스로 돌린다.

**F1 의 음성 대조군은 벽시계 구현을 잡도록 만들었다.** 안 지난 예약의 만료 시각이
`DEFAULT_TEST_INSTANT + 15분`(2026-09-03)이라 **실제 시각은 이미 그것을 지났다** —
`now()` 나 `new Date()` 를 읽는 구현은 그것을 풀고 빨개진다.
