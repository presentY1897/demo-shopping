## 1. 목적

주문서 진입 시 재고를 선점하고 결제 승인 시 확정하는 구조를 만든다. **오버셀을 구조적으로 막는다.** (D-026)

## 2. 범위

### 포함
- `StockReservation` — variant, 주문, 수량, 만료시각, 상태(HELD/CONFIRMED/RELEASED)
- 예약 생성 (조건부 갱신으로 동시성 제어)
- 예약 확정 → 재고 원장 차감 (TASK-0036 서비스 경유)
- 예약 해제 (결제 실패·이탈)
- 가용재고 계산 (`stock` − 유효 HELD 합계)
- 상품 조회에 가용재고 반영
- 예약 연장 (주문서에 오래 머무는 경우)

### 제외
- 만료 스케줄러 (TASK-0051)
- 주문 생성 (TASK-0049)

## 3. 요구사항

- [ ] 재고 1개에 두 명이 동시에 주문서 진입하면 한 명만 성공한다
- [ ] 예약된 재고는 다른 사람의 가용재고에서 빠진다
- [ ] 결제 승인 시 예약이 실제 차감으로 확정된다
- [ ] 결제 실패 시 예약이 해제된다
- [ ] 확정된 예약은 다시 확정되지 않는다 (멱등)

## 4. 설계

```
주문서 진입 → reserve(variantId, qty, orderId, ttl=15분)
              UPDATE variant SET reserved = reserved + qty
              WHERE id = ? AND stock - reserved >= qty      ← 실패하면 품절

결제 승인 → confirm(reservationId)
            원장에 SALE 기록 + stock 차감 + reserved 감소 + 상태 CONFIRMED

실패·이탈·만료 → release(reservationId)
                 reserved 감소 + 상태 RELEASED
```

`reserved` 를 Variant 에 캐시 컬럼으로 둔다. 매번 예약 테이블을 합산하면 조회가 무거워진다. 정합성은 점검 배치로 확인한다.

### 4.1 예약은 아직 `orderId` 를 가리킬 수 없다 (2026-09-05 정정)

위 스케치가 `reserve(variantId, qty, orderId, ttl)` 인데 **`Order` 테이블이 아직 없다** — 주문
생성은 TASK-0049 이고 이 TASK 의 「제외」에 적혀 있다. 없는 표를 가리키는 컬럼은 외래키를 걸 수
없고, 외래키 없는 uuid 컬럼은 아무것도 지켜 주지 않는다.

그래서 예약은 **누가**(`userId`) 잡았는지와 **어느 주문서 시도**(`checkoutId`)인지를 들고 있는다.
`checkoutId` 는 주문서에 들어갈 때 부르는 쪽이 발급하는 불투명한 값이고, 그것으로 「이 시도의
예약 전부」를 해제할 수 있다 — 결제 실패와 이탈이 그 모양이다.

TASK-0049 가 `Order` 를 만들 때 그 행에 같은 `checkoutId` 를 적거나 `orderId` 컬럼을 더한다.
어느 쪽이든 **그 TASK 의 스키마 변경**이지 여기서 미리 뚫어 둘 구멍이 아니다.

이 TASK 의 완료 기준은 전부 `reservationId` 로 확정·해제한다(F3~F5). 주문을 몰라도 성립한다.

### 4.2 스케치와 실제가 갈리는 다섯 곳 (2026-09-05 정정)

**① 이 TASK 는 엔드포인트를 더하지 않는다.** 예약을 부르는 쪽은 주문 생성
(`POST /api/v1/orders`, TASK-0049 4장 ③)이고 그것은 이 TASK 의 「제외」다. 예약은
서비스로만 존재한다 — 부를 화면이 없는 REST 표면을 먼저 뚫어 두면, 그것을 실제로
쓸 때가 되어 모양이 안 맞는다는 것을 알게 된다.

그래서 3장 A3·A4(권한·인증)는 **이 TASK 가 바꾸는 유일한 응답**인 상품 상세
(`GET /api/v1/products/:id`)로 확인한다. 새 라우트가 없으므로 새로 뚫린 구멍도 없다.

**② 원장 유형은 `SALE` 이 아니라 `RESERVE_CONFIRM` 이다.** 4장 스케치는 「원장에
SALE 기록」이라고 적었지만, 공유 열거형은 이미 `RESERVE_CONFIRM` 을 "A reservation
turning into a real decrement (M07)" 으로 잡아 두었다(`packages/shared/src/api/stock.ts`).
둘을 한 유형으로 묶으면 원장만 보고서는 **예약을 거친 판매와 그렇지 않은 판매를 구분할
수 없다** — 예약이 새는지 확인할 방법이 사라진다.

**③ `reserved` 를 먼저 줄이고 `stock` 을 나중에 줄인다.** 확정은 두 컬럼을 모두
줄이는데, 순서가 자유롭지 않다. `ProductVariant_reserved_check` 가
`reserved <= stock` 을 문장마다 검사하기 때문이다 — 재고 1·예약 1 에서 `stock` 을
먼저 0으로 내리면 그 순간 `reserved(1) > stock(0)` 이라 **제약이 확정을 거절한다.**
줄이는 순서는 예약 → 재고다.

**④ 가용재고는 응답의 새 필드다.** `productVariantSchema` 에 `availableStock` 을
더한다. 상점 응답에서 `stock` 의 뜻만 바꾸는 방법도 있지만, 그러면 같은 이름이
엔드포인트마다 다른 수를 뜻하게 된다 — 판매자 콘솔은 실물 재고를 봐야 하고 구매자는
살 수 있는 수를 봐야 한다. 두 수는 이름이 둘이어야 한다.

**⑤ 「유효한 HELD 합계」와 `reserved` 는 만료 직후 갈린다.** 만료된 예약은 스케줄러가
`RELEASED` 로 바꾸기 전까지 여전히 `HELD` 이고, `reserved` 도 여전히 그것을 세고 있다.
그래서 F7 이 재는 등식은 **`reserved` = 전체 HELD 합계**이지 「유효한 HELD 합계」가
아니다. 만료분을 실제로 풀어 주는 것은 TASK-0051 이고, 그 스케줄러가 멈추면 재고가
잠긴다는 것이 2장 상태도의 경고다.

이와 같은 이유로 **확정은 만료를 따지지 않는다.** 아직 `HELD` 라면 재고는 여전히 이
예약의 것이고, 결제가 이미 승인된 뒤에 「15분이 지났으니 안 됩니다」를 답하는 것은
아무도 원하지 않는 결과다. 반대로 **연장은 만료를 따진다** — 만료된 것을 되살리면
스케줄러가 이미 집어 든 행을 되살리는 경합이 된다.

**동시성의 근거는 이 TASK 에서 처음 만들어지지 않았다.** TASK-0106 이
`test/db/stock-contention.spec.ts` 에서 「읽고 나서 쓰는」 잘못된 예약이 이 하네스에서 실제로
**오버셀을 재현하는지**를 먼저 보였다. 그래서 F2 의 「하나만 통과했다」는 운이 아니라 구현에 대한
증거다.

**제약이 마지막 줄로 남아 있다.** 조건부 갱신이 나중에 틀리게 고쳐지더라도
`ProductVariant_reserved_check`(`0 <= reserved <= stock`)가 오버셀을 거절한다. 그 제약이 재고를
**내리는 쪽도** 막는다는 것을 확인했다 — 2개가 잡힌 재고 3을 1로 내리려 하면 DB 가 거절한다.

이 제약을 더하면서 기존 검사 하나가 이름을 바꿔 달았다. 음수 재고는 이제
`ProductVariant_stock_check` 가 아니라 `ProductVariant_reserved_check` 로 거절된다 —
`0 <= reserved <= stock` 이 `stock >= 0` 을 **함의하기 때문**이고, 둘 다 위반이라 어느 이름이
나오는지는 Postgres 의 검사 순서다. 앞의 제약을 지우지 않은 이유는 예약 제약이 언젠가 바뀌어도 그
규칙이 남아야 하기 때문이다.
