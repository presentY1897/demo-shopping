# TASK-0019: 콘솔 레이아웃 (seller · admin)

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M03 디자인 시스템 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/console-layout` |

## 1. 목적

판매자·관리자 앱이 공유하는 콘솔 레이아웃을 만든다. 사이드바 메뉴 구성만 다르고 구조는 같다.

## 2. 범위

### 포함
- `packages/ui` 의 콘솔 셸 (사이드바 + 상단바 + 본문)
- 사이드바: 메뉴 정의를 prop 으로 받아 렌더, 접기·펼치기, 현재 경로 강조
- 상단바: 페이지 제목, 사용자 메뉴 자리, 알림 자리
- 페이지 헤더 규약 (제목 + 액션 버튼 + 필터 영역)
- 두 앱에 적용, 메뉴는 `docs/design/pages.md` 기준으로 구성
- 콘솔은 밀도 2단계 고정
- **모바일 대응 범위 규약** — seller 주요 3화면만 제대로, 나머지는 깨지지만 않게

### 제외
- 각 메뉴의 실제 화면 (해당 도메인 마일스톤)
- 권한에 따른 메뉴 표시 제어 (M04)

## 3. 요구사항

- [x] 두 앱이 같은 셸 컴포넌트를 쓰고 메뉴만 다르다
- [x] 현재 경로에 해당하는 메뉴가 강조된다
- [x] 1024px 미만에서 사이드바가 접힌다
- [x] 콘솔은 데스크톱 퍼스트로 작성되고 좁은 화면에서 깨지지 않는다
- [x] 밀도 토글이 노출되지 않는다

## 4. 설계

```
apps/*/app/layout.tsx  →  <ConsoleShell menu={SELLER_MENU} …>{children}</ConsoleShell>
apps/*/app/orders/page.tsx →  <PageHeader title="주문 관리" actions=… filters=… />
```

메뉴 정의는 각 앱이 소유하고 셸은 렌더만 한다. M04 에서 권한 필터를 이 정의에 얹는다.

**콘솔 밀도를 고정하는 이유**: 관리 화면은 정보 밀도가 높은 것이 항상 정답이다. 미니멀하게 만들면 오히려 쓰기 나빠진다. (D-033) 덕분에 콘솔에는 밀도 × 뷰포트 문제가 없다.

### 4.1 TASK-0018 의 `layout/` 에서 무엇을 재사용하는가

콘솔은 헤더+푸터가 아니라 사이드바+상단바라 **겉모습은 공유할 것이 없다.** 공유되는 것은
껍데기가 아니라 그 아래의 규약이다.

| `packages/ui/src/layout/` | 콘솔에서 | 판단 |
| --- | --- | --- |
| `SkipLink` | **그대로 재사용** | 사이드바 메뉴 13개를 지나야 본문에 닿는다. shop 헤더보다 오히려 더 필요하다 |
| `useViewportBand` | **재사용하지 않음** | 밴드가 768/1280 이다. 콘솔이 갈리는 지점은 **1024px**(F3) 이라 `md` 밴드 한가운데다 |
| `PageContainer` | **재사용하지 않음** | 가운데 정렬된 고정 폭이다. 콘솔 본문은 사이드바 옆의 남은 폭 전부를 쓴다 |
| `DensityToggle` · `density-icons` | **쓰지 않음** | D-033. 콘솔에 밀도 토글이 없다 |
| `@shopping/ui/components` | **그대로 재사용** | `Drawer`(모바일 메뉴) · `IconButton` · `Popover` · `Button` |

새로 만드는 것은 `useMinWidth` 하나와 `@shopping/ui/console` 진입점의 4개다.

| 새로 만드는 것 | 이유 |
| --- | --- |
| `useMinWidth(px, serverSnapshot)` | 위 — 1024px 는 밀도 밴드가 아니다. `useViewportBand` 를 이 훅 위로 다시 얹어 `matchMedia` 배선이 두 벌이 되지 않게 한다 |
| `ConsoleShell` | 사이드바 · 상단바 · 본문의 조립. 앱이 갖는 것은 메뉴 정의뿐 |
| `ConsoleSidebar` | 메뉴 렌더 · 현재 경로 강조. 컬럼과 시트 두 자리에 같은 것이 들어간다 |
| `ConsoleTopbar` | 네비 토글 · 현재 위치 · 알림/사용자 슬롯 |
| `PageHeader` | 페이지 헤더 규약(제목 + 액션 + 필터) |

`@shopping/ui/layout` 이 아니라 **`@shopping/ui/console` 진입점을 새로 연다.** `layout` 은
`apps/shop` 이 매 화면에서 import 하는 곳이고, 거기에 콘솔 셸을 얹으면 shop 번들이 트리셰이킹에
의존하게 된다 — shop 의 P1(LCP) 이 이미 번들 파싱 비용에 걸려 있는 상태(TASK-0018 6.4)에서
질 이유가 없는 위험이다. 새 진입점은 `test/story-coverage.spec.ts` 에 **등록한다.** 등록하지
않으면 이 셸은 axe 스윕 밖에서 머지된다.

### 4.2 사이드바 브레이크포인트는 1024px

F3 이 요구하는 지점은 1024(`lg`)이고, 밀도 밴드(768 / 1280)와 다르다. 콘솔에는 밀도가 없으므로
밴드를 따라갈 이유도 없다 — 사이드바 240px + 표 하나가 성립하는 최소 폭이 기준이다.

D-055 는 **두 형태를 모두 렌더하고 CSS 로 숨기지 말라**고 못박으므로, shop 헤더와 같은 방식으로
훅이 하나만 마운트한다.

| 폭 | 사이드바 | 여는 방법 |
| --- | --- | --- |
| 1024~ | 고정 컬럼(240px) | 상단바 토글로 접고 편다 |
| ~1023 | 컬럼 없음 | 상단바 토글이 **왼쪽 드로어**를 연다 (Radix Dialog) |

`useMinWidth` 의 서버 스냅샷은 **`false`(좁은 쪽)** 이다. 콘솔은 데스크톱 퍼스트지만, 서버가
데스크톱으로 추측하면 폰 방문자가 첫 프레임에 본문 위를 덮은 사이드바를 보게 된다. 반대 방향의
대가는 4.3 이 구조로 없앤다.

### 4.3 레이아웃 시프트는 구조로 없앤다

하이드레이션 시점에 사이드바가 나타나면 본문이 밀린다. shop 은 두 헤더의 **높이를 같게** 만들어
이 문제를 없앴는데(TASK-0018 4.4), 콘솔의 교체는 세로가 아니라 가로다. 그래서 같은 수를 쓴다 —
**자리를 미리 비워 둔다.**

- 사이드바는 `position: fixed` 다. 문서 흐름에서 빠져 있으므로 마운트·언마운트가 아무것도 밀지 않는다
- 본문 래퍼는 `lg:pl-60` 을 **항상** 갖는다. 미디어 쿼리는 JS 없이 첫 페인트에 이미 맞으므로, 사이드바가 아직 없어도 본문은 처음부터 제자리다
- 상단바의 네비 토글은 **폭에 상관없이 항상 있다.** 넓으면 접기/펴기, 좁으면 드로어 열기 — 같은 버튼, 같은 크기, 같은 자리다. 없앴다 만들었다 하면 그 옆의 제목이 44px 씩 움직인다

접기 상태는 래퍼의 `data-sidebar` 로 내려가 `lg:data-[sidebar=collapsed]:pl-0` 이 여백을 거둔다.
사용자가 누른 결과이므로 이 이동은 CLS 로 계산되지 않는다.

### 4.4 "접기" 는 아이콘 레일이 아니라 완전히 숨기는 것이다

접힌 사이드바를 아이콘 레일로 만들려면 메뉴 항목마다 서로 구별되는 글리프가 필요하다 — 두 앱
합쳐 22개다. 그리고 "정산 관리"와 "수수료 설정"을 아이콘만으로 구별시키는 것은 텍스트 메뉴보다
나쁘다. 토글이 존재하는 이유는 **넓은 표에 가로 폭을 돌려주는 것**이고, 그 목적은 숨기는 쪽이
완전히 달성한다.

접기 상태는 localStorage 에 저장하지 않는다. 저장하면 첫 페인트 전에 값을 적용할 인라인 부트
스크립트가 또 하나 필요해지고(TASK-0018 4.1), 표시 밀도와 달리 **콘솔 셸은 정적으로 프리렌더되는
것이 콜드 스타트 대응의 전제**다(TASK-0101). 셸이 루트 레이아웃에 있으므로 상태는 클라이언트
네비게이션 사이에는 유지되고, 새로고침에서만 펼친 상태로 돌아온다.

### 4.5 상단바의 "페이지 제목" 과 `<h1>` 의 소유권

명세는 상단바에 페이지 제목을, 그리고 페이지 헤더에 제목을 요구한다. 그대로 만들면 `<h1>` 이
둘이거나 같은 문장이 두 번 나온다. 그래서 **역할을 갈랐다.**

| | 무엇 | 요소 | 출처 |
| --- | --- | --- | --- |
| 상단바 | **현재 위치** | `<p>` | 활성 **메뉴 항목의 라벨** — 셸이 경로에서 스스로 구한다 |
| 페이지 헤더 | **이 화면의 제목** | `<h1>` | 페이지가 넘긴다 |

셸은 F2(경로 강조) 때문에 어차피 활성 항목을 알고 있다. 그것을 그대로 쓰면 상단바 제목에
prop 배선이 없고, 라우트가 바뀌면 저절로 맞는다. 목록 화면에서 둘이 같은 문장이 되는 것은
정상이다 — 상세 화면에서 갈라진다(위치 "주문 관리", 제목 "주문 2026-0001").

**`<h1>` 을 페이지에 두는 것은 되돌릴 수 없는 제약이기도 하다.** 루트 레이아웃은 상세 화면의
주문 번호를 알 수 없고, TASK-0029 의 `/categories` 테스트는 페이지를 단독 렌더해
`heading level 1` 을 확인한다.

### 4.6 페이지 헤더 규약

```tsx
<PageHeader title="주문 관리" description="…" actions={<Button/>} filters={<OrderFilters/>} />
```

- 훅도 브라우저 API 도 쓰지 않는 **서버 렌더 가능** 컴포넌트다. 콘솔 화면의 LCP 요소는 대개 이 `<h1>` 이므로 클라이언트 경계 뒤로 넘기지 않는다
- `actions` 는 오른쪽 정렬, 좁은 화면에서 제목 아래로 내려간다
- `filters` 는 제목줄 아래 자기 영역을 갖는다. 여기 없으면 각 화면이 필터를 서로 다른 자리에 둔다

### 4.7 링크는 prop 으로 받는다

`packages/ui` 는 `next/link` 를 모른다(그래야 한다). 셸은 링크 **컴포넌트를 prop 으로** 받고
각 앱이 `next/link` 를 그대로 넘긴다. 드로어를 닫는 일은 셸이 `onClick` 으로 붙인다.

현재 경로도 같은 이유로 prop 이다. `usePathname()` 은 앱의 클라이언트 래퍼가 부른다.

### 4.8 활성 메뉴 판정

순수 함수다(`activeMenuItem`). 규칙 셋:

1. `/` 는 **완전 일치**일 때만 활성이다. 접두사로 보면 모든 경로가 대시보드를 켠다
2. 그 외는 `href` 와 같거나 `href + '/'` 로 시작하면 활성이다 — `/products/new` 가 `/products` 를 켠다 (F2)
3. 여러 개가 맞으면 **가장 긴 것**이 이긴다. 메뉴에 `/orders` 와 `/orders/returns` 가 함께 있어도 갈리지 않는다

### 4.9 메뉴 구성 — `docs/design/pages.md` 3장·2장 그대로

pages.md 의 경로표에서 **`/login` 과 상세·하위 경로를 뺀 나머지**가 사이드바다. 로그인은 콘솔
안 이동이 아니고, `/products/new` 나 `/orders/[id]` 는 섹션 안의 동작이다. 13개(admin) · 9개
(seller)를 한 줄로 세우면 읽히지 않으므로 절로 묶는다. 절 제목은 pages.md 에 없는 **이 TASK 의
분류**이며, 항목과 경로는 pages.md 가 유일한 출처다.

| 앱 | 절 | 항목 |
| --- | --- | --- |
| seller | (제목 없음) | 대시보드 `/` |
| | 판매 | 상품 관리 `/products` · 주문 관리 `/orders` · 취소·반품 `/claims` |
| | 고객 | 리뷰 관리 `/reviews` · 문의 관리 `/questions` |
| | 정산·설정 | 쿠폰 `/coupons` · 정산 내역 `/settlements` · 스토어 설정 `/settings` |
| admin | (제목 없음) | 대시보드 `/` |
| | 운영 | 회원 관리 `/users` · 판매자 관리 `/sellers` · 상품 관리 `/products` · 주문 관리 `/orders` · 클레임 관리 `/claims` · 신고 처리 `/reports` |
| | 카탈로그 | 카테고리 관리 `/categories` · 속성 관리 `/attributes` |
| | 정산·프로모션 | 수수료 설정 `/commissions` · 정산 관리 `/settlements` · 플랫폼 쿠폰 `/coupons` |
| | 시스템 | 데모 계정 관리 `/demo` |

### 4.10 목적지 스텁을 함께 만든다

TASK-0018 4.5 와 같은 이유다 — 누를 수 있는 것은 어딘가에 닿아야 하고, **F2(하위 경로 강조)와
F5(키보드 순회)는 실제 라우트 없이 잴 수 없다.** 메뉴가 가리키는 20개 경로에 공용
`PlaceholderScreen` 한 벌을 깐다(각 3줄). 화면 제목은 메뉴 정의에서 읽으므로 문구가 두 곳에
적히지 않는다. F2 를 브라우저에서 재기 위해 seller `/products/new` 하나를 더 둔다.

로딩·없음·오류 라우트 상태(P5)도 두 앱에 깐다. 콘솔에는 아직 하나도 없다.

### 4.11 알림 · 사용자 메뉴 "자리"

비활성 버튼으로 두지 않는다(TASK-0018 4.5). 각 앱이 상단바 슬롯에 **눌리는 팝오버**를 넘기고,
팝오버는 이 자리가 어느 마일스톤에서 채워지는지 한 줄로 말한다. 셸은 `ReactNode` 슬롯만 갖는다.

### 4.12 모바일 대응 범위

콘솔은 **데스크톱 퍼스트**다. 전 화면을 모바일에 최적화하지 않는다.

| 대상 | 수준 |
| --- | --- |
| seller 주문 목록 · 주문 상세 · 발송 처리 | **카드 변환 등 전용 레이아웃** (TASK-0060 에서 구현) |
| seller 나머지 · admin 전체 | 가로 스크롤. 레이아웃이 깨지지만 않으면 통과 |

판매자가 폰으로 주문을 확인하고 발송 처리하는 것은 실제 패턴이다(쿠팡 윙 앱). 반면 관리자
대시보드를 폰으로 보는 경우는 드물고, 관리 화면 30여 개를 전부 카드 변환하는 비용은 얻는 것에
비해 크다.

**이 TASK 가 지는 몫은 셸까지다.** 셸은 360px 에서 가로 넘침 0 이어야 하고(F3b), 그 위에 올라올
표의 카드 변환은 각 도메인 TASK 가 `TableToCards`(TASK-0016) 로 한다.

### 6.4 실측

측정 환경: 로컬 프로덕션 빌드, `PORT_OFFSET=60`, PostgreSQL·Meilisearch·API 기동 후, Chromium 141(Playwright 번들), Lighthouse 12 모바일 프로파일.

**27조합** — 9화면 × 3뷰포트. 콘솔은 밀도가 고정이므로 밀도 축이 없다(P6 해당 없음).

| 뷰포트 | 사이드바 | 본문 왼쪽 | 상단바 높이 | 가로 넘침 | 44px 미만 |
| --- | --- | --- | --- | --- | --- |
| 360 | 시트 (컬럼 없음) | 0 | 56 | 0 | 0 |
| 768 | 시트 (컬럼 없음) | 0 | 56 | 0 | 0 |
| 1440 | 컬럼 223 (패딩 포함 240) | 240 | 56 | 0 | 0 |

**사이드바가 나타나도 본문이 밀리지 않는가** — 4.3 의 주장을 재는 부분이다. JS 를 끈 렌더(= 서버가 보낸 것)와 하이드레이션 후를 비교했다.

| 앱 × 뷰포트 | 서버 `main` 왼쪽 | 하이드레이션 후 | 상단바 |
| --- | --- | --- | --- |
| 6조합 전부 | 0 / 0 / 240 | **같음** | 56 → 56 |

Lighthouse CLS 도 15회 전부 **0** 이다. 미디어 쿼리가 첫 페인트에 이미 자리를 비워 두므로, 사이드바가 하이드레이션에 붙어도 옮겨지는 것이 없다.

**토글** — 폭에 따라 하는 일이 다른 같은 버튼

| 폭 | 버튼 이름 | 누르면 |
| --- | --- | --- |
| 1440 · 1024 | 사이드바 접기 | `nav` 1→0, 본문 왼쪽 240→0 |
| 1023 · 768 · 360 | 메뉴 열기 | `dialog` 1개, `nav` 0→1, 포커스가 시트 안으로 |

**키보드 순회 (1440px)**

| 앱 | 탭 정지 | 순서 |
| --- | --- | --- |
| seller | 14 | 본문 바로가기 → 판매자 콘솔 → 메뉴 9 → 사이드바 접기 → 알림 → 내 계정 |
| admin | 18 | 본문 바로가기 → 관리자 콘솔 → 메뉴 13 → 사이드바 접기 → 알림 → 내 계정 |

사이드바가 DOM 에서 상단바보다 앞에 있으므로 토글에 닿으려면 메뉴를 지나야 한다. 본문 바로가기가 첫 정지인 이유가 이것이고, 실제로 `main#console-main` 으로 포커스가 옮겨가는 것을 확인했다.

**LCP 대조군 — 셸이 더한 값**

`/orders` 는 본문이 제목·설명·배지뿐이라 셸 비용만 남는다. 같은 화면을 **루트 레이아웃에서 셸을 걷어낸 빌드**(`<main>` 하나)로 다시 쟀다. 같은 서버, 같은 프로파일, 각 5회.

| | 스크립트 | LCP 중앙값 (5회) | CLS | 접근성 |
| --- | --- | --- | --- | --- |
| 셸 없음 (대조군) | 199,526B / 8개 | 1,811ms | 0 | 100 |
| 셸 적용 (`/orders`) | 202,077B / 7개 | **1,804ms** | 0 | 100 |
| 차이 | **+2,551B (+1.3%)** | **−7ms** | – | – |

회차별 LCP — 대조군 1,806 / 1,806 / 1,811 / 1,811 / 2,366ms · 셸 1,804 / 1,804 / 1,804 / 1,804 / 2,359ms. 두 분포가 겹친다.

**셸은 LCP 에 값을 더하지 않았다.** shop 셸이 +104KB · +379ms 였던 것과 대비된다(TASK-0018 6.4). 이유는 두 가지다 — 콘솔에는 밀도 제공자·부트 스크립트·검색 폼이 없고, 셸이 얹는 클라이언트 코드가 Radix Dialog·Popover 와 셸 자신뿐이다. LCP 요소는 두 빌드 모두 `PageHeader` 의 설명 문단이고, 셸 쪽에서는 상단바 아래(top 118px)에 있을 뿐 같은 텍스트다.

**seller 셸 기준선 등록**

`apps/seller` 에는 셸 기준선이 없었다(TASK-0097 1장). 같은 방법으로 `/orders` 를 5회 재
**1,804ms** 를 등록했다.

| | 스크립트 | LCP 중앙값 (5회) | CLS | 접근성 |
| --- | --- | --- | --- | --- |
| seller `/orders` (셸 + 페이지 헤더) | 199,475B / 7개 | **1,804ms** | 0 | 100 |
| admin `/orders` (같은 것) | 202,077B / 7개 | 1,804ms | 0 | 100 |

두 콘솔이 같은 셸을 쓰므로 값이 겹치는 것이 정상이고, 그것 자체가 F1(같은 셸)의 또 다른 증거다.

**`/categories` 는 이번에 재지 않았다.** M04 가 아직 없어 API 가 세션 없이 401 을 응답하고,
화면이 오류 상태로 렌더된다 — TASK-0029 가 트리를 띄운 채 잰 2,557ms 와 비교할 수 있는
값이 나오지 않는다. 셸의 비용은 위 대조군이 이미 갈라 두었다.

**실제 브라우저에서만 드러난 것 하나.**

| 무엇 | 원인 | 조치 |
| --- | --- | --- |
| 시트를 Escape 로 닫으면 포커스가 `<body>` 로 사라진다 | 상단바 토글을 상태로만 연결하고 Radix Dialog 에 트리거를 주지 않았다. Radix 는 자기가 아는 트리거로만 포커스를 돌려준다 | 좁은 화면에서는 토글 자체를 `Drawer` 의 트리거로 만든다. `console-shell.spec.tsx` 가 이 케이스로 실패했다 |

여기에 더해 **소유권 밖 결함 하나**를 고쳤다. `Popover` 의 제목·닫기 줄이 `<header>` 였는데, 패널은 `<body>` 로 포털되고 모달이 아니라 뒤 페이지가 가려지지 않으므로 그 `<header>` 가 두 번째 `banner` 랜드마크가 된다. 상단바를 가진 앱에서 팝오버를 열면 axe 가 `landmark-no-duplicate-banner` · `landmark-unique` 를 올린다. `<div>` 로 바꿨다. `Modal` · `Drawer` 는 Radix 가 여는 동안 나머지를 `aria-hidden` 으로 덮으므로 해당되지 않는다.

**TASK-0029 `/categories` 는 깨지지 않았다.**

| 무엇 | 결과 |
| --- | --- |
| `pnpm --filter @shopping/admin test` | **144 통과** (기존 134 + 이번 셸 검증 10) |
| `categories-page.spec.tsx` · `categories-a11y.spec.tsx` | **한 줄도 바뀌지 않았다** |

바뀐 것은 `app/categories/page.tsx` 뿐이고, TASK-0029 가 남긴 "`<main>` 을 감싸고 제목을 지우면 된다"를 그대로 실행한 것이다 — `<main>` 은 `ConsoleShell` 이 갖고 제목은 `PageHeader` 다. `heading level 1` 을 확인하는 기존 단언이 그대로 통과한다.
