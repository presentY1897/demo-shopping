## 1. 목적

구매자 앱의 공통 레이아웃과 밀도 토글 UI 를 만든다. 이후 모든 shop 화면이 이 레이아웃 위에 올라간다.

## 2. 범위

### 포함
- 헤더: 로고, 카테고리 네비, 검색창 자리, 장바구니·마이페이지 아이콘 자리
- 푸터
- **밀도 토글 UI** — 3단계 선택, 현재 값 표시
- 모바일 네비게이션 (햄버거·바텀시트)
- 반응형 브레이크포인트 적용
- 확인용 임시 페이지 교체
- 로딩 표시 (라우트 전환)

### 제외
- 검색 기능 (M06) — 입력창 자리만
- 장바구니 개수 배지 (M07) — 자리만
- 로그인 상태 표시 (M04) — 자리만

## 3. 요구사항

- [x] 세 밀도 단계에서 헤더·푸터가 정상 표시된다
- [x] 360 / 768 / 1440px 에서 레이아웃이 깨지지 않는다

## 4. 설계

### 4.1 밀도 값의 저장 위치 — localStorage, 쿠키가 아니다

토글이 없었을 뿐 저장 장치는 TASK-0014 가 이미 만들어 두었다. `packages/ui/src/density/` 의
외부 스토어가 값을 `<html data-density>` 와 `localStorage['shopping.shop.density']` 두 곳에
쓰고, `<head>` 의 인라인 부트 스크립트가 **첫 페인트 전에** 저장값을 적용한다. 이 TASK 는
그 위에 UI 를 얹는다.

**쿠키를 쓰지 않는 이유가 이 결정의 핵심이다.**

| | localStorage | 쿠키 |
| --- | --- | --- |
| 첫 페인트 | 인라인 스크립트가 적용 → 깜빡임 없음 | 서버가 알고 렌더 → 깜빡임 없음 |
| 정적 렌더 | 유지된다 | **깨진다.** 쿠키를 읽는 페이지는 동적 렌더로 떨어진다 |
| CDN 캐시 | 한 벌 | 밀도별로 3벌, 또는 캐시 불가 |

`apps/shop` 의 홈은 TASK-0101 이 `force-dynamic` 에서 정적 프리렌더로 되돌린 페이지다. 콜드
스타트(최대 90초) 동안 사용자가 보는 것이 **정적으로 미리 만들어진 셸**이고, 서버가 깨어나는
동안 헤더·스켈레톤이 즉시 뜨는 것이 그 TASK 의 결론이었다. 밀도를 쿠키로 읽으면 그 페이지가
다시 요청 시점 렌더가 되어 **콜드 스타트 대응이 원상복구된다.** 표시 설정 하나를 위해 치를
값이 아니다.

로그인 사용자는 M04 에서 `UserPreference` 가 우선한다. `DensityProvider.serverDensity` 와
`onPersist` 시임이 이미 있으므로 이 TASK 는 시임을 그대로 두고 익명 경로만 완성한다.

### 4.2 토글의 형태 — 세그먼트 라디오그룹

3개 중 1개를 고르는 것은 라디오다. Radix RadioGroup 프리미티브를 쓰고 스타일만 직접 쓴다
(D-056). 그러면 두 가지가 공짜로 따라온다.

- **로빙 탭 인덱스** — 그룹 전체가 탭 정지 1개이고 화살표 키로 단계를 옮긴다. 헤더에 탭 정지
  3개를 추가하지 않는다
- 선택 상태가 `aria-checked` 로 노출되어 스크린 리더가 "3개 중 2번째, 선택됨" 을 읽는다

`packages/ui` 의 기존 `Radio` 는 동그란 폼 컨트롤이라 헤더의 세그먼트 컨트롤 모양이 나오지
않는다. 같은 프리미티브 위에 다른 표현을 얹은 별도 컴포넌트(`DensityToggle`)로 만들고
`@shopping/ui/layout` 진입점으로 내보낸다. **문구는 전부 prop 이다** — `packages/ui` 에는
한국어가 없다.

### 4.3 토글의 위치 — 데스크톱은 헤더에 펼치고, 모바일은 팝오버

간판 기능이므로 찾기 쉬운 자리에 둔다. 다만 360px 헤더에 3칸(3 × 44px = 132px)을 상시로
내줄 수 없다 — 로고 + 햄버거 + 장바구니 + 마이페이지만으로 이미 266px 다.

| 뷰포트 | 형태 |
| --- | --- |
| ~767 | 아이콘 버튼 1개 → 팝오버 안에 **라벨이 보이는** 3단계 |
| 768~ | 헤더에 세그먼트 3칸, 아이콘만 + 툴팁 |

두 경우 모두 같은 `DensityToggle` 이 팝오버 안/헤더 위에 놓인다. 모바일 드로어(햄버거) 안에도
같은 토글을 한 번 더 두지 않는다 — 상태를 가진 컨트롤이 화면에 둘이면 어느 쪽을 눌러도 다른
쪽이 갱신되어야 하고, 그 자리는 팝오버로 이미 있다.

### 4.4 모바일 · 데스크톱 분기는 뷰포트 훅으로 (D-055)

D-055 는 **두 컴포넌트를 모두 렌더하고 CSS 로 숨기지 말라**고 못박는다. DOM 과 접근성 트리가
두 벌이 되기 때문이다. 그래서 `useViewportBand()` 훅을 만들어 하나만 마운트한다.

밴드는 새로 정의하지 않고 **밀도 매트릭스의 3구간(`base` / `md` / `xl`)을 그대로 쓴다.**
`DENSITY_VIEWPORT_MIN_WIDTH` 가 이미 768 / 1280 을 갖고 있으므로 브레이크포인트가 두 곳에
적히지 않는다.

**대가는 하이드레이션 전 한 프레임이다.** 서버는 이 방문자의 화면 폭을 모르므로 모바일
퍼스트에 맞춰 `base` 로 렌더하고, 데스크톱 방문자는 하이드레이션 시점에 데스크톱 헤더로
바뀐다. 그래서 **두 형태의 헤더 높이를 같은 토큰으로 고정**한다 — 높이가 같으면 교체가
본문을 밀지 않으므로 CLS 가 0 이다. `useSyncExternalStore` 로 구독하므로 하이드레이션
불일치 경고도 나지 않는다.

### 4.5 헤더에 들어가는 것과, 그 링크가 갈 곳

| 자리 | 이번 TASK | 채우는 TASK |
| --- | --- | --- |
| 로고 → `/` | 실제 링크 | – |
| 카테고리 네비 | 고정 6개(패션), 문구는 카탈로그 | TASK-0042 가 API 로 대체 |
| 검색 | `GET /search` 로 제출되는 실제 폼 | TASK-0041 |
| 밀도 토글 | **완성** | – |
| 장바구니 · 마이페이지 | 링크(배지·로그인 상태 없음) | TASK-0045 · M04 |

**목적지 스텁 4개를 함께 만든다** (`/search` · `/categories/[slug]` · `/cart` · `/mypage`).
비활성 컨트롤이나 404 로 끝나는 링크로 두지 않는 이유가 두 가지다.

1. P4(키보드 순회)와 데모에서 죽은 컨트롤은 둘 다 나쁘다. 누를 수 있는 것은 어딘가에 닿아야 한다
2. **범위에 있는 "라우트 전환 로딩" 을 검증하려면 실제 라우트가 최소 2개 필요하다**

스텁은 공용 `PlaceholderScreen` 한 벌이고 각 화면은 12줄 남짓이다. 해당 마일스톤 TASK 가
파일을 그대로 대체한다.

### 4.6 라우트 전환 로딩은 두 겹

- `app/loading.tsx` — 세그먼트 서스펜스 폴백. 새 화면 자리에 스켈레톤이 뜬다
- 링크 자신의 진행 표시 — Next 16 의 `useLinkStatus()` 로 **누른 링크 안에** 표시를 낸다

스켈레톤만 있으면 "눌리긴 한 건가" 를 누른 자리에서 확인할 수 없다. 반대로 링크 표시만 있으면
새 화면이 언제 오는지 모른다. 둘 다 둔다.

### 4.7 첫 방문 안내 (R1 대응)

저장된 밀도 값이 **없을 때만** — 즉 한 번도 바꾼 적이 없는 방문자에게만 — 토글 옆에 한 줄
안내를 띄운다. 닫거나 밀도를 한 번이라도 바꾸면 다시 뜨지 않는다.

서버 렌더에는 넣지 않고 마운트 뒤에 붙인다. 서버는 localStorage 를 볼 수 없어 안내를 띄울지
말지 판단할 수 없고, 추측해서 렌더하면 하이드레이션 불일치가 된다. 헤더 아래에 겹쳐 띄우므로
레이아웃을 밀지 않는다.

### 4.8 홈은 "밀도가 눈에 보이는" 임시 화면으로 바꾼다

F5 는 밀도 3 × 뷰포트 3 = 9조합에서 깨짐이 없음을 요구하는데, 확인하려면 밀도에 반응하는
내용물이 있어야 한다. `Grid columns="density"` 위에 자리 카드 6장을 올린 미리보기 절을 둔다.
실제 상품 카드는 TASK-0040, 홈 화면 자체는 TASK-0044 가 만든다.

**TASK-0101 의 콜드 스타트 장치(`ApiWakeGate`)는 그대로 홈 본문에 남는다.** 새 레이아웃은 그
바깥을 감쌀 뿐이고, 기존 테스트 6개 파일이 그대로 통과하는 것으로 확인한다.

CLS 는 Lighthouse 기준 홈 0, `/cart` 0 이다.

**Lighthouse 모바일** — 화면마다 5회, 중앙값

| 화면 | 성능 | 접근성 | FCP | LCP | TBT | CLS | 스크립트 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `/cart` (셸 + 최소 본문) | 98 | 100 | 754ms | **2,036ms** | 29ms | 0 | 301,897B / 10개 |
| `/` (홈) | 96 | 100 | 755ms | **2,707ms** | 25ms | 0 | 301,897B / 10개 |

회차별 LCP — `/cart` 1,804 / 1,845 / 2,036 / 2,364 / 2,371ms · 홈 1,956 / 2,420 / 2,707 / 2,707 / 2,784ms.

**LCP 대조군 — 셸이 더한 값**

`/cart` 는 본문이 제목 한 줄과 문단 하나뿐이라 셸 비용만 남는다. 같은 화면을 루트 레이아웃에서 헤더·푸터·밀도 제공자·본문 바로가기를 걷어낸 빌드로 다시 쟀다(같은 서버, 같은 프로파일, 5회).

| | 스크립트 | LCP 중앙값 (5회) |
| --- | --- | --- |
| 셸 없음 (대조군) | 197,562B / 8개 | 1,657ms |
| 셸 적용 (`/cart`) | 301,897B / 10개 | 2,036ms |
| 차이 | **+104,335B · +2개** | **+379ms** |
| 셸 + 홈 본문 (`/`) | 301,897B / 10개 | 2,707ms |

**셸 자체는 게이트를 넘지 않는다** — 셸이 더한 379ms 를 얹고도 `/cart` 는 2,036ms 로 2.5s 안이고, 5회 중 최댓값(2,371ms)도 그렇다. 목표를 넘긴 것은 홈뿐이고, 홈은 셸과 스크립트 양이 완전히 같으므로 그 671ms 차이는 **번들이 아니라 홈 본문의 렌더 비용**이다.

그렇다면 남은 값이 무엇인지가 P1 을 어디에 둘지 정한다. 홈의 LCP 분해는 **TTFB 452ms(16%) · Render Delay 2,332ms(84%)** 이고, LCP 요소는 미리보기 설명 문단 — 이미지도, 폰트도, 늦게 오는 데이터도 아닌 **서버가 이미 보낸 텍스트**다. 즉 늦는 것은 받아오는 일이 아니라 **메인 스레드가 스크립트를 파싱하느라 그릴 차례가 오지 않는 것**이고, Lighthouse 도 같은 답을 준다 — `unused-javascript` **131KiB, LCP 절감 추정 700ms**. 렌더 블로킹 리소스는 150ms 뿐이다.

이것은 admin 이 이미 부딪힌 것과 같은 형태다(TASK-0029 6.4 — TTFB 453ms · Render Delay 2,106ms, 스크립트 276KB, LCP 2,557ms). 거기서 내린 결론이 여기에도 그대로 적용된다: **미달을 충족으로 적지 않되, 화면을 하나 더 잘 만든다고 없어지는 값도 아니다.** 그래서 P1 을 `[-]` 로 두고 위 실측을 [TASK-0097 성능 최적화 · 측정](../M15-polish/TASK-0097-performance.md) 의 기준선으로 남긴다. 홈 본문 자체도 이 TASK 의 임시 화면이라 **TASK-0044 가 통째로 대체**한다.

`[ ]` 로 두지 않는 이유는 admin 때와 같다 — 셸의 고정 비용이 내려가기 전까지 shop 의 어떤 화면도 완료될 수 없게 되고, 그것은 이 TASK 가 만든 문제가 아니다.

**실제 브라우저에서만 드러난 것 세 가지** — 전부 고쳤고, 세 개 모두 jsdom 테스트로는 잡히지 않는 종류였다.

| 무엇 | 원인 | 조치 |
| --- | --- | --- |
| 360 × 미니멀에서 가로 20px 넘침 | 밀도 1 의 모바일 간격 단위가 5px 라 `control-md` 버튼이 55px 가 된다 | 헤더 아이콘 컨트롤을 `control-sm`, 간격을 `gap-1` 로 |
| 화살표 키가 밀도를 바꾸지 않음 | Radix 의 선택 로직이 `document` 키다운 플래그를 읽는데, React 19 루트가 document 에 붙어 있어 로빙 포커스가 먼저 움직인다 | `:focus-visible` 로 키보드 포커스를 판별해 직접 선택 |
| 홈 CLS 0.099 | 콜드 스타트 패널이 응답을 받아 채워지며 아래 섹션을 밀었다 | 패널을 미리보기 아래로 이동. 재측정 5회 전부 **CLS 0** (LCP 는 위 P1 참조 — 이동으로 없어지는 값이 아니었다) |

**TASK-0101 콜드 스타트 장치** — `components/{api-wake-gate,wake-waiting,wake-failure,search-readiness,health-panel}.tsx` 와 `lib/{wake,use-api-wake,wake-policy}.ts`, 그리고 그 테스트 파일들은 **한 줄도 바뀌지 않았다**(`git diff main..` 에 없다). 새 셸은 바깥을 감쌀 뿐이고 패널은 홈 본문에 그대로 있다.
