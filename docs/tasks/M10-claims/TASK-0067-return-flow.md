## 1. 목적

배송 후 반품을 구현한다. 수거·검수 단계를 포함해 실제 서비스와 같은 흐름을 만든다.

## 2. 범위

### 포함
- 구매자 반품 신청 (항목·수량·사유·사진 첨부)
- 귀책 구분 — 단순 변심 / 상품 하자 / 오배송
- 판매자 승인·거절
- 수거 처리 (가상 회수 운송장)
- 입고 검수 — 합격/불합격
- 검수 합격 시 환불 + 재고 복원
- 검수 불합격 시 반송 처리
- 귀책에 따른 반품 배송비 부담 결정
- 반품 진행 상태 조회

### 제외
- 교환 (구현하지 않음)
- 환불 계산 로직 (TASK-0068)

## 3. 요구사항

- [x] 항목·수량을 골라 반품할 수 있다
- [x] 하자 반품은 사진을 첨부할 수 있다
- [x] 수거·검수 단계가 상태로 추적된다
- [x] 검수 합격 시에만 환불된다
- [x] 귀책에 따라 반품 배송비 부담자가 달라진다

## 4. 설계

```
반품신청 → 판매자 승인 → 수거중(가상) → 입고검수 ─합격→ 환불 + 재고 복원
                    └거절                        └불합격→ 반송
```

| 귀책 | 반품 배송비 | 원 배송비 |
| --- | --- | --- |
| 단순 변심 | 구매자 부담 (환불액에서 차감) | 환불 안 함 |
| 상품 하자 | 판매자 부담 | 환불 |
| 오배송 | 판매자 부담 | 환불 |

**검수 단계를 두는 이유**: 반품 상품이 실제로 도착하고 상태가 확인돼야 환불한다. 이게 없으면 물건을 안 보내고 환불받는 게 가능해진다. 실제 커머스가 검수를 거치는 이유이기도 하다.

**교환을 만들지 않는 이유**(D-027): 회수+재배송+재고 2회 이동+차액 정산이 엮여 상태 머신이 두 배가 된다. 반품 후 재구매로 안내한다.

### 4.1 문서가 정한 것과 **우리가 정한 것**을 갈랐다

귀책별 **부담자**는 `pricing.md` 4장에 있어 그대로 따랐다. 문서에 없는 것은 반품 배송비의
**금액**이었고, 후보 셋 중 **`Seller.shippingFee` 스냅샷**을 골랐다.

`SellerOrder.shippingFee` 는 무료배송이면 0 이라 **무료배송 주문의 변심 반품이 공짜**가
된다 — 회수 운송은 무료배송 조건과 무관하다. 새 상수는 판매자별 값을 플랫폼이 대신 정하는
일이다.

**「귀책 셋이 각각 다른 부담자」는 문서상 성립하지 않는다.** 하자와 오배송은 둘 다 판매자
부담이다. 그래도 값을 셋으로 유지한 것은 **하나는 물건의 문제, 하나는 이행의 실수**라
분쟁·정산·통계가 다투는 사실이 다르기 때문이고, 두 값짜리 `ClaimFault` 는 그 셋에서
**파생**시킨다 — 요청이 `fault` 를 주장하면 「오배송인데 구매자 귀책」이 만들어진다.

### 4.2 회수는 **표를 갈랐고 번호 발급기는 함께 쓴다**

같이 못 쓰는 이유가 셋이다. `Shipment.sellerOrderId` 가 유니크이고(풀면 「이 주문은 배송
중인가」의 답이 여러 개가 된다), `SellerOrder.trackingNumber` 사본과 복합 외래키가 **몫당
배송 1건**을 전제하며, `TrackingEventSource` 가 `CARRIER | SELLER` 뿐인데 **회수의 집화는
구매자에게서** 일어난다 — 그대로 쓰면 이력에 「판매자로부터 인수했어요」가 남는다.

같이 쓰는 것은 번호 생성과 DB CHECK 다(글자까지 같은 조건). 「진짜 운송장과 구분된다」는
성질은 **물건이 가는 방향과 무관**하다.

회수에는 추적 사건표를 두지 않았고 진행은 클레임 상태가 말한다. `ReturnShipment` 에
`status` 를 두면 두 표가 같은 순간에 다른 말을 한다.

### 4.3 사진은 **요구하거나 금지한다** — 「선택」이 없다

하자·오배송은 1~5장 **필수**, 단순 변심은 **첨부 금지**다.

앞의 둘은 판매자에게 **돈을 물리는 주장**이라 근거가 없으면 판매자가 할 수 있는 일이 전부
거절뿐이다. 뒤엣것은 뒤집을 것이 없어 받아 두면 **아무도 안 보는 이미지와 지우지 못하는
개인정보**만 쌓인다.

열쇠는 `returns/{userId}/{objectId}.{ext}` 이고 접두어가 **올린 사람**이다 — 사진이
신청서보다 먼저 올라가므로 클레임 id 를 가리킬 수 없고, 열쇠 하나로 소유자를 말할 수 있어야
「남의 사진을 내 신청서에」를 조회 없이 막는다.

**상한을 계약이 아니라 규칙이 갖는다.** zod 에 `.max()` 를 두면 여섯 번째 장이 스키마에서
먼저 죽어 `RETURN_PHOTO_TOO_MANY` 가 **영영 나가지 못한다** — 코드도 문장도 만들어 놓고
아무도 못 받는다. `quantity` 의 하한을 계약에 두지 않은 것과 같은 이유다(TASK-0065 4.3).

### 4.4 구매자에게 업로드 권한이 없었다

`BUYER` 에게 `media.upload` 가 없고 키 빌더가 판매자용 하나뿐이라, **사진 첨부가 반쪽**이었다.
`media.upload:own` 을 열고 목적별 빌더를 하나 더 뒀다 — 그 파일의 주석이 이미 답을 적어
두었다: 「접두어와 그것을 승인하는 주인이 함께 간다」.

반품 사진 요청에는 **소유자 칸이 아예 없다.** 주인은 토큰이 정한다 — 없는 칸은 막을 필요가
없다.
