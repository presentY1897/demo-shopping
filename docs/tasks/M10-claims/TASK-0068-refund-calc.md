## 1. 목적

부분 취소·반품 시 환불액을 정확히 계산하고 결제 프로바이더로 실행한다. **`docs/design/pricing.md` 3장이 이 코드의 명세다.**

## 2. 범위

### 포함
- 환불액 계산 — 항목 저장된 안분액 기반 (재계산하지 않음)
- 배송비 환불 규칙 (전체/부분, 귀책별)
- 프로바이더 부분 취소·환불 호출 (가상 카드 / 토스)
- `Refund` 기록, 누적 취소액 갱신
- 환불 실패 시 재시도·수동 처리 경로
- 여러 번의 부분 환불 누계 검증
- 환불 완료 알림 이벤트 자리

### 제외
- 쿠폰·적립금 복구 (M11 에서 이 로직에 연결)
- 정산 차감 (M12)

## 3. 요구사항

- [x] 환불액이 주문 시 저장된 안분액을 기반으로 계산된다
- [x] 부분 환불을 여러 번 해도 누계가 실결제금액을 넘지 않는다
- [x] 전량 취소 시 환불 합계가 실결제금액과 정확히 일치한다
- [x] 배송비 규칙이 정확히 적용된다
- [x] 환불 실패가 감지되고 재시도된다

## 4. 설계

```
환불액 = Σ(항목 상품금액 − 항목 쿠폰안분액 − 항목 적립금안분액) + 배송비 조정
```

**저장된 안분액을 쓰는 이유**: 환불 시점에 재계산하면 그 사이 쿠폰 정책이 바뀌었을 때 값이 달라진다. 주문 시점의 계산 결과가 진실이다.

| 상황 | 배송비 |
| --- | --- |
| 판매자 항목 전체 취소 | 전액 환불 |
| 부분 취소 후 무료배송 조건 미달 | 배송비 재부과 (환불액에서 차감) |
| 판매자 귀책 반품 | 배송비·반품비 판매자 부담 |
| 단순 변심 반품 | 반품 배송비 차감 |

### 4.1 항목의 몫을 **누적으로** 센다 — 1원이 사라지는 자리

한 항목을 여러 번 나눠 환불할 수 있다(3개 중 1개, 나중에 또 1개). 그때마다 「이번
몫」을 따로 반올림하면 **합계가 원래 금액과 어긋난다.**

```
10,000원짜리 3개를 하나씩 세 번:  floor(10000/3) × 3 = 9,999   ← 1원이 사라진다
```

그 1원은 아무 데도 가지 않고 **전량 환불한 사람의 장부에 남는다.** 그리고 빨간
테스트로 나타나지 않는다.

그래서 매번 **처음부터 다시 센다** — 「지금까지 n개」의 누적액에서 「지금까지 n−k개」를
뺀 것이 이번 몫이다. 마지막 환불이 잔여를 자동으로 가져가고, 전량 환불의 합계가
`lineNetAmount` 와 **정확히** 같아진다. `pricing.md` 1장의 「원 단위 잔여를 버리지
않는다」를 **시간 축에 적용한 것**이고, 항목 사이의 안분이 「마지막 항목에 잔여를 몰아」
합계를 지키는 것과 같은 장치다.

**검사가 그것을 전수로 증명한다** — 수량 2~12 × 순액 7가지 × **모든 순서 분할**
(4,094가지). 그리고 「따로 floor 한 계산」을 스펙 안에서 흉내 내 **실제로 다른 값이
나오는 것**을 단언한다. 그것이 없으면 이 구현이 왜 누적인지가 코드에만 남는다.

### 4.2 배송비도 **차분으로** 접는다

계산을 쓰고 나서 발견한 것이다. `shippingAdjustment` 를 환불마다 한 번씩 부르면
**전량 취소의 합계가 실결제금액과 어긋난다.**

```
무료배송(0원)으로 산 3개를 하나씩 취소
  ① 재부과 −3,000   ② 0   ③ 전량이지만 낸 배송비가 0원이라 0
  → 3,000원이 사라진다
```

그래서 항목과 같은 장치를 쓴다: **이번 환불 뒤의 판정 − 이번 환불 전의 판정.** ③이
`0 − (−3,000) = +3,000` 이 되어 ①을 되돌리고, 재부과도 두 번 일어나지 않는다.

**그래서 승인 시점의 「전체인가」를 읽지 않는다.** 그것은 그때의 답이라, 실패한 환불이
며칠 뒤 재시도될 때 옛 답으로 배송비를 두 번 돌려준다. 차분이 접히려면 두 판정이 같은
사실(**환불 원장**)을 봐야 한다.

### 4.3 「이미 몇 개 환불했나」는 **매번 원장에서 센다**

캐시 컬럼을 두지 않았다. `claimedQuantity` 캐시가 있는 이유는 초과 **신청**을 조건부
갱신 한 문장으로 접으려는 것인데, 환불에서 그 자리를 지키는 것은 이 수가 아니라
`Payment.canceledAmount` 와 그 CHECK 이고 판단과 쓰기가 이미 결제 행 잠금 아래 한
곳이다. **이 수는 입장 심사가 아니라 회계 입력이다.**

그리고 **틀렸을 때 조용한 쪽이 캐시다** — 1 어긋나면 환불액이 1원 어긋나고 아무 검사도
안 잡는다. 원장을 세면 「어긋난다」는 상태 자체가 없다.

### 4.4 멱등은 **세 겹**이다

| 겹 | 막는 것 |
| --- | --- |
| 클레임 상태를 잠그고 확인 | 같은 클레임 재호출 (`REFUNDED` 는 종착) |
| 환불 기록의 기본키 = 클레임 id | 두 번째 **기록**이 애초에 불가능 |
| 항목몫·프로바이더·`Refund`·누계·전이가 **한 트랜잭션** | 「돈은 나갔는데 안 적혔다」가 없으므로 위 둘이 거짓말하지 않는다 |

`PaymentService.refund` 를 새로 만들지 않고 **트랜잭션 본체를 갈랐다** — 기존 환불과
클레임 환불이 같은 코드를 지나므로 프로바이더 호출·기록·누계·전이가 여전히 한 곳이다.
그때 트랜잭션 마감을 16초로 늘렸다: Prisma 기본이 5초인데 결제사 왕복이 15초라, 그대로
두면 **「돈은 나갔는데 기록이 롤백된」** 상태가 난다.
