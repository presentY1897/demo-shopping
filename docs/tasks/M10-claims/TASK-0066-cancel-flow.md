| 항목 | 내용 |

| 상태 | 완료 |

## 1. 목적

배송 전 취소를 구현한다. 부분 취소를 포함하고, 취소된 만큼 결제가 부분 환불된다.

## 2. 범위

### 포함
- 구매자 취소 신청 화면 (항목·수량 선택, 사유 입력)
- 신청 → 승인 → 환불 → 완료 흐름
- **결제완료(PAID) 상태는 자동 승인** — 판매자가 아직 준비 안 함
- 상품준비중(PREPARING)은 판매자 승인 필요
- 취소 완료 시 재고 복원 트리거 (TASK-0069)
- 환불 실행 트리거 (TASK-0068)
- 전체 취소 시 SellerOrder CANCELED 전환
- 부분 취소 시 남은 항목 기준 상태 유지
- 취소 불가 안내 (이미 발송 등)

### 제외
- 반품 (TASK-0067)
- 환불 계산 로직 자체 (TASK-0068)

## 3. 요구사항

- [x] 항목·수량을 골라 취소할 수 있다
- [x] 결제완료 상태의 취소는 즉시 처리된다
- [x] 준비중 상태는 판매자 승인 후 처리된다
- [x] 전체 취소하면 주문 묶음이 취소 상태가 된다
- [x] 부분 취소 후 남은 항목은 계속 진행된다

## 4. 설계

```
PAID       → 취소 신청 → 자동 승인 → 환불 → 재고 복원 → 완료
PREPARING  → 취소 신청 → 판매자 승인/거절 → (승인 시) 환불 → 재고 복원 → 완료
```

**결제완료 상태를 자동 승인하는 이유**: 판매자가 아직 아무것도 하지 않았다. 승인을 기다리게 하면 구매자가 불필요하게 대기하고, 판매자에게도 의미 없는 업무가 생긴다.

판매자가 이미 발송했는데 취소 요청이 들어오면 **거절 후 반품으로 안내**한다.

### 4.1 「전체 취소」는 **이 승인 뒤에 남은 잔여가 0** 이다

후보가 셋이었다 — 항목 수 / 이번 신청의 수량 합 / **잔여**. 앞의 둘은 「이번 신청」만
보므로, 세 개를 **하나씩 세 번 나눠** 취소하면 어느 신청도 「전체」가 아니다. 그러면
**보낼 물건이 하나도 없는 주문이 「상품 준비중」으로 영원히 남고, 아무것도 실패하지
않는다.** 부분 취소를 여러 번 하는 것이 이 도메인의 정상 흐름(D-027)이라 그 경로가 곧
정상 경로다.

세는 대상은 **확정된 취소만**이다(`CANCEL_APPROVED`·`REFUNDED`). `claimedQuantity`
캐시를 쓰면 **아직 승인 안 된 신청**이 주문을 `CANCELED` 로 닫고, 전이표에 거기서
돌아오는 화살표가 없다.

### 4.2 전이표에 `SYSTEM` 을 열었다

`PAID`·`PREPARING → CANCELED` 의 주체가 `['SELLER','ADMIN']` 이었다. 그 표는 M10 보다
먼저 쓰였고 막으려던 것은 **구매자**였는데, 자동 승인이라는 주체를 예상하지 못했다.

없는 동안 자동 승인은 `SYSTEM` 을 `SELLER` 로 접어 넣었고, 그것은 주문 이력에
**「판매자가 취소했다」는 거짓**을 남기는 모양이었다. 이 TASK 의 승인된 범위가 「결제완료
상태는 자동 승인」이고 그 주체는 사람이 아니므로, 표를 그 요구사항에 맞췄다 — 접던 함수는
사라졌다.

### 4.3 신청 화면은 **라우트**다

`pages.md` 가 이미 `/mypage/orders/[id]/claim` 을 적어 뒀고 문서가 기준이다. 덧붙여
① 폼이 길어 360px·맥시멀에서 다이얼로그면 **스크롤 안의 스크롤**이 되고, ② 「배송이
시작되어 취소할 수 없다」는 **앉아서 읽고 다음 할 일을 정하는 문장**이라 띄웠다 닫는
자리가 아니며, ③ 주소가 남아 새로고침·문의에 쓸 수 있다.

신청 단위가 판매자 몫이라 묶음은 `?bundle=` 이 나른다(경로에 자리가 없다).
