# TASK-0069: 재고 복원

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M10 취소·반품·환불 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/stock-restore` |
| 선행 작업 | TASK-0066, TASK-0067 |

## 1. 목적

취소·반품된 수량만큼 재고를 되돌린다. 원장(TASK-0036)을 통해서만 처리한다.

## 2. 범위

### 포함
- 취소 완료 시 재고 복원 (원장 CANCEL 기록)
- 반품 검수 합격 시 재고 복원 (원장 RETURN_IN 기록)
- 검수 불합격 시 복원하지 않음
- 판매 종료·삭제된 Variant 의 복원 처리
- 복원 멱등 처리 (같은 클레임으로 두 번 복원 금지)
- 재고 복원 시 판매자 알림 이벤트 자리
- 정합성 검증

## 3. 요구사항

- [x] 취소·반품 완료 시 재고가 정확히 복원된다
- [x] 검수 불합격은 복원되지 않는다
- [x] 같은 클레임으로 두 번 복원되지 않는다
- [x] 삭제된 Variant 도 처리가 실패하지 않는다
- [x] 복원 후 원장 합계와 재고가 일치한다

## 4. 설계

```
취소 완료  → adjustStock(type=CANCEL,    +수량, refType=CLAIM, refId=claimId)
반품 합격  → adjustStock(type=RETURN_IN, +수량, refType=CLAIM, refId=claimId)
반품 불합격 → 복원 없음
```

**멱등 처리**: `(refType, refId, variantId)` 조합으로 이미 기록된 원장이 있으면 건너뛴다. 환불 재시도나 이벤트 중복 시 재고가 부풀지 않아야 한다.

**삭제된 Variant**: 데모 판매자가 만료돼 상품이 사라졌을 수 있다(TASK-0025). 이 경우 복원을 건너뛰되 로그를 남긴다. 클레임 처리 자체는 실패하지 않아야 한다.

### 4.1 멱등 열쇠의 `refId` 는 클레임이 아니라 **클레임 항목**이다

문서는 `(refType, refId, variantId)` 를 열쇠로 적었고, `StockLedger` 에 **이미 그 유니크
인덱스가 있다**(TASK-0036). 새로 만들 것이 없었고, 정한 것은 **`refId` 에 무엇을 넣는가**다.

클레임 id 를 넣으면 **한 클레임에 같은 조합이 항목 둘로 들어온 날 둘째 줄이 조용히
삼켜진다.** 지금 그런 주문이 안 생기는 것은 장바구니가 같은 조합을 합쳐 주기 때문이지
**주문 표의 약속이 아니다** — `OrderItem` 에 `(sellerOrderId, variantId)` 유니크가 없다.

항목 id 를 넣으면 두 줄이 서로 다른 원장 행이 되어 둘 다 돌아온다. **막는 것이 「같은
클레임을 두 번」이지 「같은 클레임의 두 줄」이 아니라는 것**이 이 선택의 전부다.

겹은 둘이다 — 클레임 행 잠금(앞)과 인덱스(마지막 방어선). **음성 대조로 확인했다**:
잠금을 빼면 동시 4건 중 3건이 유니크 위반으로 실패하지만 **재고는 여전히 한 번만 는다.**
잠금은 **답**을 지키고 인덱스는 **데이터**를 지킨다 (TASK-0065 4.1 과 같은 결론).

### 4.2 「사라진 조합」은 **소프트 삭제**이지 `isActive` 가 아니다

하드 삭제는 애초에 불가능하다 — `OrderItem.variantId` 와 `StockLedger.variantId` 가 둘 다
`RESTRICT` 라 팔린 조합의 행은 남는다. 그래서 판정은 `deletedAt` 이고, 데모 정리와 판매자
상품 삭제가 둘 다 그것을 찍는다.

**`isActive` 를 쓰지 않은 것이 중요하다.** 그것만 꺼진 것은 「지금은 이 조합을 안 판다」이고
**되살아날 수 있다** — 그때 안 되돌려 둔 재고는 되돌릴 방법이 없다. 검사가 그 구분을 잰다.

건너뛴 줄은 원장에 아무것도 남기지 않으므로 **경고 로그가 유일한 흔적**이고, 검사가 그
로그를 실제로 잡는다.

### 6.4 범위 중 하지 않은 것

**「재고 복원 시 판매자 알림 이벤트 자리」(2장)를 만들지 않았다.** 받는 쪽이 없는 포트를 하나
더 만들면 **바인딩되지 않는 죽은 코드**가 된다 — 환불·구매확정의 포트들은 받는 TASK 가
정해져 있어서(M11·M12) 그 자리가 뜻을 갖지만, 재고 복원 알림은 그 대상이 아직 없다. 지금
그 자리에 해당하는 것은 경고 로그 하나이고, M13(알림)이 그 목록을 정할 때 함께 붙는다.

**복원 실패의 재시도 배치도 없다.** 환불에는 있지만(TASK-0068) 재고에는 없어, 실패한
복원을 **다시 부르는 사람이 없다.** 발견은 `reconcile()` 과 로그에 기대고 있고, 그 둘을
읽는 배치가 필요하다 — HANDOFF 2절로 넘겼다.
