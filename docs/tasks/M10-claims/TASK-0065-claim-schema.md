## 1. 목적

취소와 반품을 하나의 클레임 모델로 다룬다. **항목·수량 단위 신청**을 스키마가 지원하게 한다.

## 2. 범위

### 포함
- `ClaimRequest` — SellerOrder, 유형(CANCEL/RETURN), 상태, 사유, 귀책(고객/판매자), 신청자
- `ClaimItem` — 대상 OrderItem, 수량, 계산된 환불액
- 클레임 상태 머신 (취소 경로 / 반품 경로)
- 신청 가능 여부 판정 — 주문 상태·기간·이미 신청된 수량 확인
- 상태 이력 기록
- 항목별 잔여 신청 가능 수량 계산

### 제외
- 실제 취소·반품 처리 (TASK-0066, 0067)
- 환불 실행 (TASK-0068)

## 3. 요구사항

- [x] 주문 항목 3개 중 1개만, 그 중 일부 수량만 신청할 수 있다
- [x] 이미 신청한 수량만큼은 다시 신청할 수 없다
- [x] 주문 상태에 따라 취소·반품 경로가 자동으로 갈린다
- [x] 정의되지 않은 상태 전이는 거부된다
- [x] 구매확정 후에는 일반 반품이 불가능하다

## 4. 설계

상태 정의는 `docs/design/state-machines.md` 4장을 따른다.

| 주문 상태 | 가능한 클레임 |
| --- | --- |
| PAID / PREPARING | 취소 |
| SHIPPED | 취소 불가 (배송중), 도착 후 반품 |
| DELIVERED | 반품 (기간 내) |
| CONFIRMED | 일반 반품 불가, 관리자 개입만 |

```
잔여 신청 가능 수량 = OrderItem.quantity − 이미 신청·처리된 수량 합계
```

**항목 단위로 설계하는 이유**: 주문 항목 3개 중 1개만 취소하는 건 정상 흐름이다. 주문 단위로만 만들면 실제 서비스로 쓸 수 없다.

### 4.1 잔여 수량은 **조건부 갱신**으로 잡는다 (R1)

선례가 둘이었고 갈린 기준은 **「판단이 그 행 안에서 끝나는가」**다.

| 선례 | 판단이 보는 것 | 모양 |
| --- | --- | --- |
| `PaymentService.lock()` | 행 밖 — 프로바이더 응답·상태 머신 | 잠그고 읽고 판단하고 쓴다 |
| `ReservationService.reserve()` | **한 행의 두 컬럼** (`stock - reserved >= q`) | 한 문장 |

잔여 수량은 뒤쪽이다. 그래서 `OrderItem.claimedQuantity` 를 두고(`ProductVariant.reserved`
와 같은 성질 — 살아 있는 클레임 합계의 캐시) 잡는 일 전체를 한 문장으로 접었다.

```sql
UPDATE "OrderItem" SET "claimedQuantity" = "claimedQuantity" + $q
 WHERE "id" = $id AND "quantity" - "claimedQuantity" >= $q
```

0행이면 진 것이고, 그때 다시 읽어 **지금의** 잔여를 답한다 — 조건부 갱신은 앞사람의
커밋을 기다렸다가 조건을 다시 보므로 그 값이 낡지 않는다. 한 신청에 항목이 여럿이면
**항목 id 순서로** 잡아 데드락을 막는다.

**마지막 방어선은 DB 다** — `OrderItem_claimedQuantity_check (0 <= claimedQuantity <= quantity)`.
잠금이 답이라도 제약이 없으면 그 잠금을 안 쓰는 코드가 하나 생기는 날 조용히 넘친다.

**두 층이 각각 다른 것을 지킨다는 것을 음성 대조로 확인했다**: 서비스의 `WHERE` 조건을
지우면 **초과는 여전히 막히지만**(CHECK 이 잡는다) 진 쪽이 409 대신 500 을 받아 「진 쪽에게
잔여를 알려 준다」가 깨진다.

### 4.2 반품 기간은 **구매확정과 같은 축**이다 (R2)

새 변수를 만들지 않고 `autoConfirmWindowMsOf(config)` 를 그대로 부른다 (`FULFILLMENT_PACE`).

값이 같아야 하는 이유가 있다 — 반품 기간이 **짧으면** 확정을 기다리는 동안 아무것도 못 하는
구간이 생기고, **길면** 확정된 주문에 반품을 받아야 하는데 `CONFIRMED` 가 이미 거절한다(F5).
검사가 `returnWindowEndsAt === autoConfirmAt` 을 단언해 두 값이 같은 축임을 못 박는다.

「배송완료 시각」은 배송 표가 아니라 **상태 이력의 첫 `DELIVERED` 줄**에서 읽는다 —
TASK-0064 4.1 과 같은 근거이고, 배송 행이 없는 몫으로 그것을 재는 검사가 있다.

### 4.3 수량의 하한을 **스키마에 걸지 않았다**

`quantity` 에 `min(1)` 을 걸면 「0개」가 zod 단계에서 400 이 되어 **거절의 순서가 뒤집힌다** —
배송 중인 주문에 0개를 신청하면 답이 「배송 중이라 안 됩니다」여야 하는데 「수량이
올바르지 않다」가 나가고, 사람은 수량을 고쳐 다시 시도한다.

하한은 `claimEligibility` 가 갖는다. **거절의 순서가 답의 우선순위**라는 규칙이 스키마
검증보다 위에 있다.

### 4.4 「신청자가 자기 클레임을 승인하지 못한다」의 방어선이 **둘**이다

첫째는 퍼미션이다 — 신청은 `order.write`(구매자가 가진 것), 전이는 `claim.handle`(구매자에게
없는 것). 둘째는 전이표이고, 어느 화살표에도 `BUYER` 가 없다.

**두 번째를 실제로 재려면 첫 번째를 통과한 사람이 필요하다.** 그래서 검사가 *다른 가게의
주인이면서 이 주문의 구매자*로 호출한다 — 가드는 지나고 전이표에서 거절된다.
