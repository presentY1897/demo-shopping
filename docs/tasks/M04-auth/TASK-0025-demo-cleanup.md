## 1. 목적

만료된 데모 계정과 그 계정이 만든 데이터를 자동 삭제한다. 공용 카탈로그와 다른 사용자의 데이터는 건드리지 않는다.

## 2. 범위

### 포함
- 만료 스케줄러 (주기 실행)
- 삭제 대상 정의와 순서 (외래키 역순)
- 공용 데이터 보호 규칙
- **주문에 포함된 상품은 스냅샷 덕분에 이력이 깨지지 않음을 검증**
- 관리자 화면용 강제 만료 API
- 정리 결과 로깅 + 헬스체크에 마지막 실행 시각 노출
- 만료 임박 알림 (남은 시간 1시간 이하 배너 강조)

### 제외
- 관리자 데모 관리 화면 (M14)

## 3. 요구사항

- [ ] 만료된 계정과 개인 데이터가 삭제된다
- [ ] 공용 카탈로그와 다른 사용자 데이터는 남는다
- [ ] 삭제 후에도 과거 주문 이력이 조회된다
- [ ] 스케줄러가 멈추면 헬스체크로 알 수 있다
- [ ] 정리 작업이 실패해도 다음 주기에 재시도된다

## 4. 설계

> **2026-09-05 구현 중 정정 — 상품은 하드 삭제할 수 없다. 스키마가 막는다.**
>
> 아래 표의 「주문에 포함된 적 없으면 삭제」는 성립하지 않는다. 이유는 주문이 아니라 **재고 원장**이다.
>
> | 무엇이 막나 | 어디서 |
> | --- | --- |
> | `StockLedger_append_only` 트리거가 원장 행의 UPDATE · DELETE 를 거부한다 | TASK-0036 마이그레이션 |
> | `StockLedger.variantId` → `ProductVariant` 가 `ON DELETE RESTRICT` 다 | 같은 곳 |
> | `StockLedger.actorId` → `User` 도 `RESTRICT` 다 | 같은 곳 |
>
> 모든 Variant 는 태어나면서 개시 `INBOUND` 를 하나 갖는다(TASK-0036 4.7). 즉 **원장 행이 없는
> Variant 는 없고**, 그 행이 Variant 를 잡고 있으므로 상품은 지워지지 않는다. 주문 이력이 있든
> 없든 마찬가지다. HANDOFF 3.6 이 이 사실을 미리 적어 뒀다.
>
> **그래서 상품은 언제나 소프트 삭제다** — `Product.deletedAt` · `ProductVariant.deletedAt` ·
> `ProductOption.deletedAt`. 목록과 상세가 이미 `deletedAt IS NULL` 로 거르므로 구매자에게는
> 사라진 것과 같다.
>
> **`User` 도 원래대로 소프트 삭제다.** 원장의 `actorId` 가 `RESTRICT` 라 조정을 한 번이라도 한
> 데모 판매자는 하드 삭제되지 않는다. 원래 설계가 이미 소프트 삭제였으므로 결정은 바뀌지 않고,
> **왜** 그래야 하는지에 이유가 하나 더 붙는다.

> **2026-09-05 — 아래 표의 절반은 아직 테이블이 없다.**
>
> 장바구니 · 위시리스트 · 최근본 · 알림(M07~M13), 주문 · 결제 · 정산(M07~M12), 리뷰 · 문의(M13),
> 가상 카드(M08) 중 무엇도 `schema.prisma` 에 없다. **이번에 지우는 것은 지금 존재하는 것뿐**이고,
> 나머지는 그 테이블을 만드는 TASK 가 정리 계획에 항목 하나를 더하는 방식으로 회수한다 —
> `DemoSeedService` 가 「페르소나별 시더 목록」으로 같은 회수 장치를 이미 쓴다.
>
> 그것을 잊지 않게 하는 것은 문서가 아니라 **검사**다. 계정이 소유할 수 있는 테이블 목록을
> `schema.prisma` 에서 읽어, 정리 계획이 다루지 않는 것이 있으면 실패한다(F8).

| 대상 | 처리 | 지금 있나 |
| --- | --- | --- |
| `RefreshToken` | 하드 삭제 | ✅ |
| `UserPreference` | 하드 삭제 | ✅ |
| `Address` | 하드 삭제 | ✅ |
| `UserRole` | 하드 삭제 | ✅ |
| 데모 판매자가 등록한 상품 · 옵션 · Variant | **소프트 삭제** (위 정정) | ✅ |
| `Seller` | `SUSPENDED` + 사유 기록. 행은 남는다 — `Product.sellerId` 가 `RESTRICT` 다 | ✅ |
| `User` | 소프트 삭제 (`deletedAt`) | ✅ |
| `StockLedger` | **건드리지 않는다.** append-only 이고, 지워진 상품의 재고 이력이 남는 것이 옳다 | ✅ |
| 장바구니·위시리스트·최근본·알림 | 하드 삭제 | ❌ M07~M13 |
| 주문·결제·정산 | **보존** (스냅샷 기반이라 사용자 없이도 조회 가능) | ❌ M07~M12 |
| 리뷰·문의 | 하드 삭제 | ❌ M13 |
| 가상 카드 | 하드 삭제 | ❌ M08 |

**주문을 보존하는 이유**: 데모 판매자의 상품을 다른 데모 구매자가 샀을 수 있다. 주문을 지우면 상대의 이력이 깨진다. `OrderItem` 이 상품 스냅샷을 갖고 있으므로 상품이 사라져도 주문서는 온전하다.

| 패키지 | 버전 |

**`@nestjs/schedule` 을 쓰지 않는다.** 이 TASK 가 필요한 것은 **15분마다 한 번**이고 cron 식이
아니다. 그 패키지가 주는 것은 cron 파싱과 `SchedulerRegistry` 인데, 하나는 안 쓰고 하나는 스윕
메서드를 직접 부르는 검사로 대체된다. 남는 것은 `setInterval` 한 줄이고, Nest 의 `OnModuleInit` ·
`OnModuleDestroy` 가 수명을 이미 준다. `pnpm db:seed` 에서 faker 를 뺀 것과 같은 판단이다.
