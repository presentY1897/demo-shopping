# TASK-0110: 관리자 입점 심사 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M04 인증·계정 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-03 |
| 브랜치 | `feature/seller-review-admin` |
| 선행 작업 | TASK-0108, TASK-0023, TASK-0019, TASK-0016, TASK-0107 |

> **분할 유래** — TASK-0026(판매자 입점 신청 · 승인)의 관리자 화면 절반이다. D-208 에 따라 화면과 API 를
> 나눴고, API 는 TASK-0108, 판매자 쪽 화면은 TASK-0109 가 맡는다.

## 1. 목적

`apps/admin` 에서 입점 신청을 심사하는 화면을 만든다. 관리자가 대기 목록을 훑고, 상세를 보고, 승인 ·
반려 · 정지 · 해제를 처리할 수 있게 한다.

**권한이 두 단계로 갈린다는 사실이 화면에 드러나야 한다** — 승인·반려는 운영자(`ADMIN_OPERATOR`),
정지·해제는 최고 관리자(`ADMIN_SUPER`)다.

## 2. 범위

### 포함
- `/sellers` — 심사 목록. 상태 필터(전체 / `PENDING` / `ACTIVE` / `REJECTED` / `SUSPENDED`), 커서 페이지네이션
- `/sellers/[id]` — 심사 상세. 신청 내용, 현재 상태, 최근 사유·변경 시각
- 처리 액션 — 승인 · 반려 · 정지 · 해제. **반려·정지는 사유 입력이 필수**.
  **목록의 행과 상세가 같은 액션을 가진다** — 심사 큐는 훑으면서 처리하는 화면이고, 행마다 상세로
  들어갔다 돌아오게 만들면 대기 40건이 이동 80번이 된다. 행이 내놓는 것은 **그 상태에서 가능한
  것뿐**이라 버튼은 행당 최대 2개다 (아래 「상태가 액션을 고른다」)
- **권한에 따른 액션 비활성 + 사유 툴팁** — TASK-0023 의 `can(permission)` 훅 사용
- 처리 중 중복 클릭 차단, 처리 후 목록 갱신
- 낙관적 잠금 충돌(409) 안내
- `sellerReviewListResponseSchema` · `sellerResponseSchema` 로 **모킹 데이터를 만들고 `parse` 로 검증**

### 제외 (이번에 하지 않는 것)
- **심사 API · 상태 머신** → TASK-0108
- **판매자 쪽 신청 · 설정 화면** → TASK-0109
- 판매자 개별 수수료율 편집 → M12(TASK-0079)
- 판매자 계정 정보 · 매출까지 아우르는 종합 관리 화면 → M14(TASK-0094). 이 화면은 **입점 심사만** 다룬다
- 실제 API 호출 테스트 — 백엔드는 모킹한다

## 3. 요구사항

### 기능 요구사항
- [ ] 대기 중인 신청을 한 화면에서 볼 수 있다
- [ ] 상태로 목록을 걸러낼 수 있다
- [ ] 상세에서 신청 내용과 최근 상태 변경 사유를 볼 수 있다
- [ ] 승인·반려·정지·해제를 처리할 수 있다
- [ ] 반려·정지는 사유를 비우면 제출되지 않는다
- [ ] 권한 없는 액션 버튼은 비활성이고 이유가 표시된다
- [ ] 100건에서 페이지를 넘겨도 중복·누락이 없다

### 비기능 요구사항
- 콘솔 화면 — 밀도 토글 없음, 데스크톱 우선(TASK-0019 의 모바일 대응 범위 규약)
- 표는 좁은 화면에서 가로 스크롤 + 첫 열 고정 (TASK-0016 의 Table)

## 4. 설계

### 화면 / 컴포넌트

```
apps/admin/src/app/sellers/page.tsx        목록 (필터 + 커서 페이지네이션)
        └ SellerReviewWorkspace            네 상태 · 필터 · 페이지 이동
                └ SellerReviewTable        행 + 상태 배지 + 그 상태의 액션
apps/admin/src/app/sellers/[id]/page.tsx   상세 + 처리 액션
        └ SellerReviewDetailWorkspace      신청 내용 · 최근 상태 변경 · 액션
apps/admin/src/components/sellers/seller-decision-dialog.tsx
        └ SellerDecisionDialog             확인 + 사유 입력 (반려 · 정지)
apps/admin/src/lib/sellers/api.ts          심사 엔드포인트 5종의 이음매
apps/admin/src/lib/sellers/decisions.ts    상태 → 액션 · 액션 → 퍼미션 (순수)
apps/admin/src/lib/sellers/use-seller-review.ts        목록 · 필터 · 커서 · 결정
apps/admin/src/lib/sellers/use-seller-review-detail.ts 한 건 · 결정
```

경로는 실제 레이아웃(`src/app/...`)으로 고쳤다. 원안의 `apps/admin/app/...` 은 이 저장소에 없는
경로다.

`docs/design/pages.md` 3장의 `/sellers`(판매자 관리 — 입점 승인, 정지, 개별 수수료율) 중 **입점 승인과
정지**가 이번 범위다. 개별 수수료율은 M12 가 같은 화면에 덧붙인다.

### 액션과 권한

| 액션 | 필요한 퍼미션 | 사유 입력 | 권한 없을 때 |
| --- | --- | --- | --- |
| **심사 목록 · 상세 조회** | **`seller.approve`** | – | 화면이 조회를 시작하지 않고 이유를 보여준다 |
| 승인 | `seller.approve` | 불필요 | 버튼 비활성 + 이유 |
| 반려 | `seller.approve` | **필수** | 〃 |
| 정지 | `seller.suspend` | **필수** | 버튼 비활성 + 이유 |
| 해제 | `seller.suspend` | 불필요 | 〃 |

**조회가 `seller.read` 가 아닌 이유는 TASK-0108 이 이미 적었다** — 그 그랜트는 모든 `BUYER` 가
가지므로(스토어 조회는 공개다) 심사 큐가 `seller.read:any` 였다면 로그인한 아무 구매자나 대기 중인
신청을 신청자 계정 id 까지 붙여 페이지네이션할 수 있었다. 화면도 같은 퍼미션으로 판정한다.

그래서 **사이드바 `/sellers` 항목의 퍼미션도 `seller.read` → `seller.approve` 로 바꿨다.** 메뉴가
요구하는 것과 그 화면이 실제로 부르는 엔드포인트가 요구하는 것이 달라지면, 메뉴에 보이는데 열면
비어 있는 항목이 생긴다. 오늘은 콘솔에 들어오는 세 역할이 모두 `seller.approve` 를 가지므로 보이는
결과는 같고, 달라지는 것은 **무엇을 근거로 보이느냐**다.

**비활성 사유는 두 조각을 잇는다.** 앞은 TASK-0023 훅의 `reason(permission)` — 판정 결과를 그대로
옮긴 문장이라 API 403 의 `details` 와 어휘가 같다. 뒤는 이 화면의 한 줄("정지·해제는 최고 관리자만
할 수 있어요.")이다. 훅의 문장만으로는 *어느* 권한이 없는지 알 수 없고, 화면의 문장만 쓰면 판정과
설명이 따로 놀기 시작한다.

버튼을 숨기지 않고 **비활성 + 사유**로 두는 이유: 숨기면 운영자가 "이 화면에서 정지가 되는가"를 알 수
없어 문의가 생긴다. 판정은 `@shopping/shared` 의 `canPerform` 을 감싼 TASK-0023 의 훅 하나를 쓴다.

**화면의 판정은 편의일 뿐 방어선이 아니다.** 실제 차단은 TASK-0108 의 `PermissionGuard` 가 403 으로
한다(F11). 화면 판정이 틀려도 데이터는 안전하다.

### 절단면 — `packages/shared` 의 zod 스키마

TASK-0108 이 정의한 스키마를 그대로 쓰고, **모킹 응답도 같은 스키마로 만든다.**

| 스키마 | 이 화면에서의 용도 |
| --- | --- |
| `sellerReviewListQuerySchema` | 목록 질의 문자열 구성 (status · cursor · limit) |
| `sellerReviewListResponseSchema` | 목록 응답. **모킹 3페이지를 이 스키마로 `parse`** |
| `sellerResponseSchema` | 상세 응답 |
| `sellerStatusSchema` | 필터 선택지와 상태 배지의 값 출처 |
| `sellerDecisionRequestSchema` | 승인·해제 요청 본문 (`reason` 선택, `version` 필수) |
| `sellerReasonedDecisionRequestSchema` | 반려·정지 요청 본문 — 같은 모양에 **`reason` 필수** |
| `sellerStatusReasonSchema` | 사유 입력의 **규칙**. 문장만 이 앱의 것이다 |

**사유 필수는 스키마 두 개로 갈려 있다.** 원안은 `sellerDecisionRequestSchema` 하나가 "반려에는 사유가
필수"까지 담는다고 적었는데, TASK-0108 이 구현하면서 `sellerReasonedDecisionRequestSchema` 로 나눴다
(그쪽 9장 3번). 화면도 그대로 따른다 — 반려·정지 다이얼로그는 사유 입력을 요구하고, 승인·해제
다이얼로그는 확인만 받는다.

**폼의 문장은 이 앱 것이고 규칙은 계약 것이다.** `sellerStatusReasonSchema` 를 폼 스키마에 그대로 쓰면
zod 의 영어 메시지가 화면에 뜬다. 그래서 **술어는 `packages/shared` 에서 가져오고 문장만 카탈로그에서
가져온다** — TASK-0031 의 `attributeFormSchema` 가 같은 이유로 같은 모양을 하고 있다.

### 이음매 — `ApiClient` 에 판매자 메서드가 없다

`packages/shared` 의 `ApiClient` 는 엔드포인트마다 메서드를 하나씩 가진다(`getCategoryTree`,
`getAttributes` …). **판매자 엔드포인트의 것은 없다.** TASK-0108 은 서버 쪽 TASK 라 클라이언트가 필요
없었고, 자기 통합 테스트에서도 범용 `client.request({ path, schema })` 를 썼다
(`apps/api/test/api/sellers.integration.spec.ts`).

이 화면도 같은 이음매를 쓴다. `apps/admin/src/lib/sellers/api.ts` 가 다섯 경로를 한 곳에 모으고, 응답
스키마는 전부 `@shopping/shared` 의 것이다 — **앱이 응답 타입을 다시 정의하지 않으므로 C1 은 그대로
성립한다.** 다만 메서드가 생기면 그쪽으로 옮기는 편이 낫고, `packages/shared` 는 이 TASK 의 소유가
아니다. **오케스트레이터 판단 필요** (9장).

### 상태가 액션을 고른다 — 전이표는 아직 `apps/api` 안에 있다

행이 내놓는 액션은 그 행의 상태가 정한다.

| 상태 | 행·상세가 내놓는 액션 |
| --- | --- |
| `PENDING` | 승인 · 반려 |
| `ACTIVE` | 정지 |
| `SUSPENDED` | 해제 |
| `REJECTED` | 없음 — 다음 수는 판매자의 재신청이다 |

이 표는 `docs/design/state-machines.md` 6장의 화살표를 그대로 읽은 것이고, 코드로는
`apps/api/src/sellers/seller-status.ts` 의 `TRANSITIONS` 가 같은 것을 담는다. **그 파일은
`packages/shared` 가 아니라 `apps/api` 안에 있어서 화면이 부를 수 없다.** TASK-0108 4장은 전이 판정을
"부수효과 없는 순수 함수로 분리한다"고 적었지만 놓일 자리까지는 정하지 않았고, 지금 두 번째 소비자가
생겼다.

그래서 이 TASK 는 `apps/admin/src/lib/sellers/decisions.ts` 에 **거울 하나**를 둔다. 거울이라는 사실을
파일 머리에 적고, 분기 커버리지 100% 로 잡아 둔다. 근본 해법은 전이표를 `packages/shared` 로 올려
양쪽이 같은 객체를 읽는 것이며 — 그 파일은 TASK-0108 의 소유다. **오케스트레이터 판단 필요** (9장).

**틀려도 데이터는 안전하다.** 거울이 어긋나면 최악이 "누를 수 있게 보이는 버튼이 400 을 받는다" 이고,
그 400 은 `params.allowed` 로 실제 가능한 수를 함께 실어 온다(TASK-0108 F10). 화면은 그것을 그대로
보여준다.

### 역할별 권한

`apps/admin` 진입은 TASK-0023 의 부팅 시점 가드가 `ADMIN_*` 역할로 판정한다(미들웨어가 아니다 —
`docs/design/pages.md` 진입 가드 규약). `DEMO_ADMIN` 도 들어오며, 데모 관리자는 **데모 계정이 만든
신청만 처리할 수 있다** — 실계정 신청의 액션은 서버가 403 으로 막는다(TASK-0108 F12).

**그런데 화면은 어느 행이 데모 것인지 알 수 없다.** 스코프 판정은 `authorizeResource(subject,
permission, ownership)` 이고 `ResourceOwnership` 은 `ownerIsDemo` 를 요구하는데, **`sellerSchema` 에
그 필드가 없다.** 서버는 `Seller.user.isDemo` 를 조인해 읽지만(`resource-ownership.ts`) 응답에는
싣지 않는다.

없는 값을 지어내는 두 길은 둘 다 틀린다 — `ownerIsDemo: false` 로 두면 데모 관리자는 **자기 데모
신청까지** 못 누르게 되고(스코프 `demo` 를 둔 이유 자체가 사라진다), `true` 로 두면 실계정 신청을
누를 수 있는 것처럼 보인다. 그래서 **행 단위 판정을 하지 않는다.**

대신 데모 관리자에게는 **화면 상단에 상시 안내**를 띄운다 — "데모 관리자는 데모 계정이 만든 신청만
처리할 수 있어요." 판정은 `grantedScopes(subject, 'seller.approve')` 가 `demo` 뿐인지로 하며, 이것은
행이 아니라 **주체**에 대한 질문이라 지금 있는 값으로 답할 수 있다. 실제로 눌렀을 때의 403 은 다른
실패와 같은 경로로 표시된다.

`sellerSchema` 에 `ownerIsDemo` 한 칸이 생기면 F8 을 원안대로 구현할 수 있다. 그 파일은 TASK-0108 의
소유다. **오케스트레이터 판단 필요** (9장).

## 9. 변경 이력

| 날짜 | 내용 |
| --- | --- |
| 2026-09-03 | 최초 작성. D-208 에 따라 TASK-0026 에서 분할 |
| 2026-09-04 | 구현 전에 문서를 먼저 고쳤다. 아래 7건 |

**2026-09-04 — 코드보다 먼저 고친 것**

1. **P1(LCP)을 게이트에서 뺐다** (6.2). 이 문서는 2026-09-03 작성분이라 아직 "Lighthouse 모바일
   2.5s 이하"를 들고 있었는데, 그 뒤 QUALITY-GATES 2장이 **LCP 는 게이트가 아니라 조사 도구**로
   바뀌었다(D-217). 화면 TASK 마다 Lighthouse 를 5회씩 돌려 30분~1시간을 쓰고도 **화면이 만든 회귀는
   한 건도 잡지 못했다**는 것이 그 근거다. 접근성(P2)은 자동 검사가 값싸고 실제로 회귀를 잡아 와서
   그대로 게이트로 남는다.
2. **심사 목록·상세의 퍼미션을 표에 명시했다** (4장). TASK-0108 이 `seller.read:any` → `seller.approve`
   로 고친 그 판단을 화면도 그대로 따른다. 곁들여 **사이드바 `/sellers` 항목의 퍼미션도
   `seller.read` → `seller.approve`** 로 맞췄다 — 메뉴가 요구하는 것과 화면이 부르는 엔드포인트가
   요구하는 것이 다르면, 보이는데 열면 비어 있는 항목이 생긴다.
3. **F8(데모 스코프)을 다시 썼다.** 원안은 "`DEMO_ADMIN` + 실계정 신청 → 처리 버튼 비활성"인데,
   그러려면 행마다 `ownerIsDemo` 가 필요하고 **`sellerSchema` 에 그 필드가 없다.** 없는 값을 지어내면
   데모 관리자가 자기 데모 신청까지 못 누르거나(false) 실계정을 누를 수 있어 보인다(true). 행 단위
   판정을 포기하고 **주체 단위 안내**로 대체했다. 4장 「역할별 권한」에 근거를 적었다.
   **오케스트레이터 판단 필요** — `sellerSchema` 에 한 칸이면 원안대로 된다.
4. **`ApiClient` 에 판매자 메서드가 없다는 사실을 적었다** (4장 「이음매」). TASK-0108 은 서버 TASK 라
   클라이언트 메서드를 만들지 않았고 자기 통합 테스트도 범용 `client.request({ path, schema })` 를
   쓴다. 화면도 같은 이음매를 쓰되 다섯 경로를 `lib/sellers/api.ts` 한 곳에 모았다. 응답 타입을 앱에서
   다시 정의하지 않으므로 C1 은 그대로다. **오케스트레이터 판단 필요.**
5. **전이표가 `apps/api` 안에 있다는 사실을 적었다** (4장 「상태가 액션을 고른다」). 행이 어떤 액션을
   내놓을지는 상태가 정하는데, 그 표(`seller-status.ts` 의 `TRANSITIONS`)는 화면이 부를 수 없는 곳에
   있다. 거울을 하나 두고 거울임을 밝히고 분기 100% 로 잡았다. **오케스트레이터 판단 필요** —
   `packages/shared` 로 올리면 거울이 없어진다.
6. **액션을 목록 행에도 뒀다** (2장 · 4장). 원안의 컴포넌트 트리는 처리를 상세에만 뒀지만, 2장이
   요구하는 "처리 후 목록 갱신"과 F5 의 "목록 상태 갱신"은 목록에서 처리할 수 있어야 문자 그대로
   성립한다. 심사 큐는 훑으면서 처리하는 화면이기도 하다. 행은 그 상태에서 가능한 액션만 내므로
   버튼은 행당 최대 2개다.
7. **`sellerReasonedDecisionRequestSchema` 를 절단면 표에 넣었다** (4장). 원안은
   `sellerDecisionRequestSchema` 하나가 사유 필수까지 담는다고 적었는데, TASK-0108 이 구현하며 둘로
   갈랐다. 화면도 갈라 쓴다.

**표에 남지 않는 것 하나** — `docs/design/pages.md` 의 커서 규약은 응답 형태를 `{ items, nextCursor }`
라고 적었지만, 실제 계약 둘(`productListResponseSchema` · `sellerReviewListResponseSchema`)은 배열에
담기는 것의 이름을 쓴다(`products` · `sellers`). 규약 쪽 한 줄을 실제에 맞췄다.
