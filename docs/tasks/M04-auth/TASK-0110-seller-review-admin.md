# TASK-0110: 관리자 입점 심사 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M04 인증·계정 |
| 상태 | 승인 대기 |
| 작성일 | 2026-09-03 |
| 브랜치 | `feature/seller-review-admin` |
| 선행 작업 | TASK-0108, TASK-0023, TASK-0019, TASK-0016, TASK-0107 |

> **분할 유래** — TASK-0026(판매자 입점 신청 · 승인)의 관리자 화면 절반이다. D-208 에 따라 화면과 API 를
> 나눴고, API 는 TASK-0108, 판매자 쪽 화면은 TASK-0109 가 맡는다.

## 1. 목적

`apps/admin` 에서 입점 신청을 심사하는 화면을 만든다. 관리자가 대기 목록을 훑고, 상세를 보고, 승인 ·
반려 · 정지 · 해제를 처리할 수 있게 한다.

**권한이 두 단계로 갈린다는 사실이 화면에 드러나야 한다** — 승인·반려는 운영자(`ADMIN_OPERATOR`),
정지·해제는 최고 관리자(`ADMIN_SUPER`)다.

## 2. 범위

### 포함
- `/sellers` — 심사 목록. 상태 필터(전체 / `PENDING` / `ACTIVE` / `REJECTED` / `SUSPENDED`), 커서 페이지네이션
- `/sellers/[id]` — 심사 상세. 신청 내용, 현재 상태, 최근 사유·변경 시각
- 처리 액션 — 승인 · 반려 · 정지 · 해제. **반려·정지는 사유 입력이 필수**
- **권한에 따른 액션 비활성 + 사유 툴팁** — TASK-0023 의 `can(permission)` 훅 사용
- 처리 중 중복 클릭 차단, 처리 후 목록 갱신
- 낙관적 잠금 충돌(409) 안내
- `sellerReviewListResponseSchema` · `sellerResponseSchema` 로 **모킹 데이터를 만들고 `parse` 로 검증**

### 제외 (이번에 하지 않는 것)
- **심사 API · 상태 머신** → TASK-0108
- **판매자 쪽 신청 · 설정 화면** → TASK-0109
- 판매자 개별 수수료율 편집 → M12(TASK-0079)
- 판매자 계정 정보 · 매출까지 아우르는 종합 관리 화면 → M14(TASK-0094). 이 화면은 **입점 심사만** 다룬다
- 실제 API 호출 테스트 — 백엔드는 모킹한다

## 3. 요구사항

### 기능 요구사항
- [ ] 대기 중인 신청을 한 화면에서 볼 수 있다
- [ ] 상태로 목록을 걸러낼 수 있다
- [ ] 상세에서 신청 내용과 최근 상태 변경 사유를 볼 수 있다
- [ ] 승인·반려·정지·해제를 처리할 수 있다
- [ ] 반려·정지는 사유를 비우면 제출되지 않는다
- [ ] 권한 없는 액션 버튼은 비활성이고 이유가 표시된다
- [ ] 100건에서 페이지를 넘겨도 중복·누락이 없다

### 비기능 요구사항
- 콘솔 화면 — 밀도 토글 없음, 데스크톱 우선(TASK-0019 의 모바일 대응 범위 규약)
- 표는 좁은 화면에서 가로 스크롤 + 첫 열 고정 (TASK-0016 의 Table)

## 4. 설계

### 화면 / 컴포넌트

```
apps/admin/app/sellers/page.tsx        목록 (필터 + 커서 페이지네이션)
apps/admin/app/sellers/[id]/page.tsx   상세 + 처리 액션
        └ SellerDecisionDialog         사유 입력 + 확인 (반려 · 정지)
```

`docs/design/pages.md` 3장의 `/sellers`(판매자 관리 — 입점 승인, 정지, 개별 수수료율) 중 **입점 승인과
정지**가 이번 범위다. 개별 수수료율은 M12 가 같은 화면에 덧붙인다.

### 액션과 권한

| 액션 | 필요한 퍼미션 | 사유 입력 | 권한 없을 때 |
| --- | --- | --- | --- |
| 승인 | `seller.approve` | 불필요 | 버튼 비활성 + "승인 권한이 없습니다" |
| 반려 | `seller.approve` | **필수** | 〃 |
| 정지 | `seller.suspend` | **필수** | 버튼 비활성 + "정지는 최고 관리자만 가능합니다" |
| 해제 | `seller.suspend` | 불필요 | 〃 |

버튼을 숨기지 않고 **비활성 + 사유**로 두는 이유: 숨기면 운영자가 "이 화면에서 정지가 되는가"를 알 수
없어 문의가 생긴다. 판정은 `@shopping/shared` 의 `canPerform` 을 감싼 TASK-0023 의 훅 하나를 쓴다.

**화면의 판정은 편의일 뿐 방어선이 아니다.** 실제 차단은 TASK-0108 의 `PermissionGuard` 가 403 으로
한다(F11). 화면 판정이 틀려도 데이터는 안전하다.

### 절단면 — `packages/shared` 의 zod 스키마

TASK-0108 이 정의한 스키마를 그대로 쓰고, **모킹 응답도 같은 스키마로 만든다.**

| 스키마 | 이 화면에서의 용도 |
| --- | --- |
| `sellerReviewListQuerySchema` | 목록 질의 문자열 구성 (status · cursor · limit) |
| `sellerReviewListResponseSchema` | 목록 응답. **모킹 3페이지를 이 스키마로 `parse`** |
| `sellerResponseSchema` | 상세 응답 |
| `sellerStatusSchema` | 필터 선택지와 상태 배지의 값 출처 |
| `sellerDecisionRequestSchema` | 승인·반려·정지·해제 요청 본문 검증 (`reason` 필수 여부 포함) |

`sellerDecisionRequestSchema` 가 "반려에는 사유가 필수"를 담는다. 화면과 서버가 같은 규칙을 쓰게 하려면
그 조건이 스키마 안에 있어야 한다.

### 역할별 권한

`apps/admin` 진입은 TASK-0023 의 미들웨어가 `ADMIN_*` 역할로 판정한다. `DEMO_ADMIN` 도 들어오며,
데모 관리자에게는 **데모 계정이 만든 신청만 처리 가능**하다 — 실계정 신청의 액션은 서버가 403 을
주므로(F12 of TASK-0108) 화면도 같은 판정으로 비활성한다.

## 5. 구현 계획

1. 목록 화면 — TASK-0016 의 Table · 커서 Pagination 연결
2. 상태 필터 + 빈 상태 · 로딩 · 에러
3. 상세 화면 + 상태 배지
4. 처리 액션 4종 + 사유 다이얼로그
5. 권한 훅 연결 (비활성 + 툴팁)
6. 409 충돌 안내, 처리 중 잠금
7. 모킹 응답 `parse` 테스트, 키보드 순회, Lighthouse 측정
