## 1. 목적

방문자가 가입 없이 즉시 역할별 임시 계정을 받아 전체 기능을 체험하게 한다. **이 프로젝트의 핵심 진입 경로**다.

지금은 그보다 앞선 이유가 하나 더 있다. **로그인 경로가 Google OAuth 뿐이라 만들어 둔 화면을 브라우저로 열 수가 없다.** TASK-0109 · 0110 · 0112 · 0023 이 전부 같은 벽에 부딪혀 Lighthouse 와 레이아웃 실측을 axe 로 대신했다(각 문서 R4 · R7). 이 TASK 가 붙으면 그 화면들이 한 번에 열린다.

## 2. 범위

### 포함
- 데모 발급 엔드포인트 (역할별)
- 세 앱 각각의 발급 진입점 (로그인 페이지)
- **발급 시 초기 데이터 세팅** — 빈 화면을 보지 않도록 역할별로 미리 채운다 (4.7)
- 발급 즉시 로그인 상태로 전환
- **관리자 데모의 권한** — `DEMO_ADMIN` 역할 부여 (D-058, 가드는 TASK-0105 가 이미 구현)
- 남은 시간 표시 배너
- 발급 남용 방지 (IP 기준 rate limit)

### 제외

- 만료·정리 (TASK-0025)

## 4. 설계

### 4.1 두 개의 엔드포인트

```
POST /api/v1/auth/demo         X-App-Id: shop | seller | admin
     { role: BUYER | SELLER | ADMIN }
  → 200 { demo: { role, expiresAt } }
       + Set-Cookie: shopping_refresh_<app>
  → 400  role 과 X-App-Id 가 어긋남 · 헤더 없음
  → 429  같은 IP 에서 창(60초) 안에 5회를 넘김

GET  /api/v1/auth/demo         (퍼미션 user.read)
  → 200 { demo: { role, expiresAt } | null }
```

**POST 응답에 access 토큰이 없는 것은 누락이 아니다.** Google 콜백이 토큰을 리다이렉트 URL 에 싣지 않는 것과 같은 이유이고(TASK-0021 4장), 같은 결과다 — 응답에는 refresh 쿠키만 실리고 앱은 첫 `POST /auth/refresh` 로 access 토큰을 받는다. 그것이 이후 모든 갱신이 지나는 경로이므로 발급만 다른 길을 갈 이유가 없다. 프론트에서는 `useAuth().recheck()` 한 줄이다.

**`X-App-Id` 가 세션이 사는 곳을 정하고, 본문의 `role` 은 방문자가 무엇을 요청했는지를 말한다.** 둘이 어긋나면 400 이다 — shop 앱에 판매자 데모 세션을 발급하면 쿠키는 `shopping_refresh_shop` 인데 그 세션으로는 판매자 콘솔에 들어갈 수 없어(콘솔은 자기 앱의 쿠키만 읽는다, D-218) **로그인은 됐는데 아무 데도 못 가는 상태**가 된다. 클라이언트 버그를 조용히 통과시키는 대신 거절한다.

| `X-App-Id` | 허용되는 `role` | 부여되는 역할 |
| --- | --- | --- |
| `shop` | `BUYER` | `BUYER` |
| `seller` | `SELLER` | `SELLER_OWNER` |
| `admin` | `ADMIN` | `DEMO_ADMIN` |

`role` 의 값이 `Role` enum 이 아니라 `BUYER | SELLER | ADMIN` 인 것은 의도적이다. 방문자가 고르는 것은 **페르소나**이고, 그것이 어떤 역할 행으로 번역되는지는 서버가 정한다. `DEMO_BUYER` · `DEMO_SELLER` 역할이 없는 것과 같은 판단이다(`packages/shared/src/auth/roles.ts`).

### 4.2 왜 GET 이 따로 있나 — 배너는 새로고침을 견뎌야 한다

남은 시간 배너는 발급 직후에만 필요한 것이 아니라 **데모를 쓰는 24시간 내내** 필요하다. 그런데 앱은 새로고침할 때마다 `POST /auth/refresh` 로만 자기가 누구인지 알아내고, 그 응답은 `SessionResponse` 다.

`SessionResponse` 에 `demoExpiresAt` 를 더하는 안을 쓰지 않았다. **세션이 무엇인지를 정하는 것은 TASK-0022 의 계약**이고, 거기에 데모 개념을 넣으면 세 앱의 세션 타입이 전부 데모를 알게 된다 — 판매자 상태를 세션에 싣지 않기로 한 것과 같은 판단이다(TASK-0109 4장, `docs/design/pages.md` 217행). 대신 **계정에 대한 질문은 계정에게 묻는다**: 배너 컴포넌트가 로그인된 뒤 한 번 `GET /auth/demo` 를 부른다.

비용은 **로그인 사용자당 앱 부팅 1회의 작은 조회 하나**다. 실계정에게는 `{ demo: null }` 이 돌아오고 배너는 아무것도 그리지 않는다.

### 4.3 데모 계정을 만드는 트랜잭션

DB 가 데모를 두 개의 CHECK 로 못박고 있다.

| 제약 | 내용 | 이 경로가 지키는 방법 |
| --- | --- | --- |
| `User_demo_expiry_check` | 데모에는 항상 만료가 있고 실계정에는 없다 | `isDemo` 와 `demoExpiresAt` 를 **같은 INSERT 에서** 함께 쓴다. 중간 상태가 없다 |
| `User_google_identity_check` | 살아 있는 실계정에는 `googleSub` 가 있다 | 데모는 `isDemo` 로 이 검사를 통과한다. `googleSub` 는 `null` — 데모는 Google 을 지난 적이 없다 |

**발급 전체가 한 트랜잭션이다.** 계정 · 역할 · 초기 데이터 · **그리고 refresh 토큰**까지 같은 트랜잭션에서 커밋된다.

토큰까지 넣는 이유는 둘이다. 하나는 절반만 남는 경우를 없애는 것 — 계정만 커밋되고 세션 발급이 실패하면 아무도 쓰지 않는 데모 계정이 24시간 남는다. 다른 하나는 4.4 의 rate limit 이 **그 토큰 행을 세기 때문**이다. 계정이 먼저 커밋되고 토큰이 나중에 쓰이면 그 사이에 들어온 동시 요청이 앞의 발급을 세지 못한다.

그래서 `SessionService.issue` 가 **선택적 트랜잭션 클라이언트**를 받도록 한 줄 넓혔다. 인자를 주지 않으면 지금까지와 똑같이 동작하므로 Google 콜백은 바뀌지 않는다.

판매자 데모의 스토어도 같은 트랜잭션에 들어간다. `SellerService.openDemoStore` 는 TASK-0108 이 이 경로를 위해 미리 만들어 둔 진입점이고(그 문서 F7 · R1), 같은 이유로 선택적 트랜잭션 클라이언트를 받도록 넓혔다 — **승인된 스토어와 `SELLER_OWNER` 역할이 함께 들어가는 성질은 그대로다.**

### 4.4 rate limit — 새 의존성도 새 인프라도 없이

**저장소에 rate limit 장치가 없다.** `@nestjs/throttler` 도, Redis 도, 그 비슷한 것도 없다. 세 가지를 놓고 골랐다.

| 안 | 왜 아닌가 / 왜인가 |
| --- | --- |
| `@nestjs/throttler` 도입 | 새 의존성. 기본 저장소가 **프로세스 메모리**라 재시작하면 초기화되고 인스턴스가 둘이면 한도가 두 배가 된다. 그것을 고치려면 Redis 가 필요하고, 그것은 새 인프라다 |
| 인메모리 카운터 자작 | 위와 같은 문제를 직접 만드는 것. 게다가 테스트가 **실 PostgreSQL 을 쓰는데 한도는 메모리에 있어** A7 의 동시성 증명이 DB 밖에서 이뤄진다 |
| **DB 로 센다** ← 채택 | 새 의존성 0, 새 인프라 0. 재시작과 다중 인스턴스에 강하다. 그리고 **셀 행을 이 경로가 이미 쓰고 있다** |

세는 것은 **창 안에 이 IP 에서 발급된 데모 계정의 수**다.

```sql
SELECT count(*)::int
  FROM "User" u
 WHERE u."demoExpiresAt" IS NOT NULL
   AND u."createdAt" > $window_start
   AND EXISTS (SELECT 1 FROM "RefreshToken" t
                WHERE t."userId" = u."id" AND t."ipAddress" = $ip)
```

- **토큰이 아니라 계정을 센다.** refresh 토큰 행은 15분마다 갱신으로도 늘어나므로, 토큰을 세면 탭을 몇 개 열어 둔 방문자가 아무것도 발급하지 않고 한도에 걸린다.
- **`isDemo` 가 아니라 `demoExpiresAt` 를 읽는다.** `User_demo_expiry_check` 때문에 두 컬럼은 서로를 함축한다 — 스키마 주석이 그렇게 적혀 있다("어느 컬럼을 보든 답이 하나"). 덕분에 4.5 의 허용 목록을 한 파일만 넓히면 된다.
- 한도는 **60초에 5회**. 하한은 F7(탭 3개에서 동시 발급)이고 상한은 F6(1분에 10회 시도 중 초과분 429)이다.

**동시 발급은 어드바이저리 락으로 직렬화한다.** 세고 나서 쓰는 사이에 다른 요청이 끼어들면 둘 다 한도를 통과한다. 카테고리 트리와 같은 장치를 쓴다(D-201, `catalog/category-lock.ts`).

```sql
SELECT pg_advisory_xact_lock($1::int4, hashtext($2)::int4)   -- (0xDE0, ip)
```

`pg_advisory_xact_lock` 이고 세션 스코프가 아닌 이유도 같다 — COMMIT · ROLLBACK 이 알아서 놓아주므로 죽은 요청이 IP 하나를 영원히 잠그지 못한다. 락 키가 **IP 별**이므로 서로 다른 방문자는 경합하지 않는다.

`X-Forwarded-For` 도 소켓 주소도 없으면 `unknown` 이라는 한 바구니에 모인다. 그 경우 서로 다른 방문자가 같은 한도를 나눠 쓰지만, 그것이 IP 를 알 수 없는 요청에 한도를 **주지 않는 것**보다 안전한 쪽이다.

### 4.5 `isDemo` 격리 장치를 정확히 한 파일만 넓힌다

`auth/demo-containment.spec.ts`(TASK-0105 F8)가 `isDemo` 를 이름으로 부르는 파일을 목록으로 고정한다. 그 장치의 의도는 "읽는 곳이 생기는 TASK 가 같은 커밋에서 목록을 고친다" 이고, 이 TASK 가 그 TASK 다.

넓히는 것은 **`apps/api/src/demo/demo-account.ts` 하나**다. 데모 컬럼 두 개를 쓰는 유일한 자리이고, 그 파일이 하는 일은 그것뿐이다.

넓히지 **않은** 곳들과 그 이유:

| 넓힐 뻔한 곳 | 대신 무엇을 읽는가 |
| --- | --- |
| rate limit 질의 | `demoExpiresAt IS NOT NULL` (4.4) |
| 발급 응답 · 배너 계약 | `expiresAt` — 프론트에 가는 값은 만료 시각이지 불리언이 아니다 |
| `GET /auth/demo` 의 조회 | `demoExpiresAt` |

즉 **프론트는 `isDemo` 를 영영 모른다.** 배너가 답해야 하는 질문이 "데모인가"가 아니라 "언제까지인가"이므로 그것이 더 정확한 계약이기도 하다.

### 4.6 남은 시간 배너

세 앱 모두 같은 자리를 쓴다 — 루트 레이아웃의 `AuthProvider` 바로 아래. 콘솔에서 `ConsoleFrame` 안쪽에 두면 `/login` 과 `/no-permission` 에서 사라진다(그 두 경로는 셸 밖에서 렌더된다).

- 로그인 상태가 되면 한 번 `GET /auth/demo` 를 부르고, `{ demo: null }` 이면 아무것도 그리지 않는다
- 남은 시간은 **분 단위 이상으로만** 표시한다("23시간 12분 남음"). 초를 세면 1초마다 리렌더가 돌고, 24시간짜리 만료에서 초는 정보가 아니다
- 1분마다 갱신한다. 남은 시간이 0 이하가 되면 만료 문구로 바뀐다(정리는 TASK-0025)
- `role="status"` 로, 알림이 아니라 **상태**로 읽힌다. 24시간 내내 떠 있는 배너를 `role="alert"` 로 두면 스크린리더가 매 페이지마다 끼어든다

### 4.7 초기 데이터 — 지금 만들 수 있는 것과 없는 것

**이 표는 2026-09-02 승인본과 다르다.** 그때는 M07~M13 의 테이블이 곧 생긴다는 전제였는데, 실제 순서는 M04 가 M05 와 병행해 먼저 왔다. 지금 스키마에 있는 테이블은 계정 · 역할 · 주소 · 설정 · 판매자 · 카테고리 · 속성 · 상품 · 옵션 · Variant · 재고 원장까지다. **주문 · 쿠폰 · 적립금 · 가상카드 · 정산 · 리뷰 · 위시리스트 테이블은 아직 없다.**

없는 테이블에 행을 넣는 코드는 쓸 수 없고, 쓸 수 있는 척하는 문서는 더 나쁘다. 그래서 이 절을 **지금 만드는 것**과 **받는 TASK** 로 나눈다.

| 역할 | 지금 만든다 | 나중에, 그 테이블을 만드는 TASK 가 이 경로에 붙인다 |
| --- | --- | --- |
| 구매자 | 기본 배송지 1개, 표시 설정 1행 | 가상 카드 1장(TASK-0053) · 쿠폰 3장(TASK-0072) · 적립금 잔액(TASK-0076) · 진행 중 주문 3건(TASK-0049 · 0059) · 위시리스트 3개(TASK-0086) · 최근 본 상품 5개(TASK-0087) |
| 판매자 | `ACTIVE` 스토어(브랜드명·슬러그 자동 생성), **공용 카탈로그에서 복제한 상품 최대 12개**(이미지·옵션·Variant·재고 원장 포함) | 주문 5건(TASK-0049 · 0059) · 정산 2회차(TASK-0080) · 리뷰 4건(TASK-0083) |
| 관리자 | **승인 대기 판매자 신청 2건** — 각각 자기 데모 계정이 소유하므로 `demo` 스코프 안에 들어온다 | 개입 대기 클레임 1건(TASK-0065) · 승인 대기 정산서 1건(TASK-0080) |

**"받는 TASK 가 붙인다" 를 말로만 두지 않는다.** 초기 데이터 생성은 역할별 **시더 목록**으로 되어 있고, 새 시더를 더하는 것이 배열에 한 항목을 넣는 일이 되도록 만든다. 그 목록이 이 표의 오른쪽 칸을 회수하는 자리다.

**상품을 복제로 만드는 이유**는 승인본 그대로다 — 새로 생성하면 이미지가 없어 초라하다. 공용 카탈로그의 `ACTIVE` 상품을 복제해 소유자만 바꾸면 이미지·속성이 그대로 온다.

**"최대 12개" 인 이유**: 복제할 원본이 있어야 복제가 된다. 시드 카탈로그를 만드는 TASK-0037 이 아직 완료가 아니므로, 새 환경에서는 원본이 0개일 수 있다. 그때 발급이 실패하는 것이 아니라 **상품 0개인 스토어가 열린다.** 카탈로그가 채워지면 같은 코드가 12개를 복제한다.

복제할 때 지켜야 하는 것:

- **SKU 는 판매자 안에서만 유일하다**(`ProductVariant_seller_sku_key`). 서로 다른 원본 판매자의 상품을 한 데모 스토어로 모으면 SKU 가 겹칠 수 있으므로 겹치는 것만 꼬리를 붙여 떼어 놓는다
- **옵션 조합 서명은 새 옵션 값 id 로 다시 계산한다**(`ProductVariant_product_signature_key`)
- **재고에는 원장이 따라온다**. 복제한 Variant 의 `stock` 이 0 이 아니면 `INBOUND` 한 줄을 같이 넣는다 — 그러지 않으면 L1(`stock = SUM(quantity)`)이 깨진 상태로 시작한다(TASK-0036 4.1)
- 원본은 **데모가 아닌 계정의 `ACTIVE` 상품**만 고른다. 데모가 데모를 복제하면 24시간마다 사본의 사본이 생긴다

### 4.8 데모 계정이 데이터를 자유롭게 다룰 수 있어야 한다

승인본 그대로. 데모의 목적은 **직접 만들고 지워보는 것**이다. 판매자 데모는 복제받은 상품을 수정·삭제할 수 있고 새로 등록할 수도 있다 — 소유권이 자기 스토어이므로 `own` 스코프가 그대로 답한다. 별도 장치가 없다.

### 4.9 관리자 데모 권한 (D-058)

**별도 장치를 만들지 않는다.** `DEMO_ADMIN` 역할과 `demo` 스코프로 권한 체계 안에서 표현한다. TASK-0105 가 이미 구현했고, 이 TASK 는 **역할을 부여하기만 한다.**

```
DEMO_ADMIN = ADMIN_OPERATOR 퍼미션 + 리소스 스코프 demo
             → 데모 계정이 만든 데이터만 처리 가능
             → 시드·실계정 데이터는 조회만
             → delete · settlement.pay · user.delete 퍼미션 자체가 없음
```

판단 축은 셋이다.

| 축 | 차단 대상 |
| --- | --- |
| 남에게 피해를 주는가 | 실계정 사용자·판매자의 데이터 변경 |
| 되돌릴 수 없는가 | 삭제, 정산 지급 확정 |
| 공용 자산을 훼손하는가 | 시드 카탈로그·카테고리 파괴 |

**반대로 자기가 만든 것과 다른 데모가 만든 것은 전부 다룰 수 있다.** 어차피 24시간 후 삭제되고, 직접 처리해보는 것이 데모의 목적이다. 그래서 4.7 의 관리자 초기 데이터가 **데모 계정이 소유한** 신청 2건인 것이 핵심이다 — 실계정 신청만 있으면 관리자 콘솔은 조회만 되는 껍데기가 된다.

UI 에서는 **버튼을 숨기지 않고 비활성 + 사유 툴팁**으로 보여준다(TASK-0023 이 `GuardedButton` 으로 이미 구현). 기능이 있다는 것을 알리는 게 데모의 목적이다.

| # | 내용 | 대응 |

| R5 | rate limit 이 **한 IP 뒤의 여러 방문자**를 함께 막는다 | 사내망·모바일 캐리어 NAT 에서 실제로 생긴다. 창을 60초로 짧게 두어 회복이 빠르도록 했다. 발급이 실제로 몰리는 것이 관측되면 세션 쿠키 기준을 더한다 |

| R7 | **복제한 상품을 지울 수 없다** | 구현하며 알았다. `StockLedger` 에는 append-only 트리거가 걸려 있어 원장 행을 지울 수 없고, 그 행이 `ProductVariant` 를 `Restrict` 로 잡는다. 그래서 데모 정리(TASK-0025)는 상품을 **소프트 삭제**로 다뤄야 한다 — 원장의 `actorId` 는 `null` 로 넣어 두었으므로 계정 자체의 삭제는 막히지 않는다. `state-machines.md` 8장에 적었다 |
| R8 | **워크스페이스를 병행 실행하면 `apps/admin` 스펙이 가끔 시간 초과한다** | 이 브랜치의 것이 아니다 — 새 스펙 두 개를 빼고 돌려도 같은 자리에서 난다(`attributes-error-contract` · `sellers-page`). `pnpm -r --workspace-concurrency=1` 로 돌리면 전부 통과한다. 오케스트레이터 판단이 필요하다 |
