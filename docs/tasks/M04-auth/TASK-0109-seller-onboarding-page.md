# TASK-0109: 판매자 입점 신청 · 스토어 설정 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M04 인증·계정 |
| 상태 | 완료 |
| 작성일 | 2026-09-03 |
| 브랜치 | `feature/seller-onboarding-page` |
| 선행 작업 | TASK-0108, TASK-0023, TASK-0019, TASK-0017, TASK-0107 |

> **분할 유래** — TASK-0026(판매자 입점 신청 · 승인)의 판매자 화면 절반이다. D-208 에 따라 화면과 API 를
> 나눴고, API 는 TASK-0108 이 맡는다. TASK-0027 에 있던 **판매자 스토어 설정 화면**도 여기로 옮겼다 —
> 입점 신청 폼과 스토어 설정 폼은 같은 필드를 쓰므로 한 화면에서 다루는 것이 자연스럽다.

## 1. 목적

`apps/seller` 에서 입점 신청과 스토어 설정을 하는 화면을 만든다. 신청 전·심사 중·반려·운영 중이라는
**네 가지 상태가 같은 화면의 다른 얼굴**이 되게 하는 것이 이 화면의 핵심이다.

이 작업이 끝나면 판매자는 브라우저만으로 입점을 신청하고, 반려 사유를 확인해 재신청하고, 승인 후에는
같은 폼으로 브랜드 정보를 고칠 수 있다.

## 2. 범위

### 포함
- `/apply` — 입점 신청 폼 (브랜드명 · 스토어 slug · 소개 · 로고 URL)
- **브랜드명 실시간 중복 확인** — 입력 정지 후 조회, 결과를 필드 옆에 표시
- **상태별 화면 분기** — 신청 전(폼) / `PENDING`(안내) / `REJECTED`(사유 + 재신청) / `ACTIVE`(설정 폼) /
  `SUSPENDED`(제한 안내)
- `/settings` — 스토어 설정 (브랜드명 · 소개 · 로고 수정). 신청 폼과 **같은 필드 컴포넌트를 공유**
- **낙관적 잠금 충돌 안내** — 409 응답 시 "다른 곳에서 수정되었습니다. 최신 내용을 불러올까요?"
- 서버 검증 오류(400 `details`)를 해당 필드에 매핑 (TASK-0017 규약)
- 승인 대기 상태에서 콘솔 사이드바가 안내 화면만 보이게 하는 연동 (TASK-0023 의 메뉴 필터링 활용)
- `sellerApplicationRequestSchema` · `sellerResponseSchema` 로 **모킹 데이터를 만들고 `parse` 로 검증**

### 제외 (이번에 하지 않는 것)
- **입점 API · 상태 머신** → TASK-0108
- **관리자 심사 화면** → TASK-0110
- **로고 이미지 업로드 위젯** → TASK-0033. 이번에는 `logoUrl` 을 입력·붙여넣기로 받고, 위젯이 나온 뒤
  같은 필드를 위젯으로 교체한다. 위젯을 선행으로 걸면 입점 플로 전체가 M05 뒤로 밀린다
- 배송 정책 · 정산 계좌 등 나머지 스토어 설정 (M09 · M12)
- 실제 API 호출 테스트 — 백엔드는 모킹한다 (QUALITY-GATES 6장)

## 3. 요구사항

### 기능 요구사항
- [ ] 로그인한 사용자가 입점 신청 폼을 제출할 수 있다
- [ ] 브랜드명이 이미 쓰이고 있으면 제출 전에 필드 옆에서 알려준다
- [ ] `PENDING` 이면 폼 대신 심사 중 안내가 보인다
- [ ] `REJECTED` 면 사유가 보이고 같은 폼으로 재신청할 수 있다
- [ ] `ACTIVE` 면 같은 폼이 스토어 설정으로 동작한다
- [ ] 저장 중에는 버튼이 잠기고 두 번 눌러도 요청이 한 번만 나간다
- [ ] 서버가 400 을 주면 해당 입력 필드에 메시지가 붙는다
- [ ] 409(낙관적 잠금 충돌)면 덮어쓰지 않고 다시 불러올지 묻는다

### 비기능 요구사항
- 접근성 — 오류 메시지가 `aria-describedby` 로 필드에 연결된다 (TASK-0017 규약)
- 콘솔 화면이므로 밀도 토글이 없다 (2단계 고정, TASK-0019)

## 4. 설계

### 화면 / 컴포넌트

```
apps/seller/app/apply/page.tsx      신청 · 재신청 · 상태 안내
apps/seller/app/settings/page.tsx   스토어 설정 (ACTIVE 전용)
        └ StoreProfileFields        브랜드명 · slug · 소개 · 로고  ← 두 화면이 공유
```

`docs/design/pages.md` 2장의 `/settings`(스토어 설정 — 브랜드명, 로고, 소개, 배송 정책) 중 **브랜드명 ·
로고 · 소개**가 이번 범위다. 배송 정책은 M09 가 같은 화면에 덧붙인다.

`/apply` 는 `pages.md` 2장 표에 없던 라우트다. TASK-0023 이 `console-access.ts` 의
`SIGNED_IN_ONLY_ROUTES` 에 **화면 없이 먼저 등록해 둔** 경로이고(그 TASK 9장, 2026-09-03), 이번에
실물이 들어오면서 라우트 표에도 올린다(6.3 D2).

### 상태를 어디서 읽는가 — `GET /api/v1/sellers/me`

**이 화면이 부팅할 때 `GET /api/v1/sellers/me` 를 부른다. 세션 응답에 상태를 싣지 않는다.**

이유가 둘이다.

- **반려 사유(`statusReason`)가 화면에 필요하다.** 그것을 세션 응답에 담으면 로그인 응답이 판매자
  도메인을 갖게 된다 — `sessionResponseSchema` 는 세 앱이 함께 쓰는 계약이고, `apps/shop` 이 읽을
  일 없는 필드가 거기 생긴다.
- **세션에 담긴 값은 갱신할 때만 새로 온다.** access token 은 15분이므로(TASK-0022 4장) 관리자가
  승인해도 화면은 최대 15분간 "심사 중" 으로 남는다. 세 역할을 탭 3개로 함께 여는 데모 동선에서
  정확히 눈에 띄는 지연이다.

세션의 `user.sellerId` 는 **"신청한 적이 있는가" 까지만** 말한다. 신청하는 순간 `PENDING` 행이 생기니
`sellerId` 는 채워지지만, 그것으로는 `PENDING` · `REJECTED` · `ACTIVE` · `SUSPENDED` 를 가를 수 없다.
다섯 갈래를 가르는 것은 `GET /sellers/me` 하나다 — TASK-0023 4장이 "세션은 `Seller.status` 를 싣지
않으므로 추측하지 않는다" 고 비워 둔 자리를 이 호출이 채운다.

**미신청은 404 다.** `SellerService.ownStore` 가 행이 없으면 `NotFoundException` 을 던지므로, 이
화면에서 "아직 신청하지 않았다" 는 200 의 한 갈래가 아니라 **404 라는 응답**이다. 그래서 상태 모델은
`loading` · `absent` · `ready` · `error` 네 갈래이고, `ready` 안에서 다시 네 상태로 갈린다.

### 엔드포인트를 부르는 방법 — `ApiClient.request`

`packages/shared` 의 `ApiClient` 에는 판매자 메서드가 없다(`getCategoryTree` 처럼 이름 붙은 메서드가
카테고리 · 속성 · 상품 · 업로드에만 있다). **이 TASK 는 `packages/shared` 를 소유하지 않으므로**
메서드를 더하지 않고, 같은 클라이언트가 공개하는 `request({ path, schema, method, body })` 로 부른다.

잃는 것이 없다. `request` 도 응답을 넘겨받은 zod 스키마로 `parse` 하므로 드리프트는 여전히
`malformed_response` 로 떨어지고, 스키마는 `@shopping/shared/api/sellers.ts` 의 것 그대로다(C1).
이름 붙은 메서드는 계약을 소유한 TASK 가 넣는 편이 맞다 — **오케스트레이터 판단 필요**(9장).

### 상태별 얼굴

| `sellerSchema.status` | 배너 | 폼 | 제출 버튼 |
| --- | --- | --- | --- |
| (스토어 없음 · 404) | 없음 | 빈 폼 | "입점 신청" → `POST /sellers/applications` |
| `PENDING` | 심사 중 안내 | 값 채워짐 · **편집 가능** | "저장" → `PATCH /sellers/me` |
| `REJECTED` | 반려 사유 | 값 채워짐 · 편집 가능 | "재신청" → `POST /sellers/applications` |
| `ACTIVE` | 운영 중 안내 | 값 채워짐 · 편집 가능 | "저장" → `PATCH /sellers/me` |
| `SUSPENDED` | 정지 사유 | 값 채워짐 · **편집 가능** | "저장" → `PATCH /sellers/me` |

**하나의 컴포넌트로 다루는 이유**: 다섯 화면을 따로 만들면 필드 검증 규칙이 다섯 벌이 된다. 원본
TASK-0026 과 TASK-0027 이 신청 폼과 설정 폼을 각각 다른 TASK 에 뒀던 것이 정확히 그 위험이었다.

**`PENDING` 의 "읽기 전용" 과 `SUSPENDED` 의 "폼 비활성" 을 지웠다** (9장, 2026-09-04).
`docs/design/state-machines.md` 6장은 "스토어 정보(브랜드명·소개·로고) 수정은 **모든 상태에서 열려
있다**. 반려된 이름을 고치는 것과 정지 중에 소개를 바로잡는 것은 막을 이유가 없다" 고 적고,
`SellerService.updateStore` 도 상태를 보지 않는다. 잠긴 폼은 **API 가 허락하는 일을 화면만 거절하는
것**이고, 하필 그 두 상태가 고칠 것이 가장 많은 상태다.

`slug` 는 신청할 때만 받는다. `sellerStoreUpdateRequestSchema` 에 `slug` 가 없기 때문이고, 그것이
없는 이유는 R4 — 브랜드명이 바뀌어도 스토어를 가리키는 링크가 깨지면 안 된다. 그래서 스토어가 있는
네 상태에서 slug 입력은 읽기 전용으로 두고 값만 보여 준다.

### 낙관적 잠금 충돌은 폼 위의 안내다

`PATCH /sellers/me` 는 두 가지 이유로 409 를 낸다. 둘을 가르는 것은 `details[].field` 다.

| `details[].field` | 뜻 | 화면 |
| --- | --- | --- |
| `version` | 다른 탭이 먼저 저장했다 (`SellerService.versionConflict`) | 폼 위 안내 + "다시 불러오기" · "그대로 저장" |
| `brandName` · `slug` | 유니크 제약이 거부했다 (`Seller_brandName_key`) | 해당 **필드 아래** 메시지 (F3·F7 과 같은 경로) |

`domainErrorCodes` 에 판매자 코드가 없으므로(TASK-0108 4장 — 두 콘솔의 메시지 카탈로그가
`Record<UserFacingErrorCode, string>` 이라 코드를 하나 늘리면 남의 소유 경로 둘을 함께 고쳐야 한다)
`error.code` 는 `CONFLICT` 하나뿐이고, **필드 이름이 유일한 판별자**다.

안내는 모달이 아니라 **폼 바로 위의 `role="alert"` 영역**이다. 고칠 대상이 화면에 한 벌뿐이라
"내가 쓴 것 / 저장된 것" 을 나란히 놓을 이유가 없고, 모달은 포커스 트랩과 포털을 하나 더 들여 axe
검사에서 예외를 늘린다. 입력값은 **덮어쓰지 않는다** — 다시 불러오기를 누른 사람만 값이 바뀐다.

### 절단면 — `packages/shared` 의 zod 스키마

TASK-0108 이 정의한 스키마를 **그대로 가져다 쓰고, 모킹 응답도 같은 스키마로 만든다.**

| 스키마 | 이 화면에서의 용도 |
| --- | --- |
| `sellerApplicationRequestSchema` | 신청·재신청 폼의 클라이언트 검증 (TASK-0017 어댑터) |
| `sellerStoreUpdateRequestSchema` | 설정 폼의 클라이언트 검증 (`version` 포함) |
| `sellerResponseSchema` | 상태 분기의 입력. **모킹 응답 5종을 이 스키마로 `parse`** |
| `sellerStatusSchema` | 상태별 분기의 유일한 값 출처 (문자열 리터럴을 화면에 적지 않는다) |
| `brandNameAvailabilityResponseSchema` | 중복 확인 응답 |

앱에서 응답 타입을 다시 정의하지 않는다(C1). 모킹 데이터가 스키마를 통과하는지 테스트가 확인한다(C2).

### 승인 전 사이드바 — 퍼미션 필터만으로는 좁혀지지 않는다

2장이 "TASK-0023 의 메뉴 필터링 활용" 이라고 적었지만, **그것만으로는 아무것도 가려지지 않는다.**
신청자는 아직 `BUYER` 이고 `role-permissions.ts` 의 `BUYER_GRANTS` 는 `product.read` · `order.read` ·
`claim.read` · `coupon.read` · `seller.read` 를 전부 가진다 — 카탈로그와 스토어 조회가 공개이고 자기
주문·클레임·쿠폰은 자기 것이기 때문이다. 그래서 `filterConsoleMenu` 가 걸러 내는 항목은 실제로
`/settlements` 하나뿐이고, 심사 대기자는 **누르면 `/no-permission` 으로 튕기는 링크 여덟 개**를 보게
된다.

메뉴는 "무엇을 조회할 수 있는가" 로 걸러지는데 이 화면이 묻는 것은 "이 콘솔에 들어올 수 있는가" 다.
그 판정은 이미 `console-access.ts` 의 `mayEnterConsole(roles)` 이 하고 있고, `ConsoleGuard` 가 쓰는
것과 같은 함수다. 그래서 `SellerShell` 이 그 한 줄을 앞에 세운다.

```
mayEnterConsole(roles) === false  →  사이드바는 「입점 신청」 한 항목      (layout.onboardingMenu)
mayEnterConsole(roles) === true   →  기존 메뉴 + 퍼미션 필터              (layout.menu)
```

세션이 아직 확인 중이면 **기존 메뉴를 그대로 둔다.** TASK-0019·0023 이 같은 이유로 그렇게 했다 —
확인 중 프레임에서는 모든 판정이 `false` 라, 좁혔다가 한 프레임 뒤 펼치면 로드마다 레이아웃이 뛴다.
막는 것은 메뉴가 아니라 가드다.

### 역할별 권한

`apps/seller` 진입은 TASK-0023 의 미들웨어가 판정한다. 이 화면은 **역할이 없는 사용자에게도 열려 있어야
한다** — 입점 신청은 아직 판매자가 아닌 사람이 하기 때문이다. 신청 화면은 로그인만 요구하고, 나머지
판매자 메뉴는 `ACTIVE` 가 아니면 보이지 않는다.

   소유가 아니다. 스키마는 그대로 쓰므로 C1 도 파싱도 잃는 것이 없다. **오케스트레이터 판단 필요** —
   이름 붙은 메서드(`getOwnStore` 등)는 계약을 소유한 TASK 가 넣는 편이 맞다.
6. **F3 의 "제출 버튼 비활성" 을 지키지 않았다** (6.1 F3 은 `[~]`). 구현하고 검사를 쓰다가
   알았다 — **네이티브 `disabled` 인 제출 버튼은 브라우저의 암묵적 제출까지 막는다.** 텍스트
   필드에서 Enter 를 눌러도 아무 일이 일어나지 않고, 이유도 말하지 않는다. 그 자리는 TASK-0018
   4.5 가 "누를 수 없는 컨트롤은 키보드 사용자에게 막다른 길" 이라고 못박은 곳이고, `Button` 이
   `loading` 에 네이티브 `disabled` 대신 `aria-disabled` 를 쓰는 이유도 같다.

   그래서 버튼은 살려 두고 **`onSubmit` 의 가드**가 막는다. 요청은 나가지 않고, 이유는 그 이름을
   입력한 필드 아래에 붙는다 — **서버의 409 가 도착하는 자리와 같다.** 이것은 이 문서 7장 R2 가
   이미 적어 둔 것이기도 하다("확인은 편의이고 판정은 서버다 … F3·F7이 같은 표시 경로를 쓴다").
   승인본 안에서 F3 과 R2 가 서로 다른 것을 말하고 있었고, R2 를 따랐다.
