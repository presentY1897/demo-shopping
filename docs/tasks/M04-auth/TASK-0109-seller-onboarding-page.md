# TASK-0109: 판매자 입점 신청 · 스토어 설정 화면

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M04 인증·계정 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-03 |
| 브랜치 | `feature/seller-onboarding-page` |
| 선행 작업 | TASK-0108, TASK-0023, TASK-0019, TASK-0017, TASK-0107 |

> **분할 유래** — TASK-0026(판매자 입점 신청 · 승인)의 판매자 화면 절반이다. D-208 에 따라 화면과 API 를
> 나눴고, API 는 TASK-0108 이 맡는다. TASK-0027 에 있던 **판매자 스토어 설정 화면**도 여기로 옮겼다 —
> 입점 신청 폼과 스토어 설정 폼은 같은 필드를 쓰므로 한 화면에서 다루는 것이 자연스럽다.

## 1. 목적

`apps/seller` 에서 입점 신청과 스토어 설정을 하는 화면을 만든다. 신청 전·심사 중·반려·운영 중이라는
**네 가지 상태가 같은 화면의 다른 얼굴**이 되게 하는 것이 이 화면의 핵심이다.

이 작업이 끝나면 판매자는 브라우저만으로 입점을 신청하고, 반려 사유를 확인해 재신청하고, 승인 후에는
같은 폼으로 브랜드 정보를 고칠 수 있다.

## 2. 범위

### 포함
- `/apply` — 입점 신청 폼 (브랜드명 · 스토어 slug · 소개 · 로고 URL)
- **브랜드명 실시간 중복 확인** — 입력 정지 후 조회, 결과를 필드 옆에 표시
- **상태별 화면 분기** — 신청 전(폼) / `PENDING`(안내) / `REJECTED`(사유 + 재신청) / `ACTIVE`(설정 폼) /
  `SUSPENDED`(제한 안내)
- `/settings` — 스토어 설정 (브랜드명 · 소개 · 로고 수정). 신청 폼과 **같은 필드 컴포넌트를 공유**
- **낙관적 잠금 충돌 안내** — 409 응답 시 "다른 곳에서 수정되었습니다. 최신 내용을 불러올까요?"
- 서버 검증 오류(400 `details`)를 해당 필드에 매핑 (TASK-0017 규약)
- 승인 대기 상태에서 콘솔 사이드바가 안내 화면만 보이게 하는 연동 (TASK-0023 의 메뉴 필터링 활용)
- `sellerApplicationRequestSchema` · `sellerResponseSchema` 로 **모킹 데이터를 만들고 `parse` 로 검증**

### 제외 (이번에 하지 않는 것)
- **입점 API · 상태 머신** → TASK-0108
- **관리자 심사 화면** → TASK-0110
- **로고 이미지 업로드 위젯** → TASK-0033. 이번에는 `logoUrl` 을 입력·붙여넣기로 받고, 위젯이 나온 뒤
  같은 필드를 위젯으로 교체한다. 위젯을 선행으로 걸면 입점 플로 전체가 M05 뒤로 밀린다
- 배송 정책 · 정산 계좌 등 나머지 스토어 설정 (M09 · M12)
- 실제 API 호출 테스트 — 백엔드는 모킹한다 (QUALITY-GATES 6장)

## 3. 요구사항

### 기능 요구사항
- [ ] 로그인한 사용자가 입점 신청 폼을 제출할 수 있다
- [ ] 브랜드명이 이미 쓰이고 있으면 제출 전에 필드 옆에서 알려준다
- [ ] `PENDING` 이면 폼 대신 심사 중 안내가 보인다
- [ ] `REJECTED` 면 사유가 보이고 같은 폼으로 재신청할 수 있다
- [ ] `ACTIVE` 면 같은 폼이 스토어 설정으로 동작한다
- [ ] 저장 중에는 버튼이 잠기고 두 번 눌러도 요청이 한 번만 나간다
- [ ] 서버가 400 을 주면 해당 입력 필드에 메시지가 붙는다
- [ ] 409(낙관적 잠금 충돌)면 덮어쓰지 않고 다시 불러올지 묻는다

### 비기능 요구사항
- 접근성 — 오류 메시지가 `aria-describedby` 로 필드에 연결된다 (TASK-0017 규약)
- 콘솔 화면이므로 밀도 토글이 없다 (2단계 고정, TASK-0019)

## 4. 설계

### 화면 / 컴포넌트

```
apps/seller/app/apply/page.tsx      신청 · 재신청 · 상태 안내
apps/seller/app/settings/page.tsx   스토어 설정 (ACTIVE 전용)
        └ StoreProfileFields        브랜드명 · slug · 소개 · 로고  ← 두 화면이 공유
```

`docs/design/pages.md` 2장의 `/settings`(스토어 설정 — 브랜드명, 로고, 소개, 배송 정책) 중 **브랜드명 ·
로고 · 소개**가 이번 범위다. 배송 정책은 M09 가 같은 화면에 덧붙인다.

### 상태별 얼굴

| `sellerResponseSchema.status` | 화면 |
| --- | --- |
| (스토어 없음) | 신청 폼. 제출 버튼 "입점 신청" |
| `PENDING` | 심사 중 안내 + 제출한 내용 읽기 전용 |
| `REJECTED` | 사유 배너 + 같은 폼(값 채워짐) + 버튼 "재신청" |
| `ACTIVE` | 설정 폼. 버튼 "저장" |
| `SUSPENDED` | 정지 사유 배너 + 폼 비활성 |

**하나의 컴포넌트로 다루는 이유**: 다섯 화면을 따로 만들면 필드 검증 규칙이 다섯 벌이 된다. 원본
TASK-0026 과 TASK-0027 이 신청 폼과 설정 폼을 각각 다른 TASK 에 뒀던 것이 정확히 그 위험이었다.

### 절단면 — `packages/shared` 의 zod 스키마

TASK-0108 이 정의한 스키마를 **그대로 가져다 쓰고, 모킹 응답도 같은 스키마로 만든다.**

| 스키마 | 이 화면에서의 용도 |
| --- | --- |
| `sellerApplicationRequestSchema` | 신청·재신청 폼의 클라이언트 검증 (TASK-0017 어댑터) |
| `sellerStoreUpdateRequestSchema` | 설정 폼의 클라이언트 검증 (`version` 포함) |
| `sellerResponseSchema` | 상태 분기의 입력. **모킹 응답 5종을 이 스키마로 `parse`** |
| `sellerStatusSchema` | 상태별 분기의 유일한 값 출처 (문자열 리터럴을 화면에 적지 않는다) |
| `brandNameAvailabilityResponseSchema` | 중복 확인 응답 |

앱에서 응답 타입을 다시 정의하지 않는다(C1). 모킹 데이터가 스키마를 통과하는지 테스트가 확인한다(C2).

### 역할별 권한

`apps/seller` 진입은 TASK-0023 의 미들웨어가 판정한다. 이 화면은 **역할이 없는 사용자에게도 열려 있어야
한다** — 입점 신청은 아직 판매자가 아닌 사람이 하기 때문이다. 신청 화면은 로그인만 요구하고, 나머지
판매자 메뉴는 `ACTIVE` 가 아니면 보이지 않는다.

## 5. 구현 계획

1. `StoreProfileFields` — TASK-0017 어댑터로 zod 스키마 연결
2. 상태 분기 컨테이너 + 5종 모킹 응답(`parse` 통과 확인)
3. 신청 · 재신청 흐름
4. 브랜드명 중복 확인 (디바운스 · 로딩 · 결과 표시)
5. 스토어 설정 화면 + 낙관적 잠금 충돌 처리
6. 서버 오류 → 필드 매핑, 제출 중 잠금
7. 키보드 순회 · Lighthouse 측정
