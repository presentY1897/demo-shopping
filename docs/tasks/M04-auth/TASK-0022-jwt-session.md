# TASK-0022: JWT 발급 · 갱신 · 로그아웃

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M04 인증·계정 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/jwt-session` |
| 선행 작업 | TASK-0021 |

## 1. 목적

access + refresh 토큰 체계를 구현한다. **세 앱의 세션이 서로 독립**이라는 전제를 코드로 못박는다.

## 2. 범위

### 포함
- access token (짧은 수명, 메모리 보관) / refresh token (httpOnly 쿠키)
- refresh 토큰 저장·회전(rotation)·재사용 감지
- **앱별 세션 분리** — `RefreshToken.app` + **앱별 쿠키 이름**(D-218). `Domain` 미지정만으로는 부족하다
- 토큰 갱신 엔드포인트
- 로그아웃 (현재 앱) / 전체 로그아웃 (모든 앱)
- **`AnonymousPrincipalResolver` 교체** — access token 을 읽는 리졸버로. TASK-0021 이 남긴 자리다
- **TASK-0021 콜백에 세션 얹기** — 흐름도의 ⑤. `CallbackOutcome.user` 를 쓰는 쪽이 생긴다
- 만료된 refresh 토큰 정리

### 제외
- 프론트 인증 UI (TASK-0023)
- 데모 계정 발급 (TASK-0024)
- **역할 검사 데코레이터** → 이미 있다. TASK-0105 의 `@RequirePermission` · `PermissionGuard` ·
  `assertResourceAccess` 가 그 일을 하고, 이 TASK 는 **그것들이 읽을 `RequestPrincipal` 을 진짜로
  채우는 것**까지다. 원문의 "역할 검사 데코레이터" 는 RBAC 가 아직 없던 시점의 표현이다
- 새 도메인 오류 코드 → `AUTH_REQUIRED` 가 이미 있다 (`error-codes.ts`)

## 3. 요구사항

- [ ] shop 에서 로그인해도 seller 는 로그아웃 상태다
- [ ] access 만료 시 자동으로 갱신된다
- [ ] refresh 토큰이 재사용되면 해당 세션 전체가 무효화된다
- [ ] **정상적인 동시 갱신은 무효화되지 않는다** (재시도·탭 둘)
- [ ] 쿠키가 httpOnly · Secure · SameSite 설정을 갖는다
- [ ] 로그아웃하면 해당 앱의 refresh 토큰이 폐기된다
- [ ] refresh 토큰은 **평문으로 저장되지 않는다**
- [ ] Google 로그인이 끝나면 세션이 붙는다 (TASK-0021 ⑤)
- [ ] 인증된 요청이 `RequestPrincipal` 을 갖고, 없으면 익명이다

## 4. 설계

| 토큰 | 수명 | 보관 | 형식 |
| --- | --- | --- | --- |
| access | 15분 | 클라이언트 메모리 | **JWT (HS256)** — 자기완결적이라 매 요청 DB 조회가 없다 |
| refresh | 14일 | httpOnly 쿠키 | **불투명 난수** — JWT 가 아니다 (아래) |

**회전 + 재사용 감지**: 갱신 시 새 refresh 를 발급하고 기존 것을 폐기한다. 폐기된 토큰이 다시 오면
탈취로 간주하고 그 사용자의 해당 앱 세션을 전부 끊는다.

### refresh 는 JWT 가 아니다

`RefreshToken.tokenHash` 가 **다이제스트**를 담는다(스키마 주석: "토큰 자체는 저장하지 않는다").
회전과 재사용 감지가 **매번 DB 를 봐야 하므로** 자기완결적일 이유가 없고, 자기완결적이면 폐기를
표현할 방법이 없다. 그래서 refresh 는 난수이고 DB 가 그 상태를 쥔다.

**JWT 가 필요한 곳은 access 하나뿐이다.** 이 사실이 아래 라이브러리 선택의 전제다.

### 앱별 독립 세션 — `Domain` 미지정만으로는 부족하다

**원문의 근거가 성립하지 않는다.** 자세한 것은 [D-218](../../decisions/2026-09-04-session-04.md).

쿠키를 발급하는 것은 각 앱이 아니라 **세 앱 공통의 API 오리진**이고, 클라이언트가 매 요청에
`credentials: 'include'` 를 붙인다. 그래서 refresh 쿠키 하나는 세 앱 모두가 보낸다 — `Domain` 을
안 붙여도 그렇다. 로컬은 **쿠키가 포트를 구분하지 않아** 더 분명하다.

| 장치 | 막는 것 |
| --- | --- |
| `Domain` 미지정 (유지) | 쿠키가 `demo-shopping.com` 전체로 퍼지는 것 |
| **앱별 쿠키 이름** (`shopping_refresh_<app>`) | 같은 API 오리진 안에서 세 앱이 서로의 세션을 쓰는 것 |

어느 이름을 읽고 쓸지는 **`X-App-Id` 헤더**가 정한다. 그 헤더는 이미 있고 주석에 용도가
"which cookie name to set" 이라고 적혀 있다.

`Path` 는 `/api/v1/auth` 로 좁힌다 — 갱신·로그아웃만 이 쿠키를 쓰고, 다른 요청에 14일짜리 자격이
딸려 나갈 이유가 없다.

### JWT 를 라이브러리 없이 만든다

**새 의존성 없음.** 8장 참조. 근거는 셋이다.

- **쓰는 표면이 함수 둘**이다 — access 토큰 서명 1종, 검증 1종. refresh 는 JWT 가 아니므로(위)
  라이브러리가 맡을 나머지(JWE·JWK·비대칭 키)는 쓰이지 않는다.
- `@nestjs/jwt` → `jsonwebtoken` 은 **의존성을 12~15개** 끌고 온다. `jws`·`semver`·`ms` 와
  **lodash 마이크로패키지 7개**. 지금 `apps/api` 의 dependencies 는 여섯 줄이다.
- 이 저장소는 이미 **AWS SigV4 서명을 259줄로 직접** 만들어 쓴다(`storage/sigv4.ts`). HS256 JWT
  보다 복잡한 암호다. "SigV4 는 직접, JWT 는 라이브러리" 의 경계는 설명할 수 없다.

**`jose` 는 뺐다** — 의존성 0이지만 v6 이 ESM 만 내보내고 `apps/api` 는 `"type": "commonjs"` 다.

**알고리즘을 값으로 두지 않는다.** 헤더는 `{"alg":"HS256","typ":"JWT"}` 로 **고정 생성**하고, 검증은
토큰이 말하는 alg 를 읽지 않는다. 이러면 alg confusion 이 표현 불가능해진다 — 라이브러리를 쓸 때
`algorithms: ['HS256']` 을 빠뜨려 생기는 종류의 실수가 애초에 존재하지 않는다.

서명 비교는 `timingSafeEqual` 이다. 길이가 다르면 던지지 않고 `false` 다.

### 재사용 감지와 정상 재시도 (R2)

회전은 경합에 약하다. 탭 둘이 동시에 갱신하거나 네트워크가 재시도하면 **같은 refresh 가 두 번**
온다. 그것을 탈취로 판정하면 정상 사용자의 세션이 끊긴다.

**진짜 멱등은 불가능하다.** 스키마가 `tokenHash` — 다이제스트만 담고, 후속 토큰을 가리키는 컬럼도
없다. 즉 "아까 발급한 그 토큰을 다시 내려준다" 를 할 수 없다. **해시만 가진 값은 다시 보낼 수
없기 때문**이고, 이것은 구현 방식의 문제가 아니라 해시 저장을 택한 순간 정해진 성질이다.
(2026-09-04 에 이 문서가 한 번 "멱등 재발급" 으로 적혔다가 되돌려졌다. 9장 참조.)

**그래서 유예 창을 쓴다.** `revokedAt` 이 **10초 이내**면 재시도로 보고 한 번 더 회전한다. 그보다
오래됐으면 탈취로 판정하고 그 사용자의 **해당 앱** 토큰을 전부 폐기한다.

| 들어온 것 | 판정 |
| --- | --- |
| 살아있는 토큰 | 회전. 새 쌍을 주고 옛 것에 `revokedAt` |
| `revokedAt` 이 10초 이내 | **재시도.** 다시 회전한다. 세션은 끊지 않는다 |
| `revokedAt` 이 10초 초과 | **탈취.** `(userId, app)` 의 살아있는 토큰 전부 폐기 |
| 만료 | 401. 그 행도 폐기한다 |
| 모르는 해시 | 401. 폐기할 것이 없다 |

### 세션을 끝낼 때는 만료도 함께 당긴다

**유예 창에는 함정이 있고, 구현 중에 실제로 밟았다.** 탈취를 판정해 토큰을 전부 폐기하면 그 토큰들의
`revokedAt` 이 방금이 된다. 다음 요청이 그중 하나를 들고 오면 **창 안**이므로 재시도로 판정되어
다시 회전한다 — **세션이 자기 탈취 탐지를 살아남는다.**

그래서 세션을 끝내는 경로(탈취 판정 · 로그아웃)는 `revokedAt` 뿐 아니라 **`expiresAt` 도 지금으로**
당긴다. 그리고 갱신은 **만료를 폐기보다 먼저** 본다.

| 폐기 이유 | `expiresAt` | 창 안에서 |
| --- | --- | --- |
| 회전 | 원래대로(14일 뒤) | **재시도로 통과** — 이것이 창의 목적이다 |
| 탈취 판정 · 로그아웃 | **지금** | 만료로 거절. 창이 되살리지 못한다 |

검사 순서가 곧 보안 성질이다. 순서를 뒤집으면 위 표의 두 줄이 같아진다.

**이 창이 무엇을 내주는가.** 10초 안에 재생하는 공격자는 유효한 토큰을 받는다. 다만 그때부터
살아있는 토큰이 둘이 되고, **둘 중 하나가 창 밖에서 조상 토큰을 제시하는 순간 전부 폐기된다.**
즉 탐지가 사라지는 것이 아니라 한 주기 늦어진다. 창을 없애면 탐지는 즉시가 되지만 **정상
사용자가 탭 두 개를 열었다는 이유로 로그아웃된다** — 실제로 훨씬 자주 일어나는 쪽이다.

프론트에서 갱신을 single-flight 로 묶으면 빈도가 줄지만 없어지지는 않는다(탭이 여럿이면 프로세스가
여럿이다). 그것은 TASK-0023 의 몫이고, 서버는 그 가정 없이도 옳아야 한다.

### 로그아웃

| 경로 | 하는 일 |
| --- | --- |
| `POST /auth/logout` | **이 앱의** refresh 를 폐기하고 쿠키를 만료. 다른 앱 세션은 그대로 |
| `POST /auth/logout-all` | 그 사용자의 **모든 앱** refresh 를 폐기. 쿠키는 이 앱 것만 지울 수 있다 |

`logout-all` 이 다른 앱의 쿠키를 지우지 못하는 것은 제약이 아니라 사실이다 — 그 쿠키는 이름이
달라 이 응답으로 건드릴 수 없다. 다만 **DB 의 토큰이 폐기되므로 그 쿠키는 다음 갱신에서 죽는다.**

### `AnonymousPrincipalResolver` 를 교체한다

TASK-0021 이 남긴 자리다. 새 리졸버는 `Authorization: Bearer <access>` 를 읽어
`RequestPrincipal` 을 만든다. **`PermissionGuard` 와 `assertResourceAccess` 는 바뀌지 않는다** —
TASK-0105 가 만든 그것들이 읽을 값이 이제 진짜가 될 뿐이다.

토큰이 없거나 상하면 **익명**으로 둔다. 401 을 내는 것은 리졸버가 아니라 가드다(`AUTH_REQUIRED`) —
공개 엔드포인트가 토큰 없이도 동작해야 하기 때문이다.

## 5. 구현 계획

1. HS256 서명·검증 순수 모듈 (`node:crypto`, 분기 100% 대상)
2. env 스키마에 `JWT_SECRET` + `.env.example` · `render.yaml` 반영
3. 앱별 쿠키 이름·속성 (D-218), `X-App-Id` 로 고르기
4. access/refresh 발급 + refresh 해시 저장
5. 회전 · 유예 창 안의 재시도 처리 · 탈취 판정
6. 갱신 · 로그아웃 · 전체 로그아웃 엔드포인트
7. `AnonymousPrincipalResolver` → access token 리졸버 교체
8. TASK-0021 콜백에 ⑤ 얹기
9. 만료 토큰 정리
10. 실제 PostgreSQL 통합 테스트 + 동시 갱신 경합 테스트

| R2 | 재사용 감지 오탐(네트워크 재시도) | **10초 유예 창**(4장). 한때 「멱등 재발급」으로 적었으나 스키마가 해시만 담아 구현 불가능하다 — 다시 보낼 평문이 없다. 창이 내주는 것과 없앨 때 잃는 것을 4장에 적었다 |
| R3 | **`JWT_SECRET` 이 없는 환경** | R2·Google 과 달리 **없으면 부팅을 거부한다.** 로그인은 선택 기능이 아니고, 없는 채로 뜨면 모든 인증 요청이 500 이 된다. CI 는 테스트 설정이 값을 주므로 영향 없다 |
| R4 | access 토큰이 탈취되면 15분간 유효하다 | 폐기 목록을 두지 않는다 — 매 요청 DB 조회를 되살려 자기완결 토큰의 이유를 없앤다. 15분이 그 절충이고, 계정 단위 차단이 필요해지면 M14 가 다룬다 |

## 8. 확정된 버전

**새 의존성 없음.** `@nestjs/jwt`(→ `jsonwebtoken`)를 쓰지 않는다 — 근거는 4장 「JWT 를
라이브러리 없이 만든다」. HS256 서명·검증은 `node:crypto` 의 `createHmac` · `timingSafeEqual` 로
충분하고, 이 저장소는 이미 더 복잡한 AWS SigV4 를 직접 만들어 쓴다.
