## 1. 목적

세 앱에 로그인 화면과 경로 보호를 붙인다. 권한 없는 사용자가 콘솔에 접근하지 못하게 한다.

## 2. 범위

### 포함
- 앱별 로그인 페이지 (Google 버튼 + 데모 발급 진입점 자리)
- Next.js 미들웨어 권한 가드 — `apps/seller` 는 `SELLER_OWNER`, `apps/admin` 은 `ADMIN_*` 역할 필요
- API 는 **퍼미션 기반 가드**(TASK-0105)를 사용한다. 미들웨어는 앱 진입 여부만 판정
- **프론트 권한 훅 — 버튼 비활성 + 사유 툴팁** (2026-09-03 TASK-0105 에서 이관). `@shopping/shared` 의 `canPerform` · `authorizeResource` 를 감싸 `can(permission)` · `reason(permission)` 을 제공한다
- 인증 상태 컨텍스트, 자동 토큰 갱신 인터셉터
- 로그인 후 원래 가려던 경로로 복귀
- 헤더·상단바의 사용자 메뉴 (프로필·로그아웃)
- 권한 없음 / 승인 대기 안내 화면
- 콘솔 사이드바 메뉴를 역할에 따라 필터링

### 제외
- 데모 발급 실제 동작 (TASK-0024)
- 프로필 편집 (TASK-0027)

## 3. 요구사항

- [ ] 비로그인 상태로 보호 경로 접근 시 로그인으로 이동한다
- [ ] 로그인 후 원래 경로로 돌아온다
- [ ] SELLER 역할이 없으면 판매자 콘솔에 들어갈 수 없다
- [ ] access 만료 시 사용자가 눈치채지 못하게 갱신된다
- [ ] 승인 대기 판매자는 안내 화면을 본다
- [ ] 권한 없는 버튼이 비활성 + 사유가 표시된다 (TASK-0105 에서 이관)

## 4. 설계

```
middleware.ts (seller)
  요청 → refresh 쿠키 확인 → 없으면 /login?next=<경로>
                            → 있으면 access 갱신 → 역할에 SELLER 없으면 /no-permission
```

역할 검사는 **서버(미들웨어와 API 가드) 양쪽**에서 한다. 미들웨어만 있으면 API 를 직접 호출해 우회할 수 있다.

역할이 두 층으로 나뉜다 — **미들웨어는 "이 앱에 들어올 수 있나"(역할), API 가드는 "이 동작을 할 수 있나"(퍼미션 + 스코프)** 를 본다.

### 권한 훅 (TASK-0105 에서 이관)

권한 없는 버튼은 **숨기지 않고 비활성 + 사유 툴팁**으로 보여준다. 기능이 있다는 것을 알리는 게 데모의 목적이다.

```tsx
<Button disabled={!can('user.delete')} title={reason('user.delete')}>
```

판정 로직은 새로 만들지 않는다. TASK-0105 가 `@shopping/shared` 에 넣은 순수 함수
(`canPerform` · `authorizeResource` · `AuthorizationSubject`)를 그대로 쓰고, 훅은 세션에서
`AuthorizationSubject` 를 만들어 넘기는 일만 한다. 서버와 화면이 같은 표를 읽어야
"버튼은 살아 있는데 호출하면 403" 이 생기지 않는다.

`reason()` 문구는 API 403 응답의 `details` 와 같은 어휘를 쓴다 — 거부 사유는
`missing_permission`(그 역할이 못 하는 일) / `out_of_scope`(할 수는 있지만 이 리소스에는 안 되는 일)
두 가지다.
