# TASK-0023: 인증 UI · 권한 가드

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M04 인증·계정 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/auth-guard` |
| 선행 작업 | TASK-0022 |

## 1. 목적

세 앱에 로그인 화면과 경로 보호를 붙인다. 권한 없는 사용자가 콘솔에 접근하지 못하게 한다.

## 2. 범위

### 포함
- 앱별 로그인 페이지 (Google 버튼 + 데모 발급 진입점 자리)
- **앱 진입 가드** — `apps/seller` 는 `SELLER_OWNER`, `apps/admin` 은 `ADMIN_*` 역할 필요.
  Next 미들웨어가 아니라 **클라이언트 부팅 시점**에 판정한다 (4장 「미들웨어는 쿠키를 볼 수 없다」)
- API 는 **퍼미션 기반 가드**(TASK-0105)를 사용한다. 앱 가드는 앱 진입 여부만 판정
- **프론트 권한 훅 — 버튼 비활성 + 사유 툴팁** (2026-09-03 TASK-0105 에서 이관). `@shopping/shared` 의 `authorizePermission` · `authorizeResource` 를 감싸 `can(permission)` · `reason(permission)` 을 제공한다
- 인증 상태 컨텍스트, 자동 토큰 갱신 인터셉터 (single-flight)
- 로그인 후 원래 가려던 경로로 복귀
- 헤더·상단바의 사용자 메뉴 (프로필 자리·로그아웃)
- 권한 없음 / 콘솔 이용 불가 안내 화면
- 콘솔 사이드바 메뉴를 퍼미션에 따라 필터링

### 제외
- 데모 발급 실제 동작 (TASK-0024)
- 프로필 편집 (TASK-0112)
- **판매자 입점 상태(`PENDING` · `REJECTED` · `SUSPENDED`)를 구분한 안내** — 세션 응답에 상태가 없다.
  4장 「승인 대기를 구분할 계약이 없다」 · 7장 R2

## 3. 요구사항

- [ ] 비로그인 상태로 보호 경로 접근 시 로그인으로 이동한다
- [ ] 로그인 후 원래 경로로 돌아온다
- [ ] SELLER 역할이 없으면 판매자 콘솔에 들어갈 수 없다
- [ ] access 만료 시 사용자가 눈치채지 못하게 갱신된다
- [ ] 콘솔에 들어갈 수 없는 계정은 안내 화면을 본다
- [ ] 권한 없는 버튼이 비활성 + 사유가 표시된다 (TASK-0105 에서 이관)

## 4. 설계

```
앱 부팅(클라이언트)
  POST /api/v1/auth/refresh   (헤더 X-App-Id, refresh 쿠키는 브라우저가 붙인다)
    ├─ 401 → 익명 → 보호 경로면 /login?next=<경로>
    └─ 200 → access 토큰(메모리) + user{ id, roles, sellerId }
              └─ 이 앱에 필요한 역할이 없으면 /no-permission
```

역할 검사는 **서버(API 가드)와 화면 양쪽**에서 한다. 화면 가드만 있으면 API 를 직접 호출해 우회할 수 있고,
API 가드만 있으면 사용자가 빈 화면과 403 을 마주한다.

역할이 두 층으로 나뉜다 — **앱 가드는 "이 앱에 들어올 수 있나"(역할), API 가드는 "이 동작을 할 수 있나"(퍼미션 + 스코프)** 를 본다.

### 미들웨어는 쿠키를 볼 수 없다

**원문의 `middleware.ts` 설계는 성립하지 않는다.** refresh 쿠키를 심는 것은 앱이 아니라 **API 오리진**이고
(TASK-0022 4장 · D-218), 그 쿠키에는 `Domain` 이 없다. 그래서 브라우저는 그것을 API 호스트에만 보낸다.

| | 로컬 | 운영 |
| --- | --- | --- |
| 앱 | `localhost:3011` | `seller.demo-shopping.com` |
| 쿠키 주인 | `localhost` (`Path=/api/v1/auth`) | `api.demo-shopping.com` |
| 앱 요청에 쿠키가 실리는가 | **아니오** — `Path` 가 다르다 | **아니오** — 호스트가 다르다 |

즉 `middleware.ts` 가 `request.cookies` 에서 읽을 것이 **없다.** 로컬에서 호스트가 우연히 같아 보이는 것은
쿠키가 포트를 구분하지 않기 때문이고, 그마저 `Path=/api/v1/auth` 가 막는다. 게다가 쿠키는 `HttpOnly` 라
스크립트도 읽지 못한다.

**그래서 가드는 클라이언트에서 부팅 시 한 번 도는 갱신 요청이다.** 이것은 우회로가 아니라 원래 R1 이
말하던 것과 같은 결론이다 — "갱신은 클라이언트 인터셉터가 담당한다". 미들웨어가 할 수 있는 일이 남지
않으므로 `middleware.ts` 를 만들지 않는다.

**잃는 것과 얻는 것.** 잃는 것은 서버 리다이렉트다 — 비로그인 방문자는 콘솔 셸의 첫 프레임(스켈레톤)을
보고 나서 로그인으로 이동한다. 얻는 것은 정확성이다: 미들웨어 판정은 **쿠키의 존재**만 볼 수 있었고
(만료·폐기된 쿠키도 통과), 클라이언트 판정은 **세션이 실제로 살아 있는지와 역할까지** 본다. 콘솔 화면은
어차피 `noindex` 이고 SSR 로 내용을 그리지 않으므로 첫 프레임의 손실이 없다.

### 승인 대기를 구분할 계약이 없다

원문 F6 은 "PENDING 판매자로 접속 → 승인 대기 안내" 였다. **오늘의 세션 응답으로는 그 판정을 할 수 없다.**

`sessionResponseSchema` 가 주는 것은 `id` · `roles` · `sellerId` 뿐이다. `Seller.status` 는 스키마에 있지만
그것을 실어 나르는 엔드포인트가 없고, 그 API 는 **TASK-0108** 이 만드는 중이다.

`sellerId !== null && roles 에 SELLER_OWNER 없음` 으로 추론할 수는 있다. 하지만 그 조건은 `PENDING` 과
`REJECTED` 를 **구분하지 못한다** — 반려된 판매자에게 "심사 중입니다" 를 보여주는 화면이 된다. 그래서
추론하지 않는다.

**이 TASK 가 하는 것**: 콘솔에 들어올 수 없는 계정에게 하나의 안내 화면(`/no-permission`)을 보여준다.
미신청 · 심사 중 · 반려를 아직 구분하지 않는다는 사실을 화면이 스스로 말한다.

**이월**: 상태별 안내와 재신청 동선은 **TASK-0109**(판매자 입점 신청 화면)가 TASK-0108 의 상태 계약 위에서
회수한다. 필요한 것은 `GET /sellers/me` 류의 조회이거나 세션 응답에 실린 상태 한 칸이며, **어느 쪽인지는
TASK-0108 이 정한다.**

### 자동 갱신은 single-flight 다

access 토큰은 메모리에 있고 15분이다. `createApiClient` 에 **인증하는 `fetch` 를 주입**해서 처리한다 —
`ApiClientOptions.fetch` 가 이미 그 자리다. `packages/shared` 를 고치지 않는다.

| 시점 | 하는 일 |
| --- | --- |
| 요청 전 | 만료 30초 전이면 **미리** 갱신한다. 401 을 만들 이유가 없다 |
| 401 을 받으면 | 갱신하고 **한 번만** 재시도한다 |
| 갱신 중 다른 요청이 오면 | **같은 약속을 기다린다.** 두 번 부르지 않는다 |

single-flight 가 필요한 이유는 서버의 10초 유예 창(TASK-0022 4장)이 아니다. 그 창이 있어 치명적이지
않을 뿐이고, 회전은 매번 새 refresh 를 심으므로 **동시에 두 번 부르면 하나의 결과가 버려진다.**

### 권한 훅은 판정을 다시 만들지 않는다

권한 없는 버튼은 **숨기지 않고 비활성 + 사유**로 보여준다. 기능이 있다는 것을 알리는 게 데모의 목적이다.

판정 로직은 새로 만들지 않는다. TASK-0105 가 `@shopping/shared` 에 넣은 순수 함수
(`authorizePermission` · `authorizeResource` · `AuthorizationSubject`)를 그대로 쓰고, 훅은 세션에서
`AuthorizationSubject` 를 만들어 넘기는 일만 한다. 서버와 화면이 같은 표를 읽어야
"버튼은 살아 있는데 호출하면 403" 이 생기지 않는다.

`reason()` 문구는 API 403 응답의 `details` 와 같은 어휘를 쓴다 — 거부 사유는
`missing_permission`(그 역할이 못 하는 일) / `out_of_scope`(할 수는 있지만 이 리소스에는 안 되는 일)
두 가지이고, `denialReasons` 가 그 목록의 단일 출처다.

**비활성은 `disabled` 가 아니라 `aria-disabled` 다.** 네이티브 `disabled` 는 탭 순서에서 빠지므로 키보드
사용자는 버튼이 있다는 것도, 왜 못 누르는지도 알 수 없다 — P4 를 통과하지 못한다. `packages/ui` 의
`Button` 이 `loading` 에 이미 쓰고 있는 방식(`aria-disabled` + 핸들러 차단)을 사유가 있는 경우로 넓힌
`GuardedButton` 을 더한다.

**실제 적용 지점은 관리자 카테고리·속성 콘솔의 삭제 버튼이다.** `DELETE /categories/:id` 가
`catalog.delete` 를 요구하고, `ADMIN_OPERATOR` 와 `DEMO_ADMIN` 은 그것을 **갖고 있지 않다**
(`role-permissions.ts`). 즉 지어낸 예시가 아니라 오늘 서버가 403 을 내는 자리다.

### 메뉴 필터는 오늘 아무것도 가리지 않는다 — 그래도 넣는다

사이드바 항목마다 그 화면이 첫 번째로 부를 **조회 퍼미션**을 적고 걸러낸다. 다만 오늘의 역할 표에서는
콘솔에 들어올 수 있는 역할(`SELLER_OWNER` · `ADMIN_OPERATOR` · `ADMIN_SUPER` · `DEMO_ADMIN`)이 **모든
`*.read` 를 갖는다** — `DEMO_ADMIN` 도 조회는 `any` 로 남기기 때문이다(`role-permissions.ts`). 그래서
가려지는 항목이 하나도 없다.

없는 차이를 만들어 내지 않는다. 필터는 **순수 함수 검사**로 증명하고, 화면 검사는 "오늘은 전부 보인다"
를 확인한다. `/commissions`(수수료 설정)과 `/reports`(신고 처리)는 대응하는 퍼미션이 아직 없으므로
걸지 않고 비워 둔다 — M12 · M13 이 채운다.

### 로그인 화면이 읽는 것

콜백은 `{앱 오리진}/login?status=…&reason=…&notice=…` 로 돌아온다(TASK-0021 복귀 계약). 화면은
`parseOauthResult` 로 읽고, 값이 상해서 `null` 이면 일반 문장을 보여준다.

| 실린 값 | 화면 |
| --- | --- |
| `status=ok` | 세션을 갱신하고 `next` 로 이동 |
| `status=ok&notice=no_role` | 로그인은 됐지만 이 콘솔에 역할이 없다는 안내 |
| `status=cancelled` | 오류가 아니다. 조용히 로그인 화면 |
| `status=error&reason=…` | 네 가지 사유별 문장 |

세션 갱신이 거절될 때의 사유(`sessionFailureReasons`)도 같은 자리에서 문장이 된다 — `reused` 만 "보안을
위해 로그아웃했다" 로 다르게 말한다.

**세 앱의 문구는 각 앱의 메시지 카탈로그가 갖는다.** 새 `auth` 슬라이스는 위 네 유니온
(`oauthOutcome` · `oauthFailureReason` · `oauthNotice` · `sessionFailureReason`)과 `denialReasons` 로
**타입상 전수**이므로, `@shopping/shared` 에 값이 하나 늘면 세 앱이 `pnpm typecheck` 에서 걸린다.

### `apps/shop` 에 `errors.ts` 를 들이지 않는다

`docs/HANDOFF.md` 3.3 이 "세 번째 앱이 필요로 할 때" 를 `api-failure.ts` 통합의 발동 조건으로 뒀다.
**이 TASK 는 그 조건을 만족시키지 않는다.**

shop 이 이 TASK 에서 마주하는 API 실패는 둘뿐이다 — 갱신 거절(`AUTH_REQUIRED` + `details[].params.reason`)
과 API 에 닿지 못함. 둘 다 `domainErrorCode` 카탈로그가 아니라 위의 `auth` 슬라이스가 답한다.
`Record<UserFacingErrorCode, string>` 을 shop 에 들이면 **닿을 수 있는 문장이 하나뿐인 15줄짜리 카탈로그**
가 생기고, 그것이야말로 TASK-0117 4.7 J6 이 "카탈로그가 조용히 어긋난다" 며 admin 에만 준 이유다.

판단과 근거는 6.3 D3 · 9장에 남긴다.

## 5. 구현 계획

1. `packages/ui` — 사유를 말하는 비활성 버튼(`GuardedButton`) + 스토리, 메뉴 필터 순수 함수
2. `packages/api-mocks` — `/auth/refresh` · `/auth/logout` 대역과 세션 픽스처
3. 세 앱 공통 — 세션 클라이언트(메모리 토큰 · single-flight 갱신) + 인증 컨텍스트 + 권한 훅
4. 로그인 화면 3벌, 복귀 경로 처리
5. 콘솔 진입 가드 + `/no-permission` 안내 화면
6. 사용자 메뉴(로그아웃), 메뉴 퍼미션 필터
7. 관리자 카테고리·속성 콘솔의 삭제 버튼에 권한 훅 적용
