## 1. 목적

리뷰를 만든다. **구매 검증을 애플리케이션이 아니라 스키마가 강제**하는 것이 설계의 핵심이다.

## 2. 범위

### 포함
- `Review` — `orderItemId` **unique**, 상품, 사용자, 평점, 내용, 상태
- `ReviewImage` — 사진 첨부
- 작성 가능 조건 — 배송완료 이상, 작성 기한 내
- 작성·수정·삭제 API (본인만, 수정 기한 제한)
- 작성 가능한 리뷰 목록 (마이페이지)
- 이미지 업로드 연동
- 작성 유도 알림 이벤트 자리

### 제외
- 표시·집계 (TASK-0084)
- 판매자 답변 (TASK-0085)

## 3. 요구사항

- [x] 구매하지 않은 상품에는 리뷰를 쓸 수 없다
- [x] 같은 주문 항목에 리뷰를 두 번 쓸 수 없다
- [x] 배송완료 전에는 쓸 수 없다
- [x] 본인 리뷰만 수정·삭제할 수 있다
- [x] 사진을 첨부할 수 있다

## 4. 설계

```
Review.orderItemId  UNIQUE   ← 구매 검증과 중복 방지를 DB 가 보장
```

**애플리케이션 검사 대신 스키마로 막는 이유**: 코드 검사는 우회 경로가 생기면 뚫린다. `orderItemId` 를 필수 unique 로 두면 구매하지 않은 사람은 참조할 행이 없어 애초에 만들 수 없다. 중복도 같은 제약으로 막힌다.

수정 기한: 작성 후 30일. 무기한 수정을 허용하면 좋은 리뷰를 받고 나중에 내용을 바꾸는 조작이 가능하다.

### 4.1 서비스에 「샀는가」를 묻는 코드가 한 줄도 없다

4장의 한 줄을 그대로 만들었더니 그렇게 됐다. 요청이 가리키는 것이 **주문 항목**이므로, 그 항목이 이 사람의 것이 아니면 조회가 아무것도 찾지 못한다. 중복도 마찬가지다 — `Review.orderItemId` 가 유니크라, 이 서비스의 검사를 모두 우회해 들어와도 두 번째 행은 저장되지 않는다.

**검사도 그 구조를 재도록 썼다.** 스펙의 두 검사가 서비스를 통째로 건너뛰고 DB 에 직접 넣어 본다 — 하나는 중복을, 하나는 「사지 않은 상품의 리뷰」를 시도한다. 이 두 검사가 이 TASK 의 설계 그 자체다 (D-238).

### 4.2 「이 상품의 리뷰」도 조회 없이 참이다

상품 상세가 읽는 축이 `productId` 인데, 리뷰에서 상품까지 되짚으려면 세 표를 지나야 한다. 그래서 사본을 두되 **거짓이 될 수 없게** 만들었다:

```
OrderItem(variantId, productId) → ProductVariant(id, productId)
Review(orderItemId, productId) → OrderItem(id, productId)
```

주문 항목마다 유니크 인덱스 하나를 더 쓰는 값이고, 그 값으로 사는 것은 **규율이 아니라 제약이 지키는 사본**이다. 딸려 온 이득으로 정산의 「많이 팔린 상품」이 스냅샷 JSON 에서 상품 id 를 꺼내던 것을 그만두고 컬럼을 읽는다.

### 4.3 지운 리뷰는 행이 남고, 다시 쓸 수 없다

신고가 그 행을 가리키고 있을 수 있고(TASK-0091), 지웠다 다시 쓰는 길을 열면 「좋은 리뷰를 쓰고 혜택을 받은 뒤 지우고 나쁜 리뷰를 쓴다」가 가능해진다 — **수정 기한이 막으려는 것과 같은 조작**이다. 마음이 바뀌었으면 기한 안에 고쳐 쓴다 (D-239).

### 4.4 작성 기한은 90일, 수정 기한의 기준은 「쓴 시각」

작성 기한이 있는 이유는 **오래된 리뷰가 지금의 상품을 설명하지 못하기** 때문이고, 90일인 것은 구매확정(D+7)보다 넉넉히 뒤여야 쓸 수 있는 창이 실제로 존재하기 때문이다.

수정 기한의 기준이 「고친 시각」이 아닌 것이 중요하다 — 고칠 때마다 30일이 새로 시작하면 무기한 수정과 같아지고, 4장이 막으려던 조작이 그대로 가능해진다.

### 4.5 남의 것을 물으면 「없다」고 답한다

남의 주문 항목에 리뷰를 쓰려는 요청에 403 을 주면 **그 id 가 존재한다는 사실을 알려 주는 것**이 된다. 404 는 「당신에게는 없다」이고, 그것이 사실이다.

사진도 같은 판단이다. 없는 사진인지 남의 사진인지 갈라 답하면 열쇠를 넣어 보는 것만으로 남의 사진이 있다는 사실을 알 수 있다.

### 4.6 이름은 서버가 가려서 내려보낸다

리뷰는 로그인하지 않은 사람도 읽는다. 가리는 일을 화면마다 하게 두면 한 화면이 잊는 날 그 화면만 이름을 다 보여 주고, 그때 증상은 오류가 아니라 **이미 공개된 개인정보**다 (D-246).
