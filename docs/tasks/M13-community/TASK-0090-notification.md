# TASK-0090: 알림 시스템

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M13 회원 부가 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/notification` |
| 선행 작업 | M12 완료 |

## 1. 목적

앞선 마일스톤들이 발행해 둔 알림 이벤트를 실제 알림으로 만든다. 앱 내 알림센터만 구현하고 이메일·푸시는 범위 밖이다. (D-030)

## 2. 범위

### 포함
- `Notification` — 사용자, 유형, 제목, 본문, 링크, 읽음 여부
- 이벤트 → 알림 변환 (주문 상태 변경, 배송 시작·완료, 클레임 처리, 답변 등록, 재입고, 신상품, 정산)
- 알림센터 (헤더 드롭다운 + 전체 목록 페이지)
- 읽음 처리 (개별·전체)
- 미읽음 배지
- 알림 유형별 수신 설정 (`UserPreference`)
- 오래된 알림 정리 배치
- 판매자·관리자 알림 (신규 주문, 클레임, 승인 요청)

### 제외
- 이메일·푸시·SMS
- 실시간 푸시(WebSocket) — 폴링으로 처리

## 3. 요구사항

- [ ] 주문 상태가 바뀌면 구매자에게 알림이 온다
- [ ] 알림을 클릭하면 관련 화면으로 이동한다
- [ ] 미읽음 개수가 배지에 표시된다
- [ ] 유형별로 수신을 끌 수 있다
- [ ] 알림 생성이 원래 작업을 지연시키지 않는다

## 4. 설계

```
도메인 이벤트 → 알림 핸들러 → 수신 설정 확인 → Notification 생성
                                                  ↓
                              헤더 폴링(30초) 또는 화면 진입 시 조회
```

**알림 생성을 비동기로** 처리한다. 주문 상태 변경 트랜잭션에 알림 생성이 끼면 실패 지점이 늘어난다.

**실시간 푸시를 하지 않는 이유**: WebSocket 인프라를 추가하는 비용 대비 얻는 게 적다. 30초 폴링으로 충분하고, 데모에서 세 탭을 동시에 열어 상태 변화를 보는 시나리오도 이 정도면 자연스럽다.

### 4.1 던지지 않고, 기다리지 않는다 (F6)

알림 서비스는 **예외를 삼킨다.** 그리고 부르는 쪽은 `await` 하지 않는다. 주문 상태 변경 트랜잭션에 알림 생성이 끼면 실패 지점이 늘어나고, 그 실패는 「배송 처리가 안 됐다」로 나타난다 — 알림을 못 받는 것과 물건이 안 가는 것은 다른 일이다 (D-242).

### 4.2 부르는 자리는 이미 정해져 있었다

TASK-0059 가 `SellerOrderEvents` 포트를 남기며 「부르는 자리는 지금 정해야 한다 — 전이가 일어나는 곳이 여기뿐인 동안에 자리를 잡아야, 나중에 **상태를 바꾸는 코드 전부를 찾아 알림을 끼워 넣는** 작업이 되지 않는다」고 적어 두었다. 그 예상이 맞았다: 여기 한 곳을 채우는 것으로 발송 · 배송완료 · 취소 · 확정이 전부 알림을 갖는다.

### 4.3 배지를 올리는 알림은 읽을 이유가 있어야 한다

전부에 알리지 않는다. **결제완료**는 사람이 방금 누른 결과라 알림이 「방금 한 일」을 다시 말하는 것이 되고, **준비중**은 판매자의 내부 상태라 구매자에게는 아직 아무 일도 일어나지 않은 것과 같다.

같은 전이가 두 사람에게 **다른 말**을 하기도 한다 — 구매자에게 결제완료는 알릴 것이 아니지만 판매자에게는 「새 주문이 들어왔다」다.

### 4.4 수신 설정을 보내기 전에 본다 (F5)

만들어 두고 화면에서 거르면 **끈 사람의 배지가 올라간다.** 배지는 「할 일이 몇 개」이고 읽지 않을 알림은 할 일이 아니다.

스위치는 `UserPreference` 의 기존 세 칸에 얹었다. 새 칸을 만들지 않은 이유는 그 셋이 이미 사람이 이해하는 축이기 때문이다 — 「거래」와 「취소·반품」과 「홍보」.

**스위치가 없는 것들이 있다.** 답변 알림은 내가 물어본 것에 대한 답이라 끄는 것이 뜻을 갖지 않고, 재입고·신상품은 찜과 팔로우가 곧 신청이라 끄는 방법이 이미 있다 — 홍보 스위치(기본 꺼짐)에 묶으면 **신청해 놓고 안 오는** 상태가 만들어진다.

### 4.5 배지를 위한 라우트가 따로 없다

목록이 미읽음 수를 함께 답한다. 따로 두면 목록을 연 화면이 같은 것을 두 번 묻고, 헤더는 `limit=5&unreadOnly=true` 한 번으로 목록과 배지를 함께 얻는다.

### 4.6 보관 기간이 지나면 **안 읽은 것도** 지운다

90일을 안 읽었다는 것은 그 알림이 할 일을 이미 놓쳤다는 뜻이고, **배지에 영영 남는 숫자는 배지를 무의미하게 만든다.**

### 4.7 링크는 앱 안의 경로다

알림을 읽는 앱이 셋이고 각자 자기 도메인에서 연다. 도메인을 데이터에 실으면 배포마다 달라지는 값이 굳고, 도메인을 옮기는 날 **지난 알림이 전부 남의 사이트를 가리킨다** (F2).
