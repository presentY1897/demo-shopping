## 1. 목적

앞선 마일스톤들이 발행해 둔 알림 이벤트를 실제 알림으로 만든다. 앱 내 알림센터만 구현하고 이메일·푸시는 범위 밖이다. (D-030)

## 2. 범위

### 포함
- `Notification` — 사용자, 유형, 제목, 본문, 링크, 읽음 여부
- 이벤트 → 알림 변환 (주문 상태 변경, 배송 시작·완료, 클레임 처리, 답변 등록, 재입고, 신상품, 정산)
- 알림센터 (헤더 드롭다운 + 전체 목록 페이지)
- 읽음 처리 (개별·전체)
- 미읽음 배지
- 알림 유형별 수신 설정 (`UserPreference`)
- 오래된 알림 정리 배치
- 판매자·관리자 알림 (신규 주문, 클레임, 승인 요청)

### 제외
- 이메일·푸시·SMS
- 실시간 푸시(WebSocket) — 폴링으로 처리

## 3. 요구사항

- [ ] 주문 상태가 바뀌면 구매자에게 알림이 온다
- [ ] 알림을 클릭하면 관련 화면으로 이동한다
- [ ] 미읽음 개수가 배지에 표시된다
- [ ] 유형별로 수신을 끌 수 있다
- [ ] 알림 생성이 원래 작업을 지연시키지 않는다

## 4. 설계

```
도메인 이벤트 → 알림 핸들러 → 수신 설정 확인 → Notification 생성
                                                  ↓
                              헤더 폴링(30초) 또는 화면 진입 시 조회
```

**알림 생성을 비동기로** 처리한다. 주문 상태 변경 트랜잭션에 알림 생성이 끼면 실패 지점이 늘어난다.

**실시간 푸시를 하지 않는 이유**: WebSocket 인프라를 추가하는 비용 대비 얻는 게 적다. 30초 폴링으로 충분하고, 데모에서 세 탭을 동시에 열어 상태 변화를 보는 시나리오도 이 정도면 자연스럽다.

## 5. 구현 계획

1. 스키마·마이그레이션
2. 알림 유형 정의·템플릿
3. 이벤트 핸들러 (기존 이벤트 자리에 연결)
4. 수신 설정 확인
5. 알림센터 UI (드롭다운·페이지)
6. 읽음 처리·배지·폴링
7. 정리 배치
