## 1. 목적

상품 문의와 판매자 답변을 만든다. 구매 전 문의라 구매 검증이 없다는 점이 리뷰와 다르다.

## 2. 범위

### 포함
- `ProductQuestion` / `ProductAnswer`
- 문의 작성 (공개/비공개 선택)
- 판매자 답변
- 상품 상세의 Q&A 섹션 (밀도 맥시멀에서만 노출)
- 마이페이지 내 문의 목록
- 판매자 문의 관리 화면 (미답변 우선)
- 비공개 문의는 작성자·판매자·관리자만 조회
- 답변 알림 이벤트

### 제외
- 신고 처리 (TASK-0091)

## 3. 요구사항

- [x] 로그인한 사용자가 문의를 남길 수 있다
- [x] 비공개 문의는 제3자에게 보이지 않는다
- [x] 판매자가 자기 상품 문의에만 답변할 수 있다
- [x] 답변이 달리면 작성자에게 알림이 간다
- [x] 미답변 문의가 판매자 화면에서 우선 표시된다

## 4. 설계

**비공개 문의의 접근 제어**를 API 레벨에서 처리한다. 목록 조회 시 조건으로 필터링하고, 상세 조회 시에도 권한을 재확인한다. 클라이언트에서 숨기는 방식은 안 된다.

Q&A 를 **맥시멀 단계에서만 노출**하는 이유: 미니멀 상품 페이지에 문의 목록이 붙으면 정보 밀도가 올라가 밀도 구분이 흐려진다. 표준·미니멀에서는 링크나 접힘으로 처리한다.

### 4.1 남의 비공개 문의는 **줄 자체가 오지 않는다**

내용을 비우고 보내는 길도 있었지만, 그러면 「여기 뭔가 있다」가 새어 나간다 — 「이 상품에 비공개 문의가 세 건 있다」는 그 자체로 정보다 (D-244).

거르는 자리는 **질의의 조건**이다 (4장이 말하는 「API 레벨」이 이것이다). 조회의 축이 넷(상품 · 작성자 · 스토어 · 하나)인데 한 함수인 이유도 그것이다 — 규칙이 네 곳에 흩어지면 그중 하나가 잊히는 날 새어 나간다.

### 4.2 판매자는 비공개 문의도 본다

답할 사람이 읽지 못하면 **비공개 문의라는 것이 성립하지 않는다.** 가리는 대상은 제3자이지 판매자가 아니다.

### 4.3 답변은 문의당 하나이고 기본키가 만든다

리뷰 답변과 같은 판단이다 (TASK-0085 4.2). 두 번째 답변은 저장될 자리가 없다.

### 4.4 기본은 공개다

문의는 **상품 정보의 일부**이고, 같은 것을 궁금해하는 다음 사람이 읽는다. 비공개는 고르는 것이지 기본이 아니다.

## 5. 구현 계획

1. 스키마·마이그레이션
2. 문의 작성 API (공개 여부)
3. 답변 API (소유권)
4. 조회 권한 필터
5. 상품 상세 Q&A 섹션 (밀도 분기)
6. 마이페이지·판매자 화면
7. 알림 이벤트
