## 1. 목적

판매자가 자기 부담 쿠폰을 발행하는 화면을 만든다. **정산에서 차감된다는 사실을 명확히 보여준다.**

## 2. 범위

### 포함
- 쿠폰 목록·발행 (범위는 자기 상품·자기 스토어로 제한)
- **판매자 부담 명시** — "정산 시 차감됩니다" 경고
- 예상 부담액 표시
- 발행 중단
- 쿠폰별 사용 현황·부담액 누계
- 정산 화면과 연결 (M12)

### 제외
- 플랫폼 쿠폰 (TASK-0073)

## 3. 요구사항

- [ ] 판매자는 자기 상품 범위 쿠폰만 발행할 수 있다
- [ ] 정산에서 차감된다는 안내가 명확히 표시된다
- [ ] 지금까지의 부담액 누계를 볼 수 있다
- [ ] 발행 중단이 가능하다

## 4. 설계

발행 폼 상단에 경고를 배치한다.

```
⚠ 이 쿠폰의 할인액은 판매자 정산에서 차감됩니다.
   예상 최대 부담: 100장 × 5,000원 = 500,000원
```

**판매자가 부담 구조를 모르고 쿠폰을 뿌리는 상황**이 실제로 흔하다. 발행 전에 숫자로 보여준다. D-029 의 부담 주체 구분이 사용자에게 드러나는 지점이다.

### 4.1 「예상 최대 부담」은 **없을 수 있는 수**다

4장의 그림(`100장 × 5,000원 = 500,000원`)은 두 값이 모두 정해졌을 때의 이야기다.
정률 쿠폰에 상한이 없거나 발급 수량이 무제한이면 최대 부담은 **큰 수가 아니라 없는
수**이고, 거기에 숫자를 적으면 그 숫자가 곧 「이만큼만 나가겠구나」가 된다 — 이 TASK
가 막으려는 오해가 정확히 그것이다.

그래서 답이 셋이다: 정해졌으면 그 곱, 경계가 없으면 **왜 없는지**(상한이 없어서인지
수량이 무제한이어서인지 — 고치는 칸이 다르다), 아직 안 채웠으면 아무것도.

### 4.2 부담 누계는 페이지의 합이 아니다

처음 만들었을 때 목록이 페이지의 줄만 실어 주어, 화면은 **다음 장을 넘길 때마다
달라지는 수**를 누계라고 부를 수밖에 없었다. 판매자가 정산과 견주려는 수가 그것이라
더 나쁘다. 계약에 `totals` 가 생겼고(발행자 전체, 필터·페이지 무관), 화면은 그것을
읽기만 한다 — 줄에서 다시 더하지 않는 것이 「페이지가 바뀌어도 안 움직인다」를
보장하는 자리다.

## 5. 구현 계획

1. 목록 화면
2. 발행 폼 (범위 제한 + 부담 경고 + 예상액)
3. 발행 중단
4. 사용 현황·부담액 누계
5. 정산 연결 자리

**F1** — 화면이 내놓는 범위가 둘뿐이고(자기 스토어 · 지정 상품), 상품 목록의 출처가
`GET /seller/products` 하나다. 「남의 상품이 없다」가 걸러 낸 결과가 아니라 **출처의
성질**인 것이 이 설계의 값이고, 그래도 서버의 403 을 그 칸에 그린다 — 화면만 막으면
API 를 직접 부르는 길이 남는다.
**F3** — 경계가 없는 두 경우(상한 없는 정률 · 무제한 수량)는 숫자 대신 이유를
말한다 (4.1).
**F5** — 필터와 페이지에 무관한 값이다 (4.2).
