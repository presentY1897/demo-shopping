## 4. 설계

```
구매확정 → earn(userId, 실결제금액 × 적립률, refType='ORDER', refId)
주문     → use(userId, amount, refType='ORDER', refId)
```

**구매확정 시 지급하는 이유**: 배송완료 직후 주면 반품 시 이미 쓴 적립금을 회수할 수 없다. 확정은 "문제없음"의 표시다.

**적립금은 플랫폼 부담**이다. 판매자 정산에서 차감하지 않는다.

사용 상한: 주문 금액의 일정 비율(예: 전액 가능하되 최소 결제금액 100원 이상). 규칙은 설정값으로 둔다.

### 4.1 잔액은 **행 잠금**으로 지킨다 — 조건부 갱신이 아니다

잔액만 보면 `balance >= amount` 하나라 조건부 갱신처럼 보인다. 그런데 같은 트랜잭션이
**어느 통에서 빼는가**(다른 행들) · **이 사건의 자리**(`max(seq)`) · **그 뒤 잔액**(원장에
박제될 `balanceAfter`)까지 정해야 하고, **그 셋이 계좌 행 안에 없다.**

잔액만 조건부 갱신으로 지키면 **통과 잔액이 갈라지고 만료가 돌 때까지 안 보인다.**

`balance` 는 더하지 않고 **대입**한다 — 산술로는 갈라질 수 없고, 갈라지려면 이 파일 밖에서
써야 하며 그것을 대사가 본다.

**DB 로 내린 것과 못 내린 것을 갈라 적는다.** 「원장 합계 = 잔액」 다섯은 **다른 행들에 대한
집계라 CHECK 에 넣을 수 없다** — 재고 원장이 멈춘 것과 같은 자리다. 계좌 행 잠금 안에서
지키고 대사가 깨진 것을 센다. 마지막 방어선은 `PointAccount_balance_check (balance >= 0)`.

### 4.2 통(lot) 이 없으면 **만료가 잔액을 음수로 만든다**

`EARN` 한 줄이 사건이면서 잔고를 담은 통이다(`expiresAt` · `remainingAmount` · `earnRateBp`).

통이 없으면 만료가 계산될 수 없다: **1,000원 받아 전부 쓴 뒤 기한이 지났을 때 적립액을
그대로 만료시키면 잔액이 음수가 된다.** 사용은 먼저 사라질 통부터 비우고, 만료된 통은 배치
전이라도 사용 후보에서 빠진다.

### 4.3 적립률은 **`AppMeta` 가 아니라 자기 표에** — 그리고 원장에 박제된다

`AppMeta` 는 실제로 **배치가 자기 실행 시각을 적는 운영용 문자열 저장소**로만 쓰인다.
적립률은 성격이 다르다 — **실결제금액에 곱해지므로** 음수나 100% 초과가 들어가면 산 금액보다
많은 적립금이 나가고 **아무 요청도 실패하지 않는다.** `AppMeta.value` 가 문자열이라 그 CHECK 을
쓸 수 없다.

**적립 시점의 적립률은 원장 행에 박제된다** — 정책을 나중에 읽어 되짚으면 적립률을 바꾼 날
과거가 전부 바뀐다.

### 4.4 사용 상한은 **문서에 하나뿐이었고, 그것은 이미 엔진 안에 있다**

`pricing.md` 의 유일한 상한은 1장 ⑤ 「①−③+④ 범위 내에서 차감」이고 계산 엔진이 이미 그것을
한다. 그래서 엔진을 다시 만들지 않고 할인 하나로 꽂았다(D-036).

**「주문금액 대비 비율」이나 「최소 결제금액」 규칙은 문서 어디에도 없다.** TASK 4장이 「예:」로
든 문장뿐이라 **지어내지 않았다** — 필요하면 문서를 먼저 고쳐야 한다.

`bearer` 가 `PLATFORM` 인 것은 정산이 읽는 값이라 중요하다 — 틀리면 **판매자가 자기가 주지도
않은 할인을 물어낸다.**
