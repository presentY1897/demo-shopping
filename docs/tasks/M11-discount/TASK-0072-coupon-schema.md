## 1. 목적

쿠폰 정책과 발급 데이터를 만든다. **부담 주체(플랫폼/판매자)를 스키마에 못박는다.**

## 2. 범위

### 포함
- `Coupon` — 발행 주체, 이름, 할인 유형(정액/정률), 값, 최대 할인액, 최소 주문금액, 적용 범위(전체/카테고리/상품/판매자), 유효기간, 발급 수량 제한
- `UserCoupon` — 발급된 쿠폰, 상태(발급/사용/만료), 사용 주문
- 발행 API (관리자·판매자 권한 분기)
- 발급 API (사용자에게 지급, 중복 발급 제한)
- 만료 처리 배치
- 발급 수량 소진 처리
- 쿠폰 코드 방식 지원 (코드 입력으로 발급)

### 제외
- 화면 (TASK-0073, 0074)
- 적용·검증 (TASK-0075)

## 3. 요구사항

- [x] 플랫폼 쿠폰과 판매자 쿠폰이 구분되어 저장된다
- [x] 판매자는 자기 상품에만 적용되는 쿠폰만 발행할 수 있다
- [x] 발급 수량이 소진되면 더 발급되지 않는다
- [x] 같은 쿠폰을 중복 발급받을 수 없다
- [x] 만료된 쿠폰이 자동으로 상태 전환된다

## 4. 설계

| 필드 | 설명 |
| --- | --- |
| `issuerType` | PLATFORM / SELLER — **정산의 근거** |
| `sellerId` | 판매자 쿠폰일 때만 |
| `discountType` | FIXED(정액) / PERCENT(정률) |
| `maxDiscountAmount` | 정률일 때 상한 |
| `minOrderAmount` | 최소 주문금액 |
| `scopeType` / `scopeIds` | ALL / CATEGORY / PRODUCT / SELLER |

**판매자 쿠폰의 범위를 자기 상품으로 강제**한다. 판매자가 전체 쿠폰을 발행하면 다른 판매자 매출에 자기 부담이 들어간다.

### 4.1 발급 수량은 **조건부 갱신**, 마지막 줄은 CHECK

판단에 필요한 값(`issueLimit`·`issuedCount`)이 **둘 다 같은 행에** 있으므로 한 문장이다
(TASK-0065 4.1 의 기준 그대로). 0행이면 진 것이고, **이유는 진 다음에만** 읽는다 — 소진인가
중복인가를 미리 알아야 할 이유가 없다.

자리 잡기와 발급 행 삽입이 **한 트랜잭션**이라, 중복으로 진 요청의 증가분이 롤백된다 —
**아무에게도 안 간 한 장이 소진되지 않는다.**

마지막 방어선은 `Coupon_issued_count_check`. 중복 발급의 방어선은 조회가 아니라
`UserCoupon_couponId_userId_key` 이고, 애플리케이션은 그 위반을 문장으로 바꿀 뿐이다.

**동시성 검사가 실제로 경합을 재는지 확인했다.** 조건부 갱신을 읽기-쓰기로 바꾼 통제군에서
**배리어만 있는 판은 초록이었다** — 다섯 건이 차례로 지나갔기 때문이다. 그래서 바깥
커넥션이 행을 먼저 잠그고, `pg_stat_activity` 가 「둘 이상이 그 갱신에서 기다린다」고 말한
뒤에 커밋한다. 「자리가 남으면 전부 받는다」를 함께 둬서 **무조건 하나만 통과시키는 구현이
초록이 되지 않게** 했다.

### 4.2 판매자 범위 강제 — **두 겹은 DB, 한 겹은 서버**

| 규칙 | DB | 서버 |
| --- | --- | --- |
| 판매자 쿠폰은 `ALL`·`CATEGORY` 를 가질 수 없다 | ✅ | ✅ |
| `SELLER` 범위의 대상은 **자기 자신** | ✅ | ✅ |
| `PRODUCT` 범위의 상품이 그 가게 것인가 | ❌ **불가능** | ✅ |

마지막 줄이 못 내려간 이유는 **CHECK 가 한 행만 보기 때문**이다 — 「이 상품이 저 가게
것인가」는 조인이 필요하다. 트리거로는 되지만 이 저장소에 트리거 선례가 없어(전부 부분 유니크
인덱스 + CHECK) 서버에 두고 근거를 마이그레이션 주석에 적었다.

`CATEGORY` 를 함께 막은 것은 카테고리가 **플랫폼 공용**이라 「셔츠 10%」가 이름만 좁을 뿐
**남의 셔츠까지 덮기** 때문이다.

**부담 주체를 요청이 고르지 않는다** — `sellerId` 가 있으면 판매자 쿠폰이다. 그래서 **권한
검사가 곧 부담 주체 검사**가 되고, 서비스가 역할을 직접 보지 않는다.

### 4.3 쿠폰 코드 — 주문번호와 **다른 두 가지**

`order-number.ts` 의 Crockford base32 를 쓰되 둘이 다르다.

- **날짜 접두어가 없다** — 주문번호의 그것은 문의를 받는 쪽을 위한 것인데, 쿠폰 코드는 **입력하는** 문자열이다
- **10자리(50비트)** — 주문번호는 맞혀도 의미가 없지만 쿠폰 코드는 **맞히면 이득이 되는** 문자열이다

**저장은 canonical 형태만이고 하이픈은 보여 줄 때만 붙인다.** 저장하면 「하이픈 있는 코드」와
「없는 코드」가 다른 문자열이 되어 유니크가 무력해진다. 입력은 대소문자·하이픈·공백을 받고
`I`·`L`→`1`, `O`→`0` 을 접되 **알파벳 밖 글자는 버리지 않는다** — 버리면 `WELCOME!!` 같은
입력이 우연히 남의 코드를 가리킨다. 형식 오류와 없는 코드는 **같은 답**이다.
