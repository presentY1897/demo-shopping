# TASK-0075: 쿠폰 적용 · 검증

| 항목 | 내용 |

## 1. 목적

주문서에서 쿠폰을 적용한다. **M07 계산 엔진의 `discounts` 목록에 쿠폰을 넣는 것**이 전부이며, 계산기 자체는 건드리지 않는다.

## 2. 범위

### 포함
- 적용 가능 쿠폰 조회 (주문 내용 기준 필터링)
- 쿠폰 검증 — 유효기간, 최소 주문금액, 적용 범위, 사용 여부
- 계산 엔진에 할인 항목으로 전달 (부담 주체 포함)
- 중복 사용 규칙 — 플랫폼 1장 + 판매자 쿠폰 판매자당 1장
- 주문서 쿠폰 선택 UI
- 최대 할인 조합 추천
- 주문 확정 시 쿠폰 사용 처리 (동시성 제어)

### 제외
- 적립금 (TASK-0076)
- 환불 시 복구 (TASK-0078)

## 3. 요구사항

- [ ] 적용 불가한 쿠폰은 목록에 나오지 않거나 사유가 표시된다
- [ ] 판매자 쿠폰은 해당 판매자 항목에만 안분된다
- [ ] 같은 쿠폰이 두 주문에 동시 사용되지 않는다
- [ ] 계산 엔진 코드를 수정하지 않고 연결된다
- [ ] 최대 할인 조합을 추천한다

## 4. 설계

```
쿠폰 선택 → discounts 목록 구성
[
  { type:'COUPON', amount: 5000, scope:'ORDER',  bearer:'PLATFORM', couponId },
  { type:'COUPON', amount: 3000, scope:'SELLER', targetId: sellerId, bearer:'SELLER', couponId }
]
→ calculateOrder(items, discounts, shipping)   ← M07 그대로
```

**계산기를 수정하지 않는 것이 이 TASK 의 성공 기준**이다. M07 에서 `discounts` 를 목록으로 받게 설계한 이유가 여기서 검증된다.

중복 사용: 플랫폼 쿠폰 1장 + 판매자별 판매자 쿠폰 1장. 플랫폼 쿠폰끼리는 중복 불가.

### 4.1 스케치와 실제가 갈린 다섯 곳

**계산기는 한 줄도 고치지 않았다** (F1). 갈린 것은 그 주변이다.

#### ① 쿠폰의 범위 넷 중 둘은 계산기의 범위 셋 중 어느 것도 아니다

계산기가 아는 범위는 `ORDER` · `SELLER` · `ITEM` 이고, 쿠폰의 범위는 `ALL` ·
`CATEGORY` · `PRODUCT` · `SELLER` 다. 앞의 짝은 맞지만 **`CATEGORY` 와 `PRODUCT` 는
주문의 일부만, 그것도 여러 판매자에 걸쳐** 가리킬 수 있다.

그래서 세 갈래로 옮긴다.

| 닿는 것 | 넘기는 모양 |
| --- | --- |
| 주문 전체 | `ORDER` 한 줄 |
| 어느 판매자의 전부 | `SELLER` 한 줄 |
| 그 밖 | 우리가 안분해서 줄마다 `ITEM` 한 줄 |

앞의 둘을 남긴 이유는 **계산기의 안분이 우리 것보다 낫기** 때문이다 — 그룹 전체를
한 번에 나누므로 한도에 걸린 몫을 형제 항목으로 돌린다. 셋째 갈래는 이미 나뉜 뒤라
그 재분배를 할 수 없고, 차이가 드러나는 것은 두 쿠폰이 같은 항목을 덮어 한도가
실제로 걸릴 때뿐이며, 드러나는 방향은 언제나 덜 깎이는 쪽이다. 셋째 갈래의 안분에도
**계산기와 같은 `allocate`** 를 쓴다 — 잔여를 버리지 않는 규칙이 두 곳에 따로
구현되면 1원이 어긋난다(F8).

#### ② 장별 금액을 계산기가 말해 주지 않는다

계산기는 「쿠폰 할인 합계」만 답한다. 정산(M12)이 필요로 하는 것은 **어느 장이 얼마를
깎았는가**이고(`pricing.md` 6장), 계산기를 고쳐 그것을 내게 하는 것이 곧 F1 이
금지하는 일이다.

그래서 **앞에서부터 하나씩 더해 가며 합계의 증분을 읽는다.** k번째 장의 몫은
「k장까지의 합계 − (k−1)장까지의 합계」다. 계산기가 순서대로 적용하고 각 장이 남은
금액까지만 깎으므로 이 증분이 곧 그 장이 실제로 깎은 금액이며, 증분들의 합은
정의상 전체 합계와 같다. 계산기를 n+1번 부르는 비용은 순수한 정수 산술이고 n 은
「플랫폼 하나 + 판매자당 하나」라 작다.

값은 `UserCoupon.discountAmount` 에 남는다 — **지금 채우지 않으면 나중에 채울 수
없다.** M12 에 컬럼을 더하면 그때 이미 저장된 주문들은 그 값을 영영 갖지 못한다.

#### ③ 「최대 할인 조합」이 최대화하는 것은 할인액이 아니다

무료배송 판정이 「상품금액 − 쿠폰 할인」 기준이므로(`pricing.md` 1장), 큰 쿠폰이 그
문턱 아래로 끌어내리면 **배송비가 되살아난다.**

```
상품 10,000원 · 배송비 3,000원 · 무료배송 9,000원 이상

쿠폰 1,000원 → 상품 9,000원 → 무료배송 → 낼 돈  9,000원
쿠폰 2,000원 → 상품 8,000원 → 배송비 3,000원 → 낼 돈 11,000원
```

할인액을 기준으로 고르면 아래쪽을 권하게 된다 — **쿠폰을 더 쓰고 더 내는 조합**이고,
그것을 만든 것은 우리다. 그래서 기준은 `paidAmount` 최소이고, 동점이면 적게 쓰는
쪽, 장수까지 같으면 플랫폼 쿠폰을 쓰는 쪽이다(정산에서 아무도 차감되지 않는다).

이 셋은 `pricing.md` 3장으로 갔다(D-222). 문서에 없던 규칙을 코드가 정하고 있으면
다음 사람은 그것을 구현 세부로 읽는다.

#### ④ 카테고리 범위는 **조상까지** 닿아야 한다

「셔츠」 쿠폰이 「반팔 셔츠」에 안 붙으면 발행자는 잎 카테고리를 전부 나열해야 하고,
나중에 추가된 잎은 아무도 다시 나열해 주지 않는다. 판정은 `Category.path` 로 하고,
`/12/` 로 **감싸서** 견준다 — 감싸지 않으면 카테고리 1이 11 · 21 · 120 에까지 붙는다.

그 값을 읽으려고 주문 줄에 `productId` 와 `categoryPath` 가 붙었고, 그 자리에서
`order.service.ts` 가 `VARIANT_LINE_SELECT` 와 **같은 내용을 손으로 적어 두고 있던
것**을 발견했다. 쿠폰의 카테고리 범위가 실제로 그 두 벌이 갈리는 자리였다.

#### ⑤ 선택을 서버에 저장하지 않는다

주문서에 「고른 쿠폰」 칸을 두는 길도 있었지만, 그러면 **고르기가 상태를 바꾸는
요청**이 되고 그때부터 새로고침·뒤로가기·두 번째 탭이 각각 다른 주문서를 본다.
선택은 화면이 들고, 주문서를 읽을 때마다 쿼리로 함께 온다. 주문 생성도 같은 목록을
몸통으로 받는다 — 화면이 본 금액과 저장되는 금액이 **같은 입력**에서 나온다.

### 4.2 동시 사용 — 조건부 갱신 한 문장

```sql
UPDATE "UserCoupon" SET "status" = 'USED', … WHERE "id" = $1 AND "status" = 'ISSUED'
```

행 잠금이 아니라 조건부 갱신인 것은 TASK-0065 4.1 의 기준 그대로다 — **판단이 그 행
안에서 끝나는가.** 여기서 판단에 필요한 값은 `status` 하나이고 그것은 이 행에 있다.

진 쪽은 0행을 고치고 **주문 트랜잭션 전체가 롤백된다.** 쿠폰 없이 주문을 만들어
주는 길도 있지만, 그러면 사는 사람이 동의한 적 없는 금액이 결제된다.

검사는 잠금으로 **겹침을 배열해서** 잰다(`test/api/coupon-apply.spec.ts`). 동시에
쏘는 것만으로는 겹침이 우연이고, 겹치지 않은 실행에서도 「하나만 성공했다」는
초록이다. 두 주문이 서로 다른 가게의 서로 다른 상품을 사는 것도 그래서다 — 같은
조합이면 재고 예약에서 먼저 줄을 서게 되어 쿠폰 앞에서 겹치지 않는다.
