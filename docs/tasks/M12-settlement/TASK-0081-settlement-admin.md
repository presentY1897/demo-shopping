# TASK-0081: 관리자 정산 승인 · 지급

| 항목 | 내용 |

| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |

| 선행 작업 | TASK-0080 |

## 1. 목적

관리자가 정산서를 검토하고 승인·지급 처리하는 화면을 만든다. 실제 이체는 없고 상태만 바뀐다.

## 2. 범위

### 포함
- 정산서 목록 (회차·판매자·상태 필터)
- 정산서 상세 (항목별 내역, 계산 근거)
- 승인 / 보류 / 지급완료 처리
- 보류 사유 입력 (분쟁·이상 건)
- 일괄 승인
- 정산 총액 요약 (회차별 지급 예정 총액)
- 정산서 내보내기 (CSV)
- 데모 관리자는 `settlement.pay` 퍼미션이 없어 지급 확정 불가 (D-058)

### 제외
- 실제 이체·은행 연동

## 3. 요구사항

- [x] 정산서 항목별 계산 근거를 볼 수 있다
- [x] 승인 후 지급완료로 전환할 수 있다
- [x] 보류 시 사유를 입력해야 한다
- [x] 지급완료된 정산서는 수정할 수 없다
- [x] 데모 관리자는 지급 확정을 할 수 없다

## 4. 설계

정산서 상세에 **계산 근거를 항목별로 펼쳐 보여준다.**

```
판매액          1,890,000
− 수수료 (10%)   -189,000
− 판매자 쿠폰     -30,000
− 반품 차감      -120,000
────────────────────────
지급액          1,551,000
```

각 줄을 클릭하면 해당하는 주문 목록으로 내려갈 수 있게 한다. 판매자가 이의를 제기했을 때 근거를 즉시 확인할 수 있어야 한다.

**지급완료 후 수정 불가**: 돈이 나간 것으로 간주되므로 잠근다. 오류가 있으면 다음 회차에서 조정한다.

### 4.1 전이표가 없는 화살표를 불가능하게 만든다

`state-machines.md` 5장의 네 화살표를 표로 두고, 서비스는 그 표만 읽는다. 서비스가 `if` 로 흩어 쓰면 「지급완료된 정산서를 다시 승인」 같은 전이는 아무도 막지 않는 것이 아니라 **아무도 생각하지 않은 것**이 되고, 그 차이는 사고가 난 뒤에만 보인다.

F5 의 「지급완료된 정산서는 수정할 수 없다」가 이 서비스의 조건문이 아니라 **전이표의 빈 배열**이 만드는 것도 그래서다 (D-234).

**「거절」이 없다.** 보류에서 갈 수 있는 곳은 승인뿐이다 — 정산은 거절할 수 있는 것이 아니고, 금액이 틀렸으면 고쳐서 다음 회차에서 조정한다. 보류는 승인의 반대가 아니라 **판단을 미룬 상태**다.

### 4.2 상태를 옮기는 일은 한 문장이다

「지금 상태를 읽고 → 옮겨도 되는지 보고 → 쓴다」로 나누면 그 사이에 남이 끼어들 수 있고, 그때 일어나는 일이 **같은 정산서를 두 번 지급**하는 것이다. 판단이 그 행 안에서 끝나므로(TASK-0065 4.1 의 기준) 잠그지 않고 조건부 갱신으로 옮긴다. 옮길 수 있는 출발 상태의 목록은 전이표가 준다 (D-235).

거절은 409 와 `SETTLEMENT_WRONG_STATUS` 로 나간다. **화면이 버튼을 가리고 있어도 온다** — 다른 관리자가 방금 지급 처리했을 수 있고, 그때 이 답은 「당신이 틀렸다」가 아니라 「목록을 다시 읽어 보라」는 뜻이다.

### 4.3 사유 없는 보류가 불가능하다 (F4)

계약(`trim().min(1)`)이 먼저 거절하고 `Settlement_holdReason_check` 가 그 뒤를 받친다. 공백만 적고 넘어갈 수 있으면 「사유를 입력해야 한다」는 화면의 예의이지 규칙이 아니게 되고, 판매자가 「왜 제 정산이 멈췄죠」라고 물었을 때 답할 것이 없다.

**사유는 해소된 뒤에도 남는다.** 「이 회차가 왜 늦었나」는 지급이 끝난 뒤에 물어보는 질문이다.

### 4.4 일괄 승인은 한 건씩 옮기고, 실패를 숨기지 않는다 (F6)

한 트랜잭션에 넣으면 지급완료된 한 장이 섞였을 때 아홉 장의 승인이 함께 사라진다. 그리고 답에 실패 목록이 함께 오는 것이 이 문의 요점이다 — 「10건 골랐는데 8건이 승인됐다」를 화면이 말하지 못하면 남은 2건은 아무도 다시 보지 않고, 그 2건이야말로 사람이 봐야 하는 것들이다.

### 4.5 합계는 페이지가 아니라 필터의 것이다

목록이 함께 답하는 「지급 예정 총액」은 **지금 필터가 고른 것 전부**의 합이다. 페이지 합으로 답하면 다음 장을 넘길 때마다 총액이 달라지고, 그 숫자를 보고 지급을 결정하는 사람에게 그것은 답이 아니다.

### 4.6 F7 은 조건문이 아니다

읽기는 `settlement.read`, 승인·보류는 `settlement.approve`, 지급은 `settlement.pay` 다. 셋을 나눈 이유는 **되돌릴 수 있는 정도가 다르기** 때문이고, 「데모 관리자는 지급 확정 불가」가 따로 판정되지 않는 것도 그래서다 — 데모 관리자는 운영자에서 파생되고 운영자에게는 뒤의 둘이 없다.
