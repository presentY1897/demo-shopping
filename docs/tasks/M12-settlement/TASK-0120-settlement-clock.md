## 1. 목적

`main` 이 빨갛다. `test/api/settlement-batch.spec.ts` 의 「반품 (F7)」 4건이 실패한다.

**그런데 하루 종일 빨간 것이 아니다.** 오전에 돌리면 통과하고 오후에 돌리면 실패한다. 실패가
시계에 달려 있고, 마지막 커밋이 2026-09-07 이라 그 뒤로 아무도 오후에 전체를 돌리지 않았다.

원인은 정산 배치가 **시각을 두 곳에서 읽는 것**이다. 이 저장소에는 시간을 한 곳에서만 읽으라고
`CLOCK` 추상이 있는데, 정산 줄 하나가 그것을 우회해 데이터베이스 시계를 쓴다. 그 시각이 「이 뒤에
온 반품인가」 판정의 기준이므로, 우회는 조용한 오판이 된다.

끝나면 정산 배치의 모든 시각이 한 시계에서 나오고, 검사는 몇 시에 돌리든 같은 답을 낸다.

## 2. 범위

## 4. 설계

### 4.1 무엇이 어긋나 있나

판정은 `settlement-batch.service.ts:411` 한 줄이다.

```sql
AND cr."refundedAt" > si."createdAt"
```

「이 정산 줄이 적힌 **뒤에** 환불된 반품인가」. 규칙은 옳고, 코드도 그 중요성을 알고 있다
(같은 파일 229행).

> `createdAt` 이 「이 금액이 언제 계산됐나」를 뜻해야 하기 때문이다 — 그 시각이 다음 주기의
> 「이 뒤에 온 반품」 판정에 쓰인다.

그런데 두 시각의 출처가 다르다.

| 값 | 어디서 오나 |
| --- | --- |
| `Settlement.createdAt` (321행) | `createdAt: now` — **주입된 시계** (`this.clock.now()`) |
| `SettlementItem.createdAt` (268행) | **아무것도 넘기지 않는다** → Prisma 가 열 기본값에 맡긴다 → **데이터베이스 시계** |

```ts
private async insert(...): Promise<void> {
  await tx.settlementItem.create({
    data: { settlementId, sellerOrderId, type, ...amounts },   // ← createdAt 이 없다
  })
}
```

정산서는 앱 시계로, 그 안의 줄은 DB 시계로 적힌다. **배포에서는 둘 다 실제 시각이라 대개
몇 밀리초 차이로 지나간다.** 그래서 지금까지 드러나지 않았다. 다만 API 는 Render 에, Postgres 는
Neon 에 있는 서로 다른 기계이고, 두 기계의 시계가 같다는 보장은 어디에도 없다.

### 4.2 검사에서는 그 차이가 몇 시간이 된다

검사는 앱 시계를 `2026-09-09T05:00:00Z` 로 고정한다. DB 시계는 고정되지 않는다 — 진짜 지금이다.

```
앱 시계  05:00:00Z   ← si.createdAt 이 여기서 나와야 하는데
DB 시계  11:18:00Z   ← 실제로는 여기서 나온다 (그날 검사를 돌린 시각)
반품     05:00:00Z   ← refundedAt: NOW

판정:  refundedAt(05:00) > si.createdAt(11:18)  →  거짓  →  반품이 없는 것으로 처리된다
```

그래서 `tally.amended` 가 1 이어야 하는데 0 이 된다. 실측으로 확인했다.

| `NOW` | 실제 실행 시각 | 결과 |
| --- | --- | --- |
| `05:00:00Z` (현재 코드) | 11:18Z | **4 failed** |
| `23:30:00Z` | 11:18Z | **22 passed** |

**즉 이 검사는 실제 시각이 05:00Z(14:00 KST) 이전일 때만 통과한다.** CI 가 오전에 돌면 초록,
오후에 돌면 빨강이다. 통과했던 것이 운이었지 검증이 아니었다.

### 4.3 시계를 고치는 것만으로는 부족하다

`createdAt` 을 주입된 시계로 바꿔 보면 여전히 4건이 실패한다. 실측했다.

```
si.createdAt = 05:00:00.000Z   (이제 앱 시계)
refundedAt   = 05:00:00.000Z   (테스트가 NOW 를 그대로 준다)

판정:  05:00:00.000 > 05:00:00.000  →  거짓
```

**검사가 「나중에 온 반품」을 표현하지 않고 있었다.** `refundedAt: NOW` 는 "정산과 같은 순간"이고,
지금까지 통과한 이유는 DB 시계가 우연히 그보다 앞서 있었기 때문이다. 시각을 한 곳으로 모으면
그 우연이 사라지고 검사의 의도가 드러난다 — 그리고 의도가 틀려 있다.

그래서 **둘을 함께 고친다.**

| | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| `insert()` | `createdAt` 없음 → DB 시계 | `createdAt: this.clock.now()` |
| 반품 검사 | `refundedAt: NOW` (같은 순간) | 정산 줄보다 **확실히 나중인** 시각 |

두 변경을 함께 적용해 22건 전부 통과하는 것을 확인했다 (6.3).

**검사 쪽을 상수로 할지 `clock.advance()` 로 할지는 구현에서 정한다.** `advance` 가 「정산을 돌린
뒤 시간이 흘렀고 그 사이에 반품이 왔다」는 이야기를 그대로 쓰므로 그쪽이 낫다. 상수 하나를 더
두면 그 상수와 `NOW` 의 관계를 읽는 사람이 다시 계산해야 한다.

### 4.4 같은 패턴이 정산 안에 더 있는지 훑는다

`insert()` 하나만 고치고 끝내면, 다음에 누가 같은 방식으로 줄을 하나 더 추가할 때 같은 일이
반복된다. **정산 모듈 안에서 `create`/`createMany` 에 시각을 넘기지 않는 자리를 전부 확인하고**,
「이 시각이 판정에 쓰이는가」를 기준으로 판단한다.

- **판정에 쓰인다** → 주입된 시계로 채운다
- **기록용일 뿐이다** → 그대로 둔다. 다만 그 판단을 주석 한 줄로 남긴다

전부 시계로 바꾸는 것이 목적이 아니다. **판정에 쓰이는 시각이 두 시계에서 나오지 않게 하는 것**이
목적이다.

### 4.5 데이터 모델 · API · 화면

- 데이터 모델 변경: **없음.** 열 기본값은 그대로 두고, 코드가 값을 넘길 뿐이다. 마이그레이션 없음
- API: 없음
- 화면: 없음
- 역할별 권한: 해당 없음

**기존 행은 손대지 않는다.** 이미 적힌 `createdAt` 은 그때의 DB 시계 값이고, 배포에서 두 시계 차이는
밀리초 단위였다. 소급해 고칠 근거가 없고, 고치면 「이 금액이 언제 계산됐나」라는 기록을 사후에
바꾸는 일이 된다.
