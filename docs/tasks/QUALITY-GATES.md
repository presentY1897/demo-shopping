### Q5 — 레이어별 테스트 기준

**커버리지는 "테스트 종류"가 아니라 "코드 라인이 실행됐는가"를 잰다.** UI 코드에 커버리지 수치를 강제하면 아무것도 검증하지 않는 테스트가 양산된다.

```tsx
// 커버리지만 올리고 버그는 못 잡는 테스트
test('렌더된다', () => {
  const { container } = render(<ProductCard product={mock} />)
  expect(container).toBeTruthy()
})
```

그래서 **얼마나**(커버리지)와 **무엇을 대상으로**(대역 규약)를 레이어별로 나눈다. 아래 2~4장의 게이트와 **같은 조건으로 적용**된다 — 한 TASK 가 화면과 API 를 모두 만들면 두 기준을 모두 받는다.

| 레이어 | 적용 조건 | 얼마나 | **무엇을 대상으로** |
| --- | --- | --- | --- |
| **순수 로직** — 금액 계산·안분·재고·상태 머신·권한 판정·검증기·자모 변환 | 해당 코드가 있으면 | **분기 커버리지 100%** | 아무것도 필요 없음. 입력 → 출력 |
| **백엔드 서비스 · API** | **`apps/api` 에 서비스·리포지토리·배치 코드가 있으면** (엔드포인트 유무와 무관) | 라인 커버리지 **80%** | **실제 PostgreSQL** ([대역 규약](#6-테스트-대역-규약)) |
| **프론트 컴포넌트 · 화면** | 2장 화면 게이트를 받는 TASK | 커버리지 수치 없음 → 아래 상호작용 목록 | **백엔드는 모킹.** 실 API 를 부르지 않는다 |
| **계약** | 프론트가 API 를 부르는 TASK **와 그 응답을 만드는 백엔드 TASK** | 5장 계약 게이트 | 양쪽이 같은 zod 스키마를 통과 |
| **E2E** | TASK-0099 | 정의된 시나리오 통과 | 실 스택 전부 |

> **적용 조건이 "엔드포인트"가 아니라 "서비스 코드"인 이유.** 처음에는 3장(엔드포인트를 추가하는 TASK)에 걸어 뒀는데, 그러면 **엔드포인트 없이 서비스만 만드는 TASK 가 어떤 커버리지 기준도 받지 않는다.** 실제로 걸리는 것이 `TASK-0048 재고 예약`(조건부 갱신으로 동시성 제어, 소비자는 TASK-0049)과 `TASK-0080 정산서 배치`(돈 집계, 중복 방지)다. 하필 이 문서가 가장 지키려는 두 곳이었다.

**왜 백엔드는 실제 DB 인가.** 이 프로젝트는 불변식을 **DB 가 강제**하도록 설계했다 — 기본 배송지 1개(부분 유니크 인덱스), 재고 `UPDATE ... WHERE stock - reserved >= qty`, 잔액 행 잠금, 카테고리 트리 어드바이저리 락. Prisma 를 모킹하면 **정확히 그 부분만 검증에서 빠진다.** 통과하는데 프로덕션에서 초과판매가 나는 테스트가 된다.

**왜 프론트는 모킹인가.** 화면이 검증할 것은 "이 응답이 오면 올바르게 그리는가"이지 "백엔드가 그 응답을 만들 수 있는가"가 아니다. 실 API 를 부르면 백엔드 장애로 프론트 테스트가 빨개지고, 느려지고, 결국 아무도 안 본다.

**모킹의 대가는 계약 게이트로 갚는다.** 프론트 모킹 데이터가 실제 응답과 어긋나면 양쪽 테스트가 다 초록인데 앱이 깨진다. 5장 참조.

### UI 컴포넌트 필수 상호작용

커버리지 대신 **"이 동작이 검증되는가"** 로 관리한다. 해당하는 항목만 적용한다.

| # | 항목 |
| --- | --- |
| U1 | 조건부 렌더 4상태 (로딩 / 빈 / 에러 / 정상) |
| U2 | 폼 검증 실패 시 **해당 필드에** 오류 표시 |
| U3 | 제출 중 중복 클릭 차단 |
| U4 | 밀도 3단계에서 각각 렌더 (`apps/shop`) |
| U5 | 키보드만으로 조작 |
| U6 | 서버 오류 응답 시 사용자에게 표시 |

테스트는 렌더 후 **실제로 클릭·입력을 발생시키고 결과를 확인**한다. 마크업이나 클래스명을 검증하지 않는다.

```tsx
test('필수 속성이 비면 오류가 표시된다', async () => {
  render(<ProductForm categoryId={3} />)
  await userEvent.click(screen.getByRole('button', { name: '저장' }))
  expect(await screen.findByText('소재를 입력해주세요')).toBeVisible()
})
```

### LCP 는 화면 게이트가 아니다 — 조사 도구다

**성능은 각 화면 TASK 가 통과해야 할 문턱이 아니라, 고칠 곳을 찾을 때 쓰는 방법이다.**
측정 절차와 누적된 실측은 [TASK-0097](./M15-polish/TASK-0097-performance.md) 1장이 소유한다.

이렇게 정한 것은 절대값 게이트(2.5s)와 증분 게이트(+500ms) 를 차례로 시도해 본 뒤다.

| 무엇이 문제였나 | |
| --- | --- |
| **기준선을 세 번 잘못 잡았다** | ① admin **홈 페이지** 2,557ms(콜드 스타트 장치 포함) → ② `/orders` **스텁** 1,804ms(상호작용 번들 미포함) → ③ 실제 화면 `/categories` 2,858ms. "셸" 의 정의가 사람마다 갈려 매번 다른 라우트를 쟀다 |
| **비용이 컸다** | 화면 TASK 마다 셸 없는 빌드를 따로 만들고 Lighthouse 를 5회씩 돌렸다. 30분~1시간이 들고, 측정 도중 중단된 적도 있다 |
| **한 번도 잡지 못했다** | 걸린 것은 전부 앱 셸·공통 번들의 기존 부채였고, **화면이 만든 회귀는 한 건도 없었다** |

**대신 무거운 것을 새로 들이면 TASK 문서에 적는다.** 큰 라이브러리, 대용량 자산, 새 폰트 같은
것이다. 이것은 측정이 아니라 신고이고, `next build` 가 이미 출력하는 First Load JS 를 옮겨
적는 것으로 충분하다. **판정이 아니라 기록이므로 통과·실패가 없다.**

접근성(P2)은 그대로 게이트다. 그쪽은 자동 검사가 값싸고(스토리마다 axe 가 CI 에서 돈다)
실제로 회귀를 잡아 왔다.

## 5. 계약 게이트 (프론트가 API 를 부르는 TASK · 그 응답을 만드는 백엔드 TASK)

프론트가 백엔드를 모킹하는 순간 **모킹이 실제 응답과 어긋날 수 있다.** 양쪽 테스트가 다 초록인데 앱이 깨지는 유일한 경로다.

```
프론트 테스트  { status: 'ok', database: 'ok' } 가 오면 3줄을 그린다     ✅
백엔드 테스트  /health 가 올바른 값을 만든다                              ✅
실제로는      백엔드가 필드명을 database → db 로 바꿨는데 아무도 못 잡음   ❌
```

| # | 기준 | 측정 방법 | 목표 |
| --- | --- | --- | --- |
| C1 | 스키마 단일 출처 | 요청·응답 타입이 `packages/shared` 의 zod 스키마에서 나오는가 | 앱에서 응답 타입을 다시 정의하지 않음 |
| C2 | 모킹 데이터 검증 | 프론트 모킹 응답을 해당 zod 스키마로 `parse` | 전부 통과 |
| C3 | 실제 응답 검증 | 백엔드 통합 테스트에서 실제 응답을 같은 스키마로 `parse` | 전부 통과 |

C2·C3 가 **같은 스키마**를 쓰는 것이 핵심이다. 한쪽만 하면 드리프트가 그대로 남는다.

**그래서 이 게이트는 두 TASK 에 걸쳐 적용된다.** C2 는 프론트 TASK 가, **C3 는 응답을 만드는 백엔드 TASK 가** 책임진다. 백엔드 쪽을 빼면 드리프트의 절반이 비어 버린다.

## 6. 테스트 대역 규약

**무엇을 실제로 쓰고 무엇을 대역으로 바꾸는가.**

| 대상 | 대역 | 이유 |
| --- | --- | --- |
| **PostgreSQL** | **실제** | 불변식을 DB 가 강제한다. 모킹하면 그 부분만 검증에서 빠진다 |
| **Meilisearch** | **모킹** | 검색 품질은 별도 관심사. 인덱싱 파이프라인 TASK 만 실제를 쓴다 |
| **토스페이먼츠** | **모킹** | 외부 서비스. 응답을 우리가 통제할 수 없고 실패 케이스를 만들 수 없다 |
| **Google OAuth** | **모킹** | 〃 |
| **Cloudflare R2** | **모킹** | 〃. presigned URL 생성 로직만 순수 로직으로 검증 |
| **시간** | **주입** | 순수 로직은 현재 시각을 **인자로** 받고, 서비스는 **`Clock` 포트**로 받는다. `vi.setSystemTime` 으로 대신하지 않는다 — **DB 의 `now()` 가 따라오지 않아** 만료 판정이 테스트에서만 맞는다. 상세는 TASK-0106 |
| **가상 카드** | **실제** | 우리 도메인이다. 외부가 아니다 |

### DB 테스트 격리

**테스트를 트랜잭션으로 감싸 롤백하는 방식은 쓰지 않는다.**

빠르고 청소가 공짜지만, 두 가지가 깨진다.

1. **커밋되지 않은 데이터는 다른 커넥션에서 보이지 않는다.** 동시 요청 상황을 만들 수 없다. 같은 커넥션으로 두 번 호출하면 순차 실행되어 경합이 재현되지 않는다 — 통과하지만 아무것도 증명하지 못한다.
2. **프로덕션 코드가 연 트랜잭션이 savepoint 로 강등된다.** PostgreSQL 에는 중첩 트랜잭션이 없다. 그래서 격리 수준을 지정할 수 없고(`SET TRANSACTION ISOLATION LEVEL must be called before any query`), 어드바이저리 락이 바깥 트랜잭션 범위로 늘어난다.

우리가 반드시 검증해야 할 것들 — 초과판매 방지, 잔액 잠금, 트리 이동, 결제 멱등, 정산 배치 — 이 전부 여기 걸린다.

**대신 이렇게 한다.**

| | 방법 |
| --- | --- |
| 워커 사이 | **워커별 데이터베이스.** 템플릿 DB 에 마이그레이션을 1회 적용하고 `CREATE DATABASE ... TEMPLATE ...` 로 복제 (파일 복사라 저렴) |
| 테스트 사이 | **`TRUNCATE ... RESTART IDENTITY CASCADE`.** 테이블 목록은 `information_schema` 에서 뽑아 스키마가 늘어도 손대지 않는다 |

> **마이그레이션 지문이 같으면 템플릿과 워커 DB 를 재사용한다.** 매번 다시 만들지 않는다 — 비싼 쪽은 복제(70ms)가 아니라 `DROP DATABASE`(1.2~2초, 즉시 체크포인트 강제)이고, 행은 어차피 `TRUNCATE` 되므로 재사용 DB 와 새 DB 가 테스트 입장에서 구분되지 않는다. 실측 근거는 TASK-0106 4.2.
>
> **`CREATE DATABASE ... TEMPLATE` 의 전제**: 원본 DB 에 **다른 세션이 붙어 있으면 실패한다.** 템플릿을 만든 커넥션을 명시적으로 닫은 뒤 복제하고, 이전 실행이 남긴 커넥션은 `DROP DATABASE ... (FORCE)` 로 정리한다. 구현자가 반드시 한 번 걸리는 지점이다.

전부 진짜 커밋이므로 트랜잭션·잠금이 프로덕션과 같은 의미로 동작한다. 초기화된 상태로 시작하는 성질은 그대로다.

기반 구축은 **TASK-0106**, 프론트 모킹·계약은 **TASK-0107** 이 담당한다.

## 예외 표기 방법

TASK 문서에서 이렇게 쓴다.

```markdown
### 6.2 품질 게이트
[공통 품질 게이트](../QUALITY-GATES.md) 적용. 예외:
- **Q5 면제** — 스캐폴딩이라 의미 있는 테스트 대상이 없음
- **2장 화면 게이트 해당 없음** — 사용자 대상 화면 없음
```

게이트 2~5장은 **TASK 가 무엇을 만드는지에 따라 자동으로 적용**된다. 화면과 API 를 모두 만드는 TASK 는 2·3·5장을 모두 받는다. 어느 게이트를 받는지 헷갈리면 그 TASK 가 레이어를 섞고 있다는 신호이므로, 쪼개는 것을 먼저 검토한다.

`Q5 강화` 라고 쓰면 해당 TASK 의 로직이 **분기 커버리지 100%** 대상이라는 뜻이다.
