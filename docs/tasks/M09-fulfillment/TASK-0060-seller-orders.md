## 1. 목적

판매자가 자기 주문을 처리하는 화면을 만든다. 발송 처리가 여기서 이뤄진다.

## 2. 범위

### 포함
- 주문 목록 (상태 탭, 기간·검색 필터, 커서 페이지네이션)
- 주문 상세 (항목·수령인·금액·상태 이력)
- 상태별 액션 버튼 (가능 액션 API 기반)
- 발송 처리 (운송장 발급 → SHIPPED)
- 일괄 발송 처리
- 신규 주문·처리 대기 건수 뱃지
- 주문서 인쇄용 뷰
- 엑셀 내보내기
- **모바일 전용 레이아웃** — 목록은 카드 변환, 상세·발송 처리는 폰에서 완결 가능

### 제외
- 배송 추적 (TASK-0061)
- 클레임 처리 (M10)

## 3. 요구사항

- [x] 자기 SellerOrder 만 보인다
- [x] 상태별로 필터링된다 — 탭 하나가 상태 여럿일 수 있어 **쉼표 목록**이다
- [x] 발송 처리하면 구매자 화면에 즉시 반영된다
- [x] 여러 건을 한 번에 발송 처리할 수 있다 — 실패 건은 개별로 남는다
- [x] 수령인 개인정보가 필요 이상 노출되지 않는다 — **마스킹은 서버가 한다**(4.2)
- [x] 360px 에서 주문 확인부터 발송 처리까지 완결할 수 있다

## 4. 설계

상태 탭: `결제완료` / `상품준비중` / `배송중` / `배송완료` / `취소·반품` / `전체`

액션 버튼은 **가능 액션 API 응답으로 렌더**한다. 화면에서 상태별 분기를 하드코딩하면 상태 머신과 어긋난다.

**개인정보**: 목록에는 이름 일부만(홍*동), 상세에서 전체를 보여준다. 데모 계정 데이터라도 습관을 들인다.

### 4.1 「배송완료 처리」는 **전용 라우트**다 (TASK-0061 4.4 에서 넘어옴)

전이표는 `SHIPPED → DELIVERED` 를 판매자에게도 허용하지만, 전이 라우트로 직접 찍으면
`Shipment.status` 가 따라오지 않는다 — 구매자의 추적 화면이 「이동 중」인 채로 주문만
배송완료가 된다. 셋 중 하나를 골라야 했고 **전용 라우트**(`POST /seller-orders/:id/delivery`)를
골랐다.

| 버린 안 | 왜 |
| --- | --- |
| 전이의 문이 배송을 알게 한다 | `SellerOrderModule` 이 `PrismaModule` 하나만 아는 성질이 깨진다. **그 좁음이** 예약 스케줄러와 결제 확정이 순환 없이 그 문을 지나는 이유다 (TASK-0059) |
| 버튼을 주지 않는다 | `GET /actions` 가 그 버튼을 **답으로 준다.** 안 그리려면 화면이 서버의 답을 걸러야 하고, 그것이 정확히 「화면이 상태로 분기하지 마라」가 금지하는 일이다 |

**사건의 출처를 함께 만들었다.** 판매자가 찍은 것을 그대로 기록하면 추적 줄에 「운송사가
알려 준 사실」의 문장이 남아, TASK-0061 이 그 자리에 라우트를 열지 않은 이유가 되살아난다.
그래서 사건에 출처(`CARRIER`/`SELLER`)를 두고 문장과 지점을 갈랐으며, **출처와 전이 주체를
한 값으로 묶어** 둘이 갈라질 수 없게 했다.

### 4.2 마스킹은 **서버가** 한다

목록 응답에 원본 이름도 전화번호도 **없다**. 화면이 가리면 응답에는 그대로 실려 나가고,
그 응답은 네트워크 탭·로그·캐시에 남는다 — 「가렸다」가 아니라 「안 보이게 그렸다」일 뿐이다.
검사가 응답 본문 전체를 훑어 원본이 없는지 본다. CSV 내보내기도 가려진 이름으로 나간다.

### 4.3 뱃지는 목록과 **따로** 센다

같은 요청으로 주면 싸 보이지만 셋이 어긋난다. ① 필터를 타면 그것은 뱃지가 아니라 「지금
목록의 개수」이고, 한 응답이 서로 다른 두 질문에 답하게 된다 ② 페이지를 넘길 때마다 표
전체를 다시 센다 ③ 뱃지가 필요한 자리는 목록 밖에도 있다(대시보드).

**「무엇이 처리 대기인가」는 서버가 정한다.** 화면 셋이 각자 더하면 상태가 늘 때 한 곳만
고쳐진다.

### 4.4 화면이 `GET /actions` 를 **그대로 믿으면 안 되는 자리가 하나 있다**

`PREPARING → SHIPPED` 는 전이의 문 앞에서 **언제나** `enabled: false, blockedBy: 'tracking'`
이다 — 운송장을 만드는 것이 바로 그 발송 라우트이기 때문이다. 그대로 믿고 버튼을 잠그면
판매자는 **영영 발송할 수 없다.**

그래서 화면은 「모자란 조건을 이 문이 채우는가」를 본다. 서버의 답을 무시하는 것이 아니라
**그 답이 어느 문 앞에서의 답인지**를 함께 읽는 것이고, API 검사가 그 전제(`enabled:false` +
`blockedBy:'tracking'`)를 못 박아 전제가 바뀌면 화면보다 먼저 빨개진다.

## 5. 구현 계획

1. 목록 API (필터·검색·커서)
2. 목록 화면 + 상태 탭
3. 상세 화면 + 이력
4. 액션 버튼 (가능 액션 기반)
5. 발송 처리 + 일괄 처리
6. 뱃지·인쇄·내보내기
