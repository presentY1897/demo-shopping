# TASK-0061: 배송 · 운송장 가상 처리

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M09 배송·주문관리 |
| 상태 | 완료 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/shipment` |
| 선행 작업 | TASK-0059 |

## 1. 목적

배송 도메인을 실제 서비스와 동일한 구조로 만들되, 운송사 연동 없이 **운송장과 추적 정보를 가상으로 생성**한다.

## 2. 범위

### 포함
- `Shipment` — SellerOrder, 운송사, 운송장번호, 상태, 발송·완료 시각
- `ShipmentTrackingEvent` — 추적 이력 (집화·간선상차·배송출발·배송완료)
- 가상 운송장번호 생성 (운송사별 형식 흉내, 실제와 겹치지 않게)
- 가상 운송사 목록
- 배송 조회 API (구매자·판매자)
- 배송 추적 UI 컴포넌트
- 분할 배송 지원 여부 결정 — **이번 범위에서는 SellerOrder 당 1건**

### 제외
- 자동 진행 (TASK-0062)
- 실제 택배사 API

## 3. 요구사항

- [x] 발송 처리 시 운송장이 발급된다 — 발급·전이·첫 사건이 **한 트랜잭션**이다
- [x] 운송장번호가 실제 운송사 형식과 구분된다 — `DEMO-` 접두어를 **DB 제약이** 지킨다
- [x] 구매자가 배송 추적 화면을 볼 수 있다 — 컴포넌트는 `packages/ui`, 붙이는 것은 TASK-0063
- [x] 추적 이벤트가 시간순으로 기록된다 — 같은 밀리초의 타이브레이커까지

## 4. 설계

```
운송장번호: DEMO-{운송사코드}-{12자리}   ← 실제 번호와 명확히 구분
운송사: 가상 운송사 3~4개 (실제 상표 사용 금지)
```

추적 이벤트는 실제 택배 조회 화면과 같은 형태로 보여준다. 시간·장소·상태가 나열되는 타임라인이다. 장소명도 가상으로 만든다.

**분할 배송을 이번에 넣지 않는 이유**: SellerOrder 안에서 다시 나뉘면 상태 판단이 한 단계 더 복잡해진다. 얻는 것에 비해 비용이 크다. 필요하면 이후 마일스톤에서 붙인다.

### 4.1 `Shipment` 는 `SellerOrder` 에 **1:1** 이다 (R2 정정)

R2 는 「1:N 으로 두되 지금은 1건만 생성」이라고 적었다. 실제로는 **유니크 제약**을 걸어
1:1 로 만들었다.

「관계는 열어 두고 규율로 1건만 만든다」는 **아무것도 지켜 주지 않는다.** 두 건이
생기는 날 그것을 막는 것이 없고, 그때 깨지는 것은 이 TASK 가 아니라 **상태 판단**이다 —
한 주문에 배송이 둘이면 「이 주문이 배송완료인가」에 답이 둘이 된다.

분할 배송을 여는 것은 **그 인덱스를 푸는 마이그레이션 하나**다. 지금 열어 두는 것보다
그때 여는 편이 싸고, 무엇보다 그 사이에 「둘이 생길 수 있다」를 전제로 쓴 코드가 없다.

### 4.2 `SellerOrder.trackingNumber` 를 **지우지 않고 파생 사본으로** 남긴다

단일 출처를 `Shipment` 로 옮기는 것이 TASK-0059 가 남긴 약속이었는데, 사실 하나만은
`SellerOrder` 에 남겼다. **상태 머신의 잠금 문장 때문이다.**

`SellerOrderService` 의 잠금은 「잠근 그 행의 컬럼만 읽는 한 문장」이어야 한다 — 다른
표를 조인하면 잠금을 기다린 뒤에도 **문장이 시작할 때의 스냅샷**으로 낡은 판단을 한다
(`payment.service.ts` 의 `lock()` 이 같은 이유로 같은 모양이고, 그 주석이 이미 경고한다).
사실을 통째로 옮기면 그 문장이 조인이 된다.

**그래서 판정이 읽는 사실 하나만 남기고 나머지를 전부 옮겼다** — 운송사·상태·시각·추적
이력은 `Shipment` 의 것이다.

사본이 갈라지지 않는 것은 **규율이 아니라 제약이 지킨다.**

```sql
FOREIGN KEY ("id", "trackingNumber") REFERENCES "Shipment"("sellerOrderId", "trackingNumber")
```

자기 배송의 번호가 아닌 값은 그 칸에 들어갈 수 없다. 시드·백필·미래의 코드가 사본만
손으로 적는 길이 막혔고, 그것이 「옮겼다」의 유일한 증거다.

⚠️ **Prisma 는 이 외래키를 모른다** (PSL 로 두 열짜리 참조를 적을 수 없다). 그래서 다음
`migrate diff` 생성물에 이 제약의 `DROP` 이 섞여 나온다 — `Category_path_idx` 와 **같은
방식으로 지우고 커밋**한다. 실수로 지워지면 조용하지 않다: 그 제약을 직접 때리는 검사
셋이 빨개진다.

### 4.4 판매자가 **직접** 배송완료를 찍으면 배송 표가 따라오지 않는다 (TASK-0060 으로 넘김)

전이표는 `SHIPPED → DELIVERED` 를 판매자에게도 허용한다(시뮬레이터가 멈춘 데모에서 흐름을
이어 갈 수 있어야 해서다). 그런데 그 길로 가면 **주문만 움직이고 `Shipment.status` 는
`IN_TRANSIT` 에 남는다** — 구매자의 추적 화면이 「이동 중」인 채로 주문은 배송완료다.

반대 방향이라 여기서 닫을 수 없다. 닫으려면 상태 전이의 문(`applyWithin`) 안에 **배송을 아는
코드**가 들어가야 하고, 그러면 주문이 배송을 알게 된다.

**받는 곳은 TASK-0060 이다.** 판매자 콘솔의 「배송완료 처리」 버튼이 전이 라우트가 아니라
**배송 사건을 기록하는 길**을 부르면 된다 — 그러면 두 표가 함께 움직이고 이력에는 사건이
남는다. 지금도 깨지지는 않는다: 나중에 `DELIVERED` 사건이 도착하면 배송이 따라오고
`applyWithin` 은 멱등이라 조용히 지나간다.

### 4.3 F6 은 이 TASK 의 것이다 — 시뮬레이터가 아니라 **도메인 규칙**

「배송완료 사건이 기록되면 주문이 `DELIVERED` 로 간다」는 배송 도메인의 규칙이지
시뮬레이터의 것이 아니다. 시뮬레이터가 없어도 판매자가 직접 찍는 길이 있고, 그때도 같은
일이 일어나야 한다. TASK-0062 가 만드는 것은 **「시간이 지나면 다음 사건이 저절로
일어난다」**뿐이다.

사건 기록·배송 상태·주문 전이는 **한 트랜잭션**이다. 갈라지면 「배송완료라고 적혀
있는데 주문은 배송중」이 된다.
