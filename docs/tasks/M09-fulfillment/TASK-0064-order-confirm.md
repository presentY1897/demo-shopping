| 항목 | 내용 |

## 1. 목적

구매확정을 구현한다. **정산(M12)과 적립금 지급(M11)의 트리거**이므로 이후 마일스톤의 전제가 된다.

## 2. 범위

### 포함
- 수동 구매확정 (구매자)
- 자동 구매확정 스케줄러 — 배송완료 D+7
- 데모 모드 시간 단축 (예: 배송완료 후 5분)
- 확정 시 후속 이벤트 발행 (정산 대상 등록·적립금 지급 자리)
- 확정 후 반품 제한 규칙
- 확정 예정일 안내 UI
- 헬스체크에 스케줄러 상태

### 제외
- 정산 실제 처리 (M12)
- 적립금 실제 지급 (M11)

## 3. 요구사항

- [x] 구매자가 배송완료된 주문을 확정할 수 있다
- [x] 확정하지 않아도 D+7 에 자동 확정된다
- [x] 데모에서는 짧은 시간 안에 자동 확정된다
- [x] 확정 후에는 반품 신청이 제한된다
- [x] 확정 시 후속 이벤트가 발행된다

## 4. 설계

```
DELIVERED --(구매자 확정 | D+7 자동)--> CONFIRMED
                                        ├→ 정산 대상 등록 (M12)
                                        └→ 적립금 지급 (M11)
```

**확정 후 반품 제한**: 확정은 "물건에 문제없음"을 인정하는 행위다. 확정 후에는 일반 반품을 막고, 하자 반품만 관리자 개입으로 처리한다. 이 규칙을 화면에 명시해 사용자가 성급히 확정하지 않게 한다.

**자동 확정 기간**: 실제 커머스는 7일이 표준이다. 데모 모드에서는 5분으로 단축하되, 화면에는 "실제 서비스에서는 7일"임을 안내한다.

### 4.1 「배송완료 시각」은 **상태 이력**에서 읽는다

후보가 둘이었다 — `OrderStatusHistory` 의 `DELIVERED` 줄과 `Shipment.deliveredAt`. 이력을
골랐고 이유가 셋이다.

1. **이력은 반드시 있다.** 상태를 옮기는 길이 `applyWithin` 하나뿐이고 그 문이 상태 변경과 이력을 한 트랜잭션으로 쓴다.
2. **배송 행은 뒤처질 수 있다.** 판매자가 전이 라우트로 직접 찍으면 배송 표가 안 따라온다. 그때 `Shipment.deliveredAt` 은 `NULL` 이고, 그것을 기준으로 삼은 배치는 그 주문을 **영원히 확정하지 않으면서 아무것도 실패시키지 않는다.**
3. **묻는 것이 「상태가 언제 옮겨졌나」다.** D+7 은 구매자가 반품을 말할 시간이고, 그 시작은 배송완료로 **선언된** 순간이다.

부수 효과로 이 배치는 배송 표를 **아예 읽지 않아** 시뮬레이터와 떨어져 있다.

### 4.2 축은 하나, 숫자는 둘

`FULFILLMENT_PACE`(TASK-0062 4.1)를 그대로 쓴다. 압축 판단은 **함수 하나**이고
(`autoConfirmWindowMsOf`), 부르는 쪽은 전부 밀리초만 본다.

| | `demo`(기본) | `realistic` |
| --- | --- | --- |
| 배송 단계당 | 2분 (전체 6분) | 4시간 |
| **자동 확정** | **5분** | **7일** |

### 4.3 날짜는 서버가, 규칙은 화면이

「실제 서비스에서는 7일」은 `realistic` 에서 거짓이 되고, 화면이 D+7 을 직접 더하면 `demo`
에서 **날짜 자체가 거짓**이 된다. 화면은 이 설정을 어떤 응답에서도 읽을 수 없으므로 어느
쪽이든 혼자서는 정직할 수 없다.

그래서 계약에 `autoConfirmAt` 을 더했다. 서버가 자기 기간으로 계산해 보내고, 화면은 두
문장을 나란히 둔다 — **정확한 시각**(서버 값, 어느 설정에서도 참)과 **규칙**(「실제 서비스의
기준은 7일」, 어느 설정에서도 참). **화면이 「지금은 압축된 시간입니다」라고 단언하지 않는
것**이 요점이다: 단언하면 `realistic` 에서 그 말이 거짓이 된다.

### 4.4 확정 후 반품 제한은 **이미 있다** — 새 규칙을 만들지 않았다

`seller-order-transitions.ts` 에서 `CONFIRMED` 는 종착 상태(나가는 화살표 없음)이고, 상태를
옮기는 길이 그 표를 지나는 문 하나뿐이라 그것으로 끝이다. 검사가 실제로 잰다 — 확정 뒤
판매자의 반품 시도는 409 이고, 네 주체 전부에게 가능한 전이가 빈 배열이다.

**부족했던 것은 화면이었다.** 확정되면 취소·반품 안내가 그냥 **사라져** 이유를 말하지
않았다. 그 자리에 문장을 세웠다. 「하자 반품 관리자 개입」에 해당하는 전이는 **만들지
않았다** — 그것은 클레임 절차(M10)이지 이 표의 화살표가 아니다.

### 4.5 후속 이벤트를 **전이의 문에 걸었다**

정산(M12)·적립금(M11)의 자리를 `SellerOrderService.publish()` 에 뒀다. **수동·자동 두 길이
지나는 유일한 자리**라, 「구매자가 누른 확정에만 적립금이 붙는」 어긋남이 구조적으로
불가능해진다. 멱등 열쇠는 몫의 id 그 자체다 — 확정은 평생 한 번이다.
