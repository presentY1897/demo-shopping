## 1. 목적

상품 변경을 검색 인덱스에 반영하는 파이프라인을 만든다. **DB 와 검색엔진을 분리하고 이벤트로 동기화**하는 구조 자체가 이 프로젝트의 설명 포인트다. (D-013)

## 2. 범위

### 포함
- 인덱스 스키마: 검색 대상 필드, 필터 가능 필드, 정렬 가능 필드, 순위 규칙
- 상품 → 인덱스 문서 변환 (속성 JSONB 를 패싯 필드로 평탄화)
- 변경 이벤트 발행 (생성·수정·삭제·재고 변동·가격 변동)
- 인덱싱 워커 (큐 기반, **1초 주기 폴링**, 실패 재시도)
- 한글 보조 필드(자모·초성) 생성 자리 — TASK-0103 에서 채운다
- 전체 재색인 명령
- **인덱스 소실 감지 후 자동 재색인** — 배포 환경에 영구 디스크가 없어 재시작마다 인덱스가 비워진다 (TASK-0009)
- 동의어 사전 (니트↔스웨터 등)
- 인덱싱 지연·실패를 헬스체크에 노출

### 제외
- 검색 API (TASK-0039)
- 화면 (TASK-0041)

## 3. 요구사항

- [x] 상품을 등록하면 **2초 내** 검색된다
- [x] 상품을 판매중지하면 검색에서 사라진다
- [x] 인덱싱이 실패해도 상품 저장은 성공한다
- [x] 전체 재색인이 가능하다
- [x] 인덱스가 비어 있으면 자동으로 다시 채워진다
- [x] 인덱싱 큐가 밀리면 헬스체크로 알 수 있다

## 4. 설계

```
상품 저장(트랜잭션 커밋) → 아웃박스 테이블에 이벤트 기록
                            ↓
                    인덱싱 워커(1초 주기 폴링) → Meilisearch 반영 → 이벤트 완료 표시
```

**아웃박스 방식을 쓰는 이유**: 상품 저장과 인덱싱을 한 트랜잭션에 묶으면 검색엔진 장애가 상품 등록을 막는다. 반대로 트랜잭션 밖에서 직접 호출하면 커밋 실패 시 유령 문서가 남는다. 아웃박스는 둘 다 피한다.

| 인덱스 필드 | 용도 |
| --- | --- |
| `name`, `brandName`, `categoryPath`, `description` | 검색 |
| `categoryId`, `sellerId`, `price`, `attributes.*`, `inStock` | 필터·패싯 |
| `price`, `salesCount`, `ratingAvg`, `createdAt` | 정렬 |

## 5. 구현 계획

1. 인덱스 스키마·설정 (검색·필터·정렬 필드, 순위 규칙)
2. 상품 → 문서 변환기 (속성 평탄화)
3. 아웃박스 테이블·이벤트 발행
4. 인덱싱 워커 + 재시도
5. 전체 재색인 명령
6. 동의어 사전
7. 헬스체크 연동

## 8. 확정된 버전

| 패키지 | 버전 |
| --- | --- |
| (없음) | 공식 클라이언트를 쓰지 않는다 |

**`meilisearch` 클라이언트를 들이지 않는다.** 저장소에 이미 선례가 둘 있다.

- `SearchHealthIndicator` 가 **지금도** Meilisearch 와 `fetch` 로 이야기한다.
- `apps/api/src/storage/sigv4.ts` — R2 에 쓰려고 **AWS SigV4 서명을 직접 구현했다.** `@aws-sdk`
  대신에. 그것에 비하면 Meilisearch 의 REST 는 훨씬 단순하다(문서 PUT, 검색 POST, 설정 PATCH).

그리고 포트가 필요하다. `ObjectStorage` 가 그렇듯 **검색 엔진도 인터페이스 뒤에 두어야** 엔진 없이
문서 변환기와 워커 재시도를 검사할 수 있고(Q5), 엔진이 죽었을 때의 동작이 대역으로 재현된다(F4).
공식 클라이언트를 들이면 그 포트를 클라이언트 위에 한 겹 더 얹게 된다.
