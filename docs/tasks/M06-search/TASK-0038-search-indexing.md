## 1. 목적

상품 변경을 검색 인덱스에 반영하는 파이프라인을 만든다. **DB 와 검색엔진을 분리하고 이벤트로 동기화**하는 구조 자체가 이 프로젝트의 설명 포인트다. (D-013)

## 2. 범위

### 포함
- 인덱스 스키마: 검색 대상 필드, 필터 가능 필드, 정렬 가능 필드, 순위 규칙
- 상품 → 인덱스 문서 변환 (속성 JSONB 를 패싯 필드로 평탄화)
- 변경 이벤트 발행 (생성·수정·삭제·재고 변동·가격 변동)
- 인덱싱 워커 (큐 기반, **1초 주기 폴링**, 실패 재시도)
- 한글 보조 필드(자모·초성) 생성 자리 — TASK-0103 에서 채운다
- 전체 재색인 명령
- **인덱스 소실 감지 후 자동 재색인** — 배포 환경에 영구 디스크가 없어 재시작마다 인덱스가 비워진다 (TASK-0009)
- 동의어 사전 (니트↔스웨터 등)
- 인덱싱 지연·실패를 헬스체크에 노출

### 제외
- 검색 API (TASK-0039)
- 화면 (TASK-0041)

## 3. 요구사항

- [ ] 상품을 등록하면 **2초 내** 검색된다
- [ ] 상품을 판매중지하면 검색에서 사라진다
- [ ] 인덱싱이 실패해도 상품 저장은 성공한다
- [ ] 전체 재색인이 가능하다
- [ ] 인덱스가 비어 있으면 자동으로 다시 채워진다
- [ ] 인덱싱 큐가 밀리면 헬스체크로 알 수 있다

## 4. 설계

```
상품 저장(트랜잭션 커밋) → 아웃박스 테이블에 이벤트 기록
                            ↓
                    인덱싱 워커(1초 주기 폴링) → Meilisearch 반영 → 이벤트 완료 표시
```

**아웃박스 방식을 쓰는 이유**: 상품 저장과 인덱싱을 한 트랜잭션에 묶으면 검색엔진 장애가 상품 등록을 막는다. 반대로 트랜잭션 밖에서 직접 호출하면 커밋 실패 시 유령 문서가 남는다. 아웃박스는 둘 다 피한다.

| 인덱스 필드 | 용도 |
| --- | --- |
| `name`, `brandName`, `categoryPath`, `description` | 검색 |
| `categoryId`, `sellerId`, `price`, `attributes.*`, `inStock` | 필터·패싯 |
| `price`, `salesCount`, `ratingAvg`, `createdAt` | 정렬 |

## 5. 구현 계획

1. 인덱스 스키마·설정 (검색·필터·정렬 필드, 순위 규칙)
2. 상품 → 문서 변환기 (속성 평탄화)
3. 아웃박스 테이블·이벤트 발행
4. 인덱싱 워커 + 재시도
5. 전체 재색인 명령
6. 동의어 사전
7. 헬스체크 연동

## 7. 리스크 / 열린 질문

| # | 내용 | 대응 |
| --- | --- | --- |
| R1 | **한국어 복합명사 분해가 nori 대비 약함**(D-013 리스크) | 실제 상품명 800개로 검색 품질 측정. 부족하면 동의어 사전으로 보완하고 결과를 문서화 |
| R2 | 아웃박스 이벤트 적체 | 처리 지연 임계치 초과 시 헬스체크 degraded |
| R3 | 재고 변동마다 인덱싱하면 부하 | `inStock` 불리언만 인덱싱하고 값이 바뀔 때만 이벤트 발행 |
| R4 | 1초 폴링이 DB 부하를 유발 | 아웃박스 조회는 인덱스 걸린 단순 쿼리다. 부하 측정 후 필요하면 주기를 조정 |
| R5 | 자동 재색인이 반복 트리거되어 DB 를 때림 | 문서 수가 0 일 때만 트리거하고 실행 중에는 락으로 막는다 |
