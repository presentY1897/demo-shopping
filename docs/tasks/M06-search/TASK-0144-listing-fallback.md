# TASK-0144: 검색 엔진 없이도 목록은 나온다 — 질의 없는 목록의 DB 폴백

> **보류한다 (2026-09-18).** 이 문서는 「엔진이 돌아오는 데 4분 45초가 걸린다」는 관측에서 출발했는데, 그 시간은
> 잠에서 깬 시간이 아니라 서버 설정 변경에 따른 재배포였다. 같은 날 두 서비스가 Starter 가 되고 엔진에 디스크가
> 붙어(TASK-0145), 엔진에 닿지 못하는 구간은 **배포 · 재기동 때의 약 40초**로 줄었다. 그 40초는 TASK-0143 의 화면
> 대기가 덮는다. 설계는 버리지 않는다 — 검색 엔진이 자주 내려가거나 트래픽이 늘면 여기서 다시 시작한다.
> 승인된 문서가 아니며, 아래 1장의 수치는 위 사정을 감안해 읽는다.

## 1. 목적

TASK-0143 은 검색 엔진에 닿지 못하는 동안 화면이 **기다리게** 했다. 운영에서 재 보니 그것만으로는 모자랐다 —
엔진이 돌아오는 데 4분 45초가 걸린 날이 있었고(2026-09-18), 화면의 예산은 150초다. 구매자 홈의 「신상품」·
「인기 상품」은 그동안 스켈레톤이다가 실패 안내로 끝난다.

그런데 그 두 줄은 **검색이 아니다.** 검색어도 필터도 없고, `createdAt` 이나 `salesCount` 순으로 12개를 읽는
목록이다. 검색 인덱스는 PostgreSQL 의 사본이므로, 사본에 닿지 못하면 **원본에서 읽으면 된다.**

끝나면 — 엔진이 내려가 있어도 홈과 브랜드관의 상품 줄은 곧바로 나온다. 검색어 · 필터가 있는 요청만
TASK-0143 의 503 과 「검색을 준비하고 있어요」로 남는다.

## 2. 범위

### 포함

- API: 엔진에 닿지 못했을 때, **폴백이 답할 수 있는 모양의 요청**이면 PostgreSQL 에서 같은 응답을 만든다
- 폴백이 답할 수 있는 모양: 검색어 없음 · 필터 없음 · 정렬 `newest` 또는 `sales` · 첫 페이지. `sellerIds` 는 허용
  (브랜드관 · 「팔로우한 브랜드의 신상품」)
- **폴백이 낡지 않게 하는 구조** (4.3) — 이 TASK 의 절반이다
- 응답이 어디서 왔는지 알리는 헤더, 폴백이 쓰인 횟수를 헬스에 노출
- 대역 · 화면: 폴백 응답은 봉투가 같으므로 화면 변경은 없다. 있다면 스펙 보강뿐이다

### 제외 (이번에 하지 않는 것)

- 검색어 · 속성 필터 · 가격 범위 · 패싯 · 한글 자모 검색의 폴백 — 그것은 검색 엔진을 한 벌 더 만드는 일이다 (D-282 유지)
- 커서가 있는 다음 페이지의 폴백 — 홈과 브랜드관 첫 화면은 첫 페이지만 쓴다
- 폴백 결과의 캐시 · 스냅샷 테이블 — **자리만 정해 두고 만들지 않는다** (4.4)
- 엔진을 깨워 두기, 유료 플랜 · 디스크 (운영 설정의 문제이고 TASK-0143 4.6 이 따로 확인 중이다)

## 3. 요구사항

### 기능 요구사항

- [ ] 엔진에 닿지 못하고 요청이 폴백 가능한 모양이면 200 과 상품 목록으로 답한다
- [ ] 폴백이 답한 목록은 **엔진이 같은 데이터로 답했을 목록과 같다** — 같은 상품, 같은 순서, 같은 필드
- [ ] 폴백 불가능한 모양이면 TASK-0143 그대로 503 · `SEARCH_UNAVAILABLE`
- [ ] 엔진이 정상이면 폴백 경로는 한 줄도 실행되지 않는다
- [ ] 색인 대상이 아닌 상품(비공개 · 삭제 · 판매 중이 아님)은 폴백으로도 나오지 않는다
- [ ] 응답 헤더로 출처를 알 수 있다 (`X-Search-Source: database`)

### 비기능 요구사항

- 폴백 한 번의 비용: 쿼리 2개 이하, p95 200ms 이하 (검색 API 의 예산과 같다)
- 새 검색 파라미터가 생기면 **기본값은 「폴백 불가」다** — 모르는 조건을 무시한 채 목록을 주지 않는다

## 4. 설계

### 4.1 어디에 끼우는가

```
SearchService.search(query)
  → index.search(request)                    엔진이 답하면 여기서 끝난다
  ⇣ SearchEngineUnreachableError
  → fallbackPlanFor(query)                   순수 함수. 답할 수 있는 모양인가
       null  → 503 · SEARCH_UNAVAILABLE      (TASK-0143 그대로)
       plan  → readListing(prisma, plan)     PostgreSQL
             → toHit(toDocument(source))     색인에 넣을 때와 같은 변환
```

`suggest` 에는 폴백이 없다 — 자동완성은 검색어가 전부다.

### 4.2 「같은 목록」을 만드는 세 가지

폴백이 엔진과 다른 답을 하면 그것은 장애 때만 나타나는 버그다. 가장 늦게 발견되는 종류다. 그래서 새로 짓지
않고 **색인이 쓰는 것을 그대로 쓴다.**

| 같아야 하는 것 | 엔진 쪽 | 폴백이 쓰는 것 |
| --- | --- | --- |
| 무엇이 목록에 들어가는가 | `readIndexablePage` 의 SQL 조건 (`deletedAt IS NULL AND status = 'ACTIVE'`) 과 `isIndexable()` | SQL 조건은 **같은 상수**를 공유하고, 읽은 뒤 `isIndexable()` 을 한 번 더 통과시킨다 — 색인 워커가 하는 순서 그대로다 |
| 한 상품이 어떤 모양인가 | `SOURCE_SQL` → `toSource` → `toDocument` → `toHit` | **같은 함수 넷**을 그대로 부른다. 썸네일 · 재고 · 평점이 따로 계산되지 않는다 |
| 순서 | `SORTS.newest = createdAt:desc`, `SORTS.sales = salesCount:desc` | 같은 `SORTS` 표에서 SQL `ORDER BY` 를 만든다. 표에 없는 정렬은 계획이 `null` 이다 |

동률의 순서는 엔진과 DB 가 다를 수 있다. 폴백은 `id` 를 두 번째 정렬 키로 두어 **자기 안에서는** 안정적이게 하고,
엔진과의 비교(4.3)는 동률이 없는 데이터로 한다. 동률 순서까지 맞추는 것은 하지 않는다 — 장애 중의 목록에서
같은 판매량의 두 상품이 자리를 바꾸는 것은 고칠 가치가 없다.

### 4.3 폴백을 갱신하는 구조 — 낡으면 빌드가 깨진다

폴백은 평소에 실행되지 않는다. 그래서 검색이 바뀔 때 함께 바뀌지 않으면 **아무도 모르게 낡는다.** 데이터는
낡지 않는다 — 매번 PostgreSQL 을 읽으므로 항상 원본이다. 낡는 것은 **규칙**이다. 그것을 사람의 기억이 아니라
검사에 맡긴다.

1. **동등성 스펙 (parity).** 실 PostgreSQL + 실 Meilisearch 에 같은 상품을 넣고, 폴백 가능한 모양의 요청마다
   「엔진의 답」과 「엔진을 끊고 받은 폴백의 답」을 **필드 단위로 비교**한다. 문서에 필드를 더하고 폴백을 잊으면,
   정렬 규칙을 바꾸고 폴백을 잊으면, 색인 조건을 바꾸고 폴백을 잊으면 — 이 스펙이 깨진다.
2. **모양의 목록은 닫혀 있다.** `fallbackPlanFor` 는 `SearchQuery` 의 **모든 키를 나열해** 판정한다(허용 · 거부).
   스키마에 키가 생기면 타입 검사가 「이 키를 어떻게 할지 정하라」며 실패한다 — `Record<keyof SearchQuery, …>`
   한 줄이 그 일을 한다. 기본값은 거부다.
3. **쓰였다는 사실이 보인다.** 폴백이 답할 때마다 `warn` 한 줄과 헬스의 `searchFallback: { count, lastAt }`.
   한 번도 안 쓰인 폴백과 매일 쓰이는 폴백은 다른 결정을 부른다.

### 4.4 나중에 캐시가 필요해지면 — 자리만 정해 둔다

지금은 만들지 않는다. 상품 866개에서 `ORDER BY … LIMIT 12` 는 인덱스 하나로 끝난다(`Product(status, createdAt desc)`
는 있고, `salesCount` 용 인덱스는 구현 때 실측해서 정한다).

다만 목록이 커지거나 폴백이 자주 쓰이게 되면 매 요청의 쿼리가 부담이 될 수 있다. 그때를 위해 **읽는 쪽을
인터페이스 하나 뒤에 둔다.**

```ts
interface ListingFallback {
  read(plan: FallbackPlan): Promise<readonly ProductSource[]>
}
```

- 지금의 구현은 `LiveListingFallback` — 매번 PostgreSQL.
- 나중의 구현은 `SnapshotListingFallback` — 목록별 상위 N개를 테이블(또는 메모리)에 들고 있다가 읽는다.
  **그것을 갱신하는 신호는 이미 있다**: 상품이 바뀔 때마다 색인 워커가 소비하는 아웃박스 이벤트
  (`SearchOutboxService`). 스냅샷은 그 이벤트의 두 번째 소비자가 되면 되고, 새 발행 지점을 만들 필요가 없다.
- 4.3 의 동등성 스펙은 구현이 바뀌어도 그대로 쓴다 — 스냅샷이 낡으면 같은 스펙이 잡는다.

### 4.5 데이터 모델 · API · 화면 · 권한

- 데이터 모델: 변경 없음 (인덱스 추가 여부는 실측 뒤)
- API: `GET /search` 의 응답 봉투 불변. 헤더 `X-Search-Source: engine | database`. 폴백 응답은 `facets: {}`,
  `nextCursor: null`, `total` 은 색인 대상 수
- 화면: 변경 없음 — 홈 · 브랜드관은 `items` 만 쓴다. `useSection` 은 200 을 받으면 곧바로 그린다
- 권한: 공개 엔드포인트, 변경 없음

## 5. 구현 계획

1. `fallbackPlanFor` + 단위 스펙 (모든 `SearchQuery` 키의 허용 · 거부)
2. `readListing` — `SOURCE_SQL` · 색인 조건 상수 · `SORTS` 공유, `ListingFallback` 인터페이스와 `LiveListingFallback`
3. `SearchService.search` 의 분기 + 헤더 + 로그 · 헬스 계수
4. 동등성 스펙 (실 DB + 실 엔진), 장애 통합 스펙 (엔진 끊고 홈 · 브랜드관 모양 → 200, 검색어 모양 → 503)
5. 성능 스펙 — 쿼리 수 · p95, `salesCount` 인덱스 결정
6. 대역 · shop 스펙 보강 — 「헬스는 `search: down`, `/search?sort=…` 는 200」일 때 홈이 곧바로 상품을 그린다
7. 문서 — `error-contract.md` · `pages.md` · 결정 기록, 인덱스
