| 항목 | 내용 |

## 1. 목적

**`코ㅌ` 를 입력해도 `코트` 가 자동완성에 뜨게** 한다. 한글 입력은 조합 중 상태를 거치므로 일반 접두어 검색만으로는 잡히지 않는다.

## 2. 범위

### 포함
- 자모 분해·조합 유틸 (`packages/shared`)
- 인덱싱 시 보조 필드 생성 — `nameJamo`(자모 분해), `nameChosung`(초성)
- 검색어를 같은 방식으로 변환해 매칭
- **초성 검색** — `ㅋㅌ` → `코트`
- 조합 중 상태 처리 — `코ㅌ` → `코트`
- 영문·숫자 혼용 상품명 처리
- 자동완성 응답 속도 유지

### 제외
- 형태소 분석 (Meilisearch 기본 세그멘터에 의존)
- 오타 보정 (Meilisearch 기본 기능 사용)

## 3. 요구사항

- [x] `코ㅌ` 입력 시 `코트` 가 후보에 나온다
- [x] `ㅋㅌ` 입력 시 `코트` 가 후보에 나온다
- [x] 완성된 글자 검색 결과가 나빠지지 않는다
- [x] 자동완성 응답이 느려지지 않는다

## 4. 설계

Meilisearch 는 접두어 검색과 오타 보정을 기본 제공하지만, **한글의 조합 중 상태나 초성 검색은 지원하지 않는다.** `코ㅌ` 는 유니코드상 `코` + 호환 자모 `ㅌ` 이라 `코트`와 매칭되지 않는다. (D-013 에서 언급한 한국어 한계의 구체적 사례)

색인에 보조 필드를 두어 해결한다.

```
상품명   "울 롱코트"
nameJamo    "ㅇㅜㄹ ㄹㅗㅇㅋㅗㅌㅡ"     ← 자모 완전 분해
nameChosung "ㅇ ㄹㅋㅌ"                ← 초성만

검색어 "코ㅌ"  → 자모 분해 "ㅋㅗㅌ"    → nameJamo 접두어 매칭 → 적중
검색어 "ㅋㅌ"  → 초성으로 판별         → nameChosung 매칭    → 적중
```

> **2026-09-05 정정** — 위 예시의 초성이 `ㅇ ㄹㅋ` 로 적혀 있었다. 「롱코트」는 세 음절이므로
> `ㄹㅋㅌ` 이다. 한 글자가 빠진 예시를 그대로 구현하면 마지막 음절이 사라진다.

### 4.1 초성 매칭의 실제 범위 — 재 봤다 (2026-09-05)

「접두어만 맞을 것」이라고 예상했다가 **틀렸다.** 엔진의 세그멘터는 호환 자모를 **한 글자씩**
토큰으로 쪼개므로, 초성 검색은 토큰 **나열**을 찾는 것이 된다. 실제 엔진에 대고 잰 결과:

| 색인된 초성 | `ㅋㅌ` | `ㄹㅋ` | `ㅇㅋ` | `ㅌㅋ` |
| --- | --- | --- | --- | --- |
| `ㅋㅌ` (코트) | **1위** | — | — | — |
| `ㅇ` `ㄹㅋㅌ` (울 롱코트) | **2위** | ✓ | — | — |
| `ㅋㅍ` `ㅌㅅ` (커피 토스트) | **3위** | — | — | — |

읽을 것 셋:

1. **낱말 가운데도 맞는다.** 「롱코트」가 `ㅋㅌ` 로 나온다 — 접미사를 색인할 필요가 없었다.
2. **낱말을 건너서도 맞는다.** 「커피 토스트」가 `ㅋㅌ` 로 나온다. R1 이 경계한 「지나치게
   넓힘」이 바로 이것이다.
3. **순서가 그것을 감당한다.** 정확히 맞은 것이 1위, 낱말 가운데가 2위, 건너뛴 것이 3위다 —
   근접도 랭킹이 하는 일이고, 자동완성은 상위 8개만 보여 주므로 실질적으로 걸러진다.

`ㅇㅋ`·`ㅌㅋ` 가 아무것도 못 찾는 것이 이것이 「자모를 아무거나 포함」이 **아니라는** 증거다 —
순서가 있고, 사이가 너무 멀면 떨어진다.

**자모·초성 필드에서는 오타 보정을 끈다.** 거기 든 것은 사람이 친 낱말이 아니라 펴 놓은
글자열이고, 「한 글자 다름」은 뜻이 없이 후보만 넓힌다. 완성형 이름의 오타 보정은 그대로다 —
「레트루 → 레트로」는 TASK-0039 가 실측해서 남긴 기능이다.

## 5. 구현 계획

1. 자모 분해·초성 추출 유틸 + 단위 테스트
2. 검색어 유형 판별 로직
3. 인덱싱 파이프라인에 보조 필드 추가 (TASK-0038 변환기 확장)
4. 전체 재색인
5. 자동완성 API 에 분기 적용
6. 순위 가중치 조정
7. 실제 상품명 800개로 품질 측정
