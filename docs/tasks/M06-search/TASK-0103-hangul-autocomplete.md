# TASK-0103: 한글 자모 · 초성 자동완성

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M06 검색·탐색 |
| 상태 | 승인됨 |
| 작성일 | 2026-09-02 |
| 브랜치 | `feature/hangul-autocomplete` |
| 선행 작업 | TASK-0039 |

## 1. 목적

**`코ㅌ` 를 입력해도 `코트` 가 자동완성에 뜨게** 한다. 한글 입력은 조합 중 상태를 거치므로 일반 접두어 검색만으로는 잡히지 않는다.

## 2. 범위

### 포함
- 자모 분해·조합 유틸 (`packages/shared`)
- 인덱싱 시 보조 필드 생성 — `nameJamo`(자모 분해), `nameChosung`(초성)
- 검색어를 같은 방식으로 변환해 매칭
- **초성 검색** — `ㅋㅌ` → `코트`
- 조합 중 상태 처리 — `코ㅌ` → `코트`
- 영문·숫자 혼용 상품명 처리
- 자동완성 응답 속도 유지

### 제외
- 형태소 분석 (Meilisearch 기본 세그멘터에 의존)
- 오타 보정 (Meilisearch 기본 기능 사용)

## 3. 요구사항

- [ ] `코ㅌ` 입력 시 `코트` 가 후보에 나온다
- [ ] `ㅋㅌ` 입력 시 `코트` 가 후보에 나온다
- [ ] 완성된 글자 검색 결과가 나빠지지 않는다
- [ ] 자동완성 응답이 느려지지 않는다

## 4. 설계

Meilisearch 는 접두어 검색과 오타 보정을 기본 제공하지만, **한글의 조합 중 상태나 초성 검색은 지원하지 않는다.** `코ㅌ` 는 유니코드상 `코` + 호환 자모 `ㅌ` 이라 `코트`와 매칭되지 않는다. (D-013 에서 언급한 한국어 한계의 구체적 사례)

색인에 보조 필드를 두어 해결한다.

```
상품명   "울 롱코트"
nameJamo    "ㅇㅜㄹ ㄹㅗㅇㅋㅗㅌㅡ"     ← 자모 완전 분해
nameChosung "ㅇ ㄹㅋㅌ"                ← 초성만

검색어 "코ㅌ"  → 자모 분해 "ㅋㅗㅌ"    → nameJamo 접두어 매칭 → 적중
검색어 "ㅋㅌ"  → 초성으로 판별         → nameChosung 매칭    → 적중
```

> **2026-09-05 정정** — 위 예시의 초성이 `ㅇ ㄹㅋ` 로 적혀 있었다. 「롱코트」는 세 음절이므로
> `ㄹㅋㅌ` 이다. 한 글자가 빠진 예시를 그대로 구현하면 마지막 음절이 사라진다.

### 4.1 초성은 **낱말 앞에서만** 맞는다 (2026-09-05)

엔진은 접두어를 찾지 부분 문자열을 찾지 않는다. 그래서 보조 필드도 **낱말 단위**로 만든다 —
「울 롱코트」의 초성은 한 덩어리 `ㅇㄹㅋㅌ` 이 아니라 `ㅇ ㄹㅋㅌ` 이고, 검색어 `ㅋㅌ` 는
`ㄹㅋㅌ` 의 **가운데**라 걸리지 않는다.

실제 카탈로그에서는 그것으로 충분하다. 시드의 상품명은 「오버핏 울 발마칸 코트」처럼 코트가
**독립된 낱말**이므로 초성 `ㅋㅌ` 가 그 낱말의 앞에서 맞는다. 낱말 가운데를 맞히려면 모든
접미사를 색인해야 하고, 그것은 인덱스 크기를 몇 배로 만든다(R2 가 경계하는 바로 그것).

**이 한계는 적어 두고 넘어간다.** 「롱코트」를 `ㅋㅌ` 로 찾고 싶다면 그때 접미사 색인의 비용을
다시 재는 것이지, 지금 조용히 감수할 것이 아니다.

**검색어 유형 판별**이 관건이다. 입력이 전부 자음이면 초성 검색, 자모가 섞이면 자모 검색, 완성형이면 기본 검색으로 보낸다. 판별을 잘못하면 결과가 엉뚱해진다.

가중치는 **완성형 매칭 > 자모 매칭 > 초성 매칭** 순으로 둔다. 초성 검색은 후보가 넓어 정확도가 낮다.

## 5. 구현 계획

1. 자모 분해·초성 추출 유틸 + 단위 테스트
2. 검색어 유형 판별 로직
3. 인덱싱 파이프라인에 보조 필드 추가 (TASK-0038 변환기 확장)
4. 전체 재색인
5. 자동완성 API 에 분기 적용
6. 순위 가중치 조정
7. 실제 상품명 800개로 품질 측정
