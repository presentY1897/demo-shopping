# TASK-0143: 검색 엔진에 닿지 못할 때 — 500 이 아니라 503, 화면은 기다린다

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M06 검색·탐색 |
| 상태 | 완료 — 무료 플랜의 절전 상태는 잡지 못한다는 한계와 함께 (4.7) |
| 작성일 | 2026-09-17 |
| 브랜치 | `feature/search-unavailable` |
| 선행 작업 | TASK-0039, TASK-0101, TASK-0118, TASK-0119 |

## 1. 목적

2026-09-17, 운영 구매자 홈의 「신상품」·「인기 상품」 두 줄이 「상품을 불러오지 못했어요」로 끝났다.
브라우저 콘솔에는 `GET /api/v1/search?sort=sales&limit=12` 와 `sort=newest` 가 **500** 으로 찍혔다.

그 순간 API 의 `/health` 는 `database: "ok"`, `search: "down"` 이었다. **API 는 깨어 있었고 검색 엔진에만
닿지 못했다.** 검색 엔진(`shopping-search`)은 API 와 따로 뜨는 무료 서비스라 따로 잠들고, 디스크가 없어
따로 재기동한다(TASK-0009, TASK-0119 4.1). 엔진이 12.7초 만에 깨어난 뒤에는 같은 주소가 200 에 783건을
돌려줬다.

고칠 것은 두 가지다.

1. **API 가 상태를 결함이라고 말한다.** 엔진에 닿지 못한 것은 「잠깐 뒤에 된다」인데 `INTERNAL_ERROR` 500 으로
   나간다. 화면은 그것을 기다릴 일인지 포기할 일인지 구별할 수 없다.
2. **화면이 기다리는 동안 실패를 말한다.** 구매자 홈은 `search !== "ok"` 를 이미 알고(TASK-0101 4.7) 5·15·30초
   뒤에 세 번 다시 확인한다. 그런데 그 50초 동안 상품 줄은 500 을 받아 「상품을 불러오지 못했어요」와 재시도
   버튼을 띄우고, 세 번이 끝나면 멈춰 버튼을 기다린다. 부팅이 90초 걸리는 플랫폼에서 50초는 짧다.

끝나면 — 엔진이 잠들었거나 재기동 중일 때 홈을 연 방문자는 실패 문구 대신 「상품을 준비하고 있어요」를 보고,
**아무것도 누르지 않아도** 엔진이 돌아오는 대로 상품이 나타난다.

## 2. 범위

### 포함

- API: 검색 엔진에 **닿지 못한** 요청을 503 · `SEARCH_UNAVAILABLE` 로 답한다 — 엔진을 부르는 `/search` 와
  `/search/suggest`. `/search/filters` 는 PostgreSQL 만 읽으므로 엔진이 내려가 있어도 200 이다
- shop: 헬스가 `search !== "ok"` 인 동안 TASK-0118 의 예산·백오프로 헬스를 **계속 확인**하고, 돌아오면 홈의
  상품 줄이 스스로 다시 읽는다
- shop: 홈 상품 줄과 검색 결과 목록이 `SEARCH_UNAVAILABLE` 을 실패가 아니라 **준비 중**으로 그린다
- 대역(`packages/api-mocks`)에 「엔진에 닿지 못함」 상태와 그것이 풀리는 시나리오
- `docs/design/error-contract.md` 에 코드 한 줄, `docs/design/pages.md` 콜드 스타트 화면 규약에 이 경우

### 제외 (이번에 하지 않는 것)

- **검색 엔진을 계속 깨워 두기.** 타이머·주기 핑은 무료 플랜의 인스턴스 시간을 쓴다 (TASK-0009 R8, TASK-0101 4.8)
- 엔진에 영구 디스크를 붙이거나 유료 플랜으로 옮기기
- DB 로 검색을 대신하는 폴백 — 정렬·패싯·한글 자모 검색을 두 벌로 만들게 된다
- 판매자·관리자 콘솔 — 두 콘솔은 검색 API 를 부르지 않는다 (`/search` 호출부는 `apps/shop` 에만 있다)
- **2026-09-17 에 엔진이 왜 내려가 있었는지의 규명** — 7장 R1. 원인이 무엇이든 이 TASK 의 동작은 같다

## 3. 요구사항

### 기능 요구사항

- [x] 엔진에 닿지 못하면 API 는 503 과 `SEARCH_UNAVAILABLE` 로 답한다. 엔진이 **답한** 거절(키 불일치 403,
      잘못된 요청 400 등)은 지금처럼 500 이다 — 그것은 기다려서 풀리지 않는다
- [x] 없는 인덱스는 지금처럼 빈 결과다 (TASK-0119 4.3 을 되돌리지 않는다)
- [x] 구매자 홈은 `search !== "ok"` 인 동안 사람 개입 없이 헬스를 다시 확인하고, `ok` 가 되면 상품 줄을 채운다
- [x] 그동안 상품 줄은 실패 문구와 재시도 버튼을 띄우지 않는다
- [x] 예산(150초)이 끝나도 돌아오지 않으면 그때 실패 문구와 재시도 버튼을 띄운다
- [x] 검색 결과 화면은 `SEARCH_UNAVAILABLE` 에 「검색을 준비하고 있어요」를 띄우고 같은 방식으로 다시 시도한다

### 비기능 요구사항

- 타이머·주기 작업을 늘리지 않는다. 다시 확인하는 것은 **화면이 열려 있는 동안만**, 예산 안에서만이다
- 요청 수 상한은 TASK-0118 의 21회를 넘지 않는다 (같은 정책 상수를 쓴다)
- 준비 중 안내는 `role="status"`, 실패는 `role="alert"` — 지금 규약 그대로

## 4. 설계

### 4.1 「닿지 못함」과 「거절당함」을 가른다

`SearchIndex.request()` 는 지금 두 가지를 던진다 — `fetch` 가 던진 것(연결 실패 `TypeError`, 시한 초과
`TimeoutError`)과 `SearchEngineError(status, code)`. 둘 다 잡는 곳이 없어 500 이 된다.

| 일어난 일 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 연결 실패 · 시한 초과 | 500 | **503 `SEARCH_UNAVAILABLE`** |
| 502 · 503 · 504 이고 Meilisearch 의 `code` 가 **없다** (Render 관문이 답한 것) | 500 | **503 `SEARCH_UNAVAILABLE`** |
| Meilisearch 가 `code` 와 함께 답한 거절 (`invalid_api_key` 등) | 500 | 500 그대로 |
| `index_not_found` | 빈 결과 | 빈 결과 그대로 |

**`code` 가 있느냐가 기준이다.** Meilisearch 는 자기가 답할 때 항상 JSON 에 `code` 를 싣는다. 잠든 서비스 앞의
Render 관문은 HTML 을 돌려준다. TASK-0119 가 `SearchEngineError.code` 를 만든 이유와 같은 구분이다.

새 예외 `SearchEngineUnreachableError` 를 `search-index.ts` 에 두고, `SearchService` 의 공개 경로 셋이 그것만
`ServiceUnavailableException` 으로 바꾼다. 색인 워커(`SearchIndexerService`)는 건드리지 않는다 — 그쪽은 이미
실패를 삼키고 다음 틱에 다시 한다.

### 4.2 API 가 엔진을 따로 깨우지 않는 이유

처음에는 「503 을 돌려주는 순간 깨우는 요청을 보낸다」를 생각했다. **필요 없다.** Render 는 요청이 서비스의
관문에 닿는 순간 기동을 시작하고, 방금 실패한 그 검색 요청이 바로 그 요청이다. 화면이 헬스를 다시 확인할
때마다 API 의 검색 헬스 지표가 엔진의 `/health` 를 또 부르므로(TASK-0101 4.6), 깨우는 신호는 이미 충분하다.
요청을 하나 더 만들면 「정확히 한 번」이라는 `SearchWarmupService` 의 약속만 흐려진다.

### 4.3 화면 — 멈추지 말고 같은 예산으로 계속 본다

`wakeApi` 는 헬스가 `ok: true` 로 답하면 끝난다. 그 답의 `search` 가 `"down"` 이어도 끝난다. 그 뒤는 훅의
`searchRecheckDelaysMs`(5·15·30초, 세 번)가 맡고, 그것이 끝나면 **수동** 재시도 버튼만 남는다.

```
지금    health ok · search down → 5초 · 15초 · 30초 뒤 재확인(3회, 50초) → 멈춤 → [다시 시도]
        그동안 상품 줄은 「불러오지 못했어요」 + 버튼
바꾼 뒤 health ok · search down → 백오프(1·2·4·8초…)로 150초 예산 안에서 재확인 → search ok → 상품 줄이 다시 읽는다
        그동안 상품 줄은 스켈레톤
```

> **2026-09-17 정정.** 초안은 「헬스 확인이 한 번 성공하면 멈추고 아무 일도 일어나지 않는다」고 적었다. 틀렸다 —
> 세 번의 재확인이 이미 있었다. 고칠 것은 「기다리지 않는다」가 아니라 **기다리는 동안 실패를 말하고, 기다림이
> 부팅 시간보다 짧다**는 것이다. 구현 중에 발견했고 설계의 방향은 바뀌지 않는다.

- 「다시 확인할 가치가 있는 답」에 `ok: true && search !== "ok"` 를 더한다. 예산·백오프·요청 상한은
  TASK-0118 의 `WAKE_POLICY` 를 그대로 쓴다. 새 상수는 없다
- **검색까지 기다릴지는 정책이 아니라 화면의 성질이다.** `useApiWake(policy, { waitForSearch })` — 구매자 홈만
  켠다. 그 줄들이 곧 검색이라 검색 없이는 할 수 있는 일이 없기 때문이다. 콘솔은 넘기지 않으므로 첫
  `ok: true` 에서 멈추고 옛 재확인(5·15·30초)을 그대로 쓴다. 그래서 세 앱의 파일이 0줄 차이로 남는다
- `waitForSearch` 인 화면에서는 옛 재확인을 끈다. 켜 두면 예산이 끝난 뒤 요청이 세 번 더 나간다 (R3)
- 루프가 도는 동안 훅의 `result` 는 `null` 그대로이고, 「API 는 답했고 검색을 기다리는 중」은 새 필드
  `searchPending` 으로만 전한다 — 옵션을 켜지 않은 호출자는 상태 변화 순서가 전과 같다
- 상품 줄(`useSection`)은 **오류 코드를 가리지 않는다.** 게이트가 아직 묻는 중이면 어떤 실패든 스켈레톤이고,
  게이트가 끝난 뒤(준비됨 · 포기)의 실패만 실패 안내다. API 가 뜨기 전의 전송 오류도 같은 기다림이고,
  「준비된 뒤의 503 에도 로딩 유지」로 하면 다시 물어 줄 쪽이 없어 스켈레톤이 영원히 남는다
- 예산이 끝났는데도 `search !== "ok"` 면 실패 안내(`storefrontFailed` + 재시도)로 넘어간다. 상품 줄은 **새 요청
  없이** 실패로 바뀐다
- 검색 결과 화면은 게이트 밖이라 자기 요청을 같은 백오프 · 예산으로 다시 보낸다 (`until-search-answers.ts`)

### 4.4 화면별로 보이는 것

| 화면 | 엔진에 닿지 못하는 동안 | 돌아온 뒤 | 예산이 끝나면 |
| --- | --- | --- | --- |
| 홈 상품 줄 | 스켈레톤 + 한 줄 「상품을 준비하고 있어요. 잠시만 기다려 주세요.」 | 상품 | 「상품을 불러오지 못했어요.」 + 다시 시도 |
| 검색 결과 · 카테고리 | 「검색을 준비하고 있어요. 잠시만 기다려 주세요.」 | 결과 | 지금의 실패 안내 + 다시 시도 |
| 자동완성 | 아무것도 띄우지 않는다 (지금과 같다) | 제안 | — |

새 문구는 `search.preparing` 「검색을 준비하고 있어요. 잠시만 기다려 주세요.」 하나다. 검색 결과의 건수 자리에 있던
`role="status"` 에 그린다. 나머지는 있는 문구를 쓴다.

### 4.6 2026-09-18 재오픈 — 검사는 통과했고 운영에서는 맞지 않았다

`618f12f` 가 운영에 올라간 뒤(2026-09-17 08:05 UTC, GitHub 의 Render 배포 기록) 엔진이 내려가 있는 동안의
`/search` 는 **여전히 500 · `INTERNAL_ERROR`** 였다. 두 번 관측했다.

| 시각 (UTC) | 상황 | `/health` 의 `search` | `/search?sort=sales` |
| --- | --- | --- | --- |
| 09-17 08:15 | 배포 10분 뒤 | `down` | 500, 0.4초 안 |
| 09-18 13:26~13:30 | API 부팅 25초~271초 | `down` | 500 (15초 간격 17회 전부) |
| 09-18 13:30 | 부팅 286초 | `degraded` | 200 · 0건 |
| 09-18 13:31 | 부팅 316초 | `ok` | 200 · 783건 |

**무엇이 틀렸나.** 4.1 은 「Meilisearch 의 `code` 가 있느냐가 기준」이라고 적었는데 구현은 그것을 502 · 503 · 504 로
좁혔다. 헬스 지표가 `down` 이므로 응답은 성공이 아니었고, 0.4초 안에 돌아왔으므로 시한 초과도 연결 실패도
아니다 — 즉 **플랫폼이 그 셋이 아닌 상태로 빠르게 거절한다.** 정확한 상태와 본문은 API 로그의
`검색 엔진이 ○○○ 로 거절했습니다` 줄에만 있고, 아직 읽지 못했다. 통합 스펙은 「닫힌 포트」로만 재현했기 때문에
이 형태를 한 번도 만나지 않았다.

**고칠 것 (A).** 기준을 문서대로 되돌린다 — **성공이 아닌데 Meilisearch 의 `code` 가 없으면, 상태가 무엇이든
엔진이 답한 것이 아니다** → `SearchEngineUnreachableError`. `code` 가 있는 거절은 500 그대로다. 스펙에는 운영에서
읽은 실제 상태 · 본문을 그대로 넣는다.

> **아직 확정하지 않는다.** 그 사이에 원인이 하나 더 드러났다 — 소유자가 대시보드에서 올린 유료 플랜이
> 2026-09-17 의 Blueprint sync 로 `free` 로 되돌아가 있었다(TASK-0145). 이 TASK 가 출발한 「엔진이 잠든다」는
> 그 결과였을 가능성이 높고, 2026-09-18 의 「4분 45초」도 잠에서 깬 시간이 아니라 설정 변경에 따른 재배포였을 수
> 있다. TASK-0145 로 두 서비스가 Starter 가 되고 엔진에 디스크가 붙으면 「엔진에 닿지 못함」은 배포 · 재기동
> 구간으로 줄어든다. **그 뒤에 A 의 재현 방법과 스펙을 정한다.**

**4.2 의 전제도 정정한다.** 「실패한 그 요청이 엔진을 깨운다」는 관문이 요청을 붙잡는 경우의 이야기였다.
운영에서 API 가 받은 것은 빠른 거절이고, 그 요청이 기동을 시작시켰는지는 확인하지 못했다. 그리고 엔진이
돌아오는 데 걸린 시간(관측 4분 45초)은 화면의 150초 예산보다 길다 — **기다리게 하는 것만으로는 홈을 구하지
못한다.** 그 부분은 질의 없는 목록의 DB 폴백(TASK-0144, 초안 작성 중)이 맡을 일이다.

### 4.7 2026-09-18 — 재기동 구간에서는 운영에서도 503 이다. 절전 상태는 닫지 못한 채 둔다

4.6 을 적은 같은 날 원인이 드러났다. 소유자가 대시보드에서 올린 유료 플랜이 2026-09-17 의 Blueprint sync 로
`free` 로 되돌아가 있었고, 그래서 검색 엔진이 다시 잠들기 시작했다(TASK-0145 · D-283). 이 TASK 가 출발한 운영
500 은 **코드가 바뀌어서가 아니라 서버 설정이 되돌아가서** 생겼다. 09-18 의 「4분 45초」도 잠에서 깬 시간이 아니라
설정 변경에 따른 재배포였다.

TASK-0145 가 머지되며 검색 엔진이 디스크를 붙이고 재기동하는 약 40초 동안, 운영 `/search` 는 **503 ·
`SEARCH_UNAVAILABLE`** 이었다(TASK-0145 6.1a). 즉 —

| 엔진에 닿지 못하는 이유 | 운영에서 API 가 답한 것 | |
| --- | --- | --- |
| 배포 · 재기동 (지금 남은 유일한 경우) | **503** | F1 성립 |
| 무료 플랜의 절전 — 플랫폼이 0.4초 안에 빠르게 거절 | 500 | **닫지 못했다** |

**절전 상태를 고치지 않는 이유.** 두 서비스가 Starter 가 되어 그 상태는 더 생기지 않고, 그래서 재현할 수 없다.
플랫폼이 그때 무엇을 돌려줬는지(상태 · 본문)는 끝내 읽지 못했다. 4.6 의 「`code` 가 없으면 상태가 무엇이든
닿지 못한 것」으로 넓히는 것은 읽지 못한 모양을 추측으로 덮는 일이라 하지 않는다. **무료로 되돌리게 되면 이
항목부터 다시 연다** — 그때는 API 로그의 `검색 엔진이 ○○○ 로 거절했습니다` 줄을 먼저 읽는다.

4.2 의 「실패한 그 요청이 엔진을 깨운다」도 같은 이유로 확인하지 못한 채 남는다. 유료에서는 깨울 것이 없다.
