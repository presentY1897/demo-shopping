## 1. 목적

**채용 담당자가 5분 안에 이 프로젝트를 이해하게** 만든다. 코드를 다 읽지 않아도 무엇을 어떻게 만들었는지 전달되어야 한다.

## 2. 범위

### 포함
- README 전면 개편 — 데모 URL, 스크린샷, 핵심 기능, 기술 스택, 실행 방법
- **기술적 의사결정 문서** — 왜 그렇게 만들었는지 (설명거리 정리)
- 아키텍처 다이어그램
- 주요 도메인 설계 요약 (주문 2단 분할, 재고 예약, 환불 안분, 정산)
- 성능·접근성 측정 결과
- 데모 계정 안내
- 스크린샷·GIF (밀도 3단계 비교, 3역할 동시 화면)
- 저장소 description·토픽 설정

### 제외
- 블로그 글·발표 자료

## 3. 요구사항

- [ ] README 상단에서 데모 URL 과 핵심 기능이 즉시 보인다
- [ ] 기술적 판단의 근거가 문서로 정리되어 있다
- [ ] 로컬 실행 방법이 정확하다
- [ ] 스크린샷이 실제 화면과 일치한다

## 4. 설계

README 구성 순서 — **위에서부터 읽다가 멈춰도 전달되게** 배치한다.

```
1. 한 줄 소개 + 데모 URL + 데모 계정 안내
2. 스크린샷 (밀도 3단계 비교 — 이 프로젝트의 시각적 차별점)
3. 핵심 기능 (역할별 3~4개씩)
4. 기술 스택 + 아키텍처 다이어그램
5. 기술적 의사결정 (링크)
6. 로컬 실행 방법
7. 문서 구조 안내
```

**기술적 의사결정 문서**가 포트폴리오의 실질이다. `DECISIONS.md` 는 결정의 목록이지 설명이 아니다. 그중 설명거리가 되는 것들을 골라 "문제 → 선택지 → 판단 근거 → 결과"로 다시 쓴다.

- 왜 주문을 2단으로 나눴나
- 왜 속성을 EAV 대신 하이브리드로 했나
- 왜 재고를 예약 방식으로 했나
- 왜 결제 프로바이더를 추상화했나 (가상 카드의 역할)
- 왜 검색을 Meilisearch 로 했나
- 부분 환불의 안분 계산을 어떻게 풀었나
