## 1. 목적

전 화면의 접근성을 점검하고 기준 미달을 수정한다. **밀도 3단계 × 화면**의 조합이 많아 전체 점검이 필요하다.

## 2. 범위

### 포함
- 전 화면 Lighthouse Accessibility 측정
- 키보드 전용 조작 전수 확인
- 스크린리더 확인 (주요 흐름: 검색 → 상세 → 장바구니 → 주문)
- 색 대비 검사 (밀도 3단계 전부)
- **터치 타깃 크기 검사** — 밀도 3단계 전부에서 44×44px 이상
- 폼 레이블·오류 연결 확인
- 이미지 대체 텍스트
- 포커스 표시·순서
- 동적 콘텐츠 알림 (aria-live) — 토스트·장바구니 담기 등
- 차트 대체 표 제공

### 제외
- 완전한 WCAG AAA 준수

## 3. 요구사항

- [x] 전 화면이 Lighthouse a11y 90점 이상이다
- [x] 마우스 없이 구매 흐름을 완주할 수 있다
- [x] 색 대비가 밀도 3단계 모두에서 AA 를 만족한다
- [x] 폼 오류가 스크린리더로 전달된다
- [x] 동적 변화가 알려진다

## 4. 설계

**밀도 3단계를 모두 검사하는 이유**: 맥시멀 단계는 폰트가 작아지고 여백이 줄어 대비와 터치 영역이 나빠질 수 있다. 표준에서만 통과하면 의미가 없다.

**구매 흐름 키보드 완주**를 핵심 기준으로 삼는다. 개별 컴포넌트가 접근 가능해도 흐름이 끊기면 쓸 수 없다.

## 5. 구현 계획

1. 전 화면 자동 측정 (Lighthouse CI)
2. 미달 항목 목록화
3. 키보드 전수 점검
4. 스크린리더 주요 흐름 점검
5. 대비 수정 (밀도별)
6. aria-live·레이블 보완
7. 재측정

### 6.1 기능

**F1 — 여섯 화면 모두 1.00.** 로그인 없이 열리는 화면 전부다. 처음에는 카테고리
화면만 0.96 이었고 이유는 **브레드크럼**이었다 — 「홈」이 14×18px 이라 손가락이 닿는
크기에 미달했다. `link.tsx` 가 터치 하한에서 빠져 있는 것은 **문장 안의 링크**를 위한
면제인데(WCAG 2.5.8), 브레드크럼은 문장 안이 아니라 나란히 놓인 이동 목적지다.
면제를 그대로 가져다 쓴 자리였고, 글자 크기는 그대로 두고 패딩으로 44px 을 만들어
해소했다(R1 이 정한 방식). CI 게이트는 `lighthouserc.json` 이 0.9 로 건다.

**F2 — E2E 가 마우스를 쓰지 않는다.** 구매 흐름 전체를 `Tab` 으로 건넌다
(`purchase.spec.ts`). `focus()` 로 옮겨 붙이지 않는 이유는, 그러면 「눌리는가」만
답하고 마우스 없이 쓰는 사람이 실제로 겪는 「거기까지 갈 수 있는가」는 묻지 않기
때문이다.

그리고 실제로 **주문 버튼에서 막혔다.** 동의 전에는 진짜 `disabled` 라 탭 순서에서
사라졌고, 버튼에도 바로 아래 적힌 이유에도 닿을 수 없었다. 이 저장소가 TASK-0023
4장에서 정하고 담기 버튼이 지키고 있던 규칙 — 보이되 `aria-disabled` 이고 이유가
붙는다 — 이 여기만 빠져 있었다. `aria-describedby` 로 이유를 버튼에 묶었다: 화면을
못 보는 사람에게는 「아래」가 없다.

**F3 — `focus-ring.spec.ts`.** `touch-target.spec.ts` 와 같은 모양이다. 저쪽이
「손가락이 닿는 상자는 자기 하한을 말한다」를 강제한다면 이쪽은 「키보드가 닿는
상자는 자기 표시를 말한다」를 강제한다. 손으로 적은 목록이 아니라 **상대 경로
import 를 따라가서** 판단하므로 새 컴포넌트가 조용히 빠지지 않는다. `outline-none`
을 쓴 자리는 대신할 표시가 있는지를 따로 본다 — 초점 표시가 사라지는 가장 흔한
방법이 「기본 테두리가 보기 싫어서 끄고 잊는 것」이다.

이 검사가 **상품 카드**를 잡았다. 찜 · 이름 · 담기 세 곳이 링을 이름하지 않고 있었고,
브라우저 기본 테두리는 남아 있어 보이긴 했지만 다른 모든 컨트롤과 다른 모습이었다.

**F4 · F5 — `color-tokens.spec.ts` 가 OKLCH 값에서 계산한다.** 한 단계에서만 재는
것이 맞다: `density.css` 가 건드리는 것은 여백·글자 크기·모서리뿐이고 **색 토큰은
하나도 재정의하지 않는다.** 그리고 검사가 요구하는 4.5:1 은 작은 글자의 기준이라,
맥시멀에서 글자가 작아져도 그 값이 더 엄격해지지는 않는다.

**F5b — `touch-target.spec.ts`.** 밀도 3단계 × 뷰포트 3개의 아홉 칸에서 모든 크기
유틸리티가 44px 을 넘는지 보고, **컴포넌트가 그 유틸리티를 실제로 쓰는지**를 소스에서
확인한다. 토큰만 검사하면 「토큰은 안전한데 아무도 안 쓴다」가 통과한다.

**F6 — `form-field.tsx`.** 필드 오류는 `aria-invalid` 와 `aria-describedby` 로
컨트롤에 묶이고, `aria-describedby` 는 **존재하는 id 만** 나열한다(없는 id 를 가리키면
그 자체가 axe 위반이다). `role="alert"` 은 폼 전체 오류 한 곳에만 있다 — 필드마다
붙이면 열 개가 한꺼번에 읽힌다.

**F7 — `purchase-controls.tsx`.** 담긴 결과를 `aria-live` 로 말한다. E2E 도 그
문장으로 확인한다: 마우스 없이 쓰는 사람이 받는 것이 그 문장이다.

**F8 — `sales-chart.tsx` · `revenue-chart.tsx`.** `<svg>` 는 `aria-hidden` 이고
같은 숫자가 **진짜 `<table>`** 로 DOM 안에 있다. 표는 접혀 있을 수 있지만 DOM 에서
사라지지는 않는다 — 접기는 `sr-only` 로 한다.

**추가로 찾은 것 — 본문 랜드마크가 둘이었다.** shop 의 네 화면이 레이아웃의
`<main>` 안에 자기 `<main>` 을 그리고 있었다. 스크린리더의 랜드마크 목록에 「본문」이
둘 뜨고, 「본문 바로가기」가 데려간 곳이 어느 쪽인지 아무도 모른다. **화면 단위 axe
검사로는 안 잡힌다** — 그 검사들은 레이아웃 없이 페이지 하나만 그리므로 그 트리
안에서는 하나뿐이다. Lighthouse 의 기본 접근성 항목에도 이 규칙이 없어 점수 1.00 인
채로 남아 있었다. `one-main.spec.ts` 가 소스를 읽어 지킨다.

### 남은 한계

**스크린리더로 직접 들어 보지는 않았다.** R2 가 예상한 대로 시간이 들고, 이 저장소의
검사는 전부 접근성 트리와 소스에 대고 하는 것이다 — 트리가 맞다고 해서 읽히는 말이
자연스럽다는 뜻은 아니다. 실제 낭독은 소유자 확인 항목으로 남긴다.

**콘솔 세 앱은 Lighthouse 로 재지 않았다.** 로그인 뒤에 있어 그냥 붙이면 로그인
화면을 재게 된다. 대신 각 화면의 axe 검사가 있고(콘솔 화면마다 `*-a11y.spec.tsx`),
셸은 shop 과 같은 `packages/ui` 위에 있다.

**대비는 계산한 값이지 화면에서 잰 값이 아니다.** jsdom 은 아무것도 칠하지 않으므로
axe 가 대비를 판단하지 못하고, 그래서 토큰 파일의 OKLCH 값에서 직접 계산한다.
반투명이 겹치는 자리(예: `bg-surface/85`)는 그 계산에 들어오지 않는다.
