## 1. 목적

핵심 흐름을 E2E 로 고정하고, **방문자가 5분 안에 이 서비스를 이해하는 데모 시나리오**를 만든다.

## 2. 범위

### 포함
- **Playwright** 도입 (D-057)
- 핵심 시나리오 자동화
  1. 데모 발급 → 검색 → 상세 → 장바구니 → 주문 → 가상카드 결제 → 주문 확인
  2. 판매자 데모 → 상품 등록 → 주문 확인 → 발송 처리
  3. 부분 취소 → 환불 확인 (카드 잔액·재고 복원)
  4. 밀도 3단계 전환
- CI 에 E2E 연결 — **모든 PR 에서 실행** (D-057)
- **가이드 데모 시나리오** — 방문자용 안내 (3역할 동시 체험 동선)
- 데모 안내 페이지 (`/guide` 또는 첫 방문 안내 확장)

### 제외

## 4. 설계

**가이드 시나리오**가 이 TASK 의 진짜 산출물이다. 기능이 아무리 많아도 방문자가 어디서 뭘 봐야 할지 모르면 전달되지 않는다.

```
① 구매자 데모 발급 → 상품 검색 → 밀도 3단계 전환해보기 → 주문
② (새 탭) 판매자 데모 발급 → 방금 들어온 주문 확인 → 발송 처리
③ (구매자 탭) 배송 상태 변화 확인 → 부분 취소 → 카드 잔액 복구 확인
④ (새 탭) 관리자 데모 → 정산·통계 확인
```

세 앱의 세션이 독립이라 **탭 3개로 동시에 열 수 있다**(D-028). 이 구조가 데모 동선의 핵심이다.

E2E 도구는 **Playwright** 다. Cypress 대비 병렬 실행·다중 브라우저·트레이스 뷰어가 낫고 사실상 표준이다.

**시나리오는 4개로 유지한다.** 늘릴수록 깨지기 쉽고 유지비가 커진다. 커버 못 하는 영역은 단위·통합 테스트가 맡는다.

## 6. 완료 기준

### 6.1 기능

| # | 기준 | 측정 방법 | 목표 | 충족 |
| --- | --- | --- | --- | --- |
| F1 | 구매 흐름 | 시나리오 1 실행 | 통과 | [x] |
| F2 | 판매자 흐름 | 시나리오 2 실행 | 통과 | [x] |
| F3 | 취소·환불 | 시나리오 3 실행 | 카드 잔액·재고 복원 검증 | [x] 잔액만 |
| F4 | 밀도 전환 | 시나리오 4 실행 | 3단계 모두 렌더 검증 | [x] |
| F5 | CI 연결 | PR 생성 | 모든 PR 에서 E2E 실행, 실패 시 차단 | [x] |
| F6 | 안내 정확성 | 안내대로 수동 수행 | 어긋나는 단계 0건 | [x] |
| F7 | 소요 시간 | 안내 완주 | 5분 이내 | [x] |
| F8 | E2E 실행 시간 | CI 측정 | 10분 이내 | [x] 14초 |

**F1 — 그리고 마우스를 쓰지 않는다** (TASK-0098 F2 를 겸한다). `focus()` 로 옮겨
붙이지 않고 `Tab` 으로 도달한다 — 전자는 「눌리는가」만 답하고, 마우스 없이 쓰는
사람이 실제로 겪는 것은 「거기까지 갈 수 있는가」다.

**F2 — 방금 올린 상품을 산다.** 시드 상품을 사면 그 주문을 볼 판매자가 없다(데모
판매자는 자기 스토어만 본다). 검색을 거치지 않고 상세 주소로 곧장 가는 이유는 검색
색인이 비동기라서다 — 「방금 올린 상품이 언제 검색에 나타나는가」는 이 시나리오가
답할 질문이 아니다.

**F3 — 잔액은 쟀고, 재고는 못 쟀다.** 결제 직후 카드에서 정확히 결제금액만큼
빠지는 것을 확인하고(`before - paid`), 취소 뒤 돌아온 금액이 **0보다 크고 결제금액보다
작다**는 것을 확인한다. 전액이 돌아오면 남은 상품이 공짜가 된 것이고, 그것은
「취소되었습니다」라는 문장만 보고 있으면 알 수 없다.

재고 복원은 이 흐름에서 재지 않았다. 화면에 「남은 수량」이 상시로 적히지 않아
읽을 자리가 없고, 재고 원장은 `stock-ledger-performance.spec.ts` 와 정합성 배치가
이미 지킨다.

두 가지를 배웠다. **부분 취소는 줄 단위**다 — 신청 화면에 수량 칸이 없어서 「하나를
두 개 사고 하나만 취소」는 이 화면에서 할 수 없는 일이고, 그래서 두 상품을 사고
하나만 고른다. 그리고 **발송 전 취소는 판매자를 기다리지 않는다** — 상세 화면에
처리할 버튼이 없고 「환불된 금액」이 이미 적혀 있다. 물건이 아직 떠나지 않아 판단할
것이 없기 때문이고, 반품은 다르다.

**F4 — 세는 것은 「한 줄에 몇 개가 놓이는가」다.** 「토글이 눌린다」만 재면 눌리기만
하고 아무것도 안 바뀌어도 통과하고, 「카드가 몇 개 보이는가」를 재면 검색 화면에서는
답이 늘 24개다(한 쪽의 크기는 밀도가 아니라 페이지 크기가 정한다). 넓은 화면에서
열 수가 3 · 4 · 6 으로 갈리는 것을 보고, 좁은 화면에서는 팝오버로 접힌 쪽에서도
고를 수 있는지를 따로 본다 — 거기서 못 고르면 이 기능은 전화기에서 없는 기능이다.

**F5 — `paths` 로 좁히지 않는다.** 이 검사가 지키는 것은 한 파일의 동작이 아니라
화면과 화면 **사이**이고, 그 사이는 어느 파일을 고쳐도 끊어질 수 있다.

**F6 · F7 — `guide.spec.tsx` 가 안내를 검사한다.** 적힌 시간의 합이 5분 안인지,
가리키는 경로가 실제로 있는 화면인지를 본다. 그리고 그 검사가 곧바로 일했다 —
처음 적은 합이 6분이었다.

**F8 — 14초.** 예산 10분에 대해 크게 남는다. 스택을 세우고 빌드하는 시간까지 포함해
워크플로 전체에 20분을 건다.

### 이 흐름이 찾은 결함 셋

E2E 를 만들면서 실제 결함 셋이 나왔고, 셋 다 **단위 검사로는 보이지 않는 자리**에
있었다.

| 무엇 | 어디 | 왜 안 보였나 |
| --- | --- | --- |
| 장바구니를 주소로 열면 빈 것처럼 보인다 | `use-cart.ts` | 부팅 세션 갱신과 장바구니 요청이 경합한다. 앱 안에서 눌러 들어가면 세션이 이미 메모리에 있어 통과한다 |
| 주문 버튼이 탭 순서에서 사라진다 | `checkout-screen.tsx` | 진짜 `disabled` 라 버튼에도 그 아래 이유에도 닿을 수 없다. 마우스로는 아무 문제가 없다 |
| 본문 랜드마크가 둘이다 | shop 의 네 화면 | 화면 단위 axe 검사는 레이아웃 없이 페이지만 그린다 |

셋 다 **화면 하나만 보고 있으면 정상**이다. 그것이 이 흐름이 있어야 하는 이유다.

### 만드는 속도에 관하여

이 TASK 는 예상보다 오래 걸렸고, 이유는 **실패 한 번의 값이 비쌌기** 때문이다.
단추 이름 하나가 틀리면 로그인부터 주문서까지 여섯 걸음을 다시 걸었다.

두 가지를 고쳐서 반복 하나가 3분에서 5초가 됐다.

- **준비물은 화면이 아니라 서버에게 묻는다.** 환불을 검사하려고 상품 등록 폼을
  화면으로 채우고 있었는데, 그러면 이 시나리오는 환불이 아니라 등록 폼을 검사하게
  된다 — 폼이 바뀌는 날 환불 검사가 대신 빨개진다. 등록 폼은 시나리오 2 가 화면으로
  검사하고, 시나리오 3 은 데모 판매자가 이미 가진 카탈로그에서 고른다.
- **한 번에 하나씩 돈다.** 데모 발급이 한 주소에서 1분에 다섯 개로 묶여 있고 시나리오
  넷이 합쳐 딱 다섯 개를 받는다. 동시에 돌리면 뒤쪽이 거절당해 **코드가 아니라 순서
  때문에** 빨개진다. 한도를 검사용으로 끄지 않는 이유는, 그러면 이 흐름이 실제로
  열리는 문과 다른 문을 지나게 되기 때문이다.
