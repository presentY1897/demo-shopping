## 1. 목적

4~5초 쓰기 응답의 원인을 서버 구간별로 확인해 근거 있는 최적화 범위를 정한다.

## 2. 범위

### 포함

- 장바구니 추가·주문서/주문 생성·결제 생성/승인/확정의 구간별 측정
- API/DB/provider 왕복·연결 획득·응답 조립 구분
- 병목별 후속 최적화안과 성능 목표 제안

### 제외

- 근거 없이 타임아웃만 늘리거나 보안/금액 검증을 제거하지 않는다. 인프라 이전·유료 플랜 변경·확정되지 않은 최적화 구현은 별도 TASK로 다룬다.

## 3. 요구사항

[검토 보고서](../../reviews/2026-09-10-storefront-checkout-review.md)의 해당 발견을 해결하며, 실측 사실과 코드상 위험을 구분한다. 아래 완료 기준의 시나리오를 구현 전 회귀 검증으로 구체화한다.

기존 구매자/판매자 권한·데모 격리·금액 스냅샷·재고/원장 정합성을 유지한다. 변경 계약은 `packages/shared`를 기준으로 API·화면·대역에 함께 반영한다.

## 4. 설계

1. 기존 로깅/trace 도구를 먼저 사용하고 부족하면 최소 계측을 추가한다. 요청 ID·구간명·시간만 기록하며 토큰·주소·카드·메모·SQL 파라미터를 기록하지 않는다.
2. 인증/소유권, DB 연결 획득, 쿼리 횟수/누적 시간, 트랜잭션, provider, 응답 조회/직렬화 시간을 구분한다. 중첩 구간은 단순 합산하지 않는다.
3. 동일 기준 커밋/데이터/환경에서 워밍업 후 엔드포인트별 30회 이상 로컬/스테이징 표본을 수집한다. cold start는 별도 표본으로 분리한다. 운영은 소량 데모 확인만 하고 부하 테스트하지 않는다.
4. 동시성 1의 기준과 제한된 동시성의 비교를 기록하고 median/p95/최대 및 오류율을 함께 제시한다. 서버 간 지역이나 DB 풀이 원인이라는 추정을 측정 전에 결론으로 쓰지 않는다.
5. 계측된 병목의 우선순위·예상 개선 범위·검증 환경·후속 TASK 범위를 작성한다. 재현되지 않으면 차이를 구체적으로 기록하고 운영 측정 접근이 필요한 항목을 미해결로 남긴다.

### 측정 결과

[실측 보고서](../../reviews/2026-09-10-checkout-latency-measurements.md)에 로컬 warm30/32표본과 운영 JWT trace를 기록했다. 반복 DB 왕복·연결 획득 지연을 확인했으며 후처리는 TASK-0132로 배포했다. 실제 cold start는 미확보이므로 F3와 전체 상태는 진행 중이다. 주문서·주문 생성 후속 TASK-0133과 결제 조기 중단 TASK-0134는 배포·운영 검증 완료.

### 배포 후 관측

PR #136 운영 확인에서 주문서4.6초·주문 생성4.4초와 장바구니 담기/승인/확정 응답 중단을 관찰했다. 승인·확정은 자동 복구되어 구매 완료·새로고침 복구·장바구니 정리가 성공했다. 운영 지연 현상은 확인했으나 당시에는 서버 trace가 없었고, 이후 PR #137에서 확보해 F4를 충족했다. 단일 운영 표본으로 p95를 계산하지 않는다. 상세 결과는 실측 보고서의 배포 후 운영 소량 확인 절을 참조한다.

### 운영 구간 계측 구현 (계속 진행 승인)

사용자의 계속 진행 지시에 따라 기존 최소 계측 범위를 구현한다. `X-Checkout-Diagnostics: 1`로 명시한 장바구니/주문서/주문/결제 요청만 AsyncLocalStorage에 시간과 횟수를 모은다. 인증된 BUYER에게만 `Server-Timing`으로 응답하고 일반 요청·익명 요청에는 진단 헤더가 없다. 계측은 권한이나 주문 처리 조건을 바꾸지 않는다.

DB pool 획득·query·transaction, 인증 resolver, 서비스 조회/계정·provider 구간과 서버 총시간을 구분한다. 고정된 구간명만 사용하며 SQL/매개변수/사용자/카드/주소를 저장하지 않는다. 중첩 구간은 합산하지 않는다. pool은 기존 설정을 유지하고 Prisma 종료 시 함께 닫는다. 운영 소량 구매로 trace 확보 후 지배 구간을 근거로 후속 개선 범위를 정한다. 실 DB 격리·동시 요청 혼입 없음·오류/미인증 헤더 미노출을 회귀 검사한다.

### 운영 trace 확보

PR #137 배포 후 실제 JWT 구매1회의 SQL 횟수/누적 시간·pool·서비스·provider를 원자료와 함께 보고서에 기록했다. 반복 DB 왕복과 연결 획득 지연이 관측되며 JWT 및 provider capture는 지배 구간이 아니다. 대상 조회 왕복 축소의 범위·목표·검증법을 F4 근거로 기록했다. 실제 cold start는 미확보라 F3와 전체 상태는 진행 중을 유지한다.

### 복수 상품 오류의 지연 주입 조사 계획

운영500의 원인을 단정하지 않기 위해 격리된 실 PostgreSQL에서 판매자2명·상품2개 주문을 만든다. 결제 확정 구간의 DB 응답에만 약210ms 지연을 주입하고 기본 transaction 제한과 확장 제한을 비교한다. 기존 원장·예약·장바구니·판매자 주문의 결과를 확인하며 지연은 테스트 프로세스에만 적용한다. 표본은 재현 실험이며 운영 성능 통계로 사용하지 않는다. 오류는 Prisma 고정 코드만 기록하고 SQL·매개변수·비밀값을 출력하지 않는다.

### 최신 운영 잔여 지연

PR142 배포 후 두 상품 실제 모바일 구매18,976ms, 결제 요청 실패0·추가 복구 조회0·양쪽 PAID·장바구니0. 서버 주문 생성3,963ms, 결제 생성2,419ms, 승인4,584ms, 확정5,622ms다. [원자료](../../reviews/artifacts/checkout-review/payment-deadline-production-browser.json). 각 SQL·pool 누적 시간은 중첩될 수 있으므로 합산하지 않는다. 반복 후처리 transaction 오류와 브라우저 조기 중단은 해결됐지만 이 단회 warm 결과를 빠른 응답이나 cold p95 달성으로 보지 않는다. 실제 cold start 표본과 결제 단계의 남은 왕복 분석이 후속이다.

### 2026-09-11 잔여 분석 재개 계획

사용자 계속 진행 승인으로 기존 분석 worktree에서 이어간다. 운영 첫 health 요청과 직후 warm 요청을 소량 측정하며, 응답의 uptime·기동 표시 등 실제 재기동 근거가 없으면 cold로 분류하지 않는다. 별도로 로컬 production build 프로세스를 종료·재시작하여 TCP listen까지의 기동과 첫 HTTP/JWT 요청을 측정한다. DB/검색 컨테이너와 OS 캐시는 유지한 process-cold임을 명시하고 호스팅 scale-to-zero와 구분한다.

동일 최신 코드에서 warm30/32표본을 다시 수집한다. 결제 own/read/provider/context/get의 반복 조회 횟수를 확인하여 권한·신선도·상태 잠금이 필요한 조회와 재사용 가능한 불변 식별자를 구분한다. 구현 개선은 근거와 검증 기준을 별도 TASK에 먼저 기록한다. 운영 중단·부하 테스트·요금 변경은 하지 않는다.

### 재개 측정 결과

[최신 warm30/32·production process-cold30·운영 uptime 확인](../../reviews/2026-09-11-payment-read-latency.md)을 확보했다. 로컬 프로세스 기동 중앙값643ms·첫 JWT 장바구니75ms, 오류0. 운영은 uptime47,040초로 cold가 아니었다. 호스팅 scale-to-zero는 미확보라 F3는 부분 충족으로 유지한다. 반복 조회 후속 TASK0135는 설계·실 DB 검증 진행 중이다.

### 운영 DB 지역 확인

사용자가 Neon 운영 리전을 AWS US East2 Ohio로 확인했다. API는 render.yaml상Singapore이다. 장거리 DB 왕복이 유력한 원인이며, 실제 연결 대상 확인과 같은 지역 이전 후 재측정은 TASK0136 초안으로 분리한다. F3의 호스팅 cold 표본 미확보와는 별개의 근거이다.


### TASK0136 리전 이전 후 측정

사용자 승인으로 별도 TASK0136에서 Neon을Singapore로 이전했고 Render 실제Singapore도 확인했다. 운영 구매3회는1,041.55/972.15/964.94ms로 이전17,319.97ms 단회 표본보다 감소했다. 결제 응답 단일 조회는약200ms에서1.69~5.04ms가 됐다. 실제 결제/장바구니/이미지/취소·환불/권한 및 원장 대사를 통과했다. [이전 검증](../../reviews/2026-09-11-neon-region-migration.md). 표본은warm이며 hosting scale-to-zero의 F3는 여전히 부분 충족이다. 추가 작업은 이 cold 측정 범위로 남긴다.
