## 1. 목적

데모 계정을 발급한 직후 구매자·판매자·관리자가 주문과 후속 처리 기능을 실제로 체험할 수 있는 일관된 초기 데이터를 제공한다. 목록용 가짜 행만 추가하지 않고 잔액·재고·결제·정산의 근거가 함께 존재하게 한다.

## 2. 범위

TASK0024에서 후속 구현으로 남긴 거래 예제를 보완한다. 현재 BUYER는 배송지/설정/가상 카드, SELLER는 스토어/상품, ADMIN은 입점 신청2건만 생성한다. 이번 대상은 아래 거래 데이터이며, 쿠폰·찜·최근 본 상품·리뷰 예제 확장은 이번 범위에 포함하지 않는다. 이 항목들은 완료된 것으로 취급하지 않고 잔여 목록에 남긴다.

| 역할 | 유지되는 데이터 | 추가할 데이터 | 체험할 동작 |
| --- | --- | --- | --- |
| 구매자 | 배송지·표시 설정·가상 카드 | 주문3건: 결제 완료, 배송 중, 배송 완료 각1건 | 주문 상세·취소·배송 조회·구매확정/반품 |
| 판매자 | ACTIVE 스토어·초기 상품12개 | 주문5건: 결제 완료1/배송 준비1/배송 중1/구매확정2, 정산2회차 | 주문 확인·발송·정산 상세 |
| 관리자 | 승인 대기 입점 신청2건 | 개입 가능한 데모 클레임1건, 승인 대기 정산서1건 | 클레임 개입·정산 승인 |

각 수량은 해당 발급에서 생성할 예제 수다. 서로 다른 사람이 발급한 데모 계정을 자동 연결하지 않는다. 다른 역할 화면으로 이어지는 실제 거래 검증은 TASK0141에서 새 구매로 연결한다.

## 3. 요구사항

- 예제 주문마다 Order/SellerOrder/OrderItem, 금액 스냅샷, 결제·가상 카드 내역, 재고/예약 및 필요한 배송·클레임·정산 근거가 일치한다.
- 주문 상태 문자열만 직접 변경해 완료 상태를 흉내 내지 않는다. 각 상태에 필요한 도메인 불변식을 충족하는 공용 시드 빌더를 작성하고 도메인 검사로 검증한다.
- 상대방이 필요한 예제는 같은 만료 시각의 보조 데모 계정과 소유 상품을 사용한다. 기존 실사용자나 공용 원본 상품의 재고·잔액·주문을 변경하지 않는다.
- 하나의 발급 중 일부만 생성된 계정을 남기지 않는다. 실패 시 보조 계정과 원장까지 원자적으로 롤백한다.
- 외부 결제·배송 호출은 하지 않는다. 가상 카드 및 기존 가상 배송 계약을 사용하고 동일하게 노출되는 유효한 업무 상태를 만든다.
- 생성 수량을 상수/정책으로 제한하고 N+1 조회 및 파일 변환을 발급 트랜잭션에 넣지 않는다.

## 4. 설계

기존 `DemoSeedService.seeders`에 역할별 시더를 연결한다. 주입된 Clock과 동일한 transaction client를 받는 빌더를 사용한다. 도메인 로직 재사용 시 중첩 트랜잭션이나 외부 I/O가 발생하지 않는지 먼저 확인한다. 정산 예제는 귀속 기간·구매확정·수수료·환불 포함 기준을 기존 정산 계약과 일치시킨다. 예제 결제 후 가상 카드의 표시 잔액은 실제 내역에서 계산된 값이어야 한다.

보조 데모 데이터도 만료/정리 대상에 포함한다. 새 테이블이 필요한지 먼저 검토하되 이 초안은 스키마 추가를 전제하지 않는다. 구현상 계약 변경이 필요하면 문서부터 갱신한다. 기존 로그인 계정에 예제를 뒤늦게 주입하지 않고 신규 발급부터 적용한다.

## 5. 구현 계획

1. 기존 도메인 시드·테스트 fixture와 정리 규칙을 조사하고 거래별 생성 관계를 확정한다.
2. 공용 거래 빌더와 원자성·정합성 검사를 작성한다.
3. 구매자→판매자→관리자 시더를 연결하고 실제 화면의 처리 버튼이 유효한지 확인한다.
4. 발급 성능·만료 정리·실계정 격리 회귀를 검증한다.
5. 배포 후 각 역할 신규 발급을 확인하고 초기 데이터 표/가이드를 갱신한다.

## 7. 리스크 / 열린 질문

정산과 클레임은 필요한 연관 데이터가 많아 발급 비용을 증가시킨다. 전체 예제 수를 제한하고 묶음 조회/쓰기를 사용한다. 성능 게이트를 낮춰 완료 처리하지 않는다. 기존 TASK0024의 모든 초기 예제가 이번 작업으로 완성되는 것은 아니며, 쿠폰·커뮤니티 예제는 잔여로 명시한다.

## 8. 변경 이력

2026-09-12: 사용자 요청으로 TASK0139와 분리한 거래 초기 데이터 보완 초안 작성. 구현 및 운영 데이터 변경은 미실행.

사용자 승인: 2026-09-12 세 TASK 구현 진행 승인. TASK0139부터 순차 구현·검증·배포한다.

구현 계약 구체화: 판매자 주문5건 중 구매확정2건을 종료된 서로 다른 주간 정산의 근거로 사용한다. 상품을 복제할 공용 카탈로그가 없는 개발/테스트 환경에서는 기존처럼 발급을 성공시키고 거래 예제를0건으로 둔다. 상품이 있으면 수량 표를 충족한다. 데이터 빌더는 StockService의 tx 쓰기 경로를 사용하며, 카드 승인에도 호출자 트랜잭션을 받을 수 있도록 기존 charge 로직을 재사용한다. 예제의 과거 거래 시각은 주입 Clock으로부터 계산하고 구매확정 적립 등 해당 상태의 원장 효과도 같은 트랜잭션에 포함한다.

예제 금액 정책: 신규 구매 체험에 사용할 카드 한도를 남기기 위해 예제 전체 승인액을 정책 한도의 절반 이내로 제한한다. 예제 주문의 과거 단가는 현재 옵션 가격과 `한도 / (예제 수 × 2)` 중 작은 정수이며, 배송비0원인 체험 거래 스냅샷으로 기록한다. 현재 판매 가격·배송 정책은 바꾸지 않는다. 저한도 정책(최소1,000원)에서도 예제 수량과 실제 카드 대사가 유지된다.

성능 검증 분리: 기존 카탈로그 복제 SELECT 상한8개는 복제 함수만 직접 실행해 유지한다. 발급 전체는 거래의 잠금·원장 조회가 추가되므로 별도로 원본2개/36개에서 SELECT 수가 증가하지 않는지 확인한다. 50회 p95<300ms 문턱은 그대로 유지한다.

실제 처리 검사에서 발견한 권한 누락: DEMO_ADMIN은 ADMIN_OPERATOR 파생이라 정산 승인 권한이 없어 F2의 승인 체험이403으로 막혔다. 승인된 정산 체험을 구현하기 위해 `settlement.approve:demo`만 추가한다(D-279). 단건 승인·보류·일괄 승인에 판매자 소유권 검사를 적용하며 실계정 정산과 지급 처리는 거부한다. 권한 표·API 회귀·화면 버튼도 같은 계약으로 확인한다.

재고 체험 여유: 예제 주문이 신규 판매자 상품을 품절시키지 않도록 복제 옵션에 예제 수량을 먼저 입고하고 예제 결제만큼 차감한다. 원본 재고는 불변이며 복제 시 재고가0이면 신규 구매 체험용1개도 입고한다. 모든 입출고는 StockService 원장으로 설명한다.


### 로컬 검증 중간 결과 (2026-09-12)

실제 DB/API에서 역할별 주문·정산·클레임 수량, 구매자 취소/카드 환불/구매확정 적립, 판매자 주문 확인/발송, 데모 관리자 반품 승인/정산 승인 및 실계정 정산의 승인·보류·혼합 일괄 승인 거부를 확인했다. 두 번째 예제 카드 승인에 실패를 주입하면 보조 계정·주문·카드·재고 원장이 전부 롤백된다. Clock25시간 진행 후 보조 계정 포함 정리에서 실패0건이다.

다른 검사와 자원 경합이 있던 첫 성능 측정은 판매자 p95358ms로 실패해 완료로 취급하지 않았다. 분리 재측정(동일 DB·동일50표본·문턱300ms 유지)에서 BUYER cold337ms/warm p95108ms, SELLER cold210ms/p95190ms, ADMIN cold102ms/p9591ms로 통과했다. 카탈로그 복제 SELECT 상한8개와 전체 발급의 원본 수 증가에 따른 조회 수 불변도 통과했다. 전체 게이트 및 운영 결과는 이어서 기록한다.
