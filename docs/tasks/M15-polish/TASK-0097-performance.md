## 1. 목적

전 화면·API 의 성능을 측정하고 기준 미달 지점을 개선한다. 각 TASK 에서 개별 확인했지만 **전체를 한 번에 재점검**한다.

### LCP 측정 — 이 TASK 가 소유하는 조사 방법

**화면 TASK 는 성능을 재지 않는다**(QUALITY-GATES 2장). 여기 쌓인 실측은 통과·실패를 가르는
기준선이 아니라 **고칠 곳을 찾기 위한 자료**다.

```bash
CHROME_PATH=~/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome \
  npx --yes lighthouse@12 <url> --only-categories=performance \
  --chrome-flags="--headless=new --no-sandbox --disable-dev-shm-usage --user-data-dir=<임시경로>"
```

> `--user-data-dir` 을 주지 않으면 **실행 디렉터리에 `C:\Users\...` 형태의 프로필 디렉터리**가
> 생긴다. 이 저장소에서 실수로 커밋해 1,264개 파일이 들어간 적이 있다.

**한 라우트를 3~5회 재고 중앙값을 쓴다.** 1회 값은 흔들린다 — `/categories` 는 같은 조건에서
2,410 / 2,858 / 2,859ms 가 나왔다.

#### 누적 실측

| 앱 · 라우트 | LCP 중앙값 | 성격 |
| --- | --- | --- |
| `apps/admin` `/orders` | **1,806ms** | 스텁 라우트. 상호작용 번들을 싣지 않는다 |
| `apps/admin` `/categories` | **2,858ms** | 실제 화면. 스텁 대비 **+1,052ms** |
| `apps/admin` `/attributes` | (아래 참조) | 실제 화면 |
| `apps/shop` `/cart` | 2,036ms | 셸 + 최소 본문 |
| `apps/shop` `/` | 2,707ms | 셸 + 홈 본문 |
| `apps/admin` `/` | 2,557ms | 홈. 콜드 스타트 장치 포함 |

**가장 큰 단일 항목은 콘솔 상호작용 번들이다.** admin 의 스텁(1,806ms)과 실제 화면(2,858ms)
사이 +1,052ms 가 그것이고, 두 실제 화면(`/categories`·`/attributes`)이 그 청크를 공유한다.
Lighthouse 진단은 두 앱 모두 `unused-javascript` 를 지목한다 — shop 홈 131KiB, admin 230KiB.
**LCP 요소는 어느 화면에서도 서버가 이미 보낸 텍스트**이고 Render Delay 가 83~84% 다.
즉 그리는 비용이 아니라 **스크립트를 파싱하느라 그릴 차례가 오지 않는 것**이다.

### admin 홈 — 페이지 실측 (셸 기준선 아님)

[TASK-0029](../M05-catalog/TASK-0029-category-admin.md) 6.4 가 Lighthouse 12 로 실측하면서 발견했다.
**개별 화면의 문제가 아니라 앱 셸의 고정 비용**이므로 이 TASK 가 받는다.

| 측정 | 값 |
| --- | --- |
| LCP (모바일 프리셋: 4x CPU · Slow 4G) | **2,557ms** — 게이트 P1 기준 2,500ms 초과 |
| 같은 조건, admin `/` 홈 | **2,557ms** — 화면 내용과 무관하게 동일 |
| LCP 분해 | TTFB 453ms(18%) · **Render Delay 2,106ms(82%)** |
| 렌더 블로킹 CSS | 8KB 1개 (153ms) — 병목 아님 |
| 스크립트 전송량 | **276KB** — 4x CPU 스로틀에서의 파싱이 실제 병목 |
| Desktop 프리셋 LCP | 0.6s (perf 100, a11y 100) |

재현: `apps/admin` 프로덕션 빌드를 `next start -p <admin포트>` 로 띄우고
`CHROME_PATH=<playwright chromium> npx lighthouse@12 <url> --only-categories=performance,accessibility`.
Lighthouse 는 전역 설치 없이 `npx` 로 실행되고, 브라우저는 Playwright 캐시의 Chromium 을 쓴다.

**admin 의 화면 TASK 들은 이 값이 내려가기 전까지 P1 을 충족할 수 없다.** 그래서 그쪽에서는
P1 을 `[-]`(이 TASK 소유)로 두고 있다. 여기서 셸 번들을 줄이면 함께 해소된다.

### 같은 지점 — shop 셸 번들

[TASK-0018](../M03-design-system/TASK-0018-shop-layout.md) 6.4 가 같은 방법으로, 이번에는
**대조군까지 두고** 쟀다. 셸을 걷어낸 빌드와 얹은 빌드를 같은 라우트에서 각각 5회.

| 측정 | 값 |
| --- | --- |
| 셸 없는 대조군 (`/cart`) | 197,562B / 8개 — LCP **1,657ms** |
| 셸 적용 (`/cart`) | 301,897B / 10개 — LCP **2,036ms** (게이트 이내) |
| 셸이 더한 값 | **+104,335B · +379ms** |
| 셸 + 홈 본문 (`/`) | 같은 번들 — LCP **2,707ms**, 게이트 초과 |
| 홈 LCP 분해 | TTFB 452ms(16%) · **Render Delay 2,332ms(84%)** |
| Lighthouse 진단 | `unused-javascript` **131KiB · LCP 절감 추정 700ms** |

admin 과 형태가 같다 — 받아오는 비용이 아니라 **메인 스레드가 스크립트를 파싱하느라 그릴
차례가 오지 않는 것**이고, LCP 요소는 서버가 이미 보낸 텍스트다. 두 앱이 같은
`packages/ui` 위에 있으므로 **코드 스플리팅을 한 번 하면 양쪽이 같이 내려간다.**

shop 도 P1 을 `[-]`(이 TASK 소유)로 두고 있다.

### seller — TASK-0019 이 잰 값

[TASK-0019](../M03-design-system/TASK-0019-console-layout.md) 6.4 가 콘솔 셸을 얹은 뒤
같은 방법(Lighthouse 12 모바일 프리셋, 5회 중앙값)으로 쟀다. **`/orders` 는 스텁 라우트**라
상호작용 번들을 싣지 않는다 — 실제 화면과 비교할 값이 아니다.

| 측정 | 값 |
| --- | --- |
| `apps/seller` 셸 기준선 (`/orders` — 셸 + 페이지 헤더만) | **1,804ms** |
| 스크립트 전송량 | 199,475B / 7개 |
| 회차별 LCP (5회) | 1,803.7 / 1,803.8 / 1,804.1 / 1,804.6 / 1,804.9ms |
| CLS · 접근성 | 0 · 100 |

같은 조건에서 admin 은 `/orders` 가 **1,804ms** 였다. 위 admin 기준선(2,557ms)보다 낮은데,
콘솔 셸이 얹힌 화면이 그 전보다 가볍기 때문이다 — 셸 자체는 LCP 를 올리지 않았고
(대조군 대비 +2,551B · −7ms, TASK-0019 6.4), 2,557ms 를 만들던 것은 그때 admin 홈이
싣던 다른 코드다.

## 2. 범위

- 캐시 전략 (정적 자원, API 응답)
- 데이터 정합성 점검 배치 통합 — 재고·적립금·가상카드·평점·팔로워 수

## 3. 요구사항

- [ ] 주요 화면이 LCP 2.5s 이하다
- [ ] 주요 API 가 p95 300ms 이하다 (검색은 200ms)
- [ ] N+1 쿼리가 없다
- [ ] 목록·검색 조건에 인덱스가 있다
- [ ] 캐시 컬럼과 실제 값이 일치한다

## 4. 설계

**정합성 점검 배치를 하나로 통합**한다. 프로젝트 전반에 캐시 컬럼이 여럿이다.

| 캐시 | 원본 |
| --- | --- |
| `ProductVariant.stock` | StockLedger 합계 |
| `ProductVariant.reserved` | HELD 예약 합계 |
| `PointAccount.balance` | PointTransaction 합계 |
| `VirtualCard.usedAmount` | VirtualCardTransaction 합계 |
| `Product.ratingAvg/Count` | Review 집계 |
| `Product.minPrice` | Variant 최저가 |
| `Seller.followerCount` | SellerFollow 수 |

불일치는 **검출·기록만 하고 자동 보정하지 않는다.** 원인을 모르는 채 값을 고치면 문제가 숨는다.
