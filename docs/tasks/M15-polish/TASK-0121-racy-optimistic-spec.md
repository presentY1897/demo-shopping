## 1. 목적

`apps/admin/test/categories-page.spec.tsx` 의 「실패 시 원위치(F10)」가 **부하가 걸릴 때만**
실패한다. 단독으로 돌리면 통과하고, 전체 게이트처럼 여섯 패키지가 동시에 돌면 빨개진다.

원인은 검사가 **"서버 응답이 아직 도착하지 않았을 것"이라는 타이밍 가정**에 기대는 것이다.
50밀리초를 벌어 두고 그 사이에 낙관적 갱신을 확인하는데, 머신이 바쁘면 그 50밀리초 안에
실패 응답과 롤백까지 끝나 버린다.

**이것은 TASK-0120 이 찾은 것과 같은 부류의 두 번째 사례다.** 그쪽은 시계에, 이쪽은 부하에
기댔다. 공통점은 **통과가 검증이 아니라 운이었다**는 것이고, 둘 다 "고칠 것이 없어 보이는
초록"을 만들어 낸다.

끝나면 이 검사가 경과 시간과 무관해지고, 같은 가정을 쓰는 다른 자리가 목록으로 남는다.

- **`networkFailureAfterOn` 제거** — 지연 자체가 필요한 자리가 있다 (4.5). 없애는 것이 아니라
  **경합하는 자리에서만** 바꾼다
- **다른 종류의 플레이크** — 시각 의존은 TASK-0120, 여기는 부하 의존만 다룬다
- **CI 병렬도 조정** — 러너를 늘리면 증상이 숨을 뿐 가정은 남는다

## 3. 요구사항

### 기능 요구사항
- [ ] F10 검사가 **경과 시간에 의존하지 않는다** — 부하와 무관하게 같은 답

### 비기능 요구사항

## 4. 설계

### 4.1 무엇이 경합하는가

```ts
testServer.server.use(networkFailureAfterOn('post', mockPaths.categoryReorder, 50))

item('여성').focus()
await user.keyboard('{Alt>}{ArrowDown}{/Alt}')

// It moved first — that is the point of an optimistic update, and the
// failure is still in flight while this is asserted.
expect(itemNames()[0]).toContain('남성')     // ← 50ms 안에 도달해야 한다
```

주석이 가정을 정직하게 적어 두었다 — "실패가 아직 날아오는 중". **그 가정에 근거가 없다.**
`await user.keyboard(...)` 는 React 갱신을 flush 하고 돌아오는데, 그 사이에 50밀리초가 지날지는
그때 머신이 무엇을 하고 있느냐에 달렸다.

관측된 실패는 이렇다.

```
AssertionError: expected '여성하위 4women' to contain '남성'
```

낙관적 갱신을 보러 갔더니 **이미 롤백까지 끝나 있었다.** 검사가 틀린 것을 잡은 것이 아니라,
맞는 것을 놓친 것이다.

### 4.2 지연을 늘리는 것은 답이 아니다

50을 500으로 바꾸면 오늘은 통과한다. 그러면 **가정이 사라지는 것이 아니라 커질 뿐이고**,
검사 하나가 0.5초를 그냥 기다린다. 더 바쁜 머신에서는 다시 무너진다.

같은 파일의 다른 검사가 1,500밀리초를 쓰고 있는 것이 그 미끄러짐의 증거다
(`attributes-page.spec.tsx` 의 `IN_FLIGHT_MS`). 값이 커진 이유는 아무도 적어 두지 않았다.

**시간을 늘리는 대신 시간을 없앤다.**

### 4.3 응답 도착 시점을 검사가 정한다

`@shopping/api-mocks` 에 **놓아 줄 때까지 답하지 않는** 대역을 더한다.

```ts
export function gatedFailureOn(method: MockMethod, path: MockPath): {
  readonly handler: RequestHandler
  /** 붙잡아 둔 요청을 실패로 놓아 준다. */
  readonly release: () => void
}
```

요청은 `release()` 가 불릴 때까지 **응답하지 않는다.** 그러면 "아직 안 왔을 것"이 가정이 아니라
**사실**이 된다 — 검사가 놓아 주기 전에는 도착할 방법이 없다.

기존 `neverAnswersOn` 이 "영원히 답하지 않는" 쪽을 이미 담당하므로, 이것은 그 위에 `release` 를
얹은 모양이 된다. 새 개념이 아니라 **기존 개념에 스위치 하나**다.

### 4.4 검사가 이렇게 바뀐다

```ts
const failure = gatedFailureOn('post', mockPaths.categoryReorder)
testServer.server.use(failure.handler)

item('여성').focus()
await user.keyboard('{Alt>}{ArrowDown}{/Alt}')

// 응답이 아직 없다 — 가정이 아니라 대역이 그렇게 만들어져 있다.
expect(itemNames()[0]).toContain('남성')

failure.release()

expect(await screen.findByText(copy.toast.moveFailed)).toBeVisible()
expect(itemNames()).toEqual(before)
```

**검증하는 것은 그대로다.** 낙관적 갱신이 먼저 보이고, 실패가 오면 되돌아간다 — 두 단계를 그대로
확인한다. 사라지는 것은 두 단계 **사이의 경합**뿐이다.

그리고 이 검사는 이제 **더 빠르다.** 50밀리초를 기다리던 자리가 없어진다.

### 4.5 같은 가정을 쓰는 자리

지연 대역을 쓴다고 전부 경합하는 것은 아니다. **기다리는 검사는 안전하고, 앞지르려는 검사가
위험하다.**

| 자리 | 지연 | 무엇을 하나 | 판정 |
| --- | --- | --- | --- |
| `categories-page.spec.tsx` F10 | 50ms | 지연 **안에서** 낙관적 갱신을 단언 | **경합. 고친다** |
| `attributes-page.spec.tsx:453` | 20ms | 실패 토스트를 `findBy`/`waitFor` 로 **기다린다** | 안전. 그대로 |
| `attributes-page.spec.tsx:582` | 1,500ms | 중복 제출 가드 — `waitFor(posts === 1)` 로 기다린다 | 안전하지만 **여유값이 근거 없이 크다.** 4.3 대역으로 바꾸면 1.5초가 사라진다 |

**구현에서 전수로 다시 훑는다.** 위는 `networkFailureAfterOn`·`slowResponse` 사용처를 훑어
잡은 초안이고, 판정 기준은 하나다 — **지연이 끝나기 전에 무언가를 단언하는가.**

### 4.6 데이터 모델 · API · 화면

전부 해당 없음. 프로덕션 코드는 바뀌지 않는다 — 바뀌는 것은 `packages/api-mocks` 의 대역과
검사뿐이다.

**F1 이 F4 보다 앞에 있는 이유.** 부하 검사(F4)는 확률적이다 — 세 번 통과해도 네 번째를
보장하지 않는다. **지연 상수가 없다는 것은 구조적 사실**이고, 그것이 진짜 근거다. F4 는
그 사실을 뒷받침하는 관측이지 그 자체가 기준은 아니다 (TASK-0118 F4 와 같은 자세).

**F2 · F3 을 넣는 이유.** 경합을 없애는 가장 쉬운 방법은 낙관적 단언을 지우는 것이다. 그러면
검사는 안정되고 **검증은 사라진다.** 두 단언이 각각 살아 있어야 한다는 것을 지워 보고 확인한다.
