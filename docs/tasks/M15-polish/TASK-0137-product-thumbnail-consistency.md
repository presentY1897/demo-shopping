## 1. 목적

같은 상품이 화면에 따라 깨지거나 식별 이미지 없이 나오는 문제를 해결한다. [전수 조사](../../reviews/2026-09-11-thumbnail-inventory.md)를 기준으로 상품 이미지의 URL 해석·실패 처리·표시 계약을 통합한다.

## 2. 범위

- 기존 표시: 구매자 상품 카드·갤러리·장바구니·주문서·주문 상세·최근 본 스트립/전체·찜, 판매자 상품 편집/미리보기.
- 새 표시: 구매자 리뷰 작성 대상·내 문의·취소/반품 대상 선택, 판매자 상품/주문/클레임 목록과 주문/클레임 상세 상품 행, 관리자 상품 목록·클레임 상세/강제 처리·하자 반품 대상 선택.
- 리뷰 첨부·로고·증빙 사진·업로드 위젯·OG/JSON-LD·인쇄 문서는 이번 상품 식별 UI 범위에서 제외한다. 조사 결과는 후속 근거로 유지한다.
- DB 파생 이미지 생성은 TASK-0138이다. 이 TASK는 기존 응답으로도 동작해야 한다.

## 3. 요구사항

- 모든 포함 화면이 정상·null·공백·로드 실패에 같은 기본 정책을 적용한다.
- 다른 상품 사진으로 대체하지 않는다. 스냅샷·최근 본 저장값을 최신 상품 조회로 덮어쓰지 않는다.
- 기존 응답만 사용하며 상품별 추가 상세 조회를 만들지 않는다.
- 카드 반응형 크기/우선순위, 갤러리 선택·확대·스와이프, 행 선택·링크·대체 텍스트를 유지한다.

## 4. 설계

packages/ui에 프레임워크 독립적인 이미지 표시 기반을 둔다. 빈 URL/실패 상태/src 변경 복구와 기본 대체 표시를 공유하고, renderImage 슬롯으로 Next Image 최적화를 보존한다. 상품 카드·갤러리·작은 상품 행은 각 레이아웃을 유지하며 기반 처리를 조합한다. 단일 거대 갤러리 컴포넌트로 합치지 않는다.

URL 해석은 DOM 컴포넌트와 분리된 공통 순수 함수로 둔다. 알려진 시드 자산만 동일 바이트 파일로 매핑한다. 세 앱의 빌드에서 같은 원본 자산을 각 public 경로에 배치하고 해시/목록 동일성을 검증한다. shop 상대 경로를 seller/admin에서 파일 없이 사용하지 않는다. TASK-0138의 파생 URL은 준비된 경우 사용하고 기존 URL 계약도 지원한다.

DB/API/역할 권한은 변경하지 않는다. 주문 관련 행은 기존 snapshot.thumbnailUrl, 현재 상품 행은 해당 응답 thumbnailUrl을 사용한다. 컴포넌트의 alt/fit/크기/로딩 우선순위는 호출자가 명시한다.

## 5. 구현 계획

1. 승인 후 공통 이미지 계약·스토리·회귀 검사를 작성한다.
2. 세 앱 시드 자산 제공과 URL 해석을 통합한다.
3. 기존 상품 이미지 소비자를 전환하고 식별 행 썸네일을 추가한다.
4. 세 앱 브라우저·접근성·요청 수 검증 후 문서/PR/배포 결과를 기록한다.
