## 1. 목적

구매자·판매자·관리자가 동일한 상품과 주문을 이어서 처리할 수 있음을 실제 앱/API/DB/검색엔진으로 검증한다. 화면마다 따로 성공하는 검사에서 빠지는 연결 오류를 잡는다.

## 2. 범위 및 기존 검사와 차이

TASK0099의 Playwright/CI/독립 세션 구성을 재사용한다. 현재 `e2e/tests/seller.spec.ts`는 셀러가 올린 상품의 ID로 상세 페이지에 직접 진입하고, `refund.spec.ts`도 API에서 상품ID를 얻는다. 따라서 데모 초기 상품의 검색 누락이 있어도 통과한다. 관리자 context는 현재 핵심 거래 흐름에 없다.

기존4개 시나리오(구매/판매/환불/밀도)를 유지하면서 판매·환불 시나리오를 보강한다. 복잡한 실패/만료 조합은 API 통합 검사로 분리한다. UI 클릭을 API 호출로 대체해 성공시킨 결과를 브라우저 검증으로 기록하지 않는다. 실제 비용이 발생하는 결제나 실계정 데이터 조작은 제외한다.

## 3. 검증 시나리오

| 흐름 | 실행 | 반드시 대조할 결과 |
| --- | --- | --- |
| 발급·발견 | 화면에서3역할 발급, 셀러 초기 상품과 새로 등록한 상품을 구매자 검색/브랜드관에서 선택 | 상품ID·판매자ID 일치, 상세 직행으로 검색 단계 우회 없음 |
| 주문·결제 | 구매자 장바구니→주문→가상 결제, 셀러/관리자에서 같은 주문번호 조회 | SKU·수량·금액·상태 일치, 구매한 장바구니 행 정리, 재고/잔액 변화 |
| 배송 | 셀러 주문 확인→발송, 구매자/관리자 새로고침 | 동일 주문의 배송 상태·운송장 일치 |
| 상품 통제 | 데모 관리자가 해당 데모 상품 숨김→복원 | 구매자 검색 제외→재노출, 숨긴 상품의 신규 구매 거부, 기존 주문 보존 |
| 취소·반품 | 별도 거래로 발송 전 부분 취소 및 배송 후 반품/관리자 개입 검증 | 실제 취소 금액·카드 환불·재고 복원, 역할별 상태 수렴 |
| 실패·권한·만료 | API 통합 검사에서 결제 실패/중복/품절/권한 위반/시간 진행 | 이중 결제0건, 예약 유실0건, 타 계정 쓰기 거부, 만료 상품 검색 제거 |

정확한 원장 대사는 로컬 테스트 전용 읽기 검증을 사용하고 공개 진단 API를 추가하지 않는다. 배송/만료 시간은 통합 검사에서 주입된 Clock으로 제어한다. 브라우저에서는 실제 UI가 처리할 수 있는 상태를 사용하며 DB 상태 직접 수정으로 버튼을 열지 않는다. 관리자 반품 개입은 TASK0140의 적법한 초기 상태 예제 또는 도메인 전이를 거친 테스트 거래로 준비한다.

## 4. 설계 및 소유 범위

`e2e/tests/seller.spec.ts`, `refund.spec.ts`, 공용 flows/fixtures와 필요한 API 통합 검사가 주 대상이다. 상품ID·주문번호를 역할 간 전달하고 텍스트 개수만으로 성공을 판정하지 않는다. 브라우저 context는 역할별로 분리한다. 검색 등 비동기 결과는 기한 있는 상태 재확인으로 기다리고 무조건적인 고정 sleep을 추가하지 않는다.

기존 데모 발급 한도(1분5회)를 유지한다. 시나리오별 발급 수와 재시도 예산을 계산하고 직렬 실행으로 중복 발급을 피한다. 운영 검증은 새 데모 계정만 사용하며 정상 구매/노출/배송/관리자 확인을 우선한다. 강제 장애·시간 조작·반복 부하 검사는 로컬/CI에서 수행한다.

실패 증거는 trace·스크린샷·단계별 ID/상태 대조로 남기고 토큰/쿠키/개인정보를 공개 artifact에 넣지 않는다. 오류가 발견되면 담당 TASK로 연결해 해결하며 검사를 건너뛰거나 재시도 횟수를 늘려 통과시키지 않는다.

## 5. 구현 계획

1. 기존4개 시나리오와 API 통합 검사를 표의 각 단계에 매핑한다.
2. TASK0139의 좁은 회귀 검사를 유지하고 Playwright에 검색 경유 및 관리자 context를 추가한다.
3. 주문/배송/숨김/복원/환불 대조와 실패·만료 API 검사를 연결한다.
4. 실제 스택에서 최초 시도 기준3회 연속 실행하고 CI 시간·발급 한도를 확인한다.
5. 운영 데모3역할로 핵심 흐름을 재확인하고 방문자 가이드를 같은 동선으로 수정한다.

## 7. 리스크 / 열린 질문

검색 수렴·자동 배송·발급 제한이 겹치면 테스트가 느려질 수 있다. 상태 전이 조합은 API 검사로 나누고 핵심 브라우저 연결만 유지한다. 운영에서 검증하지 않은 강제 실패·메모리 등 항목을 운영 검증 완료로 표현하지 않는다. 기존 가이드의 독립 셀러 발급만으로 다른 판매자의 주문이 보인다는 오해를 해소하도록 실제 상품 선택 동선을 명시한다.

구현 착수: `feature/cross-role-demo-e2e` / `feature-cross-role-demo-e2e`를 TASK0140 커밋에서 분리했다. 모든 구매 helper는 공개 상품 정보에서 이름/판매자를 알아낸 뒤 실제 검색 화면의 링크를 클릭한다. 기존4개 시나리오의 발급 수는 구매1+환불3+판매3=7이며, 실제 발급 창을 기다리는 클라이언트 예산으로1분5회를 지킨다. API 제한이나 테스트 재시도 수를 늘리지 않는다. 운영 실행은 명시적인 E2E 앱 URL 환경변수로 새 데모 계정만 대상으로 한다. 실패 trace의 인증 헤더·쿠키·토큰은 업로드 전에 제거한다.

브라우저에서 발견한 공통 표 결함: 관리자 주문 상세 버튼의 화면 낭독용 sr-only 텍스트가 정적 위치의 표 스크롤 영역 밖으로 빠져나와412px 화면의 문서 폭이812px로 늘었다. 모바일 브라우저의 축소/터치 좌표가 어긋나 검색 폼이 상세 클릭을 가로막았다. Table 스크롤 래퍼를 위치 기준(relative)으로 만들어 숨김 텍스트를 내부에 한정한다. 실험 후 문서 폭412px 및 강제 클릭 없는 상세 열기를 확인했다. 공통 UI 검사와 세 역할 E2E에서 문서 가로 넘침0px를 검증한다. 새 컴포넌트나 화면 기능 추가는 없다.

관리자 상품 검색 결함: productQueryOf는 q를 만들지만 console-api의 productSearch가 이를 URL에 넣지 않았다. 검색 제출과 숨김 후 재조회 모두 전체 목록을 읽었다. 기존 q 계약을 그대로 직렬화하고 실제 화면 검색→대상 행1건→숨김/복원으로 회귀를 검사한다.

관리자 숨김 복구 결함: ProductService.maySeeHidden이 any/own만 인정해 demo 범위 관리자가 직접 숨긴 상품도 목록·상세에서404로 사라졌다. 기존 product.write:demo 권한을 행 소유자 isDemo와 결합해 데모 비공개 상품만 조회 가능하게 한다. 목록은 같은 SQL의 EXISTS로 범위를 적용해 N+1 없이 처리하고 상세는 이미 조회한 소유 관계를 재사용한다. 일반 구매자의 비공개 조회 및 데모 관리자의 실계정 비공개 조회는 계속 거부한다.

혼합 취소·반품 결함: 발송 전 부분 취소 후 나머지를 모두 반품해도 returnedLines가 최초 주문 수량과 비교해 배송완료에 남았다. RETURNED 판정의 대상 수량에서 확정된 CANCEL_APPROVED/REFUNDED 취소 수량을 제외한다. 승인 전·거절 취소는 제외하지 않고, 반품은 검수 합격 이후만 센다. 기존 잠금/원장/상태 전이를 재사용하며 실제 부분 취소→배송→관리자 개입 반품 E2E에서 주문 종료와 카드 환불을 함께 확인한다.

최초3회 연속 검증은14/15 통과했으나 마지막 회 관리자 발급에서429로 실패했다. 클라이언트 Date.now 기록과 서버의 발급 창 경계가 어긋났으므로 성공으로 기록하지 않는다. 발급 예산을 API 응답 Date 헤더 기준으로 바꾸고 HEAD health로 서버 현재 시각을 읽는다. Date 헤더의 초 단위 반올림 여유를 포함하며 발급 POST는 여전히 한 번뿐이다. 서버 제한과 CI 재시도 수는 유지한다.


### 로컬 실제 스택 검증 (2026-09-12)

PostgreSQL17.11(별도 shopping_demo_e2e DB), Meilisearch1.24(별도 색인), 세 Next.js 운영 빌드와 API를 사용했다. 서버 Date 기반 발급 예산으로 `--repeat-each=3 --retries=0` 실행 결과 기존4개 파일의5개 검사×3회=15개 모두 최초 시도 통과, 총4.7분이다. 발급 제한은5회/60초 그대로다. 검색→결제→장바구니 정리→관리자 같은 주문 조회→배송/운송장→숨김/복구와 부분 취소→나머지 반품→관리자 개입→회수/검수→카드 환불/RETURNED가 모두 통과했다.

별도 API 검사에서 비공개 권한/구매 거부와 만료 후 검색 제거29개, 혼합 취소·반품/관리자 개입/환불100개가 통과했다. 관리자 상품 검색/목록 검사46개, artifact 인증 제거/이미지 보존 검사도 통과했다. 전체 게이트 및 운영 결과는 최종 단계에서 기록한다. 재현 명령과 API 실패 조합의 매핑은 [검증 문서](../../demo-validation.md)에 있다.

전체 게이트에서 데모 플래그의 업무 서비스 직접 참조를 금지하는 구조 검사2개가 실패했다. 허용 목록을 늘리지 않고, SQL의 소유 그룹 판정을 기존 auth/resource-ownership으로 옮기며 상세 조회는 authorizeResource를 재사용한다. 최초 전체 검사에서 빌드와 겹친 BUYER 발급 p95502ms도 실패했다. 분리 재측정50표본에서 BUYER103ms/SELLER172ms/ADMIN99ms로 기존300ms 문턱을 통과했다.

최종 재빌드 반복에서도60초 경계에서 발급429가 재현되어 예산을 더 보수적으로 변경한다. 서버 시각으로5회 묶음을 기록하고, 다섯 번째 성공 이후 전체 창65초(헤더 초 정밀도/시각 경계 여유 포함)가 지난 다음 묶음을 시작한다. 일부 오래된 기록만 빠졌다는 이유로 다음 발급을 섞지 않는다. 서버의5회/60초 정책과 POST 재시도0회는 그대로이며 전체3회10분 예산 안에서 검증한다. 가이드 회귀는 각 역할의 첫 진입만 로그인으로 제한하고, 이후 같은 판매자 주문 화면으로 돌아오는 경로의 실재를 검사한다.
