# TASK-0141: 세 역할이 연결되는 데모 거래 E2E 검증

| 항목 | 내용 |
| --- | --- |
| 마일스톤 | M15 마무리 |
| 상태 | 초안 |

| 선행 작업 | TASK-0139, TASK-0140, TASK-0099 |

## 1. 목적

구매자·판매자·관리자가 동일한 상품과 주문을 이어서 처리할 수 있음을 실제 앱/API/DB/검색엔진으로 검증한다. 화면마다 따로 성공하는 검사에서 빠지는 연결 오류를 잡는다.

## 2. 범위 및 기존 검사와 차이

TASK0099의 Playwright/CI/독립 세션 구성을 재사용한다. 현재 `e2e/tests/seller.spec.ts`는 셀러가 올린 상품의 ID로 상세 페이지에 직접 진입하고, `refund.spec.ts`도 API에서 상품ID를 얻는다. 따라서 데모 초기 상품의 검색 누락이 있어도 통과한다. 관리자 context는 현재 핵심 거래 흐름에 없다.

기존4개 시나리오(구매/판매/환불/밀도)를 유지하면서 판매·환불 시나리오를 보강한다. 복잡한 실패/만료 조합은 API 통합 검사로 분리한다. UI 클릭을 API 호출로 대체해 성공시킨 결과를 브라우저 검증으로 기록하지 않는다. 실제 비용이 발생하는 결제나 실계정 데이터 조작은 제외한다.

## 3. 검증 시나리오

| 흐름 | 실행 | 반드시 대조할 결과 |
| --- | --- | --- |
| 발급·발견 | 화면에서3역할 발급, 셀러 초기 상품과 새로 등록한 상품을 구매자 검색/브랜드관에서 선택 | 상품ID·판매자ID 일치, 상세 직행으로 검색 단계 우회 없음 |
| 주문·결제 | 구매자 장바구니→주문→가상 결제, 셀러/관리자에서 같은 주문번호 조회 | SKU·수량·금액·상태 일치, 구매한 장바구니 행 정리, 재고/잔액 변화 |
| 배송 | 셀러 주문 확인→발송, 구매자/관리자 새로고침 | 동일 주문의 배송 상태·운송장 일치 |
| 상품 통제 | 데모 관리자가 해당 데모 상품 숨김→복원 | 구매자 검색 제외→재노출, 숨긴 상품의 신규 구매 거부, 기존 주문 보존 |
| 취소·반품 | 별도 거래로 발송 전 부분 취소 및 배송 후 반품/관리자 개입 검증 | 실제 취소 금액·카드 환불·재고 복원, 역할별 상태 수렴 |
| 실패·권한·만료 | API 통합 검사에서 결제 실패/중복/품절/권한 위반/시간 진행 | 이중 결제0건, 예약 유실0건, 타 계정 쓰기 거부, 만료 상품 검색 제거 |

정확한 원장 대사는 로컬 테스트 전용 읽기 검증을 사용하고 공개 진단 API를 추가하지 않는다. 배송/만료 시간은 통합 검사에서 주입된 Clock으로 제어한다. 브라우저에서는 실제 UI가 처리할 수 있는 상태를 사용하며 DB 상태 직접 수정으로 버튼을 열지 않는다. 관리자 반품 개입은 TASK0140의 적법한 초기 상태 예제 또는 도메인 전이를 거친 테스트 거래로 준비한다.

## 4. 설계 및 소유 범위

`e2e/tests/seller.spec.ts`, `refund.spec.ts`, 공용 flows/fixtures와 필요한 API 통합 검사가 주 대상이다. 상품ID·주문번호를 역할 간 전달하고 텍스트 개수만으로 성공을 판정하지 않는다. 브라우저 context는 역할별로 분리한다. 검색 등 비동기 결과는 기한 있는 상태 재확인으로 기다리고 무조건적인 고정 sleep을 추가하지 않는다.

기존 데모 발급 한도(1분5회)를 유지한다. 시나리오별 발급 수와 재시도 예산을 계산하고 직렬 실행으로 중복 발급을 피한다. 운영 검증은 새 데모 계정만 사용하며 정상 구매/노출/배송/관리자 확인을 우선한다. 강제 장애·시간 조작·반복 부하 검사는 로컬/CI에서 수행한다.

실패 증거는 trace·스크린샷·단계별 ID/상태 대조로 남기고 토큰/쿠키/개인정보를 공개 artifact에 넣지 않는다. 오류가 발견되면 담당 TASK로 연결해 해결하며 검사를 건너뛰거나 재시도 횟수를 늘려 통과시키지 않는다.

## 5. 구현 계획

1. 기존4개 시나리오와 API 통합 검사를 표의 각 단계에 매핑한다.
2. TASK0139의 좁은 회귀 검사를 유지하고 Playwright에 검색 경유 및 관리자 context를 추가한다.
3. 주문/배송/숨김/복원/환불 대조와 실패·만료 API 검사를 연결한다.
4. 실제 스택에서 최초 시도 기준3회 연속 실행하고 CI 시간·발급 한도를 확인한다.
5. 운영 데모3역할로 핵심 흐름을 재확인하고 방문자 가이드를 같은 동선으로 수정한다.

## 7. 리스크 / 열린 질문

검색 수렴·자동 배송·발급 제한이 겹치면 테스트가 느려질 수 있다. 상태 전이 조합은 API 검사로 나누고 핵심 브라우저 연결만 유지한다. 운영에서 검증하지 않은 강제 실패·메모리 등 항목을 운영 검증 완료로 표현하지 않는다. 기존 가이드의 독립 셀러 발급만으로 다른 판매자의 주문이 보인다는 오해를 해소하도록 실제 상품 선택 동선을 명시한다.
