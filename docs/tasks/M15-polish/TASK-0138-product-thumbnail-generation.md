## 1. 목적

상품 이미지 등록 후 작은 행·목록에 필요한 파생 이미지를 자동 생성한다. 원본 역할의 업로드 자산을 보존하면서 세 앱과 API가 같은 준비된 썸네일을 사용하게 한다. DB는 파일을 변환하지 않고 원본과 파생 파일의 관계·상태를 저장한다.

## 2. 범위

신규 상품 이미지 등록/교체, 파생 파일 저장·작업 재시도, DB migration, API와 검색 투영, 기존 소유 상품 이미지의 재개 가능한 보완 작업을 포함한다. 리뷰/로고/반품 증빙, 임의 외부 URL 수집, 원본 삭제는 제외한다. 기존 주문 스냅샷의 일괄 수정도 하지 않는다.

## 3. 현황 및 요구사항

현재 ProductImage에는 url/alt/sortOrder가 있고 별도 thumbnailUrl 컬럼이나 파생 파일 모델은 없다. 대표 이미지는 첫 번째 이미지이며 API가 그 URL을 thumbnailUrl이라는 이름으로 투영한다. 근거: apps/api/prisma/schema.prisma, catalog/product.service.ts, seller-product.service.ts, cart/cart.service.ts, orders/order-lines.ts, search/search-source.ts.

판매자 prepareImage는 긴 변 최대 2,000px로 줄인 단일 파일을 업로드한다(변환본이 크면 입력 파일 사용). blob previewUrl은 브라우저 임시 미리보기다. 구매자 SearchHitCard의 Next Image는 허용 CDN products 경로를 요청 시 최적화하며 DB에 별도 파생 파일 관계를 기록하지 않는다. 따라서 기존 최적화가 모든 화면용 자동 썸네일 생성 완료를 뜻하지 않는다.

필수: 사용자 수동 작업 없이 생성, 원본 보존, 생성 실패 시 기존 URL 사용, 재시작/중복 실행 안전, 권한 검증, 상품 저장 및 결제 트랜잭션에서 이미지 변환 대기 금지.

## 4. 설계 제안

### 데이터와 파일

- ProductImage.url은 기존 업로드 자산으로 유지한다. 이전 업로드 과정에서 이미 축소된 파일을 카메라 원본으로 복원한다는 뜻은 아니다.
- 원본 저장 키와 변환 버전으로 식별되는 ProductImageDerivative 관계를 추가한다. 원본 식별자, 크기별 파일 키/URL·실제 width/height·byteSize·format, 상태(PENDING/PROCESSING/READY/FAILED), 시도 수·재시도 시각·lease 만료를 관리한다. 정확한 Prisma 필드와 인덱스는 구현 전 erd/결정 문서에 고정한다.
- 작은 행용 긴 변 256px, 카드용 768px WebP를 제안 기본값으로 한다. 비율 유지, 확대 금지, 원본 덮어쓰기 금지. 투명도·회전 메타데이터를 반영한다. 화면 크롭은 UI 책임이다.
- 파일 경로는 원본 키/변환 버전/크기로 결정하고 업로드 성공 후에만 READY를 기록한다. 존재하지 않는 파일 주소를 먼저 API에 노출하지 않는다.

### 자동 처리

상품 저장/이미지 연결 트랜잭션에서 소유 R2 객체에 대한 영속 작업을 등록한다. 상품 등록 이전에 잠시 올려둔 파일은 아직 공개 상품에 연결되지 않았으므로 변환을 미룬다. API의 제한된 백그라운드 소비자가 DB lease로 작업을 확보하여 변환한다. 별도 Redis 도입 없이 기존 DB 작업 처리 방식과 맞추되 SearchOutbox 자체를 이미지 큐로 혼용하지 않는다.

변환은 서버 이미지 디코더(Sharp 도입안)로 수행한다. 전체 실행자 공통 풀 동시성을 1로 고정한다. 두 크기도 순차 변환하며 대기열에는 파일 바이트를 적재하지 않는다. 입력 10MiB·16메가픽셀, 변환 30초 제한을 적용하고 Sharp 캐시를 끄고 내부 스레드를 1개로 제한한다. 작업별 별도 자식 프로세스에서 디코딩하며 완료/실패/시간 초과 시 종료 및 임시 파일 정리를 보장한다. JS heap 제한만으로 native 메모리를 제한할 수 없으므로 실제 RSS를 감시하여 192MiB 초과 시 자식 프로세스를 중단한다. 전체 풀의 슬롯은 자식 종료 확인 후 해제한다. 앱 재시작·다중 인스턴스에서도 DB 소유권으로 단일 실행을 보장한다. 서버가 생성한 소유 객체 키만 읽는다. 사용자가 넣은 임의 URL로 서버 요청하지 않는다. 키 소유자/콘텐츠 실제 형식을 검증하고 재시도는 최대 3회, FAILED는 재처리 명령으로 복구한다. 프로세스 종료 후 lease 만료로 회수하고 원본이 교체된 오래된 작업은 새 이미지 연결을 덮어쓰지 못하게 한다.

### 읽기 계약과 이전 데이터

기존 thumbnailUrl은 READY인 256px 파일 우선, 없으면 기존 원본 URL을 반환한다. 카드용 768px URL은 shared 계약에 선택 필드로 추가하여 단계적으로 소비한다. 모든 카탈로그/판매자/장바구니/컬렉션/문의/검색 투영을 일관되게 연결하고 READY 전환 시 검색 outbox로 재색인한다. 상세 갤러리는 원본을 유지한다. 주문 생성은 그 시점의 표시 URL을 스냅샷에 고정한다.

주문이 참조한 파생 파일은 원본 교체·상품 삭제만으로 삭제하지 않는다. 참조 수명 정책을 설계 문서에 기록하며 이번 TASK에 자동 삭제를 넣지 않는다. 기존 주문 JSON은 바꾸지 않는다. 기존 최근 본 URL은 TASK-0137 보정과 호환한다.

기존 데이터 보완은 dry-run 목록/개수 → 제한된 배치 → 체크포인트 재개 순서다. 소유 객체만 처리하고 누락 객체·외부 URL·시드 SVG는 분리 보고한다. 알려진 SVG는 TASK-0137의 동일 바이트 자산으로 유지하며 일반 업로드 디코더에 임의 SVG를 허용하지 않는다.

## 7. 리스크 / 열린 질문

API와 변환 CPU 공유는 기존 지연 문제를 다시 만들 수 있으므로 동시성/픽셀 제한과 P2가 배포 조건이다. 기준을 넘으면 worker 분리 비용과 배포 구성을 문서 갱신 후 확정한다. 저장 용량은 파생 파일 2개만큼 증가하므로 dry-run에서 예상량을 보고한다. TASK-0130의 Next 최적화와 중복 재인코딩하지 않도록 READY 파생 파일은 직접 사용하고 기존 원본 fallback만 기존 최적화 경로로 보낸다. 실제 렌더 폭별 화질을 확인하여 크기 변경이 필요하면 구현보다 문서를 먼저 수정한다.
