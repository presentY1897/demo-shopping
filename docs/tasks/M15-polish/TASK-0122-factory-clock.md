## 4. 설계

### 4.1 무엇이 어긋나 있나

대시보드는 **KST 일 단위 범위**를 주입된 시계에서 계산한다 (`kst-days.ts` · `rangeOf`).

```ts
const range = rangeOf(params, this.clock.now(), { … })
```

검사는 앱 시계를 `2026-09-09T05:00:00.000Z` 로 고정한다. 그러면 "오늘"은 **KST 2026-09-09**,
즉 `[09-08T15:00Z, 09-09T15:00Z)` 다.

그런데 사용자 행은 그 범위와 무관하게 만들어진다.

```sql
INSERT INTO "User" ("id", …, "updatedAt")
VALUES ($1, …, now())
```

`createdAt` 은 아예 넘기지 않아 **열 기본값(`@default(now())`)** 이 채운다 — 데이터베이스 시계,
곧 진짜 지금이다. `UserOptions` 에 `createdAt` 이 없으므로 **검사가 정할 방법도 없다.**

```
앱 시계가 정한 범위   [09-08 15:00Z, 09-09 15:00Z)
행이 실제로 찍힌 시각   09-09 15:40Z            ← 범위 밖
→ current.newUsers = 0,  기대값 1
```

### 4.2 그래서 "오늘까지만" 통과했다

`NOW` 가 **고정된 날짜**라 범위도 고정된 하루다. 실제 시각이 그 하루를 지나가면 다시는 들어오지
못한다.

| 실제 시각 (UTC) | 결과 |
| --- | --- |
| 09-08 15:00 ~ 09-09 15:00 | 통과 |
| **09-09 15:00 이후** | **영구 실패** |

관측이 그대로 맞는다. 같은 날 CI 세 번 중 앞의 둘은 통과하고 마지막만 실패했다.

| PR | CI 시각 (UTC) | 결과 |
| --- | --- | --- |
| #129 | 13:0x | 통과 |
| #130 | 14:0x | 통과 |
| **#131** | **15:36** | **실패** |

로컬에서도 15:40Z 에 그대로 재현된다 (6.3).

**이것이 TASK-0120 보다 나쁜 이유.** 0120 의 정산 검사는 하루 중 시각에 따라 갈렸으므로 다음 날
오전이면 다시 통과했다 — 고약하지만 스스로 낫는 것처럼 보인다. 이쪽은 **날짜가 고정이라 낫지
않는다.** 한 번 지나가면 끝이다.

### 4.3 검사가 「언제 가입했는가」를 정한다

고칠 것은 대시보드가 아니다. **범위를 주입된 시계에서 계산하는 것은 옳고**, 프로덕션에서는 행도
같은 실시간에 찍히므로 둘이 어긋나지 않는다. 틀린 것은 **검사가 자기가 주장하는 사실을 만들지
못하는 것**이다 — "이 사람은 이번 기간에 가입했다"가 검사의 주장인데, 그 시각을 데이터베이스가
정한다.

```ts
export interface UserOptions {
  …
  readonly createdAt?: Date | string
}
```

```sql
VALUES ($1, …, $7, COALESCE($8::timestamptz, now()), now())
```

**기본값은 그대로 `now()` 다.** 시각을 신경 쓰지 않는 수백 개의 기존 호출은 한 글자도 바뀌지
않는다. 시각이 판정에 들어가는 검사만 그것을 명시한다.

```ts
await createUser(db, { isDemo: true, createdAt: NOW })
await createUser(db, { createdAt: NOW })
```

실측으로 확인했다 — 이 수정으로 19건 전부 통과한다 (6.3).

### 4.4 팩토리의 `now()` 12곳을 전수 판정한다

한 곳만 고치면 다음 폭탄이 다른 팩토리에서 터진다. **판정 기준은 하나다.**

> **그 시각이 어떤 판정에 쓰이는가?**
> - 기간 집계 · 만료 · 정렬 · 「이 뒤에 온 것인가」에 들어간다 → **검사가 정할 수 있어야 한다**
> - 감사 기록일 뿐이다 → **그대로 둔다**

`updatedAt` 은 대체로 후자이고 `createdAt`·`expiresAt`·`refundedAt` 류가 전자다. 다만 **추정하지
않고 실제로 확인한다** — 각 열이 어느 질의의 `WHERE` 에 등장하는지 찾아 표로 남긴다.

전부 옵션으로 뚫는 것이 목적이 아니다. **판정에 쓰이는 시각이 두 시계에서 나오지 않게 하는
것**이 목적이고, 그 판단 결과 자체가 이 TASK 의 산출물이다.
