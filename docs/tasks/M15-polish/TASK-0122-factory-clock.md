## 4. 설계

### 4.1 무엇이 어긋나 있나

대시보드는 **KST 일 단위 범위**를 주입된 시계에서 계산한다 (`kst-days.ts` · `rangeOf`).

```ts
const range = rangeOf(params, this.clock.now(), { … })
```

검사는 앱 시계를 `2026-09-09T05:00:00.000Z` 로 고정한다. 그러면 "오늘"은 **KST 2026-09-09**,
즉 `[09-08T15:00Z, 09-09T15:00Z)` 다.

그런데 사용자 행은 그 범위와 무관하게 만들어진다.

```sql
INSERT INTO "User" ("id", …, "updatedAt")
VALUES ($1, …, now())
```

`createdAt` 은 아예 넘기지 않아 **열 기본값(`@default(now())`)** 이 채운다 — 데이터베이스 시계,
곧 진짜 지금이다. `UserOptions` 에 `createdAt` 이 없으므로 **검사가 정할 방법도 없다.**

```
앱 시계가 정한 범위   [09-08 15:00Z, 09-09 15:00Z)
행이 실제로 찍힌 시각   09-09 15:40Z            ← 범위 밖
→ current.newUsers = 0,  기대값 1
```

### 4.2 그래서 "오늘까지만" 통과했다

`NOW` 가 **고정된 날짜**라 범위도 고정된 하루다. 실제 시각이 그 하루를 지나가면 다시는 들어오지
못한다.

| 실제 시각 (UTC) | 결과 |
| --- | --- |
| 09-08 15:00 ~ 09-09 15:00 | 통과 |
| **09-09 15:00 이후** | **영구 실패** |

관측이 그대로 맞는다. 같은 날 CI 세 번 중 앞의 둘은 통과하고 마지막만 실패했다.

| PR | CI 시각 (UTC) | 결과 |
| --- | --- | --- |
| #129 | 13:0x | 통과 |
| #130 | 14:0x | 통과 |
| **#131** | **15:36** | **실패** |

로컬에서도 15:40Z 에 그대로 재현된다 (6.3).

**이것이 TASK-0120 보다 나쁜 이유.** 0120 의 정산 검사는 하루 중 시각에 따라 갈렸으므로 다음 날
오전이면 다시 통과했다 — 고약하지만 스스로 낫는 것처럼 보인다. 이쪽은 **날짜가 고정이라 낫지
않는다.** 한 번 지나가면 끝이다.

### 4.3 검사가 「언제 가입했는가」를 정한다

고칠 것은 대시보드가 아니다. **범위를 주입된 시계에서 계산하는 것은 옳고**, 프로덕션에서는 행도
같은 실시간에 찍히므로 둘이 어긋나지 않는다. 틀린 것은 **검사가 자기가 주장하는 사실을 만들지
못하는 것**이다 — "이 사람은 이번 기간에 가입했다"가 검사의 주장인데, 그 시각을 데이터베이스가
정한다.

```ts
export interface UserOptions {
  …
  readonly createdAt?: Date | string
}
```

```sql
VALUES ($1, …, $7, COALESCE($8::timestamptz, now()), now())
```

**기본값은 그대로 `now()` 다.** 시각을 신경 쓰지 않는 수백 개의 기존 호출은 한 글자도 바뀌지
않는다. 시각이 판정에 들어가는 검사만 그것을 명시한다.

```ts
await createUser(db, { isDemo: true, createdAt: NOW })
await createUser(db, { createdAt: NOW })
```

실측으로 확인했다 — 이 수정으로 19건 전부 통과한다 (6.3).

### 4.4 팩토리의 `now()` 12곳을 전수 판정한다

한 곳만 고치면 다음 폭탄이 다른 팩토리에서 터진다. **판정 기준은 하나다.**

> **그 시각이 어떤 판정에 쓰이는가?**
> - 주입된 시계에서 파생된 창과 비교된다 → **검사가 정할 수 있어야 한다**
> - 감사 기록 · 사람이 준 파라미터와만 비교된다 → **그대로 둔다**

#### 결과 — `now()` 12곳은 전부 `updatedAt` 이었다

| 대상 | `now()` 가 채우는 열 | 판정 |
| --- | --- | --- |
| `User` · `Address` · `Seller` · `Category` · `AttributeDefinition` · `Product` · `ProductOption` · `ProductOptionValue` · `ProductVariant` · `Coupon` · `UserCoupon` · `CommissionRate` | `updatedAt` | 감사 기록. **그대로 둔다** |

`updatedAt` 은 어떤 질의의 `WHERE` 에도 등장하지 않는다. **진짜 위험은 `now()` 가 아니라
아무도 넘기지 않는 `createdAt`** — 열 기본값(`@default(now())`)이 조용히 채우는 쪽이었다.

#### 그래서 반대편에서 다시 훑었다

「주입된 시계에서 파생된 창과 `createdAt` 을 비교하는 곳」을 프로덕션에서 찾고, 그 행을 만드는
팩토리가 있는지 교차 확인했다.

| 창을 만드는 곳 | 비교 대상 | 팩토리 | 판정 |
| --- | --- | --- | --- |
| `dashboard.service.ts` `rangeOf(…, clock.now())` | `User.createdAt` | `createUser` | **위험 → 뚫는다** |
| 〃 | `SellerOrder.createdAt` | 없음 — 각 스펙이 직접 넣고 대개 시각을 명시한다 | R3 |
| `admin-claim.service.ts` `adminOverdueScanBefore(now, …)` | `ClaimRequest.createdAt` | 없음 — 〃 | R3 |
| `admin-catalog.service.ts` | `Product.createdAt` | `createProduct` | 안전 — 창이 **사람이 준 `from`/`to`** 이지 시계 파생이 아니다 |
| `Coupon` · `UserCoupon` · `CommissionRate` | `validFrom` · `validUntil` · `expiresAt` | 각 팩토리 | 안전 — **이미 명시적으로 넘긴다** |

**뚫은 것은 `createUser` 하나다.** 나머지는 이미 안전하거나 팩토리가 없다. 전부 옵션으로 뚫는 것이
목적이 아니라 판정이 목적이라고 적어 둔 그대로다.

#### 수정 실측 (같은 조건)

`UserOptions.createdAt` 을 뚫고 `dashboard.spec.ts` 가 `NOW` 를 넘기게 하니

```

```

**이 실측은 구현이 아니라 진단 확인이다.** 실험 후 되돌렸고, 승인 뒤에 정식으로 넣는다.

#### 수정 후 (2026-09-09 15:53Z — 앱 시계 창 밖)

| | 결과 |
| --- | --- |
| 수정 전, 같은 실제 시각 | **1 failed** / 18 passed |
| 수정 후, 같은 실제 시각 | **19 passed** |
| F3 — `createdAt: NOW` 를 지우고 | **1 failed** (회귀가 잡힌다) |

**같은 실제 시각에서 결과가 갈린다.** 실제 시각은 이미 앱 시계의 창(KST 09-09 종료) 밖이므로,
수정 후 통과는 「달력이 아직 맞아떨어져서」가 아니다.

#### 앱 시계를 옮기는 방법이 왜 기준이 될 수 없었나

처음 시도한 F2 는 `NOW` 를 −30일 · 당일 · +30일로 옮기는 것이었다. 결과는 이랬다.

| `NOW` | 결과 |
| --- | --- |
| `2026-08-10` | 2 failed |
| `2026-09-09` | 19 passed |
| `2026-10-09` | 2 failed |

깨진 2건은 **결함이 아니다.**

```ts
// KST 로 9월 8일 오전 0시 30분 = UTC 9월 7일 15시 30분.
await seed({ createdAt: '2026-09-07T15:30:00.000Z', amount: 7_000 })
const answer = await metrics(operator, '?from=2026-09-07&to=2026-09-09')
```

`NOW` 에 맞춰 날짜를 박아 둔 검사이고, 앱 시계를 옮기면 그 리터럴도 같이 옮겨야 한다.
**의도된 결합이지 시계 의존이 아니다.** 이 파일을 고치는 사람이 알아야 할 사실이라 R6 으로 남긴다.
