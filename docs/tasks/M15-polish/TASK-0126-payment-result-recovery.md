## 1. 목적

응답이 끊겨도 실제 주문 결과를 확인하고, 이미 결제한 사용자에게 새 결제를 권하지 않는다.

## 2. 범위

### 포함

- 결제 중/결과 확인 중/거절/완료 상태와 모든 버튼의 공통 조건
- 주문·결제 생성 응답 유실 및 새로고침 복구
- 주문 상세로 연결되는 완료 화면과 결제 단계별 요청 제한

### 제외

- 서버 중복 방지는 선행 TASK-0125의 계약을 사용한다. 일반적인 API 성능 최적화는 TASK-0131이다.

## 3. 요구사항

[검토 보고서](../../reviews/2026-09-10-storefront-checkout-review.md)의 해당 발견을 해결하며, 실측 사실과 코드상 위험을 구분한다. 아래 완료 기준의 시나리오를 구현 전 회귀 검증으로 구체화한다.

기존 구매자/판매자 권한·데모 격리·금액 스냅샷·재고/원장 정합성을 유지한다. 변경 계약은 `packages/shared`를 기준으로 API·화면·대역에 함께 반영한다.

## 4. 설계

1. 시간 초과를 거절로 확정하지 않는다. 기존 주문/결제 조회로 확인 중 상태를 유지하고 확인 전 새 결제 생성·승인을 차단한다. 조회 자체가 실패하면 결과 확인 재시도와 주문 내역 이동을 제공한다.
2. 메모리 ref에만 의존하지 않는 복구 식별 경로를 둔다. checkoutId→orderId→paymentId 복구 계약은 TASK-0125의 실제 응답을 사용한다. 브라우저 저장에는 토큰·카드번호·배송지를 넣지 않는다.
3. 조회는 요청이 끝난 후 다음 조회를 예약하고 취소·백오프·상한을 둔다. 조회 상한 도달은 결제 실패가 아니다. 서버 대사로 최종 확정된 상태도 같은 완료 화면으로 연결한다.
4. 주문하기와 재시도 모두 동의·배송지·수단·금액 재계산·진행 중 여부를 같은 함수에서 검사한다. 주문 생성 후 배송지/쿠폰 스냅샷은 잠그고 화면에도 그 값을 보여준다. 변경이 필요하면 기존 결제 상태를 확인한 후 명시적인 주문 재작성 동선을 제공한다.
5. 완료 화면은 주문 번호·결제금액·주문 상세 링크를 제공한다. 단계별 timeout은 서버 예산과 정합성을 맞추되 결과 복구를 대체하지 않는다. 가상 카드와 토스 반환 화면을 함께 점검한다.

### 구현 계약

GET /checkouts/:id/order로 인증된 구매자의 기존 주문을 복구한다. GET /orders/:id/payment는 authorizationPending을 함께 반환해 승인 전 실행 대기와 응답을 잃은 승인 진행을 구분한다. 결과 조회는 최대 12회, 1~5초 간격이며 상한 후에도 실패로 바꾸지 않고 수동 결과 조회와 주문 내역 이동을 제공한다. 완료 화면은 실제 주문 금액과 상세 경로를 사용한다.

승인을 시작하지 않은 READY에서 결제창을 열지 못한 경우에는 수단 변경을 허용한다. 서버는 authorizationStartedAt이 null인 READY만 원자적으로 FAILED 처리한 뒤 새 시도를 만든다. 실행권을 획득한 요청과 경합하면 변경을 거부한다.

### 통합 검증 진행
