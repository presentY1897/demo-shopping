# 2026-09-05 세션 07

승인만 된 결제를 되감는 화살표.

## D-221. `AUTHORIZED → CANCELED` 를 연다 — **승인 취소는 환불이 아니다**

TASK-0057 이 「보상 처리」를 하려면 필요한 화살표이고, 지금까지 없던 것이다.

### 무엇이 문제였나

승인만 받고 사라진 결제가 남는다. 시간순으로:

| 시각 | 무슨 일 | 재고 | 카드 | 결제 |
| --- | --- | --- | --- | --- |
| 0분 | 주문서 진입 | **1개 예약** (TTL 15분) | — | — |
| 1분 | 승인 | 예약 유지 | **금액이 잡힘** | `AUTHORIZED` |
| 1분 직후 | 사람이 사라진다 (창을 닫음·지하철·탭 종료) | | | |
| 16분 | 예약 만료 → 재고가 남에게 간다 | 0개 | **여전히 잡혀 있음** | `AUTHORIZED` |
| 영원히 | | | | `AUTHORIZED` |

**물건은 못 받았는데 돈은 잡혀 있다.** 가상 카드에서는 그 사람의 한도가 물리고(승인 시점에
원장을 깎는다), 토스에서는 실제 카드의 승인이 살아 있다.

풀 방법이 없었다. `paymentTransitions` 에서 `AUTHORIZED` 가 갈 수 있는 곳은 `PAID` 하나였고,
`payment-rules.ts` 는 그 이유까지 적어 뒀다 — 「설계 문서가 그 화살표를 그리지 않았으므로
여기에도 없다」. 없는 것을 지어내지 않은 판단이었고, 이제 그 문서를 고친다.

### 왜 환불과 같은 길이 아닌가

| | 환불 (`PAID → PARTIAL_CANCELED | CANCELED`) | **승인 취소** (`AUTHORIZED → CANCELED`) |
| --- | --- | --- |
| 돈이 어디에 | 이미 **우리 쪽으로 왔다** | 아직 **안 왔다**. 카드사가 잡고만 있다 |
| 결제사 API | `refund` | `cancel` |
| 수수료 | 붙는다 | 대개 없다 |
| 우리 장부 | 「돌려준 돈」 | **「받은 적 없는 돈」** |
| 부분 | 여러 번 가능 | **전액뿐** — 매입한 적이 없으니 나눌 것이 없다 |

`PaymentProviderPort` 에 `cancel` 이 처음부터 있었고 **지금까지 아무도 부르지 않았다.** 그
메서드가 기다리던 자리가 이것이다.

부분 취소가 없으므로 착지점도 `CANCELED` 하나다. `PARTIAL_CANCELED` 로는 갈 수 없고, 그
사실이 `refundDecision` 이 `AUTHORIZED` 를 계속 거절하는 이유와 같다 — 환불할 돈이 아직
우리에게 없다.

### 누가 이 화살표를 여는가

**배치만 연다.** 사용자에게는 「승인 취소」 버튼이 없다 — 그 사람은 이미 화면을 떠났고, 떠나지
않았다면 결제를 마치는 것이 그의 다음 행동이다.

**감지 조건은 둘을 함께 본다** (R1 — 자동 취소가 정상 결제를 취소하는 위험).

1. 승인된 지 오래됐다
2. **그 주문에 살아 있는 예약이 없다**

두 번째가 핵심이다. 예약이 살아 있다는 것은 「아직 이 결제로 살 수 있다」는 뜻이라 건드리면 안
되고, 없다는 것은 **재고가 이미 남에게 갔다**는 뜻이라 이 결제로 살 수 있는 것이 없다. 정상
결제는 승인에서 매입까지 몇 초라 첫 조건에도 안 걸리고, 걸려도 두 번째가 막는다.

### 같이 정한 것 — 되감지 **않는** 경우

매입까지 끝났는데 주문이 완료되지 않은 건(`Payment.PAID` + `SellerOrder.PAYMENT_PENDING`)은
**앞으로 마저 끝낸다.** 돈은 이미 우리 쪽으로 왔고 사람은 물건을 기다린다 — 그것을 취소하는
것은 사고를 두 번째로 만드는 일이다. `OrderService.markPaid` 가 멱등하므로 배치가 다시 부른다.

보상이 늘 되감기라는 생각이 이 자리에서 틀린다. **되감을지 마저 끝낼지는 「돈이 어디까지
왔는가」가 정한다.**
