# 2026-09-03 · Session 02

M01(기반 구축) 완료 직후의 세션. 개발 워크플로를 강제 수단으로 승격하고, 마일스톤을 가로지르는 병행 진행 방식을 정했다.

## 확정 사항

### D-203. `main` 브랜치 보호 규칙 — 전면 적용

`main` 을 보호된 브랜치로 만들고 **관리자 우회까지 막았다**(`enforce_admins`). 모든 변경은 PR 과 CI 4개(`typecheck`·`lint`·`build`·`test`) green 을 거친다.

**계기**: M01 내내 CI 가 사실상 돌지 않았다. `ci.yml` 의 트리거가 `pull_request` 뿐이라 `main` 직접 push 는 아무 검사도 받지 않았고, 실측하면 M01 의 main 커밋들은 체크 0개였다. CI 가 실제로 돈 것은 PR #1 하나뿐이다.

트리거에 `push: [main]` 을 추가해 구멍은 막았지만, 그것만으로는 **깨진 것을 알려줄 뿐 막지는 못한다.** 또 로컬 게이트는 워킹 트리를, CI 는 커밋된 내용을 검사한다 — `git add` 를 빠뜨린 파일은 로컬 검사를 아무리 성실히 돌려도 구조적으로 못 잡는다.

| 설정 | 값 | 근거 |
| --- | --- | --- |
| 필수 체크 | `typecheck` · `lint` · `build` · `test` | `GitGuardian` 은 **제외** — 서드파티가 보고를 멈추면 머지가 영영 안 열린다 |
| 승인 수 | **0** | 1인 저장소에서는 자기 PR 을 자기가 승인할 수 없다. 1 이상이면 머지가 영구히 막힌다 |
| 머지 방식 | **rebase 만** (squash·merge commit 끔) | squash 는 TASK 당 5~10개로 나눈 커밋을 하나로 뭉갠다 |
| 관리자 우회 | 금지 | 규칙 **우회**만 막고 **관리**는 막지 않으므로 잠길 위험이 없다 |

**폐기한 안**: "3~6번만 켜고 7·8번은 M02 이후" — CI 가 강제되지 않는 기간이 그만큼 길어지는 것이 유일한 실질 비용이라 미룰 이유가 없었다.

### D-204. 마일스톤을 가로질러 병행 진행

**마일스톤 번호는 진행 순서가 아니다.** M01~M15 는 주제별 묶음이고, 각 TASK 의 `선행` 이 실제 의존이다. 문서의 `선행 M0N 완료` 는 작성 당시의 관례였고 기술적 의존이 아닌 경우가 많다.

실제로 두 건을 정정했다 — TASK-0014(디자인 토큰)의 선행은 M02 가 아니라 M01, TASK-0020(사용자 스키마)의 선행은 M03 가 아니라 M01 이다.

병행 규칙 4가지는 `docs/tasks/README.md` "진행 순서" 절에 있다. 그중 하나는 구조적 제약이다 — **`schema.prisma` 를 건드리는 TASK 는 동시에 하나만.** 두 브랜치가 각자 마이그레이션 폴더를 만들면 타임스탬프 순서가 꼬이고 rebase 로는 정리되지 않는다. 그래서 스키마 계열 TASK 는 직렬이고, 병행 상대는 항상 프론트엔드 쪽에서 찾게 된다.

### D-205. 디자인 방향 — 현행 확정

TASK-0014 의 토큰 결과물을 검토하고 **현재 값 그대로 확정**했다. 다음 항목들을 이 값으로 고정한다.

| 항목 | 확정값 |
| --- | --- |
| 중립색 온도 | 파랑 기운 약간 (chroma 0.004~0.006) |
| 맥시멀 폰트 배율 | 데스크톱 본문 15.2px (`--font-scale: 0.95`) |
| 미니멀 여백 | 데스크톱 gutter 48px, lg 컨트롤 84px |
| 앱별 accent | shop 파랑 · seller 청록 · admin 보라 |
| 터치 타깃 하한 | 44px — 밀도와 무관하게 `max()` 로 보장 |

바꿀 일이 생기면 토큰 값만 고치면 되고 컴포넌트는 건드리지 않는다. `--space-unit` 이 Tailwind 의 `--spacing` 에 연결되어 있어 `p-4` 같은 간격 유틸리티 **전체**가 밀도를 따라간다.

### D-206. 디자인 기준은 **지속적으로 확인 가능한 형태**로 유지한다

디자인을 한 번 확정하는 것으로 끝내지 않는다. 토큰과 밀도 규격을 **언제든 눈으로 확인할 수 있는 문서**가 항상 살아 있어야 한다.

담당은 **Storybook**(TASK-0104)이다. 컴포넌트 스토리뿐 아니라 **디자인 토큰 문서 페이지**(색 스케일, 타이포, 간격, 밀도 × 뷰포트 매트릭스, 컨트롤 높이·터치 타깃)를 함께 담는다.

TASK-0014 가 만든 `apps/shop` 의 `/tokens` 프리뷰 페이지는 **개발 전용**(프로덕션 404)이며, Storybook 이 그 역할을 이어받은 뒤 제거한다. **먼저 옮기고 나중에 지운다** — 순서가 반대면 확인 수단이 없는 구간이 생긴다.
