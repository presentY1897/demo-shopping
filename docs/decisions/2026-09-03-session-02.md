## 확정 사항

### D-203. `main` 브랜치 보호 규칙 — 전면 적용

`main` 을 보호된 브랜치로 만들고 **관리자 우회까지 막았다**(`enforce_admins`). 모든 변경은 PR 과 CI 4개(`typecheck`·`lint`·`build`·`test`) green 을 거친다.

**계기**: M01 내내 CI 가 사실상 돌지 않았다. `ci.yml` 의 트리거가 `pull_request` 뿐이라 `main` 직접 push 는 아무 검사도 받지 않았고, 실측하면 M01 의 main 커밋들은 체크 0개였다. CI 가 실제로 돈 것은 PR #1 하나뿐이다.

트리거에 `push: [main]` 을 추가해 구멍은 막았지만, 그것만으로는 **깨진 것을 알려줄 뿐 막지는 못한다.** 또 로컬 게이트는 워킹 트리를, CI 는 커밋된 내용을 검사한다 — `git add` 를 빠뜨린 파일은 로컬 검사를 아무리 성실히 돌려도 구조적으로 못 잡는다.

| 설정 | 값 | 근거 |
| --- | --- | --- |
| 필수 체크 | `typecheck` · `lint` · `build` · `test` | `GitGuardian` 은 **제외** — 서드파티가 보고를 멈추면 머지가 영영 안 열린다 |
| 승인 수 | **0** | 1인 저장소에서는 자기 PR 을 자기가 승인할 수 없다. 1 이상이면 머지가 영구히 막힌다 |
| 머지 방식 | **rebase 만** (squash·merge commit 끔) | squash 는 TASK 당 5~10개로 나눈 커밋을 하나로 뭉갠다 |
| 관리자 우회 | 금지 | 규칙 **우회**만 막고 **관리**는 막지 않으므로 잠길 위험이 없다 |

**폐기한 안**: "3~6번만 켜고 7·8번은 M02 이후" — CI 가 강제되지 않는 기간이 그만큼 길어지는 것이 유일한 실질 비용이라 미룰 이유가 없었다.

### D-204. 마일스톤을 가로질러 병행 진행

**마일스톤 번호는 진행 순서가 아니다.** M01~M15 는 주제별 묶음이고, 각 TASK 의 `선행` 이 실제 의존이다. 문서의 `선행 M0N 완료` 는 작성 당시의 관례였고 기술적 의존이 아닌 경우가 많다.

실제로 두 건을 정정했다 — TASK-0014(디자인 토큰)의 선행은 M02 가 아니라 M01, TASK-0020(사용자 스키마)의 선행은 M03 가 아니라 M01 이다.

병행 규칙 4가지는 `docs/tasks/README.md` "진행 순서" 절에 있다. 그중 하나는 구조적 제약이다 — **`schema.prisma` 를 건드리는 TASK 는 동시에 하나만.** 두 브랜치가 각자 마이그레이션 폴더를 만들면 타임스탬프 순서가 꼬이고 rebase 로는 정리되지 않는다. 그래서 스키마 계열 TASK 는 직렬이고, 병행 상대는 항상 프론트엔드 쪽에서 찾게 된다.

### D-207. 테스트 레이어와 대역 규약

`QUALITY-GATES.md` 의 Q5 가 "얼마나 테스트하는가"만 정하고 **"무엇을 대상으로 테스트하는가"** 를 정하지 않아, 백엔드 검증에 구멍이 있었다.

**계기**: CI 에 PostgreSQL 이 없어서 DB 를 쓰는 테스트가 물리적으로 돌 수 없었다. 그래서 TASK-0020 의 부분 유니크 인덱스·CHECK 제약은 **마이그레이션 파일에 그 SQL 문자열이 남아 있는지**만 검사한다. 누가 지우는 것은 잡지만, **조건을 잘못 고쳐도 통과한다.** 제약이 실제로 동작하는지는 사람이 손으로 psql 을 쳐서 확인한 것이 전부였다.

| 레이어 | 얼마나 | 무엇을 대상으로 |
| --- | --- | --- |
| 순수 로직 | 분기 100% | 아무것도 필요 없음 |
| 백엔드 서비스·API | 라인 80% | **실제 PostgreSQL** |
| 프론트 컴포넌트·화면 | 상호작용 목록 | **백엔드 모킹** |
| 계약 | 계약 게이트 | 양쪽이 같은 zod 스키마 통과 |
| E2E | 시나리오 | 실 스택 |

**백엔드에 실제 DB 를 쓰는 이유**: 이 프로젝트는 불변식을 DB 가 강제하도록 설계했다(기본 배송지 1개, 재고 조건부 갱신, 잔액 행 잠금, 트리 어드바이저리 락). Prisma 를 모킹하면 정확히 그 부분만 검증에서 빠진다.

**프론트에 모킹을 쓰는 이유**: 화면이 검증할 것은 "이 응답이 오면 올바르게 그리는가"이지 "백엔드가 그 응답을 만들 수 있는가"가 아니다.

**모킹의 대가**는 계약 게이트로 갚는다. 프론트 모킹 데이터와 백엔드 실제 응답을 **같은 zod 스키마로 parse** 한다. 이게 없으면 양쪽 테스트가 다 초록인데 앱이 깨진다.

#### DB 테스트 격리 — 트랜잭션 롤백을 쓰지 않는다

테스트 전체를 트랜잭션으로 감싸고 끝에 롤백하는 방식은 청소가 공짜지만 두 가지가 깨진다. 실제 PostgreSQL 17.11 로 확인했다.

| 확인한 것 | 결과 |
| --- | --- |
| 커밋 전 다른 커넥션에서 조회 | **0행** (커밋 후 1행) → 동시 요청 상황을 만들 수 없다 |
| 트랜잭션 안에서 `BEGIN` | `WARNING: there is already a transaction in progress` → 중첩 트랜잭션이 없다. savepoint 가 된다 |
| 질의 후 격리 수준 지정 | `ERROR: SET TRANSACTION ISOLATION LEVEL must be called before any query` |
| `pg_advisory_xact_lock` 중간 해제 | `WARNING: you don't own a lock of type ExclusiveLock` / `f` → 트랜잭션이 끝나야 풀린다 |

즉 **테스트를 트랜잭션에 넣으면 트랜잭션의 동작 자체가 프로덕션과 달라진다.** 검증해야 할 것의 상당수(초과판매 방지, 잔액 잠금, 트리 이동, 결제 멱등, 정산 배치)가 여기 걸린다.

**대안**: 워커별 DB(`CREATE DATABASE ... TEMPLATE` 로 복제 — 파일 복사라 저렴) + 테스트 사이 `TRUNCATE ... RESTART IDENTITY CASCADE`. 전부 진짜 커밋이라 함정이 없고, 초기화된 상태로 시작하는 성질은 그대로다.

**폐기한 안**: "기본은 롤백, 동시성 테스트만 별도" — 테스트를 쓸 때마다 어느 쪽인지 판단해야 하고, 판단을 틀리면 통과하는데 아무것도 증명 안 하는 테스트가 되며 그것이 눈에 띄지 않는다. 규칙이 하나여야 틀릴 여지가 없다.

### D-208. TASK 분할 축은 레이어

한 TASK 가 화면과 API 를 섞지 않는다. 섞이면 어느 게이트를 받는지 모호해지고, 프론트·백엔드 테스트 규칙이 한 문서 안에서 충돌한다.

게이트 2~5장은 원래부터 **TASK 가 무엇을 만드는지에 따라 조건부**로 적용된다. 섞인 TASK 는 그 조건이 동시에 걸려 기준이 흐려진다.

절단면은 **`packages/shared` 의 zod 스키마**다. 나눈 두 쪽이 같은 스키마를 참조하므로 계약이 어긋나지 않는다. 스키마가 없으면 쪼개는 순간 드리프트가 시작된다.

대상: 혼합으로 확인된 **TASK-0026(입점 신청·승인) · 0027(프로필·배송지) · 0034(상품 등록·수정) · 0035(상품 목록·재고 관리)** 4개. 나머지는 이미 레이어로 갈려 있다(예: 0028 카테고리 스키마·트리 API ↔ 0029 관리자 카테고리 화면).

### D-210. 무료 인스턴스 시간은 자동 배포가 주로 쓴다

TASK-0101 이 배포된 API 가 **49분 관찰 동안 한 번도 잠들지 않는 것**을 발견했다. 750h/월이 워크스페이스 공유(R8)이므로 그대로면 예산이 샌다.

원인은 **`render.yaml` 의 `autoDeployTrigger: commit`** 이다. `main` 에 머지할 때마다 재배포가 돌고, 빌드·기동 시간 동안 인스턴스가 깨어 있다. 머지 직후 측정한 `uptime` 이 768초(약 13분)였던 것이 그 증거다 — 잠들었다 깨어난 값이 아니라 재배포로 재시작한 값이다.

**다만 실제 소모량은 우려보다 훨씬 작다.** 하루치 집중 개발(머지 20여 회, 헬스체크 수십 회) 후 Render 대시보드 실측이 **5.37h / 750h** 였다. 같은 속도로 한 달을 채워도 160h 안팎이다. 서비스는 정상적으로 잠들고 있고, "49분간 안 잠듦"은 그 시간대에 관찰자가 계속 요청을 보내고 있었기 때문이다.

**따라서 지금 조치가 필요한 상태가 아니다.** 아래 결정은 예산을 지키기 위한 것이 아니라 **구조적으로 한도를 넘기는 선택을 배제**하기 위한 것이다.

| 결정 | 내용 |
| --- | --- |
| cron 프리워밍 | **쓰지 않는다.** 2 서비스 × 730h = 1460h 로 한도의 1.9배. 90초를 없애는 대신 월 후반 전체가 다운타임이 된다 |
| 폴링 | **코드 어디에도 두지 않는다.** 자동 재요청은 재시도 루프(상한 3)와 `online`·`visibilitychange` 이벤트뿐 |
| 프리워밍 | **첫 데이터 요청이 곧 프리워밍**이다. 별도 핑을 두면 요청이 두 배가 된다 |
| 자동 배포 | **유지한다.** 실측 5.37h/750h 로 여유가 크다. 머지 빈도가 곧 인스턴스 시간이므로 사용량만 가끔 확인하고, 빠듯해지면 그때 `autoDeployTrigger` 를 끈다 (TASK-0012) |

### D-211. 커밋·PR 에는 누구나 열 수 있는 링크만 붙인다

PR 본문 끝에 자동으로 붙던 `https://claude.ai/code/session_...` 링크는 **저장소 소유자의 계정에 묶여 있어 다른 사람은 열 수 없다.** 이 저장소는 포트폴리오이므로 읽는 사람 대부분이 소유자가 아니고, 그들에게 이 링크는 근거가 아니라 막다른 길이다.

| 항목 | 결정 |
| --- | --- |
| 세션 링크 | **붙이지 않는다.** `~/.claude/settings.json` 의 `attribution.sessionUrl: false` |
| 커밋 트레일러 | `Co-Authored-By: Claude <모델> <noreply@anthropic.com>` 한 줄. 표준 git 트레일러이고 누구나 뜻을 안다. **모델 이름은 설정에 박지 않는다** — `attribution.commit` 에 고정 문자열을 쓰면 모델이 바뀌어도 트레일러가 그대로라 기록이 틀어진다. `attribution.sessionUrl` 만 끄면 링크만 빠지고 모델 이름은 자동으로 채워진다 |
| PR 본문 끝 | 저장소 안 문서로 가는 `../blob/main/...` 링크 (`DECISIONS.md` · TASK 인덱스 · `QUALITY-GATES.md`) |
| 근거를 남기는 곳 | **대화를 통째로 옮기지 않는다.** 남아야 할 결정만 `docs/decisions/` 에 정리하고 거기를 가리킨다 |

설정은 사용자 계정 범위(`~/.claude/settings.json`)이므로 저장소에 커밋되지 않는다. 그래서 **규칙 자체를 여기와 `CLAUDE.md` 에 남긴다** — 설정이 초기화된 환경에서 작업하더라도 규칙은 저장소를 읽으면 알 수 있어야 한다.
