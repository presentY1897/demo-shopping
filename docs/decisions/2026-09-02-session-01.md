## 확정 사항

### D-001. 프로젝트 목표
취업 포트폴리오용 쇼핑몰. 데모 수준이 아니라 **실제 운영 가능한 수준**까지 구현한다.

### D-002. 역할 분리
**사용자(구매자) / 판매자(셀러) / 사이트 관리자(어드민)** 3개 역할. 각 역할별로 페이지 영역을 분리한다.

### D-003. 데모 계정
백엔드에서 **가짜 데모 계정을 즉석 발급**하여, 방문자가 가입 절차 없이 각 역할의 기능을 체험할 수 있게 한다.

### D-004. 디자인 방향
전체적으로 **미니멀·심플**. 단 상품 페이지는 **미니멀 ↔ 맥시멀 3단계**로 표현 밀도를 전환할 수 있게 한다.

### D-005. 상품 카테고리
초기 데이터는 **패션** 중심. 카테고리와 상품 속성은 코드 수정 없이 **추가·설정 가능한 구조**여야 한다.

### D-006. 레퍼런스
국내외 유명 패션 커머스를 주 레퍼런스로 하고, 기능적으로는 알리익스프레스 / 아마존 / 쿠팡을 부분 참고한다.

### D-010. 결제 · 배송 범위
- 결제: **토스페이먼츠 테스트 연동**. 결제창 호출 → 승인 → 취소/부분취소/환불, 웹훅 수신까지 실제 흐름대로 구현한다. 실 결제는 발생하지 않는다.
- 배송: 운송사 API 연동은 하지 않는다. 대신 **배송 도메인(출고, 운송장 발급, 배송중/완료, 반품/교환)을 실제와 동일하게 구현하고 상태 전이는 가상으로 진행**시킨다.

### D-011. 상품 3단계 뷰의 주체
**사용자 토글**. 방문자가 목록/상세의 정보 밀도를 미니멀↔맥시멀 3단계로 직접 전환한다. 판매자가 상품별로 강제하지 않는다.
선택 값은 사용자 설정으로 유지되어 재방문 시에도 보존한다.

### D-012. 원격 저장소 · 배포
- 원격: **GitHub 공개 저장소**
- 배포: **Vercel**(web) + **Railway/Render**(api, PostgreSQL, Meilisearch) + 오브젝트 스토리지(상품 이미지)
- 채용 담당자가 접속 가능한 데모 URL 확보를 목표로 한다.

### D-013. 검색 엔진 — Meilisearch
PostgreSQL FTS / Meilisearch / Elasticsearch+nori 를 비교한 결과 **Meilisearch** 채택.

- 채택 이유: 오타 보정·접두어(자동완성)·패싯·동의어를 기본 제공하고, 한국어 세그멘터를 내장한다. 컨테이너 1개(~100MB)로 운영 가능해 Railway/Render 구성에 그대로 얹힌다.
- 탈락 이유: PostgreSQL FTS 는 한국어 형태소 분석이 약하고 랭킹/패싯을 직접 구현해야 한다. Elasticsearch+nori 는 한국어 품질이 가장 좋지만 메모리 2GB+ 요구로 배포 비용이 과하다.
- 상품 변경 이벤트로 인덱스를 동기화하는 **인덱싱 파이프라인**을 함께 구현한다.
- 리스크: 복합명사 분해 정확도는 nori 대비 낮다. 실제 상품명 데이터로 검증하고, 부족하면 동의어 사전으로 보완한다.

### D-014. 다국어 · 다통화
**구조만 잡고 한국어/KRW 우선**. UI 문구는 메시지 파일로 분리하고 금액은 통화 정보를 포함해 모델링한다. 문구 하드코딩을 금지해 이후 언어 추가 시 구조 변경이 없도록 한다.

- 상품 카탈로그는 공용으로 공유하고, 장바구니·주문·리뷰·판매자 상품 등 개인 데이터만 격리한다.
- 데모 계정의 권한 범위(특히 관리자)는 파괴적 작업을 막도록 별도 TASK 에서 정의한다.

### D-016. 인증 수단 — Google 로그인
실계정 로그인은 **Google OAuth 2.0** 을 사용한다.

- 이메일/비밀번호 자체 회원가입은 구현하지 않는다. 비밀번호 저장·재설정·이메일 인증 부담을 없애고, 실제 커머스의 소셜 로그인 우선 흐름과도 맞다.
- 데모 계정은 이 경로를 타지 않는다. 별도 발급 엔드포인트로 즉시 임시 계정을 만든다(D-015).
- 세션은 JWT(access + refresh), refresh 토큰은 httpOnly 쿠키로 관리한다.
- 판매자·관리자 권한은 로그인 수단과 무관하게 별도 역할 승격 절차로 부여한다.

### D-021. TASK 문서 번호·디렉터리 체계
**마일스톤 디렉터리 + 전역 4자리 평면 번호**.

```
docs/tasks/README.md                 마일스톤 요약
docs/tasks/M01-foundation/README.md  해당 마일스톤 TASK 목록
docs/tasks/M01-foundation/TASK-0001-workspace-skeleton.md
```

- **디렉터리는 그룹핑만, 번호는 전역**이다. TASK 가 다른 마일스톤으로 옮겨가도 번호는 불변이고 `TASK-0042` 참조가 깨지지 않는다.
- 마일스톤 디렉터리는 착수 시점에 생성한다.
- 검토한 대안: 계층 번호(`TASK-001-1`)는 중간 삽입 시 재번호가 필요해 탈락. 단일 디렉터리는 200개를 넘으면 재편이 필요해 탈락.
- 1000개 규모에서는 markdown 이 아니라 이슈 트래커로 가야 한다는 점을 전제로 한 선택이다.

### D-023. 주문 구조 — 2단 분할
한 주문에 여러 판매자 상품이 섞이는 것을 허용하고, 주문을 2단으로 나눈다.

```
Order (결제 1건) → SellerOrder (판매자별, 배송·취소·정산 단위) → Shipment
```

- 결제는 주문 단위 1건, 배송·취소·환불·정산은 SellerOrder 단위
- 상태는 `SellerOrder` 에 붙는다. 판매자 A는 배송완료인데 B는 준비중일 수 있어야 한다
- 대가: 결제 1건에 부분 취소가 여러 번 발생한다. 토스 부분취소 API 와 누적 취소액 추적이 필요하다

### D-024. 상품 모델 — 3단 구조
`Product` + `ProductOption` + `ProductVariant(SKU)`.

- 재고·가격은 **Variant** 단위. 블랙 M만 품절되는 게 정상이다
- 옵션 정의 테이블을 따로 두는 이유는 화면 때문이다. 없으면 옵션 선택 UI 를 그릴 때 모든 Variant 를 훑어 값을 역산해야 하고 표시 순서를 저장할 곳이 없다
- 가격은 Variant 절대값 + Product 에 목록용 최저가 캐시. "기본가 + 추가금"은 할인 계산 시 적용 대상이 모호해진다
- 옵션 없는 상품도 Variant 1개를 강제 생성해 예외 분기를 없앤다

### D-025. 상품 속성 — 정의는 테이블, 값은 JSONB
`AttributeDefinition`(테이블) + `Product.attributes`(JSONB).

- 정의가 테이블이어야 상품 등록 폼과 검색 필터 UI 를 정의로부터 자동 생성할 수 있다
- 값까지 테이블로 빼면(순수 EAV) 상품 목록 20개 조회에 조인이 폭증한다
- 필터링·패싯은 Meilisearch 가 담당하므로 DB 는 값을 통째로 읽고 쓰기만 하면 된다
- **대가**: DB 가 타입·범위를 강제하지 못한다. 저장 전 정의를 읽어 zod 스키마를 동적 생성해 검증하는 코드가 필수다
- 무결성을 포기하는 것이 아니라 **강제 주체를 DB 에서 애플리케이션으로 옮기는** 선택이다. "무엇이 올바른 값인가"는 정의 테이블에 남는다

### D-026. 재고 — 예약 후 확정
주문서 진입 시 15분 TTL 로 재고를 예약하고, 결제 승인 시 확정한다.

- 가용재고 = `stock` − 유효한 HELD 예약 합계
- 동시성은 `UPDATE ... WHERE stock - reserved >= qty` 조건부 갱신으로 막는다
- `StockLedger` 원장에 입고·판매·취소·반품입고·조정을 전부 기록한다
- **만료 스케줄러가 멈추면 재고가 잠긴다.** 헬스체크 대상에 포함한다

### D-027. 취소 · 반품 범위
- **취소(배송 전) + 반품(배송 후)** 을 구현하고, **부분 취소·부분 반품**을 지원한다
- **교환은 구현하지 않는다.** 회수+재배송+재고 2회 이동+차액 정산이 엮여 상태 머신이 두 배가 되고, 얻는 것에 비해 비용이 크다. 반품 후 재구매로 안내한다
- **구매확정** 개념을 둔다(수동 또는 D+7 자동). 배송완료 직후 정산하면 반품 시 회수할 수 없기 때문이며, 정산과 적립금 지급의 트리거가 된다

### D-028. 앱 3개 분리 + 앱별 독립 세션
`apps/shop` / `apps/seller` / `apps/admin` 을 독립된 Next.js 앱으로 분리한다. (D-009 의 `apps/web` 단일 구성을 **대체**)

- 커스텀 도메인을 구매해 `shop.` / `seller.` / `admin.` 서브도메인에 배포한다
- **세션은 앱별로 독립**이다. 쿠키에 `Domain` 을 지정하지 않아 서브도메인 간 공유되지 않는다
- 데모 계정은 각 앱에서 따로 발급한다
- 부수 효과(이점): 세 역할을 탭 3개로 동시에 열 수 있다. 판매자가 발송 처리하면 구매자 탭에서 즉시 확인되어 데모 시연 동선이 오히려 좋아진다
- 공통 UI 는 `packages/ui` 로 공유한다

### D-029. 할인 — 쿠폰 + 적립금
- 상품 할인(정가↔판매가) + 쿠폰(플랫폼·판매자) + 적립금
- **부담 주체를 반드시 기록한다.** 플랫폼 쿠폰·적립금은 플랫폼 부담, 판매자 쿠폰만 정산에서 차감한다. 이 구분이 없으면 정산이 단순 곱셈이 되어 도메인으로서 의미가 없다
- 적립은 **구매확정 시** 지급하고, 환불 시 **현금이 아니라 적립금으로** 복구한다
- 계산 순서와 안분 규칙은 `docs/design/pricing.md` 가 단일 출처다

### D-030. 회원 부가 기능 범위
리뷰·평점 / 위시리스트 / 최근 본 상품 / 알림 / 상품 Q&A / 판매자 팔로우 **전부 포함**.

- 리뷰는 `orderItemId` unique 로 **구매 검증을 스키마가 강제**한다. 구매하지 않은 사람은 행을 만들 수 없고 중복 리뷰도 DB 가 막는다
- 알림은 앱 내 알림센터만. 이메일·푸시는 범위 외

### D-031. 결제 수단 — 가상 카드 + 토스 병행
`PaymentProvider { authorize, capture, cancel, refund }` 인터페이스 뒤에 두 구현을 둔다.

- **가상 카드**(자체 구현): 발급 → 한도·잔액 차감 → 즉시 승인·거절. 데모 계정 발급 시 1장 자동 지급
- **토스페이먼츠**(테스트 연동): 실제 결제창 흐름
- 가상 카드를 넣는 이유:
  1. 방문자가 토스 테스트 카드번호를 찾을 필요 없이 바로 결제된다
  2. **한도 초과·잔액 부족·승인 거절·지연을 의도적으로 재현**할 수 있다. 결제 실패 시 재고 예약이 제대로 해제되는지 시연 가능하다
  3. 프로바이더가 둘이어야 추상화가 장식이 아닌 실제 설계가 된다
- 토스 테스트 환경은 정해진 테스트 카드번호만 받으므로, 가상 카드는 토스를 거치지 않는 별도 경로다

### D-032. 정산 범위
주간 정산서 생성 → 관리자 승인 → 지급완료(가상)까지 구현한다.

```
지급액 = 판매액 − 플랫폼 수수료 − 판매자 부담 쿠폰 − 반품 차감
```

- 수수료는 카테고리 기본율 + 판매자 개별율(우선)
- 실제 이체는 없다. 상태만 바뀐다
- 쿠폰 부담 주체·적립금·반품·구매확정이 여기서 전부 만난다. 도메인 설계를 보여주는 최종 지점이다

### D-033. 표시 밀도 3단계 적용 범위
`apps/shop` **전체**에 적용한다. 판매자·관리자 콘솔은 제외한다 — 관리 화면은 정보 밀도가 높은 것이 항상 정답이다.

- 데이터는 항상 전부 내려주고 **표시 여부와 레이아웃만** 바꾼다
- 간격·폰트 스케일·radius·그리드 열 수를 **CSS 변수 3세트(디자인 토큰)** 로 정의하고 모든 컴포넌트가 토큰만 참조한다
- 따라서 **디자인 토큰 시스템이 M03(초반)에 있어야 한다.** 나중에 확대하려면 만든 컴포넌트를 전부 고쳐야 한다
- 설정 저장: 로그인 사용자는 `UserPreference`, 비로그인은 localStorage

### D-034. 이미지 스토리지 — Cloudflare R2
- 전송량 요금 0원. 이미지가 많은 커머스에서 결정적이다
- S3 호환 API 라 AWS SDK 를 그대로 쓰고 이전도 쉽다
- presigned URL 로 브라우저에서 직접 업로드해 서버가 파일을 거치지 않는다
- 탈락: S3(전송량 과금), Vercel Blob(무료 한도 작고 벤더 종속)

### D-035. 데모 시드 데이터 규모
판매자 15 / 상품 800 / 카테고리 40(3단계) / 리뷰 3000 / 주문 500.

- 검색에 페이지네이션이 생기고 패싯 분포가 자연스러워지는 최소 규모다. 100개 규모면 필터를 걸었을 때 결과가 0이 되어 Meilisearch 가 아무것도 보여주지 못한다
- 이미지는 Unsplash·Pexels 무료 라이선스 사진을 카테고리별로 확보해 재사용한다
- **실제 브랜드명은 사용하지 않는다.** 상표권 문제이며 공개 저장소이므로 가상 브랜드명을 생성한다

### D-036. 마일스톤 구성 (M01 ~ M15)
`DECISIONS.md` 12장 참조.

- **M02 를 배포 파이프라인으로 앞당긴다.** 뼈대만 있는 상태에서 배포를 먼저 뚫어두면 이후 모든 마일스톤을 배포된 상태로 검증할 수 있고, 환경변수·CORS·쿠키 도메인 같은 배포 이슈를 원인 범위가 좁을 때 만난다
- 금액 계산은 M07 에서 "할인 목록을 받아 계산하는" 구조로 먼저 만들고 M11 에서 쿠폰·적립금 규칙을 꽂는다. 주문 로직을 두 번 만들지 않기 위해서다

### D-037. TASK 문서 전량 선작성 + 설계 변경 시 중단 규칙
M01~M15 의 TASK 문서 **100개를 지금 전부 작성**한다. (D-021 의 "착수 시점 생성" 방침을 **대체**)

검토한 대안과 판단:

- 처음 제안한 "마일스톤 완료 후 다음 것 작성"의 근거로 든 예시(후속 TASK 에서 Prisma 버전·인증 미들웨어 형태를 모른다)는 **틀렸다.** 버전은 앞선 마일스톤에서 확정되면 참조만 하면 되고, 인증 구조는 D-016·D-028 로 이미 정해져 있어 지금 기술할 수 있다.
- 실제로 지금 모르는 것은 **작업 분해 크기 추정의 정확도** 하나다. M01 을 실제로 수행해봐야 "반나절" 추정이 맞는지 알 수 있고, 어긋나면 이후 분할 단위가 조정된다.
- 남는 비용은 검토 부담(한 번에 100개)과 변경 전파(설계가 바뀌면 관련 TASK 를 함께 수정)뿐이며, 둘 다 "지금 쓰지 말자"의 근거는 되지 못한다.

**핵심 운영 규칙**:

```
구현 중 설계 변경이 필요한 문제 발견
  → 해당 작업 중단
  → 설계 문서(docs/design/, DECISIONS.md) 수정
  → 영향받는 TASK 문서 수정
  → 사용자 승인
  → 재개
```

코드를 먼저 고치고 문서를 나중에 맞추지 않는다. 문서가 실제와 어긋나기 시작하면 이 체계 전체가 무의미해진다.

### D-038. 공통 품질 게이트 분리
TASK 100개가 동일한 품질 게이트 표를 반복하면 100번 중복된다. `docs/tasks/QUALITY-GATES.md` 로 분리하고 각 TASK 는 이를 참조한 뒤 **예외만** 명시한다.

게이트 구성: 코드(Q1~Q7) / 화면(P1~P6) / API(A1~A5) / 데이터(S1~S4) / 문서(D1~D5).
커버리지 게이트(Q5, 80%)는 **M05 부터 적용**한다. 그 전 마일스톤은 스캐폴딩이라 의미 있는 테스트 대상이 없다.
