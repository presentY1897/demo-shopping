# 2026-09-05 세션 05

## D-219. API 실패 표현은 `packages/shared/src/api/` 가 소유하고, **보간은 조건 없이 공통 판이 한다**

HANDOFF 3.3 이 「이제 남은 것은 코드가 아니라 **소유 결정**」으로 좁혀 둔 항목을 닫는다.
TASK-0114 7.1 이 두 열린 질문(`hasCode` 를 공통 API 로 둘 것인가 · `params` 를 보간할 것인가)에
답을 냈고, 남은 것은 **어느 패키지가 이 모듈을 갖는가** 하나였다.

### 자리 — `packages/shared/src/api/`

TASK-0114 7.1 이 「올바른 자리이고, 이 TASK 의 소유 밖」이라고 적은 그 자리다. 그 TASK 가 못
간 이유는 자리가 틀려서가 아니라 **소유권** 때문이었고, 그 조건은 이제 없다.

| 후보 | 판단 |
| --- | --- |
| **`packages/shared/src/api/`** | **채택.** 이 모듈이 읽는 것이 전부 여기 있다 — `ApiClientError`(전송 실패), `ApiErrorBody`(오류 봉투), `UserFacingErrorCode`(코드 어휘). 세 앱이 이미 전부 의존한다 |
| `packages/ui` | 자기 `server-errors.ts` 머리말이 거부한다 — 컴포넌트 라이브러리에 REST 클라이언트를 끌고 들어오지 않는다 |
| 새 패키지 | 세 앱의 `package.json` 을 함께 고쳐야 한다. `@shopping/shared` 로 충분한 것을 위해 그럴 이유가 없다 |

`ApiConfigurationError` 도 함께 옮긴다. 세 앱의 `src/lib/api.ts` 에 **바이트까지 같은 3줄**로
있었고, `apiFailure` 가 그것을 `instanceof` 로 판별하므로 공통 판이 자기 앱 밖의 클래스를 알아야
하는 상태였다. 이 클래스는 "API 오리진이 설정되지 않았다"는 클라이언트 계약의 일부이므로
`api-client-error.ts` 에서 `ApiClientError` 옆에 둔다.

### 보간 — TASK-0114 의 제안을 **바꾼다**

TASK-0114 7.1 은 「보간기는 admin 에 남고, 공통 판은 `paramsOf` 를 넘겨주기만 하면 된다」로
적었다. 즉 `failureMessage(failure, messages, 보간기?)` 다. **그렇게 하지 않는다.**

**이유는 하나다 — 인자를 빠뜨리면 조용히 틀린 화면이 나간다.** 보간이 선택 인자면
`failureMessage` 호출 24곳(admin 13 · seller 8 · shop 3) 중 하나만 인자를 빠뜨려도 컴파일은
통과하고, 화면에는 **`카테고리는 {max}단계까지만 만들 수 있어요.`** 가 그대로 나간다. 새로
쓰는 호출부일수록 빠뜨리기 쉽다. 표현할 수 없게 만들 수 있는 실수를 선택 인자로 남겨 둘 이유가
없다.

**조건 없이 보간해도 다른 두 앱은 오늘 그대로다.** 보간기는 `{이름}` 패턴을 찾지 못하면 원본
문자열을 그대로 돌려주고, shop · seller 의 코드 카탈로그에는 플레이스홀더가 **하나도 없다**
(확인함 — `apps/{shop,seller}/src/messages/ko.ts` 의 `errors` 슬라이스). 즉 무조건 보간은 두
앱에서 항등 함수다.

**그리고 그것이 seller 가 남긴 지시이기도 하다.** `apps/seller/src/lib/errors.ts` 머리말은
이렇게 적어 두었다 — *"If a seller screen ever needs one, that is when the interpolation moves
somewhere both consoles can import — it should not be duplicated."* 두 콘솔이 함께 import 할
수 있는 자리가 바로 `@shopping/shared` 다.

**값이 없는 플레이스홀더는 서버 문장으로 떨어진다.** 이것도 admin 의 기존 동작 그대로다 —
`{max}` 를 사람에게 보여 주는 것보다, 그리고 자리만 지우고 "카테고리는 단계까지만" 을 만드는
것보다, 서버가 보낸 문장이 낫다.

### 함께 옮긴 것 — `ErrorMessages` · `errorMessage` · `interpolate` · `paramsOf`

`failureMessage` 가 이 넷을 쓰므로 자리를 함께 옮긴다. `apps/admin` 과 `apps/seller` 의
`src/lib/errors.ts` 는 사라진다.

- `ErrorMessages = Readonly<Record<UserFacingErrorCode, string>>` — 두 앱에 **글자까지 같은**
  타입 별칭으로 있었다. 코드가 늘면 문장도 늘어야 한다는 강제는 그대로다.
- `errorMessage(messages, code, params?)` — seller 판은 2인자였고 admin 판은 3인자였다.
  3인자 판의 세 번째가 선택이므로 seller 호출부는 그대로 컴파일된다.
- `firstFieldError` · `paramsOf` — 봉투의 `details` 에서 보간 값을 꺼낸다. `ApiFieldError` 와
  `isApiFieldError` 가 이미 `@shopping/shared` 에 있으므로 그 옆이 맞는 자리다.

`packages/ui/src/form/server-errors.ts` 안의 동명 `paramsOf` 는 **옮기지 않는다.** 그쪽은
`unknown` 을 받아 방어적으로 좁히는 컴포넌트 라이브러리의 함수이고, 이쪽은 이미 파싱된 봉투를
읽는다. 이름만 같고 하는 일이 다르다.

### 남긴 것

- **`apps/*/src/lib/api.ts` 76줄 × 3 이 `APP_ID` 한 줄만 다르다.** 이번에 클래스 하나를 덜어
  냈을 뿐 나머지는 그대로다. 합치려면 앱마다 다른 것(`APP_ID`)을 인자로 받는 팩토리가 되어야
  하고, 그것은 이 결정의 범위가 아니다. HANDOFF 3.7 로 남긴다.
### 게이트는 코드를 따라간다

`apps/admin/vitest.config.mjs` 가 `src/lib/errors.ts` 와 `src/lib/api-failure.ts` 를 **분기
100%** 로 잡고 있었다(TASK-0117 Q5). 두 파일이 사라지므로 그 항목을 그냥 지우면 게이트가 조용히
없어진다 — 임계값 글롭은 맞는 파일이 없으면 **통과**한다(확인함).

그래서 `packages/shared` 에 테스트 자리를 만들었다. 이 패키지에 스펙이 들어가는 것은 처음이다.

| 무엇 | 어떻게 |
| --- | --- |
| 스펙 위치 | `packages/shared/test/*.spec.ts` |
| 빌드에서 제외 | `tsconfig.build.json` 을 새로 두고 `build` 가 그것을 쓴다. `tsconfig.json` 은 `src` + `test` 를 담아 타입 검사와 lint 가 스펙까지 본다 — `apps/api` 와 같은 모양이다 |
| 임계값 | `packages/shared/vitest.config.mjs` 가 `api-failure.ts` · `error-messages.ts` 를 분기 100% 로 잡는다 |
| CI | 건드릴 것이 없다. `pnpm -r --if-present test:coverage` 가 새 스크립트를 집어 간다 |

**카탈로그는 픽스처를 쓴다.** 공통 판을 `apps/admin` 의 한국어 문장에 묶으면 문구 수정이 로직
실패로 보인다. 대신 `apps/admin/test/errors.spec.ts` 는 그대로 남겼다 — **플레이스홀더를 가진
카탈로그는 그것뿐**이고, 그 콘솔이 그런 문장을 갖는다는 사실은 `packages/shared` 의 어떤 검사도
알 수 없다.
