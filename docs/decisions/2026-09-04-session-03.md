## D-212. 2026-09-04 시점의 TASK 90개를 일괄 승인한다

인덱스가 실제와 어긋나 있었다. 세션 초반에 **"서로 병렬로 처리가능한거 병렬로 진행해"** 로 상시
승인을 받고 웨이브를 세 번 돌렸는데, 상태 필드는 착수 직전에 하나씩 바꾸는 방식이라 인덱스만
보면 **90개가 미승인**으로 보였다. 사용자가 "대부분 승인한 걸로 기억하는데" 라고 물어 드러났다.

| | 전 | 후 |
| --- | --- | --- |
| 승인됨 | 1 | **90** |
| 승인 대기 | 90 | **0** |

### 승인 대상은 닫힌 집합이다

**`d227905` 시점에 저장소에 있던 TASK 문서 90개**가 대상이다. 그 목록은 커밋으로 고정되어 있다.

**이것은 "앞으로 작성되는 TASK 도 승인이 필요 없다" 는 뜻이 아니다.** 당시 맥락은 *그때까지
작성해 둔 것들*에 대한 승인이었고, **새로 만드는 TASK 는 여전히 개별 승인을 받는다.** 승인을 받은
뒤에야 이 풀에 들어간다.

| | 승인 | 예 |
| --- | --- | --- |
| `d227905` 에 있던 90개 | **완료** | TASK-0018 · TASK-0019 · TASK-0032 … |
| 그 뒤 새로 만드는 TASK | **개별 승인 필요** | TASK-0117 (승인받고 착수) |

### 착수 규칙

승인된 풀 안에서, 선행 TASK 가 완료되고 진행 중인 작업과 파일이 겹치지 않으면 오케스트레이터가
골라 착수한다. 아래는 승인 여부와 별개로 **착수 전에 사용자에게 확인**한다.

- **새 TASK 를 만들어야 하는 경우** — 문서 작성 → 승인 → 구현 (`CLAUDE.md` 4장 그대로)
- 설계 문서(`docs/design/`, `DECISIONS.md`)를 바꿔야 하는 경우
- 외부 계정·비용·비밀값이 필요한 경우
- 완료 기준을 못 지킬 것이 착수 전에 보이는 경우

### 두 단계로 나눠 처리한 이유

1차로 "최초 작성 커밋 하나뿐, 수정 이력 없음" 기준을 적용해 54개를 처리했다. 그런데 남은 36개가
제외된 이유가 **내용과 무관**했다 — 전부 이미 승인된 결정(D-039~D-060, D-208)을 문서에 반영한

기준이 "내용이 확정됐는가" 를 재지 못했으므로 나머지도 승인했다.

## D-213. Storybook 은 GitHub Pages 로 배포한다

Vercel 에도 올려 두었으나 **배포마다 주소가 바뀌고 배포별 URL 은 로그인 뒤에 있다.** 이 저장소를
읽는 사람 대부분은 소유자가 아니므로 **열리지 않는 주소는 없는 것과 같다** (D-211 과 같은 판단).

| | GitHub Pages | Vercel |
| --- | --- | --- |
| 공개 | **기본값** | 배포별 URL 은 보호 |
| 주소 | `presenty1897.github.io/demo-shopping/` **고정** | 배포마다 바뀜 |
| PR 프리뷰 | 없음 | 있음 |

프리뷰가 없는 것은 손해가 아니다. 컴포넌트 검증은 CI 의 axe 스윕이 하고, 사람이 눈으로 볼 일은
머지 후로 충분하다.

`.github/workflows/storybook.yml` 이 `packages/ui` · `packages/config` 변경 시 배포한다. **토큰이
`packages/config` 에 있어** 색 하나가 바뀌면 전 스토리가 바뀌므로 두 경로를 모두 본다.

**서브패스 동작을 확인하고 `base` 오버라이드를 넣지 않았다.** Vite 의 기본 `base` 는 `/` 지만
Storybook 10 은 상대 경로로 내보낸다 — `grep -c 'src="/' storybook-static/*.html` 이 0 이다.

## D-214. `api` 는 Cloudflare 프록시를 켠다

문서에는 "Vercel·API 레코드는 DNS only" 로 적혀 있었으나 **실제 배포는 `api` 에 프록시를 켠 채
동작하고 있었다**(`cf-ray` 헤더로 확인). 문서를 실제에 맞췄다.

DNS only 규칙은 **Vercel 고유 사정**이다 — Vercel 은 자체 CDN 을 두고 도메인 검증·인증서 발급을
자기 엣지에서 하므로 앞에 프록시가 끼면 검증이 실패하거나 캐시가 이중으로 걸린다. **Render 에는
그 사정이 없고**, 프록시를 켜면 무료 인스턴스의 콜드 스타트 노출이 줄고 오리진 주소가 드러나지
않는다.

| 서브도메인 | 프록시 |
| --- | --- |
| `shop` / `seller` / `admin` → Vercel | **DNS only** |
| `api` → Render | 프록시 |
| `cdn` → R2 | 프록시 |

**SSL/TLS 모드는 `Flexible` 이면 안 된다.** Cloudflare↔Render 구간이 평문이 되고 이 API 는 JWT 를
실어 나른다. 현재 `Full`(오리진 구간 HTTPS, 인증서 미검증)이며 이는 허용이다. `Full (strict)` 로
올리려면 **Render 에서 `api.demo-shopping.com` 의 인증서 발급이 완료됐는지 먼저 확인**해야 한다 —
프록시 때문에 ACME 검증이 막혀 있을 수 있고, 그 상태로 strict 를 켜면 API 가 502 로 죽는다.

## D-215. 오류는 코드로 알리고 문장은 프론트가 소유한다

서버가 실패를 알릴 때 **한국어 문장 하나만** 보내고 있었다. 화면은 그 문장을 파싱해서 필드를
되짚고 있었고, **문구를 다듬는 순간 조용히 깨지는데 오류는 계속 표시되므로 테스트가 잡지 못한다.**

| 화면 | 우회 방법 |
| --- | --- |
| 폼 | `"slug 값이 올바르지 않습니다."` 의 **첫 토큰**을 필드명으로 사용 |
| 카테고리 관리 | 409 를 **자기가 보낸 HTTP 메서드**로 역추론 |

동시에 문구 자체도 세 등급으로 갈렸다 — 지금도 좋은 것, **내부 식별자가 새는 것**(`slug`,
`orderedIds`), **사용자가 볼 이유가 없는 것**(개발자 실수를 알리는 403 두 건).

```json
{ "error": { "code": "CATEGORY_SLUG_TAKEN", "requestId": "…",
  "details": [{ "field": "slug", "code": "DUPLICATE", "message": "…" }] } }
```

| 조각 | 답하는 질문 | 소유자 |
| --- | --- | --- |
| `field` | **어디에** 붙일까 | 서버 |
| `code` | **무슨 말을** 할까 | 서버가 코드, **프론트 카탈로그가 문장** |
| `message` | 카탈로그에 없는 코드가 왔을 때 | 서버 (대비책) |
| `requestId` | 사용자가 손쓸 수 없을 때 **QA 가 로그를 찾는 열쇠** | 서버 |

문장의 소유자가 프론트로 넘어가는 것이 핵심이다. `CLAUDE.md` 6장이 이미 **문구 하드코딩을
금지**하는데 오류 문구만 백엔드 소스에 흩어져 있었다. 이제 다른 UI 문구와 같은 자리(`messages/ko.ts`)
에서, 같은 말투로, 백엔드 배포 없이 다듬는다.

**문의 번호는 사용자가 고칠 수 없는 실패에만 보여 준다.** 검증 오류에 UUID 를 띄우면 잡음이다.
그리고 완료 기준은 "화면에 번호가 뜬다" 가 아니라 **"그 번호로 서버 로그의 해당 요청을 찾을 수
있다"** 이다 — QA 가 못 찾으면 기능이 아니다.

상세는 [TASK-0117](../tasks/M05-catalog/TASK-0117-error-contract.md).
