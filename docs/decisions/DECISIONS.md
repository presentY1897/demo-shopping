## 2. 앱 구성 · 계정 · 인증

| 항목 | 결정 |
| --- | --- |
| 앱 분리 | **독립된 Next.js 앱 3개** — `apps/shop` / `apps/seller` / `apps/admin` |
| 도메인 | 커스텀 도메인 구매 후 `shop.` / `seller.` / `admin.` 서브도메인 |
| 세션 | **앱별 독립**. refresh 쿠키 **이름을 앱별로** 나누고(`shopping_refresh_<app>`) API 가 `X-App-Id` 가 말하는 것만 읽는다. `Domain` 미지정은 유지하되 그것만으로는 부족하다 — 쿠키를 발급하는 것이 세 앱 공통의 API 오리진이기 때문 (D-218) |
| 실계정 로그인 | **Google OAuth 2.0**. 이메일/비밀번호 자체 가입은 구현하지 않음 |
| 토큰 | JWT (access + refresh), refresh 는 httpOnly 쿠키 |
| 역할 | **다대다.** `BUYER` / `SELLER_OWNER` / `ADMIN_OPERATOR` / `ADMIN_SUPER` / `DEMO_ADMIN` |
| 권한 | **퍼미션 기반 RBAC.** 역할→퍼미션은 코드 상수, 리소스 스코프(`own`/`demo`/`any`)가 "누구 것에"를 담당. **기본 거부** |
| 데모 계정 | 각 앱에서 **1인당 임시 계정 즉시 발급**. 가상 카드 1장 자동 지급 |
| 데모 만료 | 기본 **24시간** 후 계정과 생성 데이터 자동 삭제 |
| 데모 격리 | 상품 카탈로그는 **공용**, 개인 데이터(장바구니·주문·리뷰·판매자 상품)만 **격리** |
| 데모 초기 데이터 | 빈 화면을 보지 않도록 역할별로 채워서 발급. 구매자=카드·배송지·쿠폰·주문 3건, 판매자=스토어·상품 12개·주문 5건·정산 2회차 |
| 데모 데이터 조작 | 초기 데이터를 **자유롭게 수정·삭제·추가할 수 있다.** 직접 만들어보는 것이 데모의 목적 |
| 데모 권한 | `DEMO_ADMIN` = `ADMIN_OPERATOR` + 스코프 `demo`. **별도 장치 없이 권한 체계로 표현.** 데모끼리는 서로 처리 가능(실계정만 보호) |

**앱별 독립 세션의 이점**: 세 역할을 브라우저 탭 3개로 동시에 열 수 있다. 판매자가 발송 처리하면 구매자 탭에서 상태 변화를 즉시 확인할 수 있어 데모 시연에 유리하다.

## 4. 재고 · 동시성

### 동시 변경 제어 — 데이터 성격별로 다르게

| 대상 | 방식 | 이유 |
| --- | --- | --- |
| 사람이 편집하는 데이터 (카테고리·상품 정보) | **낙관적 잠금**(`version`) | 충돌을 알리고 선택하게 한다. last-write-wins 는 남의 작업을 조용히 지운다 |
| 수량·잔액 (재고·적립금·가상카드) | **행 잠금으로 직렬화** | 알릴 대상이 없다. 순서대로 처리하고 부족한 요청만 실패 |
| 트리 이동 (카테고리) | **어드바이저리 락** | 경로 재계산이 겹치면 트리가 깨진다 |

반영 시점: 트리 이동·정렬은 **즉시**(실패 시 원위치), 이름·설명 편집은 **저장 버튼**.

**id 는 재사용하지 않는다.** 결번은 그대로 둔다. 재사용하면 과거 스냅샷·로그가 엉뚱한 대상을 가리킨다.

| 항목 | 결정 |
| --- | --- |
| 차감 시점 | **예약 → 확정**. 주문서 진입 시 15분 TTL 예약, 결제 승인 시 확정 |
| 가용재고 | `stock` − 유효한 HELD 예약 합계 |
| 동시성 | `UPDATE ... WHERE stock - reserved >= qty` 조건부 갱신 |
| 이력 | `StockLedger` 원장에 입고·판매·취소·반품입고·조정 전부 기록 |
| 재고 수정 입력 | 절대값이 아니라 **조정량**(`+5 입고`). 절대값은 그 사이 팔린 수량을 덮어쓴다 |
| 만료 처리 | 스케줄러 필수. **헬스체크 대상** (멈추면 재고가 잠긴다) |

## 5. 주문 · 배송

| 항목 | 결정 |
| --- | --- |
| 주문 구조 | **2단 분할** — `Order`(결제 단위) → `SellerOrder`(배송·취소·정산 단위) → `Shipment` |
| 상태 위치 | 상태는 `SellerOrder` 에 붙는다 |

| 배송 | 운송사 API 연동 없음. 도메인·상태 전이는 실제와 동일하게 구현, 운송·추적은 **가상 처리** |
| 취소·반품 | **부분 취소·부분 반품 지원**. 항목·수량 단위로 신청 |
| 교환 | **구현하지 않음**. 반품 후 재구매로 안내 |

### 검색 엔진 선정 근거

- **채택(Meilisearch)**: 오타 보정·접두어 검색·패싯·동의어 기본 제공, 한국어 세그멘터 내장, 컨테이너 1개(~100MB)
- 탈락(PostgreSQL FTS): 한국어 형태소 분석이 약하고 랭킹·패싯을 직접 구현해야 함
- 탈락(Elasticsearch + nori): 한국어 품질은 최상이나 메모리 2GB+ 로 배포 비용 과다
- 리스크: 복합명사 분해 정확도가 nori 대비 낮음 → 실제 상품명으로 검증, 부족하면 동의어 사전 보완
- **한국어 한계와 그 대응** (TASK-0103): 조합 중 상태(「코ㅌ」)와 초성 검색(「ㅋㅌ」)은 엔진이
  다루지 못한다. 색인에 자모·초성 보조 필드를 두고 검색어도 **같은 함수로** 펴서 해결했다.
  오타 보정 쪽 한계도 실측해 남겼다(TASK-0039): 오타 허용이 글자 수로 세는데 한글 한 음절은
  자모 셋을 담은 한 글자라, 「코투 → 코트」는 어느 설정에서도 안 된다

### 이미지 스토리지 선정 근거

Cloudflare R2 는 **전송량 요금이 0원**이고 S3 호환 API 라 이전이 쉽다. S3 는 전송량 과금, Vercel Blob 은 무료 한도가 작고 벤더 종속이 강하다.

## 11. 개발 · 문서 규칙

| 항목 | 결정 |
| --- | --- |
| git 레이아웃 | `bare + worktree`. 루트에 `.bare/`, `main/`, `feature-<name>/` |
| 워크트리 격리 | `PORT_OFFSET` 로 전 포트 이동, `COMPOSE_PROJECT_NAME` 으로 컨테이너·볼륨 분리 |
| 브랜치 | `feature/<name>`, `fix/<name>`, `chore/<name>`, `docs/<name>` |
| `main` 보호 | **전면 적용.** 직접 push 금지(관리자 포함), PR 필수(승인 0), CI 4개 green 필수, 선형 히스토리, **rebase 머지만** |
| CI 트리거 | `pull_request` **와** `push: [main]` 양쪽. rebase 머지가 SHA 를 다시 쓰므로 PR 이 검사한 커밋과 main 의 커밋이 다르다 |
| 진행 순서 | **마일스톤 번호는 진행 순서가 아니다.** 각 TASK 의 `선행` 이 실제 의존. 마일스톤을 가로질러 병행한다 |
| 병행 제약 | **`schema.prisma` 를 건드리는 TASK 는 동시에 하나만.** 마이그레이션 타임스탬프가 꼬이면 rebase 로 정리되지 않는다 |
| 커밋 | Conventional Commits, 본문은 한국어 |
| 커밋·PR 링크 | **누구나 열 수 있는 링크만.** 계정 범위 세션 링크(`claude.ai/code/session_...`)는 붙이지 않는다. 커밋 트레일러는 `Co-Authored-By` 한 줄, PR 본문 끝은 저장소 안 문서로 가는 `../blob/main/...` 링크 |
| 판단 근거 | **저장소 안에 남긴다.** 대화 전체가 아니라 남아야 할 결정만 `docs/decisions/` 에 정리하고 참조한다 |
| git identity | `presenty1897 / presenty1897@gmail.com` (저장소 로컬 설정) |
| TASK 분할 | **한 TASK = 하나의 작업 목적** |
| TASK 문서 | `docs/tasks/M<NN>-<name>/TASK-<0000>-<slug>.md`. **번호는 전역 4자리 평면** |
| TASK 작성 시점 | **M01~M15 전량 선작성 완료** (100개). 마일스톤별로 나눠 쓰지 않는다 |
| 진행 방식 | TASK 문서 작성 → **사용자 승인** → 구현 |
| 승인 범위 | **`d227905` 시점의 TASK 90개는 승인 완료** (D-212) — 닫힌 집합이다. 그 안에서는 선행 완료 + 파일 미충돌이면 착수한다. **새로 만드는 TASK 는 개별 승인을 받는다** (4장 원칙 그대로). 설계 문서 변경 · 외부 계정/비용/비밀값 · 완료 기준 미달 예상도 착수 전 확인 |
| 완료 판정 | 각 TASK 의 **정량적 완료 기준**을 모두 충족 |
| 품질 게이트 | `docs/tasks/QUALITY-GATES.md` 공통 적용, 각 TASK 는 **예외만** 명시 |
| 오류 전달 | **실패는 `error.code` 로 말하고 `details[].field` 로 입력을 짚는다.** 사용자가 읽을 문장은 각 앱 카탈로그가 코드로 조회한다. 서버 문장은 카탈로그에 없는 코드를 위한 대비책으로만 남는다. 형식은 `docs/design/error-contract.md` |
| 오류 스펙 | **문장이 아니라 `code`·`field` 를 단언한다.** 문구를 바꿔도 필드 매핑과 복구 수단 선택이 유지되는지가 판정 기준 |
| 요청 번호 | 모든 오류 응답에 `requestId`(= 응답 헤더 `x-request-id`). **사용자가 고칠 수 없는 실패에만** 화면에 띄운다 |
| 테스트 기준 | **레이어별.** 순수 로직 분기 100% / 백엔드 서비스·API 라인 80% / **프론트는 수치 없이 상호작용 목록** / 계약 / E2E 시나리오. M05 부터 적용 |
| 테스트 대역 | **백엔드는 실제 PostgreSQL, 프론트는 백엔드 모킹.** 외부 시스템(토스·Google·R2·Meilisearch)만 모킹. 모킹의 대가는 **계약 게이트**(양쪽이 같은 zod 스키마를 통과)로 갚는다 |
| DB 테스트 격리 | **워커별 DB(`CREATE DATABASE ... TEMPLATE`) + 테스트 사이 `TRUNCATE`.** 트랜잭션 롤백 격리는 **쓰지 않는다** — 동시성 테스트가 불가능해지고 프로덕션 트랜잭션이 savepoint 로 강등된다 |
| TASK 분할 축 | **레이어.** 한 TASK 가 화면과 API 를 섞지 않는다. 절단면은 `packages/shared` 의 zod 스키마 |
| 커버리지 대상 | **변경분(patch coverage)**. 전체 기준은 코드가 쌓이면 무의미해진다 |
| E2E | **Playwright**, 시나리오 4개, **모든 PR 에서 실행** |
| 설계 변경 시 | **작업 중단 → 설계 문서 수정 → TASK 수정 → 승인 → 재개.** 코드를 먼저 고치지 않는다 |
| 설계 문서 | `docs/design/` 4종을 항상 최신으로 유지 |
| 언어 | 대화·사용자 노출 문구는 한국어, 코드 식별자·주석은 영어 |
