# 2026-09-04 세션 04

인계 문서 정합성 정정, Google OAuth 로그인(TASK-0021) 완료, 앱별 독립 세션의 근거 보강.

## D-218. 앱별 독립 세션은 `Domain` 미지정이 아니라 **앱별 쿠키 이름**으로 보장한다

D-028 을 **대체하지 않는다.** 결정("세션은 앱별로 독립이다")은 그대로이고, 거기 적힌 **근거가
성립하지 않는 것**을 바로잡는다.

### 무엇이 틀렸나

D-028 은 이렇게 적혀 있다 — *"쿠키에 `Domain` 을 지정하지 않아 서브도메인 간 공유되지 않는다."*

그 문장은 **쿠키를 각 앱이 발급할 때**만 참이다. 실제 구조는 그렇지 않다.

```
shop.demo-shopping.com   ─┐
seller.demo-shopping.com ─┼─→ api.demo-shopping.com   ← 쿠키를 발급하는 것은 여기다
admin.demo-shopping.com  ─┘
```

세 앱은 자기 서버에서 세션을 만들지 않는다. 전부 **같은 API** 를 부르고, 그 클라이언트는 매
요청에 `credentials: 'include'` 를 붙인다(`packages/shared/src/api/client.ts`). 그러면 API 가
내려준 refresh 쿠키는 `api.demo-shopping.com` 에 붙고 **세 앱이 전부 그것을 보낸다.** `Domain` 을
지정하지 않아도 그렇다 — 미지정은 "발급한 호스트에만" 이라는 뜻이고, 발급한 호스트가 셋 모두의
공통 API 이기 때문이다.

**로컬은 더 분명하다. 쿠키는 포트를 구분하지 않는다.** 앱 3개와 API 가 전부 `localhost` 이므로
같은 쿠키 공간을 쓴다.

그대로 두면 한 사람이 shop 에서 로그인했을 때 **seller 콘솔과 admin 콘솔도 로그인 상태**가 된다.
D-028 이 이점으로 든 "세 역할을 탭 3개로 동시에 연다" 가 정확히 불가능해진다.

### 어떻게 보장하나

**refresh 쿠키 이름을 앱별로 나눈다.**

```
shopping_refresh_shop
shopping_refresh_seller
shopping_refresh_admin
```

세 쿠키가 같은 오리진에 함께 존재하지만, API 는 **`X-App-Id` 헤더가 말하는 앱의 쿠키만** 읽고
쓴다. 그 헤더는 이미 있고(`packages/shared/src/api/app-id.ts`), 주석에 용도가 문자 그대로
**"which cookie name to set"** 이라고 적혀 있다 — 이 설계가 처음부터 예정돼 있었고 근거 문장만
낡아 있었던 것으로 보인다.

`Domain` 미지정은 **계속 유지한다.** 그것이 하는 일이 없어진 것이 아니라, 그것만으로 부족했던
것이다. 두 장치가 각각 다른 것을 막는다.

| 장치 | 막는 것 |
| --- | --- |
| `Domain` 미지정 | 쿠키가 `demo-shopping.com` 전체로 퍼지는 것 |
| 앱별 쿠키 이름 | **같은 API 오리진 안에서** 세 앱이 서로의 세션을 쓰는 것 |

### 대안과 판단

- **`Path` 로 가르기** — 불가능하다. 세 앱이 같은 API 경로를 부른다.
- **쿠키를 포기하고 앱이 refresh 를 보관** — `httpOnly` 를 잃어 XSS 에 노출된다. DECISIONS 2장의
  "refresh 는 httpOnly 쿠키" 를 뒤집어야 하므로 채택하지 않는다.
- **앱마다 API 서브도메인을 따로 두기**(`api-shop.` 등) — 쿠키 격리는 완벽해지지만 서비스가
  3배가 되고, 무료 인스턴스 750시간을 셋이 나눠 쓰게 된다.

### 어디에 적용되나

TASK-0022 가 refresh 쿠키에 적용한다. TASK-0021 의 OAuth `state` 쿠키는 **이미 같은 문제를 다른
방법으로 풀고 있다** — 이름은 하나지만 값 안에 앱을 담고, 10분 만료에 1회용이라 세션처럼 겹쳐
살아 있지 않다.
