# 2026-09-17 검색 엔진에 닿지 못할 때

## D-282 — 검색 엔진에 닿지 못한 것은 결함이 아니라 상태다: 503 · `SEARCH_UNAVAILABLE` 로 말하고 화면은 기다린다

사용자가 TASK-0143 을 승인했다. API 는 검색 엔진에 **닿지 못한** 요청을 500 `INTERNAL_ERROR` 가 아니라
**503 · `SEARCH_UNAVAILABLE`** 로 답하고, 구매자 화면은 그 코드를 실패가 아니라 **준비 중**으로 그리며
TASK-0118 의 예산(150초 · health 최대 21회) 안에서 사람 개입 없이 다시 확인한다.

**관측이 근거다.** 2026-09-17 운영 구매자 홈의 「신상품」·「인기 상품」 두 줄이 「상품을 불러오지 못했어요」로
끝났다. `GET /api/v1/search?sort=sales&limit=12` 는 500 이었고 같은 순간 `/health` 는 `database: "ok"`,
`search: "down"` 이었다 — API 는 깨어 있었고 엔진에만 닿지 못했다. 엔진(`shopping-search`)은 API 와 따로
뜨는 무료 서비스라 따로 잠들고, 디스크가 없어 따로 재기동한다. 12.7초 뒤 같은 주소는 200 에 783건을
돌려줬다. 「잠깐 뒤에 된다」를 500 으로 말하면 화면은 기다릴 일인지 포기할 일인지 가를 수 없다.

- **가르는 기준은 Meilisearch 의 `code` 다.** 연결 실패 · 시한 초과, 그리고 `code` 가 **없는** 502 · 503 · 504
  (잠든 서비스 앞의 Render 관문이 돌려주는 HTML)가 「닿지 못함」이다. Meilisearch 는 자기가 답할 때 항상
  JSON 에 `code` 를 싣는다 — 같은 503 이라도 `code` 가 있으면 엔진이 **답한** 거절이고, 키 불일치 403 ·
  잘못된 요청 400 과 함께 지금처럼 500 이다. 기다려서 풀리지 않는 것을 기다리게 하지 않는다. TASK-0119 가
  `SearchEngineError.code` 를 만든 이유와 같은 구분이고, `index_not_found` 는 그대로 빈 결과다.
- **바꾸는 곳은 공개 경로뿐이다.** `SearchIndex` 가 `SearchEngineUnreachableError` 를 던지고,
  `SearchService` 의 `search` · `suggest` 가 그것**만** 503 으로 바꾼다. `filtersFor` 는 PostgreSQL 만 읽으므로
  엔진이 자는 동안에도 200 이다. 색인 워커는 원래 오류를 그대로 본다 — 이미 실패를 삼키고 다음 틱에 다시
  한다.
- **상태에서 파생된 `SERVICE_UNAVAILABLE` 을 쓰지 않는다.** 그 코드는 「이미지 저장소가 설정되지 않았다」처럼
  기다려도 풀리지 않는 503 과 공유된다. 화면이 자동으로 다시 확인해도 되는 것은 이름이 붙은 이 코드 하나다.
- **503 에는 `Cache-Control: no-store` 를 붙인다.** 이 API 의 응답에는 캐시 헤더가 없고 `api` 는 프록시 뒤에
  있다(D-214). 몇 초 동안만 참인 답이 어딘가에 남으면, 돌아온 순간을 알려고 다시 묻는 화면이 옛 답을 읽는다.
- **화면은 실패를 말하지 않고 기다린다.** 헬스가 `ok: true` 여도 `search !== "ok"` 면 같은 백오프로 다시
  확인하고, `ok` 가 되면 상품 줄이 스스로 다시 읽는다. 예산이 끝나면 그때 실패 안내와 재시도 버튼이 나온다.
  새 상수는 없다 — `WAKE_POLICY` 를 그대로 쓴다.

폐기한 안:

- **503 을 돌려주는 순간 API 가 엔진을 깨우는 요청을 하나 더 보낸다** — 필요 없다. Render 는 요청이 서비스의
  관문에 닿는 순간 기동을 시작하고, 방금 실패한 그 검색 요청이 바로 그 요청이다. 화면이 헬스를 다시 확인할
  때마다 API 의 검색 헬스 지표가 엔진의 `/health` 를 또 부르므로 깨우는 신호는 이미 충분하다. 요청을 더
  만들면 「정확히 한 번」이라는 `SearchWarmupService` 의 약속만 흐려진다. API 안에는 재시도도 타이머도 없다.
- **DB 로 검색을 대신하는 폴백** — 정렬 · 패싯 · 한글 자모 검색을 두 벌로 만들게 된다. 엔진이 없는 몇 초를
  위해 검색의 의미가 둘이 되고, 두 벌이 어긋나는 것을 잡을 게이트가 없다.
- **엔진을 계속 깨워 두기(타이머 · 주기 핑)** — 무료 플랜의 인스턴스 시간을 쓴다(TASK-0009 R8, TASK-0101 4.8 의
  750시간 산술). 화면의 재확인은 **화면이 열려 있는 동안만**, 예산 안에서만 돈다.
- 영구 디스크 · 유료 플랜 이전 — 비용 결정이며 이 동작과 무관하게 따로 내릴 수 있다.

**열린 것.** 2026-09-17 에 엔진이 왜 내려가 있었는지는 모른다. 부팅 8분 된 API 옆에서 `down` 이었으므로
「15분 유휴로 잠들었다」로는 설명되지 않는다 — 메모리 재기동일 수도, 배포 직후의 교체일 수도 있다. Render 의
`shopping-search` 이벤트 · 로그는 소유자가 확인한다. 원인이 무엇이든 이 결정의 동작은 같고, 원인이 메모리
재기동이면 별도 TASK 다.

근거 및 검증: [TASK-0143](../tasks/M06-search/TASK-0143-search-unavailable.md).
