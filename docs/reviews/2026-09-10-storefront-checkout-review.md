# 구매자 반응 속도·결제 UX 검토

검토일: 2026-09-10 · 기준 커밋: `ffb85c7` · TASK-0124

운영 사이트 `https://shop.demo-shopping.com/`를 Chromium에서 직접 사용했다. 데스크톱 1440×1000, 모바일 크기 360×900으로 홈·상품·장바구니·배송지 이동·주문서·가상 카드 결제·주문 내역을 확인했다. 새로 발급한 데모 계정과 가상 카드만 사용했다. 구현 코드는 변경하지 않았다.

## 결론

가장 먼저 고칠 것은 결제 결과의 일치다. **결제 확정 요청이 5초에 끊겨 실패 안내가 나왔지만, 같은 주문은 주문 내역에서 결제완료였다.** 그 상태에서도 다시 결제를 권했다. 배송지 추가를 위한 정상 이동도 주문서를 취소하고, 배송 요청사항은 화면에서 입력받지만 서버에 전달하지 않는다.

속도 문제도 실측됐다. 장바구니 담기 요청은 4.66초, 주문서 진입은 약 6.87초였다. 홈에는 최근 TASK-0123에서 추가한 health 선행 대기로 1.39~1.59초가 직렬로 붙는다. 상품 카드에는 화면 크기에 비해 큰 원본 PNG가 내려온다.

## 우선순위별 발견

### R1 · P1 · 결제완료를 실패로 안내하고 재결제를 권함 — 운영 재현

- 재현: 데모 계정으로 22,000원 상품 1개와 배송비 3,000원의 주문서를 만들고, 약관 동의 후 가상 카드 결제.
- 관찰: 주문 생성 4,830ms → 결제 생성 2,961ms → 승인 4,104ms → 매입 확정 요청 5,001ms. 화면은 “결제 결과를 확인하지 못했어요. 잠시 후 다시 결제해 주세요.”와 “다시 결제하기”를 표시했다. 별도 탭의 같은 계정 주문 내역에는 해당 25,000원 주문 1건이 **결제완료**로 표시됐다. 네 단계 요청 시간 합계만 약 16.90초다.
- 근거: [공통 클라이언트](../../packages/shared/src/api/client.ts#L87)의 기본 제한은 5초이며, [capturePayment](../../apps/shop/src/lib/payment/payment-api.ts#L146)는 이를 재정의하지 않는다. [usePayment](../../apps/shop/src/lib/payment/use-payment.ts#L313)는 확정 요청 예외를 실패로 바꾸고 결과 재조회를 하지 않는다. Resource Timing에 capture 5,001ms가 남았고, 해당 요청의 정상 완료 이벤트는 없었다. 이 요청의 requestfailed 리스너는 사후 등록돼 예외 문자열 자체는 수집하지 못했다.
- 영향: 이미 결제된 사용자에게 재시도를 유도하고 실제 결과를 알 수 없게 한다. **중복 청구가 발생했다고 확인한 것은 아니다.** 재결제는 실행하지 않았다.
- 수정: 응답 단절을 결제 거절과 분리하고 “결제 결과 확인 중”으로 전환한다. 기존 주문/결제 ID로 상태를 조회하고 확정 결과로 복구한다. 확인 전 모든 결제 진입점을 잠근다. 결제 단계의 요청 제한과 서버 처리시간도 함께 조정하되, 제한 연장만으로 해결하지 않는다.
- 검증: 서버가 결제 확정 후 응답을 5초 넘게 지연하거나 응답을 유실하는 경우, 새 결제 없이 기존 완료 주문으로 복구되는 E2E.

### R2 · P1 · 배송지 추가 화면으로 이동하면 주문서가 취소됨 — 운영 재현

- 재현: 남은 시간이 약 14분인 주문서에서 “새 배송지 추가” → 배송지 관리 → 브라우저 뒤로가기.
- 관찰: 이동 시 `DELETE /checkouts/:id`가 200으로 완료됐다. 돌아오면 주문서 조회와 쿠폰 조회는 404이고 “주문서가 만료됐어요”가 표시됐다. 구매를 장바구니부터 다시 시작해야 했다.
- 근거: [useCheckout 이탈 정리](../../apps/shop/src/lib/checkout/use-checkout.ts#L215)가 컴포넌트 해제마다 주문서를 닫는다. [배송지 링크](../../apps/shop/src/components/checkout/checkout-screen.tsx#L392)는 이 이탈 규칙과 연결돼 있다. [useAddressBook 주석](../../apps/shop/src/lib/checkout/use-address-book.ts#L12)의 “돌아와도 주문서는 살아 있다”는 설명과 실제가 다르다.
- 수정: 주문서 내부 배송지 추가/편집을 제공하거나, 주소록 왕복에서 예약과 입력을 유지한다. 명시적 취소·실제 만료와 보조 화면 이동을 구분한다. 페이지 새로고침도 같은 pagehide 경로에 걸릴 수 있어 후속 검증에 포함한다(이번에 새로고침 자체는 미재현).
- 검증: 주소가 없는 사용자/있는 사용자 모두 추가·수정 후 동일 주문서로 복귀, 예약과 쿠폰·메모 유지.

### R3 · P1 · 배송 요청사항을 입력받고 버림 — 운영 요청으로 확인

- 재현: 배송 요청사항에 검토용 문장을 입력한 뒤 주문.
- 관찰: 주문 생성 body의 키는 `checkoutId`, `addressId`, `userCouponIds`뿐이며 입력 문장은 포함되지 않았다.
- 근거: [입력란](../../apps/shop/src/components/checkout/checkout-screen.tsx#L400)에 상태 연결이 없고 [placeOrder](../../apps/shop/src/lib/checkout/checkout-api.ts#L77)와 [요청 계약](../../packages/shared/src/api/orders.ts#L347)에도 전달 항목이 없다.
- 수정: 공유 계약→주문 스냅샷 저장→판매자 주문 조회까지 연결한다. 지원하지 않는 입력을 계속 받지 않는다.
- 검증: 작성한 요청사항이 주문 생성 body, 저장된 주문, 판매자 주문 상세에서 동일하게 확인됨.

### R4 · P1 · 결제 재시도 버튼이 공통 조건을 우회함 — UI 재현 + 코드 확인

- 재현: R1의 실패 화면에서 약관 동의를 해제했다. 하단 “주문하기”는 비활성이지만 “다시 결제하기”는 활성 상태였다. 재시도 요청은 실행하지 않았다.
- 근거: [Recovery 버튼](../../apps/shop/src/components/checkout/payment-section.tsx#L325)은 조건 없이 onRetry를 호출한다. [start](../../apps/shop/src/components/checkout/checkout-screen.tsx#L154)는 배송지/수단만 검사하고 동의·금액 재계산 여부를 검사하지 않는다. [ready](../../apps/shop/src/components/checkout/checkout-screen.tsx#L145)는 결과 확인 대기 상태도 제외하지 않아, 전용 재시도 버튼을 숨겨도 하단 주문 버튼을 통한 우회가 가능하다(이 갈래는 코드 확인).
- 추가 위험: [usePayment](../../apps/shop/src/lib/payment/use-payment.ts#L263)는 이미 만든 주문을 재사용한다. 그 후 배송지나 쿠폰을 수정해도 기존 주문 스냅샷에는 반영되지 않아 화면 선택과 결제 대상이 달라질 수 있다. 이 데이터 불일치 시나리오는 실제 재결제로 검증하지 않았다.
- 수정: 모든 결제 버튼이 동일한 상태/동의/금액 검증을 사용하도록 한다. 주문 생성 후 변경 가능한 항목과 기존 주문 처리 정책을 명시한다.
- 검증: 약관 해제·금액 재계산 중·결과 미확정 상태에서는 모든 진입점에서 요청 0건. 재시도 화면과 기존 주문의 금액·배송지가 일치함.

### R5 · P1 · 상품 상세 무료배송 안내와 실제 배송비 불일치 — 운영 재현

- 재현: “러스트 캔버스 툴 롤” 상세에서 “무료배송 · 평균 2~3일 소요”를 확인하고 1개 주문.
- 관찰: 상품가는 22,000원이고 장바구니·주문서 배송비는 3,000원, 결제금액은 25,000원이었다.
- 근거: [ProductInfo](../../apps/shop/src/components/products/product-info.tsx#L115)는 판매자 정책 대신 밀도에 따라 [고정 무료배송 문구](../../apps/shop/src/messages/ko.ts#L352)를 선택한다.
- 수정: 실제 판매자 배송 정책을 표시하고 무료배송 조건/기본 배송비를 일관되게 안내한다. 실제 근거가 없는 배송 예정일도 함께 검토한다.
- 검증: 유료/무료/조건부 무료배송의 상세·장바구니·주문서 표시와 계산이 일치함.

### R6 · P2 · 홈 상품 조회 앞에 무거운 상태 확인이 직렬로 붙음 — 운영 재현

- 관찰: 첫 유효 측정에서 health 1,591ms 이후 상품 조회 232/307ms. 다시 연 홈은 health가 내비게이션 후 223ms에 시작해 1,387ms 걸렸고, 상품 조회는 1,613/1,614ms에 시작해 259/334ms 걸렸다. 검색 API가 빠르게 응답해도 상품을 먼저 요청하지 못한다.
- 근거: [ApiWakeGate](../../apps/shop/src/components/api-wake-gate.tsx#L19)와 [useSection](../../apps/shop/src/lib/products/use-section.ts#L29). [health](../../apps/api/src/health/health.service.ts#L43)는 검색만이 아니라 여러 의존성/배치 상태를 종합한다.
- 최근 변경과의 관계: **TASK-0123에서 이번에 추가한 readiness gate가 이 직렬 대기를 만들었다.** 상태 패널 제거와 정상 조회 차단을 함께 묶은 부분을 수정해야 한다.
- 수정: 정상 상품 조회를 health와 병행하고, 수면/검색 미준비 시에만 복구 상태를 사용한다. 필요한 경우 구매 화면용 가벼운 준비 신호를 분리한다.
- 검증: 깨어 있는 API에서 상품 조회가 health 완료를 기다리지 않고 시작함. 수면·검색 준비 중·검색 실패의 재시도도 유지됨.

### R7 · P2 · 작은 상품 카드에 1.5~2.7MB 원본 PNG를 전송 — 운영 확인

- 관찰: 홈 앞쪽 이미지 3개가 모두 원본 1254×1254, 화면 표시 너비 약 290px, srcset 없음. CDN HEAD의 Content-Length는 각각 2,664,108 / 1,873,445 / 1,475,824 bytes로 합계 약 6.01MB다. 이 값은 파일 크기이며 캐시된 방문에서 매번 같은 양이 전송된다는 뜻은 아니다.
- 근거: [ProductCard](../../packages/ui/src/catalog/product-card.tsx#L216)는 기본적으로 원본 img를 사용하고 [SearchHitCard](../../apps/shop/src/components/catalog/search-hit-card.tsx)는 이미지 최적화용 renderImage를 제공하지 않는다.
- 영향: 모바일 네트워크에서 카드 이미지 표시가 늦고 목록 스크롤 시 추가 전송량이 커진다.
- 수정: 상품 업로드/서빙 경로에 카드용 크기와 WebP/AVIF 변환, 반응형 srcset/sizes를 제공한다. 첫 화면 이미지 우선순위와 나머지 lazy loading을 구분한다.
- 검증: 캐시 없는 모바일 측정에서 이미지 바이트와 표시 시간을 비교하고 화질도 확인한다.

### R8 · P2 · 주요 구매 버튼과 완료 안내가 실제 기능과 다름 — 운영 + 코드 확인

- 상품 상세의 [“바로 구매”](../../apps/shop/src/components/products/purchase-controls.tsx#L138)는 항상 aria-disabled이고 클릭은 preventDefault만 한다. 품절이 아닌 상품도 아무 동작이 없다. 기본 설명은 장바구니와 주문이 준비 중이라고 하지만 둘 다 동작한다(운영 확인).
- [완료 화면](../../apps/shop/src/components/checkout/checkout-screen.tsx#L249)은 “장바구니로 돌아가기” 링크를 `/`로 연결한다. 결제완료 안내는 주문 내역을 언급하지만 주문 상세 이동 버튼은 없다(코드 확인; 이번 결제는 R1 때문에 이 화면에 도달하지 못함).
- 수정: 바로 구매를 실제 주문 흐름에 연결하거나 사용할 수 없는 주 버튼을 제거한다. 준비 중 문구를 현재 기능에 맞춘다. 완료 화면은 주문 번호·금액·주문 상세 이동을 제공하고 링크 문구와 경로를 일치시킨다.

### R9 · P2 · 느린 요청과 실패를 사용자가 구분하기 어려움 — 코드 확인

- [주소록 훅](../../apps/shop/src/lib/checkout/use-address-book.ts#L25)과 [카드 조회](../../apps/shop/src/lib/payment/use-payment.ts#L235)는 조회 실패를 빈 목록으로 남긴다. 주소록은 로딩 중에도 빈 목록 안내가 보일 수 있다. 기존 데이터가 있어도 추가/발급하라는 안내로 이어진다.
- [장바구니 변경](../../apps/shop/src/lib/cart/use-cart.ts#L90)은 요청 동안 컨트롤을 잠그고 실패는 상태 유지로 끝낸다. 수량을 바꿔도 그대로인 이유를 알 수 없다. 실패 네트워크를 주입한 운영 재현은 하지 않았다.
- 수정: 조회 중/실패/실제 빈 상태를 분리하고 해당 영역의 재시도를 제공한다. 장바구니는 변경 중인 항목 표시와 실패 피드백을 제공한다. 서버 확정 금액과 임시 표시값은 구분한다.

### R10 · P2 · 모바일 주문서에서 결제 행동의 위치와 방해 요소 정리 필요 — 화면 확인

- 360×900 화면에서 주문 버튼은 문서 y≈1185px에 있어 초기 화면 밖이다. 주문 합계/결제 버튼은 고정되지 않고 긴 폼 아래에 있다. 이것만으로 기능 장애는 아니지만 금액을 확인하며 결제하기 불편하다.
- 첫 방문 밀도 안내 팝업은 결제까지 유지됐고 화면 왼쪽 일부가 잘리며 주문서 상단을 덮었다. [DensityHint](../../apps/shop/src/components/layout/density-hint.tsx#L48)는 헤더 기준 absolute/right-0/w-64 배치다.
- 수정: 모바일 하단에 최종 금액과 상태를 반영하는 결제 버튼을 제공하고 폼/오류가 가려지지 않게 한다. 상품 표현 안내는 구매 결정 화면을 방해하지 않게 범위를 제한한다.
- 검증: 360px/390px, 키보드 열림, 오류 안내, 동의/재계산/결과 확인 상태에서 레이아웃과 버튼 접근성을 점검한다.

| 상품 상세 | 클릭→장바구니 버튼 표시 약 2.85초 | 상세 API 2.28초 표본 포함 |
| 장바구니 담기 | 요청 4.66초, TTFB 4.56초 | 렌더링만으로 설명할 수 없는 응답 대기 |
| 주문서 생성 | 요청 4.39/4.51초 | 두 번 생성한 표본 |
| 주문서 진입 | 클릭→배송 요청 입력란 표시 약 6.87초 | 두 번째 진입의 행동 측정 |
| 가상 카드 결제 | 직렬 요청 합 약 16.90초 | 최종 5초에서 클라이언트 응답 대기 중단 |
| 홈 health | 1.39/1.59초 | 검색 요청 앞의 대기 |
| 홈 상품 검색 | 0.23~0.33초 | health 대기와 대조 |

Playwright request timing과 브라우저 Resource Timing을 사용했다. 초반 Date.now 기반 기록 중 시계 변동으로 음수가 나온 값, REPL 명령 대기가 섞인 행동 시간, 성공 토스트의 잘못된 exact locator 대기는 제외했다. 위 수치는 소수 시나리오의 표본이며 p95나 부하 테스트 결과가 아니다. 인위적 네트워크 감속은 적용하지 않았고 실제 휴대폰 터치·OS·토스 외부 결제창·모든 쿠폰 조합은 검증하지 않았다.

쓰기 요청의 시간이 대부분 TTFB에 몰려 있어 API/DB 경로 조사가 필요하다. 다만 브라우저 정보만으로 DB 지역·쿼리·커넥션 풀 중 무엇이 주원인인지 확정하지 않았다. 서버 trace로 주문 생성, 권한 확인, 트랜잭션, 결제 provider 호출, 응답 조립을 나눠 측정해야 한다. 권한이나 금액 검증을 제거해 시간을 줄이는 방식은 대상이 아니다.

기존 빠른 mock 기반 결제 테스트와 일반 구매 E2E만으로는 R1/R2/R3/R4를 보장하지 못한다. 예를 들어 `apps/shop/test/checkout-payment.spec.tsx`의 결과 대기 테스트는 재시도 버튼 부재를 보지만 하단 주문 버튼의 차단까지 검증하지 않는다. 이번 작업은 문서 검토로 코드 테스트를 다시 실행하지 않았으며, 운영 브라우저 재현과 코드 대조가 검증 근거다.

## 권장 후속 수정 범위

1. **결제 결과와 주문 보존:** R1/R2/R3/R4. 네트워크 단절 복구, 모든 결제 진입점 검증, 주소록 왕복, 메모 저장을 각각 검증 가능한 TASK로 나눈다.
2. **구매 안내의 정확성:** R5/R8/R9. 실제 배송비 정책, 작동하는 구매 버튼, 주문 상세로 이어지는 완료 화면, 빈 상태와 실패 구분.
3. **체감 속도와 모바일:** R6/R7/R10 및 API 구간별 측정. 홈 선행 대기 제거, 카드 이미지 경량화, 느린 쓰기 경로 최적화, 모바일 결제 버튼 배치.

후속 구현 계획에는 위 검증 시나리오를 완료 기준으로 넣는다. 특히 결제 응답을 늦춰도 완료/실패/확인 중이 실제 주문 상태와 일치하는지 운영과 유사한 지연 환경에서 확인한다.

## 추가 검토: 서버의 결제 중복 방지와 수정 경계

사용자의 추가 검토 요청에 따라 결제 생성·승인·카드 원장·주문 완료를 추적했다. 아래 두 항목은 **코드 경로와 DB 제약 검토 결과**이며 운영에서 중복 차감을 실행한 결과가 아니다. 앞선 10건에 추가해 총 12건이다.

### R11 · P1 · 이미 결제한 주문에도 새 결제를 만들 수 있는 경로

[PaymentService.start](../../apps/api/src/payment/payment.service.ts#L119)는 주문 소유자와 금액을 읽고 `assertNothingUnresolved`를 호출한 다음 새로운 결제를 만든다. [해당 검사](../../apps/api/src/payment/payment.service.ts#L560)는 `UNRESOLVED`만 센다. `READY`, `AUTHORIZED`, `PAID`는 차단 조건에 없다. 검사와 생성도 동일한 잠금/트랜잭션 안에 있지 않다. Payment의 주문 ID 인덱스는 유일 제약이 아니다.

따라서 R1 화면에서 재시도하면, 기존 주문 ID를 재사용하더라도 **새 결제 ID**를 만드는 경로로 간다. 새 결제는 READY라 승인 상태 검증도 통과할 수 있다. 가상 카드 승인은 새 결제 ID로 다시 한도를 사용한다. [markPaid](../../apps/api/src/orders/order.service.ts#L420)는 이미 처리된 판매자 주문이면 빈 결과로 끝나므로 앞선 카드 사용을 막는 장치가 아니다. 주문 생성의 checkoutId 멱등성과 결제 생성의 멱등성은 별개다.

수정은 서버까지 필요하다. 주문 단위로 기존 결제 조회와 새 시도 생성을 원자적으로 묶고, 진행 중인 결제는 기존 시도로 연결하며, 완료 주문에는 새 결제를 만들지 않는다. 명확하게 실패한 결제 이후의 정상 재시도는 허용한다. 생성 응답을 받기 전에 연결이 끊겨 결제 ID를 모르는 경우도 복구할 수 있어야 한다. 기존 `GET /payments/:id`는 ID를 이미 알고 있을 때 사용할 수 있지만, 생성 응답 유실에는 주문 단위 복구 계약 또는 멱등 생성 계약이 추가로 필요하다.

회귀 검증: 동일 주문에 순차/동시 결제 생성, PAID 이후 재시도, 생성 응답 유실 후 새로고침, FAILED 이후 수단 변경. 앞의 세 경우에는 새로운 승인/차감이 발생하지 않고 마지막 경우만 정상 재시도 가능해야 한다.

### R12 · P1 · 동일 가상 카드 승인 요청의 동시 실행도 원장에 중복 반영될 위험

[authorize](../../apps/api/src/payment/payment.service.ts#L163)는 결제 상태를 읽은 뒤 provider를 호출하고, **provider 호출 후** 결제 행을 잠가 상태를 다시 검사한다. 동시에 들어온 요청 둘이 처음에 READY를 읽으면 provider는 둘 다 실행될 수 있다.

[VirtualCardService.charge](../../apps/api/src/payment/virtual-card.service.ts#L197)는 카드 잠금으로 한도 초과는 막지만, 같은 결제 참조 `refId`가 이미 차감됐는지는 검사하지 않는다. [원장 생성](../../apps/api/src/payment/virtual-card.service.ts#L421)은 매번 CHARGE를 추가하며, 현재 마이그레이션에는 CHARGE의 동일 참조 중복을 막는 유일 제약이 없다. 두 승인 중 나중 요청이 결제 상태 재검사에서 거부되더라도 앞서 끝난 카드 트랜잭션은 그 거부로 롤백되지 않는다. 이는 토스의 실제 중복 처리 동작을 확인한 결과는 아니며, 여기서 확인한 범위는 자체 가상 카드 경로다.

수정: 결제 승인 시도 소유권을 원자적으로 확보하고, provider 측에도 같은 결제 참조를 한 번만 반영하는 멱등성을 둔다. 카드 CHARGE의 중복 방지는 취소·부분 환불처럼 정상적으로 여러 번 발생할 수 있는 다른 원장 종류와 구분한다. 외부 provider 왕복 동안 긴 DB 잠금을 유지하는 변경은 기존 설계와 충돌하므로 피한다.

회귀 검증: 두 요청을 승인 직전에서 동기화해 같은 paymentId로 동시에 실행하고, CHARGE 1건·사용액 1회 증가를 단언한다. 서로 다른 paymentId로 같은 주문을 결제하는 R11 검증도 별도로 필요하다.

### 수정 경계와 순서 보정

| 범위 | 필요한 변경 | 판단 |
| --- | --- | --- |
| 결제 결과 확인 | 화면 상태, 기존 결제 조회, 새로고침 복구 | 프론트 + 복구 계약 |
| 중복 결제/승인 | 주문 단위 결제 생성 원자성, 승인 멱등성, 카드 원장 제약 | API + DB 검토 필수 |
| 배송지 왕복 | 주문서 이탈 정책과 배송지 편집 동선 | 주로 프론트, 예약 정책 문서 대조 |
| 배송 요청사항 | 입력→공유 계약→주문 스냅샷→판매자 조회 | 프론트 + API + DB |
| 홈 대기 | 정상 상품 요청과 health 의존 분리 | 프론트 우선 |
| 쓰기 응답 지연 | 서버 구간별 trace 후 병목 수정 | 아직 원인 확정 전 |

최우선 수정은 **R1/R4/R11/R12를 묶은 결제 안전성**이다. 재결제 버튼을 숨기거나 요청 제한을 늘리는 것만으로 완료 처리하지 않는다. 다음으로 R2/R3의 주문 입력 보존을 수정하고, 구매 안내·속도·모바일을 진행한다. 서버의 기존 상태 조회 API와 주문 생성 멱등성은 재사용하되, 현재 없는 주문 단위 결제 복구 계약을 프론트에서 임의로 가정하지 않는다.

### R13 · P1 · 결제한 상품이 장바구니에 남음 — 사용자 관찰 + 코드 확인

사용자가 결제한 상품이 장바구니에서 사라지지 않는다고 보고했다. 서버의 [markPaid](../../apps/api/src/orders/order.service.ts#L420)는 재고 예약 확정·판매자 주문 상태 변경·알림을 처리하지만 구매한 장바구니 항목을 정리하지 않는다. 주문 생성에도 해당 처리가 없고, 결제 완료 프론트에도 장바구니 삭제/건수 갱신 호출이 없다. 화면 캐시만의 문제가 아니라 **서버 완료 처리 누락**이다. 이 항목은 사용자의 운영 관찰과 코드 대조로 확인했고 별도 결제를 추가 실행하지 않았다. 총 발견은 13건이다.

기존 [TASK-0049 4.5](../tasks/M07-cart-order/TASK-0049-order-create.md#45-장바구니는-비우지-않는다)는 주문 생성 단계에서는 남겨두고 “비우는 것은 결제 승인(M08)의 일”이라고 명시한다. 앞 단계에서 미뤄둔 책임이 실제 결제 단계에 연결되지 않은 것이다. 기존 구매 E2E도 완료 안내와 주문 내역까지만 확인하고 장바구니 상태는 검증하지 않는다.

수정은 결제 확정 시 서버에서 **이번 구매에 해당하는 항목/수량만 한 번 정리**하고, 화면에서는 장바구니와 헤더 건수를 재조회하는 방식이어야 한다. 실패·결과 확인 중에는 유지한다. 완료 응답을 브라우저가 못 받거나 웹훅/대사가 완료해도 서버에서 동일하게 처리해야 한다.

주의할 점은 현재 [CheckoutService.linesOf](../../apps/api/src/orders/checkout.service.ts#L143)가 예약 ID를 줄 ID로 사용하며 원래 장바구니 항목 ID를 전달하지 않는다는 것이다. 주문서 진입 시 원본 항목과 구매 수량을 추적할 계약이 필요하다. 상품 옵션 ID만으로 현재 장바구니 전체를 삭제하면 결제 중 다른 탭에서 추가한 상품까지 지울 수 있다. 재담기·수량 수정과 구분할 스냅샷/버전 정책을 정하고, 확정 재처리에도 중복 차감되지 않게 해야 한다.

검증 기준: 선택 구매만 제거·미선택 유지, 실패 시 유지, 확정 응답 유실/재처리에도 한 번만 정리, 다른 탭에서 추가·수정·삭제 후 재담은 항목 보존, 새로고침 및 헤더 건수 일치. 결제 완료 후처리의 일부이므로 R1의 결과 복구와 함께 우선 수정 범위에 포함한다.

### R14 · P2 · 장바구니·결제 흐름 썸네일 깨짐 제보 — 일부 확인, 직접 원인 조사 중

사용자가 장바구니와 결제 단계에서 썸네일이 깨진다고 보고했다. 제보 상품과 정확한 단계는 확인 중이며 이번 검토에서 해당 깨짐을 동일 조건으로 재현했다고 주장하지 않는다. 확인용 상품의 상세 API 대표 이미지 URL은 CDN HEAD 200·image/png로 응답했다. 이 한 표본이 모든 이미지의 브라우저 로딩 성공을 보장하지 않는다.

- [장바구니](../../apps/shop/src/components/cart/cart-line-row.tsx#L70)는 thumbnailUrl을 img에 그대로 전달하며 null만 분기한다. 이미지 로딩 실패 대체 처리가 없다. 서버는 ProductImage의 대표 URL을 반환한다.
- [결제 전 주문서](../../apps/shop/src/components/checkout/checkout-screen.tsx#L298)는 스냅샷 상품명과 금액만 렌더링하고 썸네일 img를 생성하지 않는다. 현재 코드에서 이 화면의 이미지 부재는 네트워크 실패와 별개다.
- [결제 후 주문 상세](../../apps/shop/src/components/mypage/seller-order-bundle.tsx#L92)는 주문 시점 thumbnailUrl을 img에 넣으며 로딩 실패 처리가 없다. 과거 스냅샷 URL 손상 가능성은 있지만 해당 주문을 확인하기 전 원인으로 확정하지 않는다.

TASK-0129에 정상 썸네일 표시, 실패 대체 UI, 실제 URL/응답/디코딩 대조와 제보 재현을 추가했다. TASK-0130은 이미지 경량화를 담당한다. 검증은 정상/null/빈 URL/404/403/손상 이미지와 장바구니→주문서→주문 상세를 모두 포함한다. 과거 주문 스냅샷을 현재 카탈로그 이미지로 임의 변경하지 않는다. 총 14건 중 이 항목의 제보 원인은 아직 미확정이다.
