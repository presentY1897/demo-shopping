# 금액 계산 · 환불 안분 규칙

> 코드보다 이 문서가 먼저다. 계산 순서가 바뀌면 여기부터 고친다. 최종 갱신: 2026-09-06

## 원칙

- 금액은 **정수(원 단위)** 로 다룬다. 부동소수 연산 금지.
- 나눗셈이 생기는 안분에서는 **원 단위 잔여를 버리지 않는다.** 마지막 항목에 잔여를 몰아 합계를 보존한다.
- 주문 시점의 계산 결과를 `OrderItem` 까지 **저장**한다. 환불 때 다시 계산하지 않는다.

## 1. 주문 금액 계산 순서

```
① 상품 금액        Σ (Variant.price × 수량)
② 상품 할인        판매자가 상품에 설정한 정가↔판매가 차액        → 항목별로 이미 반영
③ 쿠폰 할인        플랫폼 쿠폰 + 판매자 쿠폰                      → 항목별 안분
④ 배송비           SellerOrder 단위로 부과, 조건부 무료
⑤ 적립금 사용      ①−③+④ 범위 내에서 차감                       → 항목별 안분
─────────────────────────────────────────────
실결제금액 = ① − ③ + ④ − ⑤
```

`SellerOrder` 별 금액은 위 계산에서 해당 판매자 항목만 합산한 값이다.

④ 의 「조건부 무료」가 읽는 값은 `Seller.shippingFee` 와 `Seller.freeShippingThreshold` 다
(TASK-0049 4.1). 그 컬럼이 생기기 전까지 계산 엔진의 배송 정책 입력은 **아무도 채워 주지 않는
자리**였고, 그래서 주문이 계산될 수 없었다.

### 무료배송 조건은 **쿠폰까지 반영한 상품금액**으로 판정한다 (2026-09-05, TASK-0047)

이 문서가 「조건부 무료」라고만 적어 두고 어느 금액을 기준으로 재는지는 말하지 않았다. 코드를
쓰려면 정해야 하고, 세 후보가 실제로 다른 값을 낸다.

| 후보 | 판정 |
| --- | --- |
| ① 상품금액 | 쿠폰을 쓴 사람이 손해를 본다 — 할인받았는데 배송비가 붙는다 |
| ② **상품금액 − 쿠폰 할인** | 채택 |
| ③ ② − 적립금 | **적립금을 쓰면 무료배송을 잃는다.** 자기 잔액을 쓴 것이 벌이 된다 |

②를 고른 이유는 ③을 버린 이유와 같다. **쿠폰은 값을 깎는 것이고 적립금은 내는 방법이다.**
쿠폰이 붙으면 판매자가 물건 값으로 받는 돈이 실제로 줄어들므로 기준에 반영되어야 하고, 적립금은
누가 어떻게 내느냐의 문제라 물건 값을 바꾸지 않는다.

③이면 「적립금 3,000원을 썼더니 배송비 3,000원이 붙었다」가 생긴다. 그 화면은 설명할 수 없다.

이 판정은 판매자 단위다 — 배송비가 `SellerOrder` 단위로 붙기 때문이고, 3장의 「부분 취소 후 남은
금액이 무료배송 조건 미달」도 같은 기준으로 다시 잰다.

## 2. 안분 규칙

### 안분이 뭔가

**안분(按分) = 비례 배분.** 주문 전체에 걸린 할인을 각 항목이 차지하는 금액 비율대로 나눠서 붙이는 것이다.

```
주문:  A상품 30,000원  +  B상품 20,000원  =  50,000원
쿠폰:  5,000원 할인 (주문 전체에 적용)

안분 결과
  A상품 몫 = 5,000 × (30,000 / 50,000) = 3,000원   ← A의 "안분액"
  B상품 몫 = 5,000 × (20,000 / 50,000) = 2,000원   ← B의 "안분액"
```

**왜 나눠 저장하는가**: B상품만 취소하면 얼마를 돌려줘야 하나? 20,000원이 아니라 **18,000원**이다(B에 붙어 있던 할인 2,000원을 빼야 한다). 나눠두지 않으면 이 계산을 할 수 없다.

이 값을 `OrderItem.couponDiscountAmount` / `pointDiscountAmount` 에 주문 시점에 저장한다.

### 계산 방식

주문 단위로 적용된 쿠폰·적립금을 **항목(OrderItem) 단위로 나눠 저장**한다.

```
항목 안분액 = floor(전체 할인액 × 항목 상품금액 / 전체 상품금액)
잔여(= 전체 할인액 − Σ 안분액)는 상품금액이 가장 큰 항목에 더한다
```

**왜 저장하는가**: 부분 취소 시 "이 항목에 할인이 얼마나 붙어 있었나"를 즉시 알아야 한다. 환불 시점에 다시 계산하면 그 사이 쿠폰 정책이 바뀌었을 때 값이 달라진다.

**판매자 쿠폰**은 해당 판매자의 항목에만 안분한다. **플랫폼 쿠폰**은 주문 전체 항목에 안분한다.

## 3. 쿠폰 적용 규칙

계산 순서(1장)가 「③ 쿠폰 할인」이라고만 적어 두고 **어느 쿠폰이 어느 항목에 얼마나 닿는지**는
말하지 않았다. 코드를 쓰려면 정해야 하고, 아래 넷이 그 답이다 (TASK-0075).

### 3.1 기준 금액은 **쿠폰이 닿는 줄의 상품금액(①)** 이다

최소 주문금액도, 정률의 계산도 같은 금액으로 잰다.

- **다른 쿠폰의 할인 이전**이다. 쿠폰마다 「지금까지 깎이고 남은 금액」으로 재면 고른 순서에
  따라 할인액이 달라지고, 순서에 따라 달라지는 값 위에서는 「최대 할인 조합」이라는 말 자체가
  정의되지 않는다.
- **주문 전체가 아니라 닿는 줄**이다. 주문 전체로 재면 「최소 주문금액은 넘었는데 할인은
  0원」이 생긴다 — 5만원짜리 주문에 A 가게 상품 1만원이 섞여 있을 때, 최소 3만원짜리 A 가게
  쿠폰이 쓸 수 있는 것으로 보이고 실제로는 1만원에만 닿는다.

정액 쿠폰은 닿는 금액보다 클 수 없다. 3,000원짜리 항목에 5,000원 쿠폰을 쓰면 3,000원이
깎이고 끝이다 — 나머지는 아무 데도 가지 않는다.

### 3.2 범위는 넷이고, 카테고리만 **조상까지** 닿는다

| `scopeType` | 닿는 줄 |
| --- | --- |
| `ALL` | 주문의 모든 줄 |
| `SELLER` | 그 판매자의 줄 |
| `PRODUCT` | 그 상품의 줄 |
| `CATEGORY` | 그 카테고리 **또는 그 하위 카테고리**에 속한 상품의 줄 |

카테고리가 포함 관계인 이유는 그렇지 않으면 발행자가 잎 카테고리를 전부 나열해야 하고,
**나중에 추가된 잎은 아무도 다시 나열해 주지 않기** 때문이다. 판정은 `Category.path` 로 한다.

### 3.3 중복 사용 — **플랫폼 1장 + 판매자당 1장**

- 플랫폼 쿠폰끼리는 중복 불가. 부담이 한 주머니에서 나온다.
- 판매자 쿠폰은 **판매자마다 한 장**. 같은 판매자의 두 장은 그 판매자의 정산에서 두 번 빠진다.
- 적용 순서는 **플랫폼 → 판매자**다. 순서가 답을 바꾸는 것은 두 쿠폰이 같은 항목을 덮고 그
  합이 상품금액을 넘을 때뿐이고, 그때 잘리는 쪽이 판매자여야 한다 — 플랫폼이 광고한 금액이
  판매자 쿠폰 때문에 줄어든 채 사는 사람의 화면에 남는 것이 더 나쁘다.

### 3.4 최대 할인 조합은 **낼 돈이 가장 적은** 조합이다

할인액이 가장 큰 조합이 아니다. 무료배송 판정이 쿠폰까지 반영한 상품금액 기준이므로(1장),
큰 쿠폰이 그 문턱 아래로 끌어내리면 **배송비가 되살아난다.**

```
상품 10,000원 · 배송비 3,000원 · 무료배송 9,000원 이상

쿠폰 1,000원 → 상품 9,000원 → 무료배송 → 낼 돈 9,000원
쿠폰 2,000원 → 상품 8,000원 → 배송비 3,000원 → 낼 돈 11,000원   ← 할인은 더 큰데 더 낸다
```

할인액을 기준으로 고르면 아래쪽을 권하게 되고, 그 화면은 설명할 수 없다.

동점이면 **적게 쓰는 쪽**이다(남은 한 장은 다음 주문에서 쓸 수 있다). 장수까지 같으면 **플랫폼
쿠폰을 쓰는 쪽**이다 — 사는 사람이 내는 돈이 같다면 정산에서 아무도 차감되지 않는 쪽이 낫다.

보유 쿠폰이 많아 조합의 수가 상한(256)을 넘으면 **판매자별 최선을 이어 붙인** 근사로 답하고,
근사라는 사실을 응답에 싣는다.

### 3.5 장별 실제 할인액을 **저장한다**

`UserCoupon.discountAmount` 가 그 값이다. 정책으로 다시 계산할 수 없다 — 정률이면 그때의
상품금액이 필요하고, 겹쳐 덮인 장은 남은 금액까지만 깎였는데, 그 「그때」는 주문이 지난 뒤에는
아무 데도 없다. `SellerOrder.couponDiscountAmount` 도 답하지 못한다: 플랫폼 쿠폰과 판매자
쿠폰이 섞인 합계라 5장의 「판매자 부담 쿠폰 안분액」을 그것으로는 가를 수 없다.

## 4. 환불 금액 계산

취소·반품 대상 항목들에 대해:

```
환불액 = Σ (항목 상품금액 − 항목 쿠폰안분액 − 항목 적립금안분액)
       + 배송비 환불 (아래 규칙)
```

되돌리는 순서는 **적용의 역순**이다.

```
① 적립금 복구      항목 적립금안분액을 PointTransaction(RESTORE) 으로 적립금 계좌에 복구
② 쿠폰 복원        그 쿠폰이 닿은 몫이 전부 취소되면 UserCoupon 을 ISSUED 로 되돌린다
                   부분 취소면 복원하지 않는다 (재사용 시 최소주문금액 우회 방지)
③ 현금 환불        나머지를 결제 프로바이더로 환불. 부분 환불은 Refund 행으로 누적
```

**②의 「닿은 몫」은 판매자 쿠폰과 플랫폼 쿠폰이 다르다** (2026-09-07, D-225).

| 쿠폰 | 닿은 몫 | 복원 조건 |
| --- | --- | --- |
| 판매자 쿠폰 | 그 스토어의 `SellerOrder` 하나 | 그 몫의 항목이 전부 취소되면 |
| 플랫폼 쿠폰 | 이 주문의 `SellerOrder` **전부** | 그 전부가 취소되면 |

「`SellerOrder` 의 모든 항목이 취소되면」이라고만 적혀 있던 동안 플랫폼 쿠폰이 새는 자리가
있었다. 두 가게에 걸친 주문에서 한 가게만 취소하면 쿠폰이 돌아오는데, **남은 가게에는 그
쿠폰의 안분액이 그대로 붙어 있다** — 사는 사람은 쿠폰을 돌려받은 채 그 할인을 계속 누린다.

**되돌아온 적립금은 새 통이다.** 원래 어느 통에서 얼마씩 빠졌는지는 기록되지 않으므로(사용
행은 통을 가리키지 않는다) 그 통들의 남은 기간을 되살릴 방법이 없고, 정책의 유효기간을 그날부터
다시 주는 것이 할 수 있는 유일하게 정직한 일이다.

**쿠폰 안분액은 돌아오지 않는다.** 그것은 사는 사람이 낸 것이 아니라 깎인 값이고, 대신 조건이
맞으면 쿠폰 자체가 돌아온다. 그래서 「현금 환불 + 적립금 복구 = 사는 사람이 낸 것 전부」다.

**배송비 환불**

| 상황 | 처리 |
| --- | --- |
| 해당 판매자 항목 **전체** 취소 | 배송비 전액 환불 |
| **부분** 취소 후 남은 금액이 무료배송 조건 미달 | 배송비를 다시 부과 (환불액에서 차감) |
| 판매자 귀책 반품 | 배송비·반품비 모두 판매자 부담, 구매자에게 전액 환불 |
| 단순 변심 반품 | 반품 배송비를 환불액에서 차감 |

## 5. 적립금

| 시점 | 처리 |
| --- | --- |
| 적립 | **구매확정 시** `실결제금액 × 적립률` 지급 |
| 사용 | 주문 시 차감, `PointTransaction(USE)` |
| 복구 | 환불 시 **현금이 아니라 적립금으로** 복구 |
| 회수 | 구매확정 후 반품되면 이미 지급한 적립금을 회수. 잔액이 부족하면 음수 잔액을 허용하지 않고 `ADJUST` 로 기록 후 관리자 확인 대상으로 남긴다 |

## 6. 정산 금액

```
SellerOrder 정산액 = 판매액(실제 구매확정 금액)
                   − 플랫폼 수수료 (판매액 × 수수료율)
                   − 판매자 부담 쿠폰 안분액
                   − 반품으로 확정 취소된 금액
```

- 수수료율은 `판매자 개별율 > 카테고리 기본율 > 전역 기본율` 순으로 적용한다 (D-226)
  - 카테고리끼리는 **잎이 조상을 이긴다**. 조상에 건 요율은 「이 아래 전부」, 잎에 건 것은 「이것만은 다르게」다
  - 셋 다 없으면 코드의 기본 상수(10%)로 떨어진다. **0% 가 아니다** — 「설정을 안 했다」와 「받지 않기로 했다」는 다른 결정이다
  - 스토어와 카테고리를 **동시에 지정한 요율은 없다**. 그것은 네 번째 자리이고 우선순위를 다시 정해야 한다
- 적용되는 요율은 **주문 시점에 주문 항목마다 저장된다**. 정산은 그 값을 읽고 요율 표를 보지 않는다 — 요율을 올려도 어제 판 것의 수수료는 변하지 않는다 (D-227)
- 플랫폼 쿠폰과 적립금은 **플랫폼 부담**이라 차감하지 않는다. 판매자는 정가 기준으로 정산받는다
- 이 구분이 없으면 정산이 단순 곱셈이 되어 도메인으로서 의미가 없어진다

## 7. 검증

계산 로직은 단위 테스트로 다음을 보장한다.

- 안분액의 합 = 전체 할인액 (원 단위 오차 0)
- 전체 취소 시 환불액 합 = 실결제금액
- 부분 취소를 반복해 전량 취소했을 때 환불액 합 = 실결제금액
- 적립금 복구액 합 = 사용액
