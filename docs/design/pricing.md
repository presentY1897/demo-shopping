# 금액 계산 · 환불 안분 규칙

> 코드보다 이 문서가 먼저다. 계산 순서가 바뀌면 여기부터 고친다. 최종 갱신: 2026-09-05

## 원칙

- 금액은 **정수(원 단위)** 로 다룬다. 부동소수 연산 금지.
- 나눗셈이 생기는 안분에서는 **원 단위 잔여를 버리지 않는다.** 마지막 항목에 잔여를 몰아 합계를 보존한다.
- 주문 시점의 계산 결과를 `OrderItem` 까지 **저장**한다. 환불 때 다시 계산하지 않는다.

## 1. 주문 금액 계산 순서

```
① 상품 금액        Σ (Variant.price × 수량)
② 상품 할인        판매자가 상품에 설정한 정가↔판매가 차액        → 항목별로 이미 반영
③ 쿠폰 할인        플랫폼 쿠폰 + 판매자 쿠폰                      → 항목별 안분
④ 배송비           SellerOrder 단위로 부과, 조건부 무료
⑤ 적립금 사용      ①−③+④ 범위 내에서 차감                       → 항목별 안분
─────────────────────────────────────────────
실결제금액 = ① − ③ + ④ − ⑤
```

`SellerOrder` 별 금액은 위 계산에서 해당 판매자 항목만 합산한 값이다.

④ 의 「조건부 무료」가 읽는 값은 `Seller.shippingFee` 와 `Seller.freeShippingThreshold` 다
(TASK-0049 4.1). 그 컬럼이 생기기 전까지 계산 엔진의 배송 정책 입력은 **아무도 채워 주지 않는
자리**였고, 그래서 주문이 계산될 수 없었다.

### 무료배송 조건은 **쿠폰까지 반영한 상품금액**으로 판정한다 (2026-09-05, TASK-0047)

이 문서가 「조건부 무료」라고만 적어 두고 어느 금액을 기준으로 재는지는 말하지 않았다. 코드를
쓰려면 정해야 하고, 세 후보가 실제로 다른 값을 낸다.

| 후보 | 판정 |
| --- | --- |
| ① 상품금액 | 쿠폰을 쓴 사람이 손해를 본다 — 할인받았는데 배송비가 붙는다 |
| ② **상품금액 − 쿠폰 할인** | 채택 |
| ③ ② − 적립금 | **적립금을 쓰면 무료배송을 잃는다.** 자기 잔액을 쓴 것이 벌이 된다 |

②를 고른 이유는 ③을 버린 이유와 같다. **쿠폰은 값을 깎는 것이고 적립금은 내는 방법이다.**
쿠폰이 붙으면 판매자가 물건 값으로 받는 돈이 실제로 줄어들므로 기준에 반영되어야 하고, 적립금은
누가 어떻게 내느냐의 문제라 물건 값을 바꾸지 않는다.

③이면 「적립금 3,000원을 썼더니 배송비 3,000원이 붙었다」가 생긴다. 그 화면은 설명할 수 없다.

이 판정은 판매자 단위다 — 배송비가 `SellerOrder` 단위로 붙기 때문이고, 3장의 「부분 취소 후 남은
금액이 무료배송 조건 미달」도 같은 기준으로 다시 잰다.

## 2. 안분 규칙

### 안분이 뭔가

**안분(按分) = 비례 배분.** 주문 전체에 걸린 할인을 각 항목이 차지하는 금액 비율대로 나눠서 붙이는 것이다.

```
주문:  A상품 30,000원  +  B상품 20,000원  =  50,000원
쿠폰:  5,000원 할인 (주문 전체에 적용)

안분 결과
  A상품 몫 = 5,000 × (30,000 / 50,000) = 3,000원   ← A의 "안분액"
  B상품 몫 = 5,000 × (20,000 / 50,000) = 2,000원   ← B의 "안분액"
```

**왜 나눠 저장하는가**: B상품만 취소하면 얼마를 돌려줘야 하나? 20,000원이 아니라 **18,000원**이다(B에 붙어 있던 할인 2,000원을 빼야 한다). 나눠두지 않으면 이 계산을 할 수 없다.

이 값을 `OrderItem.couponDiscountAmount` / `pointDiscountAmount` 에 주문 시점에 저장한다.

### 계산 방식

주문 단위로 적용된 쿠폰·적립금을 **항목(OrderItem) 단위로 나눠 저장**한다.

```
항목 안분액 = floor(전체 할인액 × 항목 상품금액 / 전체 상품금액)
잔여(= 전체 할인액 − Σ 안분액)는 상품금액이 가장 큰 항목에 더한다
```

**왜 저장하는가**: 부분 취소 시 "이 항목에 할인이 얼마나 붙어 있었나"를 즉시 알아야 한다. 환불 시점에 다시 계산하면 그 사이 쿠폰 정책이 바뀌었을 때 값이 달라진다.

**판매자 쿠폰**은 해당 판매자의 항목에만 안분한다. **플랫폼 쿠폰**은 주문 전체 항목에 안분한다.

## 3. 환불 금액 계산

취소·반품 대상 항목들에 대해:

```
환불액 = Σ (항목 상품금액 − 항목 쿠폰안분액 − 항목 적립금안분액)
       + 배송비 환불 (아래 규칙)
```

되돌리는 순서는 **적용의 역순**이다.

```
① 적립금 복구      항목 적립금안분액을 PointTransaction(RESTORE) 으로 적립금 계좌에 복구
② 쿠폰 복원        SellerOrder 의 모든 항목이 취소되면 UserCoupon 을 ISSUED 로 되돌린다
                   부분 취소면 복원하지 않는다 (재사용 시 최소주문금액 우회 방지)
③ 현금 환불        나머지를 결제 프로바이더로 환불. 부분 환불은 Refund 행으로 누적
```

**배송비 환불**

| 상황 | 처리 |
| --- | --- |
| 해당 판매자 항목 **전체** 취소 | 배송비 전액 환불 |
| **부분** 취소 후 남은 금액이 무료배송 조건 미달 | 배송비를 다시 부과 (환불액에서 차감) |
| 판매자 귀책 반품 | 배송비·반품비 모두 판매자 부담, 구매자에게 전액 환불 |
| 단순 변심 반품 | 반품 배송비를 환불액에서 차감 |

## 4. 적립금

| 시점 | 처리 |
| --- | --- |
| 적립 | **구매확정 시** `실결제금액 × 적립률` 지급 |
| 사용 | 주문 시 차감, `PointTransaction(USE)` |
| 복구 | 환불 시 **현금이 아니라 적립금으로** 복구 |
| 회수 | 구매확정 후 반품되면 이미 지급한 적립금을 회수. 잔액이 부족하면 음수 잔액을 허용하지 않고 `ADJUST` 로 기록 후 관리자 확인 대상으로 남긴다 |

## 5. 정산 금액

```
SellerOrder 정산액 = 판매액(실제 구매확정 금액)
                   − 플랫폼 수수료 (판매액 × 수수료율)
                   − 판매자 부담 쿠폰 안분액
                   − 반품으로 확정 취소된 금액
```

- 수수료율은 `판매자 개별율 > 카테고리 기본율` 순으로 적용한다
- 플랫폼 쿠폰과 적립금은 **플랫폼 부담**이라 차감하지 않는다. 판매자는 정가 기준으로 정산받는다
- 이 구분이 없으면 정산이 단순 곱셈이 되어 도메인으로서 의미가 없어진다

## 6. 검증

계산 로직은 단위 테스트로 다음을 보장한다.

- 안분액의 합 = 전체 할인액 (원 단위 오차 0)
- 전체 취소 시 환불액 합 = 실결제금액
- 부분 취소를 반복해 전량 취소했을 때 환불액 합 = 실결제금액
- 적립금 복구액 합 = 사용액
