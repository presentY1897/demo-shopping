# 성능 예산

측정은 `lighthouse.yml` 이 CI 안에서 세운 스택을 잰다. 배포된 사이트가 아닌 이유는 그쪽이 무료 인스턴스라 **콜드 스타트가 최대 90초**이고, 그 수치를 예산으로 걸면 실패가 코드와 무관하게 오가기 때문이다 — 이 저장소는 공유 러너의 변동으로 이미 세 번 겪었다.

## 1. 화면 (TASK-0097 F1 · F2 · F8 · TASK-0098 F1)

로그인 없이 열리는 여섯 화면을 잰다: 홈 · 검색 · 카테고리 · 상품 상세 · 브랜드관 · 장바구니. 콘솔 세 앱은 로그인 뒤에 있어 Lighthouse 가 로그인 화면을 재게 되고, 그 수치는 「관리자 화면이 빠른가」에 답하지 않는다.

### 재는 방법이 두 가지고, 둘이 다른 답을 준다

Lighthouse 의 기본값은 **느리게 하지 않는다.** 빠른 기계에서 재고 「느린 전화기였다면」을 요청 그래프로 계산한다(Lantern). 다른 하나는 브라우저를 실제로 느리게 만든다(`--throttling-method=devtools`).

같은 빌드, 같은 화면, 같은 3회 중앙값인데 답이 갈린다.

| 화면 | LCP (계산) | LCP (실제로 느리게) |
| --- | --- | --- |
| 홈 | 3,035ms | **1,597ms** |
| 검색 | 3,012ms | **1,540ms** |
| 카테고리 | 3,013ms | **1,545ms** |
| 상품 상세 | 3,162ms | **1,537ms** |
| 브랜드관 | 3,012ms | **1,551ms** |
| 장바구니 | 3,011ms | **1,536ms** |

**실제로 느리게 한 쪽에서는 LCP 가 FCP 와 같은 값이다** — 즉 가장 큰 글은 화면에 처음 뭔가가 나타나는 그 순간 함께 그려진다. 그럴 수밖에 없는 것이, 그 글은 **정적으로 미리 만들어진 HTML 안에 이미 들어 있다**(`curl` 로 받아 보면 있다). 계산하는 쪽은 그 글을 그리기 전에 스크립트 그래프를 통과해야 한다고 보고 2.5초를 더 얹는다.

**F1 은 실제로 느리게 한 값으로 판정한다.** 사람이 겪는 것이 그쪽이기 때문이다. 여섯 화면 모두 1.54~1.60초이고 기준 2.5초 안이다.

### 그런데 게이트는 계산하는 쪽으로 건다

공유 러너에서 브라우저를 실제로 느리게 하면 값이 기계 사정에 흔들린다. 계산하는 쪽은 회차 간 편차가 작아 **회귀를 잡는 데 낫다** — 게이트가 답해야 하는 질문은 「지금 몇 초인가」가 아니라 「어제보다 나빠졌는가」다.

| 지표 | 예산 | 강도 | 지금 값 (계산) |
| --- | --- | --- | --- |
| Cumulative Layout Shift | 0.1 이하 | 실패 | 0.000~0.002 |
| 접근성 점수 | 0.9 이상 | 실패 | 0.96~1.00 |
| Speed Index | 3.4초 이하 | 실패 | 0.76~0.91초 |
| Largest Contentful Paint | 3.4초 이하 | 실패 | 3.01~3.16초 |

LCP 예산이 기준(2.5초)이 아니라 3.4초인 것은 **재는 방법이 다르기 때문**이지 봐주는 것이 아니다. 계산하는 쪽의 지금 값이 3.0초이므로 3.4초는 0.4초의 여유이고, 하이드레이션 비용이 늘면 곧바로 빨개진다.

### 고친 것 — 개선 전후 (F8)

레이아웃 이동은 네 군데였고 넷 다 **늦게 나타나는 것에 자리를 안 잡아 둔 것**이었다.

| 화면 | 전 | 후 | 무엇이 밀고 있었나 |
| --- | --- | --- | --- |
| 홈 | 0.223 | **0.000** | 데모 안내(197px)와 카테고리 바로가기(116px)가 마운트 뒤에 나타났다 |
| 검색 | 0.366 | **0.000** | Suspense 대기 화면이 한 줄짜리 글이라 바닥글이 화면 안(317px)에 있다가 4,300px 아래로 갔다 |
| 카테고리 | 0.097 | 0.002 | 같은 대기 화면 |
| 브랜드관 | 0.020 | 0.002 | 같은 대기 화면 |

**주석이 사실과 반대였던 자리가 둘 있었다.** 카테고리 바로가기는 「자리표를 두면 이름이 도착할 때 화면이 움직인다」고 적혀 있었지만 재 보니 자리표가 **없어서** 움직였고, 검색 화면은 「대기 화면은 워크스페이스가 쓰는 것과 같은 스켈레톤」이라고 적혀 있었지만 실제로는 한 줄짜리 글이었다.

LCP 쪽에서 가장 큰 항목은 **머리말의 첫 방문 안내**였다. 밀도 토글을 설명하는 작은 상자인데, 절대 배치라 자리는 밀지 않지만 마운트 뒤에 그려지느라 **여섯 화면 전부에서 「가장 큰 것이 그려진 시각」을 그 상자가 정하고 있었다.**

| 화면 | 전 (계산) | 후 (계산) |
| --- | --- | --- |
| 카테고리 | 4,329ms | **3,013ms** |
| 상품 상세 | 4,505ms | **3,162ms** |

### 어떻게 고쳤나 — 첫 페인트 전에 정한다

넷 다 같은 모양이다. 「이 방문자에게 보여야 하는가」를 아는 곳이 브라우저의 저장소뿐이라 서버는 알 수 없고, 그래서 마운트 뒤에 그렸다.

이 저장소에는 이미 그 문제의 답이 있었다 — 밀도가 쓰는 `DensityScript` 는 첫 페인트 **전에** 도는 인라인 스크립트로 `<html>` 의 속성을 고친다. 같은 장치를 세 군데에 더 썼다: 표시는 스크립트가 붙이고, 보일지는 CSS 가 정하고, React 는 상자를 늘 그린다.

**테스트가 묻는 것도 그 표시로 바꿨다.** jsdom 에는 스타일시트가 없어 `queryByText` 로는 「안 보인다」를 물을 수 없다 — 보이는지를 실제로 정하는 값을 직접 묻는다. 스크립트 자체는 문자열로 내보내 테스트에서 **실행해 본다**(`density-script.spec.ts` 가 먼저 쓰던 방식이다).

## 2. 서버 (TASK-0097 F3 · F4 · F5)

`*-performance.spec.ts` 가 실제 데이터베이스에 대고 잰다. **시간과 문장 수를 함께 잰다** — 시간만 재면 「줄마다 조회가 하나씩 느는 구현」이 작은 데이터에서 통과하고, 그 구현은 열 배에서 무너지는데 그때는 이미 운영 중이다.

| 대상 | 예산 |
| --- | --- |
| 목록·상세 API p95 | 300ms |
| 관리자 대시보드 지표 p95 (주문 500건) | 500ms |
| 목록 API 문장 수 | 데이터 양과 무관 (기울기 0) |

### 인덱스가 질의를 받는가 (F5)

`EXPLAIN` 으로 계획을 확인한다. **표를 크게 만들어 놓고 잰다** — 500행짜리 표에서는 순차 스캔이 옳은 계획이라, 작은 픽스처로 재면 그 검사는 인덱스가 아니라 **픽스처를 재는 것**이 된다. 주문 묶음 검사는 2만 행을 넣고 잰 뒤 인덱스를 지우고 다시 돌려 순차 스캔으로 떨어지는 것까지 확인했다.

## 3. 번들 (TASK-0097 F6)

`scripts/bundle-budget.mjs` 가 `build` job 안에서 잰다. 재는 것은 **어느 화면을 열든 반드시 내려가는 공통 청크**다 — 화면 하나가 무거운 것은 그 화면의 문제지만, 공통분이 무거우면 모든 화면이 무겁다.

| 앱 | gzip | 예산 |
| --- | --- | --- |
| shop | 166.4 KB | 200 KB |
| seller | 166.0 KB | 200 KB |
| admin | 166.0 KB | 200 KB |

이 Next 는 크기를 출력하지 않아(Turbopack) `build-manifest.json` 을 직접 읽는다. 매니페스트 모양이 바뀌면 **던진다** — 조용히 0 을 답하면 예산이 늘 통과하고, 그때부터 이 게이트는 있으나 마나다.

## 4. 정합성 (TASK-0097 F7)

`GET /admin/consistency` 가 캐시 컬럼 일곱 개를 원본과 대조한다. **검출만 하고 고치지 않는다** — 원인을 모르는 채 값을 고치면 다음에 같은 자리가 또 어긋나도 배치가 조용히 덮어써 버린다.
