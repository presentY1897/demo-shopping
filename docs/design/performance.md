# 성능 예산

측정은 `lighthouse.yml` 이 CI 안에서 세운 스택을 잰다. 배포된 사이트가 아닌 이유는 그쪽이 무료 인스턴스라 **콜드 스타트가 최대 90초**이고, 그 수치를 예산으로 걸면 실패가 코드와 무관하게 오가기 때문이다 — 이 저장소는 공유 러너의 변동으로 이미 세 번 겪었다.

## 1. 화면 (TASK-0097 F1 · F2 · TASK-0098 F1)

로그인 없이 열리는 여섯 화면을 잰다: 홈 · 검색 · 카테고리 · 상품 상세 · 브랜드관 · 장바구니. 콘솔 세 앱은 로그인 뒤에 있어 Lighthouse 가 로그인 화면을 재게 되고, 그 수치는 「관리자 화면이 빠른가」에 답하지 않는다.

| 지표 | 예산 | 강도 |
| --- | --- | --- |
| Cumulative Layout Shift | 0.1 이하 | 실패 |
| 접근성 점수 | 0.9 이상 | 실패 |
| Speed Index | 3.4초 이하 | 실패 |
| Largest Contentful Paint | 2.5초 이하 | **경고** |

### LCP 만 경고인 이유

지금 홈의 LCP 는 **3.0초**이고 기준을 넘는다. 그런데 같은 실행의 Speed Index 는 **0.76초**다 — 즉 **사람 눈에는 0.76초에 화면이 완성되고**, LCP 3.0초는 그 뒤 하이드레이션이 같은 `<h1>` 을 다시 칠하면서 갱신된 값이다. 정적으로 프리렌더된 문서에 그 제목이 이미 들어 있고(HTML 을 그대로 받아 보면 있다), 화면은 그때 이미 그려져 있다.

그래서 두 가지를 함께 둔다.

- **Speed Index 를 실패로** 건다. 사람이 실제로 보는 시점이 늦어지면 그것은 회귀다.
- **LCP 를 경고로** 두고 숫자를 남긴다. 지금 이 값을 실패로 걸면 첫날부터 빨간 게이트가 되고, 몇 번 반복되면 사람이 그 색을 안 믿는다 — 그것이 게이트를 없애는 가장 흔한 방법이다.

**경고는 면제가 아니다.** 줄여야 할 것은 하이드레이션 비용이고(TTI 5초, 요청 53개), 그것을 줄이면 LCP 는 따라 내려온다. 실패로 올리는 시점은 그 작업이 끝난 뒤다.

## 2. 서버 (TASK-0097 F3 · F4 · F5)

`*-performance.spec.ts` 가 실제 데이터베이스에 대고 잰다. **시간과 문장 수를 함께 잰다** — 시간만 재면 「줄마다 조회가 하나씩 느는 구현」이 작은 데이터에서 통과하고, 그 구현은 열 배에서 무너지는데 그때는 이미 운영 중이다.

| 대상 | 예산 |
| --- | --- |
| 목록·상세 API p95 | 300ms |
| 관리자 대시보드 지표 p95 (주문 500건) | 500ms |
| 목록 API 문장 수 | 데이터 양과 무관 (기울기 0) |

## 3. 정합성 (TASK-0097 F7)

`GET /admin/consistency` 가 캐시 컬럼 일곱 개를 원본과 대조한다. **검출만 하고 고치지 않는다** — 원인을 모르는 채 값을 고치면 다음에 같은 자리가 또 어긋나도 배치가 조용히 덮어써 버린다.
