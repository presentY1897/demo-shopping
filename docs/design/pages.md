# 페이지 구조

> 현재 유효한 화면 목록과 라우팅만 담는다. 최종 갱신: 2026-09-03

## 앱 구성

세 역할을 **독립된 Next.js 앱 3개**로 분리한다. 세션도 앱별로 독립이다.

| 앱 | 도메인 | 대상 | 레이아웃 |
| --- | --- | --- | --- |
| `apps/shop` | `shop.demo-shopping.com` | 구매자 | 커머스 (헤더 + 푸터) |
| `apps/seller` | `seller.demo-shopping.com` | 판매자 | 콘솔 (사이드바) |
| `apps/admin` | `admin.demo-shopping.com` | 관리자 | 콘솔 (사이드바) |

- 쿠키는 각 서브도메인 한정(`Domain` 속성 미지정)이라 세션이 섞이지 않는다.
- **세 역할을 브라우저 탭 3개로 동시에 열 수 있다.** 판매자가 발송 처리하면 구매자 탭에서 상태가 바뀌는 걸 그 자리에서 확인할 수 있다. 데모 시연의 핵심 동선이다.
- 공통 UI 는 `packages/ui` 에서 공유한다.

## 표시 밀도 3단계

`apps/shop` **전체**에 적용한다. 판매자·관리자 콘솔은 제외한다 — 관리 화면은 정보 밀도가 높은 것이 항상 정답이다.

| 단계 | 성격 | 레퍼런스 |
| --- | --- | --- |
| 1 · 미니멀 | 이미지 중심, 넓은 여백, 정보 최소 | SSENSE, 아페쎄 |
| 2 · 표준 | 브랜드·할인율·평점·색상칩 | 무신사, 29CM |
| 3 · 맥시멀 | 리뷰수·판매량·배지·잔여재고·빠른담기 | 쿠팡, 알리익스프레스 |

**데이터는 항상 전부 내려주고 표시 여부와 레이아웃만 바꾼다.** 간격·폰트 스케일·radius·그리드 열 수를 CSS 변수 3세트(디자인 토큰)로 정의하고 모든 컴포넌트가 토큰만 참조한다. 컴포넌트는 한 벌로 유지된다.

`<html data-density="1|2|3">` 하나로 전환된다. 토큰 정의는 `packages/config/tailwind/` 에 있다 — `tokens.css`(색·타이포·radius·그림자·컨트롤 크기), `density.css`(밀도 3단계 × 뷰포트 3구간).

| 변수 | 역할 |
| --- | --- |
| `--space-unit` | Tailwind 간격 스케일의 단위. `p-4` = `calc(var(--space-unit) * 4)` |
| `--font-scale` | 타이포 스케일 배율. `--text-*` 전체에 곱해진다 |
| `--radius-scale` | 모서리 반경 배율 |
| `--density-cols` | 상품 그리드 열 수. `grid-density` 유틸리티가 읽는다 |
| `--space-gutter` | 페이지 좌우 여백. `--space-unit` 에서 파생, 뷰포트별로 배수가 다르다 |
| `--touch-min` | **44px 고정.** 밀도와 무관 |

**표시 여부는 토큰이 아니라 컴포넌트가 정한다.** 토큰은 공간과 크기만 담당한다.

설정 저장: 로그인 사용자는 `UserPreference`, 비로그인은 localStorage(`shopping.shop.density`). 첫 페인트 전에 인라인 스크립트가 저장값을 `data-density` 에 적용하므로 새로고침 시 깜빡임이 없다.

**로그인하면 localStorage 값을 서버로 승격한다.** 클라이언트가 로그인 직후 저장돼 있던 값을 `PATCH /api/v1/me/preferences` 로 한 번 올리고, 그때부터 **서버 값이 단일 출처**이며 localStorage 는 첫 페인트용 캐시로만 남는다. 승격이 없으면 비로그인 상태에서 고른 밀도가 로그인하는 순간 조용히 초기값으로 되돌아간다.

서버는 승격과 일반 변경을 **구분하지 않는다.** 구분하려면 클라이언트가 보낸 플래그를 믿어야 하는데, 믿어도 결론은 "마지막에 쓴 쪽이 이긴다" 로 같다. 그래서 엔드포인트도 하나다. 설정 행은 **첫 저장에서 만들어지고**, 행이 없는 계정은 조회 시 기본값(`STANDARD`)을 받는다 — 조회가 행을 만들면 "내 설정 보기" 가 쓰기가 된다.

**쿠키를 쓰지 않는다.** 쿠키라면 서버가 값을 알고 렌더할 수 있어 깜빡임 문제는 같이 풀리지만, 쿠키를 읽는 페이지는 정적 렌더에서 요청 시점 렌더로 내려간다. `apps/shop` 의 홈은 콜드 스타트(최대 90초) 동안 방문자가 보는 유일한 화면이고 그래서 정적으로 미리 만들어 둔 것이므로(TASK-0101), 표시 설정 하나를 위해 그것을 되돌릴 수 없다. CDN 캐시가 밀도별로 3벌이 되는 문제도 따라온다.

토글 UI 는 헤더에 있다 — 데스크톱은 세 단계를 펼친 세그먼트, 모바일은 현재 단계를 아이콘으로 보여 주는 버튼 하나에 팝오버다. 한 번도 밀도를 고른 적이 없는 방문자에게는 토글 옆에 1회 안내가 뜨고, 토글을 쓰거나 닫으면 다시 나오지 않는다.

## 공통 UI 컴포넌트

세 앱이 공유하는 기본 컴포넌트는 `@shopping/ui/components` 한 곳에 있다. 스타일은 전부 디자인 토큰이고, 접근성 동작은 **Radix Primitives** 에 맡긴다 (D-056).

| 묶음 | 컴포넌트 | 기반 |
| --- | --- | --- |
| 액션 | `Button` · `IconButton` · `Link` | 직접 (플랫폼 기본 동작으로 충분) |
| 폼 | `Input` · `Textarea` | 직접 |
| 폼 | `Select` · `Checkbox` · `RadioGroup`/`Radio` · `Switch` | Radix |
| 표시 | `Badge` · `Tag` · `Divider` | 직접 |
| 표시 | `Avatar` | Radix (이미지 로드 상태) |
| 오버레이 | `Modal` · `Drawer` | Radix Dialog |
| 오버레이 | `Tooltip` · `Popover` | Radix |
| 알림 | `ToastProvider` / `useToast()` | Radix Toast |
| 구조 | `Tabs` · `Accordion` | Radix |
| 데이터 상태 | `DataList` · `EmptyState` · `ErrorState` · `Skeleton` · `ErrorBoundary` | 직접 |
| 데이터 표시 | `Table` · `TableToCards` · `Pagination` · `useInfiniteScroll` | 직접 |
| 레이아웃 | `Card` · `Grid` | 직접 |
| 포맷터 | `formatMoney` · `formatDate` (`@shopping/ui/format`) | `Intl` |

- **Radix 는 동작만, 스타일은 0줄을 쓴다.** 포커스 트랩·ARIA·키보드 탐색·팝업 위치처럼 직접 구현하면 품질이 안 나오는 부분에만 쓴다.
- **`variant` / `size` 는 prop 이고 값 목록은 배열로 export 한다** (`BUTTON_VARIANTS` 등). 스토리(TASK-0104)가 내부를 뜯지 않고 상태를 나열할 수 있어야 한다.
- **`'use client'` 는 컴포넌트 파일이 각자 선언한다.** 브라우저 동작이 필요 없는 것(`Button`·`Input`·`Textarea`·`Badge`·`Tag`·`Divider`)은 서버 컴포넌트로 렌더된다.
- **`packages/ui` 에는 한국어가 없다.** 문구가 필요한 자리(`IconButton.label`, `Modal.closeLabel`, `ToastProvider.regionLabel`, `Tag.removeLabel`)는 prop 으로 받는다. `IconButton.label` 과 `Tag.removeLabel` 은 타입으로 강제된다.
- **터치 타깃 44px 하한은 컴포넌트가 기억하지 않는다.** `h-control-*` / `size-control-*` / `touch-target` / `min-h-touch` 가 토큰 안의 `max()` 로 보장한다. 체크박스·라디오는 눈에 보이는 상자(20px)와 누르는 영역(44px)을 분리한다.
- **목록은 `DataList` 로 감싼다.** `loading` · `empty` · `error` 가 기본값 없는 필수 prop 이라 빈 상태를 빠뜨리면 컴파일되지 않는다.
- **`Grid` 의 열 수는 `--density-cols`** 에서 온다. 아래 밀도 × 뷰포트 매트릭스가 유일한 출처이고 컴포넌트는 숫자를 갖지 않는다.
- **`Card` 내부는 컨테이너 쿼리**(`@container/card`)다. 같은 카드가 1열과 6열에서 서로 다르게 배치되며, 뷰포트는 관여하지 않는다.
- **`Table` 은 가로 스크롤을 자기 래퍼 안에 가둔다.** 첫 열은 `<th scope="row">` 이면서 `position: sticky` 이고, 래퍼는 키보드로 도달 가능한 이름 있는 region 이다.
- 전 컴포넌트를 한 화면에 나열한 **개발 전용** 페이지가 세 앱 모두에 있다 (`/components`, 프로덕션 404). `/tokens` 와 함께 TASK-0104 의 Storybook 이 이어받은 뒤 제거한다 (D-206).

### 공통 셸 (TASK-0018)

모든 shop 화면이 하나의 셸 안에 들어간다. 헤더는 **한 줄**이고 뷰포트 밴드에 따라 형태가 셋이다.

| 밴드 | 헤더 구성 |
| --- | --- |
| ~767 | 햄버거 · 로고 · 밀도 버튼 · 장바구니 · 마이페이지 |
| 768~1279 | 여기에 검색창이 붙는다 (카테고리는 여전히 햄버거 안) |
| 1280~ | 햄버거 대신 카테고리를 펼친다 |

- 768px 에서 카테고리와 검색창을 한 줄에 같이 두면 헤더가 두 줄로 접힌다. 그래서 태블릿 구간까지는 메뉴 시트를 쓴다.
- **세 형태의 높이는 `h-control-lg` 로 같다.** 서버는 방문자의 뷰포트를 모르므로 모바일 퍼스트에 맞춰 좁은 형태를 렌더하고, 데스크톱 방문자는 하이드레이션 시점에 넓은 형태로 교체된다. 높이가 같아야 그 교체가 본문을 밀지 않는다(실측: 3뷰포트 × 3밀도 9조합에서 서버 렌더 높이 = 하이드레이션 후 높이).
- 모바일 네비게이션은 **바텀시트**(Radix Dialog)다. 열려 있는 동안에만 내용이 마운트되므로 카테고리 목록이 DOM 에 두 벌 있지 않다.
- 헤더 첫 탭 정지는 **본문 바로가기** 링크이고, `main` 은 `tabindex="-1"` 이라 포커스가 실제로 본문으로 넘어간다.
- 푸터에는 링크가 없다. 이용약관·고객센터 같은 목적지가 아직 없고, 전부 같은 "준비 중" 으로 가는 링크 여섯 개는 모든 화면에 죽은 탭 정지 여섯 개를 더하는 것과 같다.

라우트 상태는 셸 안에서 셋이다 — `loading.tsx`(스켈레톤), `not-found.tsx`, `error.tsx`(세그먼트 재시도). 링크 자신도 눌린 직후 진행 표시를 낸다(`useLinkStatus`).

**헤더가 링크하는 화면 중 넷은 아직 껍데기다** — `/search` · `/categories/[slug]` · `/cart` · `/mypage`. 죽은 링크나 비활성 컨트롤 대신 실제 라우트를 두고, 각 마일스톤 TASK(0041 · 0042 · M07 · M04)가 파일을 그대로 대체한다.

### 상품 이미지 업로드 규약 (TASK-0033)

상품 이미지는 **브라우저가 R2 로 직접 올린다.** 파일 본문이 API 를 거치지 않는다 — 무료 인스턴스는
메모리 512MB 이고 5MB 이미지 몇 장이 동시에 지나가는 것만으로 죽는다.

```
파일 선택 → 클라이언트 축소(긴 변 2,000px) → presign 요청 → R2 로 직접 PUT → 상품 저장 시 URL 기록
```

| 항목 | 규약 |
| --- | --- |
| 대표 이미지 | **배열의 첫 번째.** 별도 플래그가 없다 — 서버가 요청 배열의 인덱스를 `sortOrder` 로 저장하고 모든 조회가 그 순서로 읽는다. "대표로 지정"은 맨 앞으로 옮기는 조작이다 |
| 순서 변경 | **버튼**(`앞으로`·`뒤로`·`대표로`). 드래그 핸들은 키보드로 조작할 수 없어 P4 를 통과하지 못한다. 드래그 앤 드롭은 **파일을 떨어뜨리는 쪽**에만 있다 |
| 파일 선택 | 점선 패널은 진짜 `<input type="file">` 의 **label** 이다. Tab 으로 닿고 Enter·Space 로 열린다 |
| 축소 | 긴 변 2,000px 초과일 때만. 형식은 원본 유지, 축소본이 원본보다 크면 원본을 보낸다 |
| 동시 업로드 | **3개.** 오리진당 커넥션 6개를 다 쓰면 presign 이 업로드 뒤에 줄을 선다 |
| 실패 | **항목 단위.** 다른 이미지는 그대로 저장에 실릴 수 있다. 재시도는 presign 부터 다시 한다 — URL 은 5분 만료다 |
| 빼기 | 갤러리에서만 뺀다. **R2 객체는 지우지 않는다** — 삭제 엔드포인트가 아직 없다 |
| 오류 문장 | 우리 API 의 실패는 `error.code` 로 카탈로그에서 찾고, 저장소의 실패는 다섯 이유로 좁힌다. 저장소는 요청 번호가 없으므로 **번호를 보여 주지 않는다** |

### 콘솔 공통 셸 (TASK-0019)

판매자·관리자 두 콘솔은 **같은 셸**(`@shopping/ui/console` 의 `ConsoleShell`)을 쓰고 메뉴만 다르다. 메뉴 정의는 각 앱이 소유하고 셸은 렌더만 한다. M04 에서 권한 필터가 이 정의 앞에 붙는다.

```
┌──────────┬───────────────────────────────────┐
│ 콘솔 이름 │ [토글] 현재 위치      알림 · 계정  │  상단바 (h-control-lg, sticky)
│          ├───────────────────────────────────┤
│ 사이드바  │ PageHeader (제목 · 액션 · 필터)     │
│  240px   │ 화면 내용                          │  main#console-main
└──────────┴───────────────────────────────────┘
```

| 폭 | 사이드바 | 상단바 토글이 하는 일 |
| --- | --- | --- |
| 1024~ | 고정 컬럼 240px | 접고 펴기 (접으면 본문이 폭을 되찾는다) |
| ~1023 | 없음 | 왼쪽 **시트**를 연다 (Radix Dialog) |

- 두 형태 중 **하나만 마운트**한다(D-055). CSS 로 숨긴 두 벌이 아니다.
- 사이드바는 `position: fixed` 이고 본문 래퍼는 `lg:pl-60` 을 **항상** 갖는다. 미디어 쿼리는 JS 없이 첫 페인트에 맞으므로, 하이드레이션에서 사이드바가 붙어도 본문이 움직이지 않는다(실측: JS 끈 렌더와 하이드레이션 후의 `main` 왼쪽 좌표가 3뷰포트 × 2앱 전부 동일, CLS 0).
- **접기는 아이콘 레일이 아니라 완전히 숨기는 것**이다. 항목마다 글리프를 만들어도 "정산 관리"와 "수수료 설정"을 그림으로 구별시키는 것이 텍스트보다 낫지 않다. 접힘 상태는 클라이언트 네비게이션 사이에만 유지되고 새로고침하면 펼친 상태로 돌아온다.
- **밀도 토글은 어디에도 없다**(D-033). 콘솔은 2단계 고정이다.
- 첫 탭 정지는 **본문 바로가기**이고 `main` 은 `tabindex="-1"` 이라 포커스가 실제로 본문으로 넘어간다. 사이드바 항목이 13개인 콘솔에서는 shop 보다 더 필요하다.
- 상단바의 **현재 위치**는 활성 메뉴 항목의 라벨이다(`<p>`). 화면의 `<h1>` 은 `PageHeader` 가 갖는다 — 루트 레이아웃은 상세 화면의 주문 번호를 알 수 없다.
- 알림·계정은 **자리만** 있고, 비활성 버튼이 아니라 어느 마일스톤이 채우는지 말하는 팝오버다. M11 · M04 가 대체한다.

**사이드바 구성** — 경로는 위 표(2장·3장)가 출처이고, 절 제목만 이 셸의 분류다. `/login` 과 상세·하위 경로는 메뉴에 넣지 않는다.

| 앱 | 절 | 항목 |
| --- | --- | --- |
| seller | – | 대시보드 |
| | 판매 | 상품 관리 · 주문 관리 · 취소·반품 |
| | 고객 | 리뷰 관리 · 문의 관리 |
| | 정산·설정 | 쿠폰 · 정산 내역 · 스토어 설정 |
| admin | – | 대시보드 |
| | 운영 | 회원 관리 · 판매자 관리 · 상품 관리 · 주문 관리 · 클레임 관리 · 신고 처리 |
| | 카탈로그 | 카테고리 관리 · 속성 관리 |
| | 정산·프로모션 | 수수료 설정 · 정산 관리 · 플랫폼 쿠폰 |
| | 시스템 | 데모 계정 관리 |

**현재 경로 강조**는 `/` 만 완전 일치이고 나머지는 자기 하위 경로까지다. `/products/new` 는 "상품 관리"를 켠다. 여러 개가 맞으면 가장 긴 것이 이긴다.

**페이지 헤더 규약** — 모든 콘솔 화면은 `PageHeader` 로 시작한다.

```tsx
<PageHeader title="주문 관리" description="…" actions={<Button/>} filters={<OrderFilters/>} />
```

제목(`<h1>`)과 설명이 왼쪽, 액션 버튼이 오른쪽, 필터는 그 아래 자기 영역이다. 훅을 쓰지 않는 서버 렌더 컴포넌트라 콘솔 화면의 LCP 요소가 클라이언트 경계 뒤로 넘어가지 않는다.

**메뉴가 가리키는 화면 20개는 아직 껍데기다.** 죽은 링크 대신 실제 라우트를 두고, 각 도메인 TASK 가 파일을 그대로 대체한다. 라우트 상태(`loading` · `not-found` · `error`)도 셸 안에 있어 404 에서도 사이드바가 남는다.

### 관리자 트리 조작 규약 (`/categories`)

콘솔의 트리는 **드래그를 쓰지 않는다.** 키보드 경로가 어차피 필수이고(QUALITY-GATES U5),
드래그를 넣으면 같은 뮤테이션에 입력 경로가 둘 생긴다. 근거는 TASK-0029 4장.

| 키 | 동작 |
| --- | --- |
| `↑` `↓` `Home` `End` | 보이는 노드 사이 이동 (접힌 하위는 건너뛴다) |
| `←` `→` | 접고 펴기, 상위·첫 하위로 |
| `Alt+↑` `Alt+↓` | 형제 사이 순서 이동 |
| `Alt+←` `Alt+→` | 상위로 꺼내기 · 이전 형제의 하위로 넣기 |

**트리는 탭 정지 하나다**(WAI-ARIA 트리 패턴). 그래서 행 안에는 포커스 가능한 요소를 두지 않고,
수정·이동·비활성화·삭제는 트리 밖 **작업 막대**의 버튼이 맡는다. 포인터와 키보드가 같은 핸들러를
쓴다.

반영 시점은 조작에 따라 다르다 — **이동·정렬은 즉시**(실패하면 원위치), **이름·슬러그는 저장
버튼**. 다른 콘솔 트리 화면도 이 규약을 따른다.

### 속성 관리 규약 (`/attributes`)

D-005 가 눈으로 확인되는 화면이다. 관리자가 정의를 하나 추가하면 **옆의 미리보기가 곧 판매자가
채울 폼**이 된다 — 배포가 끼지 않는다. 근거는 TASK-0031 4장.

**레이아웃은 두 열이다.** 왼쪽이 목록, 오른쪽이 편집 폼과 미리보기. `lg` 미만에서는 세로로 쌓이고
읽는 순서는 같다.

| 영역 | 내용 |
| --- | --- |
| 상단 | 카테고리 선택 + `속성 추가` |
| 왼쪽 | 이 카테고리에 적용되는 속성 표 — 상속분 포함, 한 벌 |
| 오른쪽 위 | 추가·수정 폼 (열려 있을 때만) |
| 오른쪽 아래 | 상품 등록 폼 미리보기 |

**카테고리 선택은 트리가 아니라 경로 셀렉트다.** 여기서 카테고리는 편집 대상이 아니라 필터이므로,
`/categories` 의 트리를 다시 그리면 이 화면에서 쓸 수 없는 조작이 전부 따라온다. 구조는 라벨이
나른다 — `여성 › 아우터 › 코트`. 비활성 카테고리도 목록에 남는다(정의는 여전히 살아 있다).

**목록은 한 벌이고 상속분을 접지 않는다.** 이 순서가 곧 생성될 폼의 필드 순서이므로, 구역을
나누면 화면과 실제 폼이 어긋난다. 대신 각 행이 출처를 이름으로 밝히고, 상속된 행에는 수정 버튼
대신 **`{카테고리} 에서 수정`** 이 들어간다 — 누르면 선택이 그 카테고리로 옮겨 간다.

**`식별자`와 `형식`은 만들 때만 입력이다.** 둘 다 이미 저장된 상품 값의 의미를 바꾼다. 수정
화면에서는 비활성 입력이 아니라 **글자**로 보여 준다 — 비활성 컨트롤은 탭 순회에서 빠져 키보드
사용자가 값을 읽을 수 없다.

**편집 폼은 다이얼로그가 아니다.** 모달이면 미리보기를 가려서 "입력하면서 결과를 본다"가 성립하지
않는다. 모달로 남는 것은 **삭제 확인과 버전 충돌** — 편집이 아니라 답을 요구하는 질문뿐이다.

반영 시점은 `/categories` 와 같은 규약이다 — **순서 이동과 검색 필터 토글은 즉시**, **폼은 저장
버튼**. 다만 속성에는 원자적 순서 변경 엔드포인트가 없어 이동이 요청 두 번이므로, 실패하면
원위치시키는 대신 **목록을 다시 읽어** 서버가 실제로 들고 있는 순서를 보여 준다.

## 반응형

### 브레이크포인트

Tailwind 기본값을 그대로 쓴다. 검증 뷰포트(P3 게이트)와 브레이크포인트는 별개다.

| 이름 | 폭 | 대표 기기 |
| --- | --- | --- |
| (기본) | ~639 | 모바일 |
| `sm` | 640 | 큰 모바일 |
| `md` | 768 | 태블릿 |
| `lg` | 1024 | 작은 노트북 |
| `xl` | 1280 | 데스크톱 |
| `2xl` | 1536 | 대형 모니터 |

**검증은 360 / 768 / 1440px** 세 지점에서 한다. 브레이크포인트 전부를 확인하는 것이 아니라, 각 구간의 대표값을 본다.

| 앱 | 방향 |
| --- | --- |
| `apps/shop` | **모바일 퍼스트** — 커머스 트래픽의 대부분이 모바일이다 |
| `apps/seller` / `apps/admin` | **데스크톱 퍼스트** — 관리 작업은 큰 화면이 기본이다 |

### 밀도 × 뷰포트 (핵심)

`apps/shop` 의 밀도 3단계는 **뷰포트와 곱해진다.** 360px 에서 맥시멀 6열이면 카드 하나가 55px 라 성립하지 않는다.

**열 수** — 밀도와 브레이크포인트의 2차원 매트릭스

| | ~639 | 768 (`md`) | 1280+ (`xl`) |
| --- | --- | --- | --- |
| 1 미니멀 | 1열 | 2열 | 3열 |
| 2 표준 | 2열 | 3열 | 4열 |
| 3 맥시멀 | 2열 | 4열 | 6열 |

**간격·폰트 배율** — 역시 뷰포트별로 다르다. 모바일에서 미니멀의 넓은 여백은 화면 낭비이고, 맥시멀의 축소 배율은 글자를 못 읽게 만든다. 모바일에서는 세 단계의 배율 차이를 데스크톱보다 좁힌다 — `--space-unit` 의 1↔3 격차가 모바일 1.5px, 데스크톱 3px 이다.

| 밀도 | 구간 | `--space-unit` | `--font-scale` | `--radius-scale` | `--density-cols` | `--space-gutter` |
| --- | --- | --- | --- | --- | --- | --- |
| 1 미니멀 | ~767 | 5px | 1.02 | 1.25 | 1 | 20px |
| | 768~1279 | 6px | 1.05 | 1.25 | 2 | 36px |
| | 1280~ | 6px | 1.05 | 1.25 | 3 | 48px |
| 2 표준 | ~767 | 4px | 1.00 | 1.00 | 2 | 16px |
| | 768~1279 | 4px | 1.00 | 1.00 | 3 | 24px |
| | 1280~ | 4px | 1.00 | 1.00 | 4 | 32px |
| 3 맥시멀 | ~767 | 3.5px | 0.98 | 0.75 | 2 | 14px |
| | 768~1279 | 3px | 0.95 | 0.75 | 4 | 18px |
| | 1280~ | 3px | 0.95 | 0.75 | 6 | 24px |

`--space-gutter` 는 `--space-unit` × 4(모바일) / × 6(md) / × 8(xl) 이다. 360px 맥시멀에서 카드 폭은 `(360 − 14×2 − 14) ÷ 2 = 159px` 로 성립한다.

**표시 항목은 밀도만 따른다.** 브랜드·평점·판매량을 보여줄지는 뷰포트와 무관하다. 여기까지 2차원으로 만들면 조합이 9개가 되어 관리가 안 된다. 모바일에서 열 수를 줄이면 카드가 커지므로 맥시멀 정보도 들어갈 자리가 생긴다.

**카드 내부 레이아웃은 컨테이너 쿼리**로 자기 폭에 반응하게 한다. 열 수가 몇이든 알아서 맞으므로 미디어 쿼리로 조합을 나열하지 않아도 된다.

### 터치 타깃 하한

맥시멀 밀도에서 배율이 계속 줄면 버튼을 누를 수 없게 된다. **밀도 배율에 하한을 두어 인터랙티브 요소의 실제 크기가 최소 44×44px 를 유지**하게 한다. 시각적으로 작아 보이더라도 터치 영역은 패딩으로 확보한다.

하한은 각 컨트롤 토큰 안의 `max()` 가 담당한다. 컴포넌트가 기억해야 하는 규칙이 아니라 토큰 자체의 성질이다.

```css
--spacing-control-sm: max(var(--touch-min), calc(var(--space-unit) * 8));
--spacing-control-md: max(var(--touch-min), calc(var(--space-unit) * 11));
--spacing-control-lg: max(var(--touch-min), calc(var(--space-unit) * 14));
```

| 밀도 × 구간 | `control-sm` | `control-md` | `control-lg` |
| --- | --- | --- | --- |
| 1 / 모바일 | 44 | 55 | 70 |
| 1 / 데스크톱 | 48 | 66 | 84 |
| 2 / 전 구간 | 44 | 44 | 56 |
| 3 / 모바일 | 44 | 44 | 49 |
| 3 / 데스크톱 | 44 | 44 | 44 |

시각적으로 더 작아야 하는 요소(아이콘 버튼, 체크박스)는 `touch-target` 유틸리티로 히트 영역만 44px 로 넓힌다.

### 모바일은 별도 페이지를 만들지 않는다

**URL 과 코드베이스는 한 벌**이다. `m.도메인` 이나 `/m/*` 같은 별도 경로를 두지 않는다.

- canonical / alternate 를 쌍방으로 관리해야 하고 하나만 틀려도 색인이 분산된다. Google 은 모바일 우선 색인 기준으로 반응형을 권장한다
- 앱이 이미 3개인데 모바일까지 나누면 최대 6개가 된다
- **밀도 3단계 × 모바일/데스크톱 = 6벌** 유지는 이 프로젝트에서 특히 나쁘다
- 768px 태블릿이 어느 쪽인지 애매해진다

### 모바일 전용 UI 패턴 — 같은 라우트 안에서 분기

반응형이 모든 것을 CSS 로만 늘였다 줄이는 것을 뜻하지는 않는다. 모바일에만 존재하는 패턴이 있고, 이는 **같은 라우트 안에서 컴포넌트를 갈아 끼워** 처리한다.

| 화면 | 모바일 | 데스크톱 |
| --- | --- | --- |
| 상품 상세 | 하단 고정 구매 바 | 우측 정보 패널에 버튼 |
| 검색·카테고리 필터 | 바텀시트로 열림 | 좌측 사이드 패널 상시 노출 |
| 상품 이미지 갤러리 | 스와이프 | 썸네일 클릭 + 확대 |
| 헤더 네비게이션 | 햄버거 | 메가메뉴 |
| seller 주문 목록 | 카드 | 표 |

분기 기준은 **CSS 미디어 쿼리로 두 컴포넌트를 모두 렌더**하지 않는다. 그러면 DOM 이 두 배가 되고 접근성 트리도 중복된다. 뷰포트 훅으로 하나만 마운트한다.

### 콘솔 앱의 모바일 대응 범위

`apps/seller` 의 **주요 3화면만** 모바일에서 제대로 쓸 수 있게 만든다.

| 화면 | 모바일 대응 |
| --- | --- |
| seller `/orders` (주문 목록) | **카드 변환** — 표를 세로 카드로 |
| seller `/orders/[id]` (주문 상세) | **전용 레이아웃** |
| seller 발송 처리 | **전용 레이아웃** — 폰으로 운송장 입력까지 가능 |
| seller 나머지 · admin 전체 | 가로 스크롤 (깨지지만 않으면 통과) |

판매자가 폰으로 주문을 확인하고 발송 처리하는 것은 실제 패턴이다. 반면 관리자 대시보드를 폰으로 보는 경우는 드물다. 관리 화면 30여 개를 전부 카드 변환하는 비용은 얻는 것에 비해 크다.

콘솔은 밀도 2단계 고정이므로(D-033) 밀도 × 뷰포트 문제가 없다.

**셸 자체는 360px 에서도 깨지지 않는다** — 9화면 × 3뷰포트 27조합에서 가로 넘침 0, 44px 미만 터치 타깃 0개(TASK-0019 6.4). 그 위에 올라올 표의 카드 변환은 각 도메인 TASK 가 `TableToCards` 로 한다.

### 표의 모바일 처리

| 방식 | 적용 |
| --- | --- |
| 카드 변환 | seller 주문 목록 (위 3화면) |
| 가로 스크롤 (`overflow-x: auto`) | 그 외 모든 표 |

가로 스크롤 표는 **첫 열을 고정**해 무엇에 대한 행인지 잃지 않게 한다.

### 이미지

`srcset` / `sizes` 로 뷰포트별 적절한 크기를 내려받는다. 밀도 단계에 따라 카드 폭이 달라지므로 `sizes` 에 밀도별 열 수를 반영한다. 종횡비를 고정해 로딩 중 레이아웃 이동(CLS)을 막는다.

## SEO

`apps/shop` 만 대상이며, 판매자·관리자 앱은 **전체 noindex** 다.

| 페이지 | 색인 | 렌더링 | canonical |
| --- | --- | --- | --- |
| 홈 | ✓ | SSG + 재검증 | 자기 자신 |
| 카테고리 | ✓ | SSR | 필터 없는 기본 URL |
| 상품 상세 | ✓ | **ISR** | 자기 자신 |
| 브랜드관 | ✓ | SSR | 자기 자신 |

필터 조합은 속성 정의에 따라 자동 생성되므로 URL 이 수백 개가 된다. 전부 색인되면 중복 콘텐츠가 된다. 상세는 TASK-0102 참조.

## 공통 규칙

- 권한 검사는 아래 [진입 가드 규약](#진입-가드-규약-task-0023)을 따른다. **미들웨어가 아니다.**
- 목록 화면은 **커서 기반 페이지네이션**을 기본으로 한다. 오프셋은 깊은 페이지에서 느려지고 데이터 변동 시 중복·누락이 생긴다.
- 모든 사용자 노출 문구는 메시지 파일에서 가져온다. 하드코딩 금지. (D-014)
- 금액 표시는 통화 정보를 포함한 값에서 포맷한다. 통화 기호·소수 자릿수는 통화 코드에서 나오며 "원"을 붙이지 않는다.

### 진입 가드 규약 (TASK-0023)

**앱에 들어올 수 있는가**는 역할이 정하고, **그 동작을 할 수 있는가**는 퍼미션이 정한다. 앞의 것이 이 문서의 관심사이고, 뒤의 것은 `docs/design/permission-matrix.md` 가 소유한다.

| 앱 | 로그인 필요 | 필요한 역할 | 예외 경로 |
| --- | --- | --- | --- |
| shop | `/mypage` 이하만 | – (BUYER 는 로그인하면 자동으로 갖는다) | 공개 경로 전부 |
| seller | 전 경로 | `SELLER_OWNER` | `/login` · `/no-permission` · `/apply`(로그인만, TASK-0109) |
| admin | 전 경로 | `ADMIN_OPERATOR` · `ADMIN_SUPER` · `DEMO_ADMIN` 중 하나 | `/login` · `/no-permission` |

**판정은 클라이언트 부팅 시점에 한다. Next 미들웨어를 쓰지 않는다.** refresh 쿠키를 심는 것은 앱이 아니라 **API 오리진**이고 `Domain` 이 없으므로(D-218 · TASK-0022 4장), 앱으로 가는 요청에는 그 쿠키가 실리지 않는다 — 미들웨어가 읽을 것이 없다. 대신 앱이 뜨면서 `POST /api/v1/auth/refresh` 를 한 번 부르고 그 결과로 판정한다. 쿠키의 존재만 보는 것보다 정확하다: 만료·폐기된 세션도 걸러지고 역할까지 함께 온다.

```
익명            → /login?next=<원래 경로>
로그인 · 역할 없음 → /no-permission
로그인 · 역할 있음 → 그대로
```

`next` 는 **`/` 로 시작하고 `//` 로 시작하지 않는 앱 내부 경로만** 받는다. 다른 값은 무시하고 홈으로 보낸다 — 오픈 리다이렉트를 막는 것은 콜백의 오리진 허용 목록(TASK-0021)과 같은 이유다.

**화면의 판정은 서버 판정을 대신하지 않는다.** API 는 매 요청 퍼미션 가드를 거치므로, 화면 가드를 우회해도 403 이다. 화면 가드가 있는 이유는 보안이 아니라 **빈 화면과 403 대신 다음 행동을 보여주기 위해서**다.

**권한 없는 조작은 숨기지 않고 비활성 + 사유**로 보여준다 — 기능이 있다는 것을 알리는 것이 데모의 목적이다(TASK-0023 4장). 비활성은 `aria-disabled` 이고 네이티브 `disabled` 가 아니다 — 탭으로 닿지 못하면 왜 못 누르는지 알 수 없다.

### 커서 페이지네이션 규약

| 항목 | 규약 |
| --- | --- |
| 응답 형태 | `{ items, nextCursor }`. `nextCursor: null` 이 마지막 페이지 |
| 커서 값 | 정렬 키 상의 **위치**를 가리키는 불투명 문자열. 클라이언트는 해석하지 않고 그대로 되돌려준다 |
| 첫 페이지 | 커서 `null` |
| 빈 페이지 | `items: []` + `nextCursor` 가 있는 응답은 정상이다. 필터가 걸린 키셋 스캔에서 나온다 |
| 이전 페이지 | **서버가 주지 않는다.** 클라이언트가 방문한 커서를 스택으로 들고 있는다 (`useCursorPagination`) |
| 정렬·필터 변경 | 커서는 그 정렬 안에서만 의미가 있으므로 **스택을 리셋**하고 첫 페이지로 돌아간다 |
| 화면별 이동 수단 | 상품 목록은 무한 스크롤(`useInfiniteScroll`), 콘솔 표는 이전/다음(`Pagination`) |
| 오프셋 | 쓰지 않는다. "3페이지로 점프"가 필요해 보이면 필터·정렬로 좁히는 쪽을 먼저 검토한다 |

한 행이 목록 앞쪽에 추가돼도 이미 지나온 커서 뒤의 페이지는 그대로다 — 오프셋이라면 모든 행이 한 칸씩 밀려
1페이지 마지막 행이 2페이지 첫 행으로 다시 나온다. 이것이 커서를 기본으로 삼는 이유다.
